## KQ1. Multi-tenancy: tenancy models, tenant context, isolation enforcement (AWS, Microsoft, Citus, Salesforce, PostgreSQL RLS)

### Takeaway
Every authoritative source converges on the same three-way spectrum — dedicated resources per tenant (AWS "silo" / Microsoft "database-per-tenant" or "standalone"), shared resources with a tenant-identifier column (AWS "pool" / Microsoft "sharded multitenant"), and mixes of the two (AWS "bridge" / Microsoft "hybrid") — and all agree the choice is driven by compliance, noisy-neighbour risk, per-tenant cost, per-tenant restore, and schema-customisation needs rather than by application function. In a pooled schema the tenant identifier must be in every tenant-scoped table (and, for sharded/distributed designs, in the primary and foreign keys); row-level security is the database-native enforcement mechanism, but Microsoft notes many teams avoid it because of the burden of propagating tenant identity to every query, and PostgreSQL documents covert-channel and race-condition leak risks.

### Cited Findings

**AWS SaaS Lens (Well-Architected), publication date April 4, 2023 — authority 5**
- "Tenant isolation is one of the foundational topics that every SaaS provider must address… Crossing this boundary in any form would represent a significant and potentially unrecoverable event for a SaaS business." "Regardless of how the isolation is implemented, each SaaS architecture needs to ensure that it has put in place the constructs that are needed to ensure that each tenant's resources have been effectively isolated." — [SaaS Lens: Tenant Isolation](https://docs.aws.amazon.com/wellarchitected/latest/saas-lens/tenant-isolation.html) (2023-04-04)
- Silo model: "tenants are provided dedicated resources… perhaps each tenant of your system has a separate database… a silo environment still relies on a shared identity, onboarding, and operational experience where all tenants are managed and deployed via a shared construct. This differentiates SaaS from a managed service model." Pool model: "tenants share resources. This is the more classic notion of multi-tenancy where tenants rely on shared, scalable infrastructure to achieve economies of scale, manageability, agility." Bridge model: "many systems have a mixed mode where some of the system is implemented in a silo model and some is in a pooled model… The regulatory profile of a service's data and its noisy neighbor attributes might steer a microservice to a silo model. Meanwhile the agility, access patterns, and cost profile of another microservice could tip it toward a pool model." — [SaaS Lens: Silo, Pool, and Bridge Models](https://docs.aws.amazon.com/wellarchitected/latest/saas-lens/silo-pool-and-bridge-models.html) (2023-04-04)

**Microsoft, "Multitenant SaaS Patterns – Azure SQL Database", ms.date 2025-08-21 (page updated 2026-08-27) — authority 5**
- "A tenancy model determines how each tenant's data is mapped to storage. Your choice of tenancy model affects application design and management. Switching to a different model later is sometimes costly." Assessment criteria: scalability (tenants, storage per tenant, aggregate, workload), tenant isolation ("Data isolation and performance (whether one tenant's workload affects others)"), per-tenant cost, development complexity, operational complexity ("Restoring a tenant", schema management, DR), customizability. — [Multitenant SaaS Patterns – Azure SQL Database](https://learn.microsoft.com/en-us/azure/azure-sql/database/saas-tenancy-app-design-patterns) (2025-08-21)
- Models: (C) standalone single-tenant app + single-tenant DB — "greatest database isolation… the most expensive solution from an overall database cost perspective"; (D) multitenant app with database-per-tenant — "strong tenant isolation… the schema for any one given database can be customized"; elastic pools "cheaper than requiring each database to be large enough to accommodate the usage peaks"; management features "designed to manage large numbers of databases at scale, such as well over 100,000 databases"; per-tenant point-in-time restore "has no impact on other tenants"; (E/F/G) multitenant databases — "The schema of a multitenant database must have one or more tenant identifier columns… A multitenant database necessarily sacrifices tenant isolation… During development, ensure that queries never expose data from more than one tenant. SQL Database supports row-level security, which can enforce that data returned from a query be scoped to a single tenant." "the Azure system has no built-in way to monitor or manage the use of these resources by an individual tenant. Therefore, the multitenant database carries an increased risk of encountering noisy neighbors." "potentially millions of tenants could be stored in a single database." (G) sharded multitenant — "A catalog is required in which to maintain the mapping between tenants and databases"; "The SQL Database split/merge application requires that the schema includes the sharding key, which typically is the tenant identifier. The tenant identifier is the leading element in the primary key of all sharded tables." (H) hybrid — "all databases have the tenant identifier in their schema… Yet in practice some of these databases contain only one tenant… At any time, you can move a particular tenant to its own multitenant database." (same URL)
- Comparison table (verbatim rows): Scale — Standalone "Medium (1-100s)", DB-per-tenant "High (1-100,000s)", Sharded MT "Unlimited (1-1,000,000s)"; Tenant isolation — High / High / "Low; except for any single tenant (that is alone in an MT database)"; DB cost per tenant — "High; is sized for peaks" / "Low; pools used" / "Lowest, for small tenants in MT databases"; Performance monitoring — "Per-tenant only" / "Aggregate + per-tenant" / "Aggregate; although is per-tenant only for singles"; Development complexity — Low / Low / "Medium; due to sharding"; Operational complexity — "Low-High. Individually simple, complex at scale" / "Low-Medium" / "Low-High. Individual tenant management is complex". (same URL)

**Microsoft Azure Architecture Center, "Architectural approaches for storage and data in multitenant solutions", ms.date 2026-08-21 — authority 5**
- Conditions that force isolation or grouping: "Tenants need to use their own encryption keys; Tenants have individual backup and restore policies; Tenants need to have their data stored in different geographical locations." — [Architectural approaches for storage and data in multitenant solutions](https://learn.microsoft.com/en-us/azure/architecture/guide/multitenant/approaches/storage-data) (2026-08-21)
- Shared multitenant database: "highest density of tenants to infrastructure, so it tends to come at the lowest financial cost"; drawbacks: scale limits, noisy neighbors (mitigate with Throttling / Rate Limiting patterns), per-tenant metering, differing tenant requirements, "tenant-level schema customization is difficult". Sharding "can scale to large numbers of tenants… Sharding also makes it difficult to support tenant-level configuration differences and to enable customers to provide their own encryption keys." Dedicated databases per tenant: isolation and customization, higher cost, "It's important to use automated deployment approaches when you provision databases for each tenant." (same URL)
- Antipatterns for relational databases: "Table-based isolation. When you work within a single database, avoid creating individual tables for each tenant… Instead, consider using a single set of multitenant tables with a tenant identifier column." "Column-level tenant customization. Avoid schema updates that only apply to a single tenant… consider revising your data model to track custom data for each tenant in a dedicated table." "Manual schema changes… Track the schema version that you use for each tenant in a dedicated database or lookup table." "Version dependencies… ensure that your application version is backwards-compatible with at least one previous schema version, and sequence destructive schema changes across multiple versions." (same URL)
- On RLS: "When you use row-level security, you need to ensure that the user's identity and tenant identity are propagated through the application and into the data store with each query. This approach can be complex to design, implement, test, and maintain. Many multitenant solutions don't use row-level security because of those complexities." Tenant-level encryption: Always Encrypted (SQL) / customer-managed keys (Cosmos DB). Tenant lifecycle: "In a shared database, restoring a single tenant might require you to restore the database to a separate resource and selectively recover that tenant's data… Automate tenant onboarding, migration, data retention, and offboarding processes." Deployment Stamps: "it's a good practice to create deployment stamps. This recommendation applies even when you use a multitenant database or sharded databases within a stamp." (same URL)

**Citus (PostgreSQL extension) docs 13.0.1, "Multi-tenant Applications", n.d. — authority 4**
- Rationale for tenant-id distribution: "queries usually always request information for one tenant at a time, not a mix of tenants"; therefore "we must ensure all tables have a company_id column." Composite keys: `PRIMARY KEY (company_id, id)` and `FOREIGN KEY (company_id, campaign_id) REFERENCES campaigns (company_id, id)` because "Citus requires that primary and foreign key constraints include the distribution column", which also makes constraints cheaper since "only a single node has to be checked to guarantee them." Co-location of a tenant's rows lets Citus support "joins, key constraints and transactions efficiently" when `WHERE company_id = :value` is on every table in the query. Shared lookup data (e.g. `geo_ips`) becomes a reference table "replicated across all worker nodes" so joins incur "no network traffic… at query time." — [Citus: Multi-tenant Applications](https://docs.citusdata.com/en/stable/use_cases/multi_tenant.html) (n.d.)

**PostgreSQL 18 manual, "Row Security Policies", n.d. (PG 18 released 2025-09-25) — authority 5**
- "When row security is enabled on a table (with ALTER TABLE ... ENABLE ROW LEVEL SECURITY), all normal access to the table… must be allowed by a row security policy… If no policy exists for the table, a default-deny policy is used." Permissive policies combine with OR, restrictive with AND. "Superusers and roles with the BYPASSRLS attribute always bypass the row security system… Table owners normally bypass row security as well, though a table owner can choose to be subject to row security with ALTER TABLE ... FORCE ROW LEVEL SECURITY." — [PostgreSQL: Row Security Policies](https://www.postgresql.org/docs/current/ddl-rowsecurity.html) (n.d.)
- Leak risks: "Referential integrity checks, such as unique or primary key constraints and foreign key references, always bypass row security to ensure that data integrity is maintained. Care must be taken when developing schemas and row level policies to avoid 'covert channel' leaks of information through such referential integrity checks." Policies that consult other tables "can create race conditions that could allow information leakage if care is not taken" (READ COMMITTED example). Only `LEAKPROOF` functions may be evaluated before the policy check. Performance: policies that "consider only the current values in the row… This is the simplest and best-performing case." `row_security = off` makes a query error rather than silently filter (for pg_dump). (same URL)

**Salesforce Architects, "Platform Multitenant Architecture", n.d. — authority 5**
- "The heart of the platform's software architecture is its multitenant, metadata-driven design." Objects and fields are rows in metadata tables (MT_Objects, MT_Fields), not physical tables; all org-specific data sits in a single MT_Data table with flex "Value" columns stored as variable-length strings; indexes, uniqueness and relationships are implemented via pivot tables (MT_Indexes, MT_Unique_Indexes, MT_Relationships, MT_Fallback_Indexes, MT_Clob). "Every org-specific record in shared database tables has an OrgID." Data, metadata and pivot tables are "physically partitioned by OrgID using native database partitioning mechanisms." Rationale: managing definitions "as metadata rather than actual database structures" lets schema change happen online without blocking other orgs; metadata caching is essential because "frequent metadata access would prevent the service from scaling." — [Salesforce: Platform Multitenant Architecture](https://architect.salesforce.com/fundamentals/platform-multitenant-architecture) (n.d.)

### Conflicts between sources
- **RLS as the isolation mechanism**: Microsoft's Azure SQL article and the PostgreSQL manual present row-level security as the way to scope pooled data to one tenant, while Microsoft's Architecture Center states "Many multitenant solutions don't use row-level security because of those complexities." The AWS whitepaper tenet (search-only) that "isolation enforcement should not be left to service developers" pushes toward enforced mechanisms (RLS, IAM-scoped credentials) rather than hand-written `WHERE tenant_id = ?` filters. Resolution: both agree the tenant identity must reach the database on every request; they differ on whether to enforce it in the engine or the application.
- **Where tenant_id belongs**: Citus requires `tenant_id` in every primary *and* foreign key (distribution constraint); Microsoft requires it only as the leading PK element on sharded tables; Salesforce uses OrgID as a partition key on generic tables. These are implementation-specific, not contradictory, but a framework must state which it prescribes.

### Inferences
- The shared vocabulary allows a framework to prescribe: silo = dedicated DB (or schema) per tenant with a tenant catalog; pool = shared tables with a NOT NULL `tenant_id` column; bridge = pool by default with the ability to move a tenant to a silo (Microsoft's hybrid), which requires `tenant_id` to be present even in single-tenant databases.
- Because referential-integrity checks bypass RLS (PostgreSQL), unique constraints in a pooled schema should include `tenant_id` so that a uniqueness violation cannot reveal another tenant's value — this is consistent with Citus's composite-key guidance.
- Schema-per-tenant (PostgreSQL schemas) is not recommended by any fetched source; Microsoft explicitly lists "table-based isolation" within one database as an antipattern and warns about tracking schema versions per tenant, which is the main operational cost of schema-per-tenant.

### Prescriptions (labelled)
- **MANDATORY** — Every tenant-scoped table in a pooled/sharded database carries a tenant identifier column (Microsoft: "must have one or more tenant identifier columns"; Citus: "all tables have a company_id column").
- **MANDATORY** — Tenant identity is propagated to the data layer on every request and enforced there (Microsoft RLS guidance; AWS tenet that enforcement is not left to developers).
- **RECOMMENDED** — Include `tenant_id` in primary keys (leading) and in unique/foreign keys for sharded or distributed designs (Microsoft split/merge requirement; Citus requirement; PostgreSQL covert-channel warning).
- **RECOMMENDED** — Keep a tenant catalog (tenant → database/shard) and automate onboarding/offboarding/restore; version the schema per database (Microsoft).
- **RECOMMENDED** — Avoid table-per-tenant and column-per-tenant customisation; model tenant custom data in a dedicated table (Microsoft antipatterns) or metadata-driven storage (Salesforce).
- **OPTIONAL/CONTEXTUAL** — Silo (DB-per-tenant) when tenants need their own encryption keys, backup policy, residency, or regulatory isolation (Microsoft; AWS).

### Gaps
- The AWS whitepaper text could not be fetched (redirects to SaaS Lens landing page); its silo/pool/bridge definitions were taken from the SaaS Lens, which is current.
- No fetched source gave quantitative RLS performance measurements; PostgreSQL only gives qualitative guidance.
- Schema-per-tenant migration burden is inferred from Microsoft's schema-versioning guidance; no source discusses PostgreSQL schemas per tenant explicitly.

## KQ2. Multi-company inside one tenant (ERP legal entities, intercompany, consolidation)

### Takeaway
ERP vendors model a company/legal entity/subsidiary as a first-class record that (a) acts as the posting boundary for every transaction, (b) is often also the data-security boundary (Dynamics 365 `DataAreaId`), (c) owns its own currency/tax nexus/statutory reporting, and (d) is arranged in a hierarchy (NetSuite tree to a root; Dynamics organisational hierarchies; Odoo parent company + branches) used for consolidation, with intercompany transactions posting to two or more entities and being eliminated via dedicated elimination entities/journals.

### Cited Findings
- Dynamics 365 Finance: "A legal entity is an organization that has a registered or legislated legal structure. Legal entities can enter into legal contracts and must prepare statements that report on their performance. A company is a type of legal entity. Currently, companies are the only kind of legal entity that you can create, and every legal entity is associated with a company ID. This association exists because some functional areas in the program use a company ID, or DataAreaId, in their data models. In these functional areas, companies are used as a boundary for data security. Users can access data only for the company that they're currently signed in to." Operating units (cost center, business unit, value stream, department, retail channel) are "used for financial reporting… independently of legal entities." Hierarchies: "you can set up a hierarchy of legal entities for tax, legal, or statutory reporting… Organizations in a hierarchy can share parameters, policies, and transactions… However, shared master data, such as products and address books, applies to the whole organization and can't be overridden for individual organizations." "After an operating unit is added to a hierarchy, the operating unit can't be deleted." Establishments (10.0.48+) add "establishment-level Registration ID validation and immutable storage on invoices." — [Organizations and organizational hierarchies overview](https://learn.microsoft.com/en-us/dynamics365/fin-ops-core/fin-ops/organization-administration/organizations-organizational-hierarchies) (ms.date 2026-04-24)
- NetSuite OneWorld: "NetSuite OneWorld enables you to manage data for a hierarchical structure of separate legal entities (subsidiaries). This structure is organized as a tree that rolls up to a root, or top-level parent subsidiary." "Each subsidiary represents a separate company within your global organization." "the country you define for its address determines the NetSuite edition. It also determines the tax nexus associated with that subsidiary." "Each OneWorld transaction generally posts to a single subsidiary, with the exception of transactions between two or more subsidiaries." "Because intercompany transactions post to two or more subsidiaries, the revenue and expenses must be eliminated at the consolidated level to maintain balanced financials." "you must create elimination subsidiaries for use in balancing consolidated financials. OneWorld uses elimination journal entries, associated with elimination subsidiaries, to maintain this balance." Limit: "250 subsidiaries, including the root subsidiary" (elimination and inactive subsidiaries excluded). — [Subsidiaries in OneWorld](https://docs.oracle.com/en/cloud/saas/netsuite/ns-online-help/section_N268563.html) (n.d.)
- Odoo 18.0: "a company is an individual business entity that operates independently." "Branches represent subdivisions within a company." "Independent subsidiaries should be created as additional companies, not branches." A parent company "cannot be converted into a branch later." Records tied to an entity "are accessible only within that entity"; products and contacts are shared by default across parent and branches but can be restricted via the Company field. "All reports can be generated for the parent company alone or with its branches." — [Odoo 18.0: Companies](https://www.odoo.com/documentation/18.0/applications/general/companies.html) (n.d.)
- Square's Books ledger isolates clients as "shelves" with "secondary indexes… namespaced by shelf ID" — a ledger-level analogue of company scoping. — [Books: an immutable double-entry accounting database service](https://developer.squareup.com/blog/books-an-immutable-double-entry-accounting-database-service/) (2019-10-16)

### Conflicts between sources
- Scope of "shared master data": Dynamics says shared master data (products, address book) "can't be overridden for individual organizations", whereas Odoo lets shared products/contacts be restricted to a company via the Company field. Both agree the default is shared.
- Terminology: Dynamics distinguishes legal entity vs operating unit; NetSuite treats every subsidiary as a legal entity and adds pseudo-entities (elimination subsidiaries); Odoo distinguishes company vs branch. A framework needs its own neutral naming (e.g., `legal_entity` + `org_unit`).

### Inferences
- Two orthogonal identifiers emerge in ERP schemas: `tenant_id` (SaaS customer boundary, KQ1) and `company_id`/`legal_entity_id` (posting and statutory boundary within a tenant). Dynamics' use of `DataAreaId` as both security and posting boundary shows that company_id must be on every transactional table and most setup tables, while master data (party/address book, products) is modelled at the tenant level with optional per-company restriction.
- Intercompany transactions require a transaction model that can reference two companies (NetSuite "post to two or more subsidiaries") plus a consolidation hierarchy table (parent/child subsidiaries with elimination entities) to drive eliminations.

### Prescriptions (labelled)
- **MANDATORY** (for ERP) — Every financial posting carries exactly one `company_id` (NetSuite: "generally posts to a single subsidiary"); intercompany documents are modelled as paired postings per company.
- **RECOMMENDED** — Maintain a company hierarchy (tree to a root) for consolidation and statutory reporting, with elimination entities/journals (NetSuite; Dynamics hierarchies).
- **RECOMMENDED** — Shared master data at tenant level, with optional per-company restriction (Dynamics; Odoo).
- **OPTIONAL/CONTEXTUAL** — Sub-company operating units (branches/establishments) for invoicing identifiers and management reporting (Dynamics establishments; Odoo branches).

### Gaps
- SAP "company code" documentation and Oracle NetSuite's per-subsidiary currency/fiscal-calendar pages were not fetched (help.sap.com not attempted; NetSuite sub-pages not followed). Odoo's inter-company transaction and consolidation pages were not fetched.

## KQ3. Audit trails: patterns, database- vs application-level auditing, tamper evidence, regulatory requirements

### Takeaway
Four layered patterns appear in authoritative sources: (1) audit columns auto-managed by ORMs (Rails `created_at/updated_at`), (2) application/ORM-level history tables (Hibernate Envers revisions, django-simple-history), (3) database-level audit — trigger-based shadow tables (PostgreSQL wiki) or engine audit logs (pgAudit, SQL Server Audit) — and (4) tamper-evident ledgers (SQL Server ledger; QLDB, now retired). Every database-level source admits superusers/sysadmins can tamper with the audit unless the audit lives outside their control; only cryptographic ledgers claim detection of DBA tampering. Regulations (21 CFR Part 11) make secure, time-stamped, non-obscuring audit trails retained as long as the record mandatory for regulated electronic records.

### Cited Findings

**Audit columns and ORM-level history**
- Rails: "Active Record automatically timestamps create and update operations if the table has fields named created_at/created_on or updated_at/updated_on." "Timestamps are in UTC by default." Disable via `config.active_record.record_timestamps = false`. — [ActiveRecord::Timestamp (Rails 8.1.4.1)](https://api.rubyonrails.org/classes/ActiveRecord/Timestamp.html) (n.d.)
- Hibernate Envers: "an extension to Hibernate ORM that provides an easy way to add auditing / versioning for entities." "Much like source code version control, Envers uses the concept of revisions. A revision identifies the full set of changes to audited entity fields which occurred within a given transaction." Annotate with `@Audited`; Envers builds "the necessary historical audit tables"; `AuditReader` queries an entity at a revision and "revision metadata specifying when a change occurred, along with additional custom attributes you have stored on the revision entity." Latest stable line 7.4. — [Hibernate Envers](https://hibernate.org/orm/envers/) (n.d.)
- django-simple-history (3.13.0, 2026-07-22): "django-simple-history stores Django model state on every create/update/delete"; supports `history_user` set by middleware, `history_change_reason`, an index on `history_date`, and `as_of` queries on models and querysets. — [django-simple-history docs](https://django-simple-history.readthedocs.io/en/latest/) (2026-07-22)

**Trigger-based shadow/history table**
- PostgreSQL wiki "Audit trigger 91plus" (last edited 4 November 2017): records row values as hstore ("For UPDATEs, it records only changed fields"), action type I/U/D/T, client IP/port, session user, transaction/statement/wall-clock timestamps, top-level statement text, transaction ID, application_name, schema/table by OID and name; `audit.audit_table(target_table, audit_rows, audit_query_text, excluded_cols)`; "An UPDATE that only changes ignored columns won't result in an audit record being created at all." Limitations: cannot track SELECTs, DDL, or catalog changes; "Changes by the table owner and superusers are tracked, but can be trivially tampered with." Recommendation: "your app must not connect with a superuser role and must not own the tables it uses"; app role gets at most USAGE on the audit schema and SELECT on `audit.logged_actions`. — [PostgreSQL wiki: Audit trigger 91plus](https://wiki.postgresql.org/wiki/Audit_trigger_91plus) (2017-11-04)

**Database engine audit logging**
- pgAudit: "provides detailed session and/or object audit logging via the standard PostgreSQL logging facility"; `log_statement = all` "does not provide the level of detail generally required for an audit"; "The standard logging facility shows what the user requested, while pgAudit focuses on the details of what happened while the database was satisfying the request." Classes: READ, WRITE, FUNCTION, ROLE, DDL, MISC, MISC_SET; session vs object auditing (object auditing via `pgaudit.role`). Goal: logs "often required to comply with government, financial, or ISO certifications." Caveats: "it is possible for pgAudit to generate an enormous volume of logging"; "It is not possible to reliably audit superusers with pgAudit"; "Audit logging is best-effort and not transactional" (entries may be lost on crash, and a statement may be logged though its transaction rolls back). Supports PostgreSQL 14+. — [pgAudit README (GitHub)](https://github.com/pgaudit/pgaudit) (n.d.)
- SQL Server Audit (ms.date 2026-04-15): server audit + server/database audit specifications built on Extended Events; targets file, Windows Security log, Application log; "There are several levels of auditing for SQL Server, depending on government or standards requirements for your installation." Tamper caveats: "Principals in the sysadmin role can tamper with any audit component, and principals in the db_owner role can tamper with audit specifications in a database." Recommendations: restrict file ACLs; "generate audit reports from a separate instance of SQL Server… to which only Audit Administrators or Audit Readers have access"; `ON_FAILURE = SHUTDOWN` option; "Due to performance constraints, tempdb and temporary tables aren't audited." — [SQL Server Audit (Database Engine)](https://learn.microsoft.com/en-us/sql/relational-databases/security/auditing/sql-server-audit-database-engine) (2026-04-15)

**Tamper-evident ledgers**
- SQL Server ledger (ms.date 2025-08-07; SQL Server 2022+, Azure SQL): "Ledger helps protect data from any attacker or high-privileged user, including database administrators (DBAs), system administrators, and cloud administrators." Mechanism: rows "cryptographically SHA-256 hashed using a Merkle tree… The result is a root hash that forms a block. The block is then SHA-256 hashed… along with the root hash of the previous block… That hashing forms a blockchain." Database digests "can be periodically generated and stored outside the database in tamper-proof storage, such as Azure Blob Storage configured with immutability policies, Azure Confidential Ledger or on-premises WORM storage devices." ### Conflicts between sources
- **Superuser tamper-resistance**: PostgreSQL wiki trigger, pgAudit, and SQL Server Audit each state that superusers/sysadmins can tamper with or evade the audit; SQL Server ledger claims protection "from any attacker or high-privileged user, including DBAs" but only in the sense of detection on verification, not prevention. Conclusion: no relational engine prevents DBA tampering; tamper *evidence* requires hash-chaining plus off-database digest storage.
- **Transactional vs best-effort audit**: trigger-based shadow tables and Envers write in the same transaction as the change (atomic with the business write), whereas pgAudit is "best-effort and not transactional" and SQL Server Audit can be configured to shut the server down on audit failure. Engine logs capture SELECT/DDL that triggers cannot; triggers capture before/after row images that engine statement logs do not.
- **Application vs database audit**: Envers/django-simple-history capture the application user and reason (history_user, history_change_reason) that database triggers cannot see unless the app passes them (e.g., via session settings); database triggers capture changes made outside the application that ORM auditing misses.

### Inferences
- A layered design satisfies the union of requirements: audit columns for cheap "who/when last", a same-transaction history mechanism (triggers or system-versioning) for before/after values and non-obscuring change history (Part 11 "shall not obscure"), an engine audit log for access/DDL events, and hash-chained digests stored outside DBA control where attestation is required.
- The application must run as a non-owner, non-superuser role so that trigger-based audit cannot be disabled by the app's own credentials (PostgreSQL wiki).

- **MANDATORY** (regulated/financial systems) — Secure, computer-generated, time-stamped audit trail that records create/modify/delete with operator identity; changes must not overwrite prior values; retained at least as long as the record (21 CFR 11.10(e)); access limited to authorised individuals (11.10(d)).
- **MANDATORY** — The application does not connect as superuser or table owner; audit tables are writable only via trigger/engine (PostgreSQL wiki; SQL Server ACL guidance).
- **RECOMMENDED** — `created_at/created_by/updated_at/updated_by` on all business tables, stored in UTC (Rails default; SQL Server temporal UTC).
- **RECOMMENDED** — Same-transaction history capture (trigger shadow table, system-versioned table, or ORM revision table) for before/after values; engine-level audit (pgAudit/SQL Server Audit) for SELECT/DDL/role events, shipped to storage the DBA cannot alter.
- **OPTIONAL/CONTEXTUAL** — Cryptographic ledger tables with digests in immutable storage when auditors require attestation (SQL Server ledger); be aware QLDB is retired (end of support 2025-07-31).

## KQ4. Temporal/history: SQL:2011, vendor implementations, bitemporal theory, SCD, effective dating

### Takeaway
SQL:2011 standardised two orthogonal time dimensions — user-controlled application-time periods (`PERIOD FOR name (start, end)`, `WITHOUT OVERLAPS` keys, `PERIOD` foreign keys, `FOR PORTION OF` updates) and system-controlled system versioning (`PERIOD FOR SYSTEM_TIME`, `GENERATED ALWAYS AS ROW START/END`, `WITH SYSTEM VERSIONING`, `FOR SYSTEM_TIME AS OF|FROM..TO|BETWEEN..AND`), with closed-open periods, and a table using both is bitemporal. Vendors implement different subsets: SQL Server and MariaDB implement system versioning only; Oracle offers both (Temporal Validity for valid time, Flashback Time Travel for transaction time); PostgreSQL 18 (2025-09-25) added `WITHOUT OVERLAPS` and `PERIOD` foreign keys but has no native system versioning. Analytical equivalents are Kimball's SCD types; ERP "effective dating" (Workday) is application-time with out-of-order change semantics.

### Cited Findings

**The standard**
- Kulkarni & Michels (IBM), "Temporal features in SQL:2011", SIGMOD Record Vol. 41 No. 3, September 2012: "SQL:2011 was published in December of 2011… This paper covers the most important new functionality… the ability to create and manipulate temporal tables." History: TSQL2-based proposals "generated considerable controversy… the work on this new part was cancelled in 2001"; the new extensions "are now part of SQL:2011 Part 2, SQL/Foundation." Design choice: "Instead of adding a period type, SQL:2011 adds period definitions as metadata to tables… The period start and end columns are conventional columns" — because adding a type would have to propagate to "JDBC, ODBC, and .NET… ETL products, replication solutions." "SQL:2011 has adopted a closed-open period model… declaring a period definition in a table implies a table constraint that enforces [end > start]." Definitions: "valid time, the time period during which a row is regarded as correctly reflecting reality by the user of the database. transaction time, the time period during which a row is committed to or recorded in the database." — [Temporal features in SQL:2011 (PDF)](https://sigmodrecord.org/publications/sigmodRecord/1209/pdfs/07.industry.kulkarni.pdf) (2012-09)
- Application-time period tables: "the user be put in charge of setting the start and end times… free to assign any time values, either in the past, current or in the future… permitted to update the validity periods of the rows as errors are discovered." Syntax: `PERIOD FOR EPeriod (EStart, EEnd)`; `UPDATE … FOR PORTION OF EPeriod FROM … TO …` splits overlapping rows; `PRIMARY KEY (ENo, EPeriod WITHOUT OVERLAPS)`; `FOREIGN KEY (Edept, PERIOD EPeriod) REFERENCES Dept (DNo, PERIOD DPeriod)` (child period must be contained in the union of matching parent periods); querying uses ordinary predicates or `EPeriod OVERLAPS PERIOD (…)`. (same PDF)
- System-versioned tables: for "applications that must maintain an accurate history of data changes either for business reasons, legal reasons, or both… certain institutions are required by law to preserve historical data." Requirements: "any update or delete of a row must automatically preserve the old state… the system, rather than the user, maintains the start and end times… users be unable to [modify them]… This provides the guarantee that the recorded history of data changes cannot be tampered with, which is critical to meet auditing and compliance regulations." Syntax: `Sys_start TIMESTAMP(12) GENERATED ALWAYS AS ROW START`, `PERIOD FOR SYSTEM_TIME (Sys_start, Sys_end)`, `WITH SYSTEM VERSIONING`. UPDATE "first inserts a copy of the old row with its system-time period end time set to the transaction timestamp"; DELETE "does not actually delete the qualifying rows; instead it changes the system-time period end time." Constraints "need only be enforced on the current system rows. Historical system rows… form immutable snapshots of the past", so PK/FK definitions omit period columns. Queries: `FOR SYSTEM_TIME AS OF`, `FOR SYSTEM_TIME FROM … TO …` (exclusive end), `FOR SYSTEM_TIME BETWEEN … AND …` (inclusive end). "FOR PORTION OF SYSTEM_TIME is not needed (and hence not allowed)." Bitemporal: "A table may be both a system-versioned table and an application-time period table" (example combines `PERIOD FOR EPeriod`, `PERIOD FOR SYSTEM_TIME`, `WITHOUT OVERLAPS` PK, `PERIOD` FK, `WITH SYSTEM VERSIONING`). (same PDF)

**Vendor implementations**
- SQL Server temporal tables (ms.date 2026-08-18; SQL Server 2016+, Azure SQL, Fabric): "a type of user table designed to keep a full history of data changes, allowing point-in-time analysis… called a system-versioned temporal table, because the system manages the period of validity for each row." Two `datetime2` period columns (`ValidFrom`/`ValidTo`), `PERIOD FOR SYSTEM_TIME`, `WITH (SYSTEM_VERSIONING = ON (HISTORY_TABLE = …))`. Timestamps are "the begin time of the current transaction (in the UTC time zone)". "When you run any data modification queries on a temporal table, the Database Engine adds a row to the history table, even if no column values change." `FOR SYSTEM_TIME` sub-clauses: AS OF (`ValidFrom <= t AND ValidTo > t`), FROM…TO (exclusive both ends), BETWEEN…AND (inclusive upper), CONTAINED IN, ALL. "FOR SYSTEM_TIME filters out rows that have a period of validity with zero duration." Use cases: "Auditing all data changes… Reconstructing the state of the data as of any time in the past… Maintaining a slowly changing dimension… Recovering from accidental data changes." Period columns can be `HIDDEN`. — [Temporal tables – SQL Server](https://learn.microsoft.com/en-us/sql/relational-databases/tables/temporal-tables) (2026-08-18). The page describes system time only; no application-time period support is mentioned.
- MariaDB system-versioned tables: "System-versioned tables store the history of all changes, not only data which is currently applicable." "System-versioned tables were first introduced in the SQL:2011 standard." `WITH SYSTEM VERSIONING`; pseudo-columns `ROW_START`/`ROW_END`; `FOR SYSTEM_TIME AS OF | BETWEEN … AND | FROM … TO` plus MariaDB's non-standard `ALL`. `PARTITION BY SYSTEM_TIME` keeps history in HISTORY partitions (rotation by `LIMIT` rows or `INTERVAL`; `AUTO` from 10.9.1). Per-column `WITHOUT SYSTEM VERSIONING` ("Another MariaDB extension"). History removal via `DELETE HISTORY` ("requires a special DELETE HISTORY privilege"); `TRUNCATE` blocked. Transaction-precise versioning (InnoDB, `BIGINT UNSIGNED` transaction IDs, `AS OF TRANSACTION`). Limits: "Versioning clauses cannot be applied to generated (virtual and persistent) columns"; `mariadb-dump` needs `--dump-history` (10.11+) to back up history. — [MariaDB: System-Versioned Tables](https://mariadb.com/docs/server/reference/sql-structure/temporal-tables/system-versioned-tables) (n.d.)
- Oracle Temporal Validity (VLDB Guide 12.2): "The former temporal attribute (hire-date) is called the valid time (VT) while the latter (date entered into the database) is called the transaction time (TT). While the valid time is usually controlled by the user, the transaction-time is system-managed." "A valid-time period consists of two date-time columns specified in the table definition… added during the create table or alter table process" (`PERIOD FOR emp_track_time`). Session visibility via `DBMS_FLASHBACK_ARCHIVE.enable_at_valid_time('CURRENT' | 'ALL' | 'ASOF', ts)`; query `SELECT … FROM employees_temp AS OF PERIOD FOR emp_track_time TIMESTAMP '…'`. Limits: "Temporal validity is not supported with a multitenant container database (CDB)" (12.2). — [Controlling the Validity and Visibility of Data in Oracle Database](https://docs.oracle.com/database/122/VLDBG/control-validity-visibility-data.htm) (n.d.)
- Oracle Flashback Time Travel (Flashback Data Archive), 19c Development Guide: "provides the ability to track and store transactional changes to a table over its lifetime. It is useful for compliance with record stage policies and audit reports." "A Flashback Archive is configured with retention time" (`CREATE FLASHBACK ARCHIVE DEFAULT fla1 TABLESPACE tbs1 QUOTA 10G RETENTION 5 YEAR; ALTER TABLE inventory FLASHBACK ARCHIVE;`), queried with `AS OF TIMESTAMP` and `VERSIONS BETWEEN`; valid-time version queries via `VERSIONS PERIOD FOR user_valid_time`. "By default, Flashback Archive is not enabled for any tables." Reserved column names STARTSCN, ENDSCN, RID, XID, OP, OPERATION; `DROP TABLE` blocked (ORA-55610) while enabled. — [Using Oracle Flashback Technology (19c)](https://docs.oracle.com/en/database/oracle/oracle-database/19/adfns/flashback.html) (n.d.)
- PostgreSQL 18 release notes (released 2025-09-25): "Temporal constraints, or constraints over ranges, for PRIMARY KEY, UNIQUE, and FOREIGN KEY constraints." "Allow the specification of non-overlapping PRIMARY KEY, UNIQUE, and foreign key constraints (Paul A. Jungwirth). This is specified by WITHOUT OVERLAPS for PRIMARY KEY and UNIQUE, and by PERIOD for foreign keys, all applied to the last specified column." Also "Add GiST support function stratnum()". No system-versioning feature appears in the release notes. — [PostgreSQL 18 Release Notes](https://www.postgresql.org/docs/18/release-18.html) (2025-09-25)

**Theory**
- Snodgrass, *Developing Time-Oriented Database Applications in SQL*, Morgan Kaufmann (copyright page "© 2000 by Morgan Kaufmann", ISBN 1-55860-436-7; the text says "This book will have a copyright date of 1999"), free PDF: "Valid time, capturing the history of a changing reality, and transaction time, capturing the sequence of states of a changing table, are orthogonal, and can thus be separately utilized or applied in concert. A table supporting both is termed a bitemporal table." Period representation: "One common representation is termed a closed-closed representation… An alternative is the closed-open representation, in which the second datetime of the pair represents the granule immediately following the last granule… The preferred representation of a period is a closed-open pair of datetimes. Note the niggling +1 and <= that keep popping up with the closed-closed representation." Query taxonomy: "There are three basic kinds of time-oriented statements: Current: now; Sequenced: at each instant of time; Nonsequenced: ignoring time. The trichotomy applies equally well to queries, modification statements, views, and integrity constraints. The most useful is sequenced, for which SQL-92 provides absolutely no help." Chapters cover temporal keys, "Uniqueness Reexamined", referential integrity for state tables, tracking logs (transaction time), temporal partitioning and vacuuming, and bitemporal tables (Ch. 10). — [Snodgrass, tdbbook.pdf](https://www2.cs.arizona.edu/~rts/tdbbook.pdf) (2000/1999)

**Analytical equivalent — Kimball SCD**
- Design Tip #152 (Margy Ross, 2013-02-05): Type 0 "the dimension attribute value never changes, so facts are always grouped by this original value"; Type 1 overwrite; Type 2 add row; Type 3 add column; Type 4 mini-dimension — "A surrogate key is assigned to each unique profile or combination of attribute values in the mini-dimension" (for volatile attributes in large dimensions); Type 5 mini-dimension + type 1 outrigger; Type 6 "a type 2 row with a type 3 column that's overwritten as a type 1"; Type 7 "the fact table contains dual foreign keys for a given dimension" (one to the type-2 row in effect, one to the current row). — [Design Tip #152: SCD Types 0, 4, 5, 6 and 7](https://www.kimballgroup.com/2013/02/design-tip-152-slowly-changing-dimension-types-0-4-5-6-7/) (2013-02-05)
- Type 2 technique page: "Slowly changing dimension type 2 changes add a new row in the dimension with the updated attribute values… A minimum of three additional columns should be added to the dimension row with type 2 changes: 1) row effective date or date/time stamp; 2) row expiration date or date/time stamp; and 3) current row indicator." — [Kimball Techniques: Type 2 Add New Row](https://www.kimballgroup.com/data-warehouse-business-intelligence-resources/kimball-techniques/dimensional-modeling-techniques/type-2/) (n.d.)

**ERP effective dating**
- Workday (Last Updated 2025-05-02): Workday "doesn't require that effective dates be in chronological order" and processes out-of-order changes by effective date, not entry date; a backdated edit is "overwritten" by an existing later-effective edit (e.g., a change effective 2010-05-01 is superseded on 2021-12-01), so the user "must edit again with an effective date after 2021-12-01" to carry a value forward. — [Reference: Out of Order Changes and Effective Dating](https://doc.workday.com/admin-guide/en-us/human-capital-management/compensation/manage-compensation/meq1649709028535.html) (2025-05-02)

### Conflicts between sources
- **Closed-open vs inclusive ends**: SQL:2011, Snodgrass and SQL Server all use closed-open storage, yet SQL Server's `BETWEEN … AND` and SQL:2011's `BETWEEN` include the upper bound while `FROM … TO` excludes it — a query-syntax trap, not a storage conflict. Kimball's SCD Type 2 uses effective/expiration dates without specifying open/closed semantics.
- **What "temporal table" means per vendor**: SQL Server and MariaDB call system-versioned tables "temporal tables" (system time only); Oracle and SQL:2011 treat valid time (application time) as the primary user-facing feature. A framework must name the two dimensions explicitly.
- **Mutability of history**: SQL:2011 and SQL Server forbid user edits of system-period columns; MariaDB permits `DELETE HISTORY` (privileged) and Oracle Flashback purges history past `RETENTION` — history is tamper-resistant but retention-bounded by design.
- **Backdated changes**: SQL:2011 application-time `FOR PORTION OF` splits rows so a backdated change applies only to its interval; Workday's out-of-order semantics let a later-effective edit overwrite a backdated one. Both are "application time", but the merge rule differs; a framework must specify it.

### Inferences
- Application-time rows should be stored as `[valid_from, valid_to)` half-open intervals with a non-overlap constraint per business key (PostgreSQL 18 `WITHOUT OVERLAPS`, SQL:2011) — closed-open avoids the "+1" arithmetic Snodgrass warns about and matches every fetched vendor's internal representation.
- System time is best delegated to the engine where available (SQL Server, MariaDB, Oracle Flashback); on PostgreSQL it must be emulated with triggers/history tables (KQ3) because PG 18 added temporal *constraints* but not system versioning.
- SCD Type 2 is the warehouse rendering of an application-time state table (effective/expiration + current flag); SQL Server explicitly lists "maintaining a slowly changing dimension" as a temporal-table use case, so system-versioned OLTP tables can feed Type 2 dimensions.

### Prescriptions (labelled)
- **MANDATORY** (where history is required by law/audit) — System-time history must be system-maintained and not user-editable (SQL:2011 rationale; 21 CFR 11.10(e)).
- **RECOMMENDED** — Closed-open periods for both valid and system time (SQL:2011; Snodgrass; SQL Server).
- **RECOMMENDED** — Non-overlap constraint on (business key, valid period) and period-aware foreign keys where the engine supports them (SQL:2011 `WITHOUT OVERLAPS`/`PERIOD`; PostgreSQL 18).
- **RECOMMENDED** — Store period timestamps in UTC with transaction-begin semantics (SQL Server).
- **OPTIONAL/CONTEXTUAL** — Bitemporal (both dimensions) only when corrections to past-effective facts must be reconstructable as they were known at the time (insurance/finance examples in Kulkarni & Michels; Snodgrass Ch. 10).
- **OPTIONAL/CONTEXTUAL** — Partition history by system time for retention (MariaDB `PARTITION BY SYSTEM_TIME`; Oracle `RETENTION`).

## KQ5. Change data capture (CDC): log-based vs trigger/query-based, snapshots, schema impact, outbox

### Takeaway
Debezium and the PostgreSQL/SQL Server manuals agree that log-based CDC captures every committed change (including deletes and old row images) with low overhead and "requires no changes to your data model, such as a 'Last Updated' column", whereas custom trigger/timestamp solutions require schema changes and mishandle long-running transactions. The schema prerequisite is a stable row identity: PostgreSQL requires a replica identity (primary key by default) to replicate UPDATE/DELETE, and consumers must be idempotent because delivery after a crash is at-least-once. The outbox pattern makes event publication transactional with the business write via CDC.

### Cited Findings
- Debezium (3.7 features page): "Debezium is a set of source connectors for Apache Kafka Connect." Log-based CDC "Ensures that all data changes are captured"; "Produces change events with a very low delay while avoiding increased CPU usage required for frequent polling"; "Requires no changes to your data model, such as a 'Last Updated' column"; "Can capture deletes"; can capture old record state and transaction metadata. Initial snapshot optional; "support for incremental snapshots, which can be triggered at connector runtime." — [Debezium Features](https://debezium.io/documentation/reference/stable/features.html) (n.d.)
- Debezium FAQ: CDC is "a system that monitors and captures the changes in data so that other software can respond to those changes." Delivery: under normal operation every event exactly once; after a crash "the application sees every event at least once"; duplicates "will always be visible to downstream consuming applications." Schema evolution: "its events have to make sense even as the structure of the tables in the upstream databases change over time" — events are self-describing (payload + schema), and a schema registry "creates a new version of schema only if the schema logically changes." "running a connector may place additional load on the source database." — [Debezium FAQ](https://debezium.io/documentation/faq/) (n.d.)
- PostgreSQL 18 logical decoding: "Logical decoding is the process of extracting all persistent changes to a database's tables into a coherent, easy to understand format… implemented by decoding the contents of the write-ahead log." Slots "persist independently of the connection using them and are crash-safe"; "Only one receiver may consume changes from a slot at any given time." Caution: slots "will prevent removal of required resources even when there is no connection using them… In extreme cases this could cause the database to shut down to prevent transaction ID wraparound… if a slot is no longer required it should be dropped." "A logical slot will emit each change just once in normal operation… in the case of a crash the slot might return to an earlier LSN, which will then cause recent changes to be sent again." — [PostgreSQL: Logical Decoding Concepts](https://www.postgresql.org/docs/current/logicaldecoding-explanation.html) (n.d.)
- PostgreSQL 18 publications: "A published table must have a replica identity configured in order to be able to replicate UPDATE and DELETE operations… By default, this is the primary key, if there is one… If the table does not have any suitable key, then it can be set to replica identity FULL, which means the entire row becomes the key… replica identity FULL should only be used as a fallback." "Tables with a replica identity defined as NOTHING, DEFAULT without a primary key, or USING INDEX with a dropped index, cannot support UPDATE or DELETE operations when included in a publication… Attempting such operations will result in an error on the publisher. INSERT operations can proceed regardless of any replica identity." — [PostgreSQL: Publication](https://www.postgresql.org/docs/current/logical-replication-publication.html) (n.d.)
- SQL Server (ms.date 2025-08-21): custom tracking "by using a combination of triggers, timestamp columns, and additional tables… usually involves a lot of work to implement, leads to schema updates, and often carries a high performance overhead." Benefits of built-in features: "Schema changes aren't required… There's a built-in cleanup mechanism… Change tracking is based on committed transactions. The order of the changes is based on transaction commit time… Custom solutions that use timestamp values must be designed to handle these scenarios." CDC "provides historical change information… captured by using an asynchronous process that reads the transaction log"; Change Tracking "captures the fact that rows in a table were changed, but doesn't capture the data that was changed… synchronous tracking mechanism… far less storage overhead." Feature table: historical data — CDC Yes / Change Tracking No. — [Track Data Changes – SQL Server](https://learn.microsoft.com/en-us/sql/relational-databases/track-changes/track-data-changes-sql-server) (2025-08-21)
- Outbox pattern (Gunnar Morling, Debezium blog, 2019-02-19): dual writes fail because "we cannot have one shared transaction that would span the service's database as well as Apache Kafka" and Kafka "doesn't support to be enlisted in distributed (XA) transactions." "The idea of this approach is to have an 'outbox' table in the service's database"; in the same transaction "a record representing the event to be sent is inserted into that outbox table", and Debezium "tails the transaction log" to publish it. Columns: `id` (unique message id for consumer de-duplication), `aggregatetype` (routes to topic), `aggregateid` ("This id will be used as the key for Kafka messages later on" — preserves per-aggregate ordering), `type`, `payload`. Insert-then-delete trick: the outbox row is deleted immediately, Debezium ignores the DELETE, so the table "will always be empty." Semantics are "at least once"; consumers keep a message log so "any further calls for that same event will be ignored." — [Reliable Microservices Data Exchange With the Outbox Pattern](https://debezium.io/blog/2019/02/19/reliable-microservices-data-exchange-with-the-outbox-pattern/) (2019-02-19)

### Conflicts between sources
- Debezium's features page contrasts log-based CDC with polling and dual-writes, not with trigger-based CDC; SQL Server's page is the source that explicitly criticises trigger/timestamp approaches (overhead, schema changes, commit-order problems). No fetched source defends trigger-based CDC — but KQ3 shows triggers remain the standard way to capture *who* changed data inside the transaction, which log-based CDC cannot see unless the application writes it to a column.
- SQL Server Change Tracking (synchronous, no history) and CDC (asynchronous, with history) are positioned as complementary; Debezium only offers the log-based model.

### Inferences
- Schema prerequisites for CDC: every captured table needs a primary key (or a declared replica identity); without one, PostgreSQL refuses UPDATE/DELETE under a publication, and consumers cannot correlate row versions. This reinforces the KQ1 composite-key guidance and argues against key-less tables.
- Because CDC delivers at-least-once, downstream tables need idempotent upserts keyed on the source PK plus a monotonic version (LSN/commit timestamp).
- An outbox table is a schema-level artefact of the integration layer: `(id, aggregatetype, aggregateid, type, payload[, created_at])`, written in the same transaction as the business row.

### Prescriptions (labelled)
- **MANDATORY** (for CDC-enabled tables) — A primary key or explicit replica identity on every table whose UPDATE/DELETE must be captured (PostgreSQL publication docs).
- **RECOMMENDED** — Prefer log-based CDC over timestamp/trigger polling to avoid schema changes and commit-order bugs (Debezium; SQL Server).
- **RECOMMENDED** — Use the outbox pattern for application events; consumers de-duplicate by message id (Morling).
- **RECOMMENDED** — Monitor and drop unused replication slots to avoid WAL bloat/wraparound (PostgreSQL).
- **OPTIONAL/CONTEXTUAL** — Change Tracking (SQL Server) when only "which rows changed" is needed for sync, not history.

### Gaps
- Oracle GoldenGate and MySQL binlog documentation were not fetched.
- Debezium's PostgreSQL connector page (REPLICA IDENTITY FULL requirement for old-row images in change events) was not fetched; the replica-identity facts come from the PostgreSQL manual.

## KQ6. Soft deletes, erasure, retention and archival

### Takeaway
The strongest practitioner source (Brandur Leach, ex-Heroku/Stripe) argues `deleted_at` soft deletion "probably isn't worth it": every query must filter, foreign keys stop protecting integrity, GDPR purging becomes a cascading nightmare, and undeletes almost never happen; his alternative is a `deleted_record` table holding the deleted row as JSONB (populated by a trigger or `DELETE … RETURNING`). GitLab, by contrast, prefers "mark for deletion" at the aggregate (project/group) level to minimise accidental loss. Regulations set retention floors (SOX 5 years, HIPAA 6 years, PCI 12 months with 3 months online, 21 CFR 11 as long as the record) and GDPR Art. 17 sets erasure ceilings with explicit exceptions for legal obligations and legal claims; the engineering mechanisms are date partitioning (drop/detach partitions), archive tables, and object-storage lifecycle rules.

### Cited Findings
- Brandur Leach, "Soft Deletion Probably Isn't Worth It" (2022-07-19): "The concept behind soft deletion is to make deletion safer, and reversible." Costs: every query needs `deleted_at IS NULL` and forgetting it "can have dangerous consequences"; soft-deleted parents still satisfy foreign keys, so a customer can be "deleted" while its invoices remain live; purging for privacy requires fragile cascading CTEs because "it's generally frowned upon for data to be retained infinitely" (GDPR cited); across Heroku, Stripe and his current employer, "never once, in ten plus years" was soft deletion used to undelete. Alternative: a `deleted_record` table with `original_table`, `original_id` and a `jsonb` `data` column, inserted via a CTE in the same statement as the DELETE; purge with `DELETE FROM deleted_record WHERE deleted_at < now() - '1 year'::interval`. Trade-off: "the process of selecting columns into jsonb isn't easily reversible." — [Soft Deletion Probably Isn't Worth It](https://brandur.org/soft-deletion) (2022-07-19)
- Brandur, "Easy, alternative soft deletion: deleted_record_insert" (2022-12-28): a generic PL/pgSQL `AFTER DELETE` trigger `deleted_record_insert()` inserts `to_jsonb(OLD.*)`, `OLD.id`, `TG_TABLE_NAME` into `deleted_record (id uuid, data jsonb, deleted_at timestamptz, object_id uuid, table_name varchar(200), updated_at timestamptz)`; "no need to include a deleted_at IS NULL predicate in every live query, no foreign key problems"; has "saved ourselves from dozens of bugs"; `deleted_at` now remains on only a couple of core tables. — [deleted_record_insert](https://brandur.org/fragments/deleted-record-insert) (2022-12-28)
- GitLab data-deletion guidelines: two options — "Mark for deletion… identifies data for removal at a future date. This is the preferred approach" vs hard deletion which "Immediately and permanently removes data"; direct calls to `Projects::DestroyService`/`Groups::DestroyService` "can lead to unintended data loss" and should be replaced by `MarkForDeletionService`. The page gives no column-naming or retention-period guidance. — [GitLab: Data deletion guidelines](https://docs.gitlab.com/development/deleting_data) (n.d.)
- GDPR Art. 17(1): erasure "without undue delay" on listed grounds; Art. 17(3): not applicable where processing is necessary "for compliance with a legal obligation which requires processing by Union or Member State law", "for the performance of a task carried out in the public interest", or "for the establishment, exercise or defence of legal claims." — [Art. 17 GDPR (gdpr-info.eu)](https://gdpr-info.eu/art-17-gdpr/) (n.d.)
- Retention floors: SOX 18 U.S.C. 1520 — audit workpapers 5 years ([LII](https://www.law.cornell.edu/uscode/text/18/1520)); HIPAA 45 CFR 164.316(b)(2)(i) — 6 years ([LII](https://www.law.cornell.edu/cfr/text/45/164.316)); PCI DSS 4.0.1 10.5.1 — 12 months, 3 months immediately available ([WithPCI transcription](https://withpci.pages.dev/requirements/10/10.5/10.5.1)); 21 CFR 11.10(e) — audit trail "retained for a period at least as long as that required for the subject electronic records" ([LII](https://www.law.cornell.edu/cfr/text/21/11.10)); GDPR Art. 30 — document "the envisaged time limits for erasure" ([gdpr-info.eu](https://gdpr-info.eu/art-30-gdpr/)).
- PostgreSQL 18 partitioning: "Bulk loads and deletes can be accomplished by adding or removing partitions… Dropping an individual partition using DROP TABLE, or doing ALTER TABLE DETACH PARTITION, is far faster than a bulk operation. These commands also entirely avoid the VACUUM overhead caused by a bulk DELETE." "Seldom-used data can be migrated to cheaper and slower storage media." Retention example: "keep only the most recent 3 years worth of data. At the beginning of each month we will remove the oldest month's data" — `DROP TABLE measurement_y2006m02;` ("requires taking an ACCESS EXCLUSIVE lock on the parent table") or `ALTER TABLE measurement DETACH PARTITION measurement_y2006m02 [CONCURRENTLY];` which "allow further operations to be performed on the data before it is dropped… back up the data using COPY, pg_dump"; CONCURRENTLY needs only SHARE UPDATE EXCLUSIVE. — [PostgreSQL: Table Partitioning](https://www.postgresql.org/docs/current/ddl-partitioning.html) (n.d.)
- Amazon S3 Lifecycle: "Transition actions – These actions define when objects transition to another storage class… Expiration actions – These actions define when objects expire. Amazon S3 deletes expired objects on your behalf. For example, you might to choose to expire objects after they have been stored for a regulatory compliance period." "You can't use a bucket policy to prevent deletions or transitions by an S3 Lifecycle rule." Rules apply to existing and new objects. — [Managing the lifecycle of objects (S3)](https://docs.aws.amazon.com/AmazonS3/latest/userguide/object-lifecycle-mgmt.html) (n.d.)
- Oracle Flashback Time Travel documents "digital shredding (purging history older than a retention period)" as a use of `RETENTION` — [Oracle 19c Flashback](https://docs.oracle.com/en/database/oracle/oracle-database/19/adfns/flashback.html) (n.d.); MariaDB history can be removed with `DELETE HISTORY` or by dropping history partitions — [MariaDB](https://mariadb.com/docs/server/reference/sql-structure/temporal-tables/system-versioned-tables) (n.d.).
- ISO 15489-1:2016 (search-only; iso.org returned 403): the standard "defines the concepts and principles from which approaches to the creation, capture and management of records are developed" and characterises authoritative records by authenticity, reliability, integrity and useability (sections 5.2.2.1-5.2.2.4). — [iTeh catalog entry](https://standards.iteh.ai/catalog/standards/iso/baf32a1d-182a-428d-aca9-74f0e33d01a7/iso-15489-1-2016) (search-only; page body did not load).

### Conflicts between sources
- **Soft delete vs mark-for-deletion**: Brandur argues against row-level `deleted_at`; GitLab prefers marking aggregates for deletion (projects/groups) with later hard deletion. These reconcile as: soft-delete at the aggregate root for a bounded grace period, not as a permanent per-row flag.
- **Retention vs erasure**: GDPR Art. 17 demands erasure "without undue delay" while SOX/HIPAA/PCI/Part 11/VAT rules demand multi-year retention; Art. 17(3) resolves the conflict by exempting legal obligations — the schema must therefore record *which* retention basis applies to a record class (GDPR Art. 30 "time limits for erasure").
- **Immutability vs deletion**: ledgers and system-versioned history are designed never to lose rows, which collides with erasure rights; vendors answer with retention-bounded purge (Oracle `RETENTION`, MariaDB `DELETE HISTORY`) rather than row edits.

### Inferences
- If `deleted_at` is kept, uniqueness must be enforced on live rows only (e.g., a partial unique index `WHERE deleted_at IS NULL`) — this follows from Brandur's FK/uniqueness critique, though no fetched source states the partial-index remedy explicitly.
- Crypto-shredding (encrypting personal data per subject and destroying the key) is the standard reconciliation of immutable history with erasure, but no fetched source discusses it; it should be labelled inference.
- Date-range partitioning on the retention clock (created_at/posted_at) is the mechanism every source implies for cheap retention enforcement (PostgreSQL DETACH/DROP; MariaDB system-time partitions; S3 expiration).

### Prescriptions (labelled)
- **MANDATORY** — A retention schedule per record class, with the legal basis, documented and enforced (GDPR Art. 30; 21 CFR 11.10(c); SOX/HIPAA/PCI floors).
- **MANDATORY** — Erasure requests honoured "without undue delay" except where a legal obligation or legal claim requires retention (GDPR Art. 17).
- **RECOMMENDED** — Avoid pervasive per-row `deleted_at`; hard-delete with a `deleted_record` JSONB archive (Brandur) or mark-for-deletion at aggregate roots with scheduled purge (GitLab).
- **RECOMMENDED** — Partition large time-series/transaction tables by date so retention is a partition DETACH/DROP, archive via COPY/pg_dump before drop (PostgreSQL); mirror with object-storage lifecycle rules (S3).
- **OPTIONAL/CONTEXTUAL** — Legal hold flag that suspends purge for named records; crypto-shredding for immutable stores (inference, no source).

### Gaps
- gov.uk VAT record-keeping notice (6-year VAT retention) returned 404; UK retention period not verified.
- No fetched source covers legal hold mechanics in databases, BigQuery table expiration, or crypto-shredding.
- Official ISO 15489 text could not be opened.

## KQ7. ERP/financial specifics: gapless numbering, fiscal periods, multi-currency, double-entry ledger invariants

### Takeaway
EU VAT law requires invoices to carry "a sequential number, based on one or more series, which uniquely identifies the invoice", and PostgreSQL's manual states plainly that sequence objects "cannot be used to obtain 'gapless' sequences" — so document numbering needs a locked per-series counter, not `nextval`. Every ledger source (Fowler, Modern Treasury, Square, Stripe, Kleppmann) converges on the same invariants: transactions consist of entries that sum to zero (debits = credits) per transaction and per currency, entries/transactions are immutable once posted (corrections are new reversing/adjusting transactions, or archive — never edit/delete), balances are derived from entries, and writes are idempotent and atomic.

### Cited Findings
- EU VAT Directive 2006/112/EC Art. 226 (as amended by 2010/45/EU; UK-archived "Latest available (Revised)" text): invoices must show "(1) the date of issue; (2) a sequential number, based on one or more series, which uniquely identifies the invoice". — [Council Directive 2006/112/EC Article 226 (legislation.gov.uk)](https://www.legislation.gov.uk/eudr/2006/112/article/226) (n.d.; versions 2006-11-28 … 2020-12-31). WebSearch additionally reported that Directive (EU) 2025/516 will require corrective invoices to carry "the sequential number of the invoice being corrected" from 1 July 2030 (search-only; not verified on EUR-Lex).
- PostgreSQL 18 sequence functions: "To avoid blocking concurrent transactions that obtain numbers from the same sequence, the value obtained by nextval is not reclaimed for re-use if the calling transaction later aborts. This means that transaction aborts or database crashes can result in gaps in the sequence of assigned values. That can happen without a transaction abort, too. For example an INSERT with an ON CONFLICT clause will compute the to-be-inserted tuple, including doing any required nextval calls, before detecting any conflict… Thus, PostgreSQL sequence objects cannot be used to obtain 'gapless' sequences." Also "sequence state changes made by setval are immediately visible to other transactions, and are not undone if the calling transaction rolls back." — [PostgreSQL: Sequence Manipulation Functions](https://www.postgresql.org/docs/current/functions-sequence.html) (n.d.)
- Martin Fowler, "Patterns for Accounting" (first draft 24 January 2006): Account — "The value, or balance, of the Account is derived as the sum of all the Accounting Entrys"; Accounting Transaction — "linking together the Accounting Entrys involved in a transfer"; correction strategies via Retroactive Event: Replacement Adjustment "deletes the incorrect Accounting Transactions and creates the correct set" (loses history), Reversal Adjustment — "for each one you post an opposite Accounting Entry to cancel it out" then post the correct ones (keeps history, many offsetting entries), Difference Adjustment — "posts in new entries that represent the difference between the incorrect and correct entries" (keeps history, fewer entries, more complex). If all transactions derive from domain events, the accounting data "uses event sourcing, even if the rest of the application does not." — [Patterns for Accounting (Fowler)](https://martinfowler.com/eaaDev/AccountingNarrative.html) (2006-01-24)
- Modern Treasury Ledgers guarantees: "For each currency within a Ledger, credits will always equal debits." "the balance of an Account is equal to the sum of its effective credit and debit entries." "Ledger Transactions cannot be deleted, only archived." Archived transactions stop affecting balances; posted transactions cannot be archived; entries on a posted transaction cannot be changed or removed (metadata can). "Idempotency keys are supported on all POST requests to prevent creating duplicate objects." "The exact Entries that contribute to each lock_version of an account can always be queried." Creating a transaction is atomic: "its Entries will either all succeed or all fail to be written." "Each Ledger will isolate its accounting from other Ledgers." Read Committed isolation; "Writes can use locking to ensure serial writes." — [Modern Treasury: Ledgers Guarantees](https://docs.moderntreasury.com/ledgers/docs/ledgers-guarantees) (n.d.); object model (ledger → ledger accounts, ledger transactions "composed of at least two ledger entry objects", "Each ledger entry will update a single ledger account", a transaction writes to one ledger only, account categories) — [Guide to Ledger Objects](https://docs.moderntreasury.com/ledgers/docs/guide-to-ledger-objects) (n.d.)
- Square "Books" (Łukasz Strzałkowski, 2019-10-16): tables `books` (balance, type, owner), `journal_entries` (each accounting transaction), `book_entries` (debit (+) / credit (−) amounts linking entries to books, with a per-book version counter). "all transactions (which we call 'journal entries') must balance to 0." "Books are immutable and can only have the balance changed by participating in accounting transaction." "no update statements for the tables presented on the diagram, only inserts" — only the `books` balance row is mutable; to fix a mistake you "write a new entry that corrects the previous one." Append-only records form "an audit log of all operations that have ever happened"; goal: "every dollar, euro, or pound we move is accounted for"; "the data model is inherently consistent." Multi-tenancy via "shelves". Storage: Google Cloud Spanner. — [Books: an immutable double-entry accounting database service](https://developer.squareup.com/blog/books-an-immutable-double-entry-accounting-database-service/) (2019-10-16)
- Stripe "Ledger" (Ilya Ganelin, 2024-02-16): "an immutable and auditable log, as a trustworthy system of record for all of our financial data", "based on double-entry bookkeeping"; "Transactions previously published into Ledger cannot be deleted or modified"; corrections "require reverting and reprocessing prior operations rather than editing records." Clearing accounts should net to zero — "If there is water stuck in the pipes, then you have a problem"; "a single missing, late, or incorrect transaction immediately creates a detectable accuracy issue." Scale: "five billion events per day"; 99.99% of dollar volume verified within four days; >135 currencies, 185 countries. — [Ledger: Stripe's system for tracking and validating money movement](https://stripe.dev/blog/ledger-stripe-system-for-tracking-and-validating-money-movement) (2024-02-16)
- Martin Kleppmann, "Accounting for Computer Scientists" (2011-03-07): "basic accounting is just graph theory" — accounts are nodes, transactions are edges labelled with amounts; each transaction is recorded on two nodes so the sum of all balances is zero; a balance is "determined completely by the transactions in and out of the account"; partition-sum checks are "balancing the books." — [Accounting for Computer Scientists](https://martin.kleppmann.com/2011/03/07/accounting-for-computer-scientists.html) (2011-03-07)
- Company/subsidiary scoping of postings and consolidation eliminations: see KQ2 (NetSuite: "Each OneWorld transaction generally posts to a single subsidiary"; elimination journal entries). Dynamics 365 establishments feature provides "immutable storage on invoices" (10.0.48+). — [Dynamics 365 organizations overview](https://learn.microsoft.com/en-us/dynamics365/fin-ops-core/fin-ops/organization-administration/organizations-organizational-hierarchies) (2026-04-24)
- Regulatory tie-in: 21 CFR 11.10(e) "Record changes shall not obscure previously recorded information" ([LII](https://www.law.cornell.edu/cfr/text/21/11.10)); SQL:2011 system versioning ensures history "cannot be tampered with" ([Kulkarni & Michels](https://sigmodrecord.org/publications/sigmodRecord/1209/pdfs/07.industry.kulkarni.pdf)).

### Conflicts between sources
- **Correction strategy**: Fowler catalogues three (replacement deletes history; reversal; difference). Modern Treasury, Square and Stripe permit only the history-preserving options (archive/reverse/new entry); Modern Treasury adds a nuance — *pending* transactions can be archived, *posted* ones cannot. A framework should forbid replacement adjustments for posted entries.
- **Where the balance lives**: Fowler and Modern Treasury define balance as derived from entries; Square materialises the balance in the `books` row (the only mutable table) and also caches balances on `book_entries` with a version counter. These agree on the invariant but differ on materialisation — a cache keyed by version is acceptable if entries remain the source of truth.
- **Sequential ≠ gapless**: the Directive requires "sequential… uniquely identifies"; PostgreSQL warns sequences have gaps. Whether gaps are legally tolerated varies by member-state implementation (not researched); engineering sources treat gapless per-series numbering as the safe target.

### Inferences
- Gapless per (company, series, fiscal year) numbering must be implemented as a counter row updated under a row lock (`SELECT … FOR UPDATE` / single-row `UPDATE … RETURNING`) inside the posting transaction, assigned only at posting time (so drafts do not consume numbers) — derived from the PostgreSQL warning that `nextval`/`setval` are non-transactional and from the Directive's uniqueness requirement.
- Ledger schema: `journal_entry (id, company_id, ledger_id, effective_at/posted_at, status pending|posted|archived, idempotency_key UNIQUE, …)` and `ledger_line (journal_entry_id, account_id, currency, amount signed or debit/credit, …)` with an invariant that lines per (journal_entry, currency) sum to zero, enforced in the posting transaction (Modern Treasury per-currency rule; Square zero-sum); no UPDATE/DELETE grants on posted lines; corrections by reversal (Fowler; Stripe).
- Multi-currency: Modern Treasury's "credits equal debits for each currency" implies each line must carry a currency and balances are per account-currency; a functional-currency amount requires a dated exchange-rate table (not covered by fetched sources — inference).
- Fiscal period close/locking: no fetched source specifies the mechanism; the immutability rules (posted = immutable; reversal entries dated in open periods) plus Dynamics' statutory-hierarchy reporting imply a `fiscal_period (company_id, start, end, status open|closed)` table checked at posting time — inference.

### Prescriptions (labelled)
- **MANDATORY** (EU invoicing) — Invoice numbers are sequential within one or more series and unique (Directive 2006/112 Art. 226(2)); do not use database sequences for legally numbered documents (PostgreSQL "cannot be used to obtain gapless sequences").
- **MANDATORY** (ledgers) — Every journal entry balances to zero per currency (Modern Treasury; Square; Kleppmann); posted entries are never updated or deleted — corrections are new reversing/adjusting entries or archive of unposted items (Square; Stripe; Modern Treasury; Fowler reversal/difference adjustments).
- **MANDATORY** — Idempotent posting (idempotency key / external_id unique) and atomic multi-line writes (Modern Treasury).
- **RECOMMENDED** — Balances derived from entries; any materialised balance carries a version and is reconcilable to entries (Fowler; Modern Treasury `lock_version`; Square version counter).
- **RECOMMENDED** — Clearing/suspense accounts that must net to zero, monitored as a data-quality signal (Stripe).
- **OPTIONAL/CONTEXTUAL** — System-versioned or ledger tables on the journal for tamper evidence (SQL:2011; SQL Server ledger).

### Gaps
- No fetched source details fiscal-calendar/period-close locking or exchange-rate table design; these are inferred.
- EUR-Lex consolidated text of Art. 226 and the 2025/516 amendment were not opened (legislation.gov.uk archived copy was used).
- Member-state rules on whether numbering gaps are tolerated were not researched.
