Scope: official AWS, Google Cloud, and Microsoft Azure architecture frameworks, prescriptive-guidance libraries, and managed-database developer guides, as they define and recommend data architectures and schema design. Applies-to tags: OLTP, OLAP/DW, lakehouse, NoSQL, all.

## Q1. How do the three frameworks define OLTP vs OLAP vs data warehouse vs data lake vs lakehouse?

### Takeaway
Azure's Architecture Center gives the most explicit, side-by-side definitions (trait tables for OLTP and OLAP; lake vs warehouse vs lakehouse in the big-data guide). AWS defines the terms operationally inside "modern data architecture" (formerly "lake house"): a data lake + data warehouse + purpose-built stores with unified governance. Google documents lakehouse as "borderless Lakehouse" (Iceberg on Cloud Storage + BigQuery) and uses the medallion pattern; it does not publish a canonical OLTP-vs-OLAP trait table in its framework.

### Cited Findings

**Azure definitions (most explicit)**
- OLTP definition: "The management of transactional data by using computer systems is referred to as online transaction processing (OLTP). OLTP systems record business interactions as they occur in the day-to-day operation of the organization, and support querying of this data to make inferences." — [Online Transaction Processing (OLTP)](https://learn.microsoft.com/en-us/azure/architecture/data-guide/relational-data/online-transaction-processing) (ms.date 2026-02-06; updated 2026-08-28). [applies: OLTP]
- OLTP trait table (verbatim rows): Normalization "Highly normalized"; Schema "Schema on write, enforced"; Consistency "Strong consistency, ACID guarantees"; Locking "Pessimistic or optimistic"; Workload "Heavy writes, moderate reads"; Indexing "Primary and secondary indexes"; Datum size "Small to medium sized"; Scale "Small (MBs) to large (a few TBs)". — [Azure OLTP](https://learn.microsoft.com/en-us/azure/architecture/data-guide/relational-data/online-transaction-processing). [OLTP]
- Why OLTP normalizes: "The goal of efficiently processing and storing individual transactions by an OLTP system is partly accomplished through data normalization, which breaks up the data into smaller, less redundant chunks." Challenge: aggregate analytics over millions of rows "is very resource-intensive for an OLTP system"; "The common solution is to maintain a relevant window of time (such as the current fiscal year) in the OLTP system and offload historical data to other systems, such as a data mart or data warehouse." — [Azure OLTP](https://learn.microsoft.com/en-us/azure/architecture/data-guide/relational-data/online-transaction-processing). **RECOMMENDED** (offload history). [OLTP]
- HTAP: "In practice, most workloads aren't entirely OLTP. They often include an analytical component as well and require real-time reporting... This workload is referred to as hybrid transactional and analytical processing (HTAP)." — [Azure OLTP](https://learn.microsoft.com/en-us/azure/architecture/data-guide/relational-data/online-transaction-processing). [OLTP/OLAP]
- OLAP definition: "Online analytical processing (OLAP) is a technology that organizes large business databases to perform complex calculations and trend analysis. This method enables intricate queries without disrupting transactional systems." "OLAP databases are optimized for heavy-read and low-write tasks. They're modeled and cleansed for effective analysis. OLAP databases often preserve historical data for time-series analysis." — [Online Analytical Processing](https://learn.microsoft.com/en-us/azure/architecture/data-guide/relational-data/online-analytical-processing) (ms.date 2025-04-11; updated 2026-08-28). [OLAP]
- OLAP trait table (verbatim rows): Schema "Schema on write, strongly enforced"; Uses transactions "No"; Locking "None"; Updateable "No, typically requires recomputing cube"; Workload "Heavy reads, read-only"; Indexing "Multidimensional indexing"; Data shape "Cube, star, or snowflake schema"; Scale "Large, hundreds of gigabytes (GBs) to multiple petabytes (PBs)". — [Azure OLAP](https://learn.microsoft.com/en-us/azure/architecture/data-guide/relational-data/online-analytical-processing). [OLAP]
- OLAP schema contrast: "Unlike traditional, normalized relational tables in OLTP systems, OLAP data models tend to be multidimensional... OLAP systems typically use a star or snowflake schema instead of traditional normalization." — [Azure OLAP](https://learn.microsoft.com/en-us/azure/architecture/data-guide/relational-data/online-analytical-processing). [OLAP]
- OLAP on the same platform (HTAP): "Beginning with SQL Server 2016, including SQL Database, you can take advantage of hybrid transactional and analytical processing (HTAP) through updateable nonclustered columnstore indexes... This approach eliminates the need for multiple copies of your data and separate OLTP and OLAP systems." — [Azure OLAP](https://learn.microsoft.com/en-us/azure/architecture/data-guide/relational-data/online-analytical-processing). **OPTIONAL/CONTEXTUAL**. [OLTP/OLAP]
- Data warehouse vs data lake vs lakehouse (verbatim): "A data lake is a centralized data repository that stores structured data (database tables), semi-structured data (XML files), and unstructured data (images and audio files). This data is in its raw, original format and doesn't require predefined schema." "A data warehouse is a centralized repository that stores structured and semi-structured data for reporting, analysis, and BI purposes." "The Lakehouse architecture combines the best elements of data lakes and data warehouses... These systems typically use low-cost cloud storage in open formats, such as Parquet or Optimized Row Columnar, to store both raw and processed data." — [Big Data Architectures](https://learn.microsoft.com/en-us/azure/architecture/databases/guide/big-data-architectures) (ms.date 2025-09-12; updated 2026-11-03). [lakehouse]
- Big data threshold is relative: "A big data architecture manages the ingestion, processing, and analysis of data that's too large or complex for traditional database systems. The threshold for entering the realm of big data varies among organizations." Analytical store in a big-data pipeline "can be a Kimball-style relational data warehouse. Most traditional business intelligence (BI) solutions use this type of data warehouse." — [Azure Big Data Architectures](https://learn.microsoft.com/en-us/azure/architecture/databases/guide/big-data-architectures). [OLAP/DW, lakehouse]
- Lambda vs Kappa: Lambda has a batch layer (cold path, "stores all the incoming data in its raw form") and a speed layer (hot path, "designed for low latency, at the expense of accuracy"); Kappa routes "all data... through a single path via a stream processing system"; the raw data at the batch layer "is immutable." — [Azure Big Data Architectures](https://learn.microsoft.com/en-us/azure/architecture/databases/guide/big-data-architectures). [streaming]
- Warehouse sizing floor (Synapse): "Azure Synapse isn't a good fit for OLTP workloads or data sets smaller than 250 GB. For those cases you should use Azure SQL Database or SQL Server." — [Data warehousing and analytics (example scenario)](https://learn.microsoft.com/en-us/azure/architecture/example-scenario/data/data-warehouse) (ms.date 2022-11-17; updated 2026-06-03). **RECOMMENDED**. [OLAP/DW]
- Azure classification table: "Relational (OLTP) — Consistent transactional operations"; "Analytics, online analytical processing (OLAP), massively parallel processing (MPP) — Large-scale historical aggregation or business intelligence (BI) — Microsoft Fabric, Azure Data Explorer, Azure Analysis Services, or Azure Databricks". — [Understand Data Models](https://learn.microsoft.com/en-us/azure/architecture/data-guide/technology-choices/understand-data-store-models) (ms.date 2025-08-21; updated 2026-05-02). [all]

**AWS definitions**

Three movement patterns: "Inside-out" (lake subset moved to e.g. OpenSearch/Neptune), "Outside-in" (purpose-built store exported to the lake, e.g. DynamoDB game state), "Around the perimeter" (store-to-store, e.g. relational to NoSQL for dashboards). — [Data Analytics Lens: Modern data architecture](https://docs.aws.amazon.com/wellarchitected/latest/analytics-lens/modern-data-architecture.html) (Lens publication date December 22, 2023). [OLAP/DW, lakehouse]
- AWS WAF uses OLTP/OLAP as a selection axis: "Does storage and modification (OLTP - Online Transaction Processing) or retrieval and reporting (OLAP - Online Analytical Processing) have a higher priority?" Answers: DynamoDB for "high-throughput read as-is transactional processing"; Amazon RDS for "high-throughput and complex read patterns (like join) with consistency"; "For analytical queries, consider a columnar database such as Amazon Redshift or exporting the data to Amazon S3 and performing analytics using Athena." — [PERF03-BP01](https://docs.aws.amazon.com/wellarchitected/latest/framework/perf_data_use_purpose_built_data_store.html) (n.d.). **RECOMMENDED**. ### Inferences
- The three vendors converge on the same definitional stack: OLTP = normalized, schema-on-write, ACID, write-heavy; OLAP/DW = star/snowflake or cube, read-heavy, batch-refreshed; data lake = raw/open-format object storage; lakehouse = lake storage + warehouse semantics (ACID table formats: Delta on Fabric, Iceberg on Google and AWS). Azure is the only one publishing numeric trait tables; AWS and Google define by service role.
- Azure's "250 GB" Synapse floor and Google's "BigQuery often used for gold" indicate that a warehouse is positioned as the serving layer on top of a lake, not a replacement for it, in all three frameworks.

### Gaps
- Google's Architecture Framework overview and pillar pages fetched contain no formal OLTP/OLAP/DW definitions; Google's definitions live in product docs and blog posts (search-only here).
- The AWS Data Analytics Lens scenario pages for data warehouse and data lake best-practice IDs (e.g., numbered "Best practice" items) were not fetched individually; only the lens landing page and the modern-data-architecture scenario were.

## Q2. Database selection: what do the frameworks say about "purpose-built" data stores?

### Takeaway
All three frameworks make store selection a first-order architectural decision driven by access patterns, consistency needs, and scale, and all warn against one-size-fits-all. AWS codifies this as Well-Architected PERF03-BP01 (risk "High" if not followed); Azure codifies "polyglot persistence" with model-by-model heuristics and anti-patterns; Google states it in the framework's core principles only indirectly ("simplify your design and use fully managed services") and in product positioning.

### Cited Findings
- AWS PERF03-BP01 title: "Use a purpose-built data store that best supports your data access and storage requirements." "Level of risk exposed if this best practice is not established: High." Anti-patterns: "You stick to one data store because there is internal experience and knowledge of one particular type of database solution"; "You assume that all workloads have similar data storage and access requirements"; "You have not implemented a data catalog to inventory your data assets." — [PERF03-BP01](https://docs.aws.amazon.com/wellarchitected/latest/framework/perf_data_use_purpose_built_data_store.html) (n.d.). **RECOMMENDED** (WAF best practice, high risk). [all]
- Implementation steps: inventory data types; document "Data type (unstructured, semi-structured, relational)", "Data volume and growth", durability, "ACID... requirements", "Data access patterns (read-heavy or write-heavy)", latency, throughput, IOPS, retention; "Perform experiments and benchmarking in a non-production environment." — [PERF03-BP01](https://docs.aws.amazon.com/wellarchitected/latest/framework/perf_data_use_purpose_built_data_store.html). **RECOMMENDED**. [all]
- AWS store-type table (verbatim characteristics): Relational (Aurora, RDS, Redshift) "Designed to support ACID transactions, and maintain referential integrity and strong data consistency"; Key-value (DynamoDB) "Optimized for common access patterns"; Document (DocumentDB) "semi-structured data as JSON-like documents"; In-memory (ElastiCache, MemoryDB); Graph (Neptune); Time series (Timestream); Wide column (Keyspaces); Ledger (QLDB). — [PERF03-BP01](https://docs.aws.amazon.com/wellarchitected/latest/framework/perf_data_use_purpose_built_data_store.html). [all]
- AWS on referential integrity: "For foreign key constraints, relational databases such as Amazon RDS and Aurora can provide this level of integrity. Typically, within a NoSQL data-model, you would de-normalize your data into a single document or collection of documents to be retrieved in a single request rather than joining across documents or tables." And on scale: "Relational databases have upper bounds on provisioned storage, and often must be horizontally partitioned using mechanisms such as sharding once they reach these limits." — [PERF03-BP01](https://docs.aws.amazon.com/wellarchitected/latest/framework/perf_data_use_purpose_built_data_store.html). [OLTP, NoSQL]
- Azure polyglot persistence: "A single data store rarely satisfies all access patterns efficiently. Most production systems adopt polyglot persistence, which means that you select multiple storage models." Five-step method: identify access patterns, map to models, shortlist services, apply criteria "consistency, latency, scale, governance, and cost", and "Combine models only where access patterns or life cycles clearly diverge." — [Understand Data Models](https://learn.microsoft.com/en-us/azure/architecture/data-guide/technology-choices/understand-data-store-models) (ms.date 2025-08-21; updated 2026-05-02). **RECOMMENDED**. [all]
- Azure heuristics table: "Strict multi-entity transactions → Relational"; "Evolving aggregate shape, JSON-centric APIs → Document"; "Extreme low-latency key lookups or caching → Key-value"; "Wide, sparse, write-heavy telemetry → Column family or time series"; "Deep relationship traversal → Graph"; "Massive historical analytical scans → Analytics or OLAP". — [Understand Data Models](https://learn.microsoft.com/en-us/azure/architecture/data-guide/technology-choices/understand-data-store-models). [all]
- Azure anti-patterns: "Multiple microservices share one database, which creates coupling"; "Teams add another model without operational maturity, such as monitoring or backups"; "A search index becomes the primary data store." Re-evaluation signals, e.g., "Increasing ad-hoc joins on a document store → Introduce relational read model"; "Large denormalized documents create partial update contention → Reshape aggregates or split". — [Understand Data Models](https://learn.microsoft.com/en-us/azure/architecture/data-guide/technology-choices/understand-data-store-models). **RECOMMENDED** (avoid). [all]
- Azure relational considerations: "Horizontal scale generally requires sharding or partitioning, and normalization can increase join cost for read-heavy denormalized views." Nonrelational comparative table: Document/Column-family/Key-value "Denormalized", Graph "Normalized relationships"; atomicity scope "Document" / "Row or family" / "Single key". — [Understand Data Models](https://learn.microsoft.com/en-us/azure/architecture/data-guide/technology-choices/understand-data-store-models). [OLTP, NoSQL]
- Azure OLTP selection criteria include: "Is your solution multitenant? If so, consider options that support capacity pools... Azure Cosmos DB offers multiple isolation models for multitenant scenarios." "Does your workload require guaranteed ACID transactions? If you work with nonrelational data, consider Azure Cosmos DB, which provides ACID guarantees through transactional batch operations within a logical partition." — [Azure OLTP](https://learn.microsoft.com/en-us/azure/architecture/data-guide/relational-data/online-transaction-processing). [OLTP]
- Azure database hub: "The right database for your scenario depends on your data model, consistency requirements, query patterns, and operational preferences." — [Get Started with Database Architecture Design](https://learn.microsoft.com/en-us/azure/architecture/databases/database-get-started) (ms.date 2026-03-05; updated 2026-10-23). [all]
- Google framework core principles (overview page): "Design for change", "Document your architecture", "Simplify your design and use fully managed services", "Decouple your architecture", "Use a stateless architecture"; pillars: operational excellence; security, privacy, and compliance; reliability; cost optimization; performance optimization; sustainability; cross-pillar perspectives: AI and ML, financial services. The overview "doesn't give any" data-storage recommendations directly. — [Google Cloud Well-Architected Framework](https://docs.cloud.google.com/architecture/framework) (n.d.). [all]
- Google DB positioning (search-only, url_verified=false): Cloud SQL "for any general-purpose SQL database and Cloud Spanner for large-scale globally scalable, strongly consistent use cases"; Bigtable "does not support SQL queries, joins, or multi-row transactions"; Firestore "is not a relational database so not meant for relational structured data applications." — [Your Google Cloud database options, explained](https://cloud.google.com/blog/topics/developers-practitioners/your-google-cloud-database-options-explained); [Google Cloud databases](https://cloud.google.com/products/databases).

### Inferences
- AWS and Azure agree almost verbatim on the decision inputs (access pattern, ACID need, scale, read/write ratio, operational model). Azure adds explicit "avoid premature fragmentation" guidance; AWS adds "benchmark in non-production." Both treat NoSQL denormalization as the price of dropping joins/foreign keys.
- Google's framework is the least prescriptive about database choice at the framework level; its guidance is distributed into product docs (Spanner/BigQuery/Cloud SQL) rather than a pillar page.

### Gaps
- No Google Architecture Framework page with an explicit "choose a database" decision table was found in official docs (only blog posts and product pages via search).

## Q3. Multi-tenant SaaS data partitioning models (silo / bridge / pool; Azure tenancy models)

### Takeaway
AWS (SaaS Lens) and Azure (Architecture Center + Azure SQL docs) describe the same spectrum with different names: AWS silo = Azure database-per-tenant/standalone; AWS pool = Azure shared multitenant database (optionally sharded); AWS bridge = Azure hybrid/mixed-per-component. Both say isolation is non-negotiable but the *mechanism* is a trade-off among isolation, noisy-neighbor, cost, agility and compliance. Azure is the only one publishing concrete anti-patterns (table-per-tenant, manual schema changes) and a numeric comparison table.

### Cited Findings

**AWS SaaS Lens (April 4, 2023)**
- Silo: "The silo model refers to an architecture where tenants are provided dedicated resources... perhaps each tenant of your system has a separate database... a silo environment still relies on a shared identity, onboarding, and operational experience where all tenants are managed and deployed via a shared construct." — [Silo, Pool, and Bridge Models](https://docs.aws.amazon.com/wellarchitected/latest/saas-lens/silo-pool-and-bridge-models.html). [all]
- Pool: "the pool model of SaaS refers to a scenario where tenants share resources. This is the more classic notion of multi-tenancy where tenants rely on shared, scalable infrastructure to achieve economies of scale, manageability, agility, and so on. These shared resources can apply to some or all of the elements of your SaaS architecture, including compute, storage, messaging, etc." — [Silo, Pool, and Bridge Models](https://docs.aws.amazon.com/wellarchitected/latest/saas-lens/silo-pool-and-bridge-models.html). [all]
- Bridge: "many systems have a mixed mode where some of the system is implemented in a silo model and some is in a pooled model. For example, some microservices in your architecture might be implemented with silo and others might use pool. The regulatory profile of a service's data and its noisy neighbor attributes might steer a microservice to a silo model. Meanwhile the agility, access patterns, and cost profile of another microservice could tip it toward a pool model." — [Silo, Pool, and Bridge Models](https://docs.aws.amazon.com/wellarchitected/latest/saas-lens/silo-pool-and-bridge-models.html). **OPTIONAL/CONTEXTUAL** (choose per service). [all]
- Tenant isolation is foundational: "Tenant isolation is one of the foundational topics that every SaaS provider must address... Crossing this boundary in any form would represent a significant and potentially unrecoverable event for a SaaS business." "Regardless of how the isolation is implemented, each SaaS architecture needs to ensure that it has put in place the constructs that are needed to ensure that each tenant's resources have been effectively isolated." — [SaaS Lens: Tenant Isolation](https://docs.aws.amazon.com/wellarchitected/latest/saas-lens/tenant-isolation.html). **MANDATORY** (isolation itself); mechanism **OPTIONAL/CONTEXTUAL** ("strategies and approaches to achieving this isolation are not universal"). [all]
- Data partitioning definition: "Will the data be stored in separate database, for example, or will it be comingled in a shared construct? These multi-tenant storage mechanisms and patterns are typically referred to as data partitioning." — [SaaS Lens: Data Partitioning](https://docs.aws.amazon.com/wellarchitected/latest/saas-lens/data-partitioning.html). [all]
- The SaaS Lens is "available as an AWS-official lens in the Lens Catalog of the AWS Well-Architected Tool." — [SaaS Lens](https://docs.aws.amazon.com/wellarchitected/latest/saas-lens/saas-lens.html) (April 4, 2023).
- Retired whitepaper content (search summaries only; url_verified=false because the URLs redirect to the SaaS Lens): the tenant-isolation whitepaper describes bridge as applying "silo or pool isolation wherever each fits"; "Attributing consumption to a specific tenant is much easier in silo, while pooled attribution is more challenging"; "IAM works well for expressing silo isolation policies, but it becomes more involved in the pool model." The storage whitepaper's pool model "uses a partition key to scope access to shared tables, and its bridge model typically uses separate per-tenant tables in a shared database"; "Pool requires a partitioning key that scopes and controls access to tenant data." — [SaaS Tenant Isolation Strategies: The bridge model](https://docs.aws.amazon.com/whitepapers/latest/saas-tenant-isolation-strategies/the-bridge-model.html), [Pool isolation](https://docs.aws.amazon.com/whitepapers/latest/saas-tenant-isolation-strategies/pool-isolation.html), [SaaS Storage Strategies: SaaS partitioning models](https://docs.aws.amazon.com/whitepapers/latest/multi-tenant-saas-storage-strategies/saas-partitioning-models.html). Also surfaced: [Guidance for Multi-Tenant Architectures on AWS](https://docs.aws.amazon.com/solutions/multi-tenant-architectures-on-aws/) (search summary: "the Silo Model provides the strongest tenant isolation but incurs the most cost and complexity, while the Pool Model offers the least tenant isolation but costs the least"; url_verified=false).
- DynamoDB tenant-encryption implication: single-table design "Table encryption is shared across all items. For multi-tenant applications with individual tenant encryption requirements, client side encryption would be required"; multi-table "separate tenant tables make it possible for each customer to have their own encryption key." — [Data Modeling foundations in DynamoDB](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/data-modeling-foundations.html) (n.d.). **OPTIONAL/CONTEXTUAL**. [NoSQL]

**Azure Architecture Center (multitenant guidance)**

## Q4. Schema design guidance for the managed databases

### Takeaway
The vendors' developer guides converge on four rules: (1) model NoSQL from access patterns first and co-locate what is read together (DynamoDB, Cosmos DB, Spanner interleaving, BigQuery nested fields); (2) spread writes—avoid hot partitions and monotonically increasing keys (DynamoDB, Spanner, Cosmos DB); (3) in MPP warehouses, pick distribution and sort/cluster keys to avoid data movement and enable block/partition pruning (Redshift, Synapse, BigQuery); (4) keep relational OLTP normalized but bound table counts/sizes and automate maintenance (RDS/Aurora, Cloud SQL, Azure SQL).

### Inferences
- "Design from access patterns and distribute writes" is a shared NoSQL doctrine (DynamoDB, Cosmos DB) and is also Spanner's primary-key rule; it directly contradicts the classic RDBMS instruction (AWS's own words: "you design for flexibility without worrying about... performance") — the frameworks treat this as a *paradigm* difference, not a conflict.
- MPP warehouse guidance is structurally identical across Redshift and Synapse (collocate fact+dimension on a shared hash key, replicate/ALL small dimensions, round-robin/EVEN for staging, columnar storage), and BigQuery substitutes partitioning+clustering for distribution keys. Fabric's "Liquid Clustering instead of partitioning" for silver/gold and BigQuery's "clustering when partitions <10 GB" are the same engineering instinct (avoid small partitions).
- **Conflict on denormalization:** BigQuery says denormalize via nested/repeated fields but admits star schemas are "typically optimized" and denormalization may not help; Fabric Warehouse and Synapse say star schema is *the* recommended design; Redshift designs for star schemas (fact + dimension DISTKEY). Resolution: nested/repeated is a BigQuery-native alternative for hierarchical one-to-many, not a universal replacement for star schema.
- **Conflict on single-table:** DynamoDB's general guidance is "as few tables as possible" (single-table default) but its own foundations page lists multi-tenant encryption, backups, Streams cost, GraphQL, and SDK mappers as reasons to use multiple tables; Cosmos DB documents mixing item types in one container but requires a `type` discriminator and partition alignment. Both vendors therefore present single-table as **OPTIONAL/CONTEXTUAL** despite the DynamoDB default.

- AWS Prescriptive Guidance data strategy: "Security is mandatory. Apply data privacy rules, provide data protection with encryption, enable auditing, and provide automated compliance" (KMS, IAM, Secrets Manager, Audit Manager, Macie); governance via Lake Formation + Glue catalog + DataZone. — [AWS modern data architecture](https://docs.aws.amazon.com/prescriptive-guidance/latest/strategy-aws-data/aws-architecture.html). **MANDATORY** (source wording). [lakehouse]
- Google reliability principle on data loss: judge recovery tests by "data integrity, recovery time objective (RTO), and recovery point objective (RPO)"; schedule backups to meet RPO (example "at least every 15 minutes" for a 15-minute RPO); PITR for Cloud SQL; replicate backups across multiple regions; "a data restoration test must include testing of the entire application stack." — [Perform testing for recovery from data loss](https://docs.cloud.google.com/architecture/framework/reliability/perform-testing-for-recovery-from-data-loss) (n.d.). **MANDATORY** ("must") for full-stack restore tests; rest **RECOMMENDED**. [all]
- Google Cloud SQL reliability/security: backups "can't cover a single database or table"; "A point-in-time recovery always creates a new instance"; exports survive instance deletion; "Prefer Private IP"; avoid `0.0.0.0/0`; use pgAudit. — [Cloud SQL best practices](https://docs.cloud.google.com/sql/docs/postgres/best-practices). **RECOMMENDED**. [OLTP]
- Azure SQL WAF guide pillars (verbatim pillar intents): Reliability "building enough resilience and the ability to recover fast from failures"; Security "confidentiality, integrity, and availability"; Cost Optimization "detecting spend patterns, prioritizing investments in critical areas, and optimizing in others"; Performance Efficiency "maintaining user experience even when there's an increase in load." Concrete: "Use point-in-time restore to recover from human error... Combine with backup immutability to help to protect against ransomware"; "Isolate connection pools in your client code"; "Back up your TDE encryption keys." — [Azure SQL Database WAF service guide](https://learn.microsoft.com/en-us/azure/well-architected/service-guides/azure-sql-database). **RECOMMENDED**. [OLTP]
- Azure multitenant pillar lens: considerations are framed "from several perspectives, including the pillars of the Azure Well-Architected Framework"; throttling: "If you exceed a specific number of storage operations per second, Azure Storage rejects your application's requests, which affects all of your tenants"; recovery: "In a shared database, restoring a single tenant might require you to restore the database to a separate resource and selectively recover that tenant's data." — [Azure multitenant storage/data](https://learn.microsoft.com/en-us/azure/architecture/guide/multitenant/approaches/storage-data). [all]
- Azure Cosmos DB cost/performance: "Hot partitions cause inefficient use of provisioned throughput, which can result in rate limiting and higher costs." — [Cosmos DB partitioning](https://learn.microsoft.com/en-us/azure/cosmos-db/partitioning-overview). [NoSQL]
- Azure Synapse cost: "Azure Synapse allows you to scale your compute and storage levels independently. Compute resources are charged per hour, and you can scale or pause these resources on demand." — [Data warehousing and analytics](https://learn.microsoft.com/en-us/azure/architecture/example-scenario/data/data-warehouse). [OLAP/DW]
- Fabric lakehouse governance/cost: "Delta Lake maintains a history of all changes made, so the size of historical metadata grows over time... keep historical data only for a certain period of time to reduce your storage costs"; "You should plan and control who needs access to specific data in the lakehouse." — [Fabric medallion](https://learn.microsoft.com/en-us/fabric/onelake/onelake-medallion-lakehouse-architecture). **RECOMMENDED**. [lakehouse]
- DynamoDB cost via schema: single-table "Capacity management for the table is averaged across all entities, usually resulting in a more predictable consumption pattern"; Infrequent Access storage class benefits only when historical data is in its own table. — [DynamoDB data modeling foundations](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/data-modeling-foundations.html). [NoSQL]
- RDS/Aurora SLA linkage: operational guidelines (monitoring, DNS TTL < 30 s, failover testing) are what "the Amazon RDS Service Level Agreement requires." — [RDS best practices](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/CHAP_BestPractices.html). **MANDATORY**. [OLTP]

### Inferences
- The only places vendors use "must"/"required" for data stores are (a) SLA-conditioned operational guidelines (AWS RDS/Aurora, Google Cloud SQL), (b) Google's full-stack restore testing, (c) AWS's "security is mandatory" tenet, and (d) hard product limits (Cosmos DB 20 GB/10k RU per logical partition; DynamoDB 3,000 RCU/1,000 WCU per partition; Redshift single DISTKEY). Everything else is "recommend/should/consider."
- Schema design is explicitly tied to cost in every NoSQL guide (RU/RCU consumption, hot partitions) and to performance in every MPP guide (data movement, pruning), which is why these frameworks place schema decisions under the Performance and Cost pillars rather than treating them as pure data-modeling concerns.

### Gaps
- Google's pillar pages for performance optimization and cost (as applied to databases) were not fetched; the framework overview explicitly contained no database-specific recommendations.
- AWS Data Analytics Lens pillar-level best-practice items (numbered BPs) were not captured.

## Q6. Where the three frameworks agree and where they differ

### Takeaway
Agreement: purpose-built store per workload; access-pattern-first NoSQL modeling with even key distribution; star schema/columnar for warehouses; lake-plus-warehouse (lakehouse) with open ACID table formats; tenant isolation mandatory with silo/pool/bridge-style trade-offs; backups/restores tested to RPO/RTO. Differences: terminology (AWS "modern data architecture" vs Azure/Google "lakehouse"; AWS silo/pool/bridge vs Azure tenancy-model names), BigQuery's nested-field denormalization vs Fabric/Synapse/Redshift star-schema primacy, and the degree to which the framework (vs product docs) carries the data guidance.

### Cited Findings
- Agreement, purpose-built: AWS "break away from monolithic storage technology and restrictive, one-size-fits-all approaches" — [PERF03-BP01](https://docs.aws.amazon.com/wellarchitected/latest/framework/perf_data_use_purpose_built_data_store.html); Azure "A single data store rarely satisfies all access patterns efficiently" — [Understand Data Models](https://learn.microsoft.com/en-us/azure/architecture/data-guide/technology-choices/understand-data-store-models); AWS Prescriptive Guidance "Select the right service for the right job" — [AWS modern data architecture](https://docs.aws.amazon.com/prescriptive-guidance/latest/strategy-aws-data/aws-architecture.html). [all]
- Agreement, lakehouse = lake + warehouse + open format: AWS "integrates a data lake, a data warehouse, and other purpose-built data stores" — [Modern data architecture](https://docs.aws.amazon.com/wellarchitected/latest/analytics-lens/modern-data-architecture.html); Azure "combines the best elements of data lakes and data warehouses... open formats, such as Parquet or Optimized Row Columnar" — [Big Data Architectures](https://learn.microsoft.com/en-us/azure/architecture/databases/guide/big-data-architectures); Google "open-format storage systems... decouples storage from compute" — [Lakehouse key concepts](https://docs.cloud.google.com/lakehouse/docs/key-concepts). Table formats differ: Fabric standardizes on Delta Lake ("Fabric standardizes storage file format with Delta Lake" — [Fabric medallion](https://learn.microsoft.com/en-us/fabric/onelake/onelake-medallion-lakehouse-architecture)); Google and AWS lean on Apache Iceberg ([Lakehouse key concepts](https://docs.cloud.google.com/lakehouse/docs/key-concepts); [Modern data lakes - Apache Iceberg on AWS](https://docs.aws.amazon.com/prescriptive-guidance/latest/apache-iceberg-on-aws/data-lakes.html) (search-only)). [lakehouse]
- Agreement, medallion: Fabric (recommended) and Google ("common design pattern") both describe bronze/silver/gold identically; Google and Fabric both link medallion to data mesh/domains ("You can create a data mesh architecture for your data estate in Fabric by creating data domains" — [Fabric medallion](https://learn.microsoft.com/en-us/fabric/onelake/onelake-medallion-lakehouse-architecture); Google [data mesh](https://docs.cloud.google.com/architecture/data-mesh)). AWS reference to data mesh appears via linked re:Invent material in [PERF03-BP01](https://docs.aws.amazon.com/wellarchitected/latest/framework/perf_data_use_purpose_built_data_store.html). [lakehouse]
- Agreement, NoSQL partition design: DynamoDB "design data keys to distribute traffic evenly across partitions... avoiding hot spots" — [NoSQL design](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/bp-general-nosql-design.html); Cosmos DB "Spread request unit (RU) consumption and data storage evenly across all logical partitions" — [Cosmos partitioning](https://learn.microsoft.com/en-us/azure/cosmos-db/partitioning-overview); Spanner "Do not choose a column whose value monotonically increases or decreases as the first key part" — [Spanner schema design](https://docs.cloud.google.com/spanner/docs/schema-design). [NoSQL/OLTP]
- Agreement, embed vs reference: Cosmos DB "use embedded data models when... one-to-few... does not grow without bound" vs reference for "one-to-many... unbounded" — [Cosmos modeling](https://learn.microsoft.com/en-us/azure/cosmos-db/nosql/modeling-data); BigQuery repeated fields "best... when the relationships are hierarchical" — [nested/repeated](https://docs.cloud.google.com/bigquery/docs/best-practices-performance-nested); DynamoDB "Keep related data together" with exceptions for "high-volume time series data" — [NoSQL design](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/bp-general-nosql-design.html). [NoSQL, OLAP]
- Agreement, MPP distribution: Redshift "Distribute the fact table and one dimension table on their common columns" / ALL for small dimensions — [Redshift distribution](https://docs.aws.amazon.com/redshift/latest/dg/c_best-practices-best-dist-key.html); Synapse "Fact: hash-distribution... Dimension: replicated for smaller tables... Staging: round-robin" — [Synapse tables](https://learn.microsoft.com/en-us/azure/synapse-analytics/sql-data-warehouse/sql-data-warehouse-tables-overview). [OLAP/DW]
- Agreement, tenant isolation mandatory but mechanism contextual: AWS "every SaaS provider must address" — [SaaS Lens Tenant Isolation](https://docs.aws.amazon.com/wellarchitected/latest/saas-lens/tenant-isolation.html); Azure "There's no single solution that works for every scenario" — [Azure multitenant storage/data](https://learn.microsoft.com/en-us/azure/architecture/guide/multitenant/approaches/storage-data). [all]
- Agreement, relational scale ceilings: RDS "fewer than 10,000 tables" — [RDS best practices](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/CHAP_BestPractices.html); Cloud SQL "fewer than 10,000" tables and "many smaller Cloud SQL instances is better than one large instance" — [Cloud SQL best practices](https://docs.cloud.google.com/sql/docs/postgres/best-practices); Azure "Shard data" for fault isolation — [Azure SQL WAF guide](https://learn.microsoft.com/en-us/azure/well-architected/service-guides/azure-sql-database). These are consistent in spirit (avoid small/many partitions) but differ in default. [OLAP/DW, lakehouse]
- Difference, where guidance lives: Google's framework overview has "None" data-store links ([Google framework](https://docs.cloud.google.com/architecture/framework)); AWS puts selection in a numbered WAF best practice; Azure puts it in Architecture Center guides plus per-service WAF guides ([Azure SQL WAF guide](https://learn.microsoft.com/en-us/azure/well-architected/service-guides/azure-sql-database)). [all]

[OLTP/OLAP]

### Inferences
- For a schema-design framework, the vendor-neutral consensus is: pick the store by workload class (OLTP normalized/ACID; OLAP star/columnar; NoSQL access-pattern/denormalized; lake raw/open format); encode the tenant boundary in the key/partition (tenant ID leading in PK or partition key) when pooled; and treat distribution/partition/cluster keys as schema decisions with direct cost consequences.
- Terminology crosswalk for the final report: AWS "modern data architecture" ≈ Azure/Google "lakehouse"; AWS silo/pool/bridge ≈ Azure dedicated DB-per-tenant / shared (sharded) multitenant / hybrid; Redshift DISTKEY+SORTKEY ≈ Synapse hash distribution+CCI ≈ BigQuery partition+cluster.

### Gaps
- No official Google page was found that addresses multi-tenant SaaS data partitioning comparable to the AWS SaaS Lens or Azure multitenant guide.
- Numeric trait tables (datum size, scale) exist only in Azure docs; AWS and Google do not publish comparable tables, so any cross-vendor "definition table" in the report must be sourced to Azure and labeled as such.
