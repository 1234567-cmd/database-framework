## Q1. Normalization: definitions of 1NF-6NF, what each level protects against, and when denormalization is legitimate

### Takeaway
Codd (1970) coined "normalization" as the elimination of non-simple (repeating-group) domains and defined primary/foreign keys; Kent (1983) supplies the canonical plain-English definitions of 1NF-5NF and the anomalies each prevents, and explicitly states that full normalization is **not** required when performance requirements justify stopping short. Normal forms are a *logical* design discipline for base tables; denormalized read models (dimensional star schemas, materialized views) are legitimate only when the redundancy is declared and maintained by a single controlled write path.

### Cited Findings
- Codd's stated goal: "Future users of large data banks must be protected from having to know how the data is organized in the machine (the internal representation)." The paper identifies three dependencies to remove: "ordering dependence, indexing dependence, and access path dependence." — [A Relational Model of Data for Large Shared Data Banks, CACM 13(6), June 1970, pp. 377-387 (open-access copy, Univ. of Pennsylvania)](https://www.engineering.upenn.edu/~zives/03f/cis550/codd.pdf) (ACM DOI 10.1145/362384.362685 returned 403).
- Codd's definition of normalization (Section 1.4 "Normal Form"): "A relation whose domains are all simple can be represented in storage by a two-dimensional column-homogeneous array ... the possibility of eliminating nonsimple domains appears worth investigating! There is, in fact, a very simple elimination procedure, which we shall call normalization." Condition (2) of normal form: "No primary key has a component domain which is nonsimple." Codd adds: "The writer knows of no application which would require any relaxation of these conditions. Further operations of a normalizing kind are possible. These are not discussed in this paper." — [Codd 1970](https://www.engineering.upenn.edu/~zives/03f/cis550/codd.pdf)
- Codd 1970 on the cost of enforcing consistency over redundant data: "In one approach the system checks for possible inconsistency whenever an insertion, deletion, or key update occurs. Naturally, such checking will slow these operations down." (Section 2.3 Consistency) — [Codd 1970](https://www.engineering.upenn.edu/~zives/03f/cis550/codd.pdf)
- 2NF and 3NF were introduced by Codd in "Further Normalization of the Data Base Relational Model", presented at Courant Computer Science Symposia Series 6 (New York, May 24-25, 1971), published in R. Rustin (ed.), *Data Base Systems*, Prentice-Hall 1972; preprint IBM Research Report RJ909 (Aug 31, 1971). — bibliographic details only, from search results ([Wikipedia: Database normalization](https://en.wikipedia.org/wiki/Database_normalization), not fetched; ACM Turing bibliography page returned 403). Authority of the citation chain: 3 (secondary).
- Kent 1983 bibliographic: *A Simple Guide to Five Normal Forms in Relational Database Theory*, William Kent, CACM 26(2), Feb 1983, pp. 120-125; earlier as IBM TR03.159 (Aug 1981); web copy dated Sept 1982. — [Kent's own copy](https://www.bkent.net/Doc/simple5.htm)
- Kent's definitions: **1NF** — every occurrence of a record type has the same number of fields (no variable repeating fields/groups); Kent presents 1NF as "a matter of definition more than design guidance." **2NF** — violated when a non-key field depends on only part of a composite key (example: warehouse address stored in a record keyed by part+warehouse); applies only to composite keys. **3NF** — violated when a non-key field depends on another non-key field (employee/department/location example). Kent summarizes 2NF+3NF as: a non-key field must provide a fact about the key, the whole key, and nothing but the key. **4NF** — a record type should not contain two or more independent multivalued facts about an entity (skills and languages of an employee in one record). **5NF** — a record type is in 5NF when its information cannot be reconstructed from several smaller record types each with fewer fields; 5NF differs from 4NF only when a symmetric constraint exists (agents/companies/products example). — [Kent 1983](https://www.bkent.net/Doc/simple5.htm)
- Anomalies Kent attributes to under-normalization: update anomalies (repeated data must be changed in many places and copies drift); insertion/deletion problems (a department's location cannot be recorded if it has no employees); maintenance ambiguity for combined multivalued facts (several conflicting storage policies, blank fields become ambiguous); redundancy (5NF can reduce record growth "from multiplicative to additive"). — [Kent 1983](https://www.bkent.net/Doc/simple5.htm)
- Kent's explicit limits and denormalization caveat: "The guidelines assume non-key fields are updated often. They tend to penalize retrieval, since data that one unnormalized record could supply may require several normalized records. Full normalization is not required. Actual performance requirements may justify stopping short of it. Some redundancy is unavoidable ... The normal forms address redundancy within a single record type. Redundancy across record types is not covered by these forms." (paraphrase of the paper's closing section) — [Kent 1983](https://www.bkent.net/Doc/simple5.htm)
- Chen (1976) contrasts 3NF with ER relations (Section 4.1.3 "3NF Relations Versus Entity-Relationship Relations") and observes that "changes in functional dependencies of data may cause some relations not to be in 3NF", arguing ER relations have "clearer semantics". — [Chen 1976, ACM TODS 1(1), pp. 9-36 (open-access copy, NUS)](https://www.comp.nus.edu.sg/~lingtw/papers/tods76.chen.pdf)
- Karwin's logical-design antipatterns "Jaywalking" (comma-separated lists in a column) and "Multicolumn Attributes" (numbered columns for multivalue data) are 1NF violations; "Metadata Tribbles" (cloning tables/columns for scale) is a cross-record-type redundancy. — [SQL Antipatterns, Volume 1 (Pragmatic Bookshelf, Oct 2022)](https://pragprog.com/titles/bksap1/sql-antipatterns-volume-1/)
- C. J. Date, *Database Design and Relational Theory* (first published 2012; 3 editions listed) is the standard modern treatment of normal forms including BCNF/5NF/6NF — [OpenLibrary search record](https://openlibrary.org/search.json?title=database+design+and+relational+theory&author=date). Content could not be fetched (Springer/O'Reilly 403), so no quotations are given.
- Dimensional (star-schema) design for data warehouses deliberately departs from 3NF base-table design: Kimball requires every dimension to carry an integer surrogate key and every dimension/fact join to use it; attributes such as calendar logic "belong in a dimension table, not in your application code". — [Kimball, "Surrogate Keys", May 2, 1998](https://www.kimballgroup.com/1998/05/surrogate-keys/); *The Data Warehouse Toolkit, 3rd ed.*, Wiley, July 2013, ISBN 9781118530801 — [OpenLibrary record](https://openlibrary.org/isbn/9781118530801.json) (content not fetched).

### Inferences
- **MANDATORY (all workloads):** 1NF — atomic column values, no repeating groups, no numbered-column arrays. Reasoning: Codd 1970 ("no primary key has a component domain which is nonsimple"); Karwin's Jaywalking/Multicolumn Attributes antipatterns document the concrete failures (unindexable, un-joinable, un-constrainable). Applies: OLTP, OLAP, DW, lakehouse, general.
- **MANDATORY (OLTP system-of-record base tables):** 3NF (and BCNF where every determinant must be a key) for tables whose non-key fields are updated. Reasoning: Kent's update/insert/delete anomalies occur exactly when non-key fields are updated often, which is the OLTP case. Applies: OLTP.
- **RECOMMENDED:** check 4NF/5NF whenever a table holds two or more independent multivalued facts (Kent). Applies: OLTP, general.
- **OPTIONAL/CONTEXTUAL:** denormalize (flattened dimensions, materialized views, read replicas of joins) when (a) the workload is read-dominant, (b) the redundancy is produced by one controlled write path (ETL/ELT or refresh), and (c) the dependency is documented. Kent's own caveat ("performance requirements may justify stopping short") and Codd's consistency section (redundant relations must carry explicit consistency statements; checks slow updates) are the authoritative grounding; Kimball's dimensional model is the canonical OLAP instance. Applies: OLAP/DW, lakehouse, reporting replicas; **not** OLTP write paths.
- Conflict to record: Kent/Codd (normalize base tables) vs. Kimball (surrogate-keyed, flattened dimensions). This is a scope difference, not a contradiction: Kimball applies to the presentation/analytical layer fed by ETL, Kent/Codd to the transactional system of record.

### Gaps
- Primary texts for BCNF (Codd 1974), 4NF (Fagin 1977), 5NF (Fagin 1979) and 6NF (Date/Darwen/Lorentzos) were not fetched; definitions above rely on Kent's exposition and Codd 1970. Date's book content (BCNF/6NF formalisms, "orthogonal design") was inaccessible.
- No vendor documentation on materialized views was fetched for this section; the "controlled write path" condition is an inference from Codd/Kent, not a quoted vendor rule.

## Q2. Keys: natural vs surrogate; integer vs UUID v4 / v7 / ULID; composite keys in junction tables; INT exhaustion

### Takeaway
Every base table needs a declared primary key (relational theory per Codd; PostgreSQL and MySQL/InnoDB docs; Karwin "Keyless Entry"). The natural-vs-surrogate debate splits by workload: Kimball mandates integer surrogates for warehouse dimensions, Celko argues natural/industry-standard keys first and calls IDENTITY an "exposed physical locator", Karwin warns against the blanket "ID Required" convention, and Chen (1976) already sanctioned "an artificial attribute" when natural identification is absent or inconvenient. For generated keys, 64-bit integers are the modern default (Rails, Django, Alibaba; documented 32-bit exhaustion incidents), and if globally unique IDs are needed, RFC 9562 UUIDv7 (time-ordered) is preferred over random UUIDv4 because random keys destroy B-tree/clustered-index locality (Percona, EDB/2ndQuadrant, PlanetScale benchmarks).

### Cited Findings
**Definitions (foundational)**
- Codd 1970: "Normally, one domain (or combination of domains) of a given relation has values which uniquely identify each element (n-tuple) of that relation. Such a domain (or combination) is called a primary key." "A primary key is nonredundant if it is either a simple domain (not a combination) or a combination such that none of the participating simple domains is superfluous in uniquely identifying each element." "Whenever a relation has two or more nonredundant primary keys, one of them is arbitrarily selected and called the primary key of that relation." Foreign key: "We shall call a domain (or domain combination) of relation R a foreign key if it is not the primary key of R but its elements are values of the primary key of some relation S (the possibility that S and R are identical is not excluded)." — [Codd 1970](https://www.engineering.upenn.edu/~zives/03f/cis550/codd.pdf)
- Chen 1976 sanctions artificial identifiers: "If we cannot find such one-to-one mapping on available data, or if simplicity in identifying entities is desired, we may define an artificial attribute and a value set so that such mapping is possible." Weak entities are identified through "the binary relationships with 1:n mapping in which the existence of the n entities on one side of the relationship depends on the existence of one entity on the other side", applied "recursively until the entities which can be identified by their own attribute values are reached" (e.g., department key = department number + division key). — [Chen 1976](https://www.comp.nus.edu.sg/~lingtw/papers/tods76.chen.pdf)
- PostgreSQL: "Relational database theory dictates that every table must have a primary key. This rule is not enforced by PostgreSQL, but it is usually best to follow it." "A table can have at most one primary key." Primary keys "are useful both for documentation purposes and for client applications." — [PostgreSQL 18 docs, 5.5 Constraints](https://www.postgresql.org/docs/current/ddl-constraints.html)
- MySQL/InnoDB: "A primary key should be defined for each table. If there is no logical unique and non-null column or set of columns to use a the primary key [sic], add an auto-increment column." Without a PK InnoDB uses the first UNIQUE NOT NULL index, else a hidden 6-byte `GEN_CLUST_INDEX` row ID. — [MySQL 8.4 Reference Manual, InnoDB clustered and secondary indexes](https://dev.mysql.com/doc/refman/8.4/en/innodb-index-types.html)

**Natural vs surrogate**
- Kimball (data warehouse): "Every join between dimension tables and fact tables in a data warehouse environment should be based on surrogate keys, not natural keys." A surrogate key is "a simple integer, starting with one." Reasons: slowly changing dimensions ("the correct response is to issue a new dimension record"); buffering from production keys that "are generated, formatted, updated, deleted, recycled, and reused according to the dictates of production"; special rows for unknown/not-applicable ("A null key automatically turns on the referential integrity alarm"); 4-byte integers save space in large fact tables; avoiding "smart keys" that encode meaning. He also admits the join-performance benefit is something he "strongly suspect[s] but ha[s] never proven". — [Kimball, Surrogate Keys (May 2, 1998)](https://www.kimballgroup.com/1998/05/surrogate-keys/)
- Kimball Group technique page: "A dimension table is designed with one column serving as a unique primary key. This primary key cannot be the operational system's natural key because there will be multiple dimension rows for that natural key when changes are tracked over time." Surrogates "are simple integers, assigned in sequence, starting with the value 1". "The date dimension is exempt from the surrogate key rule." — [Kimball Techniques: Dimension Surrogate Keys](https://www.kimballgroup.com/data-warehouse-business-intelligence-resources/kimball-techniques/dimensional-modeling-techniques/dimension-surrogate-key/)
- Celko (OLTP, relational purist): classifies IDENTITY/auto-increment values as an "exposed physical locator" distinct from a true (hidden, system-managed) surrogate; recommends looking first for an industry-standard key, then a natural key in the attributes, and designing a new identifier only if necessary. — search-result summary of Celko's *SQL for Smarties* section "Key Types" ([O'Reilly chapter page, not fetched](https://www.oreilly.com/library/view/joe-celkos-sql/9780123693792/9780123693792_ch02lev1sec11.html)) and *Joe Celko's SQL Programming Style* (Morgan Kaufmann, April 11, 2005, ISBN 9780120887972 — [OpenLibrary record](https://openlibrary.org/isbn/9780120887972.json)). Usenet critics call his key taxonomy confusing (search snippets). Authority for the Celko position as stated here: 3 (summaries, not primary text).
- Karwin: "ID Required — Applying one primary key convention to every table" is a logical-design antipattern; "Pseudokey Neat-Freak — Filling gaps in auto-increment keys" is an application antipattern. — [SQL Antipatterns Vol. 1](https://pragprog.com/titles/bksap1/sql-antipatterns-volume-1/)
- sqlstyle.guide: "Tables must have at least one key to be complete and useful." Keep "the key as simple as possible whilst not being scared to use compound keys where necessary." "Where possible avoid simply using `id` as the primary identifier for the table." — [SQL Style Guide (Simon Holywell)](https://www.sqlstyle.guide/)
- ORM de facto conventions: Rails: "By default, Active Record will use an integer column named `id` as the table's primary key" (bigint on PostgreSQL/MySQL/MariaDB), FKs "should be named following the pattern `singularized_table_name_id`". — [Rails Guides: Active Record Basics](https://guides.rubyonrails.org/active_record_basics.html). Django: "Behind the scenes, Django appends "_id" to the field name to create its database column name"; `BigAutoField` is "A 64-bit integer ... guaranteed to fit numbers from 1 to 9223372036854775807". — [Django 5.2 model field reference](https://docs.djangoproject.com/en/5.2/ref/models/fields/). EF Core: "By convention, a property named `Id` or `<type name>Id` will be configured as the primary key"; PK constraint named `PK_<type name>`, alternate keys `AK_<type name>_<property name>`. — [EF Core docs: Keys](https://learn.microsoft.com/en-us/ef/core/modeling/keys)
- dbt (analytics layer): "Each model should have a primary key. The primary key of a model should be named `<object>_id`." and "Keys should be string data types." — [dbt: How we style our dbt models](https://docs.getdbt.com/best-practices/how-we-style/1-how-we-style-our-dbt-models). **Conflict:** this contradicts Kimball's integer surrogate rule; dbt's context is ELT models where keys are often hashed/string business keys, not Kimball dimensions.
- Alibaba: "A table must include three columns as following: id, gmt_create and gmt_modified"; id is "unsigned bigint, self-incrementing by 1". — [Alibaba Java Coding Guidelines (English)](https://alibaba.github.io/Alibaba-Java-Coding-Guidelines/)

**Integer width / exhaustion**
- PostgreSQL `integer` range is "-2147483648 to +2147483647"; `bigint` "-9223372036854775808 to +9223372036854775807"; "Attempts to store values outside of the allowed range will result in an error." `serial` types "are not true types, but merely a notational convenience" and the docs point to the SQL-standard identity column as the other way. — [PostgreSQL 18 docs, 8.1 Numeric Types](https://www.postgresql.org/docs/current/datatype-numeric.html); PostgreSQL wiki: "Don't use serial ... use identity columns" (except pre-PG10 or shared sequences). — [Don't Do This (wiki, last modified 21 Nov 2024)](https://wiki.postgresql.org/wiki/Don%27t_Do_This)
- Rails 5.1 release notes: "Change Default Primary Keys to BIGINT." (PR #26266). — [Rails 5.1 Release Notes](https://guides.rubyonrails.org/5_1_release_notes.html)
- Buildkite incident (22 July 2023): agent IDs were `bigint` but a foreign key column was 32-bit `integer`; once IDs passed 2,147,483,647 "jobs could not be assigned to agents that connected after that moment." Workaround: "we altered this ID sequence to start at -1 and 'increment' by -1." Follow-ups: "Set up monitoring and alerting when identifiers exceed 50% of their maximum value", audit all PK/FK widths, and "Added 'ratchet tests' to prevent the introduction of any new 32-bit integer identifiers." — [Buildkite status: Newly connected agents unable to run jobs](https://buildkitestatus.com/incidents/63zxhjsysszc). A similar March 2021 int→bigint incident at Shipup appears in search results ([Medium post, not fetched](https://medium.com/shipup-blog/learning-from-an-incident-hitting-the-2-147-483-265-limit-at-shipup-747e6dcd3029)).

**UUID v4 vs v7 vs ULID**
- RFC 9562 (Proposed Standard, obsoletes RFC 4122): UUIDv7 "features a time-ordered value field derived from the widely implemented and well-known Unix Epoch timestamp source"; layout: 48-bit `unix_ts_ms`, 4-bit version 0b0111, 12-bit `rand_a`, 2-bit variant, 62-bit `rand_b`; optional sub-millisecond fraction and counter for monotonicity. Motivation (Sec. 2.1): UUIDs are popular as database keys in distributed applications where auto-increment is hard to coordinate, but non-time-ordered versions such as UUIDv4 "have poor database-index locality"; Sec. 6.11: "Time-ordered monotonic UUIDs benefit from greater database-index locality." Sec. 5.7: "Implementations SHOULD utilize UUIDv7 instead of UUIDv1 and UUIDv6 if possible." Sec. 6.2: "Monotonicity (each subsequent value being greater than the last) is the backbone of time-based sortable UUIDs." Sec. 6.13 advises against name-based UUIDs (v3/v5) as primary keys and recommends time-based UUIDs as surrogate keys. UUIDv4 has 122 random bits. — [RFC 9562: Universally Unique IDentifiers (UUIDs), May 2024](https://www.rfc-editor.org/rfc/rfc9562)
- PostgreSQL 18 ships `uuidv7([shift interval])`: "Generates a version 7 (time-ordered) UUID. The timestamp is computed using UNIX timestamp with millisecond precision + sub-millisecond timestamp + random", valid "from 1970-01-01 00:00:00 UTC to approximately year 10889"; plus `uuidv4()`, `gen_random_uuid()`, `uuid_extract_timestamp()`, `uuid_extract_version()`. — [PostgreSQL 18 docs, 9.14 UUID Functions](https://www.postgresql.org/docs/current/functions-uuid.html)
- InnoDB clustered index: "Each InnoDB table has a special index called the clustered index that stores row data"; "each record in a secondary index contains the primary key columns for the row"; "If the primary key is long, the secondary indexes use more space, so it is advantageous to have a short primary key." — [MySQL 8.4: InnoDB clustered and secondary indexes](https://dev.mysql.com/doc/refman/8.4/en/innodb-index-types.html)
- Percona (Yves Trudeau, Nov 22, 2019): "InnoDB stores the rows of a table in the b-tree of the primary key." "Rows inserted out of the primary key order cause page splits causing a low filling factor." In one schema "about 70 percent of storage was for these values" (PK copies in secondary indexes). `char(36)` comparison was ~28x slower than integer in the worst case. Conclusion: "If you are using random UUID values as primary keys, your performance is limited by the amount of memory you can afford." Mitigations: `binary(16)`, pseudo-ordered (time-prefixed) UUIDs, or a UUID→integer mapping table (~4,000 inserts/s on a small VM). Caveat: pseudo-ordered UUIDs expose a timestamp. — [UUIDs are Popular, but Bad for Performance](https://www.percona.com/blog/uuids-are-popular-but-bad-for-performance-lets-discuss/)
- PlanetScale (Brian Morrison II, March 19, 2024): InnoDB fills pages to ~94% before splitting with predictable keys, but with random PKs page utilization "can be as low as 50%"; storage: 32-bit int = 1x, `BINARY(16)` UUID = 4x, `CHAR(36)` = 9x. Recommends `BINARY(16)` with `UUID_TO_BIN()`, ordered v6/v7, or Snowflake/ULID/NanoID. — [The Problem with Using a UUID Primary Key in MySQL](https://planetscale.com/blog/the-problem-with-using-a-uuid-primary-key-in-mysql)
- MySQL `UUID_TO_BIN(uuid, 1)`: swapping time-low/time-high "moves the more rapidly varying part to the right and can improve indexing efficiency if the result is stored in an indexed column"; "Time-part swapping assumes the use of UUID version 1 values"; `UUID()` values "are not necessarily unguessable or unpredictable." — [MySQL 8.4 Miscellaneous Functions](https://dev.mysql.com/doc/refman/8.4/en/miscellaneous-functions.html)
- EDB/2ndQuadrant (Tomas Vondra, Nov 27, 2018), PostgreSQL benchmarks: random UUIDs scatter inserts "with uniform distribution for all index pages", work "against adaptive cache management algorithms", and trigger full-page writes after each checkpoint. Medium dataset (fits in RAM): random throughput fell to "less than 30%" of baseline while time/sequence generators held; WAL: random >20 GB vs ~2.5 GB for time-based; cache hit ratio ~85% (random) vs ~99% (ordered). Introduces the `sequential_uuids` extension (`uuid_sequence_nextval`, `uuid_time_nextval`) that is "sequential for a while, but also wraps around once in a while" to avoid leaking creation order. — [Sequential UUID Generators](https://www.enterprisedb.com/blog/sequential-uuid-generators)
- ULID spec: 128-bit = 48-bit ms timestamp + 80 bits randomness, 26-char Crockford Base32, "Lexicographically sortable!", "1.21e+24 unique ULIDs per millisecond", "128-bit compatibility with UUID"; critiques UUID: "UUID v4 provides no other information than randomness which can cause fragmentation in many data structures." Monotonic factory increments the random component within the same millisecond; the spec also says "Within the same millisecond, sort order is not guaranteed" for the non-monotonic mode. — [ULID specification (GitHub)](https://github.com/ulid/spec)

### Inferences
- **MANDATORY (all):** every base table declares a primary key (PostgreSQL docs; InnoDB docs; Codd's definition; Karwin "Keyless Entry"). For InnoDB this is doubly important because the PK *is* the physical row order and is copied into every secondary index.
- **MANDATORY (OLAP/DW dimensions):** integer surrogate keys on every dimension except the date dimension; facts join only on surrogates; special surrogate rows replace NULL foreign keys (Kimball 1998; Kimball technique page). Applies: data_warehouse, OLAP.
- **RECOMMENDED (OLTP):** 64-bit integer (BIGINT / identity) as the default generated key; 32-bit INT only for provably bounded lookup tables. Evidence: Rails 5.1 default, Django `BigAutoField`, Alibaba's unsigned bigint rule, Buildkite's FK-width outage and its "50% alert + ratchet tests" remedies. Audit FK column widths together with PKs (Buildkite's failure was an FK, not the PK). Applies: OLTP, general.
- **RECOMMENDED (when globally unique or client-generated IDs are needed):** UUIDv7 (RFC 9562) or ULID, stored in the engine's native 16-byte type (`uuid` in PostgreSQL, `BINARY(16)` in MySQL), never `CHAR(36)`; UUIDv4 primary keys are an anti-pattern for large clustered/B-tree-indexed tables (Percona, PlanetScale, EDB). Caveat to document: v7/ULID leak creation time (RFC 9562, Percona, EDB). Applies: OLTP, general.
- **OPTIONAL/CONTEXTUAL (contested):** natural vs surrogate key for OLTP entity tables. Pro-natural (Celko, sqlstyle "avoid simply using `id`", Karwin "ID Required"): natural keys carry meaning, prevent duplicate rows, avoid an extra lookup. Pro-surrogate (Kimball for DW; Chen's "artificial attribute"; ORM conventions): natural keys change, are recycled, are wide or composite, and complicate SCD/history. A defensible framework rule: surrogate PK *plus* a UNIQUE constraint on the natural key (so both positions' integrity goals are met); natural composite PKs are acceptable for pure junction tables.
- **RECOMMENDED:** junction (association) tables use the composite `(a_id, b_id)` as primary key; add a surrogate only when the junction row itself is referenced by other tables or carries its own lifecycle. Grounding: Karwin "ID Required" (the blanket `id` convention is the antipattern), sqlstyle "not scared to use compound keys", Chen/IDEF1X identifying relationships where the child's PK includes the parent's PK (see Q7). Applies: OLTP, general.

## Q3. Integrity: constraints in the database vs the application; FK actions, deferrable constraints, CHECK, exclusion, domains; the "foreign keys in the application" controversy

### Takeaway
Vendor documentation (PostgreSQL, SQL Server), GitLab's database guidelines and Karwin all treat declared constraints (PK, FK, NOT NULL, UNIQUE, CHECK) as the integrity mechanism of record; application-level checks alone "could fail in some unfortunate cases" (GitLab). The counter-position (Alibaba's prohibition of FKs and cascades; PlanetScale/Vitess operating without FKs; gh-ost not supporting FKs) is grounded in sharding, online-DDL tooling and write-amplification concerns, and PlanetScale itself reversed course by implementing FK support in Vitess (GA Feb 2024, unsharded only). ON DELETE policy is contested: GitLab says CASCADE "in 99% of the cases", PlanetScale and Alibaba warn against cascades.

### Cited Findings
**What the engines guarantee**
- PostgreSQL CHECK: "a check constraint is satisfied if the check expression evaluates to true or the null value." "PostgreSQL does not support CHECK constraints that reference table data other than the new or updated row being checked ... If possible, use UNIQUE, EXCLUDE, or FOREIGN KEY constraints to express cross-row and cross-table restrictions." CHECK conditions are assumed immutable. NOT NULL "is functionally equivalent to creating a check constraint CHECK (column_name IS NOT NULL), but in PostgreSQL creating an explicit not-null constraint is more efficient." UNIQUE auto-creates a unique B-tree index. FK: "We say this maintains the referential integrity between two related tables." "The default ON DELETE action is ON DELETE NO ACTION." NO ACTION lets the delete proceed but the constraint "is still required to be satisfied" and can be deferred so other commands may "fix" the situation; "RESTRICT is a stricter setting than NO ACTION ... RESTRICT does not allow the check to be deferred until later in the transaction." CASCADE deletes referencing rows; SET NULL/SET DEFAULT "do not excuse you from observing any constraints." "The declaration of a foreign key constraint does not automatically create an index on the referencing columns." Exclusion constraints "ensure that if any two rows are compared on the specified columns or expressions using the specified operators, at least one of these operator comparisons will return false or null." — [PostgreSQL 18 docs, 5.5 Constraints](https://www.postgresql.org/docs/current/ddl-constraints.html)
- Deferral: "Currently, only UNIQUE, PRIMARY KEY, REFERENCES (foreign key), and EXCLUDE constraints are affected by this setting. NOT NULL and CHECK constraints are always checked immediately when a row is inserted or modified (not at the end of the statement)." Constraints are DEFERRABLE INITIALLY DEFERRED, DEFERRABLE INITIALLY IMMEDIATE, or NOT DEFERRABLE; "DEFERRED constraints are not checked until transaction commit." — [PostgreSQL 18 docs, SET CONSTRAINTS](https://www.postgresql.org/docs/current/sql-set-constraints.html)
- Domains: "A domain is a user-defined data type that is based on another underlying type. Optionally, it can have constraints that restrict its valid values to a subset of what the underlying type would allow." Example `CREATE DOMAIN posint AS integer CHECK (VALUE > 0);`. — [PostgreSQL 18 docs, 8.18 Domain Types](https://www.postgresql.org/docs/current/domains.html)
- SQL Server: primary key "enforces the entity integrity of the table"; a FK constraint "prevents this situation" (orphaned sales orders) and "enforces referential integrity by guaranteeing that changes can't be made to data in the primary key table if those changes invalidate the link." Cascading actions: NO ACTION ("raises an error and the delete or update action on the row in the parent table is rolled back"), CASCADE, SET NULL (FK columns must be nullable), SET DEFAULT. Limits: PK ≤ 32 columns / 900 bytes; a table "can reference a maximum of 253 other tables and columns as foreign keys (outgoing references)"; incoming references raised to 10,000 in SQL Server 2016 (DELETE only). "Unlike primary key constraints, creating a foreign key constraint doesn't automatically create a corresponding index." — [Microsoft Learn: Primary and foreign key constraints (ms.date 2024-07-19)](https://learn.microsoft.com/en-us/sql/relational-databases/tables/primary-and-foreign-key-constraints)
- PostgreSQL wiki: "Don't use rules ... all non-trivial rules are incorrect" — use triggers; "Don't use table inheritance" (use partitioning). — [Don't Do This](https://wiki.postgresql.org/wiki/Don%27t_Do_This)
- Codd 1970 already notes that integrity checking "whenever an insertion, deletion, or key update occurs ... will slow these operations down" and proposes logging and later remediation as an alternative — i.e., the cost/benefit trade-off is as old as the model. — [Codd 1970](https://www.engineering.upenn.edu/~zives/03f/cis550/codd.pdf)

**Pro-database-constraints practice**
- GitLab: "Foreign keys ensure consistency between related database tables." "When creating tables that reference records from other tables, an FK should be added to maintain data integrity." "Ensuring data consistency on the application level could fail in some unfortunate cases, so we might end up with inconsistent data in the table." "Every foreign key must define an ON DELETE clause, and in 99% of the cases this should be set to CASCADE." Avoid Rails `dependent: :destroy`/`:delete` and `before_destroy`/`after_destroy` callbacks ("Rails handles the removal of data, instead of letting the database handle this") unless a database specialist approves. "Indexes are required for all foreign keys and they must be added before the foreign key" — otherwise a delete on the referenced table forces "a full table scan every time a record is deleted from the referenced table"; composite index acceptable only if the FK column is first; partial indexes not acceptable. `_id` suffix only for true associations; `_xid` for third-party IDs; `spec/db/schema_spec.rb` fails if an `_id` column lacks an FK or a registered loose foreign key. — [GitLab: Foreign keys and associations](https://docs.gitlab.com/ee/development/database/foreign_keys/)
- Karwin: "Keyless Entry — Omitting constraints from the schema" is a logical-design antipattern; the book's bonus chapter catalogs FK mini-antipatterns: reversed references, mismatched data types, orphan data, and MySQL-specific ones (incompatible storage engines, references to non-unique indexes). — [SQL Antipatterns Vol. 1](https://pragprog.com/titles/bksap1/sql-antipatterns-volume-1/)
- Kimball (DW): "A null key automatically turns on the referential integrity alarm" — fact-table FKs must never be NULL; use special dimension rows. — [Kimball 1998](https://www.kimballgroup.com/1998/05/surrogate-keys/)

**The "FKs in the application layer" position**
- Alibaba Java Coding Guidelines (MySQL Rules > SQL Rules #6, Mandatory): "Foreign key and cascade update are not allowed. All foreign key related logic should be handled in application layer." Reasoning: "Foreign key and cascading update are suitable for single machine, low parallel systems", not distributed, high-parallel clusters; cascading updates are strongly blocking and "may lead to a DB update storm"; foreign keys "affect DB insertion efficiency." — [Alibaba Java Coding Guidelines](https://alibaba.github.io/Alibaba-Java-Coding-Guidelines/)
- PlanetScale docs (Vitess): reasons not to use FK constraints — "increased locking for data and metadata changes"; column types used by a constraint can't be changed; refactoring "a more complex process involving more steps"; "FOREIGN KEY constraints are difficult to maintain once your data grows and is split over multiple database servers." Alternatives: keep FK *columns* without the CONSTRAINT clause, let the app order DELETE/UPDATE, prefer NO ACTION over ON DELETE CASCADE ("great care"), and batch-clean orphans ("deleting 100 rows at a time"). The page now says FK constraints can be enabled in database settings. — [PlanetScale: Operating without foreign key constraints](https://planetscale.com/docs/vitess/operating-without-foreign-key-constraints)
- PlanetScale engineering (Shlomi Noach & Manan Gupta, Dec 5, 2023): FKs originally "could not ... work with branching and Online DDL"; the shadow-table technique "cannot work with the existing MySQL foreign key constraints implementation"; InnoDB cascades are "hidden from anyone consuming the binary log" (breaking CDC/replication tooling). Solution: Vitess "has to take control" and applies cascades explicitly at VTGate; a patched MySQL `rename_table_preserve_foreign_key`; a fuzzer found bugs around RESTRICT, `-0` values and locking. Caveats: "foreign key constraint support is limited to unsharded/single shard databases"; "there is a non-zero performance impact"; cyclic references between tables disallowed; constraint names change on deploy; reverts may leave orphans. — [The challenges of supporting foreign key constraints](https://planetscale.com/blog/challenges-of-supporting-foreign-key-constraints)
- PlanetScale GA (Taylor Barnett & Rick Branson, Feb 16, 2024): "foreign key constraints are generally available on PlanetScale within any unsharded database"; "over 2,400 PlanetScale databases have enabled foreign key constraints" in the two-month beta; sharded users must "reach out to us." — [Foreign key constraints are now generally available](https://planetscale.com/blog/foreign-key-constraints-are-now-generally-available)
- GitHub's online schema-change tool: "Foreign key constraints are not supported. They may be supported in the future, to some extent." (no reasoning given on the page). — [gh-ost requirements and limitations](https://github.com/github/gh-ost/blob/master/doc/requirements-and-limitations.md)

### Inferences
- **MANDATORY (system-of-record OLTP; general):** declare PK, FK, NOT NULL, UNIQUE and CHECK constraints in the database. Reasoning: engines enforce them atomically under concurrency (PostgreSQL/SQL Server docs); application enforcement "could fail in some unfortunate cases" (GitLab) and yields orphan data (Karwin "Keyless Entry"). The documented exceptions (Alibaba, pre-2024 PlanetScale, gh-ost) are infrastructure constraints — sharding and shadow-table online DDL — not arguments that orphans are acceptable; PlanetScale's own reversal (building FK support into Vitess) is evidence that the market treats FK enforcement as the expected baseline.
- **CONTEXTUAL exception (sharded / online-DDL-constrained MySQL):** where FK constraints are technically unavailable, the framework should require (a) FK *columns* with matching types, (b) indexed FK columns, (c) a scheduled orphan-cleanup job in small batches, and (d) a documented risk acceptance — i.e., PlanetScale's own mitigation list, not silent omission.
- **MANDATORY:** index every FK column (GitLab requires it *before* adding the FK; PostgreSQL and SQL Server both state FKs do not auto-create indexes; unindexed FKs make parent deletes full scans and are the usual cause of the "FKs are slow" complaint echoed by Alibaba). Applies: OLTP, general.
- **MANDATORY:** every FK has an explicit, reviewed ON DELETE/ON UPDATE policy (GitLab rule). Which policy is **CONTESTED**: GitLab — CASCADE in 99% of cases (child rows are owned data; the DB, not Rails, should remove them); PlanetScale — NO ACTION preferred, CASCADE "with great care"; Alibaba — cascades cause "update storms"; SQL Server docs note cascades cannot coexist with certain INSTEAD OF triggers. Defensible framework rule: CASCADE only for strict composition (child cannot exist without parent and is never referenced elsewhere); RESTRICT/NO ACTION for cross-aggregate references; SET NULL only for genuinely optional relationships. Record both sides.
- **RECOMMENDED:** use DEFERRABLE INITIALLY IMMEDIATE for FKs that participate in cyclic or bulk-load inserts; note that NOT NULL and CHECK can never be deferred (PostgreSQL). Prefer NO ACTION over RESTRICT when deferral may be needed (PostgreSQL semantics). Applies: OLTP (PostgreSQL; SQL Server lacks deferrable constraints — not verified here).
- **RECOMMENDED:** express single-row rules as CHECK constraints (remember a CHECK passes on NULL, so pair with NOT NULL), reusable value rules as DOMAINs, and "no-overlap" rules (reservations, validity ranges) as EXCLUDE constraints in PostgreSQL rather than application code or triggers. Applies: OLTP (PostgreSQL-specific for EXCLUDE/DOMAIN).
- **OPTIONAL:** triggers for cross-table rules that CHECK cannot express (PostgreSQL docs point to a trigger for one-time cross-row checks); never rules (wiki).
- Applies-to note: OLAP/DW loads commonly disable or omit FK constraints for load performance and rely on ETL lookups (Kimball's surrogate-key pipeline); the framework should label FK enforcement MANDATORY for OLTP and RECOMMENDED-with-ETL-substitute for DW/lakehouse.

### Gaps
- Karwin's actual text for "Keyless Entry" (arguments and remedies) was not fetched; only the catalog one-liners from the publisher page are available.
- SQL Server deferrable-constraint behaviour and MySQL FK edge cases (e.g., FKs referencing non-unique indexes) were not fetched from vendor docs; the latter is only cited via Karwin's chapter title.
- The original Rails-era "no foreign keys" practice (pre-Rails 4.2 `add_foreign_key`) and GitHub's own schema practice were not confirmed by a fetched primary source; gh-ost's limitation is the only verified artifact.

## Q4. Naming conventions: case, singular vs plural, suffixes, constraint/index naming, reserved words and quoting, identifier limits, ORM defaults, standards

### Takeaway
Credible guides converge on lowercase `snake_case`, no `tbl_`/Hungarian prefixes, no reserved words, no quoting, and typed suffixes (`_id`, `_at`, `_date`, `is_`/`has_`); constraint names should carry a type prefix (GitLab: `pk_`, `fk_`, `index_`, `unique_`, `check_`, `excl_`; EF Core: `PK_`, `AK_`). Singular-vs-plural table names is genuinely contested (Alibaba forbids plurals; Rails, dbt, GitLab and sqlstyle use collective/plural). Identifier limits differ per engine (PostgreSQL 63 bytes, MySQL 64 characters, SQL Server 128, Oracle 128 bytes since 12.2 / 30 before), so 30 bytes is the only fully portable ceiling. ISO/IEC 11179-5 exists as a naming-principles standard but could not be fetched; there is no official Google or Microsoft *schema* style guide.

### Cited Findings
**Style guides**
- sqlstyle.guide (Simon Holywell, CC BY-SA 4.0): "Ensure the name is unique and does not exist as a reserved keyword." "Keep the length to a maximum of 30 bytes." "Names must begin with a letter and may not end with an underscore." "Only use letters, numbers and underscores in names." "Avoid the use of multiple consecutive underscores." Avoid "Descriptive prefixes or Hungarian notation such as `sp_` or `tbl`." Avoid camelCase because "it is difficult to scan quickly." Tables: "Use a collective name or, less ideally, a plural form." "Never give a table the same name as one of its columns and vice versa." Prefer `services` over concatenated `cars_mechanics` for relationship tables. Columns: "Always use the singular name." "Where possible avoid simply using `id` as the primary identifier for the table." Uniform suffixes: `_id`, `_status`, `_total`, `_num`, `_name`, `_seq`, `_date`, `_tally`, `_size`, `_addr`. Custom names for constraints except UNIQUE/PRIMARY KEY/FOREIGN KEY; "Specify the primary key first right after the CREATE TABLE statement." Design: "Object-oriented design principles do not effectively translate to relational database designs." Avoid EAV ("use a specialist product intended for handling such schema-less data instead") and splitting one logical table across many tables (e.g., archiving). — [SQL Style Guide](https://www.sqlstyle.guide/)
- GitLab constraint naming table: Primary Key `pk_<table name>` (`pk_projects`); Foreign Key `fk_<table name>_<column name>[_and_<column name>]*_<foreign table name>` (`fk_projects_group_id_groups`); Index `index_<table name>_on_<column name>[_and_<column name>]*[_and_<column name in partial clause>]*` (`index_repositories_on_group_id`); Unique `unique_<table name>_<column name>[_and_<column name>]*`; Check `check_<table name>_<column name>[_and_<column name>]*[_<suffix>]?` (`check_projects_name_length`, `check_projects_type_enum`); Exclusion `excl_<table name>_<column name>..._[_<suffix>]?` (`excl_reservations_start_at_end_at_no_overlap`). Index names must be lowercase; "PostgreSQL limits identifiers to 63 characters" so `_and_` may be dropped and names abbreviated; "Prefixes are preferred because they make the constraint type easy to spot and group names alphabetically." — [GitLab: Constraints naming conventions](https://docs.gitlab.com/ee/development/database/constraint_naming_convention/)
- dbt: "Schema, table and column names should be in `snake_case`." "Models should be pluralized, for example, `customers`, `orders`, `products`." "The primary key of a model should be named `<object>_id`." "Use the same field names across models where possible ... `customer_id` rather than `user_id` or 'id'." "Do not use abbreviations or aliases." "Avoid reserved words as column names." "Booleans should be prefixed with `is_` or `has_`." "Timestamp columns should be named `<event>_at` (for example, `created_at`) and should be in UTC. If a different timezone is used, this should be indicated with a suffix (`created_at_pt`)." "Dates should be named `<event>_date`." "Events dates and times should be past tense." Versioned models use `_v1`, `_v2`. Column order: "ids, strings, numerics, booleans, dates, and timestamps." Use names "based on the business terminology, rather than the source terminology." — [dbt: How we style our dbt models](https://docs.getdbt.com/best-practices/how-we-style/1-how-we-style-our-dbt-models)
- Mozilla Data Documentation SQL style: uppercase reserved keywords; variable/column names lowercase `snake_case`, begin with a letter, cannot end in underscore, only letters/numbers/underscores; always `AS` for aliases; explicit join types; CTEs over nested subqueries. No table-naming rules beyond this. — [Mozilla SQL Style Guide](https://docs.telemetry.mozilla.org/concepts/sql_style.html)
- Alibaba (Table Schema Rules, Mandatory): "Names of tables and columns must consist of lower case letters, digits or underscores." "Plural nouns are not allowed as table names." Reserved keywords (desc, range, match, delayed) must not be used. Boolean columns "must be named as is_xxx, whose data type should be unsigned tinyint (1 is True, 0 is False)." Mandatory columns `id`, `gmt_create`, `gmt_modified`. — [Alibaba Java Coding Guidelines](https://alibaba.github.io/Alibaba-Java-Coding-Guidelines/)
- PostgreSQL wiki: "Don't use upper case table or column names ... Stick to using a-z, 0-9 and underscore for names and you never have to worry about quoting them." — [Don't Do This](https://wiki.postgresql.org/wiki/Don%27t_Do_This)

**Engine identifier rules and limits**
- PostgreSQL: identifiers "must begin with a letter ... or an underscore"; subsequent characters letters, underscores, digits, or `$` ("dollar signs are not allowed in identifiers according to the letter of the SQL standard"). "The SQL standard will not define a key word that contains digits or starts or ends with an underscore, so identifiers of this form are safe against possible conflict with future extensions of the standard." "By default, NAMEDATALEN is 64 so the maximum identifier length is 63 bytes" (longer names are truncated). "Quoting an identifier also makes it case-sensitive, whereas unquoted names are always folded to lower case" — which "is incompatible with the SQL standard, which says that unquoted names should be folded to upper case ... If you want to write portable applications you are advised to always quote a particular name or never quote it." — [PostgreSQL 18 docs, 4.1 Lexical Structure](https://www.postgresql.org/docs/current/sql-syntax-lexical.html)
- MySQL 8.4: database, table, column, index, constraint, view names max 64 characters (alias 256; compound statement label 16); identifiers are stored as UTF-8 and limits are "measured in characters, not bytes"; auto-generated constraint names (`_ibfk_`, `_chk_`) can exceed the limit when table names are near 64. — [MySQL 8.4: Identifier Length Limits](https://dev.mysql.com/doc/refman/8.4/en/identifier-length.html)
- SQL Server: "Both regular and delimited identifiers must contain from 1 through 128 characters. For local temporary tables, the identifier can have a maximum of 116 characters." Regular identifiers: first character a Unicode letter or `_`, `@`, `#` (`@` = variable, `#` = temp object); "The identifier must not be a Transact-SQL reserved word"; "Don't use embedded spaces or special characters"; delimit with `[]` or `""` (the latter needs `SET QUOTED_IDENTIFIER ON`). Unnamed constraints get system names like `PK__TableX__D7CB9CCCEEF0806C`. Case-sensitivity of identifiers follows database collation. — [Microsoft Learn: Database identifiers (ms.date 2026-04-08)](https://learn.microsoft.com/en-us/sql/relational-databases/databases/database-identifiers)
- Oracle 23: with COMPATIBLE ≥ 12.2 "names must be from 1 to 128 bytes long" (databases 8 bytes; tablespaces/PDBs 30 bytes); below 12.2 "names must be from 1 to 30 bytes long." "Nonquoted identifiers are not case sensitive. Oracle interprets them as uppercase." "Nonquoted identifiers cannot be Oracle SQL reserved words." "Oracle strongly discourages you from using $ and # in nonquoted identifiers." "Oracle does not recommend using quoted identifiers for database object names." Do not use names beginning with `SYS_` or `ORA_`. — [Oracle Database SQL Language Reference 23: Database Object Names and Qualifiers](https://docs.oracle.com/en/database/oracle/oracle-database/23/sqlrf/Database-Object-Names-and-Qualifiers.html)
- Google Cloud Spanner DDL (closest official Google source; no Google SQL *style* guide exists): names for schemas/tables/columns/constraints/indexes up to 128 characters; database IDs lowercase letters, digits, underscores, hyphens; reserved keywords must be backtick-quoted; names differing only by case are not allowed. — search-result summary ([Spanner GoogleSQL DDL reference](https://cloud.google.com/spanner/docs/reference/standard-sql/data-definition-language), not fetched).

**ORM de facto conventions**
- Rails: "Rails will pluralize your model's class names to find the respective database table" (`BookClub` → `book_clubs`); PK `id`; FKs `singularized_table_name_id`; magic columns `created_at`, `updated_at`, `lock_version`, `type` (STI), `(association_name)_type`, `(table_name)_count` — "they are reserved by Active Record." — [Rails Guides: Active Record Basics](https://guides.rubyonrails.org/active_record_basics.html)
- Django: FK column = field name + `_id`; "your code should never have to deal with the database column name." — [Django 5.2 model field reference](https://docs.djangoproject.com/en/5.2/ref/models/fields/)
- EF Core: PK `Id` / `<type name>Id`; constraint names `PK_<type name>`, `AK_<type name>_<property name>`. — [EF Core: Keys](https://learn.microsoft.com/en-us/ef/core/modeling/keys)

**Standards**
- ISO/IEC 11179-5 "Metadata registries (MDR) — Part 5: Naming and identification principles" (2005 edition; a 1995 edition titled "Naming and identification principles for data elements" is withdrawn) "includes principles and rules by which naming conventions can be developed; and describes example naming conventions" covering data element concepts, conceptual domains, data elements and value domains. — search-result abstracts only ([ISO catalogue page for the 1995 edition](https://www.iso.org/standard/1758.html), not fetched; ISO/SCC pages returned 403). A 2015 revision is believed current but was not confirmed.
- Celko's *SQL Programming Style* (2005) opens: "YOUR DATA WILL not come when it is called either if you do not give it a name that is always distinct and recognizable." — [OpenLibrary record](https://openlibrary.org/isbn/9780120887972.json). (The book's reliance on ISO-11179 naming is well known but was not verified from fetched text.)

### Inferences
- **MANDATORY (portability/integrity of identifiers):** lowercase letters, digits and single underscores only; start with a letter; never a reserved word; never rely on quoting or case (PostgreSQL folds to lower, Oracle to upper, SQL Server per collation — mixed-case quoted names break across engines). Length ≤ 63 bytes for PostgreSQL-only shops; ≤ 30 bytes if Oracle < 12.2 portability is required (sqlstyle's 30-byte rule has exactly this origin). Applies: general.
- **RECOMMENDED:** `snake_case` everywhere (sqlstyle, dbt, Mozilla, Alibaba, GitLab, PG wiki all agree; camelCase is "difficult to scan" and requires quoting in PostgreSQL). Applies: general.
- **RECOMMENDED:** typed suffixes — `_id` for keys (Rails/Django/dbt/sqlstyle; GitLab reserves `_id` for FK-backed associations and uses `_xid` for external IDs), `_at` for UTC timestamps, `_date` for dates, past-tense event names, `is_`/`has_` for booleans (dbt; Alibaba `is_xxx`). Prefer `<object>_id` over bare `id` where the key will be joined across models (dbt, sqlstyle) — ORM shops may keep `id` as the PK and `<object>_id` as the FK (Rails). Applies: general; the `_at`/`is_` rules are strongest in analytics layers.
- **RECOMMENDED:** constraint/index names carry a type prefix and the table + columns: `pk_<table>`, `fk_<table>_<cols>_<ref_table>`, `uq_`/`unique_<table>_<cols>`, `ck_`/`check_<table>_<col>_<rule>`, `ix_`/`index_<table>_on_<cols>`, `excl_...` (GitLab pattern; EF Core's `PK_`/`AK_` and SQL Server's auto `PK__` names show the industry norm). Never accept system-generated names (SQL Server's `PK__TableX__D7CB...`, MySQL's `_ibfk_N`) because they differ per environment and break migrations. Applies: general.
- **MANDATORY (anti-pattern):** no `tbl_`/`sp_`/Hungarian prefixes (sqlstyle); no table named the same as a column (sqlstyle); no names starting `SYS_`/`ORA_` on Oracle, `@`/`#` on SQL Server.
- **OPTIONAL/CONTEXTUAL (contested):** singular vs plural table names. Plural/collective: Rails (default), dbt, GitLab examples (`projects`, `groups`), sqlstyle ("collective name or, less ideally, a plural form"). Singular: Alibaba ("Plural nouns are not allowed"), and the relational-purist tradition (table = relation = set of one entity type; Celko — not verified from fetched text). The framework should mandate *consistency* and let the ORM default or house style decide; document the choice.
- Authority ratings: sqlstyle.guide = 3 (widely cited practitioner guide, not an organization standard); GitLab and dbt = 4 for their own ecosystems (organization engineering standards, publicly maintained); Mozilla = 3 (query style, little schema guidance); Alibaba = 3 (official corporate standard, but contested positions and translated); vendor identifier docs = 5; ISO/IEC 11179-5 = 5 as a standard but unverified here.

### Gaps
- ISO/IEC 11179-5 text (object class / property / representation term rules) was not fetched; only catalogue abstracts are available.
- No official Microsoft Azure *schema* naming guidance exists in the fetched material (Azure naming guidance concerns cloud resources; not fetched). No Google or Zalando SQL schema style guide was found; Zalando was not searched.
- Hibernate/JPA naming strategies were not fetched.

## Q5. Data types and precision: money, scale per ISO 4217, timestamps, DATE vs TIMESTAMP, TEXT vs VARCHAR(n), CHAR(n), BOOLEAN, ENUM vs lookup tables, JSON, BLOBs, numeric-looking identifiers, multi-currency

### Takeaway
Exact decimal types for money are mandated by PostgreSQL docs, Alibaba, sqlstyle and Karwin, with scale driven by ISO 4217 minor units (USD 2, JPY 0, KWD/BHD 3, CLF/UYW 4 per the SIX List One file published 2026-09-17); PostgreSQL's `money` type is rejected because it carries no currency. Store instants as `timestamptz`/UTC (PostgreSQL wiki and docs; dbt), avoid `char(n)` and arbitrary `varchar(n)` limits in PostgreSQL, treat ENUM types as acceptable only for truly static sets (PostgreSQL cannot remove enum values; MySQL ENUM has index-vs-string pitfalls; Karwin "31 Flavors"), confine JSONB to genuinely semi-structured atoms, and store codes with leading zeros (ISO 4217 numeric `048` for BHD) as strings.

### Cited Findings
**Money and exactness**
- PostgreSQL: `numeric`/`decimal` are "user-specified precision, exact ... up to 131072 digits before the decimal point; up to 16383 digits after"; "It is especially recommended for storing monetary amounts and other quantities where exactness is required." `real`/`double precision` "are inexact, variable-precision numeric types ... some values cannot be converted exactly to the internal format and are stored as approximations"; "If you require exact storage and calculations (such as for monetary amounts), use the numeric type instead." "Comparing two floating-point values for equality might not always work as expected." Numeric arithmetic is "very slow compared to the integer types, or to the floating-point types." — [PostgreSQL 18 docs, 8.1 Numeric Types](https://www.postgresql.org/docs/current/datatype-numeric.html)
- IEEE 754-2019 (published 2019-07-22, supersedes 754-2008) "specifies interchange and arithmetic formats and methods for binary and decimal floating-point arithmetic" — i.e., binary floats are a defined approximation format, not an exact decimal representation. — [IEEE 754-2019 standard page](https://standards.ieee.org/ieee/754/6210/)
- Alibaba: "Decimals should be typed as decimal. float and double are not allowed." Reason: "It may have precision loss when float and double numbers are stored," which "may lead to incorrect data comparison result." — [Alibaba Java Coding Guidelines](https://alibaba.github.io/Alibaba-Java-Coding-Guidelines/)
- sqlstyle.guide: use `REAL`/`FLOAT` "only where strictly necessary for floating-point math" and prefer `NUMERIC`/`DECIMAL`; "Where possible do not use vendor-specific data types." Avoid storing units separately from values — validate with `CHECK()`. — [SQL Style Guide](https://www.sqlstyle.guide/)
- Karwin: "Rounding Errors — Using FLOAT where exact precision is needed" (physical-design antipattern). — [SQL Antipatterns Vol. 1](https://pragprog.com/titles/bksap1/sql-antipatterns-volume-1/)
- PostgreSQL wiki on `money`: "It doesn't store a currency with the value," output depends on `lc_monetary`, and it loses fractional cents; acceptable only for single-currency, whole-cent, add/subtract-only data; otherwise use `numeric`. — [Don't Do This](https://wiki.postgresql.org/wiki/Don%27t_Do_This)
- ISO 4217 List One (maintained by SIX as ISO 4217 Maintenance Agency; file `Pblshd="2026-09-17"`; elements `Ccy`, `CcyNbr`, `CcyMnrUnts`): JPY 392 minor units 0; USD 840 → 2; EUR 978 → 2; KWD 414 → 3; BHD **048** → 3; CLF 990 → 4; UYW 927 → 4. — [SIX: ISO 4217 List One XML](https://www.six-group.com/dam/download/financial-information/data-center/iso-currrency/lists/list-one.xml) (iso.org product page returned 403).
- dbt: "Price/revenue fields should be in decimal currency (`19.99` for $19.99; many app databases store prices as integers in cents). If a non-decimal currency is used, indicate this with a suffix (`price_in_cents`)." — [dbt style guide](https://docs.getdbt.com/best-practices/how-we-style/1-how-we-style-our-dbt-models)

**Temporal**
- PostgreSQL wiki: "if what you want to store is a point in time, rather than a picture of a clock, use timestamptz." Don't use `timestamp` for UTC: "there is no way for the database to know that UTC is the intended timezone for the column values." Don't use `timetz` ("only implemented for SQL compliance"), `CURRENT_TIME`, or `timestamp(0)` ("it rounds off the fractional part rather than truncating it"). Don't use `BETWEEN` with timestamps (closed interval double-counts boundaries; use `>=` and `<`). — [Don't Do This](https://wiki.postgresql.org/wiki/Don%27t_Do_This)
- PostgreSQL docs: "The SQL standard requires that writing just timestamp be equivalent to timestamp without time zone, and PostgreSQL honors that behavior." For `timestamp with time zone`, "the value is stored internally as UTC, and the originally stated or assumed time zone is not retained"; on output "it is always converted from UTC to the current timezone zone." "We do not recommend using the type time with time zone"; its definition "exhibits properties which lead to questionable usefulness." Both timestamp types are 8 bytes with 1-microsecond resolution; `date` is 4 bytes; precision `p` 0-6. — [PostgreSQL 18 docs, 8.5 Date/Time Types](https://www.postgresql.org/docs/current/datatype-datetime.html)
- dbt: timestamps `<event>_at` "should be in UTC"; dates `<event>_date`. — [dbt style guide](https://docs.getdbt.com/best-practices/how-we-style/1-how-we-style-our-dbt-models)
- Alibaba: `gmt_create`/`gmt_modified` as DATE_TIME (MySQL). — [Alibaba](https://alibaba.github.io/Alibaba-Java-Coding-Guidelines/)

**Strings**
- PostgreSQL docs: "Values of type character are physically padded with spaces to the specified width n"; "There is no performance difference among these three types, apart from increased storage space when using the blank-padded type ... character(n) is usually the slowest of the three because of its additional storage costs. In most situations text or character varying should be used instead." "If you desire to store long strings with no specific upper limit, use text or character varying without a length specifier, rather than making up an arbitrary length limit." — [PostgreSQL 18 docs, 8.3 Character Types](https://www.postgresql.org/docs/current/datatype-character.html)
- PostgreSQL wiki: don't use `char(n)` even for fixed-length identifiers — "it doesn't reject values that are too short, it just silently pads them with spaces"; use `text` with a CHECK. Don't use `varchar(n)` by default (an arbitrary limit "risks future production errors"). — [Don't Do This](https://wiki.postgresql.org/wiki/Don%27t_Do_This)
- Alibaba (MySQL): "The length of varchar should not exceed 5000, otherwise it should be defined as text", ideally "in a separate table in order to avoid its effect on indexing efficiency of other columns." — [Alibaba](https://alibaba.github.io/Alibaba-Java-Coding-Guidelines/) **Conflict** with PostgreSQL's "use text" advice — engine-specific: MySQL row-format and index-prefix constraints differ from PostgreSQL's TOAST.

**Booleans**
- Alibaba: `is_xxx` as `unsigned tinyint (1 is True, 0 is False)` (MySQL has no true BOOLEAN storage type). dbt: boolean columns prefixed `is_`/`has_`. — see above. No fetched source endorses `CHAR(1)` Y/N flags; Karwin's "31 Flavors" covers restricting values in the column definition.

**Enumerations**
- PostgreSQL enum: "static, ordered set of values"; "An enum value occupies four bytes on disk"; labels case-sensitive, max 63 bytes; values can be added and renamed via ALTER TYPE but "Existing values cannot be removed from an enum type, nor can the sort ordering of such values be changed, short of dropping and re-creating the enum type"; different enum types cannot be compared without casts. — [PostgreSQL 18 docs, 8.7 Enumerated Types](https://www.postgresql.org/docs/current/datatype-enum.html)
- MySQL ENUM: values stored as 1-based indexes (0/empty string for invalid input in non-strict mode); max 65,535 elements; "We strongly recommend that you do not use numbers as enumeration values ... it is easy to mix up the strings and the underlying number values"; "ENUM values are sorted based on their index numbers ... 'b' sorts before 'a' for ENUM('b', 'a')". — [MySQL 8.4: The ENUM Type](https://dev.mysql.com/doc/refman/8.4/en/enum.html)
- Karwin: "31 Flavors — Restricting column values in the column definition" is an antipattern (remedy in the book: a lookup table). — [SQL Antipatterns Vol. 1](https://pragprog.com/titles/bksap1/sql-antipatterns-volume-1/)
- GitLab's example check constraint `check_projects_type_enum` shows the alternative of a CHECK-constrained plain column. — [GitLab constraint naming](https://docs.gitlab.com/ee/development/database/constraint_naming_convention/)

**JSON / BLOB**
- PostgreSQL: "most applications should prefer to store JSON data as jsonb"; jsonb "does not preserve white space, does not preserve the order of object keys, and does not keep duplicate object keys." Design guidance: "JSON data is subject to the same concurrency-control considerations as any other data type ... any update acquires a row-level lock on the whole row. Consider limiting JSON documents to a manageable size ... Ideally, JSON documents should each represent an atomic datum that business rules dictate cannot reasonably be further subdivided into smaller datums that could be modified independently." — [PostgreSQL 18 docs, 8.14 JSON Types](https://www.postgresql.org/docs/current/datatype-json.html)
- Karwin: "Phantom Files — Assuming bulky media must be stored as external files" (i.e., the antipattern is the *assumption*; the book weighs DB-stored BLOBs vs file paths); "Entity-Attribute-Value — Using a generic attribute table for variable attributes." — [SQL Antipatterns Vol. 1](https://pragprog.com/titles/bksap1/sql-antipatterns-volume-1/); sqlstyle: for schema-less data "use a specialist product." Fowler: "Serialized LOB — Saves a graph of objects as one serialized large object in a single database field." — [PoEAA catalog](https://martinfowler.com/eaaCatalog/)

### Inferences
- **MANDATORY (all):** exact `DECIMAL/NUMERIC` (or integer minor units) for money; never binary floating point (PostgreSQL docs, Alibaba, sqlstyle, Karwin; IEEE 754 defines binary formats as approximations). Scale = ISO 4217 minor units of the currency; for multi-currency tables use `NUMERIC(p, 4)` or higher (CLF/UYW need 4) *or* integer minor units with a `_in_cents`/`_minor` suffix (dbt convention). Applies: OLTP, OLAP, DW, general.
- **MANDATORY (multi-currency):** an amount column is meaningless without a `currency_code CHAR(3)`/`TEXT CHECK` column holding the ISO 4217 alphabetic code; PostgreSQL's `money` type is rejected precisely because "it doesn't store a currency with the value" (wiki). Applies: general.
- **MANDATORY:** instants stored as `timestamptz` (PostgreSQL) / UTC-normalized timestamp columns; never `timestamp without time zone` for UTC data, never `timetz`; column names `<event>_at` (dbt). Use `date` only for calendar dates without time semantics; use half-open ranges, not BETWEEN, for timestamp filtering. Applies: general.
- **RECOMMENDED (PostgreSQL):** `text` (or `varchar` without length) plus CHECK for real business limits; never `char(n)`. **CONTEXTUAL (MySQL):** bounded `varchar(n)` with `text` moved to a side table for very long values (Alibaba) — record as engine-specific conflict.
- **RECOMMENDED:** native `boolean` where the engine has one; on MySQL `tinyint unsigned` with `is_` prefix (Alibaba); never `CHAR(1)` Y/N (Karwin 31 Flavors — inference from the antipattern).
- **CONTESTED → RECOMMENDED default:** lookup/reference tables (with FK) for value sets that change or need attributes; ENUM types only for sets that are static for the life of the schema (PostgreSQL cannot remove values; MySQL ENUM has index/ordering pitfalls; Karwin). A CHECK constraint on a text column is the middle path GitLab uses (`check_projects_type_enum`).
- **RECOMMENDED:** `jsonb` only for genuinely semi-structured, sparse or externally defined attributes; core entities, keys, money and anything you filter/aggregate on stay relational; keep documents small and atomic (PostgreSQL row-lock guidance). EAV is an antipattern (Karwin; sqlstyle) — `jsonb` with GIN indexing is its sanctioned replacement when flexibility is truly required.
- **RECOMMENDED:** identifiers that look numeric but are codes — phone numbers, postal codes, national IDs, ISO 4217 numeric codes such as `048` — are strings: leading zeros are significant and no arithmetic applies (direct evidence: SIX list `CcyNbr=048` for BHD; MySQL's warning about numeric-looking ENUM confusion is the analogous pitfall). Applies: general.
- **OPTIONAL/CONTEXTUAL:** BLOBs in-database vs object store. Karwin's "Phantom Files" says do not *assume* files must be external (transactions, backups and access control favor in-DB), while sqlstyle and PostgreSQL's row-lock note favor keeping very large or independently updated objects out of hot rows. Decide per object size and lifecycle; store a checksum and content type either way (inference).

### Gaps
- iso.org pages (ISO 4217 overview, edition year) returned 403; minor-unit facts come from the SIX maintenance-agency data file, which is the normative list.
- No vendor documentation on `DECIMAL` for exchange rates/quantities (recommended scale) was fetched; the "≥ 4 decimals for multi-currency" rule is an inference from CLF/UYW minor units.
- SQL Server `datetimeoffset`/`datetime2` and MySQL `TIMESTAMP` vs `DATETIME` UTC semantics were not fetched.
- The explicit "phone/postal/SSN must be strings" rule has no fetched primary source; it is an inference supported by the leading-zero evidence above.

## Q6. NULL semantics: three-valued logic pitfalls, NOT NULL by default, NULL in UNIQUE constraints, sentinel values

### Takeaway
NULL is not a value and silently changes constraint behaviour: a CHECK constraint is satisfied by NULL, a FK row with any NULL referencing column escapes the check unless MATCH FULL, UNIQUE allows duplicate NULL rows by default in PostgreSQL (changeable with `NULLS NOT DISTINCT`, and implementation-defined across engines), and `NOT IN` with a NULL list breaks. Codd himself judged a single NULL insufficient (A-marks/I-marks, 1986-1990); Date's camp rejects NULLs entirely; Kimball forbids NULL foreign keys in fact tables and criticizes sentinel dates. The defensible policy is NOT NULL by default with documented exceptions and no magic sentinel values.

### Cited Findings
- PostgreSQL: "a check constraint is satisfied if the check expression evaluates to true or the null value." UNIQUE: "By default, two null values are not considered equal in this comparison. That means even in the presence of a unique constraint it is possible to store duplicate rows that contain a null value in at least one of the constrained columns. This behavior can be changed by adding the clause NULLS NOT DISTINCT." "The default null treatment in unique constraints is implementation-defined according to the SQL standard, and other implementations have a different behavior. So be careful when developing applications that are intended to be portable." Primary keys require values "both unique and not null" and adding a PK "will force the column(s) to be marked NOT NULL." FK: "Normally, a referencing row need not satisfy the foreign key constraint if any of its referencing columns are null. If MATCH FULL is added ... a referencing row escapes satisfying the constraint only if all its referencing columns are null." — [PostgreSQL 18 docs, 5.5 Constraints](https://www.postgresql.org/docs/current/ddl-constraints.html)
- PostgreSQL wiki: "Don't use NOT IN" — a NULL in the list makes results unexpected and the subquery plan is "horrifically slow (in fact O(N²))"; use `NOT EXISTS`. — [Don't Do This](https://wiki.postgresql.org/wiki/Don%27t_Do_This)
- SQL Server: SET NULL cascade requires nullable FK columns; PK columns "must be defined as not null" (nullability is forced). — [Microsoft Learn: Primary and foreign key constraints](https://learn.microsoft.com/en-us/sql/relational-databases/tables/primary-and-foreign-key-constraints)
- Codd, "More commentary on missing information in relational databases (applicable and inapplicable information)", ACM SIGMOD Record, posted 8 March 1987 — the title documents Codd's split of missing information into applicable (A-mark) and inapplicable (I-mark) kinds; the page exposes only metadata and a PDF link. — [SIGMOD Record archive page](https://sigmodrecord.org/1987/03/08/more-commentary-on-missing-information-in-relational-databases-applicable-and-inapplicable-information/). Search results confirm Codd's *Relational Model for Database Management: Version 2* (1990) "argues in favor of the necessity of introducing the I and A marks instead of the NULL mark" (secondary; not fetched).
- Date, *SQL and Relational Theory: How to Write Accurate SQL Code*, 3rd ed., O'Reilly 2015, ISBN 9781491941171, 563 pp. — [OpenLibrary record](https://openlibrary.org/isbn/9781491941171.json). Date and Darwen's strongly anti-null stance is noted in search results (Wikipedia talk page — authority 1-2; not fetched). Content not fetched.
- Karwin: "Fear of the Unknown — Mishandling NULL values" (query antipattern). — [SQL Antipatterns Vol. 1](https://pragprog.com/titles/bksap1/sql-antipatterns-volume-1/)
- Kimball: "A null key automatically turns on the referential integrity alarm"; use special surrogate rows for anonymous customer / missing / not-applicable; using a real date such as January 1, 2000 to mean "I don't know" is criticized. — [Kimball 1998](https://www.kimballgroup.com/1998/05/surrogate-keys/)
- Kent: when multivalued facts are combined in one record, "blank fields become ambiguous" (is the blank "unknown", "none", or "see other row"?). — [Kent 1983](https://www.bkent.net/Doc/simple5.htm)
- MySQL ENUM: in non-strict mode an invalid value becomes the empty string with index 0 — a silent sentinel. — [MySQL 8.4: ENUM](https://dev.mysql.com/doc/refman/8.4/en/enum.html)

### Inferences
- **MANDATORY:** NOT NULL on all PK columns (engines force it), on all FK columns of DW fact tables (Kimball), and on any column whose absence has no business meaning. Applies: general; the fact-table rule applies to DW/OLAP.
- **RECOMMENDED:** NOT NULL by default; every nullable column needs a written meaning for NULL (unknown vs not applicable — Codd's A/I distinction shows one NULL cannot carry both). Kent's "blank fields become ambiguous" is the normalization-side argument: many nullable columns signal that independent facts were merged into one table and should be split out (4NF/5NF). Applies: OLTP, general.
- **MANDATORY:** pair every CHECK with NOT NULL when the rule must always hold (PostgreSQL: CHECK passes on NULL). Applies: general.
- **RECOMMENDED:** when a UNIQUE constraint includes nullable columns, decide explicitly between default (NULLs distinct — allows duplicates) and `NULLS NOT DISTINCT`, or avoid nullable unique columns; never assume portability (PostgreSQL docs: implementation-defined). Applies: general; `NULLS NOT DISTINCT` is PostgreSQL syntax.
- **MANDATORY (anti-pattern):** no sentinel/magic values (`-1`, `0`, `''`, `9999-12-31`, `1900-01-01`, `'N/A'`) in place of NULL — they corrupt aggregates and joins silently (Kimball on sentinel dates). Kimball's special dimension rows are the sanctioned *explicit* alternative in DW: a real row with a surrogate key and descriptive attributes, not a magic literal. Applies: general; special rows: DW.
- **RECOMMENDED:** use `NOT EXISTS`/`IS DISTINCT FROM` instead of `NOT IN`/`=` where NULLs may appear (wiki). Applies: general (query layer).

### Gaps
- Primary text of Codd's A/I-mark proposal and Date's critique (three-valued-logic paradoxes, "nulls are wrong") were not fetched; only bibliographic records and titles are verified.
- The PostgreSQL version that introduced `NULLS NOT DISTINCT` (15) was not confirmed from release notes; the clause is documented in the current (18) manual.
- SQL Server/MySQL/Oracle behaviour for NULLs in UNIQUE constraints was not fetched; PostgreSQL's warning that other engines differ is the only verified statement.

## Q7. ER modeling and logical vs physical: Chen's model, crow's foot / IDEF1X, conceptual-logical-physical, cardinality, junction tables, supertype/subtype mapping, hierarchies

### Takeaway
Chen (1976) defines entities, relationship sets, attributes as functions into value sets, weak entities (existence dependence), 1:n / m:n mappings and the rectangle/diamond diagram, and prescribes a design procedure ending in "decide primary keys". IDEF1X (NIST FIPS 184, 1993) formalizes identifier-dependent entities, key migration, identifying relationships and category (subtype) relationships "for logical database design". Fowler's PoEAA supplies the physical mapping choices for inheritance (Single Table / Class Table / Concrete Table) and associations (Foreign Key Mapping, Association Table Mapping); Karwin and PostgreSQL's `ltree` cover hierarchy patterns. Codd's own insistence on separating the user model from "machine representation counterparts" is the root of the logical-vs-physical split.

### Cited Findings
- Chen: "An entity is a 'thing' which can be distinctly identified ... A relationship is an association among entities. For instance, 'father-son' is a relationship between two 'person' entities." "A relationship set, Ri, is a mathematical relation among n entities." "An attribute can be formally defined as a function which maps from an entity set or a relationship set into a value set or a Cartesian product of value sets." Attribute and value set "are different concepts although they may have the same name in some cases ... This distinction is not clear in the network model and in many existing data management systems." Diagram: "Each entity set is represented by a rectangular box, and each relationship set is represented by a diamond-shaped box ... The roles of the entities in the relationship are stated." Cardinality: "DEPARTMENT-EMPLOYEE is a 1:n mapping ... PROJECT-WORKER is an m:n mapping"; minimum as well as maximum participation may be specified. Weak entities: DEPENDENT "is a weak entity relation" and "the existence dependence of the dependents on the supporter is also stated." Design steps: "(3) define the value sets and attributes; (4) organize data into entity/relationship relations and decide primary keys." The model is proposed "as a basis for unification of different views of data: the network model, the relational model, and the entity set model." — [Chen 1976, ACM TODS 1(1) March 1976, pp. 9-36](https://www.comp.nus.edu.sg/~lingtw/papers/tods76.chen.pdf)
- Codd 1970 on model vs representation: "Much of the confusion in present terminology is due to failure to distinguish between type and instance (as in 'record') and between components of a user model of the data on the one hand and their machine representation counterparts on the other hand." — [Codd 1970](https://www.engineering.upenn.edu/~zives/03f/cis550/codd.pdf)
- IDEF1X: "a method for designing relational databases", "most useful for logical database design after the information requirements are known"; released by NIST as FIPS Publication 184 in December 1993; adopted by IEEE in 2012. Entities are identifier-independent or identifier-dependent ("meaningless (by definition) without another associated entity instance"). "Every entity has exactly one primary key displayed above the horizontal line in the entity box"; in a connection the parent's PK migrates to the child; in an identifying relationship the child's PK must include attributes inherited from the parent; alternate keys exist but "are not used to describe relationships"; foreign keys are marked (FK). Categorization relationships "represent mutually exclusive subsets of a generic entity", share the generic entity's primary key and are distinguished by a discriminator attribute. DoD standardization "helped IDEF1X avoid the variants that affected ER." — [IDEF1X Data Modeling Method (idef.com)](https://www.idef.com/idef1x-data-modeling-method/). The NIST FIPS 184 PDF was fetched ([nvlpubs.nist.gov FIPS 184](https://nvlpubs.nist.gov/nistpubs/Legacy/FIPS/fipspub184.pdf)) but is a scanned image without extractable text.
- Fowler, PoEAA object-relational structural patterns: "Identity Field — Stores a database ID in an object to link it to its table row." "Foreign Key Mapping — Maps an object association to a foreign key reference between tables." "Association Table Mapping — Stores an association in its own table with foreign keys to the linked tables." "Embedded Value — Maps one object into several fields of another object's table." "Serialized LOB." "Single Table Inheritance — Represents an inheritance hierarchy in one table with columns for all the classes' fields." "Class Table Inheritance — ... one table per class." "Concrete Table Inheritance — ... one table per concrete class." "Inheritance Mappers." — [Catalog of Patterns of Enterprise Application Architecture (page dated 05 March 2003)](https://martinfowler.com/eaaCatalog/)
- Rails implements Single Table Inheritance via the reserved `type` column and polymorphic associations via `(association_name)_type`. — [Rails Guides: Active Record Basics](https://guides.rubyonrails.org/active_record_basics.html)
- PostgreSQL wiki: "Don't use table inheritance" — tied to an object-oriented fad that "didn't actually produce the desired results"; use native partitioning. — [Don't Do This](https://wiki.postgresql.org/wiki/Don%27t_Do_This)
- Karwin: "Naive Trees — Storing and querying hierarchies with simple parent references"; "Polymorphic Associations — Using one foreign key to reference multiple parent tables"; "Metadata Tribbles — Cloning tables or columns to handle scale." — [SQL Antipatterns Vol. 1](https://pragprog.com/titles/bksap1/sql-antipatterns-volume-1/)
- PostgreSQL `ltree` (materialized-path hierarchies): "implements a data type ltree for representing labels of data stored in a hierarchical tree-like structure"; labels ≤ 1000 characters, paths ≤ 65535 labels; operators `@>` (ancestor), `<@` (descendant), `~` lquery, `@` ltxtquery; GiST/B-tree/hash index support; example `SELECT path FROM test WHERE path <@ 'Top.Science';`. — [PostgreSQL 18 docs, F.22 ltree](https://www.postgresql.org/docs/current/ltree.html)
- Kent: normal forms are stated over "record types" (logical), and physical "performance requirements may justify stopping short" — the logical/physical boundary in the normalization literature itself. — [Kent 1983](https://www.bkent.net/Doc/simple5.htm)
- Reference books (bibliographic only): Simsion & Witt, *Data Modeling Essentials*, 3rd ed., Morgan Kaufmann, Nov 4, 2004 (ISBN 9780126445510, 550 pp.) — [OpenLibrary record](https://openlibrary.org/isbn/9780126445510.json); Hoberman, *Data Modeling Made Simple: A Practical Guide for Business and IT Professionals*, 2nd ed., Technics Publications, 2009 (ISBN 9780977140060) — [OpenLibrary record](https://openlibrary.org/isbn/9780977140060.json). Search results note the 2nd edition "has been completely rewritten" with chapters by Simsion, Inmon and Blaha. The ANSI/X3/SPARC three-schema (external/conceptual/internal) framework of 1975 is documented only via encyclopedic search results ([Wikipedia: ANSI-SPARC Architecture](https://en.wikipedia.org/wiki/ANSI-SPARC_Architecture), not fetched; authority 2).

### Inferences
- **RECOMMENDED (process):** conceptual (entities/relationships, Chen) → logical (normalized relations, keys, IDEF1X-style identifying/non-identifying relationships) → physical (engine types, indexes, partitioning, controlled denormalization). Grounding: Codd's user-model vs machine-representation distinction, IDEF1X's self-description as a logical-design method, Kent's physical-performance caveat. Applies: general.
- **MANDATORY (logical):** every relationship has explicit cardinality *and* optionality (Chen: 1:n / m:n plus minimum participation; IDEF1X identifying vs non-identifying) before keys are assigned — Chen's step (4) "decide primary keys" comes after relationship semantics. Applies: general.
- **MANDATORY:** many-to-many relationships are realized by an association/junction table with two FKs (Fowler "Association Table Mapping"; Chen's m:n relationship relations); its PK is the composite of the FKs unless the association has independent identity (see Q2). Applies: general.
- **RECOMMENDED:** identifying relationships (weak entities) propagate the parent key into the child PK (Chen, IDEF1X); for ORM-centric OLTP schemas a surrogate child PK plus a UNIQUE on (parent_id, local_key) is the equivalent (inference).
- **OPTIONAL/CONTEXTUAL (supertype/subtype):** choose among Single Table Inheritance (one table, many NULLable columns, a discriminator — Rails default; fastest, weakest constraints), Class Table Inheritance (supertype table + one table per subtype sharing the PK — the IDEF1X category structure with a discriminator; best integrity, more joins), Concrete Table Inheritance (one table per concrete class; no shared FK target). Do **not** use PostgreSQL table inheritance for this (wiki). Prefer Class Table Inheritance when subtype-specific NOT NULL/FK constraints matter; STI when subtypes differ in few columns.
- **MANDATORY (anti-pattern):** no polymorphic `(*_type, *_id)` pairs as the only link — they cannot be FK-constrained (Karwin). Remedies consistent with Fowler/IDEF1X: a supertype table that all children reference, or one nullable FK per target with a CHECK that exactly one is non-null (exclusive arc) — inference.
- **CONTEXTUAL (hierarchies):** adjacency list (parent_id FK) is correct and FK-enforceable but needs recursive CTEs for subtree queries (Karwin "Naive Trees" — the antipattern is relying on it *alone* when deep-tree queries matter); materialized path via `ltree` (PostgreSQL) gives indexed ancestor/descendant queries; closure tables and nested sets are the other documented alternatives (Karwin). Pick per read/write ratio; keep the adjacency FK even when adding a path column (inference).

### Gaps
- Crow's foot notation's origin (Everest/Barker) and the ANSI/SPARC primary report were not fetched; only encyclopedic search snippets exist.
- Simsion & Witt and Hoberman content (their specific positions on surrogate keys, subtype implementation, and conceptual-vs-logical) was not accessible (publisher 403); bibliographic records only.
- Karwin's remedies for Naive Trees and Polymorphic Associations are known from the book's structure but not quoted from fetched text.

## Q8. Anti-patterns: Karwin's catalog and corroborating sources

### Takeaway
Karwin's *SQL Antipatterns, Volume 1* (Pragmatic Bookshelf, Oct 2022, ISBN 9781680508987) organizes 24 antipatterns plus a foreign-key bonus chapter; nearly every logical/physical item maps to a MANDATORY or RECOMMENDED rule above and is independently corroborated by vendor docs or style guides (Jaywalking/Multicolumn Attributes = 1NF; Keyless Entry = constraints in the DB; Rounding Errors = NUMERIC for money; 31 Flavors = lookup tables; EAV = jsonb or redesign; Naive Trees = hierarchy patterns; Polymorphic Associations = supertype/FK redesign).

### Cited Findings
- Karwin's catalog (publisher page): **Logical design** — Jaywalking ("Storing multiple values in one column as comma-separated lists"), Naive Trees, ID Required ("Applying one primary key convention to every table"), Keyless Entry ("Omitting constraints from the schema"), Entity-Attribute-Value ("Using a generic attribute table for variable attributes"), Polymorphic Associations ("Using one foreign key to reference multiple parent tables"), Multicolumn Attributes ("Adding numbered columns for multivalue data"), Metadata Tribbles ("Cloning tables or columns to handle scale"). **Physical design** — Rounding Errors ("Using FLOAT where exact precision is needed"), 31 Flavors ("Restricting column values in the column definition"), Phantom Files ("Assuming bulky media must be stored as external files"), Index Shotgun ("Adding indexes without a plan"). **Query** — Fear of the Unknown (NULLs), Ambiguous Groups, Random Selection, Poor Man's Search Engine, Spaghetti Query, Implicit Columns. **Application** — Readable Passwords, SQL Injection, Pseudokey Neat-Freak ("Filling gaps in auto-increment keys"), See No Evil, Diplomatic Immunity, Standard Operating Procedures. **Bonus** — Foreign Key Mini-Antipatterns (reversed references, mismatched data types, orphan data; MySQL: incompatible storage engines, references to non-unique indexes). — [SQL Antipatterns, Volume 1](https://pragprog.com/titles/bksap1/sql-antipatterns-volume-1/)

### Inferences
- Framework mapping (label / scope): Jaywalking, Multicolumn Attributes → **MANDATORY** 1NF (general). Keyless Entry → **MANDATORY** constraints in DB (OLTP; RECOMMENDED-with-ETL-substitute in DW). ## Q9. Cross-cutting: where sources conflict, and how to weight them

### Takeaway
Most conflicts are scope conflicts (OLTP vs DW vs sharded MySQL) rather than contradictions; the framework should encode the scope with each rule. The genuinely open debates are singular-vs-plural naming, natural-vs-surrogate OLTP keys, CASCADE-vs-RESTRICT defaults, ENUM-vs-lookup, and FK enforcement under sharding.

### Cited Findings
- Surrogate key type: Kimball — simple integers ([Kimball 1998](https://www.kimballgroup.com/1998/05/surrogate-keys/)) vs dbt — "Keys should be string data types" ([dbt](https://docs.getdbt.com/best-practices/how-we-style/1-how-we-style-our-dbt-models)) vs RFC 9562 — time-ordered UUIDs as surrogate keys for distributed systems ([RFC 9562](https://www.rfc-editor.org/rfc/rfc9562)).
- FK enforcement: GitLab/PostgreSQL/SQL Server/Karwin (declare FKs) vs Alibaba ("not allowed") and PlanetScale docs (operate without) — with PlanetScale's own 2023-2024 reversal ([challenges](https://planetscale.com/blog/challenges-of-supporting-foreign-key-constraints), [GA](https://planetscale.com/blog/foreign-key-constraints-are-now-generally-available)).
- ON DELETE default: GitLab "99% CASCADE" ([GitLab FKs](https://docs.gitlab.com/ee/development/database/foreign_keys/)) vs PlanetScale "NO ACTION ... CASCADE with great care" ([PlanetScale docs](https://planetscale.com/docs/vitess/operating-without-foreign-key-constraints)) vs Alibaba "cascade update not allowed" ([Alibaba](https://alibaba.github.io/Alibaba-Java-Coding-Guidelines/)).
- Table-name number: Alibaba singular ([Alibaba](https://alibaba.github.io/Alibaba-Java-Coding-Guidelines/)) vs Rails/dbt/GitLab/sqlstyle plural-or-collective ([Rails](https://guides.rubyonrails.org/active_record_basics.html), [dbt](https://docs.getdbt.com/best-practices/how-we-style/1-how-we-style-our-dbt-models), [GitLab naming](https://docs.gitlab.com/ee/development/database/constraint_naming_convention/), [sqlstyle](https://www.sqlstyle.guide/)).
- String length: PostgreSQL "use text" ([PG wiki](https://wiki.postgresql.org/wiki/Don%27t_Do_This), [PG docs](https://www.postgresql.org/docs/current/datatype-character.html)) vs Alibaba/MySQL "varchar ≤ 5000 else text in a side table" ([Alibaba](https://alibaba.github.io/Alibaba-Java-Coding-Guidelines/)).
- Identifier length ceilings: 30 bytes (sqlstyle; Oracle < 12.2) vs 63 (PostgreSQL) vs 64 (MySQL) vs 128 (SQL Server; Oracle ≥ 12.2; Spanner) — [sqlstyle](https://www.sqlstyle.guide/), [PostgreSQL](https://www.postgresql.org/docs/current/sql-syntax-lexical.html), [MySQL](https://dev.mysql.com/doc/refman/8.4/en/identifier-length.html), [SQL Server](https://learn.microsoft.com/en-us/sql/relational-databases/databases/database-identifiers), [Oracle](https://docs.oracle.com/en/database/oracle/oracle-database/23/sqlrf/Database-Object-Names-and-Qualifiers.html).
- Case folding: PostgreSQL folds unquoted identifiers to lower case and says this "is incompatible with the SQL standard, which says that unquoted names should be folded to upper case" ([PostgreSQL lexical](https://www.postgresql.org/docs/current/sql-syntax-lexical.html)); Oracle folds to upper ([Oracle](https://docs.oracle.com/en/database/oracle/oracle-database/23/sqlrf/Database-Object-Names-and-Qualifiers.html)).

### Inferences
- Weighting used: standards and vendor manuals (5) settle *semantics* (what NULL does, what CASCADE does, limits); foundational papers (5) settle *definitions* (keys, normal forms, ER constructs); recognized books and major-org engineering standards (4) settle *defaults* (GitLab, Kimball, Karwin, Percona/EDB benchmarks); practitioner guides (3) settle *style* (sqlstyle, dbt, Mozilla, Alibaba). Where a 3-level source contradicts a 5-level source on semantics, the 5 wins; where two 3-4 level sources disagree on style, the framework labels the rule OPTIONAL/CONTEXTUAL and requires consistency.
- Every rule in this document carries a scope tag; the writer should present OLTP-mandatory rules (constraints, 3NF, BIGINT/UUIDv7 keys, NOT NULL default, NUMERIC money, timestamptz) separately from DW rules (integer surrogates, flattened dimensions, special rows instead of NULL FKs, FK checks moved to ETL) and from style rules (naming) that are mandatory only in their *consistency*.

- No lakehouse/data-lake-specific primary source (e.g., Delta/Iceberg constraint semantics) was in scope of this brief; "lakehouse" tags above are inferred from the OLAP/DW reasoning and should be validated by the adjacent researcher covering storage formats.
