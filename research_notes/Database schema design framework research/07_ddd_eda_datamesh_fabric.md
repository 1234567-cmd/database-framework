## Key Question 1 — DDD: bounded contexts, aggregates, entities/value objects, ubiquitous language, context maps; and what microservices.io prescribes for data

### Takeaway
Evans defines the bounded context explicitly in terms of "physical manifestations such as code bases and database schemas," makes the aggregate the unit that governs "transactions and distribution" (synchronous consistency inside, asynchronous across), and makes the ubiquitous language binding on code naming — which together imply: one model per schema, one aggregate per transaction, and table/column names drawn from the context's language. Richardson's microservices.io operationalizes this as Database-per-Service (private tables / schema / server), with Saga, Outbox, CQRS and API Composition as the compensating patterns for the cross-boundary transactions and joins you give up.

### Cited Findings

**Bounded context (Evans, primary source)**
- Formal definition: "bounded context — A description of a boundary (typically a subsystem, or the work of a particular team) within which a particular model is defined and applicable." — [DDD Reference: Definitions and Pattern Summaries (Evans, © 2015, CC BY 4.0, PDF dated 2015-03)](https://www.domainlanguage.com/wp-content/uploads/2016/05/DDD_Reference_2015-03.pdf) (ARCH-01) [all]
- The pattern's resolution names database schemas as a boundary artifact — **MANDATORY** in Evans' wording: "Explicitly define the context within which a model applies. Explicitly set boundaries in terms of team organization, usage within specific parts of the application, and physical manifestations such as code bases and database schemas. Apply Continuous Integration to keep model concepts and terms strictly consistent within these bounds." — [DDD Reference (Evans 2015)](https://www.domainlanguage.com/wp-content/uploads/2016/05/DDD_Reference_2015-03.pdf) [all]
- Why multiple models are inevitable: "Multiple models are inevitable, yet when code based on distinct models is combined, software becomes buggy, unreliable, and difficult to understand." — [DDD Reference (Evans 2015)](https://www.domainlanguage.com/wp-content/uploads/2016/05/DDD_Reference_2015-03.pdf)
- Fowler (15 Jan 2014) cites Evans that "total unification of the domain model for a large system will not be feasible or cost-effective," that boundaries are drawn mainly by "human culture" (different language → different model), and gives as an example of a boundary inside one codebase "the separation between in-memory and relational database models in a single application." He recommends depicting relationships "using a context map" and names Vernon's Chapter 3 as "the best source on drawing context maps." — [BoundedContext (Fowler, 2014-01-15)](https://martinfowler.com/bliki/BoundedContext.html) (ARCH-02) [all]
- Microsoft's .NET microservices guidance states the strong form: "Each BC must have its own model and database; likewise, each microservice owns its related data," and "Each DDD Bounded Context correlates to one business microservice (one or several services)." It also notes the pattern itself "doesn't specify whether the Bounded Context is a distributed service or if it's simply a logical boundary (such as a generic subsystem) within a monolithic-deployment application." — [Data sovereignty per microservice (Microsoft Learn, ms.date 2018-09-20, updated 2022-04-13)](https://learn.microsoft.com/en-us/dotnet/architecture/microservices/architect-microservice-container-applications/data-sovereignty-per-microservice) (ARCH-04) [OLTP]
- Same source on identity across contexts: entities "can have different names in different Bounded Contexts, even when different domain entities share the same identity ... in a user-profile Bounded Context, the User domain entity might share identity with the Buyer domain entity in the ordering Bounded Context." — [Microsoft Learn (2018/2022)](https://learn.microsoft.com/en-us/dotnet/architecture/microservices/architect-microservice-container-applications/data-sovereignty-per-microservice)

**Aggregates as transaction/consistency boundaries**
- Evans' resolution — **MANDATORY** (stated as rules): "Cluster the entities and value objects into aggregates and define boundaries around each. Choose one entity to be the root of each aggregate, and allow external objects to hold references to the root only ... Use the same aggregate boundaries to govern transactions and distribution. Within an aggregate boundary, apply consistency rules synchronously. Across boundaries, handle updates asynchronously. Keep an aggregate together on one server. Allow different aggregates to be distributed among nodes." — [DDD Reference (Evans 2015)](https://www.domainlanguage.com/wp-content/uploads/2016/05/DDD_Reference_2015-03.pdf) [OLTP]
- Motivation in the same text: "Cautious database locking schemes cause multiple users to interfere pointlessly with each other and can make a system unusable." — [DDD Reference (Evans 2015)](https://www.domainlanguage.com/wp-content/uploads/2016/05/DDD_Reference_2015-03.pdf)
- Fowler (23 Apr 2013): "A DDD aggregate is a cluster of domain objects that can be treated as a single unit"; "Transactions should not cross aggregate boundaries"; "Aggregates are the basic element of transfer of data storage - you request to load or save whole aggregates." — [DDD_Aggregate (Fowler, 2013-04-23)](https://martinfowler.com/bliki/DDD_Aggregate.html) (ARCH-02) [OLTP]
- Vernon (Part I, 2011): "aggregate is synonymous with transactional consistency boundary"; "A properly designed aggregate is one that can be modified in any way required by the business with its invariants completely consistent within a single transaction. And a properly designed bounded context modifies only one aggregate instance per transaction in all cases." He immediately softens it: "Limiting the modification of one aggregate instance per transaction may sound overly strict. However, it is a rule of thumb and should be the goal in most cases." — [Effective Aggregate Design Part I (Vernon, 2011-09/10)](https://www.dddcommunity.org/wp-content/uploads/files/pdf_articles/Vernon_2011_1.pdf) via [library page](https://www.dddcommunity.org/library/vernon_2011/) (ARCH-03) [OLTP]
- Vernon's four rules (verbatim headings): "Rule: Model True Invariants In Consistency Boundaries"; "Rule: Design Small Aggregates" (Part I); "Rule: Reference Other Aggregates By Identity" — "Prefer references to external aggregates only by their globally unique identity, not by holding a direct object reference"; "Rule: Use Eventual Consistency Outside the Boundary" — quoting Evans "DDD p128: Any rule that spans AGGREGATES will not be expected to be up-to-date at all times. Through event processing, batch processing, or other update mechanisms, other dependencies can be resolved within some specific time." — [Effective Aggregate Design Part II (Vernon, 2011-11)](https://www.dddcommunity.org/wp-content/uploads/files/pdf_articles/Vernon_2011_2.pdf) [OLTP]
- Vernon on diagnosing bad boundaries: "If you are modifying multiple instances in a single transaction, it may be a strong indication that your consistency boundaries are wrong ... a concept of your ubiquitous language has not yet been discovered." — [Vernon Part II (2011)](https://www.dddcommunity.org/wp-content/uploads/files/pdf_articles/Vernon_2011_2.pdf)
- **CONFLICT (strength of rule):** Fowler states "Transactions should not cross aggregate boundaries" flatly ([Fowler 2013](https://martinfowler.com/bliki/DDD_Aggregate.html)); Vernon lists four "Reasons To Break the Rules": "Reason One: User Interface Convenience" (batch creation of full aggregates), "Reason Two: Lack of Technical Mechanisms" (no messaging/timers for eventual consistency), "Reason Three: Global Transactions" (enterprise 2PC policy), and (per the Part II table of contents) query performance; he adds that "user-aggregate affinity makes the decision to alter multiple aggregate instances in a single transaction more sound." — [Vernon Part II (2011)](https://www.dddcommunity.org/wp-content/uploads/files/pdf_articles/Vernon_2011_2.pdf). Net: **RECOMMENDED** (strong default) rather than absolute.
- Vernon on the query-side consequence: "Limiting a model to using reference only by identity could make it more difficult to serve clients that assemble and render user interface views. You may have to use multiple repositories in a single use case to populate views. If query overhead causes performance issues, it may be worth considering the use of CQRS." — [Vernon Part II (2011)](https://www.dddcommunity.org/wp-content/uploads/files/pdf_articles/Vernon_2011_2.pdf) [OLTP]

**Entities vs value objects (schema implications)**
- Entities: "When an object is distinguished by its identity, rather than its attributes, make this primary to its definition ... Define an operation that is guaranteed to produce a unique result for each object, possibly by attaching a symbol that is guaranteed unique. This means of identification may come from the outside, or it may be an arbitrary identifier created by and for the system, but it must correspond to the identity distinctions in the model. The model must define what it means to be the same thing." — [DDD Reference (Evans 2015)](https://www.domainlanguage.com/wp-content/uploads/2016/05/DDD_Reference_2015-03.pdf) [OLTP]
- Value objects — **MANDATORY** immutability: "When you care only about the attributes and logic of an element of the model, classify it as a value object ... Treat the value object as immutable. Make all operations Side-effect-free Functions ... Don't give a value object any identity." — [DDD Reference (Evans 2015)](https://www.domainlanguage.com/wp-content/uploads/2016/05/DDD_Reference_2015-03.pdf) [OLTP]
- Repositories: "Provide repositories only for aggregate roots that actually need direct access"; unconstrained queries "instantiate a few specific objects from the interior of an aggregate, blindsiding the aggregate root." — [DDD Reference (Evans 2015)](https://www.domainlanguage.com/wp-content/uploads/2016/05/DDD_Reference_2015-03.pdf)
- Domain events (added since the 2004 book): "Domain events are ordinarily immutable, as they are a record of something in the past. In addition to a description of the event, a domain event typically contains a timestamp for the time the event occurred and the identity of entities involved ... often has a separate timestamp indicating when the event was entered into the system and the identity of the person who entered it. When useful, an identity for the domain event can be based on some set of these properties. So, for example, if two instances of the same event arrive at a node they can be recognized as the same." Also: "We keep the aggregates internally consistent at all times, while making other changes asynchronously." — [DDD Reference (Evans 2015)](https://www.domainlanguage.com/wp-content/uploads/2016/05/DDD_Reference_2015-03.pdf) [OLTP][streaming]

**Ubiquitous language → naming**
- Definition: "A language structured around the domain model and used by all team members within a bounded context to connect all the activities of the team with the software." Resolution — **MANDATORY**: "Use the model as the backbone of a language. Commit the team to exercising that language relentlessly in all communication within the team and in the code ... Recognize that a change in the language is a change to the model ... Then refactor the code, renaming classes, methods, and modules to conform to the new model." — [DDD Reference (Evans 2015)](https://www.domainlanguage.com/wp-content/uploads/2016/05/DDD_Reference_2015-03.pdf) [all]
- Fowler (31 Oct 2006): the practice of "building up a common, rigorous language between developers and users"; "software doesn't cope well with ambiguity"; quotes Evans: "Domain experts should object to terms or structures that are awkward or inadequate to convey domain understanding; developers should watch for ambiguity or inconsistency that will trip up design." — [UbiquitousLanguage (Fowler, 2006-10-31)](https://martinfowler.com/bliki/UbiquitousLanguage.html) (ARCH-02) [all]
- Context-map pattern naming: "Name each bounded context, and make the names part of the ubiquitous language." — [DDD Reference (Evans 2015)](https://www.domainlanguage.com/wp-content/uploads/2016/05/DDD_Reference_2015-03.pdf)

**Context map and the relationship patterns (which govern schema sharing between contexts)**
- Context Map: "Identify each model in play on the project and define its bounded context. This includes the implicit models of non-object-oriented subsystems ... Describe the points of contact between the models, outlining explicit translation for any communication, highlighting any sharing, isolation mechanisms, and levels of influence. Map the existing terrain. Take up transformations later." — [DDD Reference (Evans 2015)](https://www.domainlanguage.com/wp-content/uploads/2016/05/DDD_Reference_2015-03.pdf) [all]
- Shared Kernel — the only pattern that explicitly sanctions shared database design — **OPTIONAL/CONTEXTUAL**: "Designate with an explicit boundary some subset of the domain model that the teams agree to share. Keep this kernel small. Within this boundary, include, along with this subset of the model, the subset of code or of the database design associated with that part of the model. This explicitly shared stuff has special status, and shouldn't be changed without consultation with the other team." — [DDD Reference (Evans 2015)](https://www.domainlanguage.com/wp-content/uploads/2016/05/DDD_Reference_2015-03.pdf) [OLTP]
- Customer/Supplier: "downstream priorities factor into upstream planning ... Jointly developed automated acceptance tests can validate the expected interface from the upstream." Conformist: "Eliminate the complexity of translation between bounded contexts by slavishly adhering to the model of the upstream team." Anticorruption Layer: "As a downstream client, create an isolating layer to provide your system with functionality of the upstream system in terms of your own domain model." Open-host Service: "Define a protocol that gives access to your subsystem as a set of services. Open the protocol so that all who need to integrate with you can use it." Published Language: "Use a well-documented shared language that can express the necessary domain information as a common medium of communication ... Many industries establish published languages in the form of data interchange standards." Separate Ways: "Declare a bounded context to have no connection to the others at all." Big Ball of Mud: "Draw a boundary around the entire mess and designate it a big ball of mud. Do not try to apply sophisticated modeling within this context." Partnership (new): "forge a partnership between the teams in charge of the two contexts." — [DDD Reference (Evans 2015)](https://www.domainlanguage.com/wp-content/uploads/2016/05/DDD_Reference_2015-03.pdf) [all]
- Core Domain: "Boil the model down. Define a core domain ... Make the core small. Apply top talent to the core domain." — [DDD Reference (Evans 2015)](https://www.domainlanguage.com/wp-content/uploads/2016/05/DDD_Reference_2015-03.pdf)

**microservices.io (Chris Richardson) data patterns — all pages n.d.**
- Database per Service — **RECOMMENDED** (site frames as the pattern; shared DB as alternative/anti-pattern): "Keep each microservice's persistent data private to that service and accessible only via its API." Three implementation options: "Private-tables-per-service – each service owns a set of tables that must only be accessed by that service; Schema-per-service – each service has a database schema that's private to that service; Database-server-per-service – each service has it's own database server." "Private-tables-per-service and schema-per-service have the lowest overhead." Enforce with "a separate database user per service with access grants." Drawbacks: "Distributed transactions are best avoided because of the CAP theorem"; cross-database joins are challenging; multiple DB technologies are complex. — [Pattern: Database per service (microservices.io, n.d.)](https://microservices.io/patterns/data/database-per-service.html) (ARCH-05) [OLTP]
- Shared Database: "Use a (single) database that is shared by multiple services. Each service freely accesses data owned by other services using local ACID transactions." Benefits: "A developer uses familiar and straightforward ACID transactions to enforce data consistency"; "A single database is simpler to operate." Drawbacks: development-time coupling (schema changes must be coordinated), runtime coupling (one service's long transaction blocks another), "Single database might not satisfy the data storage and access requirements of all services." — [Pattern: Shared database (microservices.io, n.d.)](https://microservices.io/patterns/data/shared-database.html) [OLTP]
- **CONFLICT (within microservices.io):** the Shared Database page is tagged "pattern" and presents it as a valid option, while the Database-per-Service page's related-patterns list calls it the "Shared Database anti-pattern." — [database-per-service](https://microservices.io/patterns/data/database-per-service.html) vs [shared-database](https://microservices.io/patterns/data/shared-database.html). Reading: Shared DB is **OPTIONAL/CONTEXTUAL**, acceptable when operated as a monolith with ACID needs, anti-pattern when services need independent deployability.
- Saga — "a reliably coordinated sequence of local transactions" with choreography ("each local transaction publishes domain events that trigger local transactions in other services") or orchestration ("an orchestrator tells the participants what local transactions to execute"). Example: Order Service creates a `PENDING` order, Customer Service reserves credit, Order Service approves/rejects. Drawbacks: no automatic rollback (compensating transactions must be written) and "lack of isolation (the 'I' in ACID)" requiring "countermeasures, which are design techniques that implement isolation." — [Pattern: Saga (microservices.io, n.d.)](https://microservices.io/patterns/data/saga.html) (ARCH-06) [OLTP]
- Transactional Outbox — **RECOMMENDED** whenever a DB update and message publish must be atomic: the service "inserts messages/events into an outbox table as part of the local transaction"; a "message relay" (Transaction log tailing or Polling publisher) publishes them. "Messages are guaranteed to be sent if and only if the database transaction commits." Issues: "The Message relay might publish a message more than once" → consumers must be idempotent; for NoSQL the outbox is a property of each record. — [Pattern: Transactional outbox (microservices.io, n.d.)](https://microservices.io/patterns/data/transactional-outbox.html) (ARCH-06) [OLTP][streaming]
- Idempotent Consumer — **MANDATORY** with at-least-once delivery: record processed message IDs in a `PROCESSED_MESSAGE` table with primary key `(subscriberId, messageID)` inserted in the same transaction as the business update; a duplicate insert fails, the transaction rolls back and the duplicate is discarded. — [Pattern: Idempotent Consumer (microservices.io, n.d.)](https://microservices.io/patterns/communication-style/idempotent-consumer.html) [OLTP][streaming]
- CQRS — "Define a view database, which is a read-only 'replica' that is designed specifically to support that query"; kept current "by subscribing to domain events"; "Necessary in an event sourced architecture"; drawbacks: "Increased complexity", "Potential code duplication", "Replication lag/eventually consistent views." — [Pattern: CQRS (microservices.io, n.d.)](https://microservices.io/patterns/data/cqrs.html) (ARCH-07) [OLTP][OLAP]
- Event Sourcing (microservices.io): "persists the state of a business entity such an Order or a Customer as a sequence of state-changing events"; "The event store also behaves like a message broker"; drawbacks: "It is a different and unfamiliar style of programming"; "The event store is difficult to query" → requires CQRS and eventually consistent data. — [Pattern: Event sourcing (microservices.io, n.d.)](https://microservices.io/patterns/data/event-sourcing.html) [OLTP]
- API Composition — "an API Composer" invokes the owning services and "performs an in-memory join"; drawback: "Some queries would result in inefficient, in-memory joins of large datasets"; CQRS "is an alternative solution." — [Pattern: API Composition (microservices.io, n.d.)](https://microservices.io/patterns/data/api-composition.html) [OLTP]
- Microsoft (same .NET guide): "distributed data structures mean that you can't make a single ACID transaction across microservices. This in turn means you must use eventual consistency when a business process spans multiple microservices ... you can't create integrity constraints or use distributed transactions between separate databases." Also the monolith's two benefits: "ACID transactions and the SQL language, both working across all the tables." — [Microsoft Learn (2018/2022)](https://learn.microsoft.com/en-us/dotnet/architecture/microservices/architect-microservice-container-applications/data-sovereignty-per-microservice) [OLTP]

### Inferences
- For a schema framework: (1) the bounded context is the unit of schema ownership — Evans names "database schemas" as a boundary manifestation, so at minimum one DB schema (namespace) per context with no cross-schema FKs; (2) the aggregate is the unit of transaction and of row-locking scope — tables for one aggregate (root + children + value-object columns/rows) should be updatable in one local transaction, and references to other aggregates should be stored as IDs (FK to the root's key or a bare identifier), never as owned child rows; (3) value objects map to immutable column groups or owned sub-rows without their own business identity; (4) table/column names should be the ubiquitous-language terms of that context, and the same real-world thing may legitimately have different table names in different contexts (User vs Buyer).
- The context-map relationship patterns are the decision table for shared data: Shared Kernel = a small, explicitly governed shared schema; Customer/Supplier and Open-host/Published Language = integration via contracts (APIs/events/published schemas) rather than table access; Conformist = adopting the upstream's schema verbatim; ACL = a translation layer (staging/translation tables) when the upstream model is poor; Separate Ways = no integration.
- Richardson's three implementation options give the practical ladder for ERP/SaaS: private tables → schema-per-service → server-per-service, with the first two explicitly "lowest overhead." This is where a modular-monolith ERP should start.

## Key Question 2 — Event-Driven Architecture: Fowler's four meanings, CloudEvents/AsyncAPI schemas, event sourcing & CQRS literature, eventual consistency, idempotent consumers

### Takeaway
Fowler's 2017 taxonomy separates event notification, event-carried state transfer, event sourcing and CQRS, warning that "all these patterns are good in the right place and bad when put on the wrong terrain"; CloudEvents fixes the event envelope (id+source uniqueness, type, dataschema URI) and AsyncAPI fixes the channel/message contract (payload schemaFormat), while the event-sourcing literature (Fowler 2005, Microsoft 2026, Young 2017) converges on immutability, append-only streams partitioned by entity, snapshots as an optimization only, upcasting/weak-schema for versioning, optimistic concurrency per stream, and idempotent at-least-once consumers — with Microsoft explicitly labelling event sourcing "a complex pattern that introduces significant trade-offs" best applied selectively (e.g. "a payment ledger").

### Cited Findings

**Fowler's four meanings (7 Feb 2017)**
- Event Notification: "the source system doesn't really care much about the response"; "implies a low level of coupling, and is pretty simple to set up"; danger: "It can be hard to see such a flow as it's not explicit in any program text." — [What do you mean by "Event-Driven"? (Fowler, 2017-02-07)](https://martinfowler.com/articles/201701-event-driven.html) (ARCH-08) [all]
- Event-Carried State Transfer: recipients "update it's own copy of customer data"; gains "greater resilience" and reduced latency; "An obvious down-side of this pattern is that there's lots of data schlepped around and lots of copies"; "more complexity on the receiver, since it has to sort out maintaining all the state." — [Fowler 2017](https://martinfowler.com/articles/201701-event-driven.html) [OLTP][streaming]
- Event Sourcing: "The event store becomes the principal source of truth, and the system state is purely derived from it"; "strong audit capability"; replay gets hard "when results depend on interactions with outside systems"; schema change over time must be handled; "Many people find the event processing adds a lot of complexity"; "There's no need for event processing to be asynchronous." — [Fowler 2017](https://martinfowler.com/articles/201701-event-driven.html) [OLTP]
- CQRS: "Strictly CQRS isn't really about events"; "the gain for using CQRS has to be balanced against the additional complexity of having separate models"; "many of my colleagues are deeply wary of using CQRS, finding it often misused." Closing: "all these patterns are good in the right place and bad when put on the wrong terrain." → all four **OPTIONAL/CONTEXTUAL**. — [Fowler 2017](https://martinfowler.com/articles/201701-event-driven.html) [all]

**Event envelope and contract specs**
- CloudEvents is "a specification for describing event data in a common way," under the CNCF; v1.0.2 released "February 5, 2022"; "On January 25, 2024 CloudEvents was approved as a 'Graduated' project in the CNCF"; formats/bindings include JSON format, HTTP binding, WebSocket binding (v1.0.1), Protobuf batching (v1.0.2); referenced by Amazon EventBridge and Azure Event Grid. — [cloudevents.io (CNCF, n.d.)](https://cloudevents.io/) (ARCH-11) [streaming]
- Core spec (main branch, 1.0.3-wip) — REQUIRED attributes: `id` (non-empty; producers "MUST ensure that `source` + `id` is unique for each distinct event"), `source` (URI-reference; absolute URI recommended), `specversion` ("MUST use a value of `1.0`"), `type` (SHOULD be prefixed with reverse-DNS, e.g. `com.github.pull_request.opened`). OPTIONAL: `datacontenttype` (RFC 2046; JSON implied when absent in JSON format), `dataschema` (URI; "Incompatible changes to the schema SHOULD be reflected by a different URI"), `subject`, `time` (RFC 3339). Attribute names: lowercase ASCII letters/digits, SHOULD NOT exceed 20 chars; `data` reserved; extension attributes allowed with no spec-defined meaning; "This specification does not place any restriction on the type of this information" (data). → envelope fields **MANDATORY** if you claim CloudEvents conformance. — [CloudEvents core spec (GitHub, main, 1.0.3-wip)](https://github.com/cloudevents/spec/blob/main/cloudevents/spec.md) [streaming]
- AsyncAPI 3.0.0: "The AsyncAPI Specification is a project used to describe message-driven APIs in a machine-readable format"; protocol-agnostic (AMQP, MQTT, Kafka, WebSockets); "A channel is an addressable component, made available by the server, for the organization of messages"; operations have `action` `send`/`receive`; Message Object has `headers` ("MUST NOT define the protocol headers"), `payload`, `correlationId`, `contentType`, `traits`. Payload `schemaFormat`: default AsyncAPI Schema Object (JSON-Schema-based); required support for AsyncAPI Schema and JSON Schema Draft 07; recommended Avro 1.9.0, OpenAPI 3.0.0 Schema, RAML 1.0, Protobuf 2/3; "Custom values are allowed but their implementation is OPTIONAL." — [AsyncAPI Specification v3.0.0](https://www.asyncapi.com/docs/reference/specification/v3.0.0) (ARCH-12) [streaming]

**Event sourcing literature**
- Fowler (12 Dec 2005): "Capture all changes to an application state as a sequence of events." **CONFLICT/nuance with his own 2017 and with Microsoft:** "The official system of record can either be the event logs or the current application state" (2005) vs 2017's "The event store becomes the principal source of truth." Snapshots: "New snapshots can be made at any time in parallel without bringing down the running application." Temporal query: "We can determine the application state at any point in time." Reversal: "If we find a past event was incorrect, we can compute the consequences by reversing it and later events"; "Reversal is the most straightforward when the event is cast in the form of a difference." Code change taxonomy: new features (reprocess), bug fixes ("make the fix and reprocess the events"), temporal logic (strategy objects tied to dates; avoid bi-temporal unless needed). External systems: wrap in gateways aware of replay — "If the domain logic calls PaymentGateway.send it should do so whether or not you are in replay mode"; record external query responses for replay. — [Event Sourcing (Fowler, 2005-12-12)](https://martinfowler.com/eaaDev/EventSourcing.html) (ARCH-09) [OLTP]
- Microsoft Azure Architecture Center (ms.date 2026-03-27; page updated 2026-09-25) — headline caution: "Event sourcing is a complex pattern that introduces significant trade-offs. It changes how you store data, handle concurrency, evolve schemas, and query state. It's costly to migrate to or from ... For most systems and most parts of a system, traditional data management is sufficient." Store design: "Each entity in an event-sourced system has its own eventstream"; "event stores partition naturally by entity ID"; options are "a purpose-built database designed for append-only eventstreams or a general-purpose relational or document database with an append-only table"; "Don't confuse an event store with an eventstream message broker. Message brokers such as Apache Kafka typically lack per-entity stream queries and optimistic concurrency ... they aren't a substitute for an event store." — [Event Sourcing pattern (Microsoft Learn, 2026)](https://learn.microsoft.com/en-us/azure/architecture/patterns/event-sourcing) (ARCH-10) [OLTP]
- **CONFLICT:** Microsoft's "Don't confuse an event store with an eventstream message broker" vs microservices.io's "The event store also behaves like a message broker" ([microservices.io event-sourcing](https://microservices.io/patterns/data/event-sourcing.html)). Reconciled reading: the store may *publish* events, but a Kafka-style log is not a substitute for a per-entity, optimistically-concurrent store.
- Microsoft's issues list (verbatim bullet heads): Event design ("an event that records *two seats were reserved* is more valuable than an event that records *remaining seats changed to 42*"); Eventual consistency; Versioning events — **MANDATORY** immutability: "you should never update the event data. The only way to update an entity or undo a change is to add a compensating event"; four schema-evolution strategies: "Tolerant deserialization", "Event versioning" (version in envelope or type name), "Upcasting" (chainable, "The stored events remain unchanged"), "In-place migration" ("breaks immutability and should be a last resort"); Event ordering (timestamp + "incremental identifier"; store rejects duplicate entity-id+event-id); Event querying ("There's no standard approach or existing mechanisms, such as SQL queries"); Entity state re-creation/snapshots ("Snapshots are an optimization, not a replacement for the eventstream"); Conflict handling (optimistic concurrency per stream; cross-entity conflicts need business reconciliation); Idempotency ("Event delivery to consumers is typically *at least once* ... **Eventual consistency and idempotent consumers**
- Evans (2015): "The state of a distributed system cannot be kept completely consistent at all times. ### Inferences
- Minimum event-store schema implied by the sources: `stream_id` (entity/aggregate id), `sequence_no` (per-stream, unique with stream_id → optimistic concurrency), `event_type` (+ version), `occurred_at`, `recorded_at`, `payload` (JSON/Avro per `dataschema`), `metadata` (correlation/causation/actor); separate `snapshot` table; PII held outside or crypto-shredded. This is a direct composite of Evans' domain-event fields, Microsoft's ordering/idempotency rules and CloudEvents attributes.
- Outbox table implied by Richardson + Microsoft: `outbox(id, aggregate_type, aggregate_id, event_type, payload, created_at, published_at)` written in the business transaction; relay via CDC/log tailing; consumers keep a processed-message table.
- For an ERP/financial system, the sources' own criteria (auditability, intent capture, conflict avoidance, ledgers) place event sourcing as **RECOMMENDED for ledger/payment/order streams** and **not recommended for reference/master data** ("lookup tables or catalogs").

## Key Question 3 — Data Mesh: Dehghani's four principles, data product quantum/output ports, polyglot storage, global vs local policies, critiques and adoption lessons

### Takeaway
Dehghani (2019, 2020, 2022 book) relocates analytical data ownership to the operational domain, defines the data product as an "architectural quantum" of code + data/metadata + infrastructure served polyglot ("events, batch files, relational tables, graphs") under federated computational governance where "the domain data model is a concern that should be localized to a domain" but cross-domain identifiers are global; Thoughtworks' own Radar never moved data mesh beyond Trial (2020–2022) and warns of "high integration costs" and vendor distraction, while Google, AWS, JPMorgan and Zalando converge on "decentralized ownership, centralized governance/infrastructure" and share-in-place rather than copy.

### Cited Findings

**Dehghani 2019 (martinfowler.com, 20 May 2019)**
- Three failure modes of lake/warehouse platforms: "Centralized and monolithic" ("We have moved away from domain oriented data ownership to a centralized domain agnostic data ownership"); "Coupled pipeline decomposition" ("It's decomposed orthogonally to the axis of change"); "Siloed and hyper-specialized ownership" (engineers "siloed from the operational units of the organization"). — [How to Move Beyond a Monolithic Data Lake to a Distributed Data Mesh (Dehghani, 2019-05-20)](https://martinfowler.com/articles/data-monolith-to-mesh.html) (ARCH-14) [OLAP][lakehouse]
- Domain-oriented data: "source domain datasets represent the facts and reality of the business" (source-aligned) vs consumer-aligned datasets shaped for use cases and regenerable; "The architectural quantum in a domain oriented data platform, is a domain and not the pipeline stage"; "Domains need to host and serve their domain datasets in an easily consumable way." — [Dehghani 2019](https://martinfowler.com/articles/data-monolith-to-mesh.html)
- Data-as-a-product qualities — **MANDATORY** for a "data product" by her definition: Discoverable (central catalog with metadata/lineage), Addressable ("global addressing convention"), Trustworthy and truthful (SLOs for quality), Self-describing (documented schemas/semantics, sample data), Interoperable (global standards, e.g. shared entity identifiers), Secure (per-product access control with central policies); requires a "data product owner" and embedded data engineers. ### Inferences
- A data product's output port, in schema terms, is a versioned, documented, access-controlled projection (view/table/topic/file) with a declared schema + SLA + quality checks — exactly the ODCS section list; Dehghani's "self-describing/addressable/trustworthy" attributes map 1:1 onto ODCS `schema`, `servers`, `slaProperties`/`quality`. - Practitioner evidence (Thoughtworks Radar, Zalando, JPMorgan) suggests the implementable core is "domain ownership + product standards + central platform/governance," not full technological decentralization.

## Key Question 5 — Implications: mapping bounded contexts to schemas/databases in ERP/SaaS; when a shared database is acceptable; data-product output schemas vs data contracts

### Takeaway
The sources support a graded rule: one bounded context ↔ one schema namespace is the floor (Evans names "database schemas" as a boundary artifact; Richardson's "schema-per-service" is "lowest overhead"), separate database servers are only required when deployment/scaling independence or storage-type divergence demands it, a shared database remains legitimate for a modular monolith that needs cross-module ACID and SQL (Richardson, Microsoft) provided ownership and schema-change governance are explicit (Evans' Shared Kernel: "Keep this kernel small"), and analytical sharing should go through data-product output ports whose schema + SLA + quality terms are exactly what a data contract (ODCS) encodes.

### Cited Findings
- Evans: boundaries set "in terms of team organization, usage within specific parts of the application, and physical manifestations such as code bases and database schemas." — [DDD Reference (Evans 2015)](https://www.domainlanguage.com/wp-content/uploads/2016/05/DDD_Reference_2015-03.pdf) → **MANDATORY**: a context must have an explicit schema boundary. [OLTP]
- Richardson: "Private-tables-per-service and schema-per-service have the lowest overhead. Using a database server per service is necessary if a service needs its own database server ... to handle high throughput"; enforce "a separate database user per service with access grants." — [Database per service (microservices.io, n.d.)](https://microservices.io/patterns/data/database-per-service.html) → server-per-context **OPTIONAL/CONTEXTUAL** (throughput/storage-type driven). [OLTP]
- Richardson on Shared Database: "A developer uses familiar and straightforward ACID transactions to enforce data consistency"; "A single database is simpler to operate"; costs are schema-change coordination and runtime interference. — [Shared database (microservices.io, n.d.)](https://microservices.io/patterns/data/shared-database.html) [OLTP]
- Microsoft: the monolith's "two important benefits: ACID transactions and the SQL language, both working across all the tables"; "The Bounded Context pattern, however, doesn't specify whether the Bounded Context is a distributed service or if it's simply a logical boundary (such as a generic subsystem) within a monolithic-deployment application"; "defining a service for each Bounded Context is a good place to start. But you don't have to constrain your design to it"; the centralized DB "initially looks simpler ... But the reality is you end up with huge tables that serve many different subsystems, and that include attributes and columns that aren't needed in most cases." — [Microsoft Learn (2018/2022)](https://learn.microsoft.com/en-us/dotnet/architecture/microservices/architect-microservice-container-applications/data-sovereignty-per-microservice) [OLTP]
- **CONFLICT:** Microsoft's "Each BC must have its own model and database" (strong) vs Evans' "database schemas" (a schema suffices) vs Richardson's three-option ladder. Resolution offered by Microsoft itself: the BC pattern does not require physical separation; the microservice pattern adds it.
- Evans' Shared Kernel is the sanctioned exception for a shared schema: "Keep this kernel small ... the subset of code or of the database design associated with that part of the model ... shouldn't be changed without consultation with the other team." — [DDD Reference (Evans 2015)](https://www.domainlanguage.com/wp-content/uploads/2016/05/DDD_Reference_2015-03.pdf) → shared reference/master tables in an ERP are **OPTIONAL/CONTEXTUAL** under Shared Kernel governance. [OLTP]
- Transaction scoping: Evans "Use the same aggregate boundaries to govern transactions and distribution"; Vernon "one aggregate instance per transaction ... a rule of thumb"; cross-aggregate rules "will not be expected to be up-to-date at all times." — [DDD Reference (Evans 2015)](https://www.domainlanguage.com/wp-content/uploads/2016/05/DDD_Reference_2015-03.pdf); [Vernon Part II (2011)](https://www.dddcommunity.org/wp-content/uploads/files/pdf_articles/Vernon_2011_2.pdf) [OLTP]
- Cross-context consistency and queries: Saga for transactions ("without using distributed transactions"), Outbox for atomic publish, CQRS/view DBs or API Composition for joins. — [Saga](https://microservices.io/patterns/data/saga.html); [Transactional outbox](https://microservices.io/patterns/data/transactional-outbox.html); [CQRS](https://microservices.io/patterns/data/cqrs.html); [API Composition](https://microservices.io/patterns/data/api-composition.html) (all microservices.io, n.d.) [OLTP]
- Microsoft CQRS: the "foundational level" is separate read/write models over "a single underlying database" — i.e. CQRS does not require a second database. — [CQRS pattern (Microsoft, 2025/2026)](https://learn.microsoft.com/en-us/azure/architecture/patterns/cqrs) → separate read store **OPTIONAL/CONTEXTUAL**. [OLTP][OLAP]
- Event sourcing fit for finance: "Apply it selectively to the parts of your system that it benefits the most, such as a payment ledger or order-processing pipeline"; use CRUD for "user profile management or application configuration"; not for "lookup tables or catalogs"; PII must be kept out of the immutable store or crypto-shredded. — [Microsoft Event Sourcing (2026)](https://learn.microsoft.com/en-us/azure/architecture/patterns/event-sourcing) [OLTP]
- Analytical sharing: Dehghani — domains "host and serve their domain datasets in an easily consumable way" as source-aligned products; "the domain data model is a concern that should be localized to a domain" while cross-domain identifiers are global. — [Dehghani 2019](https://martinfowler.com/articles/data-monolith-to-mesh.html); [Dehghani 2020](https://martinfowler.com/articles/data-mesh-principles.html) [OLAP][lakehouse]
- Output-port forms in practice: "a table, view, structured file, topic, or stream," e.g. BigQuery authorized views and Pub/Sub topics (Google); product-specific lakes shared in place via Lake Formation (JPMorgan). — [Google Cloud data mesh (n.d.)](https://docs.cloud.google.com/architecture/data-mesh); [JPMorgan (2021)](https://aws.amazon.com/blogs/big-data/how-jpmorgan-chase-built-a-data-mesh-architecture-to-drive-significant-value-to-enhance-their-enterprise-data-platform/) [OLAP][lakehouse][streaming]
- Contract encoding: ODCS sections (Schema, Data quality, SLA, Servers, Team/Roles, Pricing, Support) = "the agreement between a data producer and consumers." — [ODCS (GitHub, v3.2.0)](https://github.com/bitol-io/open-data-contract-standard) [OLAP][lakehouse][streaming]; Zalando: data quality is "A Contract between Consumer and Producer." — [Zalando/Thoughtworks 2020](https://www.slideshare.net/slideshow/data-mesh-in-practice-how-europes-leading-online-platform-for-fashion-goes-beyond-the-data-lake-236728093/236728093); Thoughtworks: products should publish "quality and SLI metrics such as freshness, completeness, and consistency." — [Data product thinking (2025)](https://www.thoughtworks.com/radar/techniques/data-product-thinking)
- Event-level contract: CloudEvents `dataschema` URI with "Incompatible changes to the schema SHOULD be reflected by a different URI"; AsyncAPI `schemaFormat` (JSON Schema/Avro/Protobuf) per message. — [CloudEvents spec](https://github.com/cloudevents/spec/blob/main/cloudevents/spec.md); [AsyncAPI 3.0.0](https://www.asyncapi.com/docs/reference/specification/v3.0.0) [streaming]

### Inferences (framework rules derived from the above)
- **MANDATORY** [OLTP]: every table belongs to exactly one bounded context; contexts are at least separate schemas/namespaces; no foreign keys across context boundaries; cross-context references stored as identifiers (Vernon's reference-by-identity, Microsoft's shared-identity example).
- **MANDATORY** [OLTP]: tables of one aggregate are the unit of a local transaction; invariants that must hold atomically live inside one aggregate's tables; anything spanning aggregates is reconciled asynchronously (Evans, Vernon) via outbox + idempotent consumers (Richardson, Microsoft).
- **RECOMMENDED** [OLTP]: in a modular-monolith ERP, one database server with schema-per-context and per-context DB users (Richardson's "lowest overhead" option); promote to database-server-per-context only when throughput, storage type, or independent deployment require it. Shared reference/master data is allowed only as a small, explicitly governed Shared Kernel.
- **RECOMMENDED** [OLTP]: naming — table and column names are ubiquitous-language terms of their context; the same business thing may carry different names in different contexts (User/Buyer), and a context's name is itself part of the language (e.g. schema name = context name).
- **OPTIONAL/CONTEXTUAL** [OLTP]: event sourcing for ledgers/payments/orders (Microsoft's own examples) with an append-only, per-entity stream, optimistic concurrency, snapshots, PII outside the stream; CRUD elsewhere. CQRS read models as views in the same database first; separate read store only for scale/different storage model.
- **RECOMMENDED** [OLAP/lakehouse/streaming]: each context publishes source-aligned data products through output ports (view/table/topic/file) governed by a data contract (ODCS-style schema + quality + SLA + owner); global policies constrain identifiers, classifications and PII; the internal OLTP schema is never the shared surface.
- Data fabric adds a cross-cutting **RECOMMENDED** [all]: every schema object carries machine-readable business metadata (description, classification, owner, lineage) so catalog/active-metadata tooling can automate discovery and policy.

### Gaps
- No source fetched gives a quantitative threshold (e.g. table count, team count, TPS) for when to split from schema-per-context to server-per-context; Richardson only says "high throughput."
- No fetched source addresses multi-tenant SaaS schema strategies (shared schema with tenant_id vs schema-per-tenant) within the DDD/mesh literature; Vernon's examples carry `TenantId` in aggregates but do not prescribe a storage layout.
- No source directly links Dehghani's output ports to ODCS; the mapping is an inference.
