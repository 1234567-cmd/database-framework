# Warehouse Modeling Methodologies: Kimball, Inmon/CIF, Data Vault 2.0, 3NF EDW, One Big Table, Anchor Modeling, and Medallion

**Scope statement.** Everything in this file is OLAP / analytical data-warehouse scope (data_warehouse, data_lake/lakehouse, OLAP). None of these methodologies is a prescription for OLTP transactional schemas; where a source mentions OLTP (e.g., Oracle noting 3NF "has a long heritage in online transaction processing (OLTP) systems"), it is only to contrast it with warehouse design.

**Source-authority convention used below.** [A5] = official methodology body / vendor docs / peer-reviewed paper; [A4] = recognized book or major-organization engineering blog or original author writing on his own channel; [A3] = reputable tool docs or well-known practitioner; [A2] = community forum / lesser-known blog / un-refereed preprint. Rule labels: **MANDATORY** = the source states it as a rule ("must", "never", "always"); **RECOMMENDED** = the source advises it ("should", "recommend", "best practice"); **OPTIONAL/CONTEXTUAL** = the source presents it as permissible or situational.

Research date: 2026-11-07 (all URLs below were opened on that date unless marked otherwise).

## Key Question 1 — Kimball dimensional modeling: official techniques, rules on surrogate keys and NULL foreign keys, bus architecture

### Takeaway
The Kimball Group's single "official" list of techniques is the 2013 "Kimball Dimensional Modeling Techniques" document, explicitly "drawn from The Data Warehouse Toolkit, Third Edition." Its hard rules are: declare the grain first and never mix grains; fact-table foreign keys are never NULL (use a default dimension row instead); every dimension gets an anonymous sequential integer surrogate key (the date dimension is the only exemption); integration happens through conformed dimensions planned on the bus matrix.

### Cited Findings

**Provenance and canonical text**
- The techniques document states: "Ralph Kimball introduced the data warehouse/business intelligence industry to dimensional modeling in 1996 with his seminal book, The Data Warehouse Toolkit... Drawn from The Data Warehouse Toolkit, Third Edition (coauthored by Ralph Kimball and Margy Ross, 2013), here are the 'official' Kimball dimensional modeling techniques." — [Kimball Dimensional Modeling Techniques (PDF, 2013)](https://www.kimballgroup.com/wp-content/uploads/2013/08/2013.09-Kimball-Dimensional-Modeling-Techniques11.pdf) [A5]; index of the same techniques with one page per technique: [Dimensional Modeling Techniques](https://www.kimballgroup.com/data-warehouse-business-intelligence-resources/kimball-techniques/dimensional-modeling-techniques/) (n.d.; page attributes content to the 3rd edition) [A5].
- Publisher record: *The Data Warehouse Toolkit: The Definitive Guide to Dimensional Modeling, 3rd Edition*, Ralph Kimball and Margy Ross, Wiley, July 2013, ISBN 978-1-118-53080-1 (paperback), 608 pages; new in the 3rd edition: "Updated and enhanced star schema dimensional modeling patterns," "Two new chapters on ETL techniques," "New and expanded business matrices for 12 case studies." — [Wiley: The Data Warehouse Toolkit, 3rd Edition](https://www.wiley.com/en-us/The+Data+Warehouse+Toolkit%3A+The+Definitive+Guide+to+Dimensional+Modeling%2C+3rd+Edition-p-9781118530801) (July 2013) [A4].

**Four-step design process — MANDATORY sequence (Kimball)**
- "The four key decisions made during the design of a dimensional model include: 1. Select the business process. 2. Declare the grain. 3. Identify the dimensions. 4. Identify the facts." Business data governance representatives "must participate in this detailed design activity." — [Kimball Techniques PDF](https://www.kimballgroup.com/wp-content/uploads/2013/08/2013.09-Kimball-Dimensional-Modeling-Techniques11.pdf) (2013) [A5].
- "Each business process corresponds to a row in the enterprise data warehouse bus matrix." — same source.

**Grain — MANDATORY**
- "Declaring the grain is the pivotal step in a dimensional design. The grain establishes exactly what a single fact table row represents. The grain declaration becomes a binding contract on the design. The grain must be declared before choosing dimensions or facts because every candidate dimension or fact must be consistent with the grain... Each proposed fact table grain results in a separate physical table; different grains must not be mixed in the same fact table." — [Kimball Techniques PDF](https://www.kimballgroup.com/wp-content/uploads/2013/08/2013.09-Kimball-Dimensional-Modeling-Techniques11.pdf) (2013) [A5].
- Atomic grain — RECOMMENDED (strongly): "We strongly encourage you to start by focusing on atomic-grained data because it withstands the assault of unpredictable user queries; rolled-up summary grains are important for performance tuning, but they pre-suppose the business's common questions." — same source. Restated as Rule 1 "Load detailed atomic data into dimensional structures" and Rule 4 "Ensure that all facts in a single fact table are at the same grain or level of detail" in [The 10 Essential Rules of Dimensional Modeling](https://www.kimballgroup.com/2009/05/the-10-essential-rules-of-dimensional-modeling/) (Margy Ross, May 29, 2009) [A5].

**Fact table types (Kimball)**
- Transaction fact table: "A row in a transaction fact table corresponds to a measurement event at a point in space and time... Transaction fact tables may be dense or sparse because rows exist only if measurements take place." — [Kimball Techniques PDF](https://www.kimballgroup.com/wp-content/uploads/2013/08/2013.09-Kimball-Dimensional-Modeling-Techniques11.pdf) (2013) [A5].
- Periodic snapshot: "A row in a periodic snapshot fact table summarizes many measurement events occurring over a standard period, such as a day, a week, or a month. The grain is the period, not the individual transaction... These fact tables are uniformly dense in their foreign keys." — same source.
- Accumulating snapshot: "summarizes the measurement events occurring at predictable steps between the beginning and the end of a process... There is a date foreign key in the fact table for each critical milestone... the accumulating fact table row is revisited and updated. This consistent updating of accumulating snapshot fact rows is unique among the three types of fact tables." — same source.
- Factless fact table: "the event merely records a set of dimensional entities coming together at a moment in time... Factless fact tables can also be used to analyze what didn't happen" via a coverage table minus an activity table. — same source.
- Rule 4 adds: "Every fact table has one of three grain types: transactional, periodic snapshot, or accumulating snapshot." — [10 Essential Rules](https://www.kimballgroup.com/2009/05/the-10-essential-rules-of-dimensional-modeling/) (2009) [A5].
- Additivity: facts are additive, semi-additive (e.g., balances, "additive across all dimensions except time"), or non-additive (ratios); store additive components and compute ratios in the BI layer. — [Kimball Techniques PDF](https://www.kimballgroup.com/wp-content/uploads/2013/08/2013.09-Kimball-Dimensional-Modeling-Techniques11.pdf) (2013) [A5].

**NULLs in fact tables — MANDATORY (no NULL foreign keys)**
- "Null-valued measurements behave gracefully in fact tables. The aggregate functions (SUM, COUNT, MIN, MAX, and AVG) all do the 'right thing' with null facts. However, nulls must be avoided in the fact table's foreign keys because these nulls would automatically cause a referential integrity violation. Rather than a null foreign key, the associated dimension table must have a default row (and surrogate key) representing the unknown or not applicable condition." — [Kimball Techniques PDF](https://www.kimballgroup.com/wp-content/uploads/2013/08/2013.09-Kimball-Dimensional-Modeling-Techniques11.pdf) (2013) [A5].
- Rule 5: "Fact table foreign keys should never be null." Many-to-many dimension relationships are resolved with "a dual-keyed bridge table." — [10 Essential Rules](https://www.kimballgroup.com/2009/05/the-10-essential-rules-of-dimensional-modeling/) (2009) [A5].
- Dimension-attribute NULLs — RECOMMENDED: "we recommend substituting a descriptive string, such as Unknown or Not Applicable in place of the null value. Nulls in dimension attributes should be avoided because different databases handle grouping and constraining on nulls inconsistently." — [Kimball Techniques PDF](https://www.kimballgroup.com/wp-content/uploads/2013/08/2013.09-Kimball-Dimensional-Modeling-Techniques11.pdf) (2013) [A5]; Rule 7 repeats "Replace nulls in dimension attributes with a default value, such as 'NA'." — [10 Essential Rules](https://www.kimballgroup.com/2009/05/the-10-essential-rules-of-dimensional-modeling/) (2009) [A5].

**Surrogate keys — MANDATORY for dimensions (date dimension exempt); OPTIONAL for fact tables**
- "This primary key cannot be the operational system's natural key because there will be multiple dimension rows for that natural key when changes are tracked over time... The DW/BI system needs to claim control of the primary keys of all dimensions; rather than using explicit natural keys or natural keys with appended dates, you should create anonymous integer primary keys for every dimension. These dimension surrogate keys are simple integers, assigned in sequence, starting with the value 1, every time a new key is needed. The date dimension is exempt from the surrogate key rule; this highly predictable and stable dimension can use a more meaningful primary key." — [Kimball Techniques PDF](https://www.kimballgroup.com/wp-content/uploads/2013/08/2013.09-Kimball-Dimensional-Modeling-Techniques11.pdf) (2013) [A5].
- Rule 8: "Make certain that dimension tables use a surrogate key." Reasoning given: smaller keys/indexes/fact tables; "required for tracking attribute history"; insulation from source changes "such as reused product numbers." — [10 Essential Rules](https://www.kimballgroup.com/2009/05/the-10-essential-rules-of-dimensional-modeling/) (2009) [A5].
- Durable (supernatural) keys: "a new durable key must be created that is persistent and does not change... should be simple integers assigned in sequence beginning with 1. While multiple surrogate keys may be associated with an employee over time as their profile changes, the durable key never changes." — [Kimball Techniques PDF](https://www.kimballgroup.com/wp-content/uploads/2013/08/2013.09-Kimball-Dimensional-Modeling-Techniques11.pdf) (2013) [A5].
- Date dimension key may be a YYYYMMDD integer "to facilitate partitioning," but "the date dimension table needs a special row to represent unknown or to-be-determined dates," and "Filtering and grouping should be based on the date dimension's attributes, not the smart key." — same source.
- Fact table surrogate keys — OPTIONAL: "single column surrogate fact keys can be useful, albeit not required," for ETL identification, resumable loads, and decomposing updates into inserts plus deletes. — same source.

**Dimension types (Kimball)**
- Degenerate dimension: "a dimension is defined that has no content except for its primary key... This degenerate dimension is placed in the fact table with the explicit acknowledgment that there is no associated dimension table. Degenerate dimensions are most common with transaction and accumulating snapshot fact tables." — [Kimball Techniques PDF](https://www.kimballgroup.com/wp-content/uploads/2013/08/2013.09-Kimball-Dimensional-Modeling-Techniques11.pdf) (2013) [A5].
- Role-playing: "A single physical dimension can be referenced multiple times in a fact table... It is essential that each foreign key refers to a separate view of the date dimension so that the references are independent." — same source.
- Junk dimension: "a single junk dimension combining [miscellaneous low-cardinality flags]... should only contain the combination of values that actually occur in the source data." — same source.
- Snowflaked dimensions — RECOMMENDED AGAINST: "you should avoid snowflakes because it is difficult for business users to understand and navigate snowflakes. They can also negatively impact query performance. A flattened denormalized dimension table contains exactly the same information as a snowflaked dimension." — same source; Rule 6: "Flatten fixed-depth hierarchies into a single dimension table instead of normalizing them into snowflake subdimensions." — [10 Essential Rules](https://www.kimballgroup.com/2009/05/the-10-essential-rules-of-dimensional-modeling/) (2009) [A5].
- Outrigger — OPTIONAL/sparingly: "Outrigger dimensions are permissible, but should be used sparingly. In most cases, the correlations between dimensions should be demoted to a fact table." — [Kimball Techniques PDF](https://www.kimballgroup.com/wp-content/uploads/2013/08/2013.09-Kimball-Dimensional-Modeling-Techniques11.pdf) (2013) [A5].
- Bridge tables for multivalued dimensions: "the multivalued dimension must be attached to the fact table through a group dimension key to a bridge table with one row for each simultaneous diagnosis in a group." When built on type 2 dimensions "the bridge table must include effective and expiration date/time stamps." Bridge tables are also the Kimball answer for ragged/variable-depth hierarchies ("a row for every possible path"). — same source.
- Denormalized flattened dimensions — RECOMMENDED: "dimensional designers must resist the normalization urges caused by years of operational database designs and instead denormalize the many-to-one fixed depth hierarchies into separate attributes on a flattened dimension row." — same source.

**Conformed dimensions, bus architecture, bus matrix — MANDATORY for enterprise integration**
- "Dimension tables conform when attributes in separate dimension tables have the same column names and domain contents... This is the essence of integration in an enterprise DW/BI system. Conformed dimensions, defined once in collaboration with the business's data governance representatives, are reused across fact tables." — [Kimball Techniques PDF](https://www.kimballgroup.com/wp-content/uploads/2013/08/2013.09-Kimball-Dimensional-Modeling-Techniques11.pdf) (2013) [A5].
- Bus architecture: "provides an incremental approach to building the enterprise DW/BI system... delivering integration via standardized conformed dimensions that are reused across processes... The bus architecture is technology and database platform independent." — same source.
- Bus matrix: "The rows of the matrix are business processes and the columns are dimensions... teams should implement one row of the matrix at a time." A "detailed implementation bus matrix" expands rows to fact tables with grain statements. — same source. Rule 9: "Create conformed dimensions to integrate data across the enterprise... The Enterprise Data Warehouse Bus Matrix serves as the blueprint." — [10 Essential Rules](https://www.kimballgroup.com/2009/05/the-10-essential-rules-of-dimensional-modeling/) (2009) [A5].
- Rule 3 — MANDATORY: "Ensure that every fact table has an associated date dimension table." — same source.

**Slowly changing dimensions, Types 0–7 (Kimball)**
- Type 0 "Retain Original": value never changes; "appropriate for any attribute labeled 'original'... also applies to most attributes in a date dimension." Type 1 "Overwrite": "destroys history"; recompute affected aggregates. Type 2 "Add New Row": new surrogate key per change; "A minimum of three additional columns should be added... 1) row effective date or date/time stamp; 2) row expiration date or date/time stamp; and 3) current row indicator." Type 3 "Add New Attribute" ("alternate reality"; "used relatively infrequently"). Type 4 "Add Mini-Dimension" for "rapidly changing monster dimension" attributes. Type 5 = Type 4 mini-dimension plus a Type 1 outrigger reference in the base dimension. Type 6 = Type 2 rows carrying current Type 1 copies of the same attributes. Type 7 "Dual Type 1 and Type 2 Dimensions": both durable key and surrogate key placed in the fact table; two views (as-is via durable key with current flag; as-was via surrogate key). — [Kimball Techniques PDF](https://www.kimballgroup.com/wp-content/uploads/2013/08/2013.09-Kimball-Dimensional-Modeling-Techniques11.pdf) (2013) [A5].

**Graceful extensibility (Kimball's claim)**
- "All the following changes can be implemented without altering any existing BI query or application": add facts consistent with grain, add dimensions via new FK columns, add attributes, and make grain more atomic while preserving column names. — same source.

### Inferences
- Kimball's two inviolable structural rules for a schema-design framework are the grain contract and non-null FKs with default dimension rows; everything else (SCD type choice, junk/outrigger/bridge, fact-table surrogate keys) is pattern selection driven by the data's shape.
- Kimball's surrogate-key rule is justified by (a) SCD2 history tracking and (b) source-key instability; where neither applies (date dimension), Kimball himself relaxes the rule — this is the hook later cloud-era critics use (see KQ5).

### Gaps
- The individual technique pages on kimballgroup.com were not opened (only the index and the consolidated PDF); the Kimball Group article "Fact Tables and Dimension Tables" (2003) returned HTTP 404.
- The Wiley page does not expose the table of contents.

## Key Question 2 — Kimball bus architecture (bottom-up) vs Inmon Corporate Information Factory (top-down): the documented disagreement

### Takeaway
Both camps agree on enterprise planning, a staging/ETL area, and that independent stovepipe marts are bad. They disagree on (1) whether atomic data must live in a normalized 3NF warehouse (Inmon/CIF) or in dimensional structures (Kimball), and (2) whether integration is achieved by the normalized warehouse plus master data (Inmon) or by conformed dimensions (Kimball). Both sides now accept a hybrid in practice, but each characterizes the hybrid as the other side conceding.

### Cited Findings
- Kimball Group position paper (byline on page: Margy Ross, March 3, 2004; note: a search-result snippet attributed it to Ralph Kimball — the page byline is Ross). It calls the alternative "the Corporate Information Factory (CIF), once known as the EDW approach." Similarities: both support decision-making, both use staging and presentation areas, both "recommend planning from an enterprise perspective," both treat standalone independent marts as problematic. — [Differences of Opinion](https://www.kimballgroup.com/2004/03/differences-of-opinion/) (2004) [A5].
- Differences per Kimball Group: CIF "requires" a 3NF normalized layer before dimensional loading; Kimball "doesn't advocate it but doesn't strictly forbid it," and considers "duplicate storage of core performance data unwarranted in most cases." Kimball requires atomic data to be dimensionally structured; summary-only marts "presuppose the questions." Integration: CIF "relies on the normalized warehouse," which Kimball says "doesn't resolve common keys and labels"; Kimball uses conformed dimensions as "the backbone of any enterprise approach." Hybrid (3NF EDW + dimensional presentation): "viable" but with "significant added cost and delay from storing atomic data twice"; sensible "if an organization already has a normalized warehouse." — [Differences of Opinion](https://www.kimballgroup.com/2004/03/differences-of-opinion/) (2004) [A5].
- Kimball Group's later stance is de-escalation: "We're not interested in further stirring the pot, especially when the motivation is commercial gain... Whatever approach you choose, embrace it"; "organizations can be successful leveraging the approaches advocated by others." — [Design Tip #139: Much Ado About Nothing](https://decisionworks.com/2011/10/design-tip-139-much-ado-about-nothing/) (Margy Ross, DecisionWorks, October 5, 2011) [A4].
- Inmon's own current statement (Dec 23, 2025): the data warehouse is a "subject oriented, integrated, non volatile, time variant collection of data for management's decision making"; the CIF is centered on a warehouse of "granular, historical, integrated data" that is the "single version of the truth" and "the only source" for data marts. He quotes Kimball's definition as "a union of all the data marts," later "a copy of the data specifically structured for query and analysis," and argues the simple star-schema/data-mart approach "was never designed for enterprise integration," that copying data "does not reconcile it," that conformed dimensions "cover only some attributes," and that MDM "golden records" are needed. He frames Kimball's later additions (conformed dimensions, MDM, hub-and-spoke) as movement toward CIF, and proposes a hybrid in which "a central integrated warehouse feeds the star-schema data marts"; DW 2.0 is "a long term architectural blueprint." — [A Tale of Two Architectures – Kimball vs Inmon](https://williaminmon.substack.com/p/a-tale-of-two-architectures-kimball) (W. H. Inmon, Substack, December 23, 2025) [A4].
- Inmon also asserts (same post) that BI/data-mart vendors favored Kimball because quick marts "make faster sales." Kimball Group (Design Tip #139) likewise accuses the renewed debate of being commercially motivated — each side alleges commercial motive of the other. — [Inmon Substack](https://williaminmon.substack.com/p/a-tale-of-two-architectures-kimball) (2025) [A4]; [Design Tip #139](https://decisionworks.com/2011/10/design-tip-139-much-ado-about-nothing/) (2011) [A4].
- Vendor reconciliation: Oracle's current guide says "the modern approach to data warehousing does not pit star schemas and 3NF against each other. Rather, both techniques are used, with a foundation layer of 3NF - the Enterprise Data Warehouse of 3NF, acting as the bedrock data, and star schemas as a central part of an access and performance optimization layer." — [Oracle Database 21c Data Warehousing Guide, Ch. 2 Logical Design](https://docs.oracle.com/en/database/oracle/oracle-database/21/dwhsg/data-warehouse-logical-design.html) (n.d.) [A5].
- A 2026 TDWI column characterizes the flow as "top-down" (Inmon: "You build the enterprise warehouse first") vs "bottom-up" (Kimball: "You build marts that answer real business questions first"), says Kimball risks "integration debt" if conformance is not managed, and that "most large warehouses are hybrids." Author/date not shown on page; URL path indicates May 2026. — [TDWI: architectural disagreement that still shapes data warehouses](https://tdwi.org/blogs/data-101/2026/05/architectural-disagreement-that-still-shapes-data-warehouses.aspx) (2026) [A3].

**CONFLICT (explicit):** Kimball Group 2004 says the 3NF layer is unnecessary duplication and conformed dimensions are sufficient integration; Inmon 2025 says conformed dimensions are insufficient and a normalized integrated warehouse plus MDM is required. Neither has retracted. Both accept the 3NF-core-plus-dimensional-marts hybrid, as does Oracle.

### Inferences
- The "top-down vs bottom-up" vocabulary is secondary-source framing; the Kimball Group 2004 paper itself does not use those words (it contrasts "bus architecture" with "CIF").
- For a framework: the live decision is not Kimball-vs-Inmon but whether an integration layer (3NF or Data Vault) is justified by multi-source key reconciliation needs; if the presentation layer is the only layer, Kimball's rules govern it; if an integration layer exists, Inmon/DV rules govern it and Kimball still governs the marts.

### Gaps
- The Wiley page for *Building the Data Warehouse* does not reproduce the four-property definition; it is sourced here from Inmon's 2025 post instead.

## Key Question 3 — Inmon: definition of a data warehouse, CIF, 3NF atomic EDW feeding dependent marts, lakehouse-era writing

### Takeaway
Inmon's definition (subject-oriented, integrated, time-variant, non-volatile) and his CIF — a granular, integrated, historical warehouse that is the sole source for dependent marts — are restated by Inmon himself in December 2025. His recent books reposition the same integrated foundation into the "data lakehouse," covering structured, textual, and analog/IoT data.

### Cited Findings
- Book record: *Building the Data Warehouse, 4th Edition*, W. H. Inmon, Wiley, October 2005 (e-book September 2005), ISBN 978-0-764-59944-6, 576 pages; publisher calls him "Father of Data Warehousing"; the 4th edition "covers new approaches and technologies," adds unstructured data, storage across multiple media, "relational versus multidimensional design," ROI measurement, and "data monitoring and testing." — [Wiley: Building the Data Warehouse, 4th Edition](https://www.wiley.com/en-us/Building+the+Data+Warehouse%2C+4th+Edition-p-9780764599446) (October 2005) [A4].
- Definition and CIF rules (Inmon's own words, 2025) — **MANDATORY in Inmon's framing:** the warehouse is "subject oriented, integrated, non volatile, time variant"; holds "granular, historical, integrated data"; is "the only source" for data marts; delivers the "single version of the truth," which he calls the architecture's most important feature. He notes "integration is slow and laborious, so building a CIF is a long-term effort." — [A Tale of Two Architectures](https://williaminmon.substack.com/p/a-tale-of-two-architectures-kimball) (December 23, 2025) [A4].
- Inmon on marts: Kimball-style star-schema marts are acceptable as the consumption layer when fed from the central integrated warehouse (his proposed hybrid). — same source.
- Lakehouse-era writing: Technics Publications lists *Building the Data Lakehouse, 2nd Edition* (also titled "Rise of the Data Lakehouse"), co-author Ranjeet [Srivastava], describing the lakehouse as "the next generation of the data warehouse and data lake" with "a deep dive into the Databricks Lakehouse Platform"; companion titles *The Data Lakehouse Architecture*, *A Methodology for Building the Data Lakehouse*, and *The Data Lakehouse: The Bedrock for AI, ML, and Data Mesh* ("There are three data types in the data lakehouse (structured, textual, and analog/ IoT)"). The publisher page shows no years or ISBNs. — [Bill Inmon's Data Lakehouse Collection](https://technicspub.com/data-lakehouse-collection/) (n.d.) [A4].
- First-edition bibliographic data from search-result listings (not fetched): *Building the Data Lakehouse*, Bill Inmon, Mary Levins, Ranjeet Srivastava, Technics Publications, October 2021, ISBN 978-1634629669. — [WebSearch result: i-programmer listing](https://www.i-programmer.info/book-watch-archive/14911-building-the-data-lakehouse-technics-publications.html) (2021; search snippet only, not opened) [A2 for this detail].

### Inferences
- Inmon's 3NF-for-the-EDW is less a hard rule in his own 2025 text than "integrated, granular, non-volatile"; the 3NF physicalization is what Oracle/Teradata practice and the Kimball Group's description attribute to CIF (see KQ2, KQ5). Treat "3NF" as RECOMMENDED in Inmon's school and "integrated/granular/non-volatile/sole-source-for-marts" as MANDATORY.
- Inmon's lakehouse books continue the CIF premise (a single integrated foundation) rather than replacing it.

## Key Question 4 — Data Vault 2.0: official standards, components, keys, raw vs business vault, PIT/bridge, loading, auditability, "not for reporting," criticisms

### Takeaway
Data Vault 2.0 (Linstedt) is a system of methodology + architecture + model whose model core is hubs (business keys), links (relationships), satellites (descriptive, historized context), loaded in parallel pattern-based, insert-driven loads with load-date and record-source metadata. Linstedt states the raw and business vault "should not be directly accessed by data consumers"; consumption is via Information Marts (dimensional, cubes, flat wide tables). Hash keys are the DV 2.0 default but the Alliance's standards criteria require support for "hash keys, sequences, natural keys." The main documented drawbacks (BARC 2023 survey) are skills (48%), implementation complexity (35%), and query performance (32%).

### Cited Findings

**What DV 2.0 is; governance of standards**
- "Data Vault 2.0" aggregates best practices for "methodology, architecture, and modeling"; "We load data in parallel"; it keeps "true, historical records of everything"; the front-end "Information Mart Layer" looks like a star schema for analysts. Page body credits Mark Budzinski; metadata lists Daniel Linstedt. — [Your Data Vault 2.0 Introduction – A Grounded Perspective](https://datavaultalliance.com/engineering/data-vault-2-0-an-introduction/) (Data Vault Alliance, published August 12, 2022; modified January 23, 2026) [A5].
- Standards governance (Linstedt): "we don't believe in voting for standards"; proposals must be "repeatable, pattern-based, and non-conditional," must "scale across data volumes and in both batch and real-time loading," be measurable, auditable, cross-platform; platform-specific items are "simply a 'best practice' for that particular platform," not standards. Modeling standards must "Not change the base definition of a Hub, a Link, or a Satellite" (new object types become "extended objects"), must work in real time "without structural changes, at up to 400k transactions per second," support "big data (over 300TB), hash keys, sequences, natural keys, change data capture, and backup/restore." Implementation must handle "1TB to 500TB," be "fault-tolerant and restartable," "platform agnostic, technology agnostic, repeatable, fault-tolerant, and scalable," automatable for "at least 98% of cases"; "there are 30,000 test cases in place for the basic Data Vault standards." — [How To: Test an Idea for Data Vault Standards](https://datavaultalliance.com/news/dv/dv-standards/how-to-propose-dv-standards) (Daniel Linstedt, September 30, 2021; modified January 23, 2026) [A5].
- Canonical book: *Building a Scalable Data Warehouse with Data Vault 2.0*, Daniel Linstedt and Michael Olschimke, Elsevier/Morgan Kaufmann imprint, 2015 (page lists September 15 and September 29, 2015), ISBN 9780128025109 (from ScienceDirect link). Chapters: 3 methodology; 4 hubs/links/satellites; 6 PIT, bridge, reference tables; 7 dimensional modeling; 11 extraction incl. hashing; 12 loading the raw Data Vault; 14 loading the dimensional information mart incl. Business Vault as intermediate layer; examples use SQL Server SSIS. — [Elsevier: Building a Scalable Data Warehouse with Data Vault 2.0](https://shop.elsevier.com/books/building-a-scalable-data-warehouse-with-data-vault-2-0/linstedt/978-0-12-802510-9) (2015) [A4].

**Components (definitions)**
- Business key: "the identifier that the business actually uses to recognise and track a business object," should be enterprise-unique and stable. Hash key: "a fixed-length value derived by applying a hashing algorithm" (MD5/SHA-256) to business keys; "serve as the primary keys of Hubs and Links, and as the foreign key references connecting Satellites to their parents." Raw Vault: "the layer of the Data Vault architecture that stores unmodified source data" (no cleansing, no business rules; auditable). Business Vault: "the layer above the Raw Vault where business logic is applied," same hub/link/satellite structures. Information Mart: "the delivery layer that presents data to end users and reporting tools," usually dimensional, "often virtualised as SQL views." PIT: "a helper structure" pre-computing satellite row timestamps per point in time. Bridge: "a helper structure that simplifies querying across multiple Links." Effectivity satellite: "tracks the active or inactive status of a Hub record or a Link relationship over time." Load date: "a technical metadata attribute on every Hub, Link, and Satellite row" (arrival time, not event time). Record source: "identifies which source system a particular record came from." Ghost/zero-key record: "a placeholder row" preserving referential integrity when a referenced record is missing. — [Data Vault Glossary](https://www.scalefree.com/blog/data-vault/data-vault-glossary-hub-link-satellite-business-vault-and-more/) (Michael Olschimke, Scalefree, May 4, 2026) [A4].
- Databricks' restatement: "A Hub represents a core business entity, like customers, products, orders, etc."; a Link "has only the join keys"; satellites hold descriptive attributes "similar to a normalized dimension"; "Additional 'business' ETL rules are not typically applied while loading the Raw Data Vault"; "Data Vault modeling recommends using a hash of business keys as the primary keys"; "The PIT tables will bolster query performance as some satellites and hubs are pre-joined." — [Prescriptive Guidance for Implementing a Data Vault Model on the Databricks Lakehouse Platform](https://www.databricks.com/blog/2022/06/24/prescriptive-guidance-for-implementing-a-data-vault-model-on-the-databricks-lakehouse-platform.html) (Bhatt, Shaikh, Wiebe, June 24, 2022) [A4].

**Hash keys vs sequence keys — RECOMMENDED (DV 2.0 default), not the only standard-compliant option**
- DV 2.0 change: "Hashes replace (integer) sequences/identity attributes everywhere as meaningless keys / surrogate keys"; "you essentially don't have to do a key lookup for Hub and Link DWH/Surrogate keys anymore"; hashes are generated in the Staging Area so loads can parallelize across MPP nodes; referential integrity "cannot be enforced by ETL either, so it falls to housekeeping processing to manage RI (soft RI)." — [Data Vault 2.0 – Introduction and (technical) differences with 1.0](https://roelantvos.com/blog/?p=1063) (Roelant Vos, May 12, 2014; page shows updated August 14, 2026) [A3].
- Scalefree rationale: "a hash key is derived from a business key or combination of business keys without the need for a lookup in the parent table"; enables parallel loading and "allows to join across multiple heterogeneous platforms"; hash diff over satellite attributes means "just one column has to be looked up" for change detection; MD5 (128-bit) recommended in most cases; collision odds compared to "a meteor landing on your data center"; hash keys are "no silver bullet" (storage cost); natural composite keys as PKs are rejected because they are slow to join, use more storage, and must be replicated into satellites; a business-key collision code (BKCC) can be hashed in when the same key means different things across sources. — [Hash Keys in Data Vault](https://www.scalefree.com/blog/data-vault/hash-keys-in-the-data-vault/) (Marc Winkelmann, Scalefree, April 28, 2017; updated May 11, 2026) [A3].
- Alliance standards criteria require a modeling standard to support "hash keys, sequences, natural keys" — i.e., the key strategy is implementation choice, not model definition. — [How To: Test an Idea for Data Vault Standards](https://datavaultalliance.com/news/dv/dv-standards/how-to-propose-dv-standards) (2021/2026) [A5].

**CONFLICT on hashing as a key strategy (cross-methodology):** DV 2.0 default = hash of business key (Scalefree 2017/2026; Databricks DV guidance 2022). Databricks' own Lakeflow dimensional-modeling docs say to "Avoid hash-based surrogates like sha2(natural_key)" because hashing scatters adjacent rows and hurts liquid clustering / Z-order; prefer natural keys and use surrogates only "when a source reuses or changes IDs." — [Dimensional modeling in Lakeflow pipelines](https://docs.databricks.com/aws/en/ldp/best-practices/dimensional-modeling) (Databricks docs, last updated Oct 15, 2026) [A5]. Kimball requires sequential integers (KQ1). dbt's tutorial uses md5-hash surrogates via `dbt_utils.generate_surrogate_key()` — [Building a Kimball dimensional model with dbt](https://docs.getdbt.com/blog/kimball-dimensional-model) (Jonathan Neo, dbt Developer Blog, April 20, 2023) [A3]. Resolution for a framework: hash keys are justified by DV's parallel, lookup-free loading; in a Kimball gold layer on a clustered lakehouse the vendor says the opposite.

**Insert-only / auditability — RECOMMENDED ("best practice, NOT a standard") per the Alliance's own course**
- Data Vault Alliance course text (returned by WebSearch, not opened): recommends "100% insert driven best practice, especially for scalability in to the trillions of records"; "not using End-Dating is a best practice, NOT a standard"; end-dates "are not in use in Hubs, Links, raw Satellites"; business-vault satellites (prefixed "bv_") may use updates with end-dates. — [DV101 Baseline Hands-On: Introduction to This Course](https://learn.datavaultalliance.com/cs/dv101-baseline-hands-on/ls/introduction-to-this-course/) (Data Vault Alliance, n.d.; search snippet only) [A5 body, A3 confidence because unopened].
- Scalefree describes the vault as "insert-only, historically complete" and "a single, auditable, historically complete view of the business"; the raw vault records "what arrived, when, and from where, with 'no business logic.'" — [Scalefree Data Vault blog listing](https://www.scalefree.com/data-vault/) (Scalefree, n.d.) [A3].
- Every row carries load date and record source (Glossary above) — this is the auditability mechanism. **MANDATORY** in DV 2.0 (standards must be "auditable").

**"The vault is not for reporting — information marts are" — MANDATORY (Linstedt's "should not")**
- "The raw vault and business vault entities are not, or at least should not, be directly accessed by data consumers."; "Report writers, analysts, and actuaries get what they need, consistently, from the Information Mart layer."; the Infomart layer includes "dimensional models, cubes, flat wide tables" plus web services/virtualization; direct vault access by data scientists is "the exception, not the rule." The author also says critics who find the vault hard misunderstand its design goals and that the Infomart layer is the stable access point. — [Data Vault Business Value – Get Data from a Vault Easy DV2](https://datavaultalliance.com/engineering/getting-data-out-of-a-data-vault-is-a-lot-easier-than-some-people-think/) (Daniel Linstedt, Data Vault Alliance, August 29, 2022; modified January 23, 2026) [A5].

**Loading patterns**
- Hashes computed in staging; hubs, links, satellites load in parallel without lookups (Vos 2014; Scalefree 2017). Raw Vault loads apply no business rules (Databricks 2022; Scalefree Glossary 2026). Business rules, DQ and cleansing happen between Raw and Business Vault; Business Vault organized by data domain with data-steward ownership. — [Databricks DV guidance](https://www.databricks.com/blog/2022/06/24/prescriptive-guidance-for-implementing-a-data-vault-model-on-the-databricks-lakehouse-platform.html) (2022) [A4].
- Pre-join query helpers (PIT/bridge) are built for the presentation layer; Databricks recommends building them with Delta Live Tables and, because "Data Vault models involve many joins," using recent runtimes with Adaptive Query Execution, OPTIMIZE/Z-order on join keys, Bloom filters, smaller target file sizes (32–64 MB). — same source.

**Criticisms (documented)**
- Survey of 238 practitioners (Dec 2022–Jan 2023; Eckerson Group with BARC): drawbacks cited — "Skills and training requirements (48%)," "Implementation complexity (35%)," "Query performance (32%)," "Design complexity (29%)," "Multiple versions of data (29%)." Drivers: extensibility 53%, accelerated data delivery 45%, scalability 40%. "Only 65% of adopters have been trained on Data Vault 2.0"; 31% say their implementation "fully" aligns with standards, 60% "partially"; Data Vault usage "lags third normal form and star schema." — [BARC/Eckerson: Data Warehouse and Data Vault Adoption Trends](https://barc.com/infographic-data-warehouse-and-data-vault-adoption/) (last edited April 27, 2023) [A4].
- Scalefree's own blog listing notes one article's finding that "vanilla PostgreSQL struggles with Data Vault joins at mid-to-high GB/TB volumes," while a Databricks/Snowflake benchmark found DV workable there. — [Scalefree Data Vault blog listing](https://www.scalefree.com/data-vault/) (n.d.) [A3].
- Practitioner forum: one dbt Discourse participant (pmo511, June 23, 2022) describes Data Vault implementations seen in practice as "a mess"; another (patrickcuba, July 16, 2021) advocates DV 2.0 with Kimball on top. — [Is Kimball dimensional modeling still relevant in a modern data warehouse?](https://discourse.getdbt.com/t/is-kimball-dimensional-modeling-still-relevant-in-a-modern-data-warehouse/225) (dbt Community Discourse, 2019–2022) [A2].
- Tooling: the Alliance's own criteria demand ≥98% automation of patterns, and Databricks' guidance lists many physical tuning steps — both imply that DV is operationally dependent on automation/tooling (inference supported by the 48% skills and 35% complexity figures above).

### Inferences
- The DV 2.0 "standard" is narrower than vendors describe: the Alliance's test-criteria page makes hub/link/satellite base definitions, pattern repeatability, batch+real-time support, auditability and restartability the invariants; hash keys and insert-only are default best practices, not standard definitions.
- DV is a write/integration-optimized layer; by Linstedt's own statement it is incomplete without an Information Mart layer, so a DV decision always implies a second (usually Kimball) model.

## Key Question 5 — 3NF enterprise warehouse vs star schema (Oracle/Teradata practice), Anchor Modeling and 6NF

### Takeaway
Oracle's guide treats 3NF as the flexible, "neutral" foundation layer for large enterprise warehouses that feed marts (at the cost of "very many tables" and complex joins), and the star schema as the access/performance layer, explicitly recommending star over snowflake. Teradata ships a 3NF industry model with a dimensional access-layer product on top. Anchor Modeling (Rönnbäck et al., 2010) pushes normalization to 6NF so that all change is "extensions, not modifications," relying on insert-only loading and optimizer table elimination for performance.

### Cited Findings

**Oracle (official vendor documentation)**
- 3NF: "Third Normal Form design seeks to minimize data redundancy and avoid anomalies in data insertion, updates and deletion"; "has a long heritage in online transaction processing (OLTP) systems"; "3NF designs have great flexibility... you can extend the data model with relative ease"; but "3NF databases use very many tables and this requires complex queries with many joins. For full scale enterprise models built in 3NF form, over one thousand tables are commonly encountered in the schema," with possible "slow query performance." — [Oracle 21c Data Warehousing Guide, Logical Design](https://docs.oracle.com/en/database/oracle/oracle-database/21/dwhsg/data-warehouse-logical-design.html) (n.d.) [A5].
- Star: "The term star schema is another way of referring to a 'dimensional modeling' approach"; "The goal for star schemas is structural simplicity and high performance data retrieval"; "Many business intelligence tools and applications are designed with the expectation that a star schema representation will be available"; "A common criticism of star schemas is that they limit analysis flexibility compared to 3NF designs," countered by "a well designed dimensional model can be extended." "Most data warehouses use a dimensional model." — same source.
- Snowflake — RECOMMENDED AGAINST: "While this saves space, it increases the number of dimension tables and requires more foreign key joins. The result is more complex queries and reduced query performance." — same source; explicit rule in the 9i edition: "Oracle Corporation recommends you choose a star schema over a snowflake schema unless you have a clear reason not to." — [Oracle9i Data Warehousing Guide Rel. 2 (9.2), Ch. 17 Schema Modeling Techniques](https://docs.oracle.com/cd/A97630_01/server.920/a96520/schemas.htm) (Part No. A96520-01, n.d.) [A5].
- When 3NF — CONTEXTUAL: "normalized (3NF) schemas in Enterprise Data Warehousing environments, star or snowflake schemas in data marts, or hybrid schemas"; "3NF schemas are typically chosen for large data warehouses, especially environments with significant data-loading requirements that are used to feed data marts and execute long-running queries"; 3NF is "neutral," "independent of any application or data-usage considerations," and "may require less data-transformation." "The determination of which schema model should be used for a data warehouse should be based upon the requirements and preferences of the data warehouse project team." Physical advice for 3NF: partition-wise joins, composite range-hash partitioning on "the most-common join key," heavy parallelism. — [Oracle 21c](https://docs.oracle.com/en/database/oracle/oracle-database/21/dwhsg/data-warehouse-logical-design.html) and [Oracle9i](https://docs.oracle.com/cd/A97630_01/server.920/a96520/schemas.htm) [A5].
- Oracle also notes "it is not uncommon to see some sensible level of denormalization in 3NF data warehousing models, in a logical form as views or in a physical form through slightly denormalized tables." — [Oracle 21c](https://docs.oracle.com/en/database/oracle/oracle-database/21/dwhsg/data-warehouse-logical-design.html) [A5].

**Teradata (official vendor product page)**
- "The Retail Data Model (RDM) is a cross-functional third normal form data warehouse data model for retailers" (customers, stores, financials, products, inventory, employees); the companion "Retail Analytic Schemas (RAS)" product "includes dimensional data models and analytic data sets in one integrated data model" for the "user access layer." Page shows "©2026 Teradata," no publication date. — [Teradata Retail Data Model](https://www.teradata.com/industries/retail/retail-data-model) (n.d.) [A5].

**Anchor Modeling / 6NF (peer-reviewed paper + official site)**
- Paper: "Anchor Modeling – Agile Information Modeling in Evolving Data Environments," L. Rönnbäck (Resight), O. Regardt (Teracom), M. Bergholtz, P. Johannesson, P. Wohed (DSV, Stockholm University); "Preprint submitted to DKE October 5, 2010"; keywords "Anchor Modeling, database modeling, normalization, 6NF, data warehousing, agile development, temporal databases, table elimination." — [Anchor Modeling (DKE preprint PDF)](https://www.anchormodeling.com/wp-content/uploads/2011/05/Anchor-Modeling.pdf) (2010) [A5]. A Stockholm University notice (search result, not opened) says it was accepted by Data & Knowledge Engineering after a best-paper award at ER 2009 — [DSV blog](https://dash.dsv.su.se/2010/10/06/a-new-article-on-anchor-modeling/) (Oct 6, 2010) [A3].
- Core claim — MANDATORY within the method: "changes in a data warehouse environment only require extensions, not modifications, to the data warehouse... all previous versions of the database schema are available as subsets of the current schema." — [Anchor Modeling PDF](https://www.anchormodeling.com/wp-content/uploads/2011/05/Anchor-Modeling.pdf) (2010) [A5].
- Constructs: "The basic building blocks in Anchor Modeling are anchors, knots, attributes, and ties." "An anchor represents a set of entities"; "A knot is used to represent a fixed, typically small, set of entities that do not change over time" (e.g., gender — "Rather than repeating the strings a single bit per instance is sufficient"); attributes are "static, historized, knotted static, and knotted historized"; ties relate two or more anchors and "come in four variants." Historized attributes couple a value with a time point. — same source.
- Guidelines (RECOMMENDED): "Use a historized attribute if versioning of attribute values are of importance, otherwise use a static" (2a); "Use a historized tie if a relationship may change over time, otherwise use a static tie" (3a); "Use several smaller ties for which all roles are known, if roles may be temporarily unknown within a large relationship" (4a). — same source.
- Loading — MANDATORY within the method: "When loading data into an anchor database a zero update strategy is used. This means that only insert..." statements are issued; "By not doing updates there is also no row locking." — same source.
- Normalization and performance: "Anchor Modeling differs from main stream approaches in data warehousing that typically emphasize de-normalization, which is considered essential for fast retrieval. Anchor Modeling, on the other hand, results in highly normalized data models, often even in 6NF. Though highly normalized, these data models still offer fast retrieval. This is a consequence of table elimination, where narrow tables with few columns are..." [eliminated when not referenced]. "In order to take advantage of table elimination primary and foreign keys have to be defined in the database." Lab experiments "indicate that under certain conditions anchor databases perform substantially better than databases constructed using traditional modeling techniques." Also claims "the absence of null values." — same source.
- Adoption evidence (self-reported): "Since 2004 several data warehouses have been built using Anchor Modeling... insurance, logistics and retail... The one having the largest data volume is currently close to one terabyte in size." — same source.
- Official site today is a blog by Rönnbäck (posts 2022: "Atomic Data" June 8, 2022 on "transitional modeling"/posits; "Information in Effect and Performance" Jan 24, 2022 with SQL Server timing tests of 3.9–9.5 s on one million rows, author cautioning that workarounds "may very well have skewed those results"). — [anchormodeling.com](https://www.anchormodeling.com/) (2022) [A4].

**CONFLICT (denormalization as performance necessity):** Kimball (KQ1) and Oracle say denormalize dimensions for speed; Anchor Modeling claims equal or better retrieval while in 6NF via table elimination, with narrow-table I/O benefits. Both Oracle and the dbt community note that join-heavy designs degrade without optimizer support; Scalefree reports PostgreSQL struggling with DV joins at scale (KQ4). Anchor's claims are "under certain conditions" and from lab tests on SQL Server.

### Inferences
- "3NF EDW" in vendor practice is an integration/foundation layer, never the BI access layer; Oracle and Teradata both pair it with a dimensional access layer, which is structurally the same two-layer pattern as Data Vault + Information Marts and Inmon's hybrid.
- Anchor Modeling and Data Vault share insert-only loading, non-destructive extension, and the dependence on query helpers/optimizer features; Anchor is more extreme (attribute-per-table) and has far less tooling/adoption evidence (one ~1 TB warehouse cited in the 2010 paper; a 2023 survey shows DV lagging 3NF and star — Anchor is not even measured).

### Gaps
- Teradata documentation stating a normalized-model preference was not retrievable from docs.teradata.com (only a training-course outline "Normalized Data Model vs. Star Schema Model" appeared in search). The 3NF-core practice is evidenced by the RDM product page and Oracle's description.
- The Oracle 19c URL in the brief returned 404; 21c and 9i editions were used.
- The 6NF definition page (6nf.pdf) on anchormodeling.com appeared in search but was not opened; the formal 6NF definition is quoted via the paper ("A table is in sixth normal form if it satisfies no [non-trivial join dependencies]").

## Key Question 6 — One Big Table / wide denormalized tables, "Kimball is dead?", Activity Schema, cloud-era critiques

### Takeaway
No credible source shows Kimball "dead": dbt Labs' 2023 tutorial calls dimensional modeling "still one of the most widely adopted data modeling technique for analytics," and Databricks (2025) says "Dimensional modeling principles thrive in the Lakehouse." What the cloud-era critiques (Beauchemin 2017, dbt community 2019–2022, Fivetran 2022) actually drop are the performance-motivated parts: mandatory integer surrogate keys, complex SCD machinery, and star-only presentation. OBT measured 25–50% faster than star on TPC-DS-derived queries but tripled storage; most sources recommend star upstream and wide tables as a derived consumption layer. Activity Schema is a vendor-originated open spec that replaces FK joins with temporal self-joins on one stream table.

### Cited Findings

**Beauchemin (well-known practitioner; creator of Airflow/Superset)**
- "Data modeling is changing": star schema approaches "are less relevant than they once were" because storage/compute are cheaper and "engineering time is now the scarcer resource"; "further denormalization" and natural human-readable keys in fact tables reduce joins; "maintaining surrogate keys in dimensions can be tricky, and it makes fact tables less readable"; snapshotting full dimension copies each ETL cycle is "a simple generic approach that requires little engineering effort" while complex SCD techniques "are not intuitive and reduce accessibility"; conformance "is still extremely important" but is now a tradeoff that can be aligned gradually. — [The Rise of the Data Engineer](https://www.freecodecamp.org/news/the-rise-of-the-data-engineer-91be18f1e603/) (Maxime Beauchemin, freeCodeCamp, January 20, 2017) [A3].
- "Functional Data Engineering — a modern paradigm for batch data processing" (Medium, January 8, 2018) argues for pure, idempotent tasks over immutable partitions and partition-based dimension snapshots instead of SCD2 — per search-result summaries; the Medium URL returned HTTP 403 and was NOT verified. The Data Council talk page of the same name was returned by search but not opened: [Functional Data Engineering – A Set of Best Practices](https://www.datacouncil.ai/functional-data-engineering-a-set-of-best-practices) (n.d.) [A3; unverified content].

**dbt Labs / dbt community**
- dbt Developer Blog (edited by dbt Labs staff; author Jonathan Neo, Canva): "While the relevance of dimensional modeling has been debated by data practitioners, it is still one of the most widely adopted data modeling technique for analytics." Defines fact tables as representing "a business process in the real world" and dimensions as "contextual or descriptive information"; recommends denormalizing to star over snowflake; uses `dbt_utils.generate_surrogate_key()` (md5/hash) for surrogate keys; benefits: "do not need to perform complex joins," conformed-dimension reuse, faster retrieval, alignment with business processes; recommends building a One Big Table (OBT) joining the fact to all its dimensions only when the BI tool lacks a semantic layer supporting relationships. — [Building a Kimball dimensional model with dbt](https://docs.getdbt.com/blog/kimball-dimensional-model) (April 20, 2023) [A3].
- Community thread (Jan 30, 2019 – Jun 23, 2022): critics list "Databases are slow and expensive" as an outdated assumption and see "over engineered" warehouses (ernesto, Feb 5, 2019); defenders keep conformed dimensions ("users across the business eventually start getting inconsistent results" otherwise — josh, Feb 9, 2019) and grain ("if facts share a grain, then widen your table"; joining mismatched grains risks "gaps and duplicates" — pmo511, Jun 23, 2022); wide-table advocates propose one wide table per analysis (levelworm, 2021); others note a single big table "hits a wall at scale" (info-assets, Mar 23, 2021), is hard to navigate, and lacks "a recognized pattern to train analysts on" (marcelvv, Jan 30, 2019); a hybrid "normalized layer maintained by engineering, plus flat tables covering about 80% of use cases" is proposed (xavierbourretsicotte, Oct 31, 2020); BI tools "still rely on fact/dimension concepts" (rothrock, Jul 28, 2021). — [Is Kimball dimensional modeling still relevant in a modern data warehouse?](https://discourse.getdbt.com/t/is-kimball-dimensional-modeling-still-relevant-in-a-modern-data-warehouse/225) (dbt Discourse) [A2].
- The Coalesce 2020 talk "Kimball in the context of the modern data warehouse: what's worth keeping, and what's not" (Dave Fowler, Chartio, Dec 12, 2020) argued dimensional modeling does "more harm than good" in the modern stack per search summaries; its getdbt.com page returned 404 and the counter-talk "Babies and bathwater: Is Kimball still relevant?" (Josh Devlin, Sydney Burns, Brooklyn Data Co.) redirected — neither verified; summarized from search snippets only.

**Fivetran benchmark (major-organization engineering blog)**
- TPC-DS "100" subset (store_sales + 4 dimensions), BI-style aggregate queries, caching off, Redshift (dc2.large single node; dc2.8xlarge 3-node), Snowflake X-Large, BigQuery default. OBT vs star: Redshift 25–30% faster excluding compile ("the denormalized table outperforms the star schema from 10% to 45%" on the multi-node cluster, 9 of 10 queries); Snowflake ~25% but mixed (star won queries 3, 4, 7); BigQuery "the average improvement in query response time is 49%" and "the star schema has a much higher variance." Storage: Redshift disk "from a bit over 30 gigabytes to over 90" (store_sales ≈29,778 MB vs OBT ≈60,250 MB); the single node ran out of disk joining all dimensions. Recommendation — CONTEXTUAL: star when you need "easier ELT code organization, easier navigation for analysts, or lower disk use"; OBT for small teams/single-subject projects where speed matters; hybrid = build star in transformation, then re-join into a wide table for end users. — [Star schema vs. OBT](https://fivetran.com/blog/star-schema-vs-obt) (Michael Kaminsky, Fivetran, August 16, 2022) [A4].

**Databricks (vendor) on dimensional modeling and keys in the cloud**
- "Dimensional modeling principles thrive in the Lakehouse"; star/snowflake "map well to Delta tables"; SCDs "easy to implement with Delta Lake's time travel features"; "Leverage identity columns for surrogate key generation"; PK/FK constraints "are for query performance, but are not enforced." — [Databricks Lakehouse Data Modeling: Myths, Truths, and Best Practices](https://www.databricks.com/blog/databricks-lakehouse-data-modeling-myths-truths-and-best-practices) (Shannon Barrow, Kyle Hale, December 15, 2025) [A4].
- Lakeflow docs: "Dimensional modeling is a technique for organizing your gold-layer data into fact tables and dimension tables"; prefer natural keys; surrogate only "when a source reuses or changes IDs"; "Avoid hash-based surrogates like sha2(natural_key)" (bad for liquid clustering/Z-order); derive order-preserving surrogates deterministically so they survive full refresh; IDENTITY only if append-only; SCD Type 2 via AUTO CDC "STORED AS SCD TYPE 2"; dim_date as a materialized view via sequence()/explode(). — [Dimensional modeling in Lakeflow pipelines](https://docs.databricks.com/aws/en/ldp/best-practices/dimensional-modeling) (last updated Oct 15, 2026) [A5].
- Gold layer "can be completely denormalized," typically for data scientists' feature engineering. — [Data Warehousing Modeling Techniques and Their Implementation on the Databricks Lakehouse Platform](https://www.databricks.com/blog/2022/06/24/data-warehousing-modeling-techniques-and-their-implementation-on-the-databricks-lakehouse-platform.html) (Soham Bhatt, Deepak Sekar, June 24, 2022) [A4].

**CONFLICT (surrogate keys, four positions):** Kimball — sequential integer surrogate MANDATORY (date exempt). Beauchemin 2017 — natural keys, surrogates "tricky." dbt tutorial 2023 — hashed surrogates via dbt_utils. Databricks Lakeflow 2026 — natural keys preferred, avoid hash surrogates, deterministic order-preserving surrogates only when IDs are unstable. Databricks 2025 blog — identity columns. The common ground: a surrogate is needed when (a) SCD2 history is tracked or (b) source IDs are reused/unstable — exactly Kimball's two stated reasons.

**CONFLICT (SCD):** Kimball Types 0–7 (row-versioning in dimensions) vs Beauchemin's full dimension snapshots per partition vs Data Vault satellites (insert-only history in the integration layer, with SCD2 marts derived via PIT) vs Databricks AUTO CDC SCD2 (Kimball Type 2 automated). These are implementation strategies for the same requirement (as-was vs as-is reporting); Kimball Type 7 and DV PIT both exist to serve both views.

**Activity Schema (open spec, vendor-originated)**

[A3].

**Holistics (vendor guidebook)**
- *The Analytics Setup Guidebook* (Huy Nguyen, Ha Pham, Cedric Chin; Holistics; year not shown) has a chapter "Data Modeling for Analytics" with sections "Kimball's Dimensional Data Modeling" and "How has data modeling evolved in modern cloud era?"; the opened chapter defines data modeling as a layer mapping raw data to business terms with transformations run "within the data warehouse, as per the ELT paradigm," models as SQL SELECT statements, persisted "for performance reasons," and says readers experienced in "Kimball, Inmon or Data Vault-style data modeling" can skim. — [Analytics Setup Guidebook: Data Modeling Layer & Concepts](https://www.holistics.io/books/setup-analytics/data-modeling-layer-and-concepts/) and [book index](http://www.holistics.io/books/setup-analytics/) (n.d.) ### Inferences
- The "Kimball is dead" position is held in talks and forum posts (A2–A3), while the A4–A5 sources (dbt Labs blog, Databricks docs/blogs, Fivetran) all retain fact/dimension structure and treat OBT as a derived layer. A framework should label OBT as CONTEXTUAL: a consumption artifact over a dimensional or vault model, justified by query speed or BI-tool limitations, costed by storage and update amplification.
- Activity Schema is a specialized event-centric alternative suited to single-entity (customer) behavioral analytics; it does not address multi-entity financial/ERP facts (no source claims it does).

### Gaps
- Beauchemin's Medium essay (403) and both Coalesce 2020 talks could not be opened; their arguments are reported only via search summaries.
- No peer-reviewed benchmark of OBT vs star beyond vendor/practitioner tests was found.

## Key Question 7 — Medallion architecture: what Databricks says it is, and how Kimball / Data Vault / 3NF map onto Bronze–Silver–Gold

### Takeaway
Databricks defines medallion as a layering/quality-progression "data design pattern," explicitly "a recommended best practice but not a requirement" and "a reference architecture, not a mandatory structure" — not a modeling methodology. Databricks' own modeling guidance places source-shaped data in Bronze, Data Vault or 3NF-like write-optimized models in Silver, and Kimball star schemas (or Inmon-style marts, or fully denormalized tables) in Gold.

### Cited Findings
- "The medallion architecture describes a series of data layers that denote the quality of data stored in the lakehouse"; it is "a data design pattern used to organize data logically"; layers "incrementally and progressively improve the structure and quality of data as it flows through each layer" (also called "multi-hop architectures"); following it "is a recommended best practice but not a requirement." Bronze = raw, unvalidated, original state; Silver = "validated, cleaned, and enriched versions of the data" (cleansing, deduplication, normalization; nested data via VARIANT/structs or flattened "into multiple tables"); Gold = refined, aggregated datasets where you model data "using a dimensional model by establishing relationships and defining measures" (example: a `weekly_bookings` materialized view). The page makes no statement about Kimball/Inmon/Data Vault. — [What is the medallion lakehouse architecture?](https://docs.databricks.com/aws/en/lakehouse/medallion) (Databricks docs, last updated Oct 29, 2026) [A5].
- "Medallion architecture is required" is listed as a myth: it is "a reference architecture, not a mandatory structure," and layers can be added or removed; Databricks supports "Hybrid Modeling Approaches to accommodate Data Vault, star schemas, snowflake" and domain layers. — [Databricks Lakehouse Data Modeling: Myths, Truths, and Best Practices](https://www.databricks.com/blog/databricks-lakehouse-data-modeling-myths-truths-and-best-practices) (December 15, 2025) [A4].
- Mapping of methodologies to layers: "The Bronze layer uses the data models of source systems"; the Data Vault style "typically fits well in the Silver layer of the Databricks Lakehouse" and Silver "has more 3rd-Normal Form like data models" / "Data Vault-like write-performant data architectures"; "Kimball style star-schema based data models or Inmon style Data marts fit in this Gold Layer of the Lakehouse"; Kimball star schemas are "pretty much the gold standard for the presentation layer"; "Both normalized Data Vault (write-optimized) and denormalized dimensional models (read-optimized) data modeling styles have a place in the Databricks Lakehouse"; "Sometimes tables in the Gold Layer can be completely denormalized." — [Data Warehousing Modeling Techniques and Their Implementation on the Databricks Lakehouse Platform](https://www.databricks.com/blog/2022/06/24/data-warehousing-modeling-techniques-and-their-implementation-on-the-databricks-lakehouse-platform.html) (June 24, 2022) [A4].
- Data Vault on medallion: landing/staging zones "naturally fit the Bronze layer"; Raw Vault and Business Vault correspond to Silver; PIT/bridge and the dimensional presentation sit in Gold ("loading a dimensional model Data Warehouse in Gold layer becomes easier" because hubs simplify keys, satellites supply dimension attributes, links simplify fact loading). — [Prescriptive Guidance for Implementing a Data Vault Model on the Databricks Lakehouse Platform](https://www.databricks.com/blog/2022/06/24/prescriptive-guidance-for-implementing-a-data-vault-model-on-the-databricks-lakehouse-platform.html) (June 24, 2022) [A4].
- Gold-layer dimensional modeling specifics (natural keys preferred, SCD2 via AUTO CDC, facts as streaming tables fed from Silver, dimensions as materialized views): [Dimensional modeling in Lakeflow pipelines](https://docs.databricks.com/aws/en/ldp/best-practices/dimensional-modeling) (Oct 15, 2026) [A5].

### Inferences
- Medallion is orthogonal to the Kimball/Inmon/DV debate: it standardizes *how many hops* and *what quality* each hop guarantees, while the methodologies decide *the shape* of tables inside Silver and Gold. In medallion terms: Inmon's 3NF EDW and Linstedt's Raw/Business Vault are Silver-layer integration models; Kimball's star schema and OBT are Gold-layer consumption models; Anchor Modeling would also be Silver.
- Databricks' DV placement implies the vault's "not for reporting" rule maps cleanly to "Silver is not for BI consumers; Gold is."

### Gaps
- Databricks is the only source for the medallion definition (it is a Databricks-originated term); Snowflake and other vendors' equivalents were not researched here.

### Inferences (workload-to-methodology routing the sources support)
- **Single-source or few-source BI/reporting; stable business processes; BI-tool consumption:** Kimball star directly (Oracle: "Most data warehouses use a dimensional model"; dbt 2023; Databricks 2025).
- **Many sources, acquisitions, regulatory audit trail, need to reload/re-derive marts from unmodified history:** Data Vault 2.0 (or Inmon 3NF EDW) as the integration layer, with Kimball marts on top — the only configuration Linstedt endorses for consumers, and the hybrid Inmon (2025) and Oracle (21c) describe.
- **Volatile, rapidly evolving schemas with heavy historization and sparse attributes (e.g., insurance, healthcare per the paper):** Anchor Modeling is the extreme-flexibility option but has the thinnest tooling/adoption evidence; treat as specialist.
- **Low-latency dashboards or BI tools without relationship support; small teams:** OBT derived from a star (Fivetran, dbt), accepting ~3x storage and update amplification.
- **Customer-behavior / event sequence analytics over one entity type:** Activity Schema; not evidenced for multi-entity financial data.
- **Lakehouse layering:** apply Medallion as the hop/quality convention; it does not change which methodology governs Silver (DV/3NF) or Gold (Kimball/OBT).

### Gaps
- No source provides a quantified, like-for-like comparison of all seven approaches; the matrix ratings are synthesized from methodology-specific sources and should be read as relative judgments.
- An arXiv preprint "Enterprise Data Modelling Methodologies: A Comparative Analysis of Inmon, Kimball, and Data Vault" (Issar Arab, arXiv:2606.29355, submitted 28 June 2026) concludes "no single methodology is universally optimal" and offers decision criteria (scale, regulatory environment, analytical maturity, upfront investment tolerance) but is un-refereed and its full scenario mapping was not read — [arXiv abstract](https://arxiv.org/abs/2606.29355) (2026) [A2].
