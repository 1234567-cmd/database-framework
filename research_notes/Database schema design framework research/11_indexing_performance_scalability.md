# 11. Indexing, Query Performance, Partitioning, Sharding and Scale-Out: Research Notes

Scope: authoritative guidance on index design, query optimization, partitioning, sharding/scale-out, replication, storage engines and the OLTP vs OLAP distinction, compiled so a schema-design framework can prescribe indexing and scalability rules per workload type and flag outdated or contested advice. Verified 2026-11-07/08. Authority levels: 5 = official vendor docs / foundational peer-reviewed paper; 4 = recognized book or major-organization engineering guidance; 3 = reputable tool docs or well-known practitioner; 2 = lesser-known blog; 1 = unverified.

Rule labels used below: **MANDATORY** (source states it as a requirement or a hard constraint), **RECOMMENDED** (source states it as best practice with reasoning), **OPTIONAL/CONTEXTUAL** (source says "consider" or ties it to a specific situation). Workload tags: [OLTP], [OLAP/DW], [lakehouse/cloud DW], [all].

## Key Question 1: What do the vendor index-design guides and Winand prescribe about index types, clustered vs non-clustered, composite column order, covering/partial/expression indexes, index-only scans, unique indexes, maintenance cost, FK indexing, fill factor, invisible/hypothetical indexes?

### Takeaway
All five vendors converge on the same core: B-tree is the default and serves equality, range, prefix-LIKE and ORDER BY; indexes are a balancing act between read speed and write/storage overhead, so index only the predicates and joins that matter and remove unused indexes; composite-index usability depends on the leading (leftmost) columns, and column order should be driven by query usage (equality columns first) rather than the "most selective first" folk rule, which Winand and the practitioners he cites explicitly reject. Engines differ on FK auto-indexing (InnoDB yes, PostgreSQL no), on clustered-table defaults (SQL Server/InnoDB/Oracle IOT vs PostgreSQL heaps), and on specialized types (bitmap, GIN/GiST/BRIN, columnstore, hash).

### Cited Findings

**Index types — B-tree default, hash, bitmap, GIN/GiST/SP-GiST/BRIN, columnstore, Bw-tree**
- PostgreSQL: "PostgreSQL provides several index types: B-tree, Hash, GiST, SP-GiST, GIN, BRIN, and the extension bloom... By default, the `CREATE INDEX` command creates B-tree indexes, which fit the most common situations." B-tree handles `<, <=, =, >=, >`, `BETWEEN`, `IN`, `IS NULL`, anchored `LIKE 'foo%'` and "can also be used to retrieve data in sorted order." Hash: "store a 32-bit hash code... can only handle simple equality comparisons." GIN: "'inverted indexes' which are appropriate for data values that contain multiple component values, such as arrays." BRIN: "store summaries about the values stored in consecutive physical block ranges of a table. Thus, they are most effective for columns whose values are well-correlated with the physical order of the table rows." — [PostgreSQL 18: Index Types](https://www.postgresql.org/docs/current/indexes-types.html) (n.d., PG 18.6 docs). **RECOMMENDED** default B-tree; GIN/GiST/BRIN **OPTIONAL/CONTEXTUAL** by data type/physical correlation. [all]
- MySQL: B-tree "can be used for column comparisons in expressions that use the `=`, `>`, `>=`, `<`, `<=`, or `BETWEEN` operators... also can be used for `LIKE` comparisons if the argument to `LIKE` is a constant string that does not start with a wildcard character." Hash indexes (MEMORY engine) "are used only for equality comparisons that use the `=` or `<=>` operators (but are *very* fast). They are not used for comparison operators such as `<`"; "The optimizer cannot use a hash index to speed up `ORDER BY`"; "Only whole keys can be used to search for a row." — [MySQL 8.4: Comparison of B-Tree and Hash Indexes](https://dev.mysql.com/doc/refman/8.4/en/index-btree-hash.html) (n.d.). [OLTP]
- SQL Server memory-optimized hash indexes: performance is "Excellent when the predicate in the `WHERE` clause specifies an *exact* value for each column in the hash index key... Poor when the predicate... looks for a *range* of values"; "The predicate must include *all* columns in the hash index key"; bucket count "should be between 1 and 2 times the number of distinct values in the index key"; if unique keys are "more than 100 times smaller than the row count... use a nonclustered index instead." Memory-optimized nonclustered indexes use "a Bw-tree... a lock and latch-free variation of a B-tree." — [SQL Server Index Architecture and Design Guide](https://learn.microsoft.com/en-us/sql/relational-databases/sql-server-index-design-guide) (ms.date 2026-09-14). **OPTIONAL/CONTEXTUAL** (In-Memory OLTP only). [OLTP]
- Oracle bitmap indexes: "primarily designed for data warehousing or environments in which queries reference many columns in an ad hoc fashion"; suited when "The indexed columns have low cardinality" and "The indexed table is either read-only or not subject to significant modification by DML statements"; because "a key points to many rows, DML on indexed data typically locks all of these rows. For this reason, bitmap indexes are not appropriate for many OLTP applications." — [Oracle Concepts: Indexes and Index-Organized Tables](https://docs.oracle.com/en/database/oracle/oracle-database/23/cncpt/indexes-and-index-organized-tables.html) (n.d.; served content labelled Oracle AI Database 26ai). **RECOMMENDED** bitmap for DW low-cardinality columns; **MANDATORY-avoid** in concurrent-DML OLTP per Oracle's locking reasoning. [OLAP/DW]
- Stonebraker (2005) states the same split as a "well known homily that warehouse applications run much better using bit-map indexes while OLTP users prefer B-tree indexes... bit-map indexes are faster and more compact on warehouse workloads, while failing to work well in OLTP environments." — ["One Size Fits All": An Idea Whose Time Has Come and Gone](https://cs.brown.edu/~ugur/fits_all.pdf) (2005). [OLAP/DW vs OLTP]
- SQL Server columnstore: "Columnstore indexes are the standard for storing and querying large data warehousing fact tables... gains up to 10 times the query performance in your data warehouse over traditional row-oriented storage... up to 10 times the data compression"; "Rowstore indexes perform best on queries that seek into the data... Use rowstore indexes with transactional workloads... Columnstore indexes give high performance gains for analytic queries that scan large amounts of data"; a rowgroup "usually contains the maximum number of rows per rowgroup, which is 1,048,576 rows"; batch mode "improves query performance typically by two to four times"; "Use a nonclustered columnstore index to perform analysis in real time on an OLTP workload." — [SQL Server: Columnstore indexes overview](https://learn.microsoft.com/en-us/sql/relational-databases/indexes/columnstore-indexes-overview) (2026-09-14). **RECOMMENDED** clustered columnstore for DW fact tables; nonclustered columnstore **OPTIONAL/CONTEXTUAL** for operational analytics. [OLAP/DW; HTAP]
- Oracle on index independence: "Indexes are schema objects that are logically and physically independent of the data... you can drop or create an index without physically affecting the indexed table"; "The absence or presence of an index does not require a change in the wording of any SQL statement." — [Oracle Concepts: Indexes](https://docs.oracle.com/en/database/oracle/oracle-database/23/cncpt/indexes-and-index-organized-tables.html). [all]

**Index anatomy (Winand)**
- Leaf nodes: "The logical order is established via a doubly linked list"; "It is thus possible to insert new entries without moving large amounts of data—it just needs to change some pointers"; "The physical location of the new node doesn't matter because the doubly linked list maintains the logical order." — [Use The Index, Luke: The Leaf Nodes](https://use-the-index-luke.com/sql/anatomy/the-leaf-nodes) (n.d.; copyright 2010-2026). [all]
- Oracle: "A B-tree index is balanced because all leaf blocks automatically stay at the same depth. Thus, retrieval of any record from anywhere in the index takes approximately the same amount of time." — [Oracle Concepts: Indexes](https://docs.oracle.com/en/database/oracle/oracle-database/23/cncpt/indexes-and-index-organized-tables.html).

**Clustered vs non-clustered / heap vs index-organized**
- SQL Server: "If you don't create a clustered index, the table is stored as a heap, which is generally not recommended." Clustered key should be **Narrow** ("The clustered index key is a part of any nonclustered index on the same base table"), **Unique** ("If the clustered index isn't unique, a 4-byte internal uniqueifier column is automatically added"), **Ever-increasing** ("data is always added on the last page of the index. This avoids page splits in the middle of the index"), **Immutable** ("When a key column of a clustered index is modified, a change must also be made in all nonclustered indexes"), not-nullable, fixed-width. "a clustered index key with a single **int** or **bigint** not nullable column has all of these properties if it's populated by an `IDENTITY` clause or a default constraint using a sequence". — [SQL Server Index Design Guide](https://learn.microsoft.com/en-us/sql/relational-databases/sql-server-index-design-guide) (2026-09-14). **RECOMMENDED** (reasoning: storage/I/O/memory overhead propagates to all nonclustered indexes). [OLTP]
- MySQL InnoDB: "When you define a `PRIMARY KEY` on a table, `InnoDB` uses it as the clustered index. A primary key should be defined for each table. If there is no logical unique and non-null column... add an auto-increment column." Without a PK, InnoDB uses "the first `UNIQUE` index with all key columns defined as `NOT NULL`", else "a hidden clustered index named `GEN_CLUST_INDEX`... 6-byte field that increases monotonically". "each record in a secondary index contains the primary key columns for the row... If the primary key is long, the secondary indexes use more space, so it is advantageous to have a short primary key." — [MySQL 8.4: Clustered and Secondary Indexes](https://dev.mysql.com/doc/refman/8.4/en/innodb-index-types.html) (n.d.). **RECOMMENDED** short PK; **MANDATORY** (de facto) to define a PK. [OLTP]
- Oracle: "In an index-organized table, rows are stored in an index defined on the primary key for the table... Thus, the index is the data, and the data is the index"; heap-organized tables "insert rows where they fit." — [Oracle Concepts: Indexes and IOTs](https://docs.oracle.com/en/database/oracle/oracle-database/23/cncpt/indexes-and-index-organized-tables.html). **OPTIONAL/CONTEXTUAL**. [OLTP]
- PostgreSQL has no clustered-table concept in the SQL Server/InnoDB sense; its index-only scan design reflects heap storage (see below). [Inference from PostgreSQL index-only scan docs.]

**Composite (concatenated/multicolumn) index column order — the nuance**
- PostgreSQL rule: "equality constraints on leading columns, plus any inequality constraints on the first column that does not have an equality constraint, will always be used to limit the portion of the index that is scanned. Constraints on columns to the right of these columns are checked in the index, so they'll always save visits to the table proper, but they do not necessarily reduce the portion of the index that has to be scanned." Also: "Multicolumn indexes should be used sparingly... Indexes with more than three columns are unlikely to be helpful unless the usage of the table is extremely stylized." GiST: "relatively ineffective if its first column has only a few distinct values"; GIN/BRIN: effectiveness "is the same regardless of which index column(s) the query conditions use." Limit: "up to 32 columns, including `INCLUDE` columns." — [PostgreSQL 18: Multicolumn Indexes](https://www.postgresql.org/docs/current/indexes-multicolumn.html) (n.d.). **RECOMMENDED** (equality-leading, few columns). [all]
- MySQL leftmost prefix: "MySQL can use multiple-column indexes for queries that test all the columns in the index, or queries that test just the first column, the first two columns... If you specify the columns in the right order in the index definition, a single composite index can speed up several kinds of queries"; "MySQL cannot use the index to perform lookups if the columns do not form a leftmost prefix of the index." Up to 16 columns. No selectivity-ordering guidance is given. — [MySQL 8.4: Multiple-Column Indexes](https://dev.mysql.com/doc/refman/8.4/en/multiple-column-indexes.html) (n.d.). **MANDATORY** constraint (prefix rule). [all]
- MongoDB ESR: "Ensure that equality fields always come first... If avoiding in-memory sorts is critical, place sort fields before range fields (ESR). If your range predicate in the query is very selective, then put it before sort fields (ERS)"; "Inequality operators such as `$ne` or `$nin` are range operators"; "`$regex` is a range operator"; "$in" behaves as equality when alone but as range in sorts with 201+ elements (threshold "not guaranteed to stay the same"). — [MongoDB Manual: The ESR Guideline](https://www.mongodb.com/docs/manual/tutorial/equality-sort-range-guideline/) (n.d., 9.0 docs). **RECOMMENDED**. [OLTP/document]
- Winand: "the column order of a concatenated index has great impact on its usability so it must be chosen carefully"; "a two-column index does not support searching on the second column alone"; the goal is to choose order "so it can be used as often as possible." — [Use The Index, Luke: Concatenated Indexes](https://use-the-index-luke.com/sql/where-clause/the-equals-operator/concatenated-keys) (n.d.). **RECOMMENDED**.
- Winand on the myth: "there is the myth that you should always put the most selective column to the first position; that is just wrong." Selectivity matters only when "indexing independent range conditions... that is the only case where the selectivity should influence the index design." He cites Guy Harrison ("Don't automatically put the most selective term first in a concatenated index", 2009), Jonathan Lewis (the rule "was never a sensible rule of thumb (except, possibly, prior to version 6.0)", 2007) and Gail Shaw ("It's useless to have the most selective column of the index on the left if very few queries filter on it", 2009); notes SQL Server keeps a histogram only on the first key column, so an unevenly-distributed column first can help statistics. — [Use The Index, Luke: Myth – Most Selective First](https://use-the-index-luke.com/sql/myth-directory/most-selective-first) (n.d.). **Contested/outdated advice flagged** (see Q6).
- SQL Server's guide gives no "most selective first" rule either; it frames index design as "a complex balancing act between query speed, index update cost, and storage cost. Narrow disk-based rowstore indexes... require less storage space and a smaller update overhead. Wide indexes, on the other hand, might improve more queries." Key columns are limited to "16 key columns maximum, and a total index key size of 900 bytes" (included columns excluded from that limit). — [SQL Server Index Design Guide](https://learn.microsoft.com/en-us/sql/relational-databases/sql-server-index-design-guide) (2026-09-14).
- PostgreSQL 18 loosens the prefix rule with skip scan: "Allow skip scans of btree indexes... multi-column btree indexes to be used in more cases such as when there are no restrictions on the first or early indexed columns". — [PostgreSQL 18 Release Notes](https://www.postgresql.org/docs/18/release-18.html) (2025-09-25). Oracle has long offered `INDEX SKIP SCAN` (per Winand's myth page). Implication: leading-column rules are engine- and version-dependent at the margin.

**Covering indexes / INCLUDE / index-only scans and visibility**
- SQL Server: "A *covering* index is a nonclustered index that satisfies all data access by a query directly without accessing the base table"; "If a column must be retrieved by a query, but isn't used in the query predicates, aggregations, and sorts, add it as an included column and not as a key column"; "Avoid creating a covering index with too many columns because that diminishes its benefit while inflating database storage, I/O, and memory footprint"; "It's often better to modify an existing index than to create a new but mostly duplicate index. For example, consider adding one or two extra included columns". — [SQL Server Index Design Guide](https://learn.microsoft.com/en-us/sql/relational-databases/sql-server-index-design-guide) (2026-09-14). **RECOMMENDED**. [OLTP]
- PostgreSQL: "Visibility information is not stored in index entries, only in heap entries"; the visibility map bit per heap page decides whether the heap must be visited; "an index-only scan... will be a win only if a significant fraction of the table's heap pages have their all-visible map bits set." INCLUDE: "`CREATE INDEX tab_x_y ON tab(x) INCLUDE (y);`"; "if the index is a unique index... the uniqueness condition applies to just column `x`"; "It's wise to be conservative about adding non-key payload columns to an index, especially wide columns... non-key columns duplicate data from the index's table and bloat the size of the index"; "there is little point in including payload columns in an index unless the table changes slowly enough that an index-only scan is likely to not need to access the heap." Only "B-tree, GiST and SP-GiST indexes currently support included columns." — [PostgreSQL 18: Index-Only Scans and Covering Indexes](https://www.postgresql.org/docs/current/indexes-index-only-scans.html) (n.d.). CREATE INDEX adds: "B-tree deduplication is never used with indexes that have a non-key column." — [PostgreSQL 18: CREATE INDEX](https://www.postgresql.org/docs/current/sql-createindex.html). **OPTIONAL/CONTEXTUAL** (depends on update rate / VACUUM-set visibility). [OLTP; read-mostly]
- MongoDB covered queries are referenced but the detail page was not fetched (gap).

**Partial / filtered indexes**
- PostgreSQL: "One major reason for using a partial index is to avoid indexing common values. Since a query searching for a common value (one that accounts for more than a few percent of all the table rows) will not use the index anyway, there is no point in keeping those rows in the index at all." Partial unique index example: `CREATE UNIQUE INDEX tests_success_constraint ON tests (subject, target) WHERE success;`. Planner caveat: "A partial index can be used in a query only if the system can recognize that the `WHERE` condition of the query mathematically implies the predicate of the index"; "parameterized query clauses do not work with a partial index". Anti-pattern: a set of non-overlapping partial indexes per category — "This is a bad idea! Almost certainly, you'll be better off with a single non-partial index" `ON mytable (category, data)`; for very large tables, partition instead. — [PostgreSQL 18: Partial Indexes](https://www.postgresql.org/docs/current/indexes-partial.html) (n.d.). **OPTIONAL/CONTEXTUAL**; **MANDATORY-avoid** partial indexes as a partitioning substitute. [OLTP]
- SQL Server filtered indexes: "especially suited for queries that require a small subset of data"; advantages "Improved query performance and plan quality" (filtered statistics "more accurate than full-table statistics"), "Reduced index update costs", "Reduced index storage costs"; useful for "Columns that contain many NULLs", "Heterogeneous columns that contain categories of data", ranges of amounts/time/dates; warning: "If the filtered index includes most of the rows in the table, it could cost more to maintain than a full-table index." — [SQL Server Index Design Guide](https://learn.microsoft.com/en-us/sql/relational-databases/sql-server-index-design-guide) (2026-09-14). **OPTIONAL/CONTEXTUAL**. [OLTP]

**Expression / function-based indexes and SARGability**
- Winand: "Although there is an index on `LAST_NAME`, it is unusable—because the search is _not_ on `LAST_NAME` but on `UPPER(LAST_NAME)`"; the fix is "a so-called _function-based index (FBI)_" with the exact expression; "SQL Server and MySQL do not support function-based indexes as described" and need a computed/generated column; "Sometimes ORM tools use `UPPER` and `LOWER` without the developer's knowledge" (Hibernate). — [Use The Index, Luke: Case-Insensitive Search](https://use-the-index-luke.com/sql/where-clause/functions/case-insensitive-search) (n.d.). **RECOMMENDED**. [OLTP]
- Oracle: "A function-based index computes the value of a function or expression... The database only uses the function-based index when the function is included in a query. When the database processes `INSERT` and `UPDATE` statements, however, it must still evaluate the function". Example `CREATE INDEX emp_fname_uppercase_idx ON employees ( UPPER(first_name) );` — [Oracle Concepts: Indexes](https://docs.oracle.com/en/database/oracle/oracle-database/23/cncpt/indexes-and-index-organized-tables.html).
- SQL Server: "Consider indexing computed columns if they are included in query predicates." — [SQL Server Index Design Guide](https://learn.microsoft.com/en-us/sql/relational-databases/sql-server-index-design-guide). MySQL offers "Optimizer Use of Generated Column Indexes" (chapter outline) — [MySQL 8.4: Optimization and Indexes](https://dev.mysql.com/doc/refman/8.4/en/optimization-indexes.html). PostgreSQL 18 made generated columns virtual by default ("Virtual generated columns generate their values when the columns are read, not written") — [PostgreSQL 18 Release Notes](https://www.postgresql.org/docs/18/release-18.html) (2025-09-25).

**Unique indexes as constraints**
- SQL Server: "If the data is unique and you want uniqueness enforced, creating a unique index instead of a nonunique index on the same combination of columns provides additional information for the query optimizer that can produce more efficient execution plans. Creating a `UNIQUE` constraint or a unique index is recommended in this case." — [SQL Server Index Design Guide](https://learn.microsoft.com/en-us/sql/relational-databases/sql-server-index-design-guide) (2026-09-14). **RECOMMENDED**. [all]
- PostgreSQL: "Adding a unique constraint will automatically create a unique B-tree index"; "Adding a primary key will automatically create a unique B-tree index... and will force the column(s) to be marked `NOT NULL`." — [PostgreSQL 18: Constraints](https://www.postgresql.org/docs/current/ddl-constraints.html) (n.d.). Oracle: "Unique indexes guarantee that no two rows of a table have duplicate values in the key column or columns." — [Oracle Concepts: Indexes](https://docs.oracle.com/en/database/oracle/oracle-database/23/cncpt/indexes-and-index-organized-tables.html). MongoDB: "MongoDB creates a unique index on the `_id` field during the creation of a collection... You cannot drop this index." — [MongoDB Manual: Indexes](https://www.mongodb.com/docs/manual/indexes/) (n.d.).

**Index maintenance cost, write amplification, too many indexes**
- PostgreSQL: "After an index is created, the system has to keep it synchronized with the table. This adds overhead to data manipulation operations. Indexes can also prevent the creation of heap-only tuples. Therefore indexes that are seldom or never used in queries should be removed." Also: writes "are blocked until the index build is finished" by default; use `CONCURRENTLY` ("requires more total work than a standard index build and takes significantly longer to complete. However, since it allows normal operations to continue... useful for adding new indexes in a production environment"). — [PostgreSQL 18: Indexes Introduction](https://www.postgresql.org/docs/current/indexes-intro.html); [PostgreSQL 18: CREATE INDEX](https://www.postgresql.org/docs/current/sql-createindex.html). **RECOMMENDED** (drop unused indexes). [all]
- MySQL: "Although it can be tempting to create an indexes for every possible column used in a query, unnecessary indexes waste space and waste time for MySQL to determine which indexes to use. Indexes also add to the cost of inserts, updates, and deletes because each index must be updated. You must find the right balance". — [MySQL 8.4: Optimization and Indexes](https://dev.mysql.com/doc/refman/8.4/en/optimization-indexes.html) (n.d.). **RECOMMENDED**.
- SQL Server: "A common design mistake is to create many indexes speculatively to 'give the optimizer choices'. The resulting overindexing slows down data modifications and can cause concurrency problems"; "Avoid over-indexing heavily updated tables and keep indexes narrow"; "You can have more indexes on tables that have few data modifications but large volumes of data... However, don't create indexes speculatively. Monitor index usage, and remove unused indexes over time"; "Indexing small tables might not be optimal"; for OLTP "a few narrow rowstore indexes targeted for the most critical queries would be a good initial index design"; for OLAP "clustered columnstore indexes would be especially appropriate." — [SQL Server Index Design Guide](https://learn.microsoft.com/en-us/sql/relational-databases/sql-server-index-design-guide) (2026-09-14). **RECOMMENDED**. [OLTP few/narrow; OLAP columnstore]
- Oracle: "the presence of many indexes on a table degrades DML performance because the database must also update the indexes." — [Oracle Concepts: Indexes](https://docs.oracle.com/en/database/oracle/oracle-database/23/cncpt/indexes-and-index-organized-tables.html).
- MongoDB: "adding an index has negative performance impact for write operations. For collections with a high write-to-read ratio, indexes are expensive because each insert must also update any indexes." — [MongoDB Manual: Indexes](https://www.mongodb.com/docs/manual/indexes/) (n.d.).
- Oracle's inverse point — when to index: "The indexed columns are queried frequently and return a small percentage of the total number of rows in the table"; selectivity defined as "the percentage of rows in the table that the query selects, with 0 meaning no rows and 1 meaning all rows." — [Oracle Concepts: Indexes](https://docs.oracle.com/en/database/oracle/oracle-database/23/cncpt/indexes-and-index-organized-tables.html). SQL Server: "Create nonclustered indexes on the columns that are frequently used in predicates and join expressions in queries. These are your *SARGable* columns." — [SQL Server Index Design Guide](https://learn.microsoft.com/en-us/sql/relational-databases/sql-server-index-design-guide).

**"Index every foreign key?" — engine dependent**
- PostgreSQL does NOT auto-index: "Since a `DELETE` of a row from the referenced table or an `UPDATE` of a referenced column will require a scan of the referencing table for rows matching the old value, it is often a good idea to index the referencing columns too. Because this is not always needed, and there are many choices available on how to index, the declaration of a foreign key constraint does not automatically create an index on the referencing columns." The referenced side is always indexed because "A foreign key must reference columns that either are a primary key or form a unique constraint, or are columns from a non-partial unique index." — [PostgreSQL 18: Constraints](https://www.postgresql.org/docs/current/ddl-constraints.html) (n.d.). **RECOMMENDED** (PostgreSQL: usually index FK columns, decide case-by-case). [OLTP]
- MySQL/InnoDB DOES auto-index: "MySQL requires indexes on foreign keys and referenced keys so that foreign key checks can be fast and not require a table scan. In the referencing table, there must be an index where the foreign key columns are listed as the *first* columns in the same order. Such an index is created on the referencing table automatically if it does not exist. This index might be silently dropped later if you create another index that can be used to enforce the foreign key constraint." — [MySQL 8.4: FOREIGN KEY Constraints](https://dev.mysql.com/doc/refman/8.4/en/create-table-foreign-keys.html) (n.d.). **MANDATORY** (engine-enforced). [OLTP]
- Oracle recommends indexing FK columns to avoid locking: consider an index when "A referential integrity constraint exists on the indexed column or columns. The index is a means to avoid a full table lock that would otherwise be required if you update the parent table primary key, merge into the parent table, or delete from the parent table." — [Oracle Concepts: Indexes](https://docs.oracle.com/en/database/oracle/oracle-database/23/cncpt/indexes-and-index-organized-tables.html). **RECOMMENDED**. [OLTP]
- Citus (distributed PostgreSQL) adds a different constraint: "Citus requires that primary and foreign key constraints include the distribution column." — [Citus: Multi-tenant Applications](https://docs.citusdata.com/en/stable/use_cases/multi_tenant.html) (Citus 13.0.1, n.d.). **MANDATORY** in Citus. [sharded OLTP]

**Fill factor**
- PostgreSQL: "B-trees use a default fillfactor of 90, but any integer value from 10 to 100 can be selected"; "B-tree indexes on tables where many inserts and/or updates are anticipated can benefit from lower fillfactor settings... Values in the range of 50 - 90 can usefully 'smooth out' the _rate_ of page splits"; fillfactor 100 only "when you are completely sure that the table is static... A fillfactor setting of 100 otherwise risks _harming_ performance: even a few updates or inserts will cause a sudden flood of page splits." — [PostgreSQL 18: CREATE INDEX](https://www.postgresql.org/docs/current/sql-createindex.html) (n.d.). **OPTIONAL/CONTEXTUAL**. [OLTP]
- SQL Server ties page splits to clustered-key design (ever-increasing keys avoid "page splits in the middle of the index, which reduce page density") — [SQL Server Index Design Guide](https://learn.microsoft.com/en-us/sql/relational-databases/sql-server-index-design-guide); Oracle reverse key indexes address "contention for leaf blocks in the right side of a B-tree index" at the cost that it "eliminates the ability to run an index range scanning query in some cases." — [Oracle Concepts: Indexes](https://docs.oracle.com/en/database/oracle/oracle-database/23/cncpt/indexes-and-index-organized-tables.html).

**Invisible / hypothetical indexes**
- Oracle: "An invisible index is maintained by DML operations, but is not used by default by the optimizer... especially useful for testing the removal of an index before dropping it"; unusable indexes are "not maintained by DML operations" and "can improve the performance of bulk loads." — [Oracle Concepts: Indexes](https://docs.oracle.com/en/database/oracle/oracle-database/23/cncpt/indexes-and-index-organized-tables.html). **RECOMMENDED** as a safe drop-test. [all]
- MySQL: "Invisible indexes make it possible to test the effect of removing an index on query performance, without making a destructive change that must be undone should the index turn out to be required"; "a unique index prevents insertion of duplicates... regardless of whether the index is visible or invisible"; "A primary key index cannot be invisible." — [MySQL 8.4: Invisible Indexes](https://dev.mysql.com/doc/refman/8.4/en/invisible-indexes.html) (n.d.).
- PostgreSQL has no native invisible index; HypoPG provides hypothetical indexes "not stored in any catalog, but in your connection private memory", usable only via "a simple EXPLAIN statement (without the ANALYZE option)"; supports btree, brin, hash (PG 10+) and bloom. — [HypoPG: Usage](https://hypopg.readthedocs.io/en/latest/usage.html) (n.d.; v1.1.0 shown). **OPTIONAL**. [all]
- SQL Server Azure: "Databases on primary replicas in Azure SQL Database automatically generate database advisor performance recommendations for indexes. You can optionally enable automatic index tuning." — [SQL Server Index Design Guide](https://learn.microsoft.com/en-us/sql/relational-databases/sql-server-index-design-guide) (2026-09-14).

**Winand on ORDER BY / pagination**
- OFFSET: "the database must count all rows from the beginning until it reaches the requested page." Seek/keyset method "searches the last entry of the previous page and fetches only the following rows"; "Paging requires a deterministic sort order" (add a unique tiebreaker such as the PK); row-values syntax `(sale_date, sale_id) < (?, ?)` is usable for index access in PostgreSQL and Db2 but "SQL Server 2017 does not support it"; drawback: "you also cannot fetch arbitrary pages." — [Use The Index, Luke: Fetching the Next Page](https://use-the-index-luke.com/sql/partial-results/fetch-next-page) (n.d.). **RECOMMENDED** keyset pagination for deep/infinite scrolling; **OPTIONAL** OFFSET for shallow random-page access. [OLTP]
- SQL Server: "If a disk-based rowstore index is created with key columns that match those in the `ORDER BY` clause in the query, the **Sort** operator in the query plan is eliminated". — [SQL Server Index Design Guide](https://learn.microsoft.com/en-us/sql/relational-databases/sql-server-index-design-guide). MongoDB ESR: "To avoid in-memory sorts, put sort fields before range in the index." — [MongoDB ESR Guideline](https://www.mongodb.com/docs/manual/tutorial/equality-sort-range-guideline/).

**Conflicts / divergences within Q1**
- FK auto-indexing: PostgreSQL (manual, case-by-case) vs MySQL InnoDB (automatic, can be silently dropped) vs Oracle (recommended to avoid parent-table locking). Framework rule must be engine-specific.
- Column order: vendor docs state only the prefix/equality-leading mechanics; the "most selective first" rule is absent from all vendor pages fetched and explicitly rejected by Winand/Harrison/Lewis/Shaw. MongoDB's ESR is the most prescriptive vendor rule and still offers ERS as an alternative when the range is very selective — i.e., selectivity re-enters only for range predicates, matching Winand.
- Covering indexes: SQL Server encourages wide INCLUDE lists more readily ("consider adding one or two extra included columns") whereas PostgreSQL warns payload columns are pointless unless the table "changes slowly enough" for index-only scans to skip the heap, and disables B-tree deduplication for INCLUDE indexes.
- Hash indexes: PostgreSQL stores 32-bit hash codes (equality-only); SQL Server positions hash only for memory-optimized tables with bucket sizing; MySQL only for MEMORY engine. No vendor recommends hash as a general-purpose default.

### Inferences
- A workload-aware rule set: OLTP = few, narrow B-tree indexes on SARGable predicates/joins + unique indexes for constraints + FK indexes (explicit on PostgreSQL/Oracle, automatic on InnoDB); OLAP/DW = columnstore/bitmap and far fewer B-trees; HTAP = row store + secondary columnar copy (SQL Server NCCI, TiDB TiFlash).
- "Equality-first, then sort, then range; order equality columns by how many queries can reuse the prefix" is the defensible composite-order rule; selectivity decides only (a) which of multiple range columns to lead with and (b) statistics quality on engines that keep histograms only on the first key column.
- Covering-index payoff is engine-dependent: strong on SQL Server/InnoDB (clustered/secondary design), conditional on PostgreSQL (visibility map).

### Gaps
- MongoDB sub-pages for covered queries, partial indexes, TTL indexes, 64-index limit and the "indexes should fit in RAM" guidance were not fetched; only the top-level Indexes page and the ESR page were verified.
- The PostgreSQL "Indexes" chapter landing page (indexes.html) itself was not fetched; five of its sub-pages were. 
- No vendor page fetched gives a numeric "max indexes per OLTP table" threshold; all guidance is qualitative ("few narrow", "avoid over-indexing").

## Key Question 2: What do the sources say about query optimization — SARGability, implicit conversions, statistics and the cost-based optimizer, EXPLAIN/EXPLAIN ANALYZE, N+1, SELECT *, join strategies, materialized views, hints, prepared statements/plan caching?

### Takeaway
The optimizer is cost-based and statistics-driven everywhere; the documented levers are: write SARGable predicates (no functions/implicit casts on indexed columns), keep statistics fresh, read EXPLAIN/EXPLAIN ANALYZE, do joins in the database rather than N+1 round trips, use materialized/indexed views for warehouse-style aggregation (never in high-DML OLTP), treat hints as a last resort (PostgreSQL deliberately has none), and understand generic-vs-custom plan caching for prepared statements.

### Cited Findings

**SARGability and implicit conversions**
- SQL Server: "The term *SARGable* in relational databases refers to a **S**earch **ARG**ument**able** predicate that can use an index to speed up the execution of the query"; "Don't always equate index usage with good performance, and good performance with efficient index use... an incorrect index choice can cause less than optimal performance." — [SQL Server Index Design Guide](https://learn.microsoft.com/en-us/sql/relational-databases/sql-server-index-design-guide) (2026-09-14). **RECOMMENDED**. [all]
- MySQL implicit conversion: "For comparisons of a string column with a number, MySQL cannot use an index on the column to look up the value quickly. If _`str_col`_ is an indexed string column, the index cannot be used when performing the lookup in the following statement: `SELECT * FROM tbl_name WHERE str_col=1;`... there are many different strings that may convert to the value `1`, such as `'1'`, `' 1'`, or `'1a'`." String vs numeric operands "are compared as floating-point (double-precision) numbers." — [MySQL 8.4: Type Conversion in Expression Evaluation](https://dev.mysql.com/doc/refman/8.4/en/type-conversion.html) (n.d.). **MANDATORY-avoid** mismatched-type predicates. [OLTP]
- PostgreSQL wiki: `char(n)` — "you may be unexpectedly unable to use an index for the comparison" when a driver sends `text`/`varchar` parameters; "there is no performance benefit whatsoever to using char(n) over varchar(n)"; `NOT IN (SELECT ...)` — "the planner can't transform it into an anti-join", use `NOT EXISTS`; `BETWEEN` with timestamps double-counts midnight, use half-open `>=`/`<`. — [PostgreSQL Wiki: Don't Do This](https://wiki.postgresql.org/wiki/Don%27t_Do_This) (2024-11-21). **RECOMMENDED** (community). [all]
- Winand on functions in WHERE: optimizer treats `UPPER` as a black box; only an index on the identical expression is usable (see Q1). — [Use The Index, Luke: Case-Insensitive Search](https://use-the-index-luke.com/sql/where-clause/functions/case-insensitive-search).

**Statistics and the cost-based optimizer**
- PostgreSQL: "you might have to run the `ANALYZE` command regularly to update statistics to allow the query planner to make educated decisions"; the planner uses an index "when it thinks doing so would be more efficient than a sequential table scan." — [PostgreSQL 18: Indexes Introduction](https://www.postgresql.org/docs/current/indexes-intro.html). Cost model: "The costs are measured in arbitrary units determined by the planner's cost parameters... Traditional practice is to measure the costs in units of disk page fetches; that is, seq_page_cost is conventionally set to `1.0`"; example "(345 \* 1.0) + (10000 \* 0.01) = 445"; estimates "can change after each `ANALYZE` command, because the statistics produced by `ANALYZE` are taken from a randomized sample." — [PostgreSQL 18: Using EXPLAIN](https://www.postgresql.org/docs/current/using-explain.html) (n.d.). **MANDATORY** (keep statistics current). [all]
- SQL Server: filtered indexes carry "filtered statistics, which are more accurate than full-table statistics"; partitioned index builds use "the default sampling algorithm" so `UPDATE STATISTICS ... FULLSCAN` may be needed. — [SQL Server Index Design Guide](https://learn.microsoft.com/en-us/sql/relational-databases/sql-server-index-design-guide); [SQL Server: Partitioned Tables and Indexes](https://learn.microsoft.com/en-us/sql/relational-databases/partitions/partitioned-tables-and-indexes) (2025-12-29).
- Oracle query rewrite requires cost-based optimization: "Cost-based optimization must be used by setting the initialization parameter `OPTIMIZER_MODE` to `ALL_ROWS`, `FIRST_ROWS`, or `FIRST_ROWS_`_n_." — [Oracle DW Guide: Basic Query Rewrite](https://docs.oracle.com/en/database/oracle/oracle-database/23/dwhsg/basic-query-rewrite-materialized-views.html) (n.d.).

**EXPLAIN / EXPLAIN ANALYZE and access-path selection**
- "The structure of a query plan is a tree of _plan nodes_"; each node shows "Estimated start-up cost... Estimated total cost... Estimated number of rows... Estimated average width". "With this option, `EXPLAIN` actually executes the query, and then displays the true row counts and true run time"; warning: "because `EXPLAIN ANALYZE` actually runs the query, any side-effects will happen as usual" — wrap data-modifying statements in `BEGIN; ... ROLLBACK;`. Plan shapes: Seq Scan with Filter for `unique1 < 7000`; "Bitmap Heap Scan... Bitmap Index Scan" for `unique1 < 100` ("still cheaper than a sequential scan"); plain Index Scan for `unique1 = 42` ("You'll most often see this plan type for queries that fetch just a single row"). — [PostgreSQL 18: Using EXPLAIN](https://www.postgresql.org/docs/current/using-explain.html) (n.d.). **MANDATORY** practice for tuning. [all]
- SQL Server: "The query optimizer in the Database Engine usually chooses the most effective indexes... select **Display Estimated Execution Plan** or **Include Actual Execution Plan**." — [SQL Server Index Design Guide](https://learn.microsoft.com/en-us/sql/relational-databases/sql-server-index-design-guide). MongoDB: use `explain` and `cursor.hint()` when testing indexes. — [MongoDB ESR Guideline](https://www.mongodb.com/docs/manual/tutorial/equality-sort-range-guideline/).

**Join strategies**
- PostgreSQL: nested loop ("run its second, or 'inner' child once for each row obtained from the outer child"), hash join ("rows of one table are entered into an in-memory hash table, after which the other table is scanned and the hash table is probed"), merge join ("requires its input data to be sorted on the join keys"); `SET enable_mergejoin = off;` to compare alternatives. — [PostgreSQL 18: Using EXPLAIN](https://www.postgresql.org/docs/current/using-explain.html). Indexes "can moreover be used in join searches. Thus, an index defined on a column that is part of a join condition can also significantly speed up queries with joins." — [PostgreSQL 18: Indexes Introduction](https://www.postgresql.org/docs/current/indexes-intro.html). [all]
- Oracle partition-wise joins and SQL Server collocated joins (see Q3) are the partition-level analogue.

**N+1 queries**
- Winand: "The nested loops join is the most fundamental join algorithm"; ORMs "don't generate SQL joins—instead they query the `SALES` table with nested selects"; "it executes N+1 selects in total if the driving query returns N rows"; "network latencies occur on top of disk latencies"; "the number of database round trips is more important for the response time than the amount of data transferred"; advice: "Execute joins in the database", use eager fetching/`JOIN FETCH`, but "Eager fetching is counterproductive if you do not need the child records every time you access the parent object... A static configuration is no solution." — [Use The Index, Luke: Nested Loops / N+1 Problem](https://use-the-index-luke.com/sql/join/nested-loops-join-n1-problem) (n.d.). **RECOMMENDED**. [OLTP]

**SELECT * concerns**
- No vendor page fetched issues a blanket "never SELECT *" rule. Related evidence: SQL Server indexed views forbid `SELECT [ <table>. ] *` ("Explicitly name columns") — [SQL Server: Create Indexed Views](https://learn.microsoft.com/en-us/sql/relational-databases/views/create-indexed-views) (2025-01-14); covering/index-only scans require "The query must reference only columns stored in the index" — [PostgreSQL 18: Index-Only Scans](https://www.postgresql.org/docs/current/indexes-index-only-scans.html); columnstore gains partly because "Queries often select only a few columns from a table, which reduces total I/O" — [SQL Server: Columnstore indexes overview](https://learn.microsoft.com/en-us/sql/relational-databases/indexes/columnstore-indexes-overview). **RECOMMENDED** (project only needed columns) by inference; see Q6.

**Materialized views / indexed views / query rewrite**
- Oracle: "Because materialized views contain already precomputed aggregates and joins, Oracle AI Database employs an extremely powerful process called query rewrite to quickly answer the query using materialized views. The transformation is transparent to the end user or application"; "materialized views can be added or dropped just like indexes without invalidating the SQL in the application code." Requirements: `ENABLE QUERY REWRITE`, `QUERY_REWRITE_ENABLED = TRUE` (default) or `FORCE`, cost-based optimizer. Integrity modes: `ENFORCED` (default, fresh data only), `TRUSTED`, `STALE_TOLERATED` ("maximum rewrite capability but creates the risk of generating inaccurate results"). — [Oracle DW Guide: Basic Query Rewrite for Materialized Views](https://docs.oracle.com/en/database/oracle/oracle-database/23/dwhsg/basic-query-rewrite-materialized-views.html) (n.d.). **RECOMMENDED** for DW. [OLAP/DW]
- SQL Server: "The first index created on a view must be a unique clustered index... the view is stored in the database in the same way a table with a clustered index is stored... The view doesn't have to be referenced in the query for the optimizer to consider that view for a substitution." Cost: "When you execute `UPDATE`, `DELETE` or `INSERT` operations... on a table referenced by a large number of indexed views, or fewer but complex indexed views, those referenced indexed views have to be updated as well. As a result, DML query performance can degrade significantly, or in some cases, a query plan can't even be produced." Requirements: `WITH SCHEMABINDING`, deterministic expressions, `COUNT_BIG(*)` with `GROUP BY`, no outer joins/subqueries/CTEs/`DISTINCT`/`TOP`/window functions; automatic matching only in specific editions (Standard needs `NOEXPAND`). — [SQL Server: Create Indexed Views](https://learn.microsoft.com/en-us/sql/relational-databases/views/create-indexed-views) (2025-01-14). **OPTIONAL/CONTEXTUAL**; **MANDATORY** requirements if used. [OLAP/DW; read-mostly OLTP]
- Stonebraker: "materialized views are a useful optimization tactic in warehouse worlds, but never in OLTP worlds. In contrast, normal ('virtual') views find acceptance in OLTP environments." — ["One Size Fits All"](https://cs.brown.edu/~ugur/fits_all.pdf) (2005). (Partial conflict: SQL Server allows indexed views on OLTP tables but documents the DML penalty; Oracle's `STALE_TOLERATED` trades freshness for rewrite.)
- CQRS read models: "it can store a materialized view of the data to avoid complex joins or O/RM mappings"; "Eventual consistency. When the read databases and write databases are separated, the read data might not show the most recent changes immediately." — [Azure Architecture Center: CQRS pattern](https://learn.microsoft.com/en-us/azure/architecture/patterns/cqrs) (2025-02-20). [read-scaling OLTP]

**Query hints caution**
- PostgreSQL community reasons for not implementing hints: "Poor application code maintainability: hints in queries require massive refactoring"; "Interference with upgrades: today's helpful hints become anti-performance after an upgrade"; "Encouraging bad DBA habits slap a hint on instead of figuring out the real issue"; "Does not scale with data size: the hint that's right when a table is small is likely to be wrong when it gets larger"; "Failure to actually improve query performance: most of the time, the optimizer is actually right"; "Interfering with improving the query planner". — [PostgreSQL Wiki: OptimizerHintsDiscussion](https://wiki.postgresql.org/wiki/OptimizerHintsDiscussion) (2015-07-05). **RECOMMENDED-avoid** (community position; dated 2015). [all]
- SQL Server offers `OPTION (EXPAND VIEWS)` / `NOEXPAND`; MongoDB `cursor.hint()` "when testing indexes"; Oracle `QUERY_REWRITE_INTEGRITY` session settings — hints exist but are framed as testing/override tools. — [SQL Server: Create Indexed Views](https://learn.microsoft.com/en-us/sql/relational-databases/views/create-indexed-views); [MongoDB ESR Guideline](https://www.mongodb.com/docs/manual/tutorial/equality-sort-range-guideline/).

**Prepared statements and plan caching**
- PostgreSQL: "When the `PREPARE` statement is executed, the specified statement is parsed, analyzed, and rewritten... This division of labor avoids repetitive parse analysis work, while allowing the execution plan to depend on the specific parameter values supplied"; "Prepared statements only last for the duration of the current database session"; plan choice: "the first five executions are done with custom plans and the average estimated cost of those plans is calculated. Then a generic plan is created and its estimated cost is compared to the average custom-plan cost. Subsequent executions use the generic plan if its cost is not so much higher than the average custom-plan cost as to make repeated replanning seem preferable"; override with `plan_cache_mode` = `force_generic_plan`/`force_custom_plan`, "primarily useful if the generic plan's cost estimate is badly off"; inspect with `EXPLAIN EXECUTE`. — [PostgreSQL 18: PREPARE](https://www.postgresql.org/docs/current/sql-prepare.html) (n.d.). **RECOMMENDED**. [OLTP]
- Partial-index interaction: "parameterized query clauses do not work with a partial index" because matching happens at plan time. — [PostgreSQL 18: Partial Indexes](https://www.postgresql.org/docs/current/indexes-partial.html).
- Pooling interaction: in PgBouncer transaction mode, `PREPARE`/`DEALLOCATE` are "Never" supported, though "Protocol-level prepared plans work in transaction mode, but only if `max_prepared_statements` is set to a non-zero value." — [PgBouncer: Features](https://www.pgbouncer.org/features.html) (n.d.; 1.26.1 listed).

### Inferences
- The framework should treat "SARGable predicates + current statistics + EXPLAIN-driven verification" as mandatory baseline practice for every workload, and treat materialized/indexed views as an OLAP/read-model tool with an explicit DML-cost gate for OLTP.
- Hints should be modelled as a last-resort override with an expiry/review obligation (PostgreSQL's upgrade argument), not a schema-design primitive.

### Gaps
- No fetched vendor page explicitly quantifies the cost of `SELECT *` on wide rows; the guidance is inferred from covering-index and columnstore mechanics.
- Oracle's optimizer-hints documentation and SQL Server's query-hint cautions were not fetched; only PostgreSQL's community position is cited.
- The PostgreSQL wiki hints page is from 2015 and predates `pg_hint_plan` maturity; it was not re-validated against current community statements.

## Key Question 3: What do the sources prescribe for partitioning — strategies, pruning, partition keys, global vs local indexes, PostgreSQL limitations, SQL Server functions/schemes, time-based retention, BigQuery/Snowflake analogues?

### Takeaway
All relational vendors offer range/list/hash (and composite) partitioning and agree that the headline benefits are manageability (fast drop/detach/switch of partitions, per-partition maintenance, tiered storage) and pruning for queries that filter on the partition key; both PostgreSQL and SQL Server warn that partitioning rarely helps and can hurt OLTP point queries, and that too many partitions costs planning time/memory. PostgreSQL requires unique/PK constraints to include the partition key; Oracle prescribes global indexes for OLTP and local for DSS; cloud warehouses replace B-tree indexes with partitioning plus clustering keys.

### Cited Findings

**Strategies and definitions**
- Oracle: "Partitioning allows a table, index, or index-organized table to be subdivided into smaller pieces, where each piece... is called a partition"; "from the perspective of the application, a partitioned table is identical to a nonpartitioned table"; strategies "Range, Hash, List"; "Range partitioning is the most common type of partitioning and is often used with dates"; hash "evenly distributes rows among partitions"; composite = one method then subpartition by another. — [Oracle VLDB and Partitioning Guide: Partitioning Concepts](https://docs.oracle.com/en/database/oracle/oracle-database/23/vldbg/partition-concepts.html) (n.d.; Oracle AI Database 26ai content). [all]
- PostgreSQL built-in forms: Range ("no overlap between the ranges"), List ("explicitly listing which key value(s) appear in each partition"), Hash ("specifying a modulus and a remainder for each partition"). — [PostgreSQL 18: Table Partitioning](https://www.postgresql.org/docs/current/ddl-partitioning.html) (n.d.).
- SQL Server: "A partition function is a database object that defines how the rows of a table or index are mapped to a set of partitions based on the values of a certain column, called a partitioning column"; "A partition scheme is a database object that maps the partitions of a partition function to one filegroup or to multiple filegroups"; `RANGE LEFT`/`RIGHT`; "`RIGHT` ranges are often simpler to work with when partitioning a table based on a column of **datetime**"; "The database engine supports up to 15,000 partitions." — [SQL Server: Partitioned Tables and Indexes](https://learn.microsoft.com/en-us/sql/relational-databases/partitions/partitioned-tables-and-indexes) (2025-12-29).

**Benefits: manageability first, performance conditional**
- Oracle: "Partitioning can provide tremendous benefit to a wide variety of applications by improving performance, manageability, and availability"; "Partition pruning is the simplest and also the most substantial means to improve performance using partitioning" (weekly-partitioned 2-year Orders table: a one-week query "could potentially execute 100 times faster simply because of partition pruning"); partition-wise joins "break a large join into smaller joins that occur between each of the partitions"; rolling window: "The load process is simply the addition of a new partition using a partition exchange load"; ILM: "enables groups of data (that is, partitions) to be distributed across different types of storage devices and managed individually." — [Oracle VLDB Guide: Partitioning Concepts](https://docs.oracle.com/en/database/oracle/oracle-database/23/vldbg/partition-concepts.html). **RECOMMENDED** for large/historical tables. [OLAP/DW; large OLTP]
- PostgreSQL: "Query performance can be improved dramatically in certain situations, particularly when most of the heavily accessed rows of the table are in a single partition or a small number of partitions. Partitioning effectively substitutes for the upper tree levels of indexes"; "Bulk loads and deletes can be accomplished by adding or removing partitions... Dropping an individual partition using `DROP TABLE`, or doing `ALTER TABLE DETACH PARTITION`, is far faster than a bulk operation. These commands also entirely avoid the `VACUUM` overhead caused by a bulk `DELETE`"; "Seldom-used data can be migrated to cheaper and slower storage media." — [PostgreSQL 18: Table Partitioning](https://www.postgresql.org/docs/current/ddl-partitioning.html). **RECOMMENDED** for retention via drop-partition. [all]
- SQL Server: "Partitioning large tables or indexes can have the following manageability and performance benefits": fast subset transfer ("loading data from an OLTP to an OLAP system takes only seconds"), per-partition maintenance ("compress data in one or more partitions, rebuild one or more partitions of an index, or truncate data in a single partition. You might also switch individual partitions out of one table and into an archive table"), equijoin speedups when "the partitioning columns are the same as the columns on which the tables are joined", and partition-level lock escalation (`LOCK_ESCALATION = AUTO`). — [SQL Server: Partitioned Tables and Indexes](https://learn.microsoft.com/en-us/sql/relational-databases/partitions/partitioned-tables-and-indexes) (2025-12-29).

**When to partition — thresholds**
- Oracle: "Tables that are greater than 2 GB. These tables should always be considered as candidates for partitioning"; "Tables that contain historical data, in which new data is added into the newest partition"; "Tables whose contents must be distributed across different types of storage devices." — [Oracle VLDB Guide](https://docs.oracle.com/en/database/oracle/oracle-database/23/vldbg/partition-concepts.html). **OPTIONAL/CONTEXTUAL**.
- PostgreSQL: "These benefits will normally be worthwhile only when a table would otherwise be very large... a rule of thumb is that the size of the table should exceed the physical memory of the database server." — [PostgreSQL 18: Table Partitioning](https://www.postgresql.org/docs/current/ddl-partitioning.html). **OPTIONAL/CONTEXTUAL**. (Conflict: Oracle's 2 GB vs PostgreSQL's "exceeds RAM" — different eras/assumptions; see Q6.)

**Partition key choice and number of partitions**
- PostgreSQL: "Often the best choice will be to partition by the column or set of columns which most commonly appear in `WHERE` clauses"; "Not having enough partitions may mean that indexes remain too large... However, dividing the table into too many partitions can also cause issues. Too many partitions can mean longer query planning times and higher memory consumption"; "The query planner is generally able to handle partition hierarchies with up to a few thousand partitions fairly well, provided that typical queries allow the query planner to prune all but a small number of partitions"; sub-partitioning/multi-column keys "can easily lead to excessive numbers of partitions, so restraint is advisable"; "Never just assume that more partitions are better than fewer partitions, nor vice-versa." — [PostgreSQL 18: Table Partitioning](https://www.postgresql.org/docs/current/ddl-partitioning.html). **RECOMMENDED**. [all]
- SQL Server: "Avoid designs with the number of partitions in many hundreds or thousands unless strictly necessary"; "We recommend that you use at least 16 GB of RAM if a large number of partitions are in use"; "Creating and rebuilding nonaligned indexes on a table with more than 1,000 partitions might be possible, but isn't supported"; "Queries that don't use partition elimination could take longer to execute as the number of partitions increases"; "a query that performs a single-row seek or a small range scan takes longer against a partitioned table than against a nonpartitioned table if query predicate doesn't include the partitioning column... For this reason, partitioning rarely improves performance in OLTP systems where such queries are common"; non-collocated joins: "the presence of partitions might actually slow down query processing instead of accelerate it." The index guide repeats: "Partitioning rarely improves query performance in OLTP systems, but it can introduce a significant overhead if a transactional query must access many partitions." — [SQL Server: Partitioned Tables and Indexes](https://learn.microsoft.com/en-us/sql/relational-databases/partitions/partitioned-tables-and-indexes) (2025-12-29); [SQL Server Index Design Guide](https://learn.microsoft.com/en-us/sql/relational-databases/sql-server-index-design-guide) (2026-09-14). **RECOMMENDED-avoid** partitioning OLTP for performance. [OLTP]
- Citus (sharded PostgreSQL): "Do not choose a timestamp as the distribution column" — use tenant/entity IDs for distribution and PostgreSQL table partitioning for time. — [Citus: Choosing Distribution Column](https://docs.citusdata.com/en/stable/sharding/data_modeling.html) (Citus 13.0.1). Oracle: range on dates is "the most common". (Nuance: time is a good *partition* key within a node but a bad *shard/distribution* key across nodes.)

**Global vs local indexes (Oracle); aligned vs nonaligned (SQL Server)**
- Oracle: "each partition of a local index is associated with exactly one partition of the table"; "In general, you should use global indexes for OLTP applications and local indexes for data warehousing or decision support systems (DSS) applications"; ordered guidelines: "1. If the table partitioning column is a subset of the index keys, then use a local index... 2. If the index is unique and does not include the partitioning key columns, then use a global index... 4. If the application is an OLTP type and users need quick response times, then use a global index. If the application is a DSS type and users are more interested in throughput, then use a local index." — [Oracle VLDB Guide: Partitioning Concepts](https://docs.oracle.com/en/database/oracle/oracle-database/23/vldbg/partition-concepts.html). **RECOMMENDED**. [OLTP global; OLAP local]
- SQL Server: "An index that is built on the same partition scheme as its corresponding table is called an aligned index. When a table and its nonclustered indexes are in alignment, the database engine can switch partitions in or out of the table quickly"; "When partitioning a clustered index, the clustering key must contain the partitioning column"; "When partitioning a unique nonclustered index, the index key must contain the partitioning column"; nonaligned indexes are useful when "The index key is unique, doesn't contain the partitioning column of the table, and the uniqueness of the index must be preserved." — [SQL Server: Partitioned Tables and Indexes](https://learn.microsoft.com/en-us/sql/relational-databases/partitions/partitioned-tables-and-indexes) (2025-12-29). **MANDATORY** (uniqueness/partition-key coupling).

**PostgreSQL declarative partitioning limitations**
- "To create a unique or primary key constraint on a partitioned table, the partition keys must not include any expressions or function calls and the constraint's columns must include all of the partition key columns. This limitation exists because the individual indexes making up the constraint can only directly enforce uniqueness within their own partitions"; "an exclusion constraint must include all the partition key columns... must compare those columns for equality"; "`BEFORE ROW` triggers on `INSERT` cannot change which partition is the final destination for a new row"; "Mixing temporary and permanent relations in the same partition tree is not allowed"; `TRUNCATE ONLY` on a partitioned table errors; partitions cannot have columns the parent lacks. Pruning: `enable_partition_pruning` (default on) and "Pruning also happens at execution time for values unknown at plan time, such as prepared-statement parameters and subquery results." Example DDL: `CREATE TABLE measurement (...) PARTITION BY RANGE (logdate); CREATE TABLE measurement_y2006m02 PARTITION OF measurement FOR VALUES FROM ('2006-02-01') TO ('2006-03-01');` — [PostgreSQL 18: Table Partitioning](https://www.postgresql.org/docs/current/ddl-partitioning.html) (n.d.). **MANDATORY**. PostgreSQL 18 adds: "Allow non-btree unique indexes to be used as partition keys and in materialized views". — [PostgreSQL 18 Release Notes](https://www.postgresql.org/docs/18/release-18.html) (2025-09-25). [all]
- Table inheritance "has been replaced by a native feature that handles tuple routing" — don't use it for partitioning. — [PostgreSQL Wiki: Don't Do This](https://wiki.postgresql.org/wiki/Don%27t_Do_This) (2024-11-21). (FK-reference behaviour on partitioned tables was not captured from the fetched page — gap.)

**Cloud warehouse analogues (BigQuery, Snowflake)**
- BigQuery: partitioned tables "improve query performance and control costs by reducing the number of bytes that a query reads"; types: integer range, time-unit column (`DATE`/`TIMESTAMP`/`DATETIME`), ingestion time; "Set a partition expiration time to automatically delete entire partitions after a specified period of time"; choose partitioning when you want to "determine query costs before a query runs"; choose clustering when you need more granularity, filter/aggregate across "multiple columns", or columns have high cardinality. — [BigQuery: Introduction to partitioned tables](https://docs.cloud.google.com/bigquery/docs/partitioned-tables) (n.d.). **RECOMMENDED**. [lakehouse/cloud DW]
- Snowflake: "A clustering key is a subset of columns in a table (or expressions on a table)" that co-locates rows in micro-partitions; natural clustering is automatic and degrades mainly on very large tables with heavy DML; consider a key if "Queries on the table are running slower than expected or have noticeably degraded over time"; target tables "Typically... multiple terabytes (TB) of data"; prioritize columns "most actively used in selective filters", then join predicates; "Snowflake recommends ordering the columns from lowest cardinality to highest cardinality"; keep to 3-4 columns; reduce cardinality via expressions (timestamp -> date); "reclustering consumes credits"; clustering is "generally most cost-effective for tables that are queried frequently and do not change frequently." — [Snowflake: Clustering Keys & Clustered Tables](https://docs.snowflake.com/en/user-guide/tables-clustering-keys) (n.d.). **OPTIONAL/CONTEXTUAL**. [lakehouse/cloud DW]
- Note the ordering inversion: Snowflake clustering keys go lowest-cardinality first (to maximize micro-partition pruning), the opposite of the (rejected) B-tree "most selective first" rule and of MongoDB's "more selective equality = more efficient" remark — because the mechanism (min/max pruning of column chunks) differs from B-tree traversal. [Inference]

**Conflicts / divergences within Q3**
- Partition-size threshold: Oracle "> 2 GB" vs PostgreSQL "exceeds physical memory"; SQL Server gives no size threshold but warns about partition counts.
- Performance framing: Oracle leads with "performance, manageability, and availability" (pruning "100 times faster"); SQL Server and PostgreSQL subordinate performance to manageability and explicitly flag OLTP regressions.
- Time as a key: ideal partition key (Oracle/PostgreSQL/BigQuery) vs explicitly bad distribution/shard key (Citus) and hotspot source (Spanner/CockroachDB, Q4).

### Inferences
- A framework rule: partition for lifecycle/retention and pruning on the dominant filter column; require the partition key in PK/unique constraints (PostgreSQL/SQL Server aligned uniqueness); cap partition counts (hundreds, not thousands); do not partition OLTP tables for point-lookup performance.
- In cloud warehouses, "partition by date + cluster by 1-4 low-to-high cardinality filter columns" replaces B-tree indexing.

## Key Question 4: What do the scale-out sources say about vertical vs horizontal scaling, shard-key selection, cross-shard joins/transactions, rebalancing, read replicas and lag, connection pooling, caching and CQRS?

### Takeaway
Scale-out docs agree on the shard-key triad — high cardinality, even frequency, non-monotonic — and on routing: queries containing the shard key are targeted, others scatter-gather and "do not scale linearly" (MongoDB). Distributed SQL systems (Spanner, CockroachDB) invert single-node PK advice by warning against sequential keys (hotspots) and recommending UUID v4/hash-sharded keys; Citus prescribes tenant_id co-location with the distribution column in every PK/FK; Vitess uses a unique Primary Vindex plus secondary vindexes to avoid scatter. Replication lag is handled by session guarantees (MongoDB causal consistency needs majority read/write concern); PgBouncer transaction pooling is the usual connection-scaling lever with documented feature breakage; cache-aside and CQRS read models trade consistency for read scale.

### Cited Findings

**Vertical vs horizontal scaling**
- "Vertical scaling: A scaling approach that adds compute capacity to existing resources"; "Horizontal scaling: A scaling approach that adds instances of a given type of resource"; vertical "is appropriate for workloads that aren't easily divided into smaller parts or when the application architecture doesn't support horizontal scaling"; horizontal "is appropriate for workloads that can be divided into smaller parts that run independently"; "Every resource has an upper scale limit. If you need to go beyond scale limits, you should partition your workload"; "The stateful parts of a workload, such as databases, are the most common cause of dependency performance issues. Databases require careful design to scale horizontally"; tradeoff: "Vertical scaling might involve higher costs due to the need for larger and more powerful resources. Horizontal scaling offers cost savings by using smaller instances"; partitioning risks: "Data skew" and cross-partition "Query performance". — [Azure Well-Architected: Optimize scaling and partitioning](https://learn.microsoft.com/en-us/azure/well-architected/performance-efficiency/scale-partition) (2023-11-15). **RECOMMENDED**. [all]

**Shard key selection**
- MongoDB: "The shard key is either a single indexed field or multiple fields covered by a compound index that determines the distribution of the collection's documents among the cluster's shards"; "The ideal shard key allows MongoDB to distribute documents evenly throughout the cluster while also facilitating common query patterns"; problems from a poor key: "Jumbo chunks", "Uneven load distribution", "Decreased query performance". — [MongoDB Manual: Shard Keys](https://www.mongodb.com/docs/manual/core/sharding-shard-key/) (n.d.). Criteria: "Where possible, choose a shard key with high cardinality"; "A shard key with high cardinality does not, on its own, guarantee even distribution"; frequency: "If the majority of documents contain only a subset of the possible shard key values, then the chunks storing the documents with those values can become a bottleneck"; monotonic: "If the shard key value is always increasing, all new inserts are routed to the chunk with `maxKey` as the upper bound... The shard containing that chunk becomes the bottleneck for write operations... consider using Hashed Sharding"; routing: "When the queries do not contain the shard key, the queries are broadcast to all shards for evaluation. These types of queries are called scatter-gather queries. Queries that involve multiple shards for each request are less efficient and do not scale linearly when more shards are added" (except large aggregations where scatter-gather parallelism helps); changes: "Starting in MongoDB 5.0, you can change your shard key and redistribute your data using the `reshardCollection` command"; `refineCollectionShardKey` adds suffix fields; 7.0 `analyzeShardKey` gives cardinality/frequency/monotonicity metrics. — [MongoDB Manual: Choose a Shard Key](https://www.mongodb.com/docs/manual/core/sharding-choose-a-shard-key/) (n.d., 9.0). **RECOMMENDED**. [sharded OLTP]
- Citus: "Choosing the distribution column for each table is one of the most important modeling decisions"; multi-tenant: "Partition distributed tables by a common tenant_id column"; "Running a query with all relevant data placed on the same node is called Table Co-Location"; real-time: "Choose a column with high cardinality as the distribution column"; "Choose a column with even distribution"; "Your fact table can have only one distribution key"; "Do not choose a timestamp as the distribution column"; small dimensions become reference tables ("distributing copies of the dimension table to all of the nodes"); cross-shard: "Given that the data is dispersed across different workers, we cannot simply perform a join". — [Citus: Choosing Distribution Column](https://docs.citusdata.com/en/stable/sharding/data_modeling.html) (13.0.1). Multi-tenant schema rules: every table has a column "to clearly mark which tenant owns which rows"; "Citus requires that primary and foreign key constraints include the distribution column" (make keys composite with `company_id`); "Reference tables are replicated across all worker nodes"; single-tenant queries filtering on `company_id` everywhere are "routed to a single node"; large tenants can be isolated via `isolate_tenant_to_new_shard`. — [Citus: Multi-tenant Applications](https://docs.citusdata.com/en/stable/use_cases/multi_tenant.html) (13.0.1). **MANDATORY** (distribution column in PK/FK) / **RECOMMENDED** (tenant_id). [multi-tenant OLTP]
- Vitess: "A keyspace in Vitess can be sharded or unsharded"; shards cover key ranges in left-justified binary ("80-c0"); "A Vindex provides a way to map a column value to a Keyspace ID"; "The Primary Vindex for a table is analogous to a database primary key"; "A Primary Vindex must be unique: given an input value, it must produce a single keyspace ID"; "Secondary Vindexes are additional vindexes against other columns of a table" — without one for a `WHERE` column, "VTGate would have to scatter the query to all shards"; "Functional Unique: The most popular category because it is the one best suited to be a Primary Vindex"; lookup vindexes are "too slow for resharding" as primaries; consistent lookup vindexes avoid 2PC "using locking and transaction sequences"; resharding copies, verifies and keeps new shards current while old shards serve traffic, with only "a few seconds of read-only downtime" at switchover; horizontal (split/merge shards) and vertical (move tables to another keyspace) sharding supported. — [Vitess: Sharding](https://vitess.io/docs/22.0/reference/features/sharding/) and [Vitess: Vindexes](https://vitess.io/docs/22.0/reference/features/vindexes/) (last updated 2026-04-30). **RECOMMENDED**. [sharded MySQL OLTP]

**Hotspots in distributed SQL (Spanner, CockroachDB)**
- Spanner: "A common cause of hotspots is using a key that monotonically increases or decreases, such as a timestamp"; "a monotonic key directs all insert traffic to a single server, creating a bottleneck"; best practice: "Do not choose a column whose value monotonically increases or decreases as the first key part for a high write rate table"; "We recommend using UUID Version 4, because it uses random values in the bit sequence"; "We don't recommend Version 1 UUIDs because they store the timestamp in the high order bits"; alternatives: bit-reverse sequential values, swap key order, hash into a `ShardId` ("set N to be equal to the number of nodes you expect your instance to have"); "it's also a bad idea to create non-interleaved indexes on columns whose values are monotonically increasing or decreasing"; interleaving keeps child rows "adjacent to the parent row"; "a split is a set of rows from one or more related tables that Spanner stores in order of row key." — [Spanner: Schema design best practices](https://docs.cloud.google.com/spanner/docs/schema-design) (n.d.). **RECOMMENDED** (strongly). [distributed OLTP]
- CockroachDB: hotspots "cannot be solved by scaling the cluster size"; index hotspot = writes always at the index tail; causes: `SERIAL`, `TIMESTAMP`, `AUTO_INCREMENT`, `CURRENT_TIMESTAMP()` in secondary indexes, application-generated sequential values; "Indexing on `DESC` with the same insertion pattern can create a hotspot at the index head"; fixes: `UUID` primary keys, hash-sharded indexes ("Data stays ordered within each shard, but writes spread across shard tails"), `unique_rowid()`, sequence caching, prefer CDC over outbox tables; trade-off: hash-sharding improves writes but "to read a subset of the data, the query must scan every shard of the index, which makes range reads more expensive"; row hotspots can't be split ("a single row cannot be split"). — [CockroachDB: Understand Hotspots](https://docs.cockroachlabs.com/docs/stable/understand-hotspots) (n.d.). **RECOMMENDED**. [distributed OLTP]

**Cross-shard joins and transactions**
- MongoDB scatter-gather (above); Citus co-location requirement for joins/FKs/transactions (above); Vitess consistent-lookup vindexes avoid 2PC (above). SQL Server/Oracle partition-wise joins require identical partitioning on the join key (Q3). **MANDATORY** design constraint: co-locate by the join/tenant key or accept scatter.

**Rebalancing**
- MongoDB chunks: "MongoDB attempts to distribute chunks evenly among the shards"; resharding (5.0+) and refining (above). Vitess resharding with seconds of read-only downtime (above). Citus tenant isolation to new shards (above). Azure WAF: "If you address partitioning as an afterthought, it's more challenging because you already have a live workload to maintain. You might need to change data access logic, distribute large quantities of data across partitions, and support continued usage during data distribution." — [Azure Well-Architected: Optimize scaling and partitioning](https://learn.microsoft.com/en-us/azure/well-architected/performance-efficiency/scale-partition) (2023-11-15). **RECOMMENDED** (plan sharding early).

**Read replicas, replication lag, read-your-writes**
- MongoDB: "only read operations with 'majority' read concern and write operations with 'majority' write concern can guarantee all four causal consistency guarantees" (read own writes, monotonic reads, monotonic writes, writes follow reads); with `{ w: 1 }` causal consistency is possible "without data durability (meaning that writes may be rolled back)"; a `"majority"` read "cannot return until the majority commit point has advanced"; in the `"local"`/`{w:1}` scenario a secondary read can return data that "doesn't reflect a state after Read 1". — [MongoDB Manual: Causal Consistency and Read and Write Concerns](https://www.mongodb.com/docs/manual/core/causal-consistency-read-write-concerns/) (n.d.). **MANDATORY** if read-your-writes is required from secondaries. [replicated OLTP]
- Vitess: "A shard typically has one primary for writes and multiple replicas"; sharding "is separate from MySQL replication." — [Vitess: Sharding](https://vitess.io/docs/22.0/reference/features/sharding/).
- CQRS: "The read data store can be a read-only replica of the write store or have a different structure. Deploying multiple read-only replicas can improve performance"; "Eventual consistency... the read data might not show the most recent changes immediately. This delay results in stale data." — [Azure Architecture Center: CQRS pattern](https://learn.microsoft.com/en-us/azure/architecture/patterns/cqrs) (2025-02-20).
- DDIA ch. 5 (Replication) covers replication lag and reading-your-own-writes in the first edition; the chapter text could not be fetched (O'Reilly 403) — see Gaps. [DDIA listed under Q5.]

**Connection pooling**
- PgBouncer: "Lightweight connection pooler for PostgreSQL"; "Low memory requirements (2 kB per connection by default)"; session pooling = "Most polite method", supports all features; transaction pooling "breaks a few session-based features" and "can be used only if the application cooperates by not using non-working features"; features marked "Never" in transaction mode: `SET/RESET`, `LISTEN`, `WITH HOLD` cursors, `PREPARE/DEALLOCATE`, `PRESERVE/DELETE ROWS` temp tables, `LOAD`, session-level advisory locks; protocol-level prepared statements work "only if `max_prepared_statements` is set to a non-zero value"; statement pooling = "Most aggressive method". — [PgBouncer: Features](https://www.pgbouncer.org/features.html) (n.d.; 1.26.1 listed under 2026/10). **RECOMMENDED** transaction pooling with the listed caveats. [OLTP]

**Caching layers**
- Cache-Aside: "Load data on demand into a cache from a data store"; "The Cache-Aside pattern doesn't guarantee consistency between the data store and the cache"; "Caching works best for relatively static data or data that applications read frequently"; invalidate-on-write: "Update the data store *before* removing the item from the cache"; not suitable when "Most requests don't experience a cache hit" or for session state in a web farm; write-through is the alternative when "read-heavy paths need read-after-write freshness". — [Azure Architecture Center: Cache-Aside pattern](https://learn.microsoft.com/en-us/azure/architecture/patterns/cache-aside) (2025-09-11). **OPTIONAL/CONTEXTUAL**. [read-heavy OLTP]

**CQRS read models**
- "Segregate the read and write operations for a data store into separate data models"; benefits: "Independent scaling", "Optimized data schemas. Read operations can use a schema that's optimized for queries. Write operations use a schema that's optimized for updates", "Simpler queries. When you store a materialized view in the read database, the application can avoid complex joins"; costs: "Increased complexity", "Messaging challenges", "Eventual consistency"; use the Transactional Outbox pattern and idempotent consumers; not suitable when "The domain or the business rules are simple" or "A simple CRUD-style user interface and data access operations are sufficient"; with event sourcing, the read model "generates materialized views from these events, typically in a highly denormalized form." — [Azure Architecture Center: CQRS pattern](https://learn.microsoft.com/en-us/azure/architecture/patterns/cqrs) (2025-02-20). **OPTIONAL/CONTEXTUAL**. [read-scaled OLTP]

**Conflicts / divergences within Q4**
- Primary-key monotonicity: single-node engines (SQL Server "Ever-increasing" clustered key; InnoDB auto-increment PK) vs distributed systems (Spanner/CockroachDB: avoid monotonic keys, use UUID v4/hash-sharded). This is the sharpest conflict in the whole corpus and must be resolved by deployment topology (see Q6).
- Hashed vs ranged distribution: MongoDB recommends hashed for monotonic keys but hashing destroys range locality; CockroachDB states the same trade-off for hash-sharded indexes; Citus and Oracle prefer time as a range partition key only inside a node.
- Scatter-gather: MongoDB calls it non-scaling for OLTP but "useful" for large aggregations — the same mechanism is a liability for OLTP and an asset for OLAP.

### Inferences
- Shard-key rule: pick the key that (1) appears in nearly every query/transaction (tenant_id or entity id), (2) has high cardinality and even frequency, (3) is not time-ordered; put it in every PK/FK/unique constraint (Citus) or use secondary vindexes/lookup tables for alternate access paths (Vitess).
- Replication-lag policy: default replica reads to eventual consistency; route read-your-writes paths to the primary or use session/causal guarantees with majority-level durability.

- Vitess shard-size guidance (e.g., target shard size) and 2PC documentation were not on the fetched pages.
- No PostgreSQL/MySQL replica-lag documentation (e.g., hot standby, `synchronous_commit`, semi-sync) was fetched; replication-lag evidence here is MongoDB- and pattern-level only.
- ProxySQL docs were not fetched; connection-pooling evidence is PgBouncer only.

## Key Question 5: What do DDIA, RocksDB, C-Store, Stonebraker and the HTAP vendors say about LSM vs B-tree, row vs column stores, "one size fits all", HTAP and in-memory OLTP, and why OLTP and OLAP schemas differ?

### Takeaway
Stonebraker's two 2005 papers supply the theoretical spine: row stores are "write-optimized" and fit OLTP; warehouses are "read-optimized" and belong in column stores with compression, projections, bitmap indexes and materialized views — and his benchmark shows two orders of magnitude gaps. RocksDB documents the LSM compaction trade-offs (write vs space vs read amplification). Modern vendors operationalize the split with a row engine plus a consistent columnar replica (SQL Server NCCI, TiDB TiFlash) rather than a single structure, and SQL Server's In-Memory OLTP uses lock-free hash/Bw-tree indexes for extreme transactional throughput.

### Cited Findings

**"One size fits all" (ICDE 2005)**
- Thesis: "The last 25 years of commercial DBMS development can be summed up in a single phrase: 'One size fits all'... we argue that this concept is no longer applicable to the database market, and that the commercial world will fracture into a collection of independent database engines, some of which may be unified by a common front-end parser." Traditional model "stores relational tables row-by-row, uses B-trees for indexing, uses a cost-based optimizer, and provides ACID transaction properties." — [Stonebraker & Çetintemel, "One Size Fits All": An Idea Whose Time Has Come and Gone](https://cs.brown.edu/~ugur/fits_all.pdf) (2005). Authority 5 (foundational paper). [all]
- OLTP vs warehouse schemas: "OLTP systems have been optimized for updates, as the main business activity is typically to sell a good or service. In contrast, the main activity in data warehouses is ad-hoc queries, which are often quite complex"; "The standard wisdom in data warehouse schemas is to create a fact table... In addition, the warehouse contains dimension tables... a star schema is the natural result. Such star schemas are omni-present in warehouse environments, but are virtually non-existent in OLTP environments"; field encoding: "it is common practice in OLTP databases to represent the state... as a two-byte character string. In contrast, it is obvious that 50 states can be coded into six bits... This is usually true in warehouses and never true in OLTP"; vendors effectively ship "a warehouse DBMS (bit-map indexes, materialized views, star schemas and optimizer tactics for star schema queries) and an OLTP DBMS (B-tree indexes and a standard cost-based optimizer), which are united by a common parser." — same source. **RECOMMENDED** basis for separate OLTP/OLAP rule sets.
- Stream example: StreamBase ran "160,000 messages per second" vs "900 messages per second" on "a popular commercial relational DBMS" — "two orders of magnitude difference", attributed to "inbound" vs "outbound" processing. — same source. [streaming]

**C-Store (VLDB 2005)**
- "This paper presents the design of a read-optimized relational DBMS that contrasts sharply with most current systems, which are write-optimized"; features: "storage of data by column rather than by row, careful coding and packing of objects into storage... storing an overlapping collection of column-oriented projections, rather than the current fare of tables and indexes... snapshot isolation for read-only transactions, and the extensive use of bitmap indexes to complement B-tree structures." "With this row store architecture, a single disk write suffices to push all of the fields of a single record out to disk. Hence, high performance writes are achieved, and we call a DBMS with a row store architecture a write-optimized system. These are especially effective on OLTP-style applications." "With a column store architecture, a DBMS need only read the values of columns required for processing a given query, and can avoid bringing into memory irrelevant attributes." Architecture: "a small Writeable Store (WS) component" plus a "Read-optimized Store (RS)" connected by a "tuple mover"; K-safety for recovery. Benchmark (simplified TPC-H scale 10, 2.7 GB budget): storage "C-Store 1.987 GB / Row Store 4.480 GB / Column Store 2.650 GB"; query times e.g. Q4 "2.09 / 722.90 / 22.23" s; "C-Store is on average 164 times faster than the commercial row-store and 21 times faster than the commercial column-store in the space-constrained case"; with materialized views the row store needed 11.9 GB and C-Store was still 6.4x faster. — [Stonebraker et al., C-Store: A Column-oriented DBMS](https://www.vldb.org/archives/website/2005/program/paper/thu/p553-stonebraker.pdf) (VLDB 2005). Authority 5. [OLAP/DW]
- Note on authenticity: the benchmark is the authors' own, single-site, read-only ("our performance analysis is limited to read-only queries, and we are not yet in a position to report on updates"). Treat the ratios as directional.

**LSM-tree vs B-tree (RocksDB)**
- "RocksDB started at Facebook as a storage engine for server workloads on various storage media, with the initial focus on fast storage (especially Flash storage)"; "It is a C++ library to store keys and values, which are arbitrarily-sized byte streams"; "The primary design point for RocksDB is that it should be performant for fast storage and for server workloads"; constructs: memtable ("in-memory data structure"), logfile ("sequentially-written file on storage"), sstfiles ("sorted to facilitate easy lookup of keys"); compaction: level-style "typically optimizes disk footprint vs. logical database size (space amplification)", universal-style "typically optimizes total bytes written to disk vs. logical database size (write amplification)" with higher space and read amplification; prefix Bloom filters skip files lacking a prefix. — [RocksDB Overview (wiki)](https://github.com/facebook/rocksdb/wiki/RocksDB-Overview) (edited 2023-07-18). Authority 4. **OPTIONAL/CONTEXTUAL** (engine choice). [write-heavy OLTP / KV]
- DDIA chapter 3 ("Storage and Retrieval") is the standard reference comparing B-trees and LSM-trees and introducing column-oriented storage and "Transaction Processing or Analytics?"; the book site says it helps readers "navigate the diverse and fast-changing landscape of technologies for storing and processing data" and explains "the trade-offs and fundamental limitations that systems face." **HTAP and in-memory OLTP**
- SQL Server: "Beginning with SQL Server 2016 (13.x) SP1, columnstore indexes enable operational analytics: the ability to run performant real-time analytics on a transactional workload"; "A nonclustered columnstore index enables real-time operational analytics where the OLTP workload uses the underlying clustered index while analytics run concurrently on the columnstore index"; "Writing to the highly compressed columnstore is an expensive operation. - TiDB: row-based TiKV for OLTP and columnar TiFlash for OLAP "co-exist, replicate data automatically, and keep strong consistency"; "TiKV does not replicate data to TiFlash automatically" — tables must be chosen; "For the tables with TiFlash replicas, TiDB uses the front-end optimizer to automatically choose the optimal execution plan"; use HTAP when analytics on ">10 million rows" exceed TiKV capability, "especially when indexes are unusable or have low selectivity"; listed scenarios: "Hybrid workload isolation" (a goal, not a guarantee), real-time stream processing, data hub, simplified ETL ("less than 100 TB, concurrency below 10"). — [TiDB: Explore HTAP](https://docs.pingcap.com/tidb/stable/explore-htap/) (n.d., v8.5). Authority 5 (vendor), but marketing-adjacent claims should be benchmarked. [HTAP]
- SQL Server In-Memory OLTP: "For extremely high throughput, consider memory-optimized tables and indexes, which provide a lock and latch-free design"; "all memory-optimized tables must have at least one index"; hash indexes and Bw-tree nonclustered indexes; row versioning: "other sessions might be able to read the older version of the row, and so avoid the performance slowdown associated with a row lock." — [SQL Server Index Design Guide](https://learn.microsoft.com/en-us/sql/relational-databases/sql-server-index-design-guide) (2026-09-14). **OPTIONAL/CONTEXTUAL**. [extreme OLTP]

**Why OLTP and OLAP schemas differ (synthesis of cited statements)**
- OLTP: write-optimized row storage (C-Store intro), B-tree indexes and cost-based optimizer (Stonebraker), "a few narrow rowstore indexes targeted for the most critical queries" (SQL Server), short/ever-increasing clustered keys (SQL Server, InnoDB), virtual views not MVs (Stonebraker), bitmap indexes inappropriate due to locking (Oracle), partitioning rarely helps (SQL Server), global indexes for quick response (Oracle).
- OLAP/DW: star schema with fact/dimension tables (Stonebraker), column storage with 10x compression and batch mode (SQL Server), bitmap indexes on low-cardinality columns (Oracle), materialized views with query rewrite (Oracle), local partitioned indexes for throughput (Oracle), range partitioning on time for rolling windows (Oracle/PostgreSQL), partition + clustering keys instead of B-trees in cloud warehouses (BigQuery, Snowflake), aggressive field encoding (Stonebraker).

### Inferences
- The framework can safely encode "two engines, two rule sets" as a first-class concept and treat HTAP as "row store of record + consistent columnar replica" with explicit write-amplification and freshness caveats, rather than as a single universal structure.
- LSM engines (RocksDB/MyRocks-style) are the storage choice when write throughput and space on flash dominate; B-trees remain the default for read-latency-sensitive OLTP (vendor docs above all assume B+ trees).

### Gaps
- DDIA chapter contents (LSM vs B-tree comparison, replication lag, partitioning by key range vs hash, rebalancing) could not be fetched; only the book site and the 2nd-edition announcement were verified. The report writer should cite DDIA chapter titles cautiously or from the book itself.
- The One Size Fits All PDF text extracted does not itself print the venue (ICDE 2005); venue is from standard citation practice.
- No independent benchmark of HTAP isolation claims (TiDB, SQL Server NCCI) was fetched.

## Key Question 6: Which commonly repeated performance rules are outdated or contested, and what do the sources actually say?

### Takeaway
Six folk rules need qualification: "most selective column first" is rejected by Winand and the practitioners he cites and is absent from vendor guides; "index all FKs" is engine-specific (InnoDB automatic, PostgreSQL/Oracle recommended-not-automatic); "never SELECT *" has no vendor mandate but strong indirect support; "denormalize for performance" belongs to warehouses/read models, not OLTP schemas; "UUIDs are fine as PKs" is wrong on single-node clustered engines but recommended (v4) on Spanner/CockroachDB, with time-ordered UUIDv7 (PostgreSQL 18) as a compromise; "partition for performance" is contradicted for OLTP by SQL Server and qualified by PostgreSQL; and "NoSQL for scale" is undercut by the distributed-SQL and sharded-SQL systems documented here.

### Cited Findings

**"Always put the most selective column first" — CONTESTED/OUTDATED**
- Winand: "that is just wrong"; selectivity matters only for "independent range conditions"; cites Jonathan Lewis (2007) that the rule "was never a sensible rule of thumb (except, possibly, prior to version 6.0)" and Gail Shaw (2009): "It's useless to have the most selective column of the index on the left if very few queries filter on it." — [Use The Index, Luke: Myth – Most Selective First](https://use-the-index-luke.com/sql/myth-directory/most-selective-first) (n.d.). Vendor guidance instead: equality-leading prefix mechanics — [PostgreSQL 18: Multicolumn Indexes](https://www.postgresql.org/docs/current/indexes-multicolumn.html); leftmost prefix — [MySQL 8.4: Multiple-Column Indexes](https://dev.mysql.com/doc/refman/8.4/en/multiple-column-indexes.html); ESR with ERS when "range predicate... is very selective" — [MongoDB ESR Guideline](https://www.mongodb.com/docs/manual/tutorial/equality-sort-range-guideline/). Residual truth: statistics on first column (SQL Server histogram, per Winand) and Snowflake's inverted "lowest cardinality first" for clustering keys — [Snowflake: Clustering Keys](https://docs.snowflake.com/en/user-guide/tables-clustering-keys). **Label: replace with "equality-first, usage-driven; selectivity only among range columns" (RECOMMENDED).** [all]

**"Index all foreign keys" — ENGINE-DEPENDENT**
- InnoDB auto-creates (and may silently drop) FK indexes — [MySQL 8.4: FOREIGN KEY Constraints](https://dev.mysql.com/doc/refman/8.4/en/create-table-foreign-keys.html). PostgreSQL: "it is often a good idea to index the referencing columns too. Because this is not always needed... the declaration of a foreign key constraint does not automatically create an index" — [PostgreSQL 18: Constraints](https://www.postgresql.org/docs/current/ddl-constraints.html). Oracle: index FK columns to "avoid a full table lock" on parent updates/deletes — [Oracle Concepts: Indexes](https://docs.oracle.com/en/database/oracle/oracle-database/23/cncpt/indexes-and-index-organized-tables.html). **Label: RECOMMENDED default on PostgreSQL/Oracle for FKs used in joins or whose parents see deletes/updates; MANDATORY (automatic) on InnoDB; exempt rarely-joined, append-only children.** [OLTP]

**"Never use SELECT *" — NO VENDOR MANDATE, STRONG INDIRECT SUPPORT**
- Indexed views forbid `SELECT *` ("Explicitly name columns") — [SQL Server: Create Indexed Views](https://learn.microsoft.com/en-us/sql/relational-databases/views/create-indexed-views) (2025-01-14); index-only scans need "The query must reference only columns stored in the index" — [PostgreSQL 18: Index-Only Scans](https://www.postgresql.org/docs/current/indexes-index-only-scans.html); columnstore speed depends on "Queries often select only a few columns" — [SQL Server: Columnstore indexes overview](https://learn.microsoft.com/en-us/sql/relational-databases/indexes/columnstore-indexes-overview). **Label: RECOMMENDED (project needed columns) rather than MANDATORY; the benefit is largest for covering indexes and columnar stores.** [all]

**"Denormalize for performance" — CORRECT FOR OLAP/READ MODELS, NOT A DEFAULT FOR OLTP**
- Star schemas "are omni-present in warehouse environments, but are virtually non-existent in OLTP environments"; MVs "useful... in warehouse worlds, but never in OLTP worlds" — ["One Size Fits All"](https://cs.brown.edu/~ugur/fits_all.pdf) (2005). CQRS: read model "typically in a highly denormalized form" with "Eventual consistency" and "Increased complexity"; not for simple CRUD — [Azure Architecture Center: CQRS pattern](https://learn.microsoft.com/en-us/azure/architecture/patterns/cqrs) (2025-02-20). SQL Server indexed views: DML "can degrade significantly" — [SQL Server: Create Indexed Views](https://learn.microsoft.com/en-us/sql/relational-databases/views/create-indexed-views). **Label: OPTIONAL/CONTEXTUAL — denormalize in the warehouse/read model (materialized views, star schema), keep the OLTP system of record normalized; where OLTP analytics are needed, prefer a columnar replica (SQL Server NCCI / TiFlash) over schema denormalization.** [OLTP vs OLAP]

**"UUIDs are fine as primary keys" — TOPOLOGY-DEPENDENT CONFLICT**
- Against (single-node clustered engines): a **uniqueidentifier** clustered key "is wider because it uses 16 bytes of storage instead of 4 bytes for **int** and 8 bytes for **bigint**, and doesn't satisfy the **ever-increasing** property unless the values are generated sequentially" — [SQL Server Index Design Guide](https://learn.microsoft.com/en-us/sql/relational-databases/sql-server-index-design-guide) (2026-09-14); "If the primary key is long, the secondary indexes use more space, so it is advantageous to have a short primary key" — [MySQL 8.4: Clustered and Secondary Indexes](https://dev.mysql.com/doc/refman/8.4/en/innodb-index-types.html).
- For (distributed systems): "We recommend using UUID Version 4" and avoid v1 — [Spanner: Schema design](https://docs.cloud.google.com/spanner/docs/schema-design); "Use `UUID` primary keys so inserts spread across the keyspace" — [CockroachDB: Understand Hotspots](https://docs.cockroachlabs.com/docs/stable/understand-hotspots).
- Middle ground: PostgreSQL 18 "Add UUID version 7 generation function `uuidv7()`... This `UUID` value is temporally sortable" — [PostgreSQL 18 Release Notes](https://www.postgresql.org/docs/18/release-18.html) (2025-09-25); "Generates a version 7 (time-ordered) UUID" — [PostgreSQL 18: UUID Functions](https://www.postgresql.org/docs/current/functions-uuid.html). Note that time-ordered UUIDs re-introduce the monotonic pattern Spanner/CockroachDB warn about.
- **Label: CONTEXTUAL — single-node B-tree-clustered OLTP: prefer narrow sequential integer/bigint (or UUIDv7 if global uniqueness is needed); range-sharded distributed SQL: prefer random UUID v4 or hash-sharded keys; never apply one rule to both.** [OLTP]

**"Partition for performance" — CONTESTED (manageability is the primary benefit)**
- "Partitioning rarely improves performance in OLTP systems"; non-pruned queries "could take longer to execute as the number of partitions increases" — [SQL Server: Partitioned Tables and Indexes](https://learn.microsoft.com/en-us/sql/relational-databases/partitions/partitioned-tables-and-indexes) (2025-12-29). PostgreSQL: benefits "normally be worthwhile only when a table would otherwise be very large"; "Never just assume that more partitions are better" — [PostgreSQL 18: Table Partitioning](https://www.postgresql.org/docs/current/ddl-partitioning.html). Oracle leads with performance (pruning "100 times faster") but also "Tables that are greater than 2 GB. These tables should always be considered as candidates" — [Oracle VLDB Guide](https://docs.oracle.com/en/database/oracle/oracle-database/23/vldbg/partition-concepts.html). Partial indexes are not a substitute: "This is a bad idea!" — [PostgreSQL 18: Partial Indexes](https://www.postgresql.org/docs/current/indexes-partial.html). **Label: RECOMMENDED for retention/maintenance/pruning on very large tables; NOT RECOMMENDED as an OLTP point-query optimization. Oracle's 2 GB threshold is dated relative to PostgreSQL's "exceeds RAM" rule.** [all]

**"NoSQL for scale" — UNDERCUT BY DOCUMENTED SQL SCALE-OUT**
- Sharded/distributed SQL systems document horizontal scaling with SQL semantics: Vitess "Sharding horizontally partitions a database across two or more servers" for MySQL — [Vitess: Sharding](https://vitess.io/docs/22.0/reference/features/sharding/) (2026-04-30); Citus distributes PostgreSQL tables by tenant/entity id with co-located joins and FKs — [Citus: Multi-tenant Applications](https://docs.citusdata.com/en/stable/use_cases/multi_tenant.html); Spanner/CockroachDB design docs address hotspot-free key design at scale — [Spanner: Schema design](https://docs.cloud.google.com/spanner/docs/schema-design), [CockroachDB: Understand Hotspots](https://docs.cockroachlabs.com/docs/stable/understand-hotspots). MongoDB itself states scatter-gather queries "do not scale linearly when more shards are added" — [MongoDB: Choose a Shard Key](https://www.mongodb.com/docs/manual/core/sharding-choose-a-shard-key/). Stonebraker's argument is for specialized engines per workload, not for abandoning SQL — ["One Size Fits All"](https://cs.brown.edu/~ugur/fits_all.pdf). **Label: CONTESTED — scale comes from shard-key/co-location design and workload-specialized engines, not from the data model label.** [all]

**Other dated items**
- PostgreSQL wiki hints discussion is from 2015 — [PostgreSQL Wiki: OptimizerHintsDiscussion](https://wiki.postgresql.org/wiki/OptimizerHintsDiscussion) (2015-07-05); RocksDB overview last edited 2023 — [RocksDB Overview](https://github.com/facebook/rocksdb/wiki/RocksDB-Overview) (2023-07-18); C-Store benchmark is 2005 hardware ("3.0 Ghz Pentium... 2 Gbytes of memory") — [C-Store](https://www.vldb.org/archives/website/2005/program/paper/thu/p553-stonebraker.pdf). PostgreSQL 18 skip scan weakens the strict "leading column must be constrained" rule — [PostgreSQL 18 Release Notes](https://www.postgresql.org/docs/18/release-18.html).

### Inferences
- The framework should express each contested rule as a conditional keyed on engine (PostgreSQL/InnoDB/SQL Server/Oracle), topology (single-node vs range-sharded), and workload (OLTP/OLAP/HTAP), with the source reasoning attached, rather than as absolute do/don't rules.

### Gaps
- No fetched source directly benchmarks UUIDv7 vs bigint vs UUIDv4 on B-tree engines; the conflict is reconstructed from vendor design statements.
- No fetched source quantifies "denormalization in OLTP" costs; the position rests on Stonebraker's categorical statements and CQRS trade-off documentation.
