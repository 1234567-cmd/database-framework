# Lakehouse and Cloud Data Warehouse Platform Guidance on Schema Design (Databricks, Snowflake, dbt)

Scope label: everything below is OLAP / data-warehouse / lakehouse / transformation-layer guidance. None of it is OLTP guidance unless explicitly marked (the only OLTP-flavoured items are Snowflake hybrid tables and the note that Databricks Delta is not an OLTP store). All URLs were opened on 2026-11-07; "Last updated" dates are the dates printed on the page, otherwise "n.d." (Snowflake docs print only a 2026 copyright). Label key: **MANDATORY** = platform-enforced or vendor says must/required; **RECOMMENDED** = vendor says "recommends"/"best practice"; **OPTIONAL/CONTEXTUAL** = vendor presents as a choice that depends on workload.

## Q1. Databricks: what medallion architecture is (and is not), and how Bronze/Silver/Gold are defined

### Takeaway
Databricks defines medallion as a *data design pattern for organizing data by quality level*, "a recommended best practice but not a requirement" — it is a layering/quality approach, not a data model; Databricks' own blogs then map classic models onto the layers (3NF/Data Vault in Silver, Kimball star schemas in Gold).

### Cited Findings
- Definition: medallion is "a series of data layers that denote the quality of data stored in the lakehouse" and "a data design pattern used to organize data logically"; also "sometimes also referred to as multi-hop architectures". Status: "Following the medallion architecture is a recommended best practice but not a requirement." (RECOMMENDED, lakehouse) — [Medallion lakehouse architecture (Databricks docs, last updated Oct 29, 2026)](https://docs.databricks.com/aws/en/lakehouse/medallion)
- The doc page does **not** say "medallion is not a data model" in those words; it frames it purely as a quality-layering pattern and never names Kimball, star schema, or Data Vault. The only modeling statement is that Gold data is modeled "using a dimensional model" by defining relationships and measures; Silver modeling choices listed are "VARIANT type, JSON strings, structs/maps/arrays, and flattening or normalizing into multiple tables". — [Medallion lakehouse architecture](https://docs.databricks.com/aws/en/lakehouse/medallion)
- Bronze (raw): raw, unvalidated data in original format, appended incrementally; "source of truth" enabling reprocessing/audit; "not for access by analysts and data scientists"; minimal validation; Databricks **recommends storing most fields as string, VARIANT, or binary** to guard against schema changes; sources include object storage, Kafka/Kinesis, Lakehouse Federation. (RECOMMENDED) — [Medallion lakehouse architecture](https://docs.databricks.com/aws/en/lakehouse/medallion)
- Silver (validated): cleaning, validation, deduplication, normalization, enrichment; operations listed: "schema enforcement, null handling, deduplication, late/out-of-order data handling, data quality checks, schema evolution, type casting, and joins"; "Databricks does not recommend writing to silver tables directly from ingestion"; reads from bronze should generally be streaming; "Should contain at least one validated, non-aggregated representation of each record." (RECOMMENDED) — [Medallion lakehouse architecture](https://docs.databricks.com/aws/en/lakehouse/medallion)
- Gold (enriched): "refined, aggregated, business-aligned datasets for analytics, dashboards, ML, and operational use"; often filtered by time/region, historical bulk stays in Silver; optimized for query/dashboard performance; multiple gold layers per domain (HR, finance, IT) are acceptable; example is a materialized view `weekly_bookings`. (RECOMMENDED) — [Medallion lakehouse architecture](https://docs.databricks.com/aws/en/lakehouse/medallion)
- The page claims "This architecture guarantees atomicity, consistency, isolation, and durability" as data passes through layers, and gives a cost/latency table: continuous incremental (higher cost, lower latency), triggered incremental (lower cost, higher latency), batch (lowest cost, highest latency). — [Medallion lakehouse architecture](https://docs.databricks.com/aws/en/lakehouse/medallion)
- Model-to-layer mapping (official blog, 2022): Bronze = source structures "as-is" plus metadata; Silver = "matched, merged, conformed, and cleaned" data using "just-enough" ELT with "3rd-Normal Form like data models" or Data Vault ("typically fits well in the Silver layer"); Gold = "denormalized, read-optimized" Kimball star schemas or Inmon-style marts; star schemas are "pretty much the gold standard for the presentation layer"; the lakehouse "can support many different data modeling styles"; Gold tables may be "completely denormalized" for data-science feature engineering. (RECOMMENDED) — [Data Warehousing Modeling Techniques and Their Implementation on the Databricks Lakehouse Platform (Bhatt & Sekar, Databricks blog, June 24, 2022)](https://www.databricks.com/blog/2022/06/24/data-warehousing-modeling-techniques-and-their-implementation-on-the-databricks-lakehouse-platform.html)
- Myth #7 "Medallion architecture is required" — rebuttal: "Medallion is a guideline, not a rigid requirement", a "reference architecture, not a mandatory structure"; layers can be added or removed; adapt to company size, regulation, usage, team structure. (OPTIONAL/CONTEXTUAL) — [Databricks Lakehouse Data Modeling: Myths, Truths, and Best Practices (Barrow & Hale, Databricks blog, Dec 15, 2025)](https://www.databricks.com/blog/databricks-lakehouse-data-modeling-myths-truths-and-best-practices)
- Unity Catalog organization: catalogs are "the primary unit of data isolation"; "Organize data and AI objects into catalogs and schemas that reflect organizational divisions and projects"; catalogs typically map to environment, team or business unit; one metastore per region; grant production catalogs/schemas to groups not users; "Databricks recommends managed tables and volumes" for all new tables and eventually migrating external tables. The best-practices page does **not** prescribe bronze/silver/gold as catalogs vs schemas (the medallion page example uses `ops.bronze`, `ops.silver`, `ops.gold` schemas). (RECOMMENDED) — [Unity Catalog best practices (Databricks docs, last updated Oct 30, 2026)](https://docs.databricks.com/aws/en/data-governance/unity-catalog/best-practices); [Medallion lakehouse architecture](https://docs.databricks.com/aws/en/lakehouse/medallion)

### Inferences
- Medallion is orthogonal to Kimball/Inmon/Data Vault: a schema-design framework should treat it as a pipeline-quality topology and plug a data model into each layer (3NF/DV in Silver, star/OBT in Gold), exactly as the 2022 Databricks blog does.
- Bronze's "store as string/VARIANT" recommendation is deliberately schema-on-read at ingestion, which contradicts classic warehouse schema-on-write at the staging boundary; schema-on-write is deferred to Silver via Delta schema enforcement and constraints.

### Gaps
- No official Databricks doc page explicitly states whether bronze/silver/gold should be separate catalogs or separate schemas; only an example (`ops.bronze` schema naming) exists.
- The medallion page's "guarantees ACID" claim is about Delta transactions per table, not cross-layer atomicity; the docs do not qualify this and I found no clarification.

## Q2. Databricks / Delta Lake: ACID, schema enforcement vs evolution, time travel, liquid clustering vs partitioning, constraints (NOT NULL, CHECK, PK/FK informational)

### Takeaway
Delta Lake gives single-table ACID with serializable writes and snapshot-isolated reads via an object-store transaction log; schema enforcement on write is the default and evolution must be opted into per write; NOT NULL and CHECK are enforced, while PK/FK/UNIQUE are informational only; Databricks now says liquid clustering "replaces table partitioning and ZORDER" and recommends it "for all new tables".

### Cited Findings
**ACID / transaction model (foundational papers)**
- Problem statement: on object stores "multi-object updates are not atomic, there is no isolation between queries"; "Rolling back writes is also difficult: if an update query crashes, the table is in a corrupted state"; metadata ops on millions of objects are expensive. — [Delta Lake: High-Performance ACID Table Storage over Cloud Object Stores (Armbrust et al., PVLDB 13(12), 2020, official PDF)](https://www.vldb.org/pvldb/vol13/p3411-armbrust.pdf)
- Design: "we maintain information about which objects are part of a Delta table in an ACID manner, using a write-ahead log that is itself stored in the cloud object store"; objects are Parquet; transactions use "optimistic concurrency protocols against the object store"; "no servers need to be running to maintain state for a Delta table". — [Delta Lake paper](https://www.vldb.org/pvldb/vol13/p3411-armbrust.pdf)
- Isolation: "all transactions that perform writes are serializable"; reads "achieve snapshot isolation" (serializable reads possible via a dummy write); "Delta Lake currently only supports transactions within one table" (MANDATORY platform constraint at paper time). Write rate "limited to several transactions per second" by object-store put-if-absent latency. — [Delta Lake paper](https://www.vldb.org/pvldb/vol13/p3411-armbrust.pdf)
- Features enabled by the log: time travel ("SQL AS OF timestamp and VERSION AS OF commit_id"), "UPSERT, DELETE and MERGE operations" for GDPR deletes and late/erroneous records, exactly-once streaming writes, Z-order layout, caching, audit logging. Schema enforcement: "Delta clients ensure that newly written data follows the table's schema. These simple checks have caught many user errors appending data with the wrong schema". Data Warehousing/BI use case: "most Delta Lake users also run ad-hoc query and BI workloads against their lakehouse datasets". — [Delta Lake paper](https://www.vldb.org/pvldb/vol13/p3411-armbrust.pdf)
- Lakehouse definition: "We define a Lakehouse as a data management system based on low-cost and directly-accessible storage that also provides traditional analytical DBMS management and performance features such as ACID transactions, data versioning, auditing, indexing, caching, and query optimization." Problems of two-tier lake+warehouse: Reliability, Data staleness, Limited support for advanced analytics, Total cost of ownership; "data may be stored with different schemas in the lake and the warehouse (e.g., denormalized in one)". Metadata layers are "a natural place to implement data quality enforcement features. For example, Delta Lake implements schema enforcement ... and constraints API that allows table owners to set constraints on the ingested data (e.g., country can only be one of a list of values)" and "a natural place to implement governance features such as access control and audit logging". Caveat: "Lakehouses' support for direct access means that they give up some aspects of data independence, which has been a cornerstone of relational DBMS design." — [Lakehouse: A New Generation of Open Platforms that Unify Data Warehousing and Advanced Analytics (Armbrust, Ghodsi, Xin, Zaharia, CIDR 2021, official PDF)](https://www.cidrdb.org/cidr2021/papers/cidr2021_paper17.pdf)
- 2025 update: Myth #1 "Databricks doesn't support relational modeling" rebutted with ACID, schema enforcement, SQL on Delta: "Relational principles are fundamental to the Lakehouse"; bonus myth: multi-statement transactions "(Private Preview at the time) provide multi-table atomicity and rollback across Delta and Iceberg tables". — [Myths, Truths, and Best Practices (Dec 15, 2025)](https://www.databricks.com/blog/databricks-lakehouse-data-modeling-myths-truths-and-best-practices)

**Schema enforcement vs evolution**
- Open-source Delta docs (schema validation on write): "If there are columns in the DataFrame not present in the table, an exception is raised"; columns present in table but missing from DataFrame are set to null; types "If they don't match, an exception is raised"; "DataFrame column names cannot differ only by case" (Delta is "case-preserving but insensitive when storing the schema"). (MANDATORY default behaviour) — [Table batch reads and writes — Delta Lake docs (delta.io, n.d.)](https://docs.delta.io/latest/delta-batch.html)
- Evolution must be opted in: `INSERT WITH SCHEMA EVOLUTION` (DBR 18.1+), `MERGE WITH SCHEMA EVOLUTION` (DBR 15.4+), `mergeSchema` write option, or legacy session config `spark.databricks.delta.schema.autoMerge.enabled` — "Databricks doesn't recommend this approach for production"; per-operation settings take precedence. New columns "are added to the end of the table schema"; existing rows get NULL; "By default, nullability is true" for ADD COLUMNS; "By default, overwriting the data in a table doesn't overwrite the schema" (`overwriteSchema` replaces schema and partitioning); "Schema updates conflict with all concurrent write operations"; schema changes terminate streams reading the table; rename/drop column require column mapping, and dropping "does not delete its data from files" (REORG + VACUUM needed). (RECOMMENDED: per-write evolution; NOT RECOMMENDED: session-wide autoMerge) — [Update Delta Lake table schema (Databricks docs, last updated Sep 11, 2026)](https://docs.databricks.com/aws/en/delta/update-schema); delta.io agrees: "Enabling schema evolution session-wide is not recommended" — [delta.io batch docs](https://docs.delta.io/latest/delta-batch.html)

**Constraints**
- "Primary key, foreign key, and unique constraints are informational only and aren't enforced." NOT NULL and CHECK are enforced: "When a constraint is violated, the transaction fails with an error." Existing rows are verified when a constraint is added. CHECK expressions may use deterministic Spark SQL functions only (no UDFs, aggregates, windows). PK/FK are "available for Unity Catalog and Delta Lake tables" (GA DBR 15.2+); UNIQUE is Public Preview (DBR 18.2+), NULLs treated as distinct; FK must reference a PK or UNIQUE in another table; "CTAS statements don't support the constraint clause". Nested struct columns can carry NOT NULL only if the parent struct is NOT NULL; "Columns nested within array or map types don't accept NOT NULL constraints." Adding a constraint upgrades the writer protocol (may affect external Delta clients). (MANDATORY semantics as stated) — [Constraints on Databricks (Databricks docs, last updated Oct 29, 2026)](https://docs.databricks.com/aws/en/tables/constraints)
- Blog corroboration: "Databricks does not support enforcement of the PK/FK relationship" but they "help analysts identify join relationships"; "Databricks supports NOT NULL and column value check constraints". — [Data Modeling Best Practices & Implementation on a Modern Lakehouse (Mao, Dey, Breese, Bhatt, Oct 20, 2022)](https://www.databricks.com/en/blog/data-modeling-best-practices-implementation-modern-lakehouse); Myth #2: PK/FK "are for query performance, but are not enforced", with `RELY` as an optimizer hint and BI-tool compatibility — [Myths (Dec 15, 2025)](https://www.databricks.com/blog/databricks-lakehouse-data-modeling-myths-truths-and-best-practices)
- The constraints doc page itself does not mention `RELY` (the 2025 blog does); I could not verify RELY semantics on Databricks from a docs page (see Gaps).

**Time travel / history**
- `DESCRIBE HISTORY`, `TIMESTAMP AS OF`, `VERSION AS OF`, `RESTORE`; history retention via `logRetentionDuration` "30 days by default"; time-travel data retention via `deletedFileRetentionDuration` default 7 days; "in Databricks Runtime 18.0 and above, time travel queries to versions older than that threshold are blocked" and `logRetentionDuration` must be ≥ `deletedFileRetentionDuration`; "Data files are deleted when VACUUM runs"; "Don't use table history as a long-term backup solution for data archival" (RECOMMENDED); raising retention "can cause your storage costs to go up"; RESTORE is a data-changing operation that can duplicate rows for streaming consumers. — [Work with Delta Lake table history (Databricks docs, last updated Nov 6, 2026)](https://docs.databricks.com/aws/en/delta/history); delta.io: "By default you can time travel to a Delta table up to 30 days old" and "data files are deleted only when you run VACUUM" — [delta.io batch docs](https://docs.delta.io/latest/delta-batch.html)

**Liquid clustering vs partitioning vs Z-ORDER**
- "Liquid clustering is a data layout optimization technique that replaces table partitioning and ZORDER"; "Databricks recommends liquid clustering for all new tables, including streaming tables and materialized views" (RECOMMENDED); "Clustering is not compatible with partitioning or ZORDER"; "Clustering columns are flexible and simple to alter, whereas partitioning is rigid and difficult to alter"; up to four clustering keys; keys need statistics (first 32 columns by default); best for high-cardinality filters, skew, fast-growing tables, concurrent writes, changing access patterns, partitions returning too many/few results; `CLUSTER BY AUTO` picks keys from query history (needs predictive optimization, UC managed tables); migration via `REPLACE PARTITIONED BY WITH CLUSTER BY` (DBR 18.1+); hierarchical clustering (DBR 17.1+) for low-cardinality priority keys; `OPTIMIZE` is incremental and should run regularly (tables with frequent updates "every one to two hours"); clustered tables require writer v7/reader v3 protocol. — [Use liquid clustering for tables (Databricks docs, last updated Nov 2, 2026)](https://docs.databricks.com/aws/en/delta/clustering)
- Older (2022) blog guidance — now superseded by the docs above: partition "sparingly", "only when you have many Terabytes of compressed data"; partitioning by date/month is "almost a bad practice" because OPTIMIZE + Z-order prune better; "Use Z-order on your Primary Keys and foreign keys that are used for the most frequent joins"; Bloom filter indexes for selective columns; `ANALYZE TABLE` for statistics; enable auto optimize / auto compaction. — [Data Modeling Best Practices & Implementation on a Modern Lakehouse (Oct 20, 2022)](https://www.databricks.com/en/blog/data-modeling-best-practices-implementation-modern-lakehouse). CONFLICT (temporal): the 2022 blog recommends Z-order on keys; the 2026 docs say liquid clustering replaces ZORDER and is incompatible with it; the 2025 myths blog already says apply liquid clustering "to frequently joined columns". Treat Z-order advice as legacy.

### Inferences
- For a schema framework "assuming integrity enforcement": on Databricks only NOT NULL and CHECK are trustworthy guards; PK uniqueness and FK referential integrity must be enforced by pipeline logic (MERGE keys, dedup in Silver, dbt `unique`/`relationships` tests) — the platform will silently accept duplicates and orphans.
- Physical design shifts from "choose partition columns at create time" to "choose (mutable) clustering keys"; a framework should model clustering keys as a changeable property, not a schema-fixing decision.

### Gaps
- `RELY` on Databricks: the 2025 blog mentions it, but the constraints docs page I fetched does not; exact Databricks RELY semantics (join elimination) not verified from docs.
- Multi-statement (cross-table) transactions on Databricks were "Private Preview" in Dec 2025; current GA status not verified.

## Q3. Databricks / Unity Catalog governance: lineage, row filters, column masks, ABAC, and dimensional modeling / SCD2 / Data Vault on the lakehouse

### Takeaway
Unity Catalog supplies the governance layer the Lakehouse paper predicted (access control, audit, automatic lineage, row filters and column masks as SQL UDF policies, tag-based ABAC), and Databricks' official blogs state that star/snowflake schemas, SCD Type 2 and Data Vault all run on Delta — star schemas in Gold, Data Vault in Silver, surrogate keys via IDENTITY columns, SCD2 via `APPLY CHANGES INTO` or time travel.

### Cited Findings
**Unity Catalog**
- UC "operates beneath every data and AI interaction in your workspaces automatically"; enabled by default for workspaces created after Nov 8, 2023; features: access control ("privileges, attribute-based policies, row and column filters, and workspace bindings"), audit log system table, lineage ("automatic tracking of how data and AI assets connect, from source data to models, services, and dashboards"), Catalog Explorer discovery, automatic data classification/tagging, data quality monitoring, OpenSharing; "Every asset you govern in Unity Catalog is modeled as a securable object"; three-level namespace `catalog.schema.object`; managed vs external tables ("Unity Catalog handles both governance and the underlying file storage lifecycle" for managed). — [What is Unity Catalog? (Databricks docs, last updated Sep 11, 2026)](https://docs.databricks.com/aws/en/data-governance/unity-catalog/)
- Privileges "are inherited downward" through the securable hierarchy; lineage graphs "do not cross region or platform boundaries". — [Unity Catalog best practices (Oct 30, 2026)](https://docs.databricks.com/aws/en/data-governance/unity-catalog/best-practices)
- Row filters / column masks: "restrict the rows and column values a user can see at query time"; a row filter is a SQL UDF where "Rows where the function returns FALSE are excluded"; a column mask is a SQL UDF returning the original or masked value, "Each column can have one mask"; bound via `ALTER TABLE ... SET ROW FILTER` / `ALTER COLUMN ... SET MASK`; "You cannot apply row filters or column masks to a view"; Databricks recommends ABAC (tag-based) policies for many tables — attached at catalog/schema, applied by governed tags, table owners "can't override or remove them"; recommends ANSI mode so failed casts in policy UDFs raise errors rather than silently NULL (the page shows a worked bug where an INT-typed filter on a STRING column returned all rows); limitations: no time travel with table-level policies, no deep/shallow clone, no path-based access, DBR ≥ 12.2. (RECOMMENDED: ABAC + ANSI mode; MANDATORY: limitations) — [Row filters and column masks (Databricks docs, last updated Nov 6, 2026)](https://docs.databricks.com/aws/en/tables/row-and-column-filters)

**Dimensional modeling / SCD2 on Databricks**
- "Dimensional modeling is one of the most popular data modeling techniques for building a modern data warehouse"; "dimension tables typically are highly denormalized with flattened many-to-one relationships"; conformed dimensions "when attributes in different dimension tables have the same column names"; "Identity columns are a form of surrogate keys"; CHECK constraints so you "never worry about data quality or data correctness issues sneaking up on you" (example `valid_product_id` on fact_sale — note this is a CHECK, not an enforced FK); "One can easily perform SCD type 1 or SCD type 2 using Delta Live Tables using APPLY CHANGES INTO" (worked example closes a store row on Jan 07 2022 and opens a new one with NULL end date); pipeline spans bronze/silver/gold. (RECOMMENDED) — [Loading a Data Warehouse Data Model in Real Time with the Databricks Lakehouse (Mao, Bhatt, Dey, Nov 7, 2022)](https://www.databricks.com/blog/2022/11/07/load-edw-dimensional-model-real-time-databricks-lakehouse.html)
- Myth #5 "You shouldn't build dimensional models in Databricks" — star and snowflake schemas "translate exceptionally well to Delta tables"; SCDs "easy to implement with Delta time travel"; best practices: define PK/FK for documentation and optimization, identity columns for surrogate keys, materialized views for pre-aggregated facts, liquid clustering on join columns, organize dimensional models with `catalog.schema.table`; Myth #4: UC Metric Views (Public Preview) give tool-agnostic semantic modeling. — [Myths (Dec 15, 2025)](https://www.databricks.com/blog/databricks-lakehouse-data-modeling-myths-truths-and-best-practices)

**Data Vault on Databricks**
- Hubs ("core business entities"), Links ("represent the relationship between Hub entities", compared to factless fact tables), Satellites (descriptive attributes); Raw Vault: "Additional 'business' ETL rules are not typically applied while loading the Raw Data Vault"; Business Vault applies business/DQ/conforming rules; landing/staging "naturally fit the Bronze layer"; PIT tables "will bolster query performance", Bridge tables pre-join hubs; recommends "a hash of business keys as the primary keys" (MD5/SHA functions); identity columns can convert hub natural keys to surrogate keys for Gold dims; OPTIMIZE/Z-order on join keys; avoid over-partitioning small satellites; Bloom filters on date/current-flag columns; lower `optimize.maxFileSize` to 32–64 MB from 1 GB default; rely on AQE for many-join DV queries. (RECOMMENDED, contextual to DV) — [Prescriptive Guidance for Implementing a Data Vault Model on the Databricks Lakehouse Platform (Bhatt, Shaikh, Wiebe, June 24, 2022)](https://www.databricks.com/blog/2022/06/24/prescriptive-guidance-for-implementing-a-data-vault-model-on-the-databricks-lakehouse-platform.html)
- CONFLICT (keys): Databricks DV blog recommends hash-of-business-key PKs; Snowflake's performance guide says for Data Vault 2.0 use "numeric surrogate keys rather than hash keys such as MD5" because "Snowflake only considers the first five bytes for clustering" of VARCHAR and random hashes prevent co-location (see Q5); the Snowflake DV blog says hash joins are slower than integer/BK joins but still "very fast" and may need "a larger size virtual warehouse" — [Tips for Optimizing the Data Vault Architecture on Snowflake (Graziano & Hoyle, Feb 3, 2020)](https://www.snowflake.com/en/blog/tips-for-optimizing-the-data-vault-architecture-on-snowflake/).

### Inferences
- Databricks' integrity story for dimensional models is: IDENTITY surrogate keys + informational PK/FK (for BI tools and optimizer) + enforced NOT NULL/CHECK + MERGE/APPLY CHANGES for SCD2. The CHECK-based "valid_product_id" example shows CHECK is used as a stand-in for an FK where the check can be expressed on the row itself; true referential integrity still needs pipeline tests.
- Policy UDF type coercion is a real schema-design risk: column data types of filtered/masked columns must match policy parameter types exactly, or ANSI mode must be on.

### Gaps
- No Databricks docs page (as opposed to blog) prescribes a dimensional/DV layering; the mapping of models to layers is blog-level guidance (authority 4), not product docs.
- UC Metric Views and multi-statement transactions were preview features in Dec 2025; current status not verified.

## Q4. Snowflake: physical storage (micro-partitions, clustering keys), data types (NUMBER(38,0), VARIANT), constraints (enforced vs not)

### Takeaway
Snowflake removes classic physical design (no indexes, no user-defined partitions — micro-partitions are automatic), adds clustering keys only for multi-TB tables, defaults integers to NUMBER(38,0) with storage sized by actual value range, stores semi-structured data in VARIANT with automatic columnar sub-column extraction, and — confirmed verbatim — enforces only NOT NULL and CHECK on standard tables while PK/UNIQUE/FK are metadata-only (hybrid tables enforce them).

### Cited Findings
**Micro-partitions and clustering**
- "Each micro-partition contains between 50 MB and 500 MB of uncompressed data"; micro-partitioning is "automatically performed on all Snowflake tables" in insertion/load order; per-partition metadata (value ranges, distinct counts) drives pruning "including columns containing semi-structured data"; micro-partitions "don't need to be explicitly defined up-front or maintained by users" (MANDATORY platform behaviour); clustering depth (lower is better; 0 for empty table) via `SYSTEM$CLUSTERING_DEPTH`/`SYSTEM$CLUSTERING_INFORMATION`; "query performance is the best indicator" of whether to cluster. — [Micro-partitions & Data Clustering (Snowflake docs, n.d.)](https://docs.snowflake.com/en/user-guide/tables-clustering-micropartitions)
- Clustering key = "a subset of columns in a table (or expressions on a table) that are explicitly designated to co-locate the data"; suits tables with "a large number of micro-partitions", typically "multiple terabytes (TB) of data"; "Clustering keys are not intended for all tables due to the costs"; "Typically, queries benefit from clustering when the queries filter or sort on the clustering key"; prioritize columns "most actively used in selective filters", then join predicates; cardinality: "A column with very low cardinality might yield only minimal pruning" and "a column with very high cardinality is also typically not a good candidate... directly" — use an expression (e.g., cast timestamp to date); "Snowflake recommends a maximum of 3 or 4 columns (or expressions) per key"; "ordering the columns from lowest cardinality to highest cardinality"; "clustering is generally most cost-effective for tables that are queried frequently and do not change frequently"; automatic reclustering consumes credits and recreates micro-partitions (retained for Time Travel/Fail-safe storage); batch DML for clustered tables. (RECOMMENDED, contextual) — [Clustering Keys & Clustered Tables (Snowflake docs, n.d.)](https://docs.snowflake.com/en/user-guide/tables-clustering-keys)
- Official modeling blog: users don't need to "pre-plan partitioning or distribution keys, or build indexes to get great performance". — [Support Multiple Data Modeling Approaches with Snowflake (Graziano & Cuba, Apr 25, 2022; originally 2019)](https://www.snowflake.com/en/blog/support-multiple-data-modeling-approaches-with-snowflake/)

**Data types**
- "By default, precision is 38, and scale is 0; that is, NUMBER(38, 0)"; INT/INTEGER/BIGINT/SMALLINT/TINYINT/BYTEINT are synonyms where "precision and scale can't be specified" (always NUMBER(38,0)); "Precision — the total number of digits — doesn't affect storage" (storage sized per micro-partition min/max: values in −128..127 use 1 byte); scale does affect storage and can slow processing; maximum scale 37; FLOAT/DOUBLE/REAL are all 64-bit IEEE 754 ("Precision is approximately 15 digits"), NaN = NaN (non-IEEE); recommendations: NUMBER "for fixed-scale numeric columns", DECFLOAT (up to 38 significant digits, exact) for ledgers/taxes/variable scale, FLOAT "for high-throughput analytics where imprecise results are acceptable"; "Casting to a fixed-point data type before aggregating can reduce or eliminate these errors". (RECOMMENDED) — [Numeric data types (Snowflake docs, n.d.)](https://docs.snowflake.com/en/sql-reference/data-types-numeric)
- VARIANT "can store a value of any other type, including OBJECT and ARRAY"; "A VARIANT value can have a maximum size of up to 128 MB of uncompressed data" (note: not the older 16 MB figure); VARIANT retains the native type (TYPEOF); non-native values such as dates/timestamps "are stored as strings" so operations "might be slower and also consume more space"; OBJECT keys are VARCHAR, values VARIANT, no empty-string keys; ARRAY elements are VARIANT, no fixed-size or typed arrays in this form; VARIANT recommended for hierarchical data with 2+ nesting levels and for loading JSON/Avro/ORC/Parquet directly. — [Semi-structured data types (Snowflake docs, n.d.)](https://docs.snowflake.com/en/sql-reference/data-types-semistructured)
- Storage internals: Snowflake "extracts as much of it as possible into columnar form" and stores the remainder as one parsed column; an element is not extracted if it contains "even a single 'null' value" or has mixed data types across rows; non-extracted elements force full-JSON scans per row; default extraction limit "200 elements per partition, per table"; guidance: store in VARIANT if query patterns unknown; "For mostly regular data that uses only native format types, storage and query performance for VARIANT and relational data are very similar"; flatten to relational columns for dates/timestamps (esp. non-ISO 8601), numbers within strings, and arrays; JSON null is stored as the string "null", distinct from SQL NULL; use `STRIP_NULL_VALUES` where nulls mean missing. (RECOMMENDED) — [Considerations for semi-structured data stored in VARIANT (Snowflake docs, n.d.)](https://docs.snowflake.com/en/user-guide/semistructured-considerations)

**Constraints — verified verbatim**
- "Snowflake doesn't enforce PRIMARY KEY, UNIQUE, and FOREIGN KEY constraints on standard tables." "NOT NULL and CHECK constraints are enforced." "Standard tables, hybrid tables, and Snowflake-managed Iceberg tables support CHECK constraints." Reason: "Checking these constraints on very large, distributed, columnar tables would slow down data loading and DML operations." Why keep them: "Even though they aren't enforced, these constraints are still useful as metadata and documentation" — "You can migrate DDL from other databases without removing the constraint definitions"; "BI and data modeling tools can read the constraints to discover keys and relationships between tables"; "The constraints describe how your tables relate to each other for people who work with the data." Hybrid tables: PRIMARY KEY required and enforced; FK/UNIQUE/NOT NULL optional and enforced; CHECK enforced but only definable at creation; "For hybrid tables, you can't set the NOT ENFORCED property on PRIMARY KEY, FOREIGN KEY, and UNIQUE constraints." `RELY`: "If you set the RELY property on a constraint, the optimizer can use it for join elimination" and "Set RELY only if you've ensured that the data complies with the constraint." (MANDATORY semantics; RELY is OPTIONAL/CONTEXTUAL) — [Constraints overview (Snowflake docs, n.d.)](https://docs.snowflake.com/en/sql-reference/constraints-overview)
- Performance guide corroboration: "Snowflake supports foreign key constraints for SQL compatibility but does not enforce them" — pipelines must enforce; with external enforcement, INNER JOINs can be optimized in ways OUTER JOINs cannot; "The RELY property, when set for a Primary Key or Unique constraint, is a prerequisite for Snowflake's Join Elimination." — [Performance guide (Snowflake Well Architected Framework Team, n.d.)](https://www.snowflake.com/en/developers/guides/performance/)

### Inferences
- Snowflake's CHECK support on standard tables is a change relative to long-standing documentation that listed CHECK as unsupported; the current page states it plainly, so a framework can rely on NOT NULL + CHECK on Snowflake standard tables, and on full PK/FK/UNIQUE enforcement only on hybrid tables (the OLTP-oriented table type).
- The NUMBER(38,0) default means declaring INT vs BIGINT is purely documentary on Snowflake; the schema framework should not treat integer width as a storage decision on Snowflake (it is on Databricks/Delta Parquet).

### Gaps
- Snowflake docs pages print no last-updated date; currency can only be asserted as "live on 2026-11-07".
- The historical date when CHECK constraints became supported on standard tables was not found in the docs.

## Q5. Snowflake: data-modeling stance (star vs Data Vault vs denormalized), Time Travel/Fail-safe, Dynamic Tables vs Streams/Tasks, governance (RBAC, row access, masking, tags), zero-copy cloning, multi-tenant SaaS patterns

### Takeaway
Snowflake officially declares itself model-agnostic ("supports multiple data modeling approaches equally"), but its own performance guide and semantic-view docs lean toward star schemas for consumption ("We recommend starting with a simple star schema") with numeric keys, and its multi-tenancy white paper recommends starting with the multi-tenant-table (MTT) pattern; Dynamic Tables are the recommended declarative pipeline tool but are explicitly unsuitable for SCD2 history.

### Cited Findings
**Modeling stance**
- "Snowflake supports multiple data modeling approaches equally"; "we support any type of relational design, including Data Vault"; Data Vault described (quoting Linstedt) as "a hybrid approach encompassing the best of breed between 3rd normal form (3NF) and star schema"; suggests "virtualizing your information mart (i.e., reporting) layer"; MD5 built-in for DV2 hash keys; multi-table INSERT loads several PIT tables in parallel. No model is required. (OPTIONAL/CONTEXTUAL) — [Support Multiple Data Modeling Approaches with Snowflake (Apr 25, 2022)](https://www.snowflake.com/en/blog/support-multiple-data-modeling-approaches-with-snowflake/)
- Performance guide: star schema "works well with Snowflake, favoring right-deep query execution plans" (largest fact on probe side); dimensions joined with OUTER JOIN can be join-eliminated when unused; cluster large fact tables on "frequently used filters, join keys" plus a temporal attribute; "Use of numerical data types for key columns involved in equality joins is strongly recommended"; DV2: use numeric surrogate keys, not MD5 hash keys ("Snowflake only considers the first five bytes for clustering"); very wide tables (hundreds of columns) raise compile time — but "Avoid combining scalar attributes frequently used for filtering and joins into a single VARIANT or VARCHAR"; "While a normalized schema ensures data integrity, it often necessitates multiple joins, adding computational overhead"; "There's no universal guideline or ideal degree of denormalization; each data model and dataset is unique"; "extensive testing is crucial"; DATE/TIMESTAMP_NTZ good for joins, TIMESTAMP_TZ/LTZ hurt pruning (keep a non-TZ column for filtering); collation "never for join keys". (RECOMMENDED; denormalization degree OPTIONAL/CONTEXTUAL) — [Performance guide (Snowflake, n.d.)](https://www.snowflake.com/en/developers/guides/performance/)
- Semantic views (schema-level metadata objects mapping logical tables/relationships/facts/dimensions/metrics to physical tables): "We recommend starting with a simple star schema." (RECOMMENDED) — [Overview of semantic views (Snowflake docs, n.d.)](https://docs.snowflake.com/en/user-guide/views-semantic/overview)
- DV key styles: sequential integer keys (DV 1.0) "work best for customers who give more priority to querying directly against the DV"; hashed keys (DV 2.0) "work well for customers who place more priority on data loading performance"; join speed ranks integers > character strings > hashes. — [Tips for Optimizing the Data Vault Architecture on Snowflake (Feb 3, 2020)](https://www.snowflake.com/en/blog/tips-for-optimizing-the-data-vault-architecture-on-snowflake/)

**Time Travel and Fail-safe**
- "The standard retention period is 1 day (24 hours) and is automatically enabled for all Snowflake accounts"; Enterprise+: permanent objects "from 0 up to 90 days", transient/temporary 0 or 1 day; "Time Travel cannot be deactivated for an account" (object-level 0 disables); `AT | BEFORE` (TIMESTAMP/OFFSET/STATEMENT) and `UNDROP`; retention clock starts at the change ("End of Time Travel = time of the change + data retention period"); after retention "the data is moved into Snowflake Fail-safe"; `DATA_RETENTION_TIME_IN_DAYS` at account/db/schema/table, floored by `MIN_DATA_RETENTION_TIME_IN_DAYS`; longer retention "requires additional storage". (MANDATORY platform behaviour) — [Understanding & using Time Travel (Snowflake docs, n.d.)](https://docs.snowflake.com/en/user-guide/data-time-travel)
- "Fail-safe provides a (non-configurable) 7-day period during which historical data may be recoverable by Snowflake"; "It is for use only by Snowflake to recover data"; "Fail-safe is not provided as a means for accessing historical data after the Time Travel retention period has ended"; best-effort, "several hours to several days". (MANDATORY) — [Understanding and viewing Fail-safe (Snowflake docs, n.d.)](https://docs.snowflake.com/en/user-guide/data-failsafe)

**Dynamic Tables vs Streams/Tasks**
- "A dynamic table materializes the results of a SELECT query and keeps them up to date"; "Snowflake infers the dependency graph automatically"; TARGET_LAG (e.g., 10 min; `DOWNSTREAM` for intermediates); refresh modes INCREMENTAL / FULL / AUTO / ADAPTIVE / CUSTOM_INCREMENTAL; not suited when you "Require data fresher than 60 seconds (the minimum target lag)" or need stored procedures/external functions; "Prefer a declarative approach". — [Dynamic tables (Snowflake docs, n.d.)](https://docs.snowflake.com/en/user-guide/dynamic-tables-about)
- Decision guide: dynamic tables are "the recommended approach for new multi-table SQL pipelines in Snowflake" (incl. "Multi-step bronze/silver/gold pipeline"); streams and tasks "give you full control" — preferred for procedural logic, MERGE/complex upserts, external calls, CRON scheduling; materialized views for single-table read acceleration ("read performance, not building a data pipeline"); constraints: "Dynamic tables are read-only"; "Dynamic tables represent the current state of the data, not a historical record" (so not for SCD Type 2); definition changes reinitialize; SEQ/UUID_STRING/RANDOM unsupported in incremental mode; a dynamic table "replaces four objects and MERGE logic with a single SELECT definition". (RECOMMENDED) — [Decision guide for dynamic tables (Snowflake docs, n.d.)](https://docs.snowflake.com/en/user-guide/dynamic-tables-comparison)
- Streams: "A stream object records data manipulation language (DML) changes made to tables"; stores only an offset; `METADATA$ACTION` (INSERT/DELETE), `METADATA$ISUPDATE` (updates are DELETE+INSERT pairs), `METADATA$ROW_ID`; types standard, append-only ("exclusively tracks row inserts"), insert-only (external/Iceberg); "Querying a stream alone does not advance its offset"; offset advances only when consumed in DML; "A stream becomes stale when its offset falls outside of the data retention period"; Snowflake may extend retention up to `MAX_DATA_EXTENSION_TIME_IN_DAYS` (14-day reference) to avoid staleness. — [Introduction to Streams (Snowflake docs, n.d.)](https://docs.snowflake.com/en/user-guide/streams-intro)

**Governance**
- Access model: DAC + RBAC ("Snowflake mainly uses this model") + UBAC only with secondary roles ALL; "Unless allowed by a grant, access is denied"; "Each securable object is owned by a single role"; managed access schemas centralize grants; system roles GLOBALORGADMIN, ACCOUNTADMIN ("top-level role... should be granted only to a limited/controlled number of users"), SECURITYADMIN, USERADMIN, SYSADMIN, PUBLIC; "A role owner... does not inherit the privileges of the owned role"; recommends "creating a hierarchy of custom roles, with the top-most custom role assigned to the system role SYSADMIN"; "it is not recommended to mix account-management privileges and entity-specific privileges in the same role"; "There is no concept of a 'super-user' or 'super-role'". (RECOMMENDED) — [Overview of Access Control (Snowflake docs, n.d.)](https://docs.snowflake.com/en/user-guide/security-access-control-overview)
- Row access policies: schema-level object that "determines whether a given row in a table or view can be viewed"; "Snowflake evaluates the policy expression by using the role of the policy owner, not the role of the operator"; mapping tables allowed but "may result in decreased performance" — centralize them in the same database, prefer memoizable functions; "Snowflake evaluates the row access policy first" when masking also applies; "the same column cannot be specified in both a row access policy signature and a masking policy signature"; "Row access policies do not currently prevent rows from being inserted"; "This feature requires Enterprise Edition (or higher)". — [Understanding row access policies (Snowflake docs, n.d.)](https://docs.snowflake.com/en/user-guide/security-row-intro)
- Dynamic Data Masking: "Column-level Security feature that uses masking policies to selectively mask plain-text data"; applied "at query time" and "at every location where the column appears"; "A security or privacy officer decides which columns to protect, not the object owner"; can "prohibit privileged users with the ACCOUNTADMIN or SECURITYADMIN role from unnecessarily viewing data"; "write a policy once and have it apply to thousands of columns"; Enterprise Edition. — [Understanding Dynamic Data Masking (Snowflake docs, n.d.)](https://docs.snowflake.com/en/user-guide/security-column-ddm-intro)
- Tag-based masking: set a masking policy on a tag via `ALTER TAG`; "the tagged column is automatically protected"; assigning at database/schema/table protects existing and new matching columns ("automatically applies the masking policy to any new table columns"); one policy per data type per tag; "the masking policy that is directly assigned to the column takes precedence over the tag-based masking policy"; Enterprise Edition. (RECOMMENDED for scale) — [Tag-based masking policies (Snowflake docs, n.d.)](https://docs.snowflake.com/en/user-guide/tag-based-masking-policies)

**Zero-copy cloning**
- Clones "share the same underlying storage as the source table" (stated for Iceberg; search-optimization paths are "a zero-copy clone"); diverging writes do not affect the source; cloning is "fast, but not instantaneous"; most CREATE ... CLONE statements do not copy grants unless `COPY GRANTS` ("copies all privileges, except OWNERSHIP"); clustering key kept but "Automatic Clustering is suspended for the new table"; tasks/alerts suspended in clone; "Cloning an individual policy object is not supported"; unconsumed stream records in clone "are inaccessible"; Time Travel cloning (AT|BEFORE) fails if any child object's retention is insufficient (`IGNORE TABLES WITH INSUFFICIENT DATA RETENTION`); avoid DML on source during clone when retention is 0. — [Cloning considerations (Snowflake docs, n.d.)](https://docs.snowflake.com/en/user-guide/object-clone)

**Multi-tenant SaaS patterns (official white paper)**
- Three patterns: "Multi-tenant table (MTT): MTT consolidates tenants within a shared table or warehouse"; "Object per tenant (OPT): OPT isolates tenants into separate tables, schemas, databases, and warehouses" within one account; "Account per tenant (APT): APT isolates tenants into separate Snowflake accounts"; "Hybrid tenancy models are common" (e.g., MTT storage + dedicated compute = MTT/OPT hybrid). — [Design Patterns for Building Multi-Tenant Applications on Snowflake (Snowflake white paper PDF, 2021 per URL/metadata; no date printed)](https://www.snowflake.com/wp-content/uploads/2021/10/Design-Patterns-for-Building-Multi-Tenant-Applications-on-Snowflake.pdf)
- Scale and fit: MTT "supports apps with millions of tenants", "usually more cost-efficient", but "an app's data model has to have the same general shape across all tenants" (custom columns introduce sparsity); OPT "is a great fit if each tenant has a different data model", "typically scales well from tens to hundreds of tenants, but starts to become unwieldy when it includes thousands of tenant databases"; APT "tenant counts in the tens to low hundreds are typical", chosen for "strong security reason" (dedicated connection string, BYOT, per-tenant IP restrictions), and "APT requires the customer to also implement OPT". Table 1: MTT "Data is stamped with a tenant_id"; MTT "Requires developers to manage security, such as an entitlement table, secure views, or row-level security"; OPT lets customers "comfortable using RBAC" avoid entitlement tables; APT "Isolates tenants, thereby reducing the risk of mismanaging security". Drawbacks: MTT — multi-region sharing hard, may need sharding, "MERGE, UPDATE, and auto-clustering operations can be a challenge on very large tables", per-tenant storage cost hard to determine; OPT/APT — "maintaining a consistent state across many similar objects is hard", lose pooled compute, need automation. — [Multi-tenant white paper](https://www.snowflake.com/wp-content/uploads/2021/10/Design-Patterns-for-Building-Multi-Tenant-Applications-on-Snowflake.pdf)
- MTT design notes: serving database with secure views joining base tables to an entitlements table on tenant_id; secure views by CURRENT_USER (one DB user per tenant) or CURRENT_ROLE (fine-grained); "Tenants should have a unique numeric identifier (that is, a tenant_id)"; "Cluster all transaction tables by tenant_id and a meaningful date field, at minimum. (The reverse, date then tenant_id, is also fine.)"; "Lock down entitlement tables with restrictive permissions", manage via automated procedures, regression-test after updates; "The type of table and the data model (such as star schema or highly denormalized) also play a role in determining which tables you need to cluster"; "Databases and schemas are largely logical constructs; they don't physically separate data." Recommendation: "Snowflake recommends starting with the MTT pattern." (RECOMMENDED) — [Multi-tenant white paper](https://www.snowflake.com/wp-content/uploads/2021/10/Design-Patterns-for-Building-Multi-Tenant-Applications-on-Snowflake.pdf)
- Note: the 2021 paper predates row access policies as the primary mechanism; it uses secure views + entitlement tables. Current docs provide row access policies (Enterprise Edition) as the first-class row-level security object (see above).

### Inferences
- Snowflake's "any model" stance is marketing-level; its engineering guidance converges on star schema for consumption with numeric surrogate keys and clustering on fact filters/joins, and DV/3NF upstream — which is the same layering Databricks blogs give.
- Because Dynamic Tables are current-state only, SCD2 history on Snowflake requires streams + tasks + MERGE or an external tool (dbt snapshots, Q7).
- For multi-tenant analytical schemas: tenant_id as a leading numeric column + clustering (tenant_id, date) + row-level policy is the canonical MTT shape.

### Gaps
- Snowflake has no single official doc page prescribing a warehouse data model; guidance is spread across blogs (2019–2022), the performance guide (undated) and semantic-view docs.
- The white paper's exact publication month/author could not be read from the PDF text (URL path indicates Oct 2021; XMP metadata shows 2021).

## Q6. dbt: project structure (staging / intermediate / marts), style guide (naming), sources & freshness, exposures

### Takeaway
dbt Labs prescribes a source-conformed → business-conformed arc: staging models (1:1 with source tables, views, rename/cast only, no joins/aggregations), optional intermediate models (ephemeral or hidden views, single purpose), and wide, denormalized, entity-grained marts (tables/incremental) — with snake_case, plural names, `<object>_id` keys, `is_`/`has_` booleans, `_at` UTC timestamps, and every model carrying a primary key.

### Cited Findings
**Structure**
- Guiding principle: "a cohesive arc moving data from source-conformed to business-conformed. Source-conformed data is shaped by external systems out of our control, while business-conformed data is shaped by the needs, concepts, and definitions we create"; "stacking our transformations in optimized, modular layers means we can apply each transformation in only one place"; "above all stay consistent". Three layers: Staging ("creating our atoms"), Intermediate ("stacking layers of logic"), Marts ("bringing together our modular pieces into a wide, rich vision of the entities"). — [How we structure our dbt projects (dbt Labs docs, last updated Aug 19, 2026)](https://docs.getdbt.com/best-practices/how-we-structure/1-guide-overview)
- Staging: subdirectory per source system ("As you add more source systems, create a subdirectory per source"); not by loader, not by business area ("By breaking things up too early, we open ourselves up to creating overlap and conflicting definitions"); file name `stg_[source]__[entity]s.sql` (double underscore for multi-word sources; plural because "unless there's a single order in your orders table, plural is the correct way"); "our staging models should have a 1-to-1 relationship to our source tables"; "Staging models are the only place we'll use the source macro"; allowed: renaming, type casting, basic computations, categorizing; not allowed: joins ("joins are almost always a bad idea here — they create immediate duplicated computation") and aggregations ("if we start changing the grain... we'll lose access to source data"); materialized as views (freshest data, no wasted warehouse space); exception: base models for unions/delete-table joins. (RECOMMENDED) — [Staging: Preparing our atomic building blocks (dbt Labs docs, Jul 7, 2026)](https://docs.getdbt.com/best-practices/how-we-structure/2-staging)
- Intermediate: grouped "by their area of business concern"; `int_[entity]s_[verb]s.sql` (verbs: pivoted, aggregated_to_user, joined, fanned_out_by_quantity); "Intermediate models should generally not be exposed in the main production schema"; materialize ephemeral (default option) or "as views in a specific custom schema"; purposes: structural simplification (combine "typically 4 to 6" models), re-graining, isolating complex operations; DAG rule: "Narrow the DAG, widen the tables"; "allowing multiple inputs to a model, but not multiple outputs" — multiple outputs post-staging is "a red flag". (RECOMMENDED) — [Intermediate: Purpose-built transformation steps (dbt Labs docs, Aug 19, 2026)](https://docs.getdbt.com/best-practices/how-we-structure/3-intermediate)
- Marts: "entity layer or concept layer"; "Marts are entity-grained. The most important aspect of marts is that they contain all of the useful data about a particular entity at a granular level"; group by department (marketing, finance) once >10 marts; name by entity (`customers`, `orders`), not time-grained (`orders_per_day` belongs to metrics); `finance_orders` vs `marketing_orders` is "an anti-pattern"; materialization ladder: "always start with a view... once that view takes too long to practically query, build it into a table, and finally once that table takes too long to build... configure it as an incremental model"; "rushing to make all your marts models incremental by default will introduce superfluous difficulty"; "Wide and denormalized"; avoid >4–5 concepts in one mart (add intermediates); marts built on marts OK with care. Kimball contrast (verbatim): "Unlike in a traditional Kimball star schema though, in modern data warehousing — where storage is cheap and compute is expensive — we'll happily borrow and add any and all data from other concepts that are relevant to answering questions about the mart's core entity." Semantic-layer caveat: "In a project without the Semantic Layer we recommend you denormalize heavily... if you're using the Semantic Layer, we want to stay as normalized as possible to allow MetricFlow the most flexibility." (RECOMMENDED; denormalization CONTEXTUAL on Semantic Layer use) — [Marts: Business-defined entities (dbt Labs docs, Jul 7, 2026)](https://docs.getdbt.com/best-practices/how-we-structure/4-marts)
- Best-practice guide families (landing page): How we structure (5), How we style (6), How we build our metrics (9), Wizard (7), dbt Mesh (5), real-time data (6), change data capture (2), Materialization best practices (6); standalone: Idempotence, custom generic tests, dbt + Unity Catalog. — [Best practice guides (dbt Labs docs, n.d.)](https://docs.getdbt.com/best-practices)

**Style guide**
- "Models should be pluralized"; "Use underscores for naming dbt models; avoid dots" (dots separate database.schema.object); "Schema, table and column names should be in snake_case"; "Each model should have a primary key"; "The primary key of a model should be named <object>_id"; "Keys should be string data types"; "Consistency is key! Use the same field names across models"; "Booleans should be prefixed with is_ or has_"; "Timestamp columns should be named <event>_at... and should be in UTC" (else suffix e.g. `created_at_pt`); "Dates should be named <event>_date"; event names past tense; "Price/revenue fields should be in decimal currency" (else `price_in_cents`); versions suffix `_v1`, `_v2`; "Do not use abbreviations or aliases"; "Avoid reserved words as column names"; "Use names based on the business terminology, rather than the source terminology"; column ordering "ids, strings, numerics, booleans, dates, and timestamps". The style page does **not** itself list `stg_`/`int_`/`fct_`/`dim_` prefixes (those come from the structure guide and the Kimball blog). (RECOMMENDED) — [How we style our dbt models (dbt Labs docs, Sep 10, 2026)](https://docs.getdbt.com/best-practices/how-we-style/1-how-we-style-our-dbt-models)
- CONFLICT (key data types): dbt style guide "Keys should be string data types" vs Snowflake performance guide "Use of numerical data types for key columns involved in equality joins is strongly recommended" and Snowflake DV guidance (numeric over hash keys) and Databricks (IDENTITY integer surrogate keys). dbt's position reflects hash-based `generate_surrogate_key` practice (see Q7/Q8); the platforms' position reflects join/clustering performance.
- CONFLICT (naming, intra-dbt): style guide says plural model names, but the dbt developer-blog Kimball tutorial uses singular `dim_product`, `dim_customer` (and `fct_sales`) — [Building a Kimball dimensional model with dbt (Jonathan Neo, dbt developer blog, Apr 20, 2023)](https://docs.getdbt.com/blog/kimball-dimensional-model).

**Sources, freshness, exposures**
- "Sources make it possible to name and describe the data loaded into your warehouse by your Extract and Load tools"; `source()` "creates a dependency between the model and the source table" (lineage); benefits: lineage, "test your assumptions about your source data", "calculate the freshness of your source data"; freshness via `loaded_at_field` + `warn_after`/`error_after` ("If neither is provided, then dbt will not calculate freshness"); "a critical component of defining Service Level Agreements (SLAs) for your warehouse"; `dbt freshness --resource-type source`; build only downstream of fresh sources with `dbt build --select source_status:fresher+`; dbt v2 with dbt State "automatically tracks source freshness using warehouse metadata". (RECOMMENDED) — [Add sources to your DAG (dbt Labs docs, Sep 16, 2026)](https://docs.getdbt.com/docs/build/sources)
- Exposures "make it possible to define and describe a downstream use of your dbt project, such as in a dashboard, application, or data science pipeline"; required: `name` (snake case), `type` (dashboard, notebook, analysis, ml, application), `owner` (name or email); expected `depends_on` (ref/source/metric); optional `url`, `maturity` (high/medium/low), `label`, `description`, `tags`, `meta`; selection `dbt run -s +exposure:<name>`; automatic exposures exist for supported BI integrations. (OPTIONAL/CONTEXTUAL) — [Add Exposures to your DAG (dbt Labs docs, Nov 3, 2026)](https://docs.getdbt.com/docs/build/exposures)

### Inferences
- dbt's three layers approximate medallion but are narrower: staging ≈ light Silver (no Bronze — raw tables are *sources*, not models), marts ≈ Gold. dbt deliberately keeps raw data as untouched "sources" with freshness SLAs, aligning with Databricks Bronze "source of truth" intent.
- dbt's "entity-grained wide marts" is OBT-leaning but not pure OBT: a mart is one entity at one grain, not a fact pre-joined with all dimensions.

### Gaps
- The structure guide does not define `fct_`/`dim_` naming formally; prefix conventions for marts appear only in examples and the developer blog.
- dbt's own Discourse debate on dimensional modeling vs OBT (linked from the Kimball blog) is community content and was not fetched.

## Q7. dbt: tests (generic, singular, unit), model contracts, model versions/access, snapshots (SCD2), ELT vs ETL

### Takeaway
dbt substitutes declarative tests and build-time contracts for the integrity enforcement warehouses lack: every model should have `unique` + `not_null` on its primary key, contracts enforce column names/types (and `not_null` where the platform enforces it) at build time, versions give a migration window for breaking changes, and snapshots implement SCD Type 2 with `dbt_valid_from`/`dbt_valid_to` — all within an ELT pattern where transformation happens inside the warehouse.

### Cited Findings
**Data tests**
- "Data tests are assertions you make about your models and other resources"; "Data tests return a set of failing records"; two kinds: singular (one-off SQL returning failing rows) and generic (parameterized `test` block — "they should make up the bulk of your dbt data testing suite"); built-ins: "unique, not_null, accepted_values, and relationships"; `relationships` checks each value exists in another model (referential integrity); `severity`, `warn_if`, `error_if`; `--store-failures` writes failing rows to `dbt_test__audit`; "We recommend that every model has a data test on a primary key, that is, a column that is unique and not_null" and "We also recommend that you test any assumptions on your source data"; in v2 test inputs nest under `arguments:`. (RECOMMENDED) — [Add data tests to your DAG (dbt Labs docs, Sep 16, 2026)](https://docs.getdbt.com/docs/build/data-tests)
- Unit tests (since v1.8): "validate your SQL modeling logic on a small set of static inputs before you materialize your full model"; use for regex/date math/window/case logic, previously buggy logic, edge cases, refactors, high-criticality (public/contracted/upstream of exposures) models; don't unit-test warehouse built-ins like `min()`; limits: SQL models only, not materialized views, recursive/introspective SQL; "dbt Labs strongly recommends only running unit tests in development or CI environments"; `dbt build` order: unit tests → materialize → data tests. (RECOMMENDED) — [Unit tests (dbt Labs docs, Sep 14, 2026)](https://docs.getdbt.com/docs/build/unit-tests)

**Model contracts, versions, access**
- "It's better to define a set of upfront 'guarantees' that define the shape of your model. We call this set of guarantees a 'contract.'"; with `contract: enforced: true`, dbt runs a "preflight" check that the query returns matching column names/types, then "includes the column names, data types, and constraints in the DDL"; "your contract must include every column's name and data_type"; constraint categories: definable+enforced ("The model won't build if it violates the constraint"), definable+not enforced ("metadata purposes only"), not definable; constraint types `not_null`, `primary_key`, `foreign_key`, `unique`, `check`; most warehouse adapters: `not_null` enforced only, PK/FK/UNIQUE metadata-only, CHECK not definable; Postgres: all enforced; some adapters enforce `not_null`/`check` only after build so they are "not part of the model contract"; Fabric: only `not_null` checked at build; Athena: none. Supported on `table`, `incremental` (with `on_schema_change: append_new_columns|fail`), `view` (names/types only); not Python, materialized view, ephemeral, sources/seeds/snapshots. Recommended "for 'public' models that are being relied on downstream"; "A model's contract defines the shape of the returned dataset... the model does not build" if violated; breaking changes (remove column, change type, remove constraint, delete/rename/disable contracted model) raise errors vs previous state. (RECOMMENDED; platform enforcement as stated) — [Model contracts (dbt Labs docs, Oct 29, 2026)](https://docs.getdbt.com/docs/mesh/govern/model-contracts)
- Cross-check against platform docs: Databricks enforces NOT NULL + CHECK, PK/FK informational — [Constraints on Databricks](https://docs.databricks.com/aws/en/tables/constraints); Snowflake enforces NOT NULL + CHECK, PK/UNIQUE/FK not enforced — [Snowflake constraints overview](https://docs.snowflake.com/en/sql-reference/constraints-overview). The dbt contracts page (as fetched) could not be mapped tab-by-tab to adapters; the platform docs are authoritative for enforcement.
- Versions: "When sharing a final dbt model with other teams or systems, that model is operating like an API"; breaking change = remove/rename column, change type or nullability; "If you're making a non-breaking change, you don't need a new version—such as adding a new column"; recommended cadence "once or twice a year, communicated well in advance"; files `<model>_v<v>.sql`, YAML `versions:` with `include: all / exclude: [...]` diffs, `latest_version`, `defined_in`; `ref('dim_customers', v=2)` pinned, unpinned ref "resolves to the latest version"; `deprecation_date` (v1.6) gives "a known boundary on the cost of that migration"; governance "can make rollbacks harder... and increase maintenance if adopted too early". (OPTIONAL/CONTEXTUAL — for mature public models) — [Model versions (dbt Labs docs, Sep 10, 2026)](https://docs.getdbt.com/docs/mesh/govern/model-versions)
- Access: `private` (same group), `protected` (same project; the default "largely for backward compatibility"), `public` (any group/package/project); recommended to set new models `private`; example marks `dim_customers` public ("a stable & mature interface"), intermediates private, staging protected; "Specifying access: public on a model does not trigger dbt to automagically grant select" (use `grants`). (RECOMMENDED) — [Model access (dbt Labs docs, Jul 20, 2026)](https://docs.getdbt.com/docs/mesh/govern/model-access)

**Snapshots (SCD Type 2)**
- "dbt provides a mechanism, snapshots, which records changes to a mutable table over time"; they "implement type-2 Slowly Changing Dimensions over mutable source tables"; meta-fields `dbt_valid_from`, `dbt_valid_to` (NULL or `dbt_valid_to_current` for current), `dbt_scd_id`, `dbt_updated_at`, `dbt_is_deleted` (with `hard_deletes: new_record`); "The unique key is used by dbt to match rows up, so it's extremely important to make sure this key is actually unique!"; strategies: `timestamp` (recommended; "handles column additions and deletions more efficiently") and `check` (for tables without reliable `updated_at`; "It is better to explicitly enumerate the columns"); `hard_deletes`: `ignore` (default), `invalidate`, `new_record`; YAML-defined snapshots (v1.9), `target_schema` optional, `dbt_valid_to_current: "to_date('9999-12-31')"`; "Snapshots are only useful if you run them frequently" ("between hourly and daily"); "Snapshots can't be rebuilt. Because of this, it's a good idea to put snapshots in a separate schema"; snapshots ignore `--full-refresh`; clean data via an ephemeral model before snapshotting. (RECOMMENDED) — [Add snapshots to your DAG (dbt Labs docs, Sep 29, 2026)](https://docs.getdbt.com/docs/build/snapshots)
- Platform contrast: Snowflake Dynamic Tables cannot hold SCD2 history ("current state of the data, not a historical record") — [Decision guide for dynamic tables](https://docs.snowflake.com/en/user-guide/dynamic-tables-comparison); Databricks does SCD2 with `APPLY CHANGES INTO` — [Loading a DW data model in real time (Nov 7, 2022)](https://www.databricks.com/blog/2022/11/07/load-edw-dimensional-model-real-time-databricks-lakehouse.html).

**ELT vs ETL**
- "With ETL, data is transformed before loading, while in ELT, data is transformed after loading into the data warehouse"; ELT "has gained popularity in cloud-native environments" and is "a paradigm for how to manage information flows in a modern data warehouse"; benefits: cloud warehouse compute at scale, faster data availability, cost efficiency, flexible/iterative transformation, data democratization; hybrids are valid (ETL for compliance-sensitive masking before load); the post does not literally say "ELT is required". (RECOMMENDED by framing) — [ETL vs ELT: What's the difference? (Daniel Poppy, dbt Labs blog, Mar 15, 2023)](https://getdbt.com/blog/etl-vs-elt)
- Lakehouse paper's related argument: "data is first ETLed into lakes, and then again ELTed into warehouses, creating complexity, delays, and new failure modes"; Delta paper: organizations "reuse existing SQL queries to perform their ETL process directly on the object store" — [Lakehouse paper](https://www.cidrdb.org/cidr2021/papers/cidr2021_paper17.pdf); [Delta Lake paper](https://www.vldb.org/pvldb/vol13/p3411-armbrust.pdf)
- Kimball-with-dbt (developer blog): dimensional modeling "still one of the most widely adopted data modeling technique for analytics"; benefits: no complex joins for consumers, reusable conformed dimensions, queries "significantly faster than a 3NF model"; surrogate keys via `dbt_utils.generate_surrogate_key()` hashing natural keys ("removes the hassle of performing a join with dimension tables when generating the surrogate key for the fact tables"); OBT "If your BI tool doesn't have a semantic layer that supports relationships... you will have to reflect that relationship by creating a One Big Table"; `not_null` + `unique` tests on every surrogate key; dims as `table`, facts `incremental` at millions/billions of rows. — [Building a Kimball dimensional model with dbt (Apr 20, 2023)](https://docs.getdbt.com/blog/kimball-dimensional-model)

### Inferences
- In dbt's model, integrity = tests (post-build) + contracts (build-time shape) — a schema framework should treat `unique`+`not_null` on PK and `relationships` on FKs as the *required* substitute for unenforced platform constraints.
- Hash surrogate keys (dbt) vs integer IDENTITY keys (Databricks/Snowflake performance guidance) is a genuine design fork: hashes enable join-free, parallel, idempotent loads; integers favour join/clustering performance.

- Exact adapter-by-adapter contract enforcement table could not be attributed from the fetched text; platform docs were used instead.
- dbt has no official page quantifying "storage is cheap" beyond the marts guide sentence; no cost model is given.

## Q8. Cross-cutting: where modern cloud DW guidance conflicts with Kimball/3NF, and which constraints are enforced vs informational

### Takeaway
All three vendors keep Kimball's *presentation-layer* star schema (Databricks: "gold standard"; Snowflake: "start with a simple star schema"; dbt: `dim_`/`fct_` plus wide entity marts) but reject Kimball-era physical assumptions — enforced PK/FK, pre-planned partitions/indexes, narrow conformed-dimension joins as a storage economy — because on these platforms only NOT NULL and CHECK are enforced, physical layout is automatic or mutable (micro-partitions, liquid clustering), and "storage is cheap and compute is expensive" tilts toward denormalized wide tables.

### Cited Findings
**Enforced vs informational constraints (critical for integrity-assuming frameworks)**

| Platform | NOT NULL | CHECK | PRIMARY KEY | UNIQUE | FOREIGN KEY | Source |
|---|---|---|---|---|---|---|
| Databricks (Delta, UC) | Enforced | Enforced (deterministic SQL only) | Informational | Informational (Preview) | Informational | [Databricks constraints (Oct 29, 2026)](https://docs.databricks.com/aws/en/tables/constraints) |
| Snowflake standard / Iceberg tables | Enforced | Enforced | Not enforced | Not enforced | Not enforced | [Snowflake constraints overview (n.d.)](https://docs.snowflake.com/en/sql-reference/constraints-overview) |
| Snowflake hybrid tables (OLTP-style) | Enforced | Enforced (creation-time only) | Required + enforced | Enforced | Enforced | [Snowflake constraints overview](https://docs.snowflake.com/en/sql-reference/constraints-overview) |
| dbt contracts (on the above) | Enforced via DDL where platform enforces | Mostly not definable | Metadata only | Metadata only | Metadata only | [dbt model contracts (Oct 29, 2026)](https://docs.getdbt.com/docs/mesh/govern/model-contracts) |

- Vendor rationale for not enforcing keys: Snowflake — "Checking these constraints on very large, distributed, columnar tables would slow down data loading and DML operations"; keys kept for DDL migration, BI-tool relationship discovery, and documentation — [Snowflake constraints overview](https://docs.snowflake.com/en/sql-reference/constraints-overview). Databricks — PK/FK "might improve performance through" optimizations; blog: they "help analysts identify join relationships" — [Databricks constraints](https://docs.databricks.com/aws/en/tables/constraints); [Data Modeling Best Practices (Oct 20, 2022)](https://www.databricks.com/en/blog/data-modeling-best-practices-implementation-modern-lakehouse).
- `RELY` exists on both platforms as an optimizer trust flag — Snowflake: "Set RELY only if you've ensured that the data complies with the constraint" — [Snowflake constraints overview](https://docs.snowflake.com/en/sql-reference/constraints-overview); Databricks mentions RELY in the 2025 myths blog — [Myths (Dec 15, 2025)](https://www.databricks.com/blog/databricks-lakehouse-data-modeling-myths-truths-and-best-practices).
- Substitute mechanisms: dbt `unique`/`not_null`/`relationships` tests ("every model has a data test on a primary key") — [dbt data tests](https://docs.getdbt.com/docs/build/data-tests); Delta "constraints API" and Delta expectations "automatically reject records that violate these expectations or quarantine them" — [Lakehouse paper](https://www.cidrdb.org/cidr2021/papers/cidr2021_paper17.pdf); Databricks CHECK used as proxy for FK validity (`valid_product_id`) — [Loading a DW data model in real time (Nov 7, 2022)](https://www.databricks.com/blog/2022/11/07/load-edw-dimensional-model-real-time-databricks-lakehouse.html).

**Conflicts with classic Kimball/3NF guidance**
1. Denormalization degree — dbt marts: "Unlike in a traditional Kimball star schema... storage is cheap and compute is expensive — we'll happily borrow and add any and all data from other concepts" ([dbt marts](https://docs.getdbt.com/best-practices/how-we-structure/4-marts)); Databricks: star schemas remain "the gold standard for the presentation layer" though Gold may be "completely denormalized" for ML ([Databricks DW modeling techniques, 2022](https://www.databricks.com/blog/2022/06/24/data-warehousing-modeling-techniques-and-their-implementation-on-the-databricks-lakehouse-platform.html)); Snowflake: "There's no universal guideline or ideal degree of denormalization" and very wide tables (hundreds of columns) raise compile time ([Snowflake performance guide](https://www.snowflake.com/en/developers/guides/performance/)). dbt itself reverses its advice under the Semantic Layer ("stay as normalized as possible"). Net: denormalization is OPTIONAL/CONTEXTUAL across all three; none mandates OBT.
2. Physical design — Kimball-era partitioning/indexing is replaced: Snowflake "don't need to pre-plan partitioning or distribution keys, or build indexes" ([Snowflake modeling blog, 2022](https://www.snowflake.com/en/blog/support-multiple-data-modeling-approaches-with-snowflake/)); Databricks "liquid clustering... replaces table partitioning and ZORDER" ([Liquid clustering docs](https://docs.databricks.com/aws/en/delta/clustering)); Databricks 2022: date partitioning "almost a bad practice" ([Data Modeling Best Practices, 2022](https://www.databricks.com/en/blog/data-modeling-best-practices-implementation-modern-lakehouse)).
3. Surrogate keys — Kimball integer surrogates survive as IDENTITY columns on Databricks ([Loading a DW data model in real time](https://www.databricks.com/blog/2022/11/07/load-edw-dimensional-model-real-time-databricks-lakehouse.html)) and are "strongly recommended" numeric on Snowflake ([Performance guide](https://www.snowflake.com/en/developers/guides/performance/)), but dbt style says "Keys should be string data types" ([dbt style guide](https://docs.getdbt.com/best-practices/how-we-style/1-how-we-style-our-dbt-models)) and the dbt Kimball tutorial hashes natural keys ([dbt Kimball blog](https://docs.getdbt.com/blog/kimball-dimensional-model)); Databricks DV blog also recommends hash keys ([DV on Databricks](https://www.databricks.com/blog/2022/06/24/prescriptive-guidance-for-implementing-a-data-vault-model-on-the-databricks-lakehouse-platform.html)). Genuine three-way conflict.
4. Schema-on-write at ingestion — Kimball/3NF assume typed staging; Databricks Bronze recommends "string, VARIANT, or binary" ([Medallion](https://docs.databricks.com/aws/en/lakehouse/medallion)) and Snowflake recommends VARIANT "if you don't yet know how you'll query the data" ([VARIANT considerations](https://docs.snowflake.com/en/user-guide/semistructured-considerations)); typing is deferred to Silver/staging models. The Lakehouse paper frames the 1st-gen warehouse as "schema-on-write" and the lake as "schema-on-read", with the lakehouse adding schema enforcement back via the metadata layer ([Lakehouse paper](https://www.cidrdb.org/cidr2021/papers/cidr2021_paper17.pdf)).
5. Data independence — the Lakehouse paper concedes lakehouses "give up some aspects of data independence, which has been a cornerstone of relational DBMS design" ([Lakehouse paper](https://www.cidrdb.org/cidr2021/papers/cidr2021_paper17.pdf)) — a direct departure from Codd/3NF premises.
6. SCD2 — preserved by all (dbt snapshots; Databricks APPLY CHANGES INTO; Snowflake streams+tasks), but Snowflake's recommended declarative tool (Dynamic Tables) cannot express it ([Dynamic tables decision guide](https://docs.snowflake.com/en/user-guide/dynamic-tables-comparison)).
7. Medallion ≠ model — Databricks: "recommended best practice but not a requirement" ([Medallion](https://docs.databricks.com/aws/en/lakehouse/medallion)) and "a guideline, not a rigid requirement" ([Myths 2025](https://www.databricks.com/blog/databricks-lakehouse-data-modeling-myths-truths-and-best-practices)); Snowflake's own decision guide now uses "bronze/silver/gold pipeline" as a scenario ([Dynamic tables decision guide](https://docs.snowflake.com/en/user-guide/dynamic-tables-comparison)), showing medallion vocabulary has crossed vendors as a *pipeline* term.
8. Time travel ≠ backup — Databricks: "Don't use table history as a long-term backup solution" ([Delta history](https://docs.databricks.com/aws/en/delta/history)); Snowflake: Fail-safe "is not provided as a means for accessing historical data" ([Fail-safe](https://docs.snowflake.com/en/user-guide/data-failsafe)). Versioning is for recovery/reproducibility windows, not archival.

**Applicability summary**
- OLAP/lakehouse only: medallion layers, Delta/Snowflake physical layout, informational keys, VARIANT-first ingestion, Dynamic Tables, dbt layers/tests/contracts.
- OLTP exceptions: Snowflake hybrid tables (enforced PK/FK/UNIQUE); the Delta paper notes write rate "limited to several transactions per second", i.e., Delta is not an OLTP store ([Delta Lake paper](https://www.vldb.org/pvldb/vol13/p3411-armbrust.pdf)).
- General: naming conventions (snake_case, `<object>_id`, `is_`, `_at` UTC) from dbt are platform-agnostic; RBAC hierarchy and tag-based policy guidance are general governance.

### Inferences
- A schema framework that "assumes integrity enforcement" must be split: *declared* integrity (PK/FK/UNIQUE as metadata for BI tools and RELY-based optimization) vs *enforced* integrity (NOT NULL, CHECK, plus pipeline/dbt tests). On these platforms the second set is the only one that fails a write.
- The three vendors converge on one layered model: raw (string/VARIANT) → integrated/normalized (3NF or Data Vault, typed, deduplicated, SCD2) → presentation (star schema or entity-grained wide marts), with the physical layer handled by clustering keys rather than partitions/indexes.

### Gaps
- No vendor provides a quantitative cost model backing "storage is cheap and compute is expensive"; the claim is asserted (dbt) rather than cited.
- No official Snowflake or Databricks doc page offers a direct comparison of OBT vs star schema performance; the only official statements are qualitative (Snowflake: wide tables raise compile time; Databricks: star schemas "translate exceptionally well").
