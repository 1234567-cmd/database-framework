# 09 — Database Security and Data Privacy Standards for Schema Design and Data Engineering

Research notes compiled 2026-11-07/08 from primary sources only (standards bodies, regulators, vendor documentation). Every claim carries an inline citation to a URL that was actually opened (or, where noted, extracted locally from an official PDF downloaded from the publisher). Dates are the publisher's own date where shown; "n.d." where the page shows none. Labels: **MANDATORY** (legally required, or required for correctness/safety), **RECOMMENDED** (the source prescribes it as best practice), **OPTIONAL/CONTEXTUAL** (depends on threat model or regime).

Conventions used below: PII = personally identifiable information; PAN = primary account number; SAD = sensitive authentication data; ePHI = electronic protected health information; RLS = row-level security; TDE = transparent data encryption.

## Key Question 1 — What do OWASP cheat sheets, the OWASP Top 10, and ASVS v5 prescribe for database access, storage, logging and data protection?

### Takeaway
OWASP's position is consistent across its cheat sheets, the Top 10:2025 and ASVS 5.0.0: bind every value with parameterized queries (never escape), give the application account only the DML it needs and never database ownership or admin rights, keep secrets out of code and repos, avoid storing sensitive data at all where possible, encrypt with authenticated AES modes under formally managed keys stored apart from the data, and log security events in structured form while explicitly excluding PII, credentials and card data from logs. Injection is still in the Top 10 (A05:2025) and Cryptographic Failures (A04:2025) and Security Logging and Alerting Failures (A09:2025) remain; ASVS 5.0.0 adds a formal requirement to inventory and classify sensitive data and to document per-level protection requirements (encryption, retention, logging, database encryption).

### Cited Findings

**Database Security Cheat Sheet** — [OWASP Database Security Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Database_Security_Cheat_Sheet.html) (n.d.)
- Network isolation: disable TCP in favour of local sockets or bind to localhost, firewall, or dedicated segment; "Direct connections should never be made from a thick client to the backend database" — use an API that enforces access control. **RECOMMENDED**
- Transport: most databases default to unencrypted connections; "Configure the database to only allow encrypted connections", clients should use "TLSv1.2+ with modern ciphers (e.g, AES-GCM or ChaCha20)" and verify the server certificate. **RECOMMENDED** (becomes MANDATORY under PCI DSS/HIPAA contexts, see KQ4)
- Authentication: "The database should always require authentication, including connections from the local server." Accounts: strong unique passwords, used by a single application/service, minimum permissions; review accounts regularly; remove on decommission; rotate when staff leave. Prefer Windows Integrated Authentication for SQL Server (no stored credentials). **RECOMMENDED**
- Credentials: "Database credentials should never be stored in the application source code, especially if they are unencrypted." Store in a config file outside the web root, read-restricted, "not checked into source code repositories", encrypted where possible (e.g., ASP.NET web.config encryption). **RECOMMENDED**
- Least privilege (schema-relevant): do not use built-in accounts (root, sa, SYS); no instance-admin rights; restrict connection hosts; "Use separate databases and accounts for development, UAT, and production"; "Most applications would only need SELECT, UPDATE and DELETE permissions"; "The account should not be the owner of the database as this can lead to privilege escalation vulnerabilities"; avoid database links/linked servers; for security-critical apps consider table-, column- and row-level permissions or block direct table access and expose restricted views. **RECOMMENDED**
- Hardening: harden OS to CIS Benchmarks / Microsoft Security Baselines; patch; run service under low-privileged OS account; remove default accounts and sample databases; store transaction logs on a separate disk; back up regularly, protect and "ideally encrypt" backups. Platform specifics: SQL Server — disable xp_cmdshell, xp_dirtree, CLR, SQL Browser, Mixed Mode unless required; MySQL — run mysql_secure_installation and "Disable the FILE privilege for all users". **RECOMMENDED**

**SQL Injection Prevention Cheat Sheet** — [OWASP SQL Injection Prevention Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/SQL_Injection_Prevention_Cheat_Sheet.html) (n.d.)
- Primary defense: prepared statements — "Prepared statements treat bound values as data rather than SQL syntax." **MANDATORY (for correctness/safety)**
- Stored procedures are not automatically safe: "Binding procedure arguments protects the call, not dynamic SQL constructed inside the procedure."
- Structural elements (table names, column names, sort direction) cannot be bound; "Keep these structural choices fixed in code where possible" or map user choices to an allow-list of application-owned tokens.
- Escaping is explicitly discouraged: "Do not use manual escaping as a substitute for parameter binding."
- Least privilege is a damage-limiting control, not a prevention: "It limits the damage an attacker can cause through a database account; it does not prevent SQL injection." Also: "DO NOT ASSIGN DBA OR ADMIN TYPE ACCESS TO YOUR APPLICATION ACCOUNTS"; use views to restrict exposed columns; do not run the DBMS as a privileged OS account. **RECOMMENDED**
- "Validation of a value does not make it safe to concatenate into SQL."

**Query Parameterization Cheat Sheet** — [OWASP Query Parameterization Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Query_Parameterization_Cheat_Sheet.html) (n.d.)
- "SQL Injection is best prevented through the use of parameterized queries"; parameterization must be server-side ("ensure that query parameterization is done server-side!"). Examples given for Java (JDBC PreparedStatement, JPA/Hibernate), .NET (SqlCommand/SqlParameter), Ruby (ActiveRecord), PHP (PDO), ColdFusion (cfqueryparam), Perl (DBI), Rust (SQLx); for dynamic SQL inside stored procedures: Oracle `EXECUTE IMMEDIATE ... USING`, SQL Server `sp_executesql`. "Dynamic SQL can be parameterized using bind variables, to ensure the dynamically constructed SQL is secure." **MANDATORY (correctness)**

**Cryptographic Storage Cheat Sheet** — [OWASP Cryptographic Storage Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Cryptographic_Storage_Cheat_Sheet.html) (n.d.)
- Four layers of encryption (application, database e.g. SQL Server TDE, filesystem e.g. BitLocker/LUKS, hardware); "Which layer(s) are most appropriate will depend on the threat model." Hardware/disk encryption defends against physical theft but not against a remote compromise of a running system. **OPTIONAL/CONTEXTUAL (threat-model dependent)**
- Minimization is the first principle: "The best way to protect sensitive information is to not store it in the first place" (especially card data under PCI DSS). **RECOMMENDED** (MANDATORY for SAD under PCI DSS, see KQ4)
- Algorithms: AES with "a key that's at least 128 bits (ideally 256 bits)"; "Where available, authenticated modes should always be used" (GCM/CCM first; CTR/CBC only with Encrypt-then-MAC); "ECB should not be used outside of very specific circumstances"; RSA ≥2048 with OAEP ("Do not use RSA without an encryption padding scheme"); post-quantum: ML-KEM (FIPS 203) in hybrid constructions where needed. **RECOMMENDED**
- Key management: formal processes for generation, storage, distribution, rotation, decommissioning; keys generated by a CSPRNG and "should not be based on common words or phrases"; rotate on suspected compromise (including departure of someone with access), at end of cryptoperiod (cites NIST SP 800-57 Part 1 Rev. 5 §5.3), before mode usage limits, or on algorithm weakening. Two re-encryption strategies: decrypt/re-encrypt (preferred for simplicity) or tag each item with its key ID and keep multiple keys for decryption; retain old keys for backups. **RECOMMENDED**
- Key storage: use HSMs/KMS (AWS KMS, Azure Key Vault), secrets managers (HashiCorp Vault, Conjur) or OS protected storage; never hard-code keys or commit to VCS; "Avoid storing keys in environment variables, as these can be accidentally exposed"; keep keys separate from the data they protect (keys on filesystem if data in database) so that one foothold (SQLi or directory traversal) cannot reach both; envelope encryption with DEK/KEK — KEK stored separately and at least as strong; encrypted DEK may sit alongside the data. **RECOMMENDED**
- Randomness: CSPRNGs required for keys, IVs, tokens; UUID v4 randomness "should not be relied upon" unless the platform is known secure. Passwords: "Passwords should not be stored using reversible encryption - secure password hashing algorithms should be used instead." **MANDATORY (correctness)**

**Logging Cheat Sheet** — [OWASP Logging Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html) (n.d.)
- Events to log include "Authentication successes and failures", authorization failures, user/privilege administration, admin activity, use of shared/break-glass accounts, access to sensitive data, cryptographic key use or rotation, configuration changes, logging start/stop. Avoid "alarm fog". Each record answers when/where/who/what (timestamps in international format, interaction ID, app/host/service, user identity, event type/severity). **RECOMMENDED**
- Data to exclude (remove, mask, hash or encrypt before logging): source code, access tokens, encryption keys, passwords and "database connection strings", session identifiers, "Sensitive personal data and PII", bank account and "payment cardholder data", commercially sensitive data; pseudonymize where identity isn't needed. **MANDATORY where regulated (PCI/GDPR), RECOMMENDED otherwise**
- Integrity and protection: "Build in tamper detection so you know if a record has been modified or deleted"; "Store or copy log data to read-only media as soon as possible"; record and monitor all access to logs; detect when logging stops; secure transport (syslog over TLS); synchronize time. **RECOMMENDED** (MANDATORY under PCI DSS Req 10 / HIPAA audit controls)
- Retention: "Log data... must not be destroyed before the duration of the required data retention period" and should not be kept beyond it — legal, regulatory and contractual obligations set the period. **MANDATORY (per applicable regulation)**
- Database logging specifics: "When using a database, it is preferable to utilize a separate database account that is only used for writing log data" with very restrictive permissions; "If writing to databases, read, understand, and apply the SQL injection cheat sheet"; "Do not use unstructured text log formats" (CR/LF injection) — prefer JSON. **RECOMMENDED**

**OWASP Top 10:2025** — [OWASP Top 10:2025](https://top10.owasp.org/2025/) and [Introduction](https://top10.owasp.org/2025/0x00_2025-Introduction) (2025; exact release date not shown on page)
- Current edition is Top 10:2025 (the 2021 URL redirects to it). Categories: A01 Broken Access Control; A02 Security Misconfiguration; A03 Software Supply Chain Failures; A04 Cryptographic Failures; A05 Injection; A06 Insecure Design; A07 Authentication Failures; A08 Software or Data Integrity Failures; A09 Security Logging and Alerting Failures; A10 Mishandling of Exceptional Conditions.
- Changes vs 2021: Injection "falls two spots from #3 to #5 in the ranking"; Cryptographic Failures "falls two spots from #2 to #4"; Software Supply Chain Failures "is an expansion of A06:2021-Vulnerable and Outdated Components"; Mishandling of Exceptional Conditions is "a new category for 2025". Data: "over 2.8 millions applications", 589 CWEs with 248 mapped into the ten categories; two categories chosen from a community survey. (Per [OWASP Top 10:2025 search results](https://owasp.org/Top10/2025/A05_2025-Injection/), the A05 page reports 100% of tested applications had some form of injection — snippet only, page not opened.)

**OWASP ASVS 5.0.0** — [OWASP ASVS](https://asvs.owasp.org/) (stable release 30 May 2025) and chapter list at [GitHub OWASP/ASVS v5.0.0](https://github.com/OWASP/ASVS/tree/v5.0.0/5.0/en)
- 17 chapters: V1 Encoding and Sanitization (§1.2 Injection Prevention), V2 Validation and Business Logic, V3 Web Frontend Security, V4 API and Web Service, V5 File Handling, V6 Authentication, V7 Session Management, V8 Authorization, V9 Self-contained Tokens, V10 OAuth and OIDC, V11 Cryptography, V12 Secure Communication, V13 Configuration, V14 Data Protection, V15 Secure Coding and Architecture, V16 Security Logging and Error Handling, V17 WebRTC. Requirement IDs are cited as `v5.0.0-<chapter>.<section>.<req>`.
- [V14 Data Protection](https://github.com/OWASP/ASVS/blob/v5.0.0/5.0/en/0x23-V14-Data-Protection.md): 14.1.1 (L2) verify "all sensitive data created and processed by the application has been identified" and classified (including Base64/JWT-encoded data); 14.1.2 (L2) "all sensitive data protection levels have a documented set of protection requirements" covering encryption, integrity, retention, logging, log access, database encryption, privacy controls; 14.2.4 (L2) those controls "are implemented as defined in the documentation for the specific data's protection level"; 14.2.6 (L3) return "only the minimum required sensitive data for the application's functionality" (e.g., partial card number); 14.2.7 (L3) "sensitive information is subject to data retention classification" with automatic/scheduled deletion of outdated data; 14.2.2 (L2) prevent caching of sensitive data in server components or purge it. **RECOMMENDED (L1–L3 verification levels)**

### Inferences
- For schema design, OWASP's guidance translates to: (a) a documented data-classification column/tag per attribute (ASVS 14.1.1/14.1.2) which then drives encryption, masking, retention and log-redaction decisions; (b) a role model with at least an application DML role (SELECT/INSERT/UPDATE/DELETE only, non-owner), a separate migration/DDL owner role, and a write-only logging role; (c) parameter binding as a non-negotiable in every data access path, including inside stored procedures and pipeline code that builds dynamic SQL.
- OWASP treats disk/TDE-style encryption as one layer whose value is bounded by threat model — this aligns with Microsoft's own TDE documentation (KQ5) and is the root of the "TDE marketing vs threat model" conflict (KQ6).

### Gaps
- The cheat sheets carry no visible last-updated dates; OWASP's pages do not show them. The Top 10:2025 landing/introduction pages do not state a release date (copyright "2021-2025"); I did not find an official dated release note.
- ASVS V11 (Cryptography) and V16 (Logging) requirement text was not opened; only chapter titles are verified.

## Key Question 2 — What do NIST SP 800-53 Rev. 5, SP 800-122, the Privacy Framework, SP 800-57, FIPS 140-3, SP 800-209, SP 800-188 and SP 800-88 define?

### Takeaway
NIST provides the control vocabulary: SP 800-53 Rev. 5 (20 families, incl. AC, AU, SC, MP and the privacy family PT) defines access enforcement, least privilege, event logging, audit protection and retention, at-rest protection, key management, media sanitization and minimization of PII in testing; SP 800-122 defines PII, a separate low/moderate/high PII confidentiality impact level driven by six factors, and distinguishes de-identified (reversible, separately stored key) from anonymized (irreversible) data; SP 800-57 defines cryptoperiods and key lifecycle; SP 800-88 Rev. 2 (Sept 2025) formally recognizes cryptographic erase as a purge technique subject to preconditions that bear directly on crypto-shredding designs.

### Cited Findings

**NIST SP 800-53 Rev. 5** — [SP 800-53 Rev. 5 (upd1) final](https://csrc.nist.gov/pubs/sp/800/53/r5/upd1/final) (September 2020, updates as of 12/10/2020; page notes Release 5.2.0 on 2025-08-27). Control text below extracted locally from the official PDF at nvlpubs.nist.gov (NIST.SP.800-53r5.pdf, 492 pp., "September 2020").
- Scope: "This publication provides a catalog of security and privacy controls for information systems and organizations"; 20 families including Access Control, Audit and Accountability, System and Communications Protection, Media Protection, and PII Processing and Transparency.
- AC-3 Access Enforcement: "Enforce approved authorizations for logical access to information and system resources in accordance with applicable access control policies." Discussion notes enforcement "can also be employed at the application and" service level. **MANDATORY for US federal systems; RECOMMENDED baseline elsewhere**
- AC-6 Least Privilege: "Employ the principle of least privilege, allowing only authorized accesses for users (or processes acting on behalf of users) that are necessary to accomplish assigned organizational tasks."
- AU-2 Event Logging: "Identify the types of events that the system is capable of logging in support of the audit function" and coordinate selection with other entities.
- AU-9 Protection of Audit Information: "Protect audit information and audit logging tools from unauthorized access, modification, and deletion" and alert designated roles on detection of such activity.
- AU-11 Audit Record Retention: "Retain audit records for [Assignment: organization-defined time period consistent with records retention policy] to provide support for after-the-fact investigations of incidents and to meet regulatory and organizational information retention requirements." Discussion: retain until no longer needed for "administrative, legal, audit, or other operational purposes", including FOIA, subpoenas and law enforcement.
- SC-28 Protection of Information at Rest: "Protect the [Selection (one or more): confidentiality; integrity] of the following information at rest"; discussion lists "databases" explicitly and says the focus "is not on the type of storage device or frequency of access but rather on the state of the information."
- SC-12 Cryptographic Key Establishment and Management: manage keys per organization-defined requirements "for key generation, distribution, storage, access, and destruction."
- MP-6 Media Sanitization: sanitize media "prior to disposal, release out of organizational control, or release for reuse" with mechanisms "commensurate with the security category or classification of the information."
- PM-25 Minimization of PII Used in Testing, Training, and Research: "Limit or minimize the amount of personally identifiable information used for internal testing, training, and research purposes." **RECOMMENDED (MANDATORY for federal)** — direct basis for masking non-production data.
- SI-12 Information Management and Retention: "Manage and retain information within the system and information output from the system in accordance with applicable laws, executive orders, directives, regulations, policies, standards, guidelines and operational requirements."

**NIST SP 800-122** — [SP 800-122 final](https://csrc.nist.gov/pubs/sp/800/122/final) (April 2010; McCallister, Grance, Scarfone). Body text extracted locally from the official PDF (nvlpubs.nist.gov/nistpubs/Legacy/SP/nistspecialpublication800-122.pdf).
- PII definition: "PII is any information about an individual maintained by an agency, including (1) any information that can be used to distinguish or trace an individual's identity, such as name, social security number, date and place of birth, mother's maiden name, or biometric records; and (2) any other information that is linked or linkable to an individual, such as medical, educational, financial, and employment information."
- "Organizations should categorize their PII by the PII confidentiality impact level." "The PII confidentiality impact level—low, moderate, or high—indicates the potential harm that could result to the subject individuals and/or the organization if PII were inappropriately accessed, used, or disclosed." It is "distinct from the confidentiality impact level described in FIPS 199". **RECOMMENDED**
- Six factors (§3.2): Identifiability; Quantity of PII ("Breaches of 25 records and 25 million records may have different impacts. The PII confidentiality impact level should only be raised and not lowered based on this factor"); Data Field Sensitivity ("SSN or financial account number is generally more sensitive than" phone/address); Context of Use (same fields may merit different levels — newsletter list vs undercover law-enforcement list); Obligation to Protect Confidentiality (laws such as the Privacy Act, Title 13/26 obligations); Access to and Location of PII.
- Safeguards (§4): operational (policy, training); privacy-specific — §4.2.1 "Minimizing the Use, Collection, and Retention of PII" (including a plan "to eliminate the unnecessary collection and use of SSNs"), §4.2.2 PIAs, §4.2.3 De-Identifying, §4.2.4 Anonymizing; security controls (§4.3) mapped to AC, AU, IA, MP, PL, RA, SC families.
- De-identified information: "records that have had enough PII removed or obscured, also referred to as masked or obfuscated, such that the remaining information does not identify an individual and there is no reasonable basis to believe that the information can be used to identify an individual." "De-identified information can be assigned a PII confidentiality impact level of low, as long as the following are both true: The re-identification algorithm, code, or pseudonym is maintained in a separate system, with appropriate controls in place to prevent unauthorized access to the re-identification information" (and the data elements are not themselves identifying). **RECOMMENDED — design implication: keep the pseudonym/key map in a separate system.**
- Anonymized information "is defined as previously identifiable information that has been de-identified and for which a code or other association for re-identification no longer exists." Use in testing: "If PII is used in the test environment, it is required to be protected at the same level that it is protected in the production" environment; anonymized data substitution "enables system testing while reducing the expense and added time of protecting PII" though "not all data can be readily anonymized (e.g., biometric data)."

**NIST Privacy Framework** — [NIST Privacy Framework](https://www.nist.gov/privacy-framework) (page n.d.; v1.0 PDF dated January 16, 2020; 1.1 Initial Public Draft listed). Functions extracted locally from the official v1.0 PDF (NIST.CSWP.01162020.pdf).
- "A voluntary tool developed in collaboration with stakeholders intended to help organizations identify and manage privacy risk." Structure: Core, Profiles, Implementation Tiers. "The five Functions, Identify-P, Govern-P, Control-P, Communicate-P, and Protect-P ... can be used to manage privacy risks arising from data processing"; "The Protect-P Function covers data protection to prevent cybersecurity-related privacy events, the overlap between privacy and cybersecurity risk management." **OPTIONAL/CONTEXTUAL (voluntary)**
- Version 1.1: per [NIST search results](https://www.nist.gov/privacy-framework/new-projects/privacy-framework-version-11) and [CSWP 40 ipd](https://csrc.nist.gov/pubs/cswp/40/nist-privacy-framework-11/ipd), the 1.1 initial public draft was released 14 April 2025 (comments closed 13 June 2025), realigns with CSF 2.0 and adds an AI/privacy section; a final 1.1 was not confirmed as published as of this research (search snippets only; pages not opened).

**NIST SP 800-57 Part 1 Rev. 5** — [SP 800-57 Pt. 1 Rev. 5](https://csrc.nist.gov/pubs/sp/800/57/pt1/r5/final) (May 2020; Elaine Barker). Text extracted locally from the official PDF.
- "A cryptoperiod is the time span during which a specific key is authorized for use by legitimate entities or the keys for a given system will remain in effect." A suitably defined cryptoperiod "Limits the amount of information that is available for cryptanalysis", "Limits the amount of exposure if a single key is compromised", limits algorithm lifetime, limits time for attacks on key-protection mechanisms, and "Limits the time available for computationally intensive cryptanalysis." Keywords include "split knowledge" (key split into n shares), key recovery, key transport. Security-strength tables reference a minimum of 112 bits with "at least 128 bits in 2031". **RECOMMENDED (MANDATORY for federal)**

**FIPS 140-3** — [FIPS 140-3](https://csrc.nist.gov/pubs/fips/140-3/final) (March 22, 2019; supersedes FIPS 140-2)
- "provides four increasing, qualitative levels of security intended to cover a wide range of potential applications and environments"; aligned with ISO/IEC 19790:2012 / 24759 via the SP 800-140x series. Relevance: PCI DSS, HIPAA NPRM and SP 800-88 CE all point to validated cryptography; SP 800-88 Rev. 2 says federal agencies "must use encryption modules validated to the current FIPS-140 standard" for CE assurance. **MANDATORY for US federal; RECOMMENDED selection criterion elsewhere**

**NIST SP 800-209** — [SP 800-209 Security Guidelines for Storage Infrastructure](https://csrc.nist.gov/pubs/sp/800/209/final) (October 2020; Chandramouli, Pinhas)
- "The main focus of this document is to provide a comprehensive set of security recommendations" covering general areas (physical security, authentication/authorization, change management, configuration control, incident response) and storage-specific areas "(e.g., data protection, isolation, restoration assurance, and encryption)." Only the abstract page was opened. **RECOMMENDED**

**NIST SP 800-188** — [SP 800-188 De-Identifying Government Datasets](https://csrc.nist.gov/pubs/sp/800/188/final) (September 2023; Garfinkel, Guttman, Near, Dajani, Singer)
- Agencies should define goals, assess release risk, choose a data-sharing model; techniques: removing identifiers, transforming quasi-identifiers, synthetic data from models; keywords include k-anonymity, differential privacy, pseudonymization. "Agencies can create a Disclosure Review Board to oversee the process of de-identification" and "can also adopt a de-identification standard with measurable performance levels and perform re-identification studies to gauge the risk." Warning: "not all tools that merely mask personal information provide sufficient functionality for performing de-identification." **RECOMMENDED**

**NIST SP 800-88 Rev. 2** — [SP 800-88 Rev. 2 Guidelines for Media Sanitization](https://csrc.nist.gov/pubs/sp/800/88/r2/final) (September 2025; Chandramouli, Hibbard; supersedes Rev. 1 of 2014). Body text extracted locally from the official PDF.
- Cryptographic erase (CE): "At a basic level, CE is based on the sanitization of keys used to encrypt data or to prevent access to the keys that encrypt data. Thus, with CE, sanitization can be performed with high assurance much faster than with other sanitization techniques." "Of the logical purge sanitization techniques, cryptographic erase is noteworthy in its ability to rapidly sanitize target data." For "virtual/logical storage (e.g., cloud storage), cryptographic erase may be the only viable purge sanitization technique option."
- Preconditions: "As a pre-condition for using CE, ISO/IEC 27040 specifies that no sensitive data has previously been stored on the ISM in plaintext form (i.e., not encrypted) as CE can only sanitize keys related to encrypted data." "Sanitization using CE should not be trusted on ISM that have been backed up or escrowed unless the organization has a high level of confidence regarding how and where the keys were stored and managed outside of the ISM." Traceability of CE operations should be recorded (§3.2.5). **RECOMMENDED; preconditions are MANDATORY for CE to be valid**

### Inferences
- SP 800-122's "separate system for the re-identification key" and SP 800-88's "keys never escrowed/backed up without control" are the two design constraints that make crypto-shredding (per-subject keys) defensible: the key store must be physically/logically separate from the data store, backups of keys must be governed, and the data must have been encrypted from first write.
- SP 800-53 PM-25 plus SP 800-122 §4.2.4 together form the standards basis for masking/anonymizing non-production data rather than copying production PII.

### Gaps
- SP 800-53 Release 5.2.0 (Aug 2025) new/revised controls were not reviewed; text quoted is Rev. 5 (Sept 2020 PDF).
- SP 800-209 body recommendations and NIST Privacy Framework 1.1 final status not verified from opened pages.

## Key Question 3 — What do the CIS Benchmarks for PostgreSQL, MySQL, SQL Server, Oracle and MongoDB cover?

### Takeaway
CIS publishes consensus, version-specific hardening benchmarks for every major database engine (and cloud database services and Snowflake); the official index page confirms current coverage but the benchmark PDFs themselves (which contain the installation/logging/access-control/encryption sections and Level 1/Level 2 profiles) require CIS registration and were not opened.

### Cited Findings
- [CIS Benchmarks](https://www.cisecurity.org/cis-benchmarks) (n.d.): "The CIS Benchmarks® are prescriptive configuration recommendations for more than 25+ vendor product families" and "represent the consensus-based effort of cybersecurity experts globally." **RECOMMENDED** (OWASP's Database Security Cheat Sheet points to CIS Benchmarks as the hardening baseline; PCI DSS requires industry-accepted hardening standards — the PCI SAQ text was not read for that requirement, so treat as RECOMMENDED here.)
- Database benchmarks listed with versions: PostgreSQL 9.5–18 (PostgreSQL 18 v1.0.0, 17 v1.1.0, 16 v1.1.0, 15 v1.2.0, 14 v1.3.0, 13 v1.4.0); Oracle MySQL Community and Enterprise 5.6–9.7 (9.7 v1.0.0, 8.4 v1.1.0, 8.0 Enterprise v1.5.0/Community v1.2.0); Microsoft SQL Server 2008 R2–2025 (2025 v1.0.0, 2022 v1.3.0, 2019 v1.6.0); Oracle Database 11g R2–26ai (26ai v1.0.0, 23ai v1.1.0, 19c v2.0.0); MongoDB 3.2–8 (8 v2.0.0, 7 v2.0.0); MariaDB 10.6/10.11; IBM Db2; Apache Cassandra; CockroachDB; YugabyteDB; SingleStore; Snowflake Foundations v2.0.1; AWS Database Services v2.0.0 and Microsoft Azure Database Services v2.0.0. DISA STIG-aligned variants exist for SQL Server 2016/2022, Oracle 12c and MariaDB Enterprise.
- Older unsupported versions are archived on CIS WorkBench.

### Inferences
- Because a benchmark exists per engine major version (e.g., PostgreSQL 18 v1.0.0, SQL Server 2025 v1.0.0, MongoDB 8 v2.0.0), schema/platform teams should pin the benchmark version in their hardening baseline alongside the engine version in migration tooling.

### Gaps
- Level 1/Level 2 profile definitions and the section structure (installation and patches, logging/auditing, access and authorization, encryption, etc.) were not visible on the public index page; benchmark PDFs are gated behind CIS registration and were not opened. Do not cite specific CIS recommendation numbers from these notes.

## Key Question 4 — Regulations and their schema implications (GDPR, CCPA/CPRA, HIPAA, PCI DSS, SOX)

### Takeaway
The regulations converge on four schema-level obligations: classify and minimize personal data (GDPR Art. 5(1)(c), Art. 25; CCPA sensitive PI), protect it with pseudonymisation/encryption and access control (GDPR Art. 32; HIPAA §164.312; PCI DSS Req. 3), keep tamper-protected audit logs for defined periods (PCI DSS Req. 10 — 12 months; HIPAA audit controls; SOX §802/§404 record integrity), and support deletion rights (GDPR Art. 17; CCPA §1798.105) subject to explicit legal-obligation and legal-claims exceptions — which is where the erasure-vs-immutability conflict is legally resolved rather than merely technically.

### Cited Findings

**GDPR — Regulation (EU) 2016/679** — [EUR-Lex 32016R0679](https://eur-lex.europa.eu/eli/reg/2016/679/oj) (Regulation of 27 April 2016). Quotes from the official EUR-Lex text:

### Inferences
- GDPR Art. 17(3)(b)/(e) and CCPA's deletion exceptions mean an immutable financial/audit ledger is not an Art. 17 violation when retention is legally required (SOX §802/§1520, PCI DSS 10.5.1) — but the controller must be able to demonstrate (Art. 5(2), Art. 30) which legal basis justifies each retained field. Schema implication: retention basis should be a modeled attribute (per table or per column class), not tribal knowledge.
- PCI DSS 3.5.1 makes the tokenization/truncation/hash/encrypt choice a schema decision per column, and 3.5.1.2 explicitly disqualifies disk-level encryption alone — see Conflicts (KQ6).
- HIPAA's encryption is currently "addressable" (document a rationale if not implemented); the 2025 NPRM would make it required. Design for encryption as if required.

## Key Question 5 — Patterns: RLS, column vs TDE vs application-layer encryption, Always Encrypted, masking, tokenization, crypto-shredding, least-privilege roles, PII separation and tagging, audit tooling, secrets, multi-tenant isolation, non-production masking

### Takeaway
Vendor documentation is unusually candid about limits: PostgreSQL and SQL Server RLS are default-deny predicate systems whose bypass rules (superuser/BYPASSRLS/owner; sysadmin/db_owner, CDC, statistics, indexed views) and side channels (error-based inference, referential-integrity leaks, non-leakproof functions) must be designed around; Microsoft states TDE protects only data at rest and that dynamic data masking "shouldn't be used alone"; Always Encrypted protects against DBAs but forbids range queries and most constraints (deterministic encryption trades pattern leakage for equality/joins/indexes); catalog tags (Snowflake, Unity Catalog, BigQuery policy tags) make PII classification machine-enforceable via tag-driven masking and column ACLs; pgAudit, SQL Server Audit and Oracle Unified Audit provide object-level audit but cannot reliably audit their own superusers; and both AWS and Azure warn that RLS-based tenant isolation requires propagating tenant identity on every query and that many solutions avoid it for that reason.

### Cited Findings

**Row-level security**
- [PostgreSQL 18: Row Security Policies](https://www.postgresql.org/docs/current/ddl-rowsecurity.html) (PostgreSQL 18.6 docs, n.d.): "When row security is enabled on a table (with ALTER TABLE ... ENABLE ROW LEVEL SECURITY), all normal access to the table for selecting rows or modifying rows must be allowed by a row security policy." "If no policy exists for the table, a default-deny policy is used, meaning that no rows are visible or can be modified." Policies combine "using either OR (for permissive policies, which are the default) or using AND (for restrictive policies)". USING governs visible/targetable rows, WITH CHECK governs inserted/updated rows. Bypass: superusers and BYPASSRLS roles always; "Table owners normally bypass row security as well, though a table owner can choose to be subject to row security with ALTER TABLE ... FORCE ROW LEVEL SECURITY"; referential-integrity checks bypass RLS, so "care must be taken when developing schemas and row level policies to avoid 'covert channel' leaks of information through such referential integrity checks." Only leakproof functions may be evaluated before the policy. `row_security = off` does not bypass — it errors if a policy would filter (safe for pg_dump). Policies consulting other tables can race under READ COMMITTED; mitigations: `SELECT ... FOR SHARE` in subqueries, SECURITY DEFINER functions. Performance: "the policy expressions consider only the current values in the row ... This is the simplest and best-performing case; when possible, it's best to design row security applications to work this way." Examples use `current_user`; a `current_setting('app.tenant_id')` pattern is common practice but is NOT in the official page. **RECOMMENDED (FORCE ROW LEVEL SECURITY and restrictive policies for defence in depth)**
- [SQL Server Row-Level Security](https://learn.microsoft.com/en-us/sql/relational-databases/security/row-level-security) (ms.date 2025-09-11): filter predicates "silently filter the rows available to read operations"; block predicates "explicitly block write operations" (AFTER INSERT/UPDATE, BEFORE UPDATE/DELETE); implemented via `CREATE SECURITY POLICY` and inline table-valued functions; "Security policies apply to all users, including dbo users in the database" (but dbo can alter/drop policies, which can be audited); "If high privileged users, such as sysadmin or db_owner, need to see all rows ... the security policy must be written to allow that." Multi-tenant middle-tier pattern: app sets `SESSION_CONTEXT` after connecting (`sp_set_session_context @key=N'UserId', @value=..., @read_only=1`) and the predicate checks `DATABASE_PRINCIPAL_ID() = DATABASE_PRINCIPAL_ID('AppUser') AND CAST(SESSION_CONTEXT(N'UserId') AS int) = @AppUserId`; column `DENY UPDATE ON Sales(AppUserId)` prevents re-homing rows. Best practices: separate schema for RLS objects; `ALTER ANY SECURITY POLICY` for a security-policy manager role; avoid type conversions, recursion, excessive joins, and session-SET-dependent logic. Side channels: a malicious policy manager can exfiltrate via crafted predicates; "SELECT 1/(SALARY-100000) FROM PAYROLL WHERE NAME='John Doe'" leaks via divide-by-zero. Cross-feature leaks: DBCC SHOW_STATISTICS (restricted), Change Data Capture "can leak entire rows", Change Tracking leaks primary keys, indexed views cannot be built over RLS tables, temporal history tables need their own predicate; Fabric/Synapse support filter predicates only. **RECOMMENDED**
- [Oracle 2 Day + Security Guide 12.2: Restricting Access with Oracle Virtual Private Database](https://docs.oracle.com/en/database/oracle/oracle-database/12.2/tdpsg/restricting-access-with-oracle-virtual-private-database.html) (n.d.): "Oracle Virtual Private Database (VPD) enables you to dynamically add a WHERE clause in any SQL statement that a user executes"; policy managed "at the database table or view level, which means that you do not modify the applications"; attach with `DBMS_RLS.ADD_POLICY`; predicate can use `SYS_CONTEXT('userenv','session_user')`; policy types include CONTEXT_SENSITIVE (re-evaluated when context changes). Per the [Oracle 19c Security Guide VPD chapter](https://docs.oracle.com/en/database/oracle/oracle-database/19/dbseg/using-oracle-vpd-to-control-data-access.html) (TOC page opened): "A VPD policy uses a function to generate the dynamic WHERE clause, and a policy to attach the function to objects to protect"; per search snippet (not opened) the EXEMPT ACCESS POLICY privilege bypasses VPD. **RECOMMENDED**

**Encryption placement: TDE vs Always Encrypted vs application layer**
- [SQL Server Transparent Data Encryption](https://learn.microsoft.com/en-us/sql/relational-databases/security/encryption/transparent-data-encryption) (ms.date 2025-09-07): "TDE protects data at rest, which is the data and log files"; threat addressed: "a malicious party who steals physical media like drives or backup tapes can restore or attach the database and browse its data"; "TDE doesn't provide encryption across communication channels"; page-level real-time I/O encryption; key hierarchy DPAPI → service master key → database master key → certificate/EKM asymmetric key → database encryption key (AES/3DES); "Backup files for databases that have TDE enabled are also encrypted with the DEK ... Data loss results if the certificates are no longer available"; FILESTREAM and buffer pool extension files are not encrypted; replication does not carry encryption automatically. Nothing on the page claims protection against authorized/privileged users querying the database. **OPTIONAL/CONTEXTUAL (at-rest/physical-theft threat model)**
- [SQL Server Always Encrypted](https://learn.microsoft.com/en-us/sql/relational-databases/security/encryption/always-encrypted-database-engine) (ms.date 2026-01-28): "You can encrypt sensitive data within client applications, ensuring that encryption keys are never exposed to the Database Engine. This approach provides a separation between those who own the data and can view it, and those who manage the data but should have no access: on-premises database administrators, cloud database operators, or other high-privileged unauthorized users." Keys: column encryption keys (encrypt data) and column master keys (key-protecting keys stored "in a trusted key store outside of the database system, such as Azure Key Vault, Windows certificate store, or a hardware security module"); "The Database Engine doesn't store or use any keys in plaintext." "Deterministic encryption always generates the same encrypted value for a given plaintext value. By using deterministic encryption, you can perform point lookups, equality joins, grouping, and indexing on encrypted columns. However, unauthorized users might guess information about encrypted values by examining patterns." "Randomized encryption ... Each identical plaintext input results in a distinct encrypted output." Limits: no sorting/filtering except equality on deterministic columns; no comparisons between encrypted and plaintext; literals cannot be inserted (must use parameters); unsupported on IDENTITY, computed, sparse, FILESTREAM, full-text, partitioning columns, columns with CHECK or DEFAULT constraints, randomized-encrypted PK/unique/FK/index columns, CDC-tracked columns, DDM-masked columns; string columns must use `_BIN2` collations; key rotation/re-encryption must happen outside the engine (unless using secure enclaves, SQL Server 2019+/Azure SQL, which allow in-place encryption, pattern matching, range comparisons). **OPTIONAL/CONTEXTUAL (insider/DBA threat model)**
- [MongoDB Security Checklist](https://www.mongodb.com/docs/manual/administration/security-checklist/) (9.0 docs, n.d.): encryption at rest via WiredTiger or "file-system, device, or physical encryption (for example dm-crypt)"; Client-Side Field Level Encryption or Queryable Encryption to encrypt fields "application-side prior to transmitting data over the wire to the server"; "Enable access control and specify an authentication mechanism"; "Create a unique MongoDB user for each person/application"; "Follow the principle of least privilege"; "Configure MongoDB to use TLS/SSL for all incoming and outgoing connections"; limit network exposure (`net.bindIp`, `authenticationRestrictions`); "Audit records permit forensic analysis" (Enterprise); run with a dedicated OS user; disable server-side scripting (`--noscripting`) if unused; "Review MongoDB database users and periodically rotate them." **RECOMMENDED**

**Dynamic data masking**
- [SQL Server Dynamic Data Masking](https://learn.microsoft.com/en-us/sql/relational-databases/security/dynamic-data-masking) (ms.date 2025-06-30): masks default/email/random/partial/datetime applied in query results; "With DDM, the data in the database isn't changed"; UNMASK permission grantable at database/schema/table/column level (SQL Server 2022+); "Users with CONTROL SERVER or CONTROL at the database level could view masked data in its original form." Security note: "Dynamic data masking doesn't aim to prevent database users from connecting directly to the database and running exhaustive queries that expose pieces of the sensitive data"; example `WHERE Salary > 99999 and Salary < 100001` infers the masked value; "dynamic data masking shouldn't be used alone to fully secure sensitive data from users running ad hoc queries ... It's appropriate for preventing accidental sensitive data exposure, but doesn't protect against malicious intent." Cannot be combined with Always Encrypted columns; `SELECT INTO` by a non-UNMASK user copies masked data (statically masked target). **OPTIONAL/CONTEXTUAL — never a substitute for access control or encryption**
- [BigQuery column-level access control](https://docs.cloud.google.com/bigquery/docs/column-level-security-intro) (n.d.): "Data masking lets you mask sensitive data by substituting null, default, or hashed content in place of the column's actual value", layered on policy tags. 

**PII tagging in catalogs**
- [Snowflake Object Tagging](https://docs.snowflake.com/en/user-guide/object-tagging) (n.d.): "A tag is a schema-level object that can be assigned to another Snowflake object"; tag-based masking: "assign a masking policy to a tag, then assign that tag to a table or column" so "the tagged column is automatically protected by the masking policy" (Enterprise Edition+); classification can auto-set a tag "on a column that was classified as containing sensitive data"; inheritance: "if a tag is set on a table, the tag will be inherited by all columns in that table"; propagation to dependent views/CTAS targets; lineage via `apply_method` in TAG_REFERENCES; governance roles: "you can create a tag_admin custom role that creates and applies tags"; quotas 50 tags/object. Row access policies complement masking. **RECOMMENDED**
- [Databricks Unity Catalog tags](https://docs.databricks.com/aws/en/data-governance/unity-catalog/tags) (n.d.): tags on catalogs, schemas, tables, columns, volumes, views, functions, models; "Governed tags are account-level tags with enforced rules for consistency and control" (only permitted principals can assign; values constrained by tag policy); used for ABAC — "tags applied at one level of the Unity Catalog object model automatically apply to all objects beneath it" during policy evaluation (not down to column level); warning: "Tag data is stored as plain text and may be replicated globally" — do not put personal data in tag values; limits 50 tags/securable, 1,000 column tags/table; dropping a column with governed tags fails until tags are removed. **RECOMMENDED**
- [BigQuery column-level access control](https://docs.cloud.google.com/bigquery/docs/column-level-security-intro) (n.d.): "Create and manage a taxonomy and policy tags for your data"; "A policy tag hierarchy can be no more than five levels deep"; one policy tag per column; readers need the Fine-Grained Reader role on the tag or `SELECT *` fails (use `SELECT * EXCEPT (ssn)`); "Enforcing access control causes the access restrictions defined for all of the policy tags in the taxonomy to be applied"; works "in addition to existing dataset ACLs"; limits: 1,000 unique policy tags per table, no legacy SQL, taxonomies regional and same-organization. **RECOMMENDED**

**Audit logging tools**
- [pgAudit](https://github.com/pgaudit/pgaudit) (n.d.): "provides detailed session and/or object audit logging via the standard PostgreSQL logging facility" to meet "government, financial, or ISO certifications"; "The standard logging facility shows what the user requested, while pgAudit focuses on the details of what happened while the database was satisfying the request" (e.g., CREATE TABLE inside a DO block); classes READ, WRITE, FUNCTION, ROLE, DDL, MISC, MISC_SET via `pgaudit.log`; object auditing via `pgaudit.role` (SELECT/INSERT/UPDATE/DELETE on relations the role has rights to); "pgAudit supports PostgreSQL 14 or greater"; "Audit logging is best-effort and not transactional"; "not possible to reliably audit superusers with pgAudit". **RECOMMENDED**
- [SQL Server Audit (Database Engine)](https://learn.microsoft.com/en-us/sql/relational-databases/security/auditing/sql-server-audit-database-engine) (ms.date 2026-04-15): server audit → server audit specification (one per audit) + database audit specifications (one per database per audit), built on Extended Events; action groups and object-level audit actions; targets file, Windows Security log or Application log ("Any authenticated user can read and write to the Windows Application event log ... less secure"); tamper mitigation via file ACLs (service account RW, audit admins RW, readers R), BitLocker/EFS, and reporting from a separate instance; `ON_FAILURE = SHUTDOWN` option; "Members of the sysadmin fixed server role are identified as the dbo user ... To audit actions of the administrators, audit the actions of the dbo user"; caution: "Principals in the sysadmin role can tamper with any audit component". All editions support database-level audit since SQL Server 2016 SP1. **RECOMMENDED**
- [Oracle 19c Introduction to Auditing (Unified Auditing)](https://docs.oracle.com/en/database/oracle/oracle-database/19/dbseg/introduction-to-auditing.html) (n.d.): unified audit trail in `AUDSYS.AUD$UNIFIED` exposed via `UNIFIED_AUDIT_TRAIL`; "The unified audit trail table AUD$UNIFIED is a specialized table ... which allows only INSERT activity. Any attempt to directly truncate, delete or update contents of the AUD$UNIFIED table fail, and generate audit records"; predefined policies ORA_SECURECONFIG and ORA_LOGON_FAILURES enabled by default; "Oracle Database has mandatory audits that cannot be turned off"; roles AUDIT_ADMIN ("Grant this role only to trusted users") and AUDIT_VIEWER (external auditors); captures database and non-database (CLIENT_IDENTIFIER) users; fine-grained audit policies; purge via DBMS_AUDIT_MGMT. **RECOMMENDED**

**Secrets management** — covered by OWASP (KQ1): credentials never in code/repos; keys in HSM/KMS/secrets manager, not env vars; keys separated from data; Always Encrypted column master keys in Key Vault/HSM; Databricks tags and Snowflake tags must not themselves hold secrets/PII. **RECOMMENDED**

**Multi-tenant isolation**
- [Azure Architecture Center: Architectural approaches for storage and data in multitenant solutions](https://learn.microsoft.com/en-us/azure/architecture/guide/multitenant/approaches/storage-data) (ms.date 2026-08-21): isolation levels span shared database/containers, database per tenant, sharding, deployment stamps, geodes; isolate (or group) tenants when "Tenants need to use their own encryption keys", have "individual backup and restore policies", or need different geographies. Antipatterns: "Table-based isolation ... avoid creating individual tables for each tenant ... Instead, consider using a single set of multitenant tables with a tenant identifier column"; "Column-level tenant customization"; "Manual schema changes ... build tooling or an automated pipeline to deploy your schema changes ... Track the schema version that you use for each tenant"; "Version dependencies ... ensure that your application version is backwards-compatible with at least one previous schema version, and sequence destructive schema changes across multiple versions to support rollbacks." On RLS: "you need to ensure that the user's identity and tenant identity are propagated through the application and into the data store with each query. This approach can be complex to design, implement, test, and maintain. Many multitenant solutions don't use row-level security because of those complexities." Tenant-level encryption via Always Encrypted / customer-managed keys; "Automate tenant onboarding, migration, data retention, and offboarding processes." **RECOMMENDED**
- [AWS Well-Architected SaaS Lens: Tenant Isolation](https://docs.aws.amazon.com/wellarchitected/latest/saas-lens/tenant-isolation.html) (publication date April 4, 2023): "Tenant isolation is one of the foundational topics that every SaaS provider must address ... Crossing this boundary in any form would represent a significant and potentially unrecoverable event for a SaaS business"; "the strategies and approaches to achieving this isolation are not universal" (domain, compliance, deployment model, services); "each SaaS architecture needs to ensure that it has put in place the constructs that are needed to ensure that each tenant's resources have been effectively isolated." The standalone whitepaper [SaaS Tenant Isolation Strategies — Core isolation concepts](https://docs.aws.amazon.com/whitepapers/latest/saas-tenant-isolation-strategies/core-isolation-concepts.html) (URL from search; fetch returned the SaaS Lens landing page, and search notes the whitepaper is marked for historical reference) describes silo (fully separate stack per tenant), pool (shared infrastructure; "an outage will likely impact all the tenants"), bridge (hybrid, e.g., pooled web tier with siloed storage) and tier-based isolation. **RECOMMENDED**

**Data masking in non-production** — NIST SP 800-53 PM-25 ("Limit or minimize the amount of personally identifiable information used for internal testing, training, and research"), SP 800-122 §4.2.4 (anonymized substitution for testing; otherwise test PII "is required to be protected at the same level" as production), PCI DSS 6.5.6 ("Live PANs are not used in pre-production environments"), OWASP Database Security ("Use separate databases and accounts for development, UAT, and production"), and SQL Server DDM's note that `SELECT INTO` by a non-UNMASK user yields a statically masked copy. **MANDATORY for PAN (PCI); RECOMMENDED otherwise**

### Inferences
- A least-privilege role model consistent with all sources: (1) `app_rw` — SELECT/INSERT/UPDATE/DELETE on application tables only, not owner, RLS enforced (PostgreSQL FORCE ROW LEVEL SECURITY protects even owners); (2) `migrator` — DDL owner used only by the deployment pipeline (Azure: automated, versioned schema changes); (3) `readonly_analyst` — SELECT via views/masked columns/policy tags; (4) `audit_writer` — INSERT-only on log tables (OWASP), mirroring Oracle's INSERT-only AUD$UNIFIED; (5) `security_policy_mgr` — ALTER ANY SECURITY POLICY / tag_admin, without SELECT on protected tables (SQL Server, Snowflake).
- Separating PII into dedicated tables/schemas (keyed by a surrogate/pseudonym) directly operationalizes GDPR Art. 4(5)/EDPB "additional information kept separately", SP 800-122's "separate system" for re-identification keys, and simplifies Always Encrypted/CSFLE scope (fewer constraints to fight) and RLS/VPD scoping.
- Crypto-shredding (per-subject DEK, envelope-wrapped by a KEK in KMS/HSM; delete the DEK to erase) is supported in principle by OWASP's key-ID-tagging rotation strategy and NIST SP 800-88 CE, but only if the SP 800-88 preconditions hold: data encrypted from first write, keys never backed up/escrowed outside controlled stores, and CE operations traceable. None of the opened sources explicitly uses the term "crypto-shredding"; this is an inference.

### Gaps
- No opened official source defines "crypto-shredding" or endorses per-subject keys as GDPR erasure; this remains an engineering inference from SP 800-88 CE + EDPB/Art. 4(5).
- Oracle VPD exemptions (EXEMPT ACCESS POLICY) and column-level VPD (`sec_relevant_cols`) come from search snippets/older references, not an opened current page.
- Tokenization vaults, Snowflake classification system tags (SEMANTIC_CATEGORY/PRIVACY_CATEGORY), Unity Catalog row filters/column masks, and BigQuery row-level security interaction were not opened in detail.

## Key Question 6 — Conflicts: immutable audit logs vs right to erasure; soft-delete vs erasure; encryption vs indexability; TDE marketing vs threat model

### Takeaway
The conflicts are real but each has a source-grounded resolution: erasure yields to documented legal-retention obligations (GDPR Art. 17(3)(b)/(e); SOX §802; PCI 10.5.1) and otherwise is satisfied by true erasure or key destruction, not soft-delete flags; encryption's cost to query capability is explicit in Microsoft's deterministic/randomized trade-off; and TDE's value is explicitly bounded to at-rest/physical-media threats by Microsoft, OWASP and PCI DSS.

### Cited Findings
- **Immutable audit logs vs erasure.** OWASP: logs must not be destroyed "before the duration of the required data retention period" and should exclude PII in the first place ([Logging Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html)). PCI DSS 10.3/10.5.1 require logs "protected to prevent modifications" and retained "at least 12 months" ([SAQ D v4.0](https://listings.pcisecuritystandards.org/documents/PCI-DSS-v4-0-SAQ-D-Merchant.pdf)). SOX §802/18 U.S.C. §1519 criminalizes knowingly destroying or altering records to obstruct federal matters ([PLAW-107publ204](https://www.govinfo.gov/content/pkg/PLAW-107publ204/html/PLAW-107publ204.htm)). GDPR Art. 17(3)(b) and (e) carve out processing necessary for a legal obligation or legal claims ([EUR-Lex](https://eur-lex.europa.eu/eli/reg/2016/679/oj)); CCPA's deletion right is "subject to some exceptions" ([CPPA FAQ](https://cppa.ca.gov/faq.html)). Resolution: **MANDATORY** to keep legally required records; **MANDATORY** to erase everything else on request; **RECOMMENDED** to design logs to reference subjects by pseudonym so the identifying "additional information" (EDPB) can be erased while the immutable log stays.
- **Soft-delete vs erasure.** GDPR Art. 17 requires that data be erased; Art. 5(1)(e) requires data be "kept in a form which permits identification of data subjects for no longer than is necessary"; Recital 26 exempts only data "rendered anonymous in such a manner that the data subject is not or no longer identifiable." A soft-delete flag keeps identifiable data and therefore does not satisfy erasure (inference from the quoted text; no source addresses "soft delete" by name). NIST SP 800-88 Rev. 2 treats CE (key destruction) as a valid purge technique only if the data was never stored in plaintext and keys were not escrowed/backed up uncontrolled ([SP 800-88r2](https://csrc.nist.gov/pubs/sp/800/88/r2/final)). **MANDATORY: soft-delete alone is insufficient for erasure obligations.**
- **Encryption vs indexability/searchability.** Microsoft: deterministic encryption permits "point lookups, equality joins, grouping, and indexing" but "unauthorized users might guess information about encrypted values by examining patterns ... especially if there's a small set of possible encrypted values"; randomized encryption permits none of these without secure enclaves; no range/LIKE queries; many constraint types unsupported ([Always Encrypted](https://learn.microsoft.com/en-us/sql/relational-databases/security/encryption/always-encrypted-database-engine)). PCI DSS permits keyed one-way hashes/index tokens for lookups ([SAQ D 3.5.1](https://listings.pcisecuritystandards.org/documents/PCI-DSS-v4-0-SAQ-D-Merchant.pdf)) and warns that co-existing hashed and truncated forms must not be correlatable. DDM preserves indexability but is bypassable by inference ([DDM](https://learn.microsoft.com/en-us/sql/relational-databases/security/dynamic-data-masking)). **OPTIONAL/CONTEXTUAL: choose per column based on required query operators.**
- **TDE marketing vs threat model.** Microsoft's own TDE page scopes TDE to "data at rest, which is the data and log files" against media theft and states it "doesn't provide encryption across communication channels" ([TDE](https://learn.microsoft.com/en-us/sql/relational-databases/security/encryption/transparent-data-encryption)); Always Encrypted exists precisely to protect against "database administrators, cloud database operators, or other high-privileged" users that TDE does not. OWASP: hardware/disk encryption "does nothing if an attacker compromises the system remotely"; layer choice "will depend on the threat model" ([Cryptographic Storage](https://cheatsheetseries.owasp.org/cheatsheets/Cryptographic_Storage_Cheat_Sheet.html)). PCI DSS 3.5.1.2: if "disk-level or partition-level encryption (rather than file-, column-, or field-level database encryption)" is used, PAN must be "also rendered unreadable via another mechanism" ([SAQ D](https://listings.pcisecuritystandards.org/documents/PCI-DSS-v4-0-SAQ-D-Merchant.pdf)). HIPAA currently lists encryption as Addressable but the 2025 NPRM would require it ([govinfo CFR §164.312](https://www.govinfo.gov/content/pkg/CFR-2024-title45-vol2/xml/CFR-2024-title45-vol2-sec164-312.xml); [NPRM](https://www.govinfo.gov/content/pkg/FR-2025-01-06/html/2024-30983.htm)). **Conflict between vendor positioning ("lets you follow many laws, regulations, and guidelines") and PCI's explicit insufficiency of disk-level encryption for PAN: resolve as TDE = RECOMMENDED baseline for at-rest; column/application-layer protection = MANDATORY for PAN and RECOMMENDED for high-impact PII.**
- **RLS as tenant isolation vs operational complexity.** SQL Server and PostgreSQL document RLS as a multitenant mechanism, while Azure's architecture guidance says "Many multitenant solutions don't use row-level security because of those complexities" and recommends tenant-identifier columns with automated schema versioning ([Azure](https://learn.microsoft.com/en-us/azure/architecture/guide/multitenant/approaches/storage-data)). Not a contradiction in requirement, but a divergence in recommendation strength: **OPTIONAL/CONTEXTUAL**.

### Inferences
- The regulations never require that a system be unable to delete; they require that specific records be retained and provably unaltered. Append-only audit tables (Oracle's INSERT-only AUD$UNIFIED is the model), write-only log roles, and pseudonymous subject references reconcile immutability with erasure.
- "Encryption at rest" should be stated in design docs with its threat model; claiming regulatory compliance from TDE alone is contradicted by PCI DSS 3.5.1.2 and by Microsoft's own scoping.

### Gaps
- No regulator text opened addresses soft-delete explicitly or endorses crypto-shredding as Art. 17 erasure; EDPB's pseudonymisation guidelines are still a consultation version. Treat these as well-grounded inferences, not settled law.
