## KQ1. Evolutionary database design, migrations, and zero-downtime change patterns

### Takeaway
The originating authors (Sadalage & Fowler 2016; Ambler & Sadalage 2006) define the discipline as: every schema/data/access-code change is a small, numbered, version-controlled migration script, applied by a tool that tracks what has run; incompatible changes go through a *transition period* in which old and new schema coexist (Parallel Change / expand–contract). The large operators (GitLab, Stripe, Braintree) turn this into concrete lock-time budgets (seconds, not minutes), multi-release sequences for renames/drops/NOT NULL/foreign keys, and tooling that rejects unsafe DDL; PostgreSQL's own documentation supplies the lock-level facts that make specific operations dangerous.

### Cited Findings

**Originators: evolutionary database design and refactoring**
- Sadalage & Fowler's rewritten article (May 2016; original Jan 2003) lists the practices: DBAs collaborate closely with developers; "all database artifacts are version controlled with application code"; "every change to the database [is represented] as a database migration script" tracked by a changelog table; each developer has an individual database instance rebuilt on demand; database changes are integrated continuously (rule of thumb: at least daily); the database is "schema plus data" (reference and test data under version control); changes are refactorings that alter schema, migrate data and update access code together; migrations are automated; data access code is in a clearly separated layer; releases are frequent. "Our usual rule is to make each database change as small as possible... The smaller it is, the easier it is to get right, and any errors are quick to spot and debug." — [Evolutionary Database Design](https://martinfowler.com/articles/evodb.html) (May 2016). **MANDATORY** (migration scripts in VCS, small changes, applied by tool); **RECOMMENDED** (per-developer sandbox; daily integration).
- Transition phase defined as "a period of time when the database supports both the old access pattern and the new ones simultaneously." "Views are one technique to enable transition phases" (e.g., `CREATE VIEW customer AS SELECT id, first_name, last_name FROM client;` after a rename); triggers are "handy for things like" renaming a column. — [Evolutionary Database Design](https://martinfowler.com/articles/evodb.html) (May 2016).
- Parallel Change ("expand and contract") is "a pattern to implement backward-incompatible changes to an interface in a safe manner" in three phases: *expand* (support old and new), *migrate* (move clients incrementally), *contract* (remove the old version). "Most database refactorings follow the parallel change pattern"; "the migrate phase is the transition period between the original and the new schema." Cost: supporting two versions; "you need discipline to finish the transition successfully." Credits Joshua Kerievsky (2006) with first documenting it. — [ParallelChange](https://martinfowler.com/bliki/ParallelChange.html), Danilo Sato, 13 May 2014. **MANDATORY** for incompatible changes under continuous delivery (source reasoning: lets code ship in any phase without breaking clients).
- *Refactoring Databases: Evolutionary Database Design* (Ambler & Sadalage, Addison-Wesley Professional, 3 March 2006, ISBN 978-0-321-29353-4, Fowler Signature Series). Refactoring = "a small change to your source code that improves its design without changing its semantics"; Chapter 3: "your database supports both the old and new schemas in parallel" so application teams can deploy their code (the transition period). Chapters: Evolutionary Database Development; Database Refactoring; The Process of Database Refactoring; Deploying into Production; Strategies; then the catalog in five categories — Structural, Data Quality, Referential Integrity, Architectural, Method — plus Transformations. — [InformIT product page](https://www.informit.com/store/refactoring-databases-evolutionary-database-design-9780321293534) (2006).
- The online catalog (Sadalage; "Last updated: July 27 2016") lists refactorings by category, e.g., Architecture: Add Mirror Table, Use Official Data Source; Structural: Drop Column, Introduce Surrogate Key, Split Table; Data Quality: Add Lookup Table, Make Column Non Nullable; Referential Integrity: Add Foreign Key Constraint, Introduce Soft Delete; Transformation: Insert Data, Introduce New Table, Update Data; Method: Rename Method, Extract Method. "A database refactoring is a small change to your database schema" that "improves its design without changing its semantics." — [databaserefactoring.com](https://www.databaserefactoring.com/) (27 Jul 2016).

**Operator rules: GitLab**
- "Migrations are not allowed to require GitLab installations to be taken offline ever." Regular migrations (`db/migrate`) run before code deploys and must finish within **3 minutes**; post-deployment migrations (`db/post_migrate`) within **10 minutes**, concurrent index creation within **20 minutes**; batched background migrations (Sidekiq) for data work beyond that and "should not change the schema"; any single query must stay under **1 second** with cold caches; combined migration time per deploy under 1 hour. Statement timeout on GitLab.com is 15 s. — [GitLab Migration Style Guide](https://docs.gitlab.com/ee/development/migration_style_guide.html) (n.d.; examples reference milestones 16.x–18.10). **MANDATORY** at GitLab (no-downtime rule; timing limits).
- Reversibility: "Migrations must be reversible"; add a comment on how reversibility was tested; if truly irreversible, still define `down` with a comment explaining why. Use `with_lock_retries` (up to 50 attempts, each with a `lock_timeout`, sleeping between) for high-traffic tables and for `add_column`, `remove_foreign_key`, `create_table`; `disable_ddl_transaction!` when PostgreSQL requires it (`CREATE INDEX CONCURRENTLY`); `add_concurrent_index` / `remove_concurrent_index`; index names under PostgreSQL's identifier limit; lowercase object names; `bigint` for integers that may exceed 2 GB; timezone-aware timestamp helpers; encrypted attributes as `jsonb`; migration timestamps no more than 21 days old; every migration specifies `milestone`; high-traffic table = over 10 GB or high read/write. — [GitLab Migration Style Guide](https://docs.gitlab.com/ee/development/migration_style_guide.html). **MANDATORY** (GitLab-internal rules enforced by RuboCop and database review).
- Multi-release sequences: **Drop column** — release M: `ignore_column` with `remove_with`/`remove_after`; M+1: `remove_column` in a post-deployment migration; M+2: remove the ignore rule. "Ignoring and dropping columns should not occur simultaneously in the same release." **Rename column** — "Renaming columns the standard way requires downtime"; use `rename_column_concurrently` + `ignore_column`, then `cleanup_concurrent_column_rename`; large tables go to batched background migrations. **Change column type** — "Avoid using `change_column` as it produces an inefficient query"; `change_column_type_concurrently` then `cleanup_concurrent_column_type_change`. **NOT NULL** — "Adding a `NOT NULL` constraint requires that any application changes are deployed *first*." **Foreign keys** — "Adding foreign keys can potentially cause downtime" (use `add_concurrent_foreign_key`). **Indexes** — "Adding indexes does not require downtime when `add_concurrent_index` is used." **Drop table** — remove code (M), then separate post-deploy migrations removing each FK (`with_lock_retries`, `remove_foreign_key_if_exists`, `reverse_lock_order: true`) then dropping the table (M+1). **Rename table** — "Renaming tables requires downtime." **Integer→bigint PK** — four-release process (`initialize_conversion_of_integer_to_bigint`, backfill, `swap_columns`, cleanup, remove ignore rules). — [Avoiding downtime in migrations](https://docs.gitlab.com/ee/development/database/avoiding_downtime_in_migrations.html) (n.d.; examples dated 2019-12-22 and 2023-05-22). **MANDATORY** sequences.
- NOT NULL on an existing column "usually requires multiple steps split into at least two different releases": release N — app always sets a value, backfill (post-deployment migration for < ~1,000 rows, else background migration); N+1 — confirm, finalize background migration (`ensure_batched_background_migration_is_finished`), add model validation, then `add_not_null_constraint :epics, :description` in a post-deployment migration. Very large tables: `add_not_null_constraint ..., validate: false` ("an invalid `NOT NULL` constraint"), `prepare_async_check_constraint_validation`, then `validate_not_null_constraint` in a separate migration. — [GitLab: NOT NULL constraints](https://docs.gitlab.com/ee/development/database/not_null_constraints.html) (n.d.; milestones 13.0–16.10).

**Operator rules: Stripe**
- Four-phase online migration of "hundreds of millions of Subscriptions objects": (1) dual writing to old and new tables and backfill; (2) change read paths; (3) change write paths (new store first, old archived); (4) remove old data (stale data cleared lazily). Verification used GitHub's *Scientist* library to compare both code paths in production and alert on differences; backfill ran offline on database snapshots via Hadoop/Scalding MapReduce, then re-run to confirm no subscriptions were missed. "Our two tables need to stay consistent with each other at every step." Changes were kept to a few hundred lines at a time. — [Online migrations at scale](https://stripe.com/blog/online-migrations), Jacqueline Xu, 2 Feb 2017. **RECOMMENDED** (pattern for data-model migrations; reasoning: zero downtime with continuous verification).

**Operator rules: Braintree (PostgreSQL)**
- Threshold: "any operation that locks a table for updates for more than a few seconds means downtime for us." Safe: add column; drop column; add index concurrently; drop constraint; add default to existing column. Unsafe on big tables (with workaround): add index (→ `CONCURRENTLY`); change column type (→ new column, dual write, backfill); add column with default (→ add column, add default separately, backfill); add non-nullable column (→ new table, dual write, backfill, switch); add column with unique constraint (→ add column, unique index concurrently, then constraint); `VACUUM FULL` (→ `pg_repack`). — [Safe Operations For High Volume PostgreSQL](https://pgrs.net/2014/05/14/safe-operations-for-high-volume-postgresql/), Paul Gross, Braintree, 14 May 2014. Note: the brief's Medium/PayPal URL returned HTTP 403; this is the original host.
- 2019 "redux" (PostgreSQL 9.1–12): requirements — live and new code/schemas forward- and backward-compatible; "exclusive locks on tables or indexes must be held for at most about 2 seconds"; "rollbacks must not revert the database schema." "We do not combine multiple DDL statements into a single transaction" (locks several objects at once). Lock levels: ACCESS EXCLUSIVE blocks everything; SHARE ROW EXCLUSIVE blocks DDL and row modification but allows reads; SHARE UPDATE EXCLUSIVE blocks concurrent DDL incl. VACUUM/ANALYZE. A *waiting* lock request "causes all subsequent queries on this table to queue until the lock is released," so acquire locks explicitly with `lock_timeout`, pause between retries, and check for long-running queries first. Column add = brief ACCESS EXCLUSIVE catalog update; PostgreSQL 11 avoids the rewrite for non-volatile defaults; `SELECT *` picks up new columns so explicit column lists are required. Type change rewrites except VARCHAR→TEXT (9.1+), unconstrained domains, increasing/removing length or precision limits (9.2+). NOT NULL: add `CHECK ... NOT VALID`, verify, `VALIDATE CONSTRAINT`. FK: SHARE ROW EXCLUSIVE on both tables (9.5+); add `NOT VALID` then validate. UNIQUE: unique index concurrently then `ADD CONSTRAINT ... USING INDEX`. EXCLUDE: ACCESS EXCLUSIVE, cannot reuse an index. `DROP INDEX CONCURRENTLY` (9.2+) cannot drop constraint-backing indexes. Enum values cannot be removed; `ALTER TYPE ... RENAME VALUE` (10+) does not lock. Announces the `pg_ha_migrations` gem that enforces these rules in ActiveRecord. — [Braintree redux gist (jcoleman)](https://gist.github.com/jcoleman/1e6ad1bf8de454c166da94b67537758b), 1 Feb 2019. **MANDATORY** at Braintree.

**Tool-encoded rules: Strong Migrations, gh-ost, pt-online-schema-change, PlanetScale**
- strong_migrations (PostgreSQL, MySQL, MariaDB) flags and offers alternatives for: removing a column (ActiveRecord column cache → `ignored_columns` first); changing column type (rewrites table → new column, dual write, backfill, swap); renaming column/table (→ expand/contract); `create_table force: true` ("can drop an existing table"); auto-increment or stored generated columns (rewrite); adding a foreign key ("blocks writes on both tables" → `validate: false` then validate; MySQL only via `foreign_key_checks` if certain); check constraint (→ `validate: false` then validate); raw SQL ("Strong Migrations can't ensure safety for raw SQL statements"); backfilling in the same transaction (→ batch, throttle, outside transaction). Postgres-specific: non-concurrent index, reference index, unique constraint (→ concurrent unique index + `using_index`), exclusion constraint (no safe alternative), `json` column (breaks `SELECT DISTINCT` → `jsonb`), volatile default (`gen_random_uuid()` → add column, set default, backfill), SET NOT NULL (→ `CHECK ... validate: false`, validate, SET NOT NULL, drop check), renaming enum value, renaming schema. MySQL/MariaDB: COPY algorithm, shared/exclusive locks, expression defaults. Best practice: non-unique indexes with more than three columns rarely help. "It's extremely important to set a short lock timeout for migrations" (`lock_timeout = 10.seconds`; `statement_timeout = 1.hour`; `ALTER ROLE ... SET lock_timeout` when using PgBouncer transaction mode). — [ankane/strong_migrations README](https://github.com/ankane/strong_migrations) (n.d.; footer 2026). **MANDATORY** (lock timeout); rest encoded as default-fail checks.
- gh-ost: "a triggerless online schema migration solution for MySQL"; creates a *ghost* table, copies rows, "uses the binary log stream to capture table changes, and asynchronously applies them onto the ghost table," then cut-over ("probably the most critical step"). "We have recognized the triggers to be the source of many limitations and risks." Features: "True pause: when gh-ost throttles, it truly ceases writes on master"; dynamic reconfiguration; `--test-on-replica`; `--postpone-cut-over-flag-file`; hooks. "Only releases are to be used in production." — [github/gh-ost](https://github.com/github/gh-ost) (n.d.; GA). **OPTIONAL/CONTEXTUAL** (MySQL large tables).
- pt-online-schema-change 3.7.2: creates an empty copy, alters it, copies rows in chunks, keeps it in sync with **triggers**, then atomic rename (original dropped by default). Requires a PRIMARY KEY or UNIQUE index; will not run if the table already has triggers (`--preserve-triggers` has restrictions). `--alter-foreign-keys-method` = auto | rebuild_constraints | drop_swap | none ("none" leaves FKs pointing at a nonexistent table). `--max-lag` (default 1 s), `--max-load` (Threads_running=25), `--critical-load` (Threads_running=50 aborts), `--check-replication-filters` on by default; alters only with `--execute`; `--dry-run`. "Do not use this tool before reading its documentation and checking your backups carefully." Unique-index changes can "fail silently and data will be lost." — [pt-online-schema-change docs](https://docs.percona.com/percona-toolkit/pt-online-schema-change.html) (n.d.; v3.7.2). **MANDATORY** (test on non-production, verify backups) per the doc's own warnings.
- PlanetScale "safe migrations" (branch setting, "highly recommended" for production): schema changes go through deploy requests so "all team members [can] check and comment on schema changes before they are applied"; on merge "a ghost table will be created with the desired schema changes" and kept in sync until you apply; schema revert keeps the old table synced for a 30-minute window; with safe migrations on, "Any CREATE, ALTER, or DELETE commands" sent directly to the branch are rejected. — [PlanetScale Safe migrations](https://planetscale.com/docs/concepts/safe-migrations) (n.d.). **RECOMMENDED** by vendor.

**PostgreSQL facts that determine danger (official docs, PostgreSQL 18.6)**
- "An `ACCESS EXCLUSIVE` lock is acquired unless explicitly noted"; `ADD FOREIGN KEY` takes only SHARE ROW EXCLUSIVE on both tables; `VALIDATE CONSTRAINT` takes SHARE UPDATE EXCLUSIVE; `SET STATISTICS` and storage parameters take SHARE UPDATE EXCLUSIVE. `ADD COLUMN` with a non-volatile DEFAULT stores the default in metadata: "In neither case is a rewrite of the table required"; volatile default (`clock_timestamp()`), stored generated, identity, or constrained-domain columns "will cause the entire table and its indexes to be rewritten"; virtual generated columns never rewrite. Type change "will normally cause the entire table and its indexes to be rewritten" unless binary-coercible with a no-op USING. `NOT VALID` skips the scan; validation "acquires only a `SHARE UPDATE EXCLUSIVE` lock." `SET NOT NULL` scans the table "unless `NOT VALID` is specified; however, if a valid `CHECK` constraint exists ... which proves no `NULL` can exist, then the table scan is skipped." `DROP COLUMN` "does not physically remove the column"; space reclaimed over time. Rewriting forms are not MVCC-safe. — [ALTER TABLE](https://www.postgresql.org/docs/current/sql-altertable.html) (PostgreSQL 18.6).
- Normal `CREATE INDEX` "locks the table to be indexed against writes"; `CONCURRENTLY` needs "two scans of the table" and waits for existing transactions, "takes significantly longer," and on failure leaves an `INVALID` index that "will still consume update overhead" — "drop the index and try again." Only one concurrent build per table at a time; "`CREATE INDEX CONCURRENTLY` cannot" run in a transaction block; a concurrently built unique index enforces uniqueness before it is usable; "Concurrent builds for indexes on partitioned tables are currently not supported" (build per partition, then attach). — [CREATE INDEX](https://www.postgresql.org/docs/current/sql-createindex.html) (PostgreSQL 18.6).

### Inferences
- The four operator sources converge on a quantified lock budget of roughly 2–10 s (Braintree ~2 s exclusive-lock ceiling; strong_migrations 10 s `lock_timeout`; GitLab 15 s statement timeout with lock retries), which is a far stricter constraint than the "minutes" allowed for the migration as a whole; a framework should state both a lock budget and a total-duration budget.
- The safe sequences are all instances of Parallel Change applied at the DDL level: NOT VALID→VALIDATE, CONCURRENTLY, add-then-set-default, ignore→drop→cleanup. The framework can therefore prescribe a single meta-rule ("every change must be deployable while the previous application version is still running") and derive the table from it.
- Because PostgreSQL 11 removed the rewrite for constant defaults, several older rules (Braintree 2014) are version-dependent; the framework should tie rules to engine versions.

## KQ2. Migration tools: Flyway, Liquibase, Alembic, Atlas, Prisma, Django, Rails; state-based vs migration-based; version tables; ownership

### Takeaway
All mainstream tools share the Fowler/Sadalage model — ordered scripts plus a history table — but differ sharply on authoring (hand-written SQL vs. generated from a model/state), rollback (Flyway Teams-only undo with explicit caveats; Liquibase automatic rollback for ~25 change types only; Rails/Django reversible operations; Prisma ORM 8 "a migration can go backwards"), and transactional DDL (PostgreSQL/SQLite yes; MySQL/Oracle no). Redgate's own analysis says "neither approach offers an ideal solution" for state vs. migrations; Atlas and Prisma both push a hybrid where the desired state is declared but the planned migration is checked in and reviewed.

### Cited Findings

**Flyway (Redgate)**
- "Versioned migrations come in 2 forms: regular and undo"; repeatable and baseline migrations also exist. Migrate "is idempotent and can be done safely regardless of the current version of the schema"; "all pending versioned migrations are applied in order first followed by any repeatable migrations that have changed"; repeatable migrations run in description order; by default each migration runs in a single transaction and on error Flyway "marks the migration as failed and automatically rolls it back if possible"; a schema history table records "which migrations have already been applied when and by whom." — [Flyway: Migrations](https://documentation.red-gate.com/flyway/flyway-concepts/migrations) (published 16 Dec 2024; updated 17 Sep 2025).
- Versioned migrations are "applied to a target database in order exactly once"; recorded with checksum in `flyway_schema_history`; each "must be assigned a unique version"; versions are dotted/underscore numerics "sorted numerically"; description is for humans only; Flyway Desktop adds a timestamp by default to reduce team conflicts. Do not edit a migration once in a permanent downstream environment: "It's best to create a new versioned migration script and roll forward any necessary changes." Example `V001.002__NewTwitterColumn.sql`. — [Flyway: Versioned migrations](https://documentation.red-gate.com/flyway/flyway-concepts/migrations/versioned-migrations) (17 Dec 2024; updated 23 Dec 2024). **MANDATORY** (never edit applied migrations; roll forward).
- Naming: `sqlMigrationPrefix` default `"V"`; pattern "prefixVERSIONseparatorDESCRIPTIONsuffix" → `V1.1__My_description.sql`. — [Flyway SQL migration prefix setting](https://documentation.red-gate.com/fd/flyway-sql-migration-prefix-setting-277579037.html) (15 Jan 2025; updated 05 Nov 2026). Separator setting page (default `__`) was returned by search: [SQL Migration Separator](https://documentation.red-gate.com/fd/flyway-sql-migration-separator-setting-277579038.html) (not fetched).
- Undo migrations (EDITION: TEAMS): "Undo migrations are the opposite of regular versioned migrations"; example `U001.002__UndoNewTwitterColumn.sql`. Caveats: "Undo migrations assume the whole migration succeeded and should now be undone"; on databases without DDL transactions "a migration can fail at any point" so undo "may require a different approach"; "you should take care if you have destructive changes (drop, delete, truncate etc)." The page's recommended alternative is to keep the database backward compatible with deployed application code so the *application* can be rolled back, plus a tested backup/restore strategy. — [Flyway: Undo migrations](https://documentation.red-gate.com/fd/undo-migrations-273973334.html) (17 Dec 2024; updated 21 May 2026). **OPTIONAL/CONTEXTUAL**.

**Liquibase**
- A changelog is a text file that lists "sequentially ... all changes made to your database"; "An individual unit of change in your changelog is called a Changeset"; formats SQL, XML, YAML, JSON (root changelog using `include`/`includeAll` must be XML/YAML/JSON); changeset identity = `id` + `author` + changelog path/name; tracking in `DATABASECHANGELOG` and, from 4.27.0, `DATABASECHANGELOGHISTORY`; preconditions "can typically be used for both documenting and enforcing expectations or assumptions"; contexts and labels select which changesets run; Liquibase can "generate automatic rollback statements for some changes"; formatted SQL uses `--rollback <SQL>` / `--rollbackSqlFile`. — [What is a Changelog?](https://docs.liquibase.com/concepts/changelogs/home.html) (Liquibase Secure 5.2.1; updated 12 Aug 2026).
- Rollback commands: `rollback <tag>` ("revert all changes made to the database after the specified tag"), `rollback-to-date`, `rollback-count`; Secure-only `rollback-one-changeset`, `rollback-one-update`. "Custom rollback definitions are not supported in formatted SQL changelogs. You must write rollback SQL manually." "Rolling back complex changes that involve structural changes and data migration is more difficult." Validation: `update-testing-rollback` (deploy → roll back → redeploy), `future-rollback-sql` ("used when auditors need to verify that all database changes have a rollback"), `rollback-sql`. "Rollback scripts need to be tested just like application code." — [Using Liquibase Rollback](https://docs.liquibase.com/workflows/liquibase-community/using-rollback.html) (updated 12 Aug 2026). **RECOMMENDED** (test rollbacks).
- Automatic rollback supported (XML/JSON/YAML only) for: addCheckConstraint, addColumn, addDefaultValue, addForeignKeyConstraint, addLookupTable, addNotNullConstraint, addPrimaryKey, addUniqueConstraint, createIndex, createSequence, createSynonym, createTable, createView, disable/enableCheckConstraint, disable/enableTrigger, dropNotNullConstraint, output, renameColumn, renameSequence, renameTable, renameTrigger, renameView, tagDatabase. **Not** supported for: addAutoIncrement, alterSequence, createFunction/Package/Procedure/Trigger, customChange, delete, drop* (dropColumn, dropTable, dropIndex, dropForeignKeyConstraint, dropPrimaryKey, dropView...), executeCommand, insert, loadData, loadUpdateData, mergeColumns, modifyDataType, sql, sqlFile, update. Error example: "No inverse to liquibase.change.core.DropTableChange created". — [Automatic and custom rollbacks](https://docs.liquibase.com/workflows/liquibase-community/automatic-custom-rollbacks.html) (updated 12 Aug 2026).
- Policy Checks (Pro/Secure): "allow you to define and adhere to code standards to ensure compliance and data quality"; run in build/deploy automation "at any point in the workflow"; results in a Checks Report; example scenarios: enforcing naming standards, flagging user/role privilege changes, custom checks; one named built-in: `NoDeleteWithoutWhere`. — [What are policy checks?](https://docs.liquibase.com/liquibase-pro/policy-checks/home.html) (Secure 5.1; updated 22 Oct 2026). **RECOMMENDED** (vendor).

**Alembic (SQLAlchemy)**
- Autogenerate compares the live database with model metadata and writes candidate migrations. Detects: table add/remove; column add/remove; nullable changes; basic index and explicitly-named unique constraint changes; basic FK changes; column type changes (`compare_type` default True since 1.12.0); server defaults only if `compare_server_default` set ("off by default so that it can be tested on the target schema first"); named CHECK constraints by name only ("Expression changes are never detected"). Cannot detect: table renames ("will come out as an add/drop of two different tables, and should be hand-edited into a name change"); column renames ("not at all the same as a name change"); anonymously named constraints; Enum on backends without native ENUM. "autogenerate is not intended to be perfect"; it is "always necessary to manually review and correct the candidate migrations that autogenerate produces." — [Alembic: Auto Generating Migrations](https://alembic.sqlalchemy.org/en/latest/autogenerate.html) (Alembic 1.20.1). **MANDATORY** (review generated migrations).

**Atlas (Ariga)**
- Declarative: "the desired state of the database schema is given as input to the migration engine"; declarative plans "rely on a network connection to the target database and on human approval of migrations plans in real-time." Versioned: "developers describe the changes themselves" as versioned SQL files; "puts the burden of planning the migration on developers." Hybrid "versioned migration authoring": desired state declared, Atlas plans, but "plans are instead written into normal migration files which can be checked-in to source control." `atlas migrate lint` will "Analyze migration files for potential issues and policy violations." — [Declarative vs Versioned](https://atlasgo.io/concepts/declarative-vs-versioned) (n.d.; © 2026).
- Lint analyzers: Destructive DS101 "Schema was dropped", DS102 "Table was dropped", DS103 "Non-virtual column was dropped"; Data-dependent MF101 "Add unique index to existing column", MF102 "Modifying non-unique index to unique", MF103 "Adding a non-nullable column to an existing table", MF104 "Modifying a nullable column to non-nullable"; Backward-incompatible BC101 "Renaming a table", BC102 "Renaming a column", BC103/BC104 dropping table/column; Constraint deletion CD101–CD103; PostgreSQL concurrent-index PG101 "Missing the `CONCURRENTLY` in index creation", PG102 (deletion), PG103 missing `atlas:txmode none`, PG104/PG105 PK/UNIQUE constraint creation acquiring ACCESS EXCLUSIVE, PG108 partitioned-table index, PG109 EXCLUDE, PG110 non-optimal column ordering (padding); PG3xx blocking changes (PG301 type rewrite, PG302 volatile defaults, PG303 NULL→NOT NULL scan, PG306 FKs); MySQL MY101 non-nullable column without default, MY110–MY123 enum/set table copies, MY130+ blocking; TX101 "Migration file contains multiple statements that cannot run in a single transaction", TX201 "Nested transaction detected"; Naming NM101–NM106 (schema/table/column/index/FK/check names); SQLite LT101; SA101 "Possible SQL injection vulnerabilities detected"; plus `restrictive`, `nestedtx`, `statement` (regex allow/deny), `cve`. — [Atlas lint analyzers](https://atlasgo.io/lint/analyzers) (n.d.).
- Schema drift = "where the live database schema deviates from its intended, version-controlled state"; caused by setups that "allow developers to make direct changes to production databases"; drifted-state migrations "may fail and cause unknown side effects"; Atlas "automatically detects schema drift by regularly comparing the actual database schema with the intended schema" and notifies Slack. — [Atlas drift detection](https://atlasgo.io/monitoring/drift-detection) (n.d.). **RECOMMENDED**.

**Prisma (ORM 8 migration graph — differs from the classic Prisma Migrate the brief described)**
- A compiled contract (`contract.json`) is the target; each migration directory records `from`/`to` hashes ("Each migration records the contract state it starts from and the state it ends at"). Tracking on PostgreSQL: `prisma_contract.marker` ("The record in the database of which contract state it matches. Reading it does not check the tables") and `prisma_contract.ledger` ("The database's own list of every migration applied to it"); MongoDB uses a `_prisma_migrations` collection. Production pipelines run `db migrate --to prod` so the deploy "never applies more than the repository has promised." Out-of-band `db update` leaves a state no migration ends at, so "your next `db migrate` run stops at the check" (drift guard). Baselining via `npx prisma db sign`. No separate down migrations: "Undoing a change is not a special mode you switch into, because a migration can go backwards" (plan with `migration plan --from <dir> --to <dir>^`). Hand-written `dataTransform` steps are not carried forward by the planner. — [Prisma: migration mental model](https://www.prisma.io/docs/orm/prisma-migrate/understanding-prisma-migrate/mental-model) (n.d.; Prisma ORM 8).

**Django**
- "You should think of migrations as a version control system for your database schema." Migration files "are designed to be committed to, and distributed as part of, its codebase"; commit model change and migration "as a single commit." Backend differences: PostgreSQL "the most capable"; "MySQL lacks support for transactions around schema alteration operations, meaning that if a migration fails to apply you will have to manually unpick the changes"; SQLite emulates ALTER by creating a new table, copying, dropping, renaming, and "It is not recommended that you run and migrate SQLite in a production environment." On DDL-transactional backends "all migration operations will run inside a single transaction by default." Data migrations via `RunPython` must use historical models (`apps.get_model`); omitting the reverse callable makes backward migration raise; "A migration is irreversible if it contains any irreversible operations." Squashing: keep old files, release, wait until all systems upgraded, then remove. — [Django 5.2: Migrations](https://docs.djangoproject.com/en/5.2/topics/migrations/) (v5.2; © 2005-2026). **MANDATORY** (commit migrations with model changes; historical models in data migrations).

**Rails**
- Files `db/migrate/YYYYMMDDHHMMSS_name.rb` (UTC timestamp orders them); applied versions in `schema_migrations`; `db/schema.rb` (Ruby DSL) or `db/structure.sql` (via `pg_dump`) when triggers/procedures are needed; "Your database remains the source of truth" and loading the schema file is the faster, less error-prone way to build a new database. `change` for auto-reversible operations, else `reversible` or `up`/`down`, raising `ActiveRecord::IrreversibleMigration`. Each migration runs in a transaction on DDL-transactional databases; `disable_ddl_transaction!` for statements that cannot. "In general, editing existing migrations that have been already committed to source control is not a good idea." Data changes in migrations are discouraged (separate lifecycles, hard rollbacks, locking) — use the `maintenance_tasks` gem. — [Rails 8.1: Active Record Migrations](https://guides.rubyonrails.org/active_record_migrations.html) (v8.1.4.1). **MANDATORY** (do not edit committed migrations); **RECOMMENDED** (keep data changes out of migrations).

**State-based vs. migration-based (Redgate)**
- "A state-based approach focuses on how the database should look" (object create scripts + comparison tool generates the deploy script); a migration-based approach "focuses on how the database should change" (ordered alter scripts from a seed). State-based advantages: current state always in source control, easier conflict resolution/auditing, multiple developers; disadvantage: deployment scripts "are unable to understand the data context of a database change" — a rename "drops the old table and creates a new one without preserving the data," so DBAs write extra scripts. Migration-based: more control over data handling and repeatable deployments; disadvantages: script counts grow, merges need manual review, redundant operations slow deployments, scripts must run in order or data can be lost. Hybrids: SQL Source Control pre/post-deployment scripts; SQL Change Automation generates migrations while tracking a schema model. "Neither approach offers an ideal solution"; teams may start state-based and move to migrations once the database stabilises. — [Introduction to DevOps Database Delivery](https://www.red-gate.com/simple-talk/devops/database-devops/introduction-to-devops-database-delivery/), Robert Sheldon, 17 Oct 2019. **OPTIONAL/CONTEXTUAL**. (The brief's Redgate "approaches" product page now only says SQL Change Automation is retired from sale.)

**Version tables and version numbering (cross-tool)**
- Flyway `flyway_schema_history` (version + checksum); Liquibase `DATABASECHANGELOG` (+ `DATABASECHANGELOGHISTORY` ≥ 4.27.0); Rails `schema_migrations`; Django "Django's migrations table" (pruned with `migrate --prune`); Prisma ORM 8 `prisma_contract.marker`/`ledger`; Fowler/Sadalage "changelog table." Numbering: Flyway dotted numeric versions or timestamps; Rails/Django ordered timestamps/sequence numbers; GitLab requires timestamps after the last required upgrade stop and ≤ 21 days old plus an explicit `milestone`. — sources as cited above.

**Ownership: developers vs. DBAs; ORM-generated vs. hand-written SQL**
- Fowler/Sadalage: DBAs "review migrations as they're committed" and developers consult the DBA on significant changes — [Evolutionary Database Design](https://martinfowler.com/articles/evodb.html). DORA: discuss changes "with the people who run the production database"; silo pitfall — teams that adopt a process "without consulting DBAs often meet resistance"; goal "100% of database changes" via automated push-button process — [DORA](https://dora.dev/capabilities/database-change-management/). GitLab routes all migrations through database reviewers and RuboCop, and tells authors to "Prefer Arel and plain SQL over ActiveRecord syntax" in data migrations — [GitLab style guide](https://docs.gitlab.com/ee/development/migration_style_guide.html). PlanetScale substitutes deploy-request review for DBA gatekeeping and rejects direct DDL — [PlanetScale](https://planetscale.com/docs/concepts/safe-migrations). Alembic requires human review of generated SQL — [Alembic](https://alembic.sqlalchemy.org/en/latest/autogenerate.html). Braintree encodes DBA knowledge into a gem (`pg_ha_migrations`) — [Braintree 2019](https://gist.github.com/jcoleman/1e6ad1bf8de454c166da94b67537758b). Liquibase centralises policy via Policy Checks — [Liquibase](https://docs.liquibase.com/liquibase-pro/policy-checks/home.html).

### Inferences
- The industry has converged on "developer-authored, machine-checked, peer-reviewed" migrations rather than DBA-authored ones; the DBA role appears as reviewer, policy author, and tool maintainer.
- Generated migrations (Alembic, Django, Prisma, Atlas declarative) are acceptable only as *candidates*; every tool's own documentation requires human review, which makes "review generated DDL before merge" a MANDATORY framework rule.
- Rollback capability is uneven and vendor-caveated; a framework should prefer forward-only, backward-compatible migrations (Flyway, Braintree, GitLab's expand/contract) and treat down migrations as an operational convenience, not a safety mechanism.

- The classic Prisma Migrate pages (`migrate dev`/`migrate deploy`, shadow database, `_prisma_migrations`) have been superseded on the live docs by the ORM 8 model; legacy behaviour was not verified.
- No source quantified adoption of ORM vs. hand-written SQL migrations.

## KQ3. Database CI/CD, testing, linting, drift and data-migration verification

### Takeaway
DORA treats database change management as a measured capability of continuous delivery: scripts in version control, migrations applied by tooling in every environment, DBA collaboration, production-like test data, and a target of 100% automated changes. Tooling exists at three layers — migration linting (Squawk, Atlas, Liquibase Policy Checks), database unit tests (pgTAP, tSQLt) and data tests (dbt), and real-engine integration tests (Testcontainers) — while drift detection (Atlas, Prisma's marker check) closes the loop between repository and production.

### Cited Findings
- DORA: "Database changes are often a major source of risk and delay when performing deployments." Practices: store database changes as scripts in version control "with the same rigor as production application changes"; capture each change as a migration script with a unique sequence number, with each instance tracking which migrations have run and a tool applying missing ones (names Flyway, Liquibase, alembic); keep schema changes beside application code and use a tool that records which changes ran where and their results; collaborate with the people who run production databases; zero-downtime techniques: online schema tools (gh-ost, pt-online-schema-change), parallel change (expand/contract), partition/archive data, event sourcing, NoSQL trade-offs; "Test every schema change against a production-like data set with sensitive information scrubbed," on at least two nodes if production is distributed. Pitfalls: silos, shared schemas (need one self-service version-controlled change mechanism), architectural effort. Measures: percentage of failed changes where database changes contributed; database work's addition to lead time; cost of scheduled downtime; share of changes via fully automated push-button process — "The goal should be that 100% of database changes are made in this way." Claims this capability predicts software delivery performance and availability. — [DORA: Database change management](https://dora.dev/capabilities/database-change-management/) (n.d.; CC BY 4.0). **MANDATORY** (VCS + automated migrations + production-like testing).
- GitLab's pipeline enforces: `db:check-migrations` (timestamp age), `db:gitlabcom-database-testing` (reports index builds > 20 min → create asynchronously), RuboCop rules, and a dedicated Testing Rails migrations guide. — [GitLab style guide](https://docs.gitlab.com/ee/development/migration_style_guide.html).
- Liquibase `update-testing-rollback` and `future-rollback-sql` for auditors — [Using Liquibase Rollback](https://docs.liquibase.com/workflows/liquibase-community/using-rollback.html). Liquibase Policy Checks run "at any point in the workflow, before or after deployment" with a Checks Report — [Policy checks](https://docs.liquibase.com/liquibase-pro/policy-checks/home.html).
- Squawk: "a linter for Postgres migrations" whose rules "focus on ensuring safe migrations and warn about statements that could block reads / writes." Rules: adding-field-with-default, adding-foreign-key-constraint, adding-not-nullable-field, adding-required-field, adding-serial-primary-key-field, ban-char-field, ban-concurrent-index-creation-in-transaction, ban-create-domain-with-constraint, ban-drop-column, ban-drop-database, ban-drop-not-null, ban-drop-table, changing-column-type, constraint-missing-not-valid, disallowed-unique-constraint, prefer-bigint-over-int, prefer-bigint-over-smallint, prefer-identity, prefer-robust-stmts, prefer-text-field, prefer-timestamptz, renaming-column, renaming-table, require-concurrent-index-creation, require-concurrent-index-deletion, transaction-nesting. — [Squawk rules](https://squawkhq.com/docs/rules) (n.d.; © 2026). **RECOMMENDED** (lint migrations in CI).
- Atlas `migrate lint` analyzer catalogue (destructive, data-dependent, backward-incompatible, concurrent-index, blocking, transaction, naming, ownership, SQL injection) — [Atlas lint analyzers](https://atlasgo.io/lint/analyzers); drift detection with Slack alerts — [Atlas drift detection](https://atlasgo.io/monitoring/drift-detection).
- SQLFluff: "Dialect-flexible and configurable SQL linter" supporting "25+ SQL dialects including T-SQL, PostgreSQL, BigQuery, Snowflake"; "70+ Rules"; `sqlfluff lint` / `sqlfluff fix`; rule bundles: Aliasing (10), Ambiguous (9), Capitalisation (5), Convention (13), Jinja (1), Layout (15), Oracle (1), Postgres (2), References (7), Structure (12), T-SQL (4) — 79 rules in 11 categories. — [SQLFluff docs](https://docs.sqlfluff.com/en/stable/) and [rules reference](https://docs.sqlfluff.com/en/stable/reference/rules.html) (stable; © 2026). **OPTIONAL/CONTEXTUAL** (style/structure linting; not a safety linter).
- pgTAP: "a suite of database functions that make it easy to write" TAP-emitting unit tests in psql scripts or xUnit-style functions; schema assertions `has_table`, `has_column`, `col_is_pk`, `can_ok`; `ok`/`is` for values; `pg_prove -d try pgtap.sql --verbose` runner; `runtests()` handles setup and rollback "including rolling back any changes made to the schema." — [pgTAP](https://pgtap.org/) (n.d.). **RECOMMENDED** where logic lives in the database.
- tSQLt: "the open source database unit testing framework for SQL Server"; tests written in T-SQL, each run in a transaction and rolled back; `FakeTable`, `SpyProcedure`, `AssertEquals`, `AssertEqualsTable`, `AssertResultSetsHaveSameMetaData`, `ExpectException`; tests grouped in schemas (test classes); output "in plain text or XML" for CI; SQL Server 2005 SP2 onward. — [tSQLt](https://tsqlt.org/) (© 2010-2020).
- dbt data tests: "assertions you make about your models and other resources"; "select statements that seek to grab 'failing' records"; zero rows = pass. Built-in generic tests: `unique`, `not_null`, `accepted_values`, `relationships` ("also known as referential integrity"); singular tests as SQL files; `severity` warn/error, `error_if`/`warn_if` thresholds, `--store-failures`; `dbt test --select "test_type:data"` separates data tests from unit tests. — [dbt: Add data tests to your DAG](https://docs.getdbt.com/docs/build/data-tests) (updated 16 Sep 2026). **RECOMMENDED** for analytics schemas (declarative constraints in warehouses that do not enforce them).
- Testcontainers: "an open source library for providing throwaway, lightweight instances of databases, message brokers, web browsers, or just about anything that can run in a Docker container"; "No more need for mocks or complicated environment configurations"; languages Java, Go, .NET, Node.js, Python, Rust, Ruby, PHP, Haskell, Clojure, Elixir, Scala; modules for PostgreSQL, MySQL, MongoDB, Cassandra, Couchbase, Neo4j, ClickHouse, CockroachDB, Elasticsearch and "50+ Modules." — [Testcontainers](https://testcontainers.com/) (n.d.). **RECOMMENDED** (run migrations against the real engine in CI).
- Data-migration verification: Stripe compared old/new reads in production with Scientist and re-ran the offline Scalding job "to confirm no subscriptions were missing" — [Stripe](https://stripe.com/blog/online-migrations). GitLab verifies NOT NULL readiness on "a thin clone of production" and finalizes background migrations before adding constraints — [GitLab NOT NULL](https://docs.gitlab.com/ee/development/database/not_null_constraints.html). pt-osc/gh-ost: test on a replica/non-production first (`--test-on-replica`, `--dry-run`) — [gh-ost](https://github.com/github/gh-ost), [pt-osc](https://docs.percona.com/percona-toolkit/pt-online-schema-change.html).
- Drift guards: Prisma ORM 8's marker check stops `db migrate` after out-of-band `db update` — [Prisma](https://www.prisma.io/docs/orm/prisma-migrate/understanding-prisma-migrate/mental-model); Atlas drift monitoring — [Atlas](https://atlasgo.io/monitoring/drift-detection); Flyway checksums "to catch accidental edits to a migration" — [Flyway versioned migrations](https://documentation.red-gate.com/flyway/flyway-concepts/migrations/versioned-migrations); PlanetScale rejects direct DDL — [PlanetScale](https://planetscale.com/docs/concepts/safe-migrations).

**What an automated schema validator should check (as evidenced by the sources)**
- Lock/rewrite safety: non-concurrent index create/drop; constraints without NOT VALID; NOT NULL/type changes; volatile defaults; renames/drops; multiple DDL per transaction — [Squawk](https://squawkhq.com/docs/rules), [Atlas](https://atlasgo.io/lint/analyzers), [strong_migrations](https://github.com/ankane/strong_migrations).
- Type hygiene: `prefer-bigint-over-int`, `prefer-identity` (over serial), `prefer-text-field` / `ban-char-field`, `prefer-timestamptz` — [Squawk](https://squawkhq.com/docs/rules); `bigint` for large counters, timezone-aware timestamps, `jsonb` not `text` — [GitLab style guide](https://docs.gitlab.com/ee/development/migration_style_guide.html); `jsonb` not `json` — [strong_migrations](https://github.com/ankane/strong_migrations).
- Naming: lowercase object names, identifier-length limits, explicit index names — [GitLab style guide](https://docs.gitlab.com/ee/development/migration_style_guide.html); NM101–NM106 naming conventions — [Atlas](https://atlasgo.io/lint/analyzers); naming standards via Policy Checks — [Liquibase](https://docs.liquibase.com/liquibase-pro/policy-checks/home.html); Alembic: name constraints explicitly or autogenerate cannot track them — [Alembic](https://alembic.sqlalchemy.org/en/latest/autogenerate.html).
- Structure: PK/column existence tests (`has_table`, `has_column`, `col_is_pk`) — [pgTAP](https://pgtap.org/); primary-key constraint drops (CD103), column ordering padding (PG110) — [Atlas](https://atlasgo.io/lint/analyzers); non-unique indexes > 3 columns — [strong_migrations](https://github.com/ankane/strong_migrations).
- Data integrity in analytics layers: unique / not_null / accepted_values / relationships — [dbt](https://docs.getdbt.com/docs/build/data-tests).
- Governance: privilege changes (GRANT/REVOKE-like), `NoDeleteWithoutWhere`, statement allow/deny regexes, SQL-injection (SA101), CVEs in extensions — [Liquibase](https://docs.liquibase.com/liquibase-pro/policy-checks/home.html), [Atlas](https://atlasgo.io/lint/analyzers).

### Inferences
- The sources support a three-tier CI gate: (1) static migration lint (fail on destructive/blocking patterns unless explicitly waived — the `safety_assured`/`atlas:lint` style escape hatch); (2) apply migrations to a disposable real engine (Testcontainers) and run schema/unit tests (pgTAP/tSQLt) plus rollback test where down scripts exist (Liquibase `update-testing-rollback`); (3) rehearse against a production-like dataset (DORA; GitLab thin clone) with timing thresholds.
- Checks the brief asked about — audit columns, money types, reserved words, `tenant_id` presence, FK indexed — are not provided out-of-the-box by any linter opened; they would need custom rules (Liquibase custom policy checks, Atlas `statement` regex rules, pgTAP assertions).

### Gaps
- No fetched source documents FK-index-presence checks, reserved-word checks, or multi-tenant `tenant_id` checks.

## KQ4. Backup, recovery and disaster recovery: definitions, vendor practice, DR tiers

### Takeaway
NIST SP 800-34 Rev. 1 supplies the vocabulary (MTD, RTO, RPO, BIA, seven-step process, full/incremental/differential, cold/warm/hot/mobile/mirrored sites) and insists backups be tested; vendors agree that physical backups plus continuous log archiving (WAL / binary log / transaction log / archived redo) are the foundation for point-in-time recovery, that logical dumps are a portable supplement, and that replication and snapshots are not substitutes for point-in-time backups. Cloud providers automate daily snapshots plus log-based PITR within a retention window; CISA/US-CERT add 3-2-1, offline/immutable copies and restore drills for ransomware.

### Cited Findings

**Definitions and planning (NIST, ISO)**
- *Contingency Planning Guide for Federal Information Systems*, NIST SP 800-34 Rev. 1 (Swanson, Bowen, Phillips, Gallup, Lynes; May 2010; updated 11 Nov 2010). Seven-step process: "1. Develop the contingency planning policy statement ... 2. Conduct the business impact analysis (BIA) ... 3. Identify preventive controls; 4. Create contingency strategies; 5. Develop an information system contingency plan; 6. [test/exercise and train]; 7. [maintain the plan]." — [CSRC record](https://csrc.nist.gov/pubs/sp/800/34/r1/upd1/final); text extracted from the [official PDF](https://nvlpubs.nist.gov/nistpubs/Legacy/SP/nistspecialpublication800-34r1.pdf). **MANDATORY** for federal systems; framework-level reference.
- MTD: "represents the total amount of time the system owner/authorizing official is willing to accept for a mission/business process outage or disruption and includes all impact considerations." RTO: "defines the maximum amount of time that a system resource can remain unavailable before there is an unacceptable impact on other system resources, supported mission/business processes, and the MTD." RPO: "represents the point in time, prior to a disruption or system outage, to which mission/business process data can be recovered (given the most recent backup copy of the data) after an outage. Unlike RTO, RPO is not considered as part of MTD. Rather, it is a factor of how much data loss the mission/business process can tolerate." "Because the RTO must ensure that the MTD is not exceeded, the RTO must normally be shorter than the MTD." Glossary forms: MTD "The amount of time mission/business process can be disrupted without causing significant harm to the organization's mission"; RPO "The point in time to which data must be recovered after an outage"; RTO "The overall length of time an information system's components can be in the recovery phase before negatively impacting the organization's mission or mission/business processes." — [NIST SP 800-34 Rev. 1 PDF](https://nvlpubs.nist.gov/nistpubs/Legacy/SP/nistspecialpublication800-34r1.pdf) §3.2 and Appendix; confirmed at [CSRC glossary: RPO](https://csrc.nist.gov/glossary/term/recovery_point_objective), [RTO](https://csrc.nist.gov/glossary/term/recovery_time_objective), [MTD](https://csrc.nist.gov/glossary/term/maximum_tolerable_downtime).
- Backup methods (§5): "Full. A full backup captures all files ... the time required to perform a full backup can be lengthy." "Incremental. An incremental backup captures files that were created or changed since the last backup, regardless of backup type ... media from different backup operations may be required." "Differential. A differential backup stores files that were created or modified since the last full backup ... Restoring from a differential backup may require fewer media than an incremental backup." Backup policy (§3.4.2): "Policies should specify the minimum frequency and scope of backups (e.g., daily or weekly, incremental or full) based on data criticality"; designate location, naming, media rotation, and transport method; offsite vendor criteria: geographic area (same-disaster probability), accessibility, security, environment, cost. Footnote 25: "Backup tapes should be tested regularly to ensure that data are being stored correctly and that the files may be retrieved without errors or lost data"; test at the alternate site too. Encryption keys "should be stored separate from, but accessible to, the primary encrypted backup data." Alternate sites: cold ("basic infrastructure ... but no equipment"), warm (equipment installed "but ... not loaded with the software or data"), hot ("fully operational equipment ... most recent version of backed-up data loaded"), mobile, mirrored ("fully redundant facilities with automated real-time information mirroring ... the most expensive choice, but it ensures virtually 100 percent availability"). — [NIST SP 800-34 Rev. 1 PDF](https://nvlpubs.nist.gov/nistpubs/Legacy/SP/nistspecialpublication800-34r1.pdf). **MANDATORY** (test backups; define RTO/RPO/MTD from BIA).
- ISO 22301:2019 "Security and resilience — Business continuity management systems — Requirements": "This document specifies requirements to implement, maintain and improve a management system to protect against, reduce the likelihood of the occurrence of, prepare for, respond to and recover from disruptions when they arise"; applicable to organizations of any type or size; valid from 30 Oct 2019; predecessor ISO 22301:2012; Amd 1:2024 "Climate action changes" valid from 23 Feb 2024. — [EVS record of ISO 22301:2019](https://www.evs.ee/en/iso-22301-2019) (official iso.org page returned HTTP 403; ISO 22313:2020 named as companion guidance in search results, not fetched). ISO/IEC 27031 was not fetched (gap).

**PostgreSQL**
- "There are three fundamentally different approaches to backing up PostgreSQL data": SQL dump, file-system-level backup, continuous archiving; "Each has its own strengths and weaknesses." — [PostgreSQL 18: Backup and Restore](https://www.postgresql.org/docs/current/backup.html).
- pg_dump: "Dumps created by pg_dump are internally consistent ... a snapshot of the database at the time pg_dump began running. pg_dump does not block other operations" (except exclusive-lock DDL). "pg_dump's output can generally be re-loaded into newer versions of PostgreSQL, whereas file-level backups and continuous archiving are both extremely server-version-specific ... the only method that will work when transferring a database to a different machine architecture." `pg_dumpall` for roles/tablespaces (`--globals-only`); custom format compresses and "tables can be restored selectively" with `pg_restore`; parallel dump `-j` (directory format only); roles must exist before restore. — [25.1 SQL Dump](https://www.postgresql.org/docs/current/backup-dump.html).
- File-system backup: "The database server *must* be shut down in order to get a usable backup. Half-way measures such as disallowing all connections will *not* work"; cannot restore individual tables/databases (needs `pg_xact`); "file system backups only work for complete backup and restoration of an entire database cluster"; frozen snapshots work while running but "the snapshots *must* be simultaneous" across volumes and WAL must be included; typically larger than an SQL dump but faster; two-pass `rsync --checksum`. — [25.2 File System Level Backup](https://www.postgresql.org/docs/current/backup-file.html).
- Continuous archiving/PITR: `wal_level = replica`, `archive_mode = on`, `archive_command`/`archive_library` returning zero "if and only if it succeeds"; base backups via `pg_basebackup` or `pg_backup_start`/`pg_backup_stop`; recovery via `restore_command` + `recovery.signal` with targets by time, named restore point or transaction ID; new timeline after each recovery. Advantages: "We do not need a perfectly consistent file system backup"; "continuous backup can be achieved simply by continuing to archive the WAL files"; restore "to its state at any time since your base backup"; warm standby. Requirements/limits: "set up and test your procedure for archiving WAL files *before* you take your first base backup"; archive commands "should generally be designed to refuse to overwrite any pre-existing archive file"; whole-cluster only; "requires a lot of archival storage"; config files not restored; "pg_dump and pg_dumpall ... cannot be used as part of a continuous-archiving solution"; "consider keeping several backup sets"; after recovery "Inspect the contents of the database to ensure you have recovered to the desired state." — [25.3 Continuous Archiving and PITR](https://www.postgresql.org/docs/current/continuous-archiving.html). **MANDATORY** (archive test before first base backup; non-overwriting archive).
- pgBackRest 2.60.0 (released 18 Oct 2026): parallel backup/restore with lz4/zstd ("Compression is usually the bottleneck"); full/differential/incremental at file or block level; "Checksums are calculated for every file in the backup and rechecked during a restore or verify"; delta restore; multiple repositories (local short-retention + remote long-retention); repository encryption; S3/Azure/GCS/SFTP; resume; async parallel WAL push/get. — [pgBackRest](https://pgbackrest.org/) (updated 17 Oct 2026). **RECOMMENDED** tooling.

**MySQL**
- Physical backups "consist of raw copies of the directories and files"; "faster than logical because they involve only file copying without conversion"; "more compact"; "portable only to other machines that have identical or similar hardware characteristics"; tools `mysqlbackup` (MySQL Enterprise Backup) or file-system commands for MyISAM. Logical backups "save information represented as logical database structure ... and content"; "slower"; "larger"; "machine independent and highly portable"; tools `mysqldump`, `SELECT ... INTO OUTFILE`; granularity server/database/table. Online vs offline ("often taken from a replica that can be taken offline without harming availability"); "warm" backups; snapshots via third-party LVM/ZFS/Veritas; "A full backup includes all data ... An incremental backup consists of the changes made ... made possible by enabling the server's binary log"; point-in-time recovery "typically follows a full recovery" and replays binary log changes; "MySQL itself does not provide" scheduling/compression/encryption (Enterprise Backup compresses; use filesystem utilities). — [MySQL 8.4 §9.1 Backup and Recovery Types](https://dev.mysql.com/doc/refman/8.4/en/backup-types.html); chapter intro — [§9 Backup and Recovery](https://dev.mysql.com/doc/refman/8.4/en/backup-and-recovery.html) ("so that you can recover your data and be up and running again in case problems occur, such as system crashes, hardware failures, or users deleting data by mistake").
- PITR: "The source of information for point-in-time recovery is the set of binary log files generated subsequent to the full backup operation. Therefore ... binary logging must be enabled on it, which is the default setting for MySQL 8.4"; `SHOW BINARY LOGS`; `mysqlbinlog binlog_files | mysql -u root -p`; select by event times or positions; review output in a temp file before applying. — [§9.5 Point-in-Time Recovery](https://dev.mysql.com/doc/refman/8.4/en/point-in-time-recovery.html) and [§9.5.1 Using Binary Log](https://dev.mysql.com/doc/refman/8.4/en/point-in-time-recovery-binlog.html).
- Percona XtraBackup 8.0 (8.0.35-36, 4 Jun 2026; 8.0 EOL June 2026, upgrade to 8.4 recommended): "an open source hot backup utility for MySQL-based servers"; full/incremental/partial backups, compression, encryption, streaming, PITR, xbcloud; does not back up pre-8.0 databases or TokuDB. — [Percona XtraBackup 8.0](https://docs.percona.com/percona-xtrabackup/8.0/index.html).

**SQL Server / Azure SQL (Microsoft)**
- "Backing up is the only way to protect your data." Terms: full backup ("all the data ... and also enough log to allow for recovering"), differential ("only the data that has changed since that base"), log backup (full recovery model), recovery models simple/full/bulk-logged ("determines what types of backup and restore scenarios the database supports"). Strategy: "You don't have a backup strategy until you successfully restore backups in every combination included in your restore strategy and test each restored database for physical consistency"; "You don't have a restore strategy until you test your backups ... run `DBCC CHECKDB`"; "Place your database backups in a separate physical location or on a separate device"; "Encrypt database backups and, if possible, compress them"; `BACKUP CHECKSUM`, `RESTORE VERIFYONLY`; least-privilege backup accounts; document in a run book; "As backups age, the risk of data loss grows"; restoring untrusted `.bak` files is a high-risk operation (arbitrary code execution). — [Back up and restore of SQL Server databases](https://learn.microsoft.com/en-us/sql/relational-databases/backup-restore/back-up-and-restore-of-sql-server-databases) (ms.date 2026-08-27). **MANDATORY** (restore testing; separate storage; encryption).
- Azure SQL Database: point-in-time restore "to an earlier point in time within its retention period" on the same server; restore of deleted databases (but deleting the server deletes PITR backups — only LTR survives); long-term retention; geo-restore "uses geo-replicated backups" and "could potentially result in data loss ... because Azure Geo-Redundant Storage (GRS) replicates data asynchronously"; "Geo-restore is the most basic disaster-recovery solution available in SQL Database ... It doesn't guarantee that the target region will have the capacity"; "For business-critical applications ... use failover groups"; "conduct periodic drills." — [Azure SQL: Restore a database from a backup](https://learn.microsoft.com/en-us/azure/azure-sql/database/recovery-using-backups) (ms.date 2026-01-26).

**Oracle**
- "RMAN is the preferred solution for database backup and recovery." "Physical backups are the foundation of any sound backup and recovery strategy. Logical backups [Data Pump] are a useful supplement ... but are not sufficient protection against data loss without physical backups." "User errors are estimated to be the greatest single cause of database downtime." Flashback "view past states of data and rewind your database without restoring backups"; Flashback Table recovers tables "without taking any part of the database offline"; Flashback Database requires a fast recovery area; "developing a disaster recovery strategy to protect against catastrophic data loss" is a core part of backup and recovery. — [Oracle 19c Backup and Recovery User's Guide: Introduction](https://docs.oracle.com/en/database/oracle/oracle-database/19/bradv/introduction-backup-recovery.html). **MANDATORY** (physical backups as foundation).
- Data Guard "create[s], maintain[s], manage[s], and monitor[s] one or more standby databases to enable production Oracle databases to survive disasters and data corruptions"; physical (block-for-block), logical, snapshot standbys; protection modes Maximum Availability, Maximum Performance (default), Maximum Protection ("no data loss"); switchover (planned, no loss) vs failover; "Take backups on a physical standby database instead of the production database" — i.e., RMAN backups are still taken even with a standby. — [Oracle 19c Data Guard Concepts](https://docs.oracle.com/en/database/oracle/oracle-database/19/sbydb/introduction-to-oracle-data-guard-concepts.html).

**MongoDB (9.0)**
- Methods: Cloud Manager/Ops Manager ("creates snapshots at set intervals and offers point-in-time recovery"; sharded-cluster consistency "Guaranteed"; requires Enterprise Server; "Sharded cluster snapshots are difficult to achieve with other MongoDB backup methods"); filesystem snapshots ("you must have journaling enabled and the journal must reside on the same logical volume"; sharded clusters: disable the balancer and snapshot every shard plus a config server at about the same moment; PITR "No"; RPO "High"); copying data files ("you must stop all writes"; no PITR; larger); `mongodump`/`mongorestore` ("tools for backing up and restoring small MongoDB deployments"; RTO/RPO "High"; requires write lock impact on sharded clusters). Encrypted storage: cold-snapshot restores need `--eseDatabaseKeyRollover`. "When deploying MongoDB in production, have a backup and restore strategy." — [MongoDB: Backup Methods for a Self-Managed Deployment](https://www.mongodb.com/docs/manual/core/backups/) (v9.0). **RECOMMENDED** (snapshots/managed backups over mongodump for non-trivial deployments).

**Cloud providers and DR strategies**
- AWS DR strategies: Backup and restore ("suitable approach for mitigating against data loss or corruption"; redeploy infrastructure with IaC or risk exceeding RTO; back up code/config/AMIs too); Pilot light (data replicated, core infrastructure provisioned but "switched off"); Warm standby ("scaled down, but fully functional, copy ... always-on in another Region"); Multi-site active/active ("most complex and costly ... recovery time to near zero for most disasters ... however data corruption may need to rely on backups"). "Continuous replication of data has the advantage of being the shortest time (near zero) to back up your data, but may not protect against disaster events such as data corruption or malicious attack (such as unauthorized data deletion) as well as point-in-time backups." "Backup and recovery are still required and should be tested regularly." "Your backup strategy must include testing your backups"; "Implementing a scheduled periodic data restore is a good idea as data restore from backup is a control plane operation." Prefer data-plane operations for failover; manual-initiated but automated failover often used; separate accounts per Region for isolation; cross-account/cross-Region AWS Backup copies protect against insider threat or account compromise; S3 versioning for human-error disasters. — [AWS: Disaster recovery options in the cloud](https://docs.aws.amazon.com/whitepapers/latest/disaster-recovery-workloads-on-aws/disaster-recovery-options-in-the-cloud.html) (n.d.). **MANDATORY** (test DR; keep point-in-time backups alongside replication); **OPTIONAL/CONTEXTUAL** (tier choice by RTO/RPO/cost).
- Amazon RDS automated backups: storage-volume snapshot of the entire instance during the backup window, retained per the backup retention period, "you can recover your DB instance to any point in time during the backup retention period"; first snapshot full, later ones incremental; backups stored in S3; backups require the `available` state; manual snapshots "are not deleted when an instance is deleted" (up to 100 per Region); automated backups deleted with the instance unless retained; cross-Region copies increase storage in the destination. — [RDS: Introduction to backups](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_WorkingWithAutomatedBackups.html) (n.d.).
- Cloud SQL (PostgreSQL): on-demand backups "can be created at any time"; automated backups "taken on a scheduled cadence, such as hourly, daily, weekly, or monthly" and "are needed to support point-in-time recovery"; final backups before deletion (default 30 days); automated retention from 1 day to 10 years depending on option (troubleshooting text says 1–365 — internal inconsistency noted); backups "are stored separately from the Cloud SQL instance"; "encrypted by default using Google-managed or Customer-Managed Encryption keys (CMEK)"; "Cloud SQL retains the backups of deleted instances for four days." — [Cloud SQL: About backups](https://docs.cloud.google.com/sql/docs/postgres/backup-recovery/backups) (n.d.; references a 31 Jul 2025 release note).

**Ransomware, 3-2-1, immutability, restore drills**
- CISA/MS-ISAC/NSA/FBI #StopRansomware Guide (Sept 2023): "Maintain offline, encrypted backups of critical data, and regularly test the availability and integrity of backups in a disaster recovery scenario"; "many ransomware variants attempt to find and subsequently delete or encrypt accessible backups"; maintain and update "golden images" and version-controlled infrastructure-as-code templates offline; retain backup hardware; consider multi-cloud; immutable cloud storage can protect data but "may not meet certain compliance criteria" and misconfiguration can be costly; recover from offline, encrypted backups prioritised by critical services. — [CISA #StopRansomware Guide](https://www.cisa.gov/stopransomware/ransomware-guide) (Sept 2023). **MANDATORY** (offline/encrypted copy; restore testing).
- 3-2-1 rule (US-CERT/CISA "Data Backup Options", Paul Ruggiero, Carnegie Mellon University, 2012): "3 – Keep 3 copies of any important file: 1 primary and 2 backups. 2 – Keep the files on 2 different media types to protect against different types of hazards. 1 – Store 1 copy offsite"; attributed to Peter Krogh, *The DAM Book*, 2nd ed., O'Reilly 2009, p. 207. — [Data Backup Options (PDF)](https://www.cisa.gov/sites/default/files/publications/data_backup_options.pdf) (2012). **RECOMMENDED** baseline.
- Vendor extension 3-2-1-1-0: "one immutable copy" ("stored in an immutable or air-gapped location") and "zero recovery errors" via automated verification; rationale "ransomware increasingly targets backups." — [Veeam: 3-2-1 backup rule](https://www.veeam.com/blog/321-backup-rule.html), Julia Furst Morgado, 5 Feb 2024 (updated 3 Jul 2026). Lower authority (vendor marketing); consistent with CISA.

### Inferences
- Across PostgreSQL, MySQL, SQL Server and Oracle the recovery architecture is identical in shape: periodic physical base backup + continuous log archive = PITR; logical dumps are for portability/partial restore, not for RPO. A framework can specify "RPO is bounded by log-archive frequency, not backup frequency."
- Every vendor and standards body opened makes restore testing a precondition of having a backup at all (Microsoft's wording is the strongest); this is the single most universal MANDATORY rule in this research.
- Cloud-managed PITR windows (RDS retention period; Azure PITR retention; Cloud SQL automated backups needed for PITR) satisfy short-horizon RPO but not long-term retention or account-compromise scenarios, which is why AWS recommends cross-account copies and Azure LTR exists.

### Gaps
- Specific numeric retention limits (e.g., RDS 0–35 days, Azure 1–35 days PITR / 10-year LTR, "latest restorable time within 5 minutes") were **not present** on the pages fetched and are therefore not asserted here.
- The AWS whitepaper's RPO/RTO ranges per tier are in a figure, not in the fetched text, so no numbers are quoted.
- ISO/IEC 27031 and ISO 22313 were not opened; MySQL Enterprise Backup and Oracle RMAN command-level docs, SQL Server Always On AG docs, and Google Cloud SQL PITR log-retention days were not fetched.
- No source quantified legal/regulatory retention requirements for database backups.

## KQ5. Conflicts and controversies across sources

### Takeaway
The sources disagree most on (a) whether migrations must be reversible, (b) state-based vs. migration-based authoring, (c) triggers vs. binlog for online schema change, (d) whether data changes belong in migrations, and (e) how far replication/snapshots count as backup; several apparent conflicts dissolve once engine version (PostgreSQL 11 defaults) or workload size is taken into account.

### Cited Findings
- **Reversibility.** GitLab: "Migrations must be reversible" (with documented exceptions) — [GitLab style guide](https://docs.gitlab.com/ee/development/migration_style_guide.html). Braintree: "Rollbacks must not revert the database schema" — [Braintree 2019](https://gist.github.com/jcoleman/1e6ad1bf8de454c166da94b67537758b). Flyway: undo "assume[s] the whole migration succeeded" and is Teams-only; recommends backward-compatible schema so the *application* rolls back — [Flyway undo](https://documentation.red-gate.com/fd/undo-migrations-273973334.html); versioned page: "roll forward" — [Flyway versioned](https://documentation.red-gate.com/flyway/flyway-concepts/migrations/versioned-migrations). Liquibase: rollbacks are first-class but ~40 change types have no automatic inverse and "Rollback scripts need to be tested just like application code" — [Liquibase rollback](https://docs.liquibase.com/workflows/liquibase-community/using-rollback.html), [auto rollbacks](https://docs.liquibase.com/workflows/liquibase-community/automatic-custom-rollbacks.html). Prisma ORM 8: no down files; "a migration can go backwards" — [Prisma](https://www.prisma.io/docs/orm/prisma-migrate/understanding-prisma-migrate/mental-model). Rails/Django: reversible operations with `IrreversibleMigration`/`IrreversibleError` — [Rails](https://guides.rubyonrails.org/active_record_migrations.html), [Django](https://docs.djangoproject.com/en/5.2/topics/migrations/). *Resolution:* GitLab's reversibility and Braintree's "never revert schema" are compatible if `down` exists for emergencies but deployment safety comes from expand/contract.
- **State vs. migrations.** Redgate: state-based cannot preserve data on renames; migrations accumulate scripts; "Neither approach offers an ideal solution" — [Sheldon 2019](https://www.red-gate.com/simple-talk/devops/database-devops/introduction-to-devops-database-delivery/). Atlas: declarative needs live connection and real-time approval; proposes checked-in planned migrations — [Atlas](https://atlasgo.io/concepts/declarative-vs-versioned). Prisma ORM 8 likewise derives migrations from a contract but ledgers them — [Prisma](https://www.prisma.io/docs/orm/prisma-migrate/understanding-prisma-migrate/mental-model). Rails: schema dump is faster for new databases but "Your database remains the source of truth" — [Rails](https://guides.rubyonrails.org/active_record_migrations.html).
- **Generated vs. hand-written SQL.** Alembic: "not intended to be perfect"; renames are undetectable — [Alembic](https://alembic.sqlalchemy.org/en/latest/autogenerate.html). Django emulates ALTER on SQLite by table copy, "not recommended ... in a production environment" — [Django](https://docs.djangoproject.com/en/5.2/topics/migrations/). GitLab: "Prefer Arel and plain SQL over ActiveRecord syntax" in data migrations; avoid `change_column` — [GitLab](https://docs.gitlab.com/ee/development/migration_style_guide.html).
- **Adding a column with a default.** Braintree 2014 lists it as unsafe — [Braintree 2014](https://pgrs.net/2014/05/14/safe-operations-for-high-volume-postgresql/); PostgreSQL ≥ 11 docs: non-volatile default needs no rewrite — [PG ALTER TABLE](https://www.postgresql.org/docs/current/sql-altertable.html); strong_migrations flags only volatile defaults (PG) and expression defaults (MySQL) — [strong_migrations](https://github.com/ankane/strong_migrations); GitLab: "Use `add_column` for new columns with defaults. PostgreSQL 11 is the minimum version" — [GitLab](https://docs.gitlab.com/ee/development/migration_style_guide.html). *Version-dependent, not a true conflict.*
- **Data changes in migrations.** Rails guide discourages (use `maintenance_tasks`) — [Rails](https://guides.rubyonrails.org/active_record_migrations.html); GitLab allows them in post-deployment/batched background migrations with strict batching — [GitLab](https://docs.gitlab.com/ee/development/migration_style_guide.html); Django provides `RunPython` with historical models — [Django](https://docs.djangoproject.com/en/5.2/topics/migrations/); strong_migrations: run backfills outside the DDL transaction — [strong_migrations](https://github.com/ankane/strong_migrations); Stripe ran backfills offline on snapshots — [Stripe](https://stripe.com/blog/online-migrations).
- **Triggers vs. binlog for online schema change.** pt-osc relies on triggers and cannot run on tables that already have triggers — [pt-osc](https://docs.percona.com/percona-toolkit/pt-online-schema-change.html); gh-ost: "triggers to be the source of many limitations and risks" — [gh-ost](https://github.com/github/gh-ost); PlanetScale uses a ghost table kept in sync by the platform — [PlanetScale](https://planetscale.com/docs/concepts/safe-migrations).
- **Lock/time budgets differ by an order of magnitude.** Braintree ~2 s exclusive lock — [Braintree 2019](https://gist.github.com/jcoleman/1e6ad1bf8de454c166da94b67537758b); strong_migrations 10 s `lock_timeout` — [strong_migrations](https://github.com/ankane/strong_migrations); GitLab 15 s statement timeout, 3/10/20-minute migration classes — [GitLab](https://docs.gitlab.com/ee/development/migration_style_guide.html). *Lock hold time vs. total runtime are different quantities.*
- **Logical vs. physical backups.** Oracle: logical "not sufficient protection ... without physical backups" — [Oracle](https://docs.oracle.com/en/database/oracle/oracle-database/19/bradv/introduction-backup-recovery.html); PostgreSQL: pg_dump is the only cross-version/cross-architecture method but "cannot be used as part of a continuous-archiving solution" — [PG dump](https://www.postgresql.org/docs/current/backup-dump.html), [PG PITR](https://www.postgresql.org/docs/current/continuous-archiving.html); MySQL: physical faster/compact but hardware-bound, logical portable but slow/large — [MySQL](https://dev.mysql.com/doc/refman/8.4/en/backup-types.html); MongoDB: mongodump for "small deployments" — [MongoDB](https://www.mongodb.com/docs/manual/core/backups/). *Complementary, not either/or.*
- **Replication/snapshots as backup.** AWS: continuous replication "may not protect against ... data corruption or malicious attack ... as well as point-in-time backups"; active/active still needs backups — [AWS](https://docs.aws.amazon.com/whitepapers/latest/disaster-recovery-workloads-on-aws/disaster-recovery-options-in-the-cloud.html); Oracle Data Guard protects against "data corruptions" and "administrative error" yet backups are offloaded to the standby, not replaced — [Data Guard](https://docs.oracle.com/en/database/oracle/oracle-database/19/sbydb/introduction-to-oracle-data-guard-concepts.html); Azure geo-restore "most basic" DR with possible data loss vs. failover groups — [Azure](https://learn.microsoft.com/en-us/azure/azure-sql/database/recovery-using-backups); PostgreSQL/MongoDB: filesystem snapshots valid only if simultaneous / journal on same volume — [PG file backup](https://www.postgresql.org/docs/current/backup-file.html), [MongoDB](https://www.mongodb.com/docs/manual/core/backups/); CISA: ransomware targets reachable backups, so offline copies — [CISA](https://www.cisa.gov/stopransomware/ransomware-guide).
- **Immutable storage.** Veeam promotes an immutable copy as part of 3-2-1-1-0 — [Veeam](https://www.veeam.com/blog/321-backup-rule.html); CISA endorses it "with caution" over compliance and misconfiguration cost — [CISA](https://www.cisa.gov/stopransomware/ransomware-guide).

### Inferences
- The framework should adopt forward-only, backward-compatible migrations as the safety mechanism, retain `down`/undo as an optional convenience with tested scope, and require backups (not rollbacks) as the recovery mechanism — a position all three of Flyway, Braintree and GitLab are consistent with.
- "Replication is not backup" is supported explicitly by AWS and implicitly by every vendor that still takes log-archive backups alongside standbys; the framework can state it as MANDATORY with those citations.

### Gaps
- No single source reconciles DBA-authored vs developer-authored migrations quantitatively; the controversy is visible only as differing process designs.
- Snapshot-based backup vendors' counter-arguments (e.g., storage-array consistency groups) were not researched.
