## Q1. ACID origins and definitions — Gray (1981), Haerder & Reuter (1983), and the "C" problem

### Takeaway
Gray's 1981 paper defined transactions by three properties (consistency, atomicity, durability) with isolation handled under locking rather than named; Haerder & Reuter (1983) added Isolation and coined "ACID", explicitly defining consistency as "the database contains the results of successful transactions" — i.e., a property guaranteed by correct transactions, which is why later critics (Kleppmann's DDIA; Brewer) say the "C" is an application-level property distinct from CAP's "C".

### Cited Findings
- Gray's abstract: "A transaction is a transformation of state which has the properties of atomicity (all or nothing), durability (effects survive failures) and consistency (a correct transformation)." The paper is Tandem TR 81.3, June 1981, and "Appeared in Proceedings of Seventh International Conference on Very Large Databases, Sept. 1981." — [The Transaction Concept: Virtues and Limitations](https://jimgray.azurewebsites.net/papers/thetransactionconcept.pdf) (June 1981)
- Gray's property list, using a contract/wedding analogy: "Consistency: the transaction must obey legal protocols. Atomicity: it either happens or it does not; either all are bound by the contract or none are. Durability: once a transaction is committed, it cannot be abrogated." He also states that "Adjustment of a bad transaction is done via further compensating transactions" and lists open problems: nested transactions and "handling transactions which last for extremely long times (days or months)." The word "ACID" does not appear in the paper and "isolation" appears only once, not as a named property. — [The Transaction Concept](https://jimgray.azurewebsites.net/papers/thetransactionconcept.pdf) (June 1981)
- Haerder & Reuter: "These four properties, atomicity, consistency, isolation, and durability (ACID), describe the major highlights of the transaction paradigm ... We therefore consider the question of whether the transaction is supported by a particular system to be the ACID test of the system's quality." Published in ACM Computing Surveys, Vol. 15, No. 4, December 1983, pp. 287-317 (DOI 10.1145/289.291; the ACM DL page returned HTTP 403, so the University of Texas course copy was used). — [Principles of Transaction-Oriented Database Recovery](https://www.cs.utexas.edu/~dsb/cs386d/Readings/Recovery/Principles-of-Recovery.pdf) (December 1983)
- Haerder & Reuter definitions: "Isolation. Events within a transaction must be hidden from other transactions running concurrently. If this were not the case, a transaction could not be reset to its beginning..."; "Durability. Once a transaction has been completed and has committed its results to the database, the system must guarantee that these results survive any subsequent malfunctions"; and the consistency definition used for recovery: "a database is consistent if and only if it contains the results of successful transactions ... A transaction, in turn, must not see anything but effects of complete transactions ... and will then, by definition, create a consistent update of the database." They also note that "the effects of an inevitable incorrect transaction ... can only be removed by countertransactions." — [Principles of Transaction-Oriented Database Recovery](https://www.cs.utexas.edu/~dsb/cs386d/Readings/Recovery/Principles-of-Recovery.pdf) (December 1983)
- Brewer (2012) separates the two "C"s: ACID consistency "covers integrity rules such as unique keys, and it cannot be fully maintained across partitions," whereas CAP's consistency "means single-copy consistency"; quote: "ACID consistency also cannot be maintained across partitions." — [CAP Twelve Years Later: How the "Rules" Have Changed](https://www.infoq.com/articles/cap-twelve-years-later-how-the-rules-have-changed/) (InfoQ republication 2012-05-30; original IEEE Computer, Feb 2012)
- Kleppmann (Hermitage announcement) on what ACID databases actually deliver: most so-called ACID databases "do not by default guarantee that your transactions are protected from race conditions," and isolation levels are "defined by implementation detail, not because someone thought they'd make a great API." — [Hermitage: Testing the "I" in ACID](https://martin.kleppmann.com/2014/11/25/hermitage-testing-the-i-in-acid.html) (2014-11-25)
- Kleppmann's Strange Loop 2015 talk frames the question "What does ACID actually mean? What race conditions can you get with weak isolation (such as 'read committed' and 'repeatable read')" and states "The purpose of transactions is to make application code simpler." — [Transactions: myths, surprises and opportunities](https://martin.kleppmann.com/2015/09/26/transactions-at-strange-loop.html) (2015-09-26)

### Inferences
- Because Haerder & Reuter define consistency circularly through "successful transactions" and Gray defines it as obeying "legal protocols", consistency in ACID is a contract the application's transaction code must satisfy; the database supplies A, I, D and only those integrity rules it can declare (constraints). For schema design this means: every invariant that can be expressed as a constraint (CHECK, UNIQUE, FK, exclusion) should be, because the engine will enforce it under every isolation level, whereas invariants enforced only by read-then-write application logic depend on the isolation level (see Q2).
- Gray's 1981 acknowledgement that long transactions are an unsolved limitation, together with Haerder & Reuter's "countertransactions", is the lineage of the Saga/compensation patterns in Q5.

### Gaps
- DDIA (Kleppmann, O'Reilly) itself is not freely available online; the specific DDIA passage ("the letter C doesn't really belong in ACID", attributing the quip to Joe Hellerstein) surfaced only in secondary summaries returned by web search (e.g., a Reddit mirror and a Japanese wiki) and could not be verified against the book's text. ## Q2. Isolation levels and anomalies — ANSI SQL, Berenson et al. (1995), SSI (Ports & Grittner 2012), per-engine semantics, Hermitage, Jepsen

### Takeaway
ANSI/ISO SQL defines four levels by three phenomena (dirty read, non-repeatable/fuzzy read, phantom); Berenson et al. showed those English definitions are ambiguous, added dirty write (P0), lost update (P4), read skew (A5A) and write skew (A5B), and defined Snapshot Isolation (SI), which is incomparable with Repeatable Read. In practice: PostgreSQL REPEATABLE READ = SI, PostgreSQL SERIALIZABLE = SSI (true serializability, <7% overhead); MySQL InnoDB's default REPEATABLE READ is weaker than both SI and ANSI RR (lost update, G-single, G2-item observed); SQL Server's defaults are lock-based (RCSI/SNAPSHOT optional); Oracle's SERIALIZABLE is SI (write skew possible); MongoDB gives SI only with read concern "snapshot" plus write concern "majority".

### Cited Findings

**ANSI phenomena and the 1995 critique**
- PostgreSQL's statement of the SQL-standard phenomena: dirty read ("reads data written by a concurrent uncommitted transaction"), nonrepeatable read ("re-reads data ... and finds it modified by another transaction that committed after the first read"), phantom read ("re-executes a query ... and finds the set of matching rows changed"), plus PostgreSQL's own fourth phenomenon, serialization anomaly ("result of committing a group of transactions is inconsistent with all possible one-at-a-time orderings"). — [PostgreSQL 18: 13.2 Transaction Isolation](https://www.postgresql.org/docs/current/transaction-iso.html) (n.d.; PostgreSQL 18.6 docs)
- Berenson, Bernstein, Gray, Melton, O'Neil, O'Neil: the ANSI SQL-92 phenomena "fail to characterize several popular isolation levels, including standard locking implementations"; the English definitions "are ambiguous" and admit a strict and a broad interpretation, and the paper argues "The Broad interpretation is the correct one." Issued as MSR-TR-95-51, June 1995, and printed as "Proc. ACM SIGMOD 95, pp. 1-10, San Jose, CA, June 1995." — [A Critique of ANSI SQL Isolation Levels](https://www.microsoft.com/en-us/research/publication/a-critique-of-ansi-sql-isolation-levels/) (June 1995); PDF: [tr-95-51.pdf](https://www.microsoft.com/en-us/research/wp-content/uploads/2016/02/tr-95-51.pdf)
- Phenomena definitions from the PDF: P0 Dirty Write "w1[x]...w2[x]...((c1 or a1) and (c2 or a2) in any order)" — "If T1 or T2 then performs a ROLLBACK, it is unclear what the correct data value should be"; P1 Dirty Read; P2 Fuzzy Read; P3 Phantom "r1[P]...w2[y in P]..."; P4 Lost Update "r1[x]...w2[x]...w1[x]...c1", with the comment "P4 is possible at the READ COMMITTED isolation level" and that P4 "is useful in distinguishing isolation levels intermediate in strength between READ COMMITTED and REPEATABLE READ"; A5A Read Skew "r1[x]...w2[x]...w2[y]...c2...r1[y]..."; A5B Write Skew "r1[x]...r2[y]...w1[y]...w2[x]...(c1 and c2 occur)". — [tr-95-51.pdf](https://www.microsoft.com/en-us/research/wp-content/uploads/2016/02/tr-95-51.pdf) (June 1995)
- Snapshot Isolation as defined there: each transaction "reads data from a snapshot of the (committed) data as of" its start; "first-committer-wins precludes P0 (dirty writes), and the timestamp mechanism prevents P1 (dirty reads), so Snapshot Isolation is no weaker than READ COMMITTED"; "Snapshot Isolation histories prohibit histories with anomaly A3, but allow A5B, while REPEATABLE READ" does the reverse; "Snapshot Isolation does not preclude P3"; and "Snapshot Isolation is non-serializable". Table 4 ("Isolation Types Characterized by Possible Anomalies Allowed") shows Snapshot: P0 Not Possible, P1 Not Possible, P4 Not Possible, P2 Not Possible, P3 Sometimes Possible, A5A Not Possible, A5B Possible. — [tr-95-51.pdf](https://www.microsoft.com/en-us/research/wp-content/uploads/2016/02/tr-95-51.pdf) (June 1995)

**Serializable Snapshot Isolation (PostgreSQL 9.1+)**
- Ports & Grittner (PVLDB 5(12), 1850-1861, VLDB Istanbul, August 2012): PostgreSQL 9.1's serializable level is "the first implementation of SSI in a production database release" and "the first in a database that did not previously have a lock-based serializable isolation level"; it "has a performance cost of less than 7% relative to snapshot isolation, and outperforms two-phase locking significantly on some workloads." — [Serializable Snapshot Isolation in PostgreSQL](https://drkp.net/papers/ssi-vldb12.pdf) (August 2012)
- Theory used: "Every cycle in the serialization graph contains ... two adjacent rw-antidependency edges" and "T3 must be the first transaction in the cycle to commit" (Fekete et al.); SSI "checks for a 'dangerous structure' of two adjacent rw-antidependencies" and aborts one transaction, which is "a less restrictive requirement" than S2PL or OCC. Reads are tracked with "SIREAD" locks that never block; the paper adds "safe snapshots" so read-only transactions can run "without any SSI overhead or abort risk", a memory-bounding summarization technique, and integration with "replication systems, two-phase commit, and subtransactions." Motivation included that "read-only transactions can be involved in SI anomalies" (Fekete et al.), and a court-system batch example where a REPORT transaction could show a batch total that omitted a receipt. — [Serializable Snapshot Isolation in PostgreSQL](https://drkp.net/papers/ssi-vldb12.pdf) (August 2012)

**PostgreSQL (official docs, 18.6)**
- Default is Read Committed. "Read Uncommitted" can be requested but "PostgreSQL treats it as Read Committed", described as "the only sensible way to map the standard isolation levels to PostgreSQL's multiversion concurrency control architecture." Table 13.1: Repeatable Read — phantom read "Allowed, but not in PG"; serialization anomaly "Possible"; Serializable — all four "Not possible". — [PostgreSQL 18: Transaction Isolation](https://www.postgresql.org/docs/current/transaction-iso.html) (n.d.)
- Read Committed: each statement "sees a snapshot as of the moment that statement begins"; UPDATE/DELETE/SELECT FOR UPDATE wait for an in-progress writer and then re-evaluate the WHERE clause against the new row version; the docs show a `DELETE ... WHERE hits = 10` that has no effect after a concurrent `UPDATE ... SET hits = hits + 1`, i.e., a single command can see an inconsistent snapshot. — [PostgreSQL 18: Transaction Isolation](https://www.postgresql.org/docs/current/transaction-iso.html) (n.d.)
- Repeatable Read: snapshot taken at the first non-transaction-control statement; the docs state this is Snapshot Isolation "as described in the academic literature" and stronger than the standard requires; a concurrent committed update of a target row raises `ERROR: could not serialize access due to concurrent update`, and "applications must be prepared to retry transactions"; read-only transactions never hit this. Before PostgreSQL 9.1, requesting Serializable gave this behavior. The docs warn the result "may not always match a serial execution" (batch control record example) and that enforcing business rules there "may require explicit locks." — [PostgreSQL 18: Transaction Isolation](https://www.postgresql.org/docs/current/transaction-iso.html) (n.d.)
- Serializable: works like Repeatable Read plus monitoring for serialization anomalies via predicate locks (`pg_locks` mode `SIReadLock`) that "never block and cannot cause deadlocks"; a failed transaction gets `ERROR: could not serialize access due to read/write dependencies among transactions`; "Serialization failures always return SQLSTATE '40001'" and applications "need a general retry mechanism"; data read in a transaction that later aborts "must not be trusted." Unique-constraint violations may surface that a serial execution would not produce, so inserting transactions should check key existence first. `SERIALIZABLE READ ONLY DEFERRABLE` waits for a safe snapshot. Tuning advice: declare `READ ONLY`, limit connections (pool), keep transactions small, avoid "idle in transaction" (use `idle_in_transaction_session_timeout`), remove explicit `SELECT FOR UPDATE/SHARE` when Serializable already protects, and raise `max_pred_locks_per_transaction/relation/page` if predicate locks are being promoted to relation level (sequential scans always take a relation-level predicate lock). — [PostgreSQL 18: Transaction Isolation](https://www.postgresql.org/docs/current/transaction-iso.html) (n.d.)
- Sequences are non-transactional in effect: changes to sequences "are immediately visible to other transactions and are not rolled back on abort." — [PostgreSQL 18: Transaction Isolation](https://www.postgresql.org/docs/current/transaction-iso.html) (n.d.)

**MySQL InnoDB (official docs, 8.4)**
- Default is REPEATABLE READ. Under it, "Consistent reads within the same transaction read the snapshot established by the first read"; locking reads (SELECT ... FOR UPDATE/FOR SHARE), UPDATE and DELETE on a unique index with a unique search condition lock only the index record, otherwise they use "gap locks or next-key locks" over the scanned range to block inserts. The page warns against mixing locking statements and non-locking SELECTs in one REPEATABLE READ transaction, because non-locking reads use the read view while locking statements see the latest committed state; it notes SERIALIZABLE is typically what is wanted in that case. — [MySQL 8.4: 17.7.2.1 Transaction Isolation Levels](https://dev.mysql.com/doc/refman/8.4/en/innodb-transaction-isolation-levels.html) (n.d.)
- READ COMMITTED: each consistent read "sets and reads its own fresh snapshot"; locks only index records (gap locking only for FK and duplicate-key checks), so "phantom rows can occur"; non-matching rows are unlocked after WHERE evaluation; "semi-consistent read" for UPDATE; only row-based binary logging is supported. READ UNCOMMITTED: SELECTs may read earlier row versions ("dirty reads"). SERIALIZABLE: like REPEATABLE READ but with autocommit disabled InnoDB "implicitly converts plain SELECTs to SELECT ... FOR SHARE"; described as used mainly for XA and troubleshooting. — [MySQL 8.4: Transaction Isolation Levels](https://dev.mysql.com/doc/refman/8.4/en/innodb-transaction-isolation-levels.html) (n.d.)

**SQL Server / Azure SQL (official docs)**
- READ COMMITTED "is the SQL Server default." With `READ_COMMITTED_SNAPSHOT OFF` (the SQL Server default) shared locks are used and "Row locks are released before the next row is processed"; with it ON, row versioning presents "a transactionally consistent snapshot of the data as it existed at the start of the statement" and "READ_COMMITTED_SNAPSHOT ON is the default on Azure SQL Database and SQL database in Microsoft Fabric." REPEATABLE READ holds shared locks to transaction end but "Other transactions can insert new rows that match the search conditions ... which results in phantom reads." SNAPSHOT requires `ALLOW_SNAPSHOT_ISOLATION ON`, reads do not take locks, and a transaction started at another level cannot switch into SNAPSHOT. SERIALIZABLE places "Range locks ... in the range of key values that match the search conditions," equivalent to HOLDLOCK on all tables. Isolation level "doesn't affect the locks acquired to protect data modifications" (exclusive locks always held to end). Azure Synapse's default is READ UNCOMMITTED. Page metadata: ms.date 2025-09-26, updated_at 2026-11-02. — [SET TRANSACTION ISOLATION LEVEL (Transact-SQL)](https://learn.microsoft.com/en-us/sql/t-sql/statements/set-transaction-isolation-level-transact-sql) (2025-09-26)
- SNAPSHOT update-conflict error: "Msg 3960, Snapshot isolation transaction aborted due to update conflict" (mentioned in the UPDLOCK discussion of the locking guide). — [Transaction locking and row versioning guide](https://learn.microsoft.com/en-us/sql/relational-databases/sql-server-transaction-locking-and-row-versioning-guide) (ms.date 2026-04-22)

**Oracle (Concepts guide)**
- Oracle offers read committed (default: "Each query sees only data committed before the query began"), serializable ("sees only changes committed before the transaction began, plus its own changes"), and read-only; "Oracle never permits a dirty read." Serializable is implemented by extending statement-level read consistency to the whole transaction using undo data; a serializable transaction that tries to update a row changed by a transaction that committed after it began fails with `ORA-08177: Cannot serialize access for this transaction`. The page states serializable transactions "do not experience dirty reads, fuzzy reads, or phantom reads" and does not mention write skew. Readers never block writers and writers never block readers, except `SELECT ... FOR UPDATE`; deadlocks are detected automatically (`ORA-00060`); reports can fail with "snapshot too old" if undo is overwritten. The URL requested the 23 release; the served page identifies as Oracle AI Database 26. — [Oracle Database Concepts: Data Concurrency and Consistency](https://docs.oracle.com/en/database/oracle/oracle-database/23/cncpt/data-concurrency-and-consistency.html) (n.d.)

**MongoDB (official docs, 9.0)**
- Multi-document transactions require FCV 4.0 (replica sets) / 4.2 (sharded clusters); standalone deployments do not support them. Read concern "snapshot" returns "data from a snapshot of majority-committed data only if the transaction commits with w: 'majority'", and on sharded clusters the snapshot "is synchronized across shards"; with `w: 1` "a transaction can be rolled back on failover" and "majority"/"snapshot" read concerns "provide no guarantees." Client-level default write concern is `w: "majority"` in 5.0+ (previously `w: 1`). The page says a single-document write is atomic and that "distributed transactions have a greater performance cost than single-document writes, and they should not replace good schema design." — [MongoDB Manual: Transactions](https://www.mongodb.com/docs/manual/core/transactions/) (n.d.)
- Production considerations: a transaction must run "less than one minute" by default (`transactionLifetimeLimitSeconds`); transactions wait up to 5 ms for locks (`maxTransactionLockRequestTimeoutMillis`) and otherwise abort; "If a transaction is in progress and a write outside the transaction modifies a document that an operation in the transaction later tries to modify, the transaction aborts because of a write conflict"; reads inside a transaction "may return old data" and `findOneAndUpdate()` inside the transaction is the documented way to take a write lock on a document; each oplog entry must fit in 16 MB. Guidance: "When you encounter an error during individual operation in the transaction, abort and retry the transaction." — [MongoDB Manual: Production Considerations](https://www.mongodb.com/docs/manual/core/transactions-production-consideration/) (n.d.)

**Hermitage (Kleppmann) — what the levels actually prevent**
- "Hermitage is an attempt to nail down precisely what different database systems actually mean with their isolation levels." Databases tested: PostgreSQL, MySQL/InnoDB, Oracle, MS SQL Server, FDB SQL Layer, CockroachDB, YugabyteDB, Memgraph. Findings: PostgreSQL "repeatable read" is snapshot isolation (prevents G0, G1a, G1b, G1c, OTV, PMP, P4, G-single; not G2-item or G2), PostgreSQL "serializable" prevents all; MySQL "repeatable read" does not prevent P4 lost update, G2-item or G2 and only partially prevents PMP and G-single; Oracle "serializable" is snapshot isolation (G2-item not prevented); CockroachDB/YugabyteDB/FDB serializable prevent all listed anomalies. Licensed CC BY 4.0; no versions or last-updated date stated. — [ept/hermitage](https://github.com/ept/hermitage) (n.d.)
- Kleppmann's conclusions from the suite: PostgreSQL, MySQL and SQL Server "each have a 'repeatable read' level, but it means something different in each"; "read committed" had the same safety properties everywhere tested; SQL Server's default lock-based modes are "remarkably similar to System R in 1975." — [Hermitage: Testing the "I" in ACID](https://martin.kleppmann.com/2014/11/25/hermitage-testing-the-i-in-acid.html) (2014-11-25)

**Jepsen analyses**
- PostgreSQL 12.3 (Kyle Kingsbury): transactions at "serializable" on a single instance "were not, in fact, serializable" — occasional G2-item under normal operation, traced by Peter Geoghegan to conflict-detection crediting the wrong transaction ID when three transactions interact, present in 9.5.22 through 13 and patched in the next minor release (August 13, 2020). Also: "PostgreSQL 'repeatable read' is actually snapshot isolation", G2-item was observed under it, which "is specifically allowed by the standard" under the strict ANSI reading though Berenson et al. argued SI and RR are incomparable; Read Committed never showed G0/G1a/G1b; recommendation that the docs name "snapshot isolation" and the specific anomalies (G-single, G2-item, G2). — [Jepsen: PostgreSQL 12.3](https://jepsen.io/analyses/postgresql-12.3) (2020-06-12)
- MySQL 8.0.34 (Peter Alvaro & Kyle Kingsbury): InnoDB Repeatable Read "permits G2-item, G-single, and lost update, even on a healthy single node"; a transaction's reads can change within the same transaction (value read as "pebble" later reads as "moss"), so Hermitage's classification of it as Monotonic Atomic View "cannot be correct"; the authors conclude "MySQL Repeatable Read transactions cannot safely read a value and then write it"; Read Uncommitted/Read Committed/Serializable matched PL-1/PL-2/PL-3 locally; with `innodb_flush_log_at_trx_commit=1` no committed data was lost in crash tests, with 0 data was lost; AWS RDS Multi-AZ "Serializable" showed G-single and G2-item linked to `replica_preserve_commit_order` OFF. Recommendation: use Serializable or `SELECT ... FOR UPDATE` when repeatable reads are needed. — [Jepsen: MySQL 8.0.34](https://jepsen.io/analyses/mysql-8.0.34) (2023-12-19)
- MongoDB 4.2.6 (Kingsbury): default write concern "acknowledges writes from a single node, so committed writes can be rolled back" and "By default, client-level write concern is w: 1"; even with read concern snapshot and write concern majority Jepsen observed read skew (G-single), cyclic information flow (G1c), duplicated writes and a transaction reading its own future writes — "Roughly 10% of transactions (1461 of 13,914 in one history) showed cyclic dependencies" with no faults; MongoDB attributed this to a transaction-retry bug (SERVER-48307) scheduled for 4.2.8; "snapshot read concern does not guarantee a majority-committed snapshot unless the write concern is also majority." — [Jepsen: MongoDB 4.2.6](https://jepsen.io/analyses/mongodb-4.2.6) (2020-05-15)
- Amazon RDS for PostgreSQL 17.4 (Kingsbury): "Amazon RDS for PostgreSQL multi-AZ clusters do not ensure Snapshot Isolation"; healthy clusters showed Long Fork and other G-nonadjacent cycles in every version 13.15-17.4, but no write skew, suggesting Parallel Snapshot Isolation; not observed on single-node PostgreSQL at Repeatable Read; cause (per AWS's Sergey Melnik, 2025-05-03 update): primaries order visibility by an in-memory lock while secondaries order by WAL position. Recommendation: use only the writer endpoint for safety-critical reads, or ensure every safety-critical transaction includes a write. — [Jepsen: Amazon RDS for PostgreSQL 17.4](https://jepsen.io/analyses/amazon-rds-for-postgresql-17.4) (2025-04-29)
- Jepsen analyses index (checked for recency): newest entries are ParticleDB 1.1.4 (2026-10-31), Orkes Conductor 5.3.2 (2026-10-20), MariaDB Galera Cluster 12.1.2 (2026-03-16), NATS 2.12.1 (2025-12-08), TigerBeetle 0.16.11 (2025-06-06), Amazon RDS for PostgreSQL 17.4 (2025-04-29); earlier: PostgreSQL 12.3 (2020-06-12), MySQL 8.0.34 (2023-12-19), MongoDB 3.4.0-rc3 (2017-02-07), 3.6.4 (2018-10-23), 4.2.6 (2020-05-15), CockroachDB beta-20160829 (2017-02-16), TiDB 2.1.7 (2019-06-12), YugaByte DB 1.1.9 (2019-03-26) and 1.3.1 (2019-09-05). — [Jepsen Analyses](https://jepsen.io/analyses) (index, n.d.)

| Oracle 23/26 ([Concepts](https://docs.oracle.com/en/database/oracle/oracle-database/23/cncpt/data-concurrency-and-consistency.html)) | READ COMMITTED | Not offered ("never permits a dirty read") | Statement-level read consistency via undo/SCN | Not offered | SERIALIZABLE is transaction-level read consistency = SI | Named SERIALIZABLE but is SI ([Hermitage](https://github.com/ept/hermitage)) | SERIALIZABLE: write skew/G2-item not prevented (Hermitage) although docs say no dirty/fuzzy/phantom reads | ORA-08177 "Cannot serialize access"; ORA-00060 deadlock; ORA-01555 snapshot too old |

Reference (Jepsen models page): "Snapshot isolation allows write skew (A5B), which repeatable read prohibits. Repeatable read allows G-single over predicates, which snapshot isolation prohibits," so the two are incomparable; cursor stability, snapshot isolation and everything stronger are "unavailable" in asynchronous networks. — [Jepsen: Consistency Models](https://jepsen.io/consistency/models) (n.d.)

### Inferences
- "Serializable" is the only level name whose meaning is portable across PostgreSQL, SQL Server, CockroachDB/YugabyteDB; it is **not** portable to Oracle (SI) and is implementation-divergent in MySQL (lock-based with implicit FOR SHARE only when autocommit is off). A framework must key its guarantees to (engine, level, configuration flags such as RCSI/ALLOW_SNAPSHOT_ISOLATION, `replica_preserve_commit_order`, MongoDB read/write concern), never to the level name alone.
- Any read-then-write business rule (credit limit, stock >= 0, on-call minimum, double-entry balancing across rows) is exposed to write skew under PostgreSQL RR, Oracle SERIALIZABLE, SQL Server SNAPSHOT and MySQL RR. The portable remedies documented by the vendors are: (a) PostgreSQL SERIALIZABLE with 40001 retry; (b) explicit row locks (`SELECT ... FOR UPDATE`, SQL Server UPDLOCK/HOLDLOCK, MongoDB `findOneAndUpdate` inside the transaction); (c) declarative constraints that the engine checks at write time.
- Replicated read endpoints (RDS multi-AZ reader endpoints) can weaken a single-node guarantee below SI even when the primary is correct; reports that must be transactionally consistent with writes should read from the primary or be made read-write.

### Gaps
- The Oracle Concepts page gives no version date; the served page identifies as "Oracle AI Database 26" even though the 23 URL was fetched, so exact release provenance is uncertain.
- Hermitage does not state the engine versions tested or a last-updated date (the repository shows 62 commits). Its MySQL result is partly superseded by Jepsen 2023 (MAV classification disputed).
- No Jepsen analysis of a current SQL Server, Oracle or Spanner release exists in the index; conclusions for those rest on vendor docs and Hermitage.

## Q3. MVCC vs locking: optimistic/pessimistic control, version columns, FOR UPDATE, deadlocks, lock escalation, bloat, advisory locks

### Takeaway
All five engines implement MVCC-style readers-don't-block-writers for at least one mode, but each pays differently: PostgreSQL leaves dead tuples that VACUUM must reclaim and that long transactions pin; SQL Server escalates fine-grained locks to table locks at 5,000 locks per statement; Oracle can hit "snapshot too old"; MongoDB aborts on write conflicts after 5 ms. The Optimistic Offline Lock (version/rowversion column checked in the UPDATE's WHERE clause) is the documented cross-engine pattern for conflicts spanning multiple system transactions, while `SELECT ... FOR UPDATE` and advisory locks are the pessimistic tools within one transaction.

### Cited Findings
- Row-level lock modes in PostgreSQL: FOR UPDATE, FOR NO KEY UPDATE, FOR SHARE, FOR KEY SHARE, with the conflict table (FOR UPDATE conflicts with all four; FOR KEY SHARE conflicts only with FOR UPDATE); "Row-level locks do not affect data querying"; under REPEATABLE READ/SERIALIZABLE "an error is thrown if a row to be locked has changed since the transaction started"; locking a row "can also cause a disk write." — [PostgreSQL 18: 13.3 Explicit Locking](https://www.postgresql.org/docs/current/explicit-locking.html) (n.d.)
- Deadlocks: "PostgreSQL automatically detects deadlocks and aborts one of the transactions," which one "is difficult to predict and should not be relied upon"; the docs' example is two account transfers updating rows 11111 and 22222 in opposite order. Guidance: acquire locks "in a consistent order across all applications", take the most restrictive mode first, otherwise "retry transactions that abort due to deadlocks", and avoid holding transactions open "while waiting for user input." — [PostgreSQL 18: Explicit Locking](https://www.postgresql.org/docs/current/explicit-locking.html) (n.d.)
- Advisory locks "have application-defined meanings"; they are "useful for pessimistic-locking patterns that fit poorly with MVCC", are faster than a table flag, "avoid table bloat", and are cleaned up at session end; session-level advisory locks ignore transaction semantics (a lock taken in a rolled-back transaction is still held), transaction-level ones release at transaction end; the docs warn that `SELECT pg_advisory_lock(id) FROM foo WHERE id > 12345 LIMIT 100` is dangerous because LIMIT may run after the lock call. Lock table size is bounded by `max_locks_per_transaction` x `max_connections`. — [PostgreSQL 18: Explicit Locking](https://www.postgresql.org/docs/current/explicit-locking.html) (n.d.)
- MVCC cost in PostgreSQL: "an UPDATE or DELETE of a row does not immediately remove the old version of the row"; VACUUM reclaims space, updates statistics and the visibility map, and prevents transaction ID wraparound (32-bit XIDs, modulo-2^32 arithmetic; "vacuum every table in every database at least once every two billion transactions"; warnings at 40 million remaining, refusal of new XIDs at 3 million). Recovery guidance names long-running transactions explicitly: "End long-running open transactions. You can find these by checking pg_stat_activity for rows where age(backend_xid) or age(backend_xmin) is large"; stale replication slots also hold back cleanup. Autovacuum is "optional but highly recommended" and enabled by default. — [PostgreSQL 18: 24.1 Routine Vacuuming](https://www.postgresql.org/docs/current/routine-vacuuming.html) (n.d.)
- SQL Server lock escalation triggers when "A single Transact-SQL statement acquires at least 5,000 locks on a single nonpartitioned table or index" (or per partition with `LOCK_ESCALATION = AUTO`), or when lock memory exceeds 24% of Database Engine memory (default `locks` = 0; ~100 bytes per lock); escalation converts row/key-range/page locks to table (or HoBT) locks and retries every additional 1,250 locks if blocked; mitigations: optimized locking, RCSI/SNAPSHOT/READ UNCOMMITTED to reduce shared locks, batch large deletes (`DELETE TOP (500)` loop), `ALTER TABLE ... SET (LOCK_ESCALATION = ...)`; trace flags 1211/1224 disable escalation instance-wide and risk error 1204. — [Transaction locking and row versioning guide](https://learn.microsoft.com/en-us/sql/relational-databases/sql-server-transaction-locking-and-row-versioning-guide) (ms.date 2026-04-22)
- SQL Server deadlock detection: a "lock monitor thread ... periodically initiates a search through all of the tasks" at a default interval of 5 seconds, dropping "to as low as 100 milliseconds" when deadlocks are frequent; the engine "chooses one of the tasks as a deadlock victim, and returns error 1205 to the application", releasing all the victim's locks; victim choice can be influenced with `SET DEADLOCK_PRIORITY`. — [Deadlocks guide](https://learn.microsoft.com/en-us/sql/relational-databases/sql-server-deadlocks-guide) (ms.date 2025-10-09)
- SQL Server `rowversion`: "automatically generated, unique binary numbers within a database", 8 bytes, "just an incrementing number and does not preserve a date or a time"; one per table; incremented on every insert/update "even if no row values are changed"; `timestamp` is a deprecated synonym. The documented optimistic-concurrency pattern: `UPDATE MyTest SET myValue = 2 OUTPUT inserted.myKey INTO @t(myKey) WHERE myKey = 1 AND RV = <myRv>;` then `IF (SELECT COUNT(*) FROM @t) = 0` raise an error. Explicitly "a poor candidate for keys, especially primary keys." — [rowversion (Transact-SQL)](https://learn.microsoft.com/en-us/sql/t-sql/data-types/rowversion-transact-sql) (ms.date 2017-07-22; updated 2026-10-19)
- Fowler/Rice, PoEAA: Optimistic Offline Lock "Prevents conflicts between concurrent business transactions by detecting a conflict and rolling back the transaction"; motivation is that "a business transaction spans several system transactions" so the DBMS alone cannot protect against lost updates; validation that a session's changes do not conflict must happen "in a single system transaction" with the updates; the optimistic variant assumes conflicts are unlikely, the pessimistic variant limits concurrency. (The web catalog page is a summary; the version-column mechanics are in the book chapter, not on the page.) — [Optimistic Offline Lock](https://martinfowler.com/eaaCatalog/optimisticOfflineLock.html) (2003-03-05)
- Oracle: "A row is locked only when a writer modifies it"; "A reader never blocks a writer, and a writer never blocks a reader", except `SELECT ... FOR UPDATE`; deadlocks detected automatically with `ORA-00060`; "snapshot too old" when undo is overwritten (set undo retention). — [Oracle Concepts: Data Concurrency and Consistency](https://docs.oracle.com/en/database/oracle/oracle-database/23/cncpt/data-concurrency-and-consistency.html) (n.d.)
- MySQL: under READ COMMITTED InnoDB releases record locks on non-matching rows after WHERE evaluation, which "reduces deadlocks but does not eliminate them"; the docs' two-session UPDATE example shows REPEATABLE READ holding x-locks on all five scanned rows versus READ COMMITTED releasing non-matching ones. — [MySQL 8.4: Transaction Isolation Levels](https://dev.mysql.com/doc/refman/8.4/en/innodb-transaction-isolation-levels.html) (n.d.)
- MongoDB: write conflicts abort the transaction, outside writes wait on documents the transaction has locked, and `findOneAndUpdate()` with `$set: { lockId: ObjectId() }` inside the transaction is the documented pessimistic-lock idiom; cache pressure can abort with `TransactionTooLargeForCache`. — [MongoDB: Production Considerations](https://www.mongodb.com/docs/manual/core/transactions-production-consideration/) (n.d.)
- PostgreSQL on explicit locks versus SSI: "Remove explicit locks, SELECT FOR UPDATE, and SELECT FOR SHARE when Serializable already provides the protection" (performance advice). — [PostgreSQL 18: Transaction Isolation](https://www.postgresql.org/docs/current/transaction-iso.html) (n.d.)

### Inferences
- Schema consequence of MVCC: a hot, frequently updated row (e.g., an account balance or a counter) produces dead tuples in PostgreSQL, write-conflict aborts in MongoDB/SI engines, and lock convoys in locking engines. Ledger-style append-only designs (Q6) convert hot updates into inserts and move balance derivation to summation or periodically materialized balances.
- The version column should be a monotonically increasing integer (or engine rowversion) owned by the aggregate root (Q6) so that a single compare-and-set UPDATE protects the whole business transaction; `updated_at` timestamps are not safe substitutes because they are not guaranteed unique or monotonic across sessions.

### Gaps
- `deadlock_timeout`, `SKIP LOCKED` and `NOWAIT` are not on the PostgreSQL explicit-locking page fetched (they live in other sections), so they are not cited here.
- The SQL Server locking guide was read only to character 100,000 of 176,855; the row-versioning internals (tempdb version store, 14-byte overhead) were not reached and are not cited.

## Q4. CAP and PACELC — Brewer, Gilbert & Lynch, Abadi, Kleppmann, Jepsen consistency map; implications for ERP/financial vs analytics

### Takeaway
CAP (Gilbert & Lynch's 2002 formalization) only constrains behavior during partitions; Brewer (2012) says the "2 of 3" reading is misleading and that systems should manage partitions explicitly with compensation; Abadi's PACELC adds the normal-operation latency/consistency trade-off that actually drives most designs; Kleppmann (2015) argues CAP's definitions are too ambiguous to guide practice; Jepsen's model map places snapshot isolation and anything stronger in the "unavailable" class. For ERP/financial systems the sources point to PC/EC (strong consistency, pay latency); for analytics replicas PA/EL or EL is acceptable.

### Cited Findings
- Abadi: "CAP only posits limitations in the face of certain types of failures, and does not constrain any system capabilities during normal operation"; "one particular tradeoff — between consistency and latency — arguably has been more influential on DDBS design than the CAP tradeoffs." PACELC ("pass-elk"): "if there is a partition (P), how does the system trade off availability and consistency (A and C); else (E), when the system is running normally in the absence of partitions, how does the system trade off latency (L) and consistency (C)?" Classification: "The default versions of Dynamo, Cassandra, and Riak are PA/EL systems"; "Fully ACID systems such as VoltDB/H-Store and Megastore are PC/EC"; "BigTable and related systems such as HBase are also PC/EC"; "MongoDB can be classified as a PA/EC system"; "PNUTS is a PC/EL system." Even with R + W > N, Dynamo-style systems "cannot achieve full consistency as defined by Gilbert and Lynch." Published in IEEE Computer, February 2012 (PDF created 2012-01-25). — [Consistency Tradeoffs in Modern Distributed Database System Design: CAP is Only Part of the Story](https://www.cs.umd.edu/~abadi/papers/abadi-pacelc.pdf) (February 2012)
- Brewer 2012: "CAP prohibits only a tiny part of the design space: perfect availability and consistency in the presence of partitions, which are rare"; "pragmatically, a partition is a time bound on communication"; choices are fine-grained per subsystem/operation/data; recommended partition management: detect the partition, enter an explicit partition mode that limits operations, then recover (version vectors, CRDTs/commutative operations, compensating transactions "as in sagas"); the ATM example keeps the invariant balance >= 0 by capping withdrawals at k during a partition and fixing violations afterwards "through fees or auditing." Originally in IEEE Computer (vol. 45 no. 2, Feb 2012, pp. 23-29 per Kleppmann's reference list). — [CAP Twelve Years Later](https://www.infoq.com/articles/cap-twelve-years-later-how-the-rules-have-changed/) (2012-05-30 InfoQ)
- Gilbert & Lynch 2002 is cited by Abadi as "Brewer's Conjecture and the Feasibility of Consistent, Available, Partition-Tolerant Web Services," ACM SIGACT News, June 2002, pp. 51-59. The CMU-hosted PDF was fetched (163 KB) but is a bitmap scan with no text layer, so its formal statements are not quoted here. — [GL-cap.pdf](https://users.ece.cmu.edu/~adrian/731-sp04/readings/GL-cap.pdf) (June 2002; content not machine-readable)
- Gilbert & Lynch's 2012 retrospective (downloaded from MIT via curl, text extracted): "Consistency (as defined in the CAP Theorem) is a classic safety property: every response sent to a client is correct"; "The CAP Theorem, in this light, is simply one example of the fundamental fact that you cannot achieve both safety and liveness in an unreliable distributed system"; they note systems may "sacrifice both" C and A. — Perspectives on the CAP Theorem, Gilbert & Lynch (MIT copy, groups.csail.mit.edu/tds/papers/Gilbert/Brewer2.pdf; retrieved with curl, not WebFetch — treat URL as unverified by the project's rule)
- Kleppmann: CAP suffers from "inconsistent and ambiguous definitions and problems in its formalization"; the common reading that eventually consistent databases have better availability "has some truth but requires more careful reasoning"; he proposes a "delay-sensitivity" framework analyzing "how operation latency responds to network delay." arXiv:1509.05393, submitted 2015-09-17 (v2 2015-09-18). — [A Critique of the CAP Theorem](https://arxiv.org/abs/1509.05393) (September 2015)
- Jepsen's consistency map: multi-object hierarchy strict serializable > serializable > {repeatable read, snapshot isolation} > monotonic atomic view / cursor stability > read committed > read uncommitted; single-object hierarchy strict serializable > linearizable > sequential > causal > {PRAM, writes-follow-reads} > {monotonic reads, monotonic writes, read your writes}. Availability: "Cursor stability, snapshot isolation, sequential, and every model stronger than these" are unavailable in asynchronous networks; "Read your writes and every model stronger than it" are at most sticky available; weaker models are totally available. "Strict serializable combines ... serializability and ... linearizability." — [Jepsen: Consistency Models](https://jepsen.io/consistency/models) (n.d.); overview page defines a consistency model as "a safety property" and gives the example that serializability means "every legal history must be equivalent to a totally ordered execution." — [Jepsen: Consistency](https://jepsen.io/consistency) (n.d.)
- Bailis et al. (HAT): achievable with high availability are Read Committed, Item Cut Isolation, Monotonic Atomic View and the ANSI implementation-agnostic Repeatable Read; "Read your writes is not achievable in a highly available system" (needs sticky availability); serializability and snapshot isolation are unachievable; the benefit of HATs is "often two to three orders of magnitude over wide-area networks." — [Highly Available Transactions](http://www.vldb.org/pvldb/vol7/p181-bailis.pdf) (VLDB 2014)
- Bailis et al. (Coordination Avoidance): invariant confluence "provides a necessary and sufficient condition for safe, coordination-free execution"; "ten of twelve of TPC-C's invariants are I-confluent under the workload transactions"; prototype scaled "to over 12.7M TPC-C New-Order transactions per second on 200 servers"; the motivating counter-example is unique ID assignment, which requires coordination. — [Coordination Avoidance in Database Systems](http://www.bailis.org/papers/ca-vldb2015.pdf) (VLDB 2015)

### Inferences
- For ERP/financial OLTP, the invariants that matter (balance >= 0, unique invoice numbers, debits = credits per journal entry, FK integrity) are exactly the non-I-confluent or coordination-requiring class (uniqueness, sequential IDs, cross-row sums), so the sources collectively justify a PC/EC, single-writer or consensus-replicated store (PostgreSQL/SQL Server/Oracle primary, Spanner/CockroachDB-class systems) rather than an AP store. Analytics/reporting replicas can be EL (asynchronous replicas) provided reports do not feed back into transactional decisions (see RDS Long Fork finding in Q2).
- Brewer's partition-mode recommendation maps onto schema: record a partition/degraded-mode flag and a per-operation "limit k" to enable bounded operation, plus an audit/compensation table to reconcile afterwards.

### Gaps
- The Gilbert & Lynch 2002 proof text (asynchronous vs partially synchronous theorems, t-connected consistency) could not be extracted; the ACM DL and Semantic Scholar endpoints returned 403/429. The paper's existence, venue and page range are confirmed only via Abadi's bibliography.
- Brewer's original 2000 PODC keynote slides were not fetched; the 2012 retrospective is used as his authoritative statement.

## Q5. Distributed transactions — 2PC/XA, Sagas, Transactional Outbox, idempotency keys, exactly-once, Spanner, Calvin, Raft

### Takeaway
Vendors position 2PC/XA as a transaction-manager facility, not an application tool (PostgreSQL: "Unless you're writing a transaction manager, you probably shouldn't be using PREPARE TRANSACTION"); Spanner shows 2PC over Paxos is viable at Google scale and argues for giving programmers transactions; Calvin removes 2PC by deterministic pre-ordering; Raft supplies the consensus layer and prescribes client serial numbers for exactly-once application. Where a single transaction cannot span services, Sagas (1987) with compensating transactions, the Transactional Outbox, and idempotency keys (Stripe/Brandur) are the documented building blocks, each of which requires specific tables and unique constraints.

### Cited Findings
- PostgreSQL `PREPARE TRANSACTION`: "its state is fully stored on disk, and there is a very high probability that it can be committed successfully, even if a database crash occurs before the commit is requested"; "PREPARE TRANSACTION is not intended for use in applications or interactive sessions. Its purpose is to allow an external transaction manager to perform atomic global transactions across multiple databases"; "It is unwise to leave transactions in the prepared state for a long time. This will interfere with the ability of VACUUM to reclaim storage, and in extreme cases could cause the database to shut down to prevent transaction ID wraparound"; keep `max_prepared_transactions` at zero without a transaction manager; completion via `COMMIT PREPARED`/`ROLLBACK PREPARED` from any session; standards reference X/Open XA. — [PostgreSQL 18: PREPARE TRANSACTION](https://www.postgresql.org/docs/current/sql-prepare-transaction.html) (n.d.)
- MySQL XA: based on the X/Open XA specification; Resource Manager = MySQL server, Transaction Manager = client program; prepare phase ("Each RM records its work in stable storage and reports whether it can commit") then commit/rollback phase; one-phase commit for single-branch transactions; the page says SERIALIZABLE "may be preferred if the application is sensitive to read phenomena" and REPEATABLE READ "may not be sufficient for distributed transactions"; InnoDB only. — [MySQL 8.4: 15.3.8 XA Transactions](https://dev.mysql.com/doc/refman/8.4/en/xa.html) (n.d.)
- Spanner (OSDI 2012; the fetched PDF is the ACM TOCS 31(3) version, August 2013): "the first system to distribute data at global scale and support externally-consistent distributed transactions"; TrueTime "directly exposes clock uncertainty ... If the uncertainty is large, Spanner slows down to wait out that uncertainty," with uncertainty "generally less than 10ms" via GPS and atomic clocks; commit wait: "The coordinator leader ensures that clients cannot see any data committed by Ti until TT.after(si) is true"; measured commit wait "about 4ms"; cross-group transactions use two-phase commit coordinated by Paxos-group leaders, with the client driving 2PC. Design stance: "We believe it is better to have application programmers deal with performance problems due to overuse of transactions as bottlenecks arise, rather than always coding around the lack of transactions. Running two-phase commit over Paxos mitigates the availability problems." — [Spanner: Google's Globally-Distributed Database](https://research.google/pubs/spanner-googles-globally-distributed-database-2/) (OSDI 2012); PDF: [1974.pdf](https://storage.googleapis.com/gweb-research2023-media/pubtools/1974.pdf)
- Calvin (SIGMOD 2012): "a practical transaction scheduling and data replication layer that uses a deterministic ordering guarantee to significantly reduce the normally prohibitive contention costs associated with distributed transactions"; agreement on a global order happens before execution, which, with a deterministic locking mechanism, enables elimination of two-phase commit's multiple round trips; "it is possible to run half a million TPC-C transactions per second on a cluster of commodity machines in the Amazon cloud." — [Calvin: Fast Distributed Transactions for Partitioned Database Systems](http://cs.yale.edu/homes/thomson/publications/calvin-sigmod12.pdf) (SIGMOD 2012)
- Raft (Ongaro & Ousterhout, USENIX ATC 2014, extended version): "a consensus algorithm for managing a replicated log. It produces a result equivalent to (multi-)Paxos, and it is as efficient as Paxos"; decomposed into leader election, log replication and safety; entries commit once "stored on a majority of servers"; for exactly-once semantics the client retry problem is solved because "clients assign unique serial numbers to every command. Then, the state machine tracks the latest serial number processed for each client, along with the associated response. If it receives a command whose serial number has already been executed, it responds immediately without re-executing"; "Our goal for Raft is to implement linearizable semantics." — [In Search of an Understandable Consensus Algorithm](https://raft.github.io/raft.pdf) (2014); the project site adds that a 5-server cluster "can keep operating with 2 failures." — [raft.github.io](https://raft.github.io/) (n.d.)
- Sagas (Garcia-Molina & Salem, SIGMOD 1987, pp. 249-259; ACM DL 403, Cornell copy used): "Long lived transactions (LLTs) hold on to database resources for relatively long periods of time, significantly delaying the termination of shorter and more common transactions ... A LLT is a saga if it can be written as a sequence of transactions that can be interleaved with other transactions. The database management system guarantees that either all the transactions in a saga are successfully completed or compensating transactions are run to amend a partial execution." The paper relaxes "the requirement that an LLT be executed as an atomic action" so LLTs can "release their resources before they complete"; examples include monthly bank statements and insurance claims; the airline reservation example motivates per-seat sub-transactions with compensations. — [Sagas](https://www.cs.cornell.edu/andru/cs711/2002fa/reading/sagas.pdf) (1987)
- microservices.io Saga (Chris Richardson): context is Database per Service; "two-phase commit (2PC) is not an option"; a saga is "a reliably coordinated sequence of local transactions" with compensating transactions to undo completed steps; choreography (events) vs orchestration (orchestrator commands); drawbacks: no automatic rollback and "no isolation" (concurrent sagas can produce anomalies, countermeasures deferred to the book); Create Order example creates a PENDING order, Customer Service reserves credit, order is approved or rejected. — [Pattern: Saga](https://microservices.io/patterns/data/saga.html) (n.d.; site copyright 2026)
- microservices.io Transactional Outbox: the service "stores the message in the database as part of the same transaction that updates business entities"; a separate relay (Polling publisher or Transaction log tailing) sends the stored messages; results: "2PC is not used", "Messages are sent if and only if the database transaction commits", ordering preserved, but "The relay might publish a message more than once, so consumers must be idempotent." For NoSQL the outbox is a property of each record rather than a table. — [Pattern: Transactional outbox](https://microservices.io/patterns/data/transactional-outbox.html) (n.d.)
- Stripe idempotent requests: clients send an `Idempotency-Key` header; "we suggest using V4 UUIDs, or another random string with enough entropy"; keys are "up to 255 characters"; for API v1 Stripe "saves the status code and body of the first request made with a given idempotency key after endpoint execution begins. Retries with the same key return the saved response, including 500 errors"; API v2 instead "retries failed or partially failed work to completion"; keys may be pruned "after they're at least 24 hours old"; "The idempotency layer compares incoming parameters to those of the original request and errors if they're not the same"; results are not saved if validation fails or the request conflicts with a concurrent one; only POST accepts keys ("GET and DELETE ... are idempotent by definition"); avoid sensitive data in keys. — [Stripe API: Idempotent requests](https://docs.stripe.com/api/idempotent_requests) (n.d.)
- Brandur Leach's Postgres implementation: an `idempotency_keys` table with `id, created_at, idempotency_key, last_run_at, locked_at, request_method, request_params, request_path, response_code, response_body, recovery_point, user_id` and "A unique index on (user_id, idempotency_key)"; work is split into "atomic phases" (local DB transactions) between "foreign state mutations" (e.g., calls to Stripe), with `recovery_point` advancing from `started` to `finished`; `locked_at` ensures only one request works a key (409 if locked); each phase runs in a SERIALIZABLE transaction and a serialization abort maps to 409 Conflict; a "completer" finishes abandoned requests and a "reaper" deletes keys older than a horizon (24 h suggested in one place, ~72 h in another); advice: use random keys, "Non-ACID stores such as MongoDB can't support atomic phases", build idempotency into internal services too, and aim for passive safety. — [Implementing Stripe-like Idempotency Keys in Postgres](https://brandur.org/idempotency-keys) (2017-10-27)

### Inferences
- "Exactly-once" is achieved in every source by the same mechanism — a durable, uniquely constrained record of (client/user, operation key) plus the stored outcome — whether called a Raft client serial number, a Stripe idempotency key, a TigerBeetle 128-bit transfer id, or an outbox message id checked by an idempotent consumer. The schema primitive is therefore a UNIQUE constraint scoped to the tenant/client, not a probabilistic de-duplication.
- Saga state belongs in a table (saga_id, type, current_step, status, started_at, updated_at, correlation keys, compensation log), and the "no isolation" drawback implies status columns on business rows (e.g., `order.status = PENDING`) acting as semantic locks so concurrent sagas can detect in-flight work.

### Gaps
- The Spanner page on research.google names OSDI 2012 but the text extracted came from the 2013 TOCS version; page-level TrueTime epsilon averages are from that version.
- The microservices.io pages carry no publication dates; the saga countermeasures (semantic lock, commutative updates, pessimistic view, reread value, version file, by value) are referenced to the book and were not available on the page.
- No primary source for the general XA specification itself (X/Open) was fetched; XA facts are from the MySQL and PostgreSQL docs.

## Q6. Schema-level implications — what columns/tables transaction correctness requires (version columns, idempotency keys, outbox, saga state, ordering vs sequence gaps, aggregates, retry on 40001, double-entry invariants)

### Takeaway
The sources converge on a small set of schema artifacts: a version/rowversion column per aggregate root for optimistic offline locking; an idempotency table with a tenant-scoped unique key and stored response; an outbox table written in the same transaction as the business rows; a saga/process state table with status columns on business rows; an append-only, double-entry ledger with immutable transfers and compensating entries; and a gapless-number counter table (with exclusive locking) when legal numbering is required, because sequences are never rolled back. Transactions are bounded by DDD aggregates and must be wrapped in retry logic keyed to the engine's serialization-failure signal.

### Cited Findings
- Aggregates as the transaction boundary: "A DDD aggregate is a cluster of domain objects that can be treated as a single unit"; outside references point only to the root; aggregates are the unit of loading and saving, and "Transactions should not cross aggregate boundaries." — [DDD_Aggregate](https://martinfowler.com/bliki/DDD_Aggregate.html) (2013-04-23)
- Retry contracts per engine: PostgreSQL "Serialization failures always return SQLSTATE '40001'" and applications "need a general retry mechanism" ([PostgreSQL 18: Transaction Isolation](https://www.postgresql.org/docs/current/transaction-iso.html), n.d.); Oracle returns ORA-08177 and the application "can then commit the work done so far, roll back to a savepoint, or roll back the whole transaction" ([Oracle Concepts](https://docs.oracle.com/en/database/oracle/oracle-database/23/cncpt/data-concurrency-and-consistency.html), n.d.); SQL Server returns error 3960 for snapshot update conflicts and error 1205 to a deadlock victim ([locking guide](https://learn.microsoft.com/en-us/sql/relational-databases/sql-server-transaction-locking-and-row-versioning-guide), 2026-04-22; [deadlocks guide](https://learn.microsoft.com/en-us/sql/relational-databases/sql-server-deadlocks-guide), 2025-10-09); MongoDB: "abort and retry the transaction" on any operation error ([Production Considerations](https://www.mongodb.com/docs/manual/core/transactions-production-consideration/), n.d.).
- Sequence gaps: "Because nextval and setval calls are never rolled back, sequence objects cannot be used if 'gapless' assignment of sequence numbers is needed"; gapless assignment "is possible by 'exclusive locking of a table containing a counter'" but is "much more expensive than sequence objects"; with CACHE > 1 values may be lost at session end ("holes") and "generated out of sequence" across sessions, so with CACHE > 1 only distinctness should be assumed. — [PostgreSQL 18: CREATE SEQUENCE](https://www.postgresql.org/docs/current/sql-createsequence.html) (n.d.)
- Version column pattern: SQL Server's `rowversion` documentation gives the compare-and-set UPDATE with `OUTPUT inserted.myKey` and a zero-row check as the optimistic-concurrency idiom, and warns the column is unsuitable as a key ([rowversion](https://learn.microsoft.com/en-us/sql/t-sql/data-types/rowversion-transact-sql), 2017-07-22); PoEAA's Optimistic Offline Lock requires conflict validation and the update to happen in one system transaction ([Optimistic Offline Lock](https://martinfowler.com/eaaCatalog/optimisticOfflineLock.html), 2003-03-05).
- Idempotency table shape and constraint: `(user_id, idempotency_key)` unique index, stored `response_code/response_body`, `recovery_point`, `locked_at`, `request_params` for parameter comparison ([brandur.org](https://brandur.org/idempotency-keys), 2017-10-27); Stripe's contract — parameters must match, results saved after execution begins, keys <= 255 chars, 24-hour retention ([Stripe](https://docs.stripe.com/api/idempotent_requests), n.d.).
- Outbox table: for a relational database "the outbox is a table storing messages to be sent", written in the same transaction; consumers must be idempotent because the relay may re-publish ([Transactional outbox](https://microservices.io/patterns/data/transactional-outbox.html), n.d.).
- Saga state: orchestration keeps an orchestrator object that "tells participants which local transactions to run"; orders are created in PENDING state until the saga approves or rejects them ([Saga](https://microservices.io/patterns/data/saga.html), n.d.); the 1987 paper requires each sub-transaction Ti to have a compensating transaction Ci and the system to persist enough saga state to complete or compensate after a crash ([Sagas](https://www.cs.cornell.edu/andru/cs711/2002fa/reading/sagas.pdf), 1987).
- Double-entry ledger invariants in practice (Stripe): "Ledger is based on double-entry bookkeeping"; "Accounts are buckets of money distinguished by their type"; "Events move money between accounts"; it is append-only — "Transactions previously published into Ledger cannot be deleted or modified", corrections are made by "revert and reprocess prior operations"; clearing accounts must zero out at steady state ("Find the clearing Accounts with nonzero balance" is the detection query); scale: "five billion events" per day; 99.99% of dollar volume verified within four days. — [Ledger: Stripe's system for tracking and validating money movement](https://stripe.dev/blog/ledger-stripe-system-for-tracking-and-validating-money-movement) (2024-02-16)
- Double-entry ledger as a database (TigerBeetle, Jepsen): "a distributed OLTP database oriented towards financial transactions" storing only accounts and transfers; transfers have "a unique, user-specified 128-bit id" and requests "execute at most once"; each account tracks pending and posted debits and credits; pending transfers reserve capacity; balance constraints are enforced; "Transfers are immutable. Corrections are made with compensating transfers"; "as of version 0.16.30, TigerBeetle appeared to meet its promise of Strong Serializability"; defects found included missing query results (#2544), client crashes, panics on disk corruption, and no recovery path for node disk loss (#2767) until `tigerbeetle recover` in 0.16.43. — [Jepsen: TigerBeetle 0.16.11](https://jepsen.io/analyses/tigerbeetle-0.16.11) (2025-06-06)
- Write-skew risk for invariants spanning rows: Berenson's A5B example is "a constraint at a bank" between two accounts (sum constraint), and the on-call/predicate variant where "a sum of hours" constraint is violated ([tr-95-51.pdf](https://www.microsoft.com/en-us/research/wp-content/uploads/2016/02/tr-95-51.pdf), 1995); Ports & Grittner's motivating court-system example is a receipts batch report that can omit a receipt under SI, with "regulatory requirements" as the reason SI anomalies were unacceptable ([SSI paper](https://drkp.net/papers/ssi-vldb12.pdf), 2012).
- Coordination needs for ERP-style invariants: uniqueness / distinct ID assignment is the canonical non-I-confluent invariant requiring coordination, while many FK-style invariants are I-confluent ([Coordination Avoidance](http://www.bailis.org/papers/ca-vldb2015.pdf), 2015).
- Timeouts to protect MVCC health: `idle_in_transaction_session_timeout` ([PostgreSQL 18: Transaction Isolation](https://www.postgresql.org/docs/current/transaction-iso.html), n.d.); MongoDB's one-minute transaction lifetime ([Production Considerations](https://www.mongodb.com/docs/manual/core/transactions-production-consideration/), n.d.); PostgreSQL's warning that prepared transactions block VACUUM ([PREPARE TRANSACTION](https://www.postgresql.org/docs/current/sql-prepare-transaction.html), n.d.).

### Inferences
- Minimal schema kit for an ERP/financial/SaaS OLTP database, derived from the cited sources:
  1. `version INTEGER NOT NULL DEFAULT 0` (or `rowversion`) on every aggregate root; all updates are `... WHERE id = ? AND version = ?` and bump the version.
  2. `idempotency_keys(tenant_id, idempotency_key, request_hash/params, response_code, response_body, recovery_point, locked_at, created_at, UNIQUE(tenant_id, idempotency_key))` with a retention/reaper job (24-72 h).
  3. `outbox(id, aggregate_type, aggregate_id, event_type, payload, created_at, published_at NULL)` written in the same transaction as the business rows; relay marks `published_at`; consumers keep a processed-message table keyed by message id.
  4. `saga_instances(saga_id, saga_type, current_step, status, correlation_id, payload, started_at, updated_at)` plus `status` columns on business rows (PENDING/APPROVED/REJECTED) acting as semantic locks.
  5. Ledger: `accounts(id, type, currency, ...)`, `journal_entries(id, posted_at, idempotency/transfer_id UNIQUE, ...)`, `journal_lines(entry_id, account_id, debit, credit)` with a CHECK that each line has exactly one of debit/credit > 0 and a transaction-level or trigger-level check that SUM(debit) = SUM(credit) per entry; never UPDATE/DELETE posted lines — insert reversing entries.
  6. `document_numbers(series, last_number)` updated under `SELECT ... FOR UPDATE` when gapless legal numbering is required; surrogate keys continue to use sequences/identity.
  7. `created_at` is for audit ordering only; monotonic ordering across sessions must come from a serial/sequence or a ledger timestamp assigned by a single writer (sequences with CACHE > 1 are not ordered; see PostgreSQL CREATE SEQUENCE).
- Transaction scripts for invariants that span rows (credit checks, stock, on-call) must either run at PostgreSQL SERIALIZABLE with 40001 retries, or lock the parent/aggregate row (`SELECT ... FOR UPDATE`, UPDLOCK) before reading the children, or encode the invariant as a constraint (e.g., a materialized balance column with CHECK (balance >= 0) updated in the same transaction).

### Gaps
- No vendor source was found that specifies a canonical outbox column list; the column set above is an inference from the pattern description and Brandur's idempotency table.
- Formal guidance on SKIP LOCKED-based queue tables and on partial-index enforcement of ledger invariants was not fetched in this round.

## Q7. Where the sources conflict, and which principles are MANDATORY / RECOMMENDED / OPTIONAL-CONTEXTUAL

### Takeaway
The main conflicts are between vendor names for isolation levels and independently tested behavior (Oracle SERIALIZABLE, MySQL REPEATABLE READ, MongoDB "strongest guarantees"), between CAP framings (Brewer vs Abadi vs Kleppmann), and between "give programmers transactions" (Spanner) and "2PC is not an option" (microservices patterns). The labels below follow the sources' own reasoning.

### Cited Findings — conflicts
- **Oracle "serializable" vs tested behavior.** Oracle's Concepts guide says serializable transactions "do not experience dirty reads, fuzzy reads, or phantom reads" and never mentions write skew ([Oracle Concepts](https://docs.oracle.com/en/database/oracle/oracle-database/23/cncpt/data-concurrency-and-consistency.html)); Hermitage classifies Oracle "serializable" as snapshot isolation with G2-item not prevented ([Hermitage](https://github.com/ept/hermitage)); Berenson et al. prove SI "is non-serializable" and allows A5B ([tr-95-51.pdf](https://www.microsoft.com/en-us/research/wp-content/uploads/2016/02/tr-95-51.pdf)).
- **MySQL REPEATABLE READ.** The MySQL manual says consistent reads "read the snapshot established by the first read" ([MySQL 8.4](https://dev.mysql.com/doc/refman/8.4/en/innodb-transaction-isolation-levels.html)); Jepsen found lost update, G-single and G2-item and intra-transaction read changes, calling the documentation misleading, while noting the manual's own caveat that the snapshot applies to SELECT "not necessarily to DML statements" ([Jepsen MySQL 8.0.34](https://jepsen.io/analyses/mysql-8.0.34)). Hermitage labels MySQL RR "monotonic atomic view"; Jepsen 2023 says that "cannot be correct."
- **PostgreSQL terminology.** PostgreSQL's docs call RR stronger than the standard requires and list only "serialization anomaly" as remaining ([PostgreSQL docs](https://www.postgresql.org/docs/current/transaction-iso.html)); Jepsen asked for the term "snapshot isolation" and the specific anomalies to be documented, and noted G2-item under RR is allowed under the strict ANSI reading but surprising under the Berenson broad reading where SI and RR are incomparable ([Jepsen PostgreSQL 12.3](https://jepsen.io/analyses/postgresql-12.3); [Jepsen models](https://jepsen.io/consistency/models)).
- **MongoDB defaults and claims.** MongoDB's docs state `w: "majority"` "is not strictly required" but that snapshot/majority guarantees depend on it ([MongoDB Transactions](https://www.mongodb.com/docs/manual/core/transactions/)); Jepsen found that even snapshot+majority produced anomalies in 4.2.6 until a retry bug was fixed, and criticized the "strongest data consistency ... of any database" claim ([Jepsen MongoDB 4.2.6](https://jepsen.io/analyses/mongodb-4.2.6)). Abadi classifies MongoDB as PA/EC and describes manual rollback-directory reconciliation after failover ([PACELC](https://www.cs.umd.edu/~abadi/papers/abadi-pacelc.pdf)).
- **CAP framing.** Brewer: CAP constrains only a tiny design-space corner; manage partitions explicitly ([Brewer 2012](https://www.infoq.com/articles/cap-twelve-years-later-how-the-rules-have-changed/)). Abadi: CAP "is for failures"; latency/consistency dominates normal operation ([PACELC](https://www.cs.umd.edu/~abadi/papers/abadi-pacelc.pdf)). Kleppmann: CAP's definitions are too ambiguous to be useful; replace with delay-sensitivity ([Kleppmann 2015](https://arxiv.org/abs/1509.05393)). Gilbert & Lynch 2012: CAP is one instance of safety-vs-liveness (curl-retrieved, see Q4 note).
- **2PC: use it or avoid it.** Spanner: better for programmers to "deal with performance problems due to overuse of transactions" than code around their absence, and 2PC over Paxos "mitigates the availability problems" ([Spanner](https://storage.googleapis.com/gweb-research2023-media/pubtools/1974.pdf)). microservices.io: "2PC is not an option" ([Saga](https://microservices.io/patterns/data/saga.html)). PostgreSQL: PREPARE TRANSACTION is only for transaction managers and is risky to leave open ([PREPARE TRANSACTION](https://www.postgresql.org/docs/current/sql-prepare-transaction.html)). Calvin: eliminate 2PC via determinism ([Calvin](http://cs.yale.edu/homes/thomson/publications/calvin-sigmod12.pdf)).
- **Explicit locks under SERIALIZABLE.** PostgreSQL advises removing `SELECT FOR UPDATE` when SERIALIZABLE already protects ([PostgreSQL docs](https://www.postgresql.org/docs/current/transaction-iso.html)); Brandur combines SERIALIZABLE with a `locked_at` column (no FOR UPDATE) ([brandur.org](https://brandur.org/idempotency-keys)); Jepsen recommends `SELECT ... FOR UPDATE` or Serializable as alternatives for MySQL ([Jepsen MySQL](https://jepsen.io/analyses/mysql-8.0.34)).
- **Idempotency replay semantics.** Stripe v1 replays the saved response "including 500 errors"; v2 retries failed work to completion ([Stripe](https://docs.stripe.com/api/idempotent_requests)). Brandur's retention is stated as ~24 h in one place and ~72 h in another ([brandur.org](https://brandur.org/idempotency-keys)).
- **Report-internal inconsistency.** The TigerBeetle report's abstract says all issues but indefinite retries were addressed by 0.16.45 while the body recommends 0.16.43 ([Jepsen TigerBeetle](https://jepsen.io/analyses/tigerbeetle-0.16.11)).

### Cited Findings — principle labels (with the source's reasoning)
**MANDATORY**
- Wrap every transaction that can fail with a serialization/deadlock/write-conflict error in a whole-transaction retry: PostgreSQL ("applications using this level must be prepared to retry"; SQLSTATE 40001) ([PostgreSQL docs](https://www.postgresql.org/docs/current/transaction-iso.html)); MongoDB ("abort and retry the transaction") ([MongoDB](https://www.mongodb.com/docs/manual/core/transactions-production-consideration/)); SQL Server error 1205 victim must be retried ([deadlocks guide](https://learn.microsoft.com/en-us/sql/relational-databases/sql-server-deadlocks-guide)); PostgreSQL deadlocks ("retry transactions that abort due to deadlocks") ([explicit locking](https://www.postgresql.org/docs/current/explicit-locking.html)).
- Do not rely on an isolation level's name; specify guarantees per engine/configuration, because "repeatable read" differs across PostgreSQL, MySQL and SQL Server and Oracle "serializable" is SI ([Hermitage blog](https://martin.kleppmann.com/2014/11/25/hermitage-testing-the-i-in-acid.html); [Jepsen MySQL](https://jepsen.io/analyses/mysql-8.0.34)).
- For cross-row invariants under SI/RR engines, use SERIALIZABLE (PostgreSQL), explicit row locks, or declarative constraints — SI allows write skew by construction ([Berenson](https://www.microsoft.com/en-us/research/wp-content/uploads/2016/02/tr-95-51.pdf); [Ports & Grittner](https://drkp.net/papers/ssi-vldb12.pdf); PostgreSQL RR "may require explicit locks" ([docs](https://www.postgresql.org/docs/current/transaction-iso.html))).
- Enforce idempotency keys with a tenant-scoped UNIQUE constraint and compare request parameters on replay ([Stripe](https://docs.stripe.com/api/idempotent_requests); [brandur.org](https://brandur.org/idempotency-keys)).
- Write outbox rows in the same local transaction as the business change, and make consumers idempotent ([Transactional outbox](https://microservices.io/patterns/data/transactional-outbox.html)).
- Never use sequences/identity for gapless legal numbering ([CREATE SEQUENCE](https://www.postgresql.org/docs/current/sql-createsequence.html)).
- MongoDB: set read concern "snapshot" and write concern "majority" explicitly on each transaction ([MongoDB](https://www.mongodb.com/docs/manual/core/transactions/); [Jepsen MongoDB](https://jepsen.io/analyses/mongodb-4.2.6)).
- Keep transactions short and never wait on user input inside one; configure `idle_in_transaction_session_timeout` ([PostgreSQL docs](https://www.postgresql.org/docs/current/transaction-iso.html); [explicit locking](https://www.postgresql.org/docs/current/explicit-locking.html)); do not leave prepared transactions open ([PREPARE TRANSACTION](https://www.postgresql.org/docs/current/sql-prepare-transaction.html)).
- Ledgers: append-only, immutable postings; corrections by reversing/compensating entries; clearing accounts must net to zero ([Stripe Ledger](https://stripe.dev/blog/ledger-stripe-system-for-tracking-and-validating-money-movement); [Jepsen TigerBeetle](https://jepsen.io/analyses/tigerbeetle-0.16.11)).

**RECOMMENDED**
- Version/rowversion column and compare-and-set UPDATE for business transactions spanning multiple system transactions ([rowversion](https://learn.microsoft.com/en-us/sql/t-sql/data-types/rowversion-transact-sql); [Optimistic Offline Lock](https://martinfowler.com/eaaCatalog/optimisticOfflineLock.html)).
- Bound transactions by aggregate: "Transactions should not cross aggregate boundaries" ([DDD_Aggregate](https://martinfowler.com/bliki/DDD_Aggregate.html)); MongoDB similarly prefers single-document atomicity over multi-document transactions ([MongoDB](https://www.mongodb.com/docs/manual/core/transactions/)).
- Acquire locks in a consistent order; take the most restrictive lock first ([explicit locking](https://www.postgresql.org/docs/current/explicit-locking.html); [deadlocks guide](https://learn.microsoft.com/en-us/sql/relational-databases/sql-server-deadlocks-guide)).
- SQL Server: enable RCSI or SNAPSHOT to cut shared-lock blocking and escalation; batch large deletes ([locking guide](https://learn.microsoft.com/en-us/sql/relational-databases/sql-server-transaction-locking-and-row-versioning-guide)).
- PostgreSQL SERIALIZABLE tuning: declare READ ONLY, pool connections, favor index scans, raise `max_pred_locks_*` ([PostgreSQL docs](https://www.postgresql.org/docs/current/transaction-iso.html)).
- Advisory locks for pessimistic patterns that fit MVCC poorly, instead of lock-flag columns that cause bloat ([explicit locking](https://www.postgresql.org/docs/current/explicit-locking.html)).
- Saga orchestration with a persisted state machine and PENDING status columns ([Saga](https://microservices.io/patterns/data/saga.html); [Sagas 1987](https://www.cs.cornell.edu/andru/cs711/2002fa/reading/sagas.pdf)).
- Read safety-critical data from the primary/writer endpoint, not asynchronous replicas ([Jepsen RDS PostgreSQL 17.4](https://jepsen.io/analyses/amazon-rds-for-postgresql-17.4)); set `replica_preserve_commit_order` on MySQL replicas ([Jepsen MySQL](https://jepsen.io/analyses/mysql-8.0.34)).

**OPTIONAL / CONTEXTUAL**
- XA/2PC through an external transaction manager, with SERIALIZABLE on MySQL branches if read phenomena matter ([MySQL XA](https://dev.mysql.com/doc/refman/8.4/en/xa.html); [PREPARE TRANSACTION](https://www.postgresql.org/docs/current/sql-prepare-transaction.html)).
- Globally distributed strong consistency (Spanner-class TrueTime + 2PC over Paxos; Raft-based systems) when data must be geo-distributed ([Spanner](https://research.google/pubs/spanner-googles-globally-distributed-database-2/); [Raft](https://raft.github.io/raft.pdf)).
- Deterministic scheduling (Calvin) when read/write sets are known up front ([Calvin](http://cs.yale.edu/homes/thomson/publications/calvin-sigmod12.pdf)).
- Coordination-avoidance analysis (I-confluence) to find which invariants can be enforced without synchronous coordination at scale ([Coordination Avoidance](http://www.bailis.org/papers/ca-vldb2015.pdf)).
- PACELC EL (latency-favoring) replicas for analytics; EC/PC for the system of record ([PACELC](https://www.cs.umd.edu/~abadi/papers/abadi-pacelc.pdf)); highly available transactions (RC/MAV level) for geo-distributed, partition-tolerant workloads that can tolerate the listed anomalies ([HAT](http://www.vldb.org/pvldb/vol7/p181-bailis.pdf)).
- Brewer-style partition mode with bounded operations and post-partition compensation/auditing for systems that must stay available during partitions ([Brewer 2012](https://www.infoq.com/articles/cap-twelve-years-later-how-the-rules-have-changed/)).

### Inferences
- The engines' own documentation rarely spells out their weaker-than-named behavior (Oracle, MySQL), so a schema framework should encode anomaly matrices from Hermitage/Jepsen alongside vendor docs and re-check them when engine major versions change (the PostgreSQL SSI bug of 2020 shows even "correct" implementations regress).

### Gaps
- Jepsen has not published analyses of current SQL Server or Oracle releases; the Oracle/SQL Server rows of the matrix rest on vendor docs plus Hermitage (undated).
- DDIA's exact text on the "C" in ACID and Fowler's version-column code are in books not accessible online; both are corroborated only by summaries or adjacent vendor documentation.
