## Key Question 1 — Validation layers: schema constraints (OLTP) vs pipeline checks vs warehouse tests; WAP, quarantine, dead-letter queues, circuit breakers, data-quality SLAs/SLOs

### Takeaway
Credible tool documentation converges on a layered model: (1) the database/platform enforces structural guarantees in DDL where the platform actually enforces them (dbt's own contract docs admit "most platforms only enforce `not_null`" in analytical warehouses, which is why OLTP constraints matter most); (2) the pipeline/orchestrator gates promotion of data with blocking checks (Write-Audit-Publish via Iceberg branches, Databricks expectations with warn/drop/fail, Airflow SQL check operators, circuit breakers at Intuit, "blocking" checks at Airbnb); (3) the warehouse layer runs post-build assertions (dbt data tests, GX, Soda) plus pre-build logic tests (dbt unit tests). Freshness SLAs are expressed declaratively (dbt `warn_after`/`error_after`; ODCS SLA section).

### Cited Findings

**Layer 1 — schema/DDL constraints (platform-enforced)**
- dbt model contracts: when `contract: enforced: true`, dbt does a preflight check that query columns match the YAML names and data types, then "includes the names, types, and constraints in the DDL, so the platform enforces them at build time." Constraint types are `not_null`, `primary_key`, `foreign_key`, `unique`, `check`, each classified per adapter as "definable and enforced", "definable and not enforced (metadata purposes only)", or "not definable". FAQ: "Most platforms only enforce `not_null`." Postgres is shown as the platform where all five constraint types are both definable and enforced; Microsoft Fabric checks only `not_null` at build and merely records PK/FK/unique. Contracts are supported for `table`, `incremental` (with `on_schema_change: append_new_columns` or `fail`) and `view` (names/types only), not for Python models, materialized views, ephemeral models, sources, seeds or snapshots. — [dbt: Model contracts](https://docs.getdbt.com/docs/collaborate/govern/model-contracts) (last updated Oct 29, 2026)
- dbt explicitly positions contracts vs tests: "A model's contract defines the **shape** of the returned dataset"; data tests validate content after the build; some data tests can be replaced by constraints *only* where the platform enforces them and a full contract exists. — [dbt: Model contracts](https://docs.getdbt.com/docs/collaborate/govern/model-contracts)
- PostgreSQL `COMMENT ON` supports TABLE, COLUMN, CONSTRAINT, VIEW, MATERIALIZED VIEW, SCHEMA, DATABASE, DOMAIN, FUNCTION, POLICY, TRIGGER, etc.; one comment per object; comments drop with their object; viewable via psql `\d` family and `obj_description`/`col_description`/`shobj_description`. Security note: "any user connected to a database can see all the comments for objects in that database", so no sensitive data in comments. — [PostgreSQL 18: COMMENT](https://www.postgresql.org/docs/current/sql-comment.html) (PostgreSQL 18 docs, n.d.)

**Layer 2 — pipeline/orchestration checks and promotion gates**
- Apache Iceberg "Audit Branch" / Write-Audit-Publish: (1) enable table property `write.wap.enabled`; (2) create an audit branch from a snapshot with a retention (e.g., 7 days); (3) set `spark.wap.branch` to the branch and run the write — "The main table history is unaffected"; (4) validate the audit branch, e.g., with data quality checks; (5) publish by calling the `fast_forward` procedure to move `main` to the head of the audit branch; (6) the branch reference is removed when `expireSnapshots` runs after retention. Schema note: "The table's schema applies across all branches. Writes to a branch are validated against the current table schema." — [Apache Iceberg: Branching and Tagging](https://iceberg.apache.org/docs/latest/branching/) (Java docs 1.12.0, n.d.)
- Origin of WAP at Netflix (2017): deck "Whoops, the Numbers Are Wrong! Scaling Data Quality @ Netflix" by Michelle Ufford (Netflix Data Engineering & Analytics), Hadoop/DataWorks Summit San Jose, dated June 12, 2017. WAP = Stage 0 Prep (set up an audit table for the run) → Stage 1 Write (write the new partition to the audit table, not production) → Stage 2 Audit (the "Quinto" data-quality service evaluates metrics against configured rules; each rule maps a metric + evaluation to a behaviour: fail the job or warn) → Stage 3 Publish (move the partition into the warehouse table; example sets a "valid-thru" timestamp stored in the Metacat catalog). Example audits: row count ≥ 0 and ≥ prior value (fail); null count vs normal distribution (warn; a jump from 21 to 17,240 nulls was flagged). Lessons: "Not every table needs quality coverage"; "Build modular components rather than all-or-nothing frameworks." — [Scaling Data Quality @ Netflix (SlideShare)](https://www.slideshare.net/MichelleFUfford/scaling-data-quality-netflix-76917740) (2017-06-12)
- Databricks Lakeflow Declarative Pipelines expectations are "quality constraints that validate data as it flows through ETL pipelines"; each expectation = name + SQL boolean constraint + action. Actions: **warn** (default; `EXPECT` / `dp.expect`; invalid rows written, metrics tracked), **drop** (`ON VIOLATION DROP ROW` / `dp.expect_or_drop`; rows dropped, count logged), **fail** (`ON VIOLATION FAIL UPDATE` / `dp.expect_or_fail`; update fails, transaction rolled back, manual intervention needed, no metrics recorded). Constraints cannot call custom Python/external services or subqueries on other tables. Metrics appear in the pipeline UI "Data quality" tab or the event log. — [Databricks: Manage data quality with pipeline expectations](https://docs.databricks.com/aws/en/ldp/expectations) (last updated Oct 26, 2026)
- Databricks quarantine pattern: define rules as named predicates, build the inverse rule `NOT(rule1 AND rule2 ...)`, compute an `is_quarantined` column (partitioned by it) with `@dp.expect_all(rules)` so metrics are recorded, then expose two views filtered on the flag — "keeps everything in one table with a flag, not a separate physical quarantine table." Row-count validation pattern: a materialized view with `CONSTRAINT no_rows_dropped EXPECT (a_count == b_count)` and `expect_or_fail` to stop the update on mismatch. Range-based validation: compute mean ± 3 standard deviations over the last 30 days, cross-join, `expect_or_drop` outside the band. Caveat: "expectations control data quality, not orchestration. A validation table doesn't block downstream tables" — put validation and downstream logic in separate pipelines linked by a job. — [Databricks: Expectation recommendations and advanced patterns](https://docs.databricks.com/aws/en/ldp/expectation-patterns) (last updated Oct 26, 2026)
- Kafka Connect dead-letter queue: "Dead Letter Queues (DLQs) are only applicable for sink connectors." `errors.tolerance=none` (default) fails the task on a bad record; `errors.tolerance=all` skips errors and keeps processing but "writes no errors to the worker log, so you must use internal metrics or compare source and processed record counts to find failures." `errors.deadletterqueue.topic.name` routes invalid records to a topic; `errors.deadletterqueue.context.headers.enable=true` adds `_connect.errors.*` headers explaining the failure (default false — "Without them, the topic shows which records failed but not why"). — [Confluent: Kafka Connect Concepts](https://docs.confluent.io/platform/current/connect/concepts.html) (Confluent Platform 8.4, last updated Oct 16, 2026)
- Airflow common-sql provider check operators: `SQLColumnCheckOperator` (per-column `null_check`, `distinct_check`, `unique_check`, `min`, `max`, with `equal_to`/`greater_than`/`geq_to`/`less_than`/`leq_to` and a `tolerance` percentage; partition clauses at operator/column/check level), `SQLTableCheckOperator` (`check_statement` must resolve to boolean, e.g., `COUNT(*) = 1`), `SQLValueCheckOperator` (`pass_value` ± tolerance), `SQLThresholdCheckOperator` ("If the value returned by the query is within the thresholds, the task passes. Otherwise, it fails."). — [Airflow common-sql provider: Operators](https://airflow.apache.org/docs/apache-airflow-providers-common-sql/stable/operators.html) (provider 2.4.0, n.d.)
- Airflow best practices: "You should treat tasks in Airflow equivalent to transactions in a database"; "the tasks should produce the same outcome on every re-run"; "Do not use INSERT during a task re-run, an INSERT statement might lead to duplicate rows" (use upsert); "Never read the latest available data in a task" — partition by `data_interval_start`; avoid `datetime.now()`; tasks should "never produce incomplete results"; DAGs "should have various associated tests". — [Apache Airflow: Best Practices](https://airflow.apache.org/docs/apache-airflow/stable/best-practices.html) (Airflow 3.4.0, n.d.)
- Intuit circuit breakers (Strata SF, March 27, 2019; Sandeep Uttamchandani, chief data architect / head of data platform engineering at Intuit): "Inspired by microservices design patterns, Intuit implemented circuit breakers in data pipelines," making "data availability in dashboards a function of the data quality," which the abstract says radically reduces time to debug. Companion patterns: source crawlers (time to discover) and "table bounties" that auto-define cataloging work from access patterns. — [Strata 2019: How Intuit reduced time to reliable insights for data pipelines](https://conferences.oreilly.com/strata/strata-ca-2019/public/schedule/detail/73082.html) (2019-03-27). A third-party slide copy (sambuz.com, lower authority) adds: each stage runs checks on metrics and correctness rules, a failed check halts progression, the framework repairs/reschedules or cancels and notifies, alerts split into soft and hard levels — NOT verified against a primary source.
- Airbnb "Wall" (Medium; fetch returned HTTP 403, so details come from search snippets only): Wall is a Python framework on top of Airflow where users add checks via a config file and a helper call in the DAG; for stage-check-exchange checks users can declare checks **blocking or non-blocking**, reportedly because minor check failures had been holding up critical pipelines' SLAs. — [How Airbnb Built "Wall" to prevent data bugs](https://medium.com/airbnb-engineering/how-airbnb-built-wall-to-prevent-data-bugs-ad1b081d6e8f) (URL from search only; fetch returned 403; n.d.). The companion series [Data Quality at Airbnb](https://medium.com/airbnb-engineering/data-quality-at-airbnb-870d03080469) (URL from search only; fetch returned 403) describes the "Midas" certification process whose goal is "a single promise to end users that 'Midas Certified' data is the gold standard for quality"; search results list Part 2 under a Jan 27, 2021 byline, so the "2020" date in the brief could not be confirmed.

**Layer 3 — warehouse tests and freshness SLAs**
- dbt data tests "are `select` statements that seek to grab 'failing' records... If the data test returns zero failing rows, it passes." Two types: singular (one-off SQL in `tests/`) and generic (parameterised; `unique`, `not_null`, `accepted_values`, `relationships` built in). "Generic data tests tend to be much more common—they should make up the bulk of your dbt data testing suite." Recommendation: "every model has a data test on a primary key, that is, a column that is `unique` and `not_null`." Severity `warn`/`error`, `error_if`/`warn_if` thresholds, `store_failures` writes failing rows to a `dbt_test__audit` schema (replaces previous failures). "Tests are now called data tests to disambiguate from unit tests." — [dbt: Add data tests to your DAG](https://docs.getdbt.com/docs/build/data-tests) (last updated Sep 16, 2026)
- dbt unit tests (added v1.8) "validate your SQL modeling logic against small, static input rows, before you materialize the full model"; recommended for complex logic (regex, date math, window functions, many-branch CASE), public/contracted models, models upstream of an exposure, previously-buggy logic, and pre-refactor; "Run unit tests in development and CI, not production, since their inputs are static." SQL models only; must live under `models/`. — [dbt: Unit tests](https://docs.getdbt.com/docs/build/unit-tests) (last updated Sep 14, 2026)
- dbt source freshness: requires `loaded_at_field` (unless warehouse metadata supplies it) and at least one of `warn_after`/`error_after` (`{count: 12, period: hour}`); hierarchical (source-level default, table-level override, `freshness: null` to opt out); evaluated with `select max(_etl_loaded_at), current_timestamp`; `dbt freshness --resource-type source` (v2.0+) writes `target/freshness.json` (and `sources.json`). — [dbt: Add sources to your DAG](https://docs.getdbt.com/docs/build/sources) (last updated Sep 16, 2026)
- Monte Carlo [vendor] defines "data downtime" as "periods of time when data is partial, erroneous, missing, or otherwise inaccurate" and proposes it as an SLA-like metric for consumers "much like a SaaS product being up or down"; data reliability engineering "borrows from site reliability engineering (SRE)". — [What is Data Observability? (Monte Carlo)](https://montecarlo.ai/blog-what-is-data-observability) (Barr Moses; updated Oct 28, 2026)

### Inferences
- Prescription for the framework (with labels):
  - **MANDATORY** — In OLTP schemas, declare PK/UNIQUE/NOT NULL/FK/CHECK in DDL: dbt's own docs show these are the only layer that is "definable and enforced" on all five constraint types in Postgres, while analytical platforms mostly enforce only `not_null`; nothing downstream can retro-enforce what the source DB let in.
  - **MANDATORY** — Every warehouse model has a PK test (`unique` + `not_null`) — dbt states this as its recommendation for every model; Netflix's and Databricks' examples both start with row-count/non-null checks.
  - **MANDATORY (for pipelines that publish to consumers)** — A promotion gate: write to a non-visible location (Iceberg audit branch, Netflix audit table, Databricks fail-on-violation), audit, then publish. Both Netflix (2017) and Iceberg (2025-26 docs) prescribe exactly this; Databricks warns that a validation table alone does not block downstream work unless orchestration is wired to it.
  - **RECOMMENDED** — Severity tiers (warn vs error/fail; blocking vs non-blocking) because Netflix's Quinto, Databricks (warn/drop/fail), dbt (`warn`/`error`) and Airbnb's Wall all converged on the same two-or-three-level model after finding that all-blocking checks stall SLAs.
  - **RECOMMENDED** — Quarantine with a flag column plus views rather than physical side tables (Databricks), and DLQ topics with context headers for streaming sinks (Confluent). Note Confluent's warning that `errors.tolerance=all` is silent unless counts are reconciled.
  - **RECOMMENDED** — Idempotent, partition-scoped loads (upsert, never plain INSERT on retry; never read "latest") per Airflow best practices, as a precondition for safe re-runs after failed audits.
  - **OPTIONAL/CONTEXTUAL** — Unit tests for transformation logic (dbt says not for simple `min()`-style logic; CI only).
- The three layers are complementary, not alternatives: constraints guarantee shape at write time; pipeline gates stop bad batches from being published; warehouse tests assert content and business rules after the fact.

### Gaps
- Airbnb posts could not be fetched (HTTP 403 on Medium); Midas certification criteria and the Wall architecture are reported from search snippets only.
- Intuit's stage-gating details (soft/hard alerts, repair/reschedule) exist only in a third-party slide copy; the primary Strata abstract confirms the circuit-breaker concept but not those mechanics.
- No official source was found that defines numeric data-quality SLO targets (e.g., "99% freshness"); sources give the mechanism (warn/error thresholds, SLA sections) but not benchmark values.

## Key Question 2 — Tools and their models (GX, dbt tests, Soda, Deequ, Pandera, Elementary, Monte Carlo pillars); declarative vs code-based; where they run

### Takeaway
Every mainstream tool compiles declarative or Python-declared assertions into SQL/Spark jobs that run *where the data lives* (warehouse or Spark cluster); the differentiators are the authoring surface (YAML vs Python), whether metrics are persisted over time for anomaly detection (Deequ, Elementary, Monte Carlo), and whether validation can occur pre-materialisation (Pandera in-process, dbt unit tests, Databricks expectations) versus post-build (dbt data tests, GX checkpoints, Soda scans).

### Cited Findings
- **Great Expectations (GX Core 1.x, page shows 1.24.1)**: "a framework for describing data using expressive tests and then validating that the data meets test criteria." Components: Data Context (Python object giving access to configs/metadata/results), Data Source, Data Asset ("analogous to a table or a query result"), Batch Definition, Expectation ("a verifiable assertion about data"; "Expectations provide a flexible, declarative language for describing expected data qualities"), Expectation Suite, Validation Definition (links Batch Definition to a Suite), Checkpoint ("runs a list of Validation Definitions... and can trigger Actions. It is the main validation method in production"), Actions (alerts to email/chat), Data Docs (generated human-readable sites hosting suites and results). Workflows are "programmatically defined" (Python API) even though expectations themselves are declarative. — [GX Core overview](https://docs.greatexpectations.io/docs/core/introduction/gx_overview) (n.d.; © 2026)
- **dbt data tests / unit tests / contracts** — see Key Question 1. Tests are SQL `select` queries compiled and run in the warehouse (e.g., against `analytics.orders`); batching in dbt v2 groups `unique` and `not_null` tests per model into one query per test type. — [dbt data tests](https://docs.getdbt.com/docs/build/data-tests)
- **dbt-expectations** (maintained fork of the calogica package, now under the `metaplane` org): "Great Expectations-style tests in their data warehouse directly from dbt"; categories: table shape (column existence/count, row count, recency), missing/unique/types, sets and ranges, string matching (LIKE/regex), aggregate functions (distinct counts, mean/median/stdev/quantiles), multi-column, distributional (anomaly checks by standard deviations, data in every date part). Example: `dbt_expectations.expect_column_values_to_be_between: {min_value: 0, max_value: 10, row_condition: "id is not null"}`. Requires dbt ≥ 1.7; Postgres/Snowflake/BigQuery/DuckDB/Trino (Spark experimental); install pin 0.10.9; Apache-2.0. — [metaplane/dbt-expectations](https://github.com/metaplane/dbt-expectations) (n.d.)
- **Soda Core v4**: "a data quality and data contract verification engine"; contracts in YAML; dataset-level `schema` and `row_count` checks, column-level `missing` (optional percent threshold) and `invalid` (with `valid_values`); "50+ built-in data quality checks"; CLI `soda contract verify` locally, in pipelines, or remotely via Soda Cloud / Soda Runner; packages `soda-{datasource}` (Athena, BigQuery, Databricks, DuckDB, Fabric, PostgreSQL, Redshift, Snowflake, Spark DataFrames, SQL Server, Synapse, Trino); legacy v3 packages `soda-core-{datasource}` pinned to 3.5.x. — [sodadata/soda-core](https://github.com/sodadata/soda-core) (n.d.). The docs home shows a reconciliation example: `row_count_diff` comparing a Snowflake `orders` dataset with a MySQL source with `must_be_less_than: 1`, described as "Compare a target dataset against one or more sources, from row counts and aggregates down to individual records"; run locations: Soda-hosted Runner, self-hosted Runner, Python libraries. — [Soda Docs](https://docs.soda.io/) (n.d.). Note: the GitHub README no longer uses the name "SodaCL"; the v4 surface is "contracts".
- **AWS Deequ** (Apache-2.0; PyDeequ Python interface): "unit tests for data" on Apache Spark. Add `Check`s to a `VerificationSuite` (completeness, uniqueness, value sets, non-negativity, URL content, approximate quantiles); checks are evaluated by computing metrics that are passed to assertion functions; constraint suggestion for large datasets; `MetricsRepository` persists metrics; anomaly detection on metrics over time; incremental metric computation for growing/partitioned data via algebraic states; profiling. Example run reports `productName` 80% complete and only 40% of `description` values containing a URL. Deequ 2.x artifacts per Spark version (`-spark-3.5` for Spark 3.1-3.5); 2.1.0+ requires Java 11. Cites Schelter et al., "Automating large-scale data quality verification," PVLDB 11(12), 2018, pp. 1781-1794. — [awslabs/deequ](https://github.com/awslabs/deequ) (n.d.)
- **Pandera 0.35.0**: runtime validation of dataframe-like objects, "statistically typed dataframes". `DataFrameSchema` (dict of `pa.Column(type, checks)`) or class-based `DataFrameModel` "inspired by dataclasses and pydantic" (`column1: int = pa.Field(ge=0)`, `@pa.check` methods). Backends: pandas, PySpark SQL, Polars, Ibis, PyArrow, DataFusion; Dask/Modin/GeoPandas/pyspark.pandas via pandas backend; optional Narwhals backend for fully lazy validation. `lazy=True` collects all errors into a report grouped as `DATA` or `SCHEMA`. Decorators `check_input`/`check_output`/`check_io`/`check_types`; schema inference (pandas only); data synthesis via Hypothesis (`pandera[strategies]`). Import from `pandera.pandas` (top-level import warns since v0.24.0). — [Pandera docs](https://pandera.readthedocs.io/) (n.d.)
- **Elementary** (Apache-2.0; 2.4k stars): "The dbt-native data observability solution"; OSS = Elementary dbt package + CLI that "Run tests, detect anomalies and send alerts" (Slack, Microsoft Teams); features: anomaly detection tests as native dbt tests, automated monitors for freshness/volume/schema, end-to-end lineage enriched with test results, data-quality dashboard, run-result/performance tracking, configuration as code in the dbt project, a dbt artifacts uploader, catalog. The README attributes column-level lineage to Elementary Cloud, and the Cloud docs state a "metadata-only architecture: We never access or process your raw data." — [elementary-data/elementary](https://github.com/elementary-data/elementary) and [Elementary docs](https://docs.elementary-data.com/) (n.d.)
- **Monte Carlo five pillars** [vendor; Barr Moses, who the page says coined "data observability" in 2019]: freshness ("how up-to-date tables are and how often they update"), **quality** (percent NULLs, percent uniques, values in accepted range — the page uses "quality", not "distribution"), volume (table completeness and source health), schema (changes to organisation, who made them and when), lineage (upstream sources and downstream consumers affected; producing/accessing teams). Definition: observability "provides full visibility into the health of your data and systems"; it applies to data "the same approach... that DevOps applies observability to software." — [What is Data Observability?](https://montecarlo.ai/blog-what-is-data-observability) (updated Oct 28, 2026)
- **Airflow check operators** and **Databricks expectations** — see Key Question 1 (orchestrator-level and pipeline-level declarative checks).

### Inferences
- "Declarative vs code-based" is a spectrum: dbt/Soda/Databricks SQL are YAML/SQL-declarative; GX and Pandera declare assertions in Python objects; Deequ is code-first. For a schema-design framework the practical rule is: declare structural assertions in the same artefact as the schema (dbt YAML `columns:` with `data_tests` and `constraints`, or Soda/ODCS contract YAML), and reserve code-based tools for in-process validation (Pandera) or Spark-native metric computation (Deequ).
- **RECOMMENDED**: persist metrics over time (Deequ MetricsRepository, Elementary, dbt `store_failures`) because distributional/anomaly checks (Netflix null-count distribution, Databricks mean ± 3σ, dbt-expectations stdev checks) all need history.
- **OPTIONAL/CONTEXTUAL**: a commercial observability platform; Monte Carlo's pillar list is vendor-originated and should be treated as a taxonomy rather than a standard.

### Gaps
- GX's docs page does not describe metric history or anomaly detection; it was not possible to confirm whether GX Core 1.x persists metrics for trend analysis.
- Soda's docs home page contains embedded agent instructions and little technical detail; the exact v4 check list was not retrieved.
- Elementary's anomaly-detection parameters (training period, sensitivity/z-score) were not retrievable from the pages fetched.
- OpenTelemetry: no source fetched in this research connects OTel to data-quality observability; treat as a gap.

## Key Question 3 — Data contracts: ODCS, PayPal template, Data Contract Specification, Chad Sanderson / shift-left, dbt model contracts; relation to schema registries

### Takeaway
There is now a single open standard — the Open Data Contract Standard v3.2.0 (Bitol, LF AI & Data, Apache-2.0), which evolved from PayPal's template and into which the INNOQ Data Contract Specification has been deprecated (as of ODCS v3.1.0). A contract bundles schema, data-quality rules, SLA, team/roles, servers, pricing and custom properties; "shift-left" practice (Sanderson manifesto; Confluent/Andrew Jones) enforces it at the producer in CI, and in streaming it is operationalised through a schema registry with explicit compatibility modes.

### Cited Findings
- **ODCS v3.2.0** — "the agreement between a data producer and consumers"; current version v3.2.0; media type `application/odcs+yaml;version=3.2.0`; Apache 2.0; citation lists "LF AI & Data Foundation" (2025); sections: Fundamentals, Schema, References, Data quality, Support & communication channels, Pricing, Team, Roles, Service-level agreement (SLA), Infrastructure & servers, Authoritative definitions, Tags, Custom & other properties; JSON Schema provided for IDE validation. — [bitol-io/open-data-contract-standard](https://github.com/bitol-io/open-data-contract-standard) (n.d.). The docs site adds Context and Variables sections (15 total) and notes each section has its own page "starting with v3.1.0"; the companion JSON Schemas "may contain bugs, and the standard takes precedence in a conflict." — [ODCS docs (latest)](https://bitol-io.github.io/open-data-contract-standard/latest/) (n.d.)
- **PayPal data-contract template** — "describes the data contract being used in the implementation of Data Mesh at PayPal"; sections: Fundamentals, Schema, Data quality, SLA, Security & stakeholders, Custom properties; Apache-2.0; README says the project "has evolved and is now called" ODCS, part of Bitol "hosted by The Linux Foundation and AIDA User Group". 494 stars, 28 commits (not formally archived but superseded). — [paypal/data-contract-template](https://github.com/paypal/data-contract-template) (n.d.)
- **Data Contract Specification v1.2.1** (Jochen Christ, Dr. Simon Harrer; MIT): YAML format "describing the structure, format, semantics, quality, and terms of data exchanged between a provider and its consumers", following OpenAPI/AsyncAPI conventions; root: `dataContractSpecification`, `id`, `info` (title, version, status, owner, contact), `servers`, `terms` (usage, limitations, billing, notice period), `models` (fields + model-level `quality`/`examples`), `definitions` (`$ref`), `servicelevels` (availability, retention, latency, freshness, frequency, support, backup), `links`, `tags`. **Deprecation notice**: "With the release of the Open Data Contract Standard v3.1.0, the maintainers deprecate the Data Contract Specification to focus on a single industry standard"; ODCS is the "conceptual successor"; CLI/Entropy Data support continues until end of 2026; Data Contract CLI can "lint, test, import and export data contracts" for both DCS and ODCS and run tests against live data. — [datacontract/datacontract-specification](https://github.com/datacontract/datacontract-specification) (n.d.)
- **dbt model contracts** as breaking-change detection: comparing against a previous project state flags removing a column, changing a column's `data_type`, removing/modifying a constraint (v1.6+), and removing a contracted model by deleting/renaming/disabling (v1.9+; error for versioned models, warning for unversioned). "When the contract changes in a backwards-incompatible way, it is a breaking change that requires a bump in major version." Contracts are "meant for public models that other teams or dbt projects rely on." — [dbt model contracts](https://docs.getdbt.com/docs/collaborate/govern/model-contracts)
- **Shift left (Confluent, Andrew Jones, April 2, 2025)** [vendor]: a data contract is "a human- and machine-readable document that captures this metadata" — schema definitions, SLAs ("codified in the contract, and changes to them are tracked over time"), documentation, data categorisation, versioning and change-management policies; "The contract belongs to the data product owner"; the contract is published to Schema Registry and applied to a Kafka topic; the registry "can also enforce data-quality checks within streams and define migration rules." Quotes: "Instead of reacting to data issues downstream, you prevent them at the source"; "Improving data quality upstream (to the left) reduces costs and improves outcomes downstream (to the right)". Argument: each downstream consumer otherwise repeats remediation "with slightly different logic", and unmanaged upstream schema changes break every consumer. — [Shifting Left: How Data Contracts Underpin People, Processes, and Technology](https://www.confluent.io/blog/shifting-left/) (2025-04-02)
- **Chad Sanderson's "Shift Left Data Manifesto"** (as reported by InfoWorld, Andrew C. Oliver, July 17, 2025 — secondary): "the only sustainable path to trustworthy AI and analytics is to treat data changes in the same manner as software changes"; contracts "define shape, semantics, lineage, and ownership" and are checked in CI as a merge gate; expectations belong "inside the code base, not downstream"; notifications go to the developer who opened the PR; example: a one-line change dropping a prefix would have silently removed 40% of new records from an attribution model, caught at check-in in ~30 seconds with a contract; "Quality shifted left. Security shifted left. Data is next." — [It is time to shift data left (InfoWorld)](https://www.infoworld.com/article/4023622/it-is-time-to-shift-data-left.html) (2025-07-17). Search results also attribute to Sanderson the O'Reilly book *Data Contracts* (with Mark Freeman) and the Gable company; the manifesto text itself was not fetched.
- **Confluent Schema Registry compatibility** (Confluent Platform 8.4, last updated Oct 13, 2026): BACKWARD (default; consumers on new schema read last schema; add optional fields / remove fields), BACKWARD_TRANSITIVE (all earlier versions), FORWARD (remove optional fields / add fields), FORWARD_TRANSITIVE, FULL (add/remove optional fields only), FULL_TRANSITIVE, NONE (checks disabled). "When a schema is updated, Schema Registry checks it for compatibility against previous versions before accepting the new version." Upgrade order: BACKWARD → upgrade consumers first; FORWARD → producers first; FULL → independent. BACKWARD is preferred for Kafka "so consumers can be rewound to the start of a topic"; Kafka Streams supports only BACKWARD-based types. — [Schema Evolution and Compatibility](https://docs.confluent.io/platform/current/schema-registry/fundamentals/schema-evolution.html) (2026-10-13)

### Inferences
- **MANDATORY (per ODCS/DCS structure)** for any dataset shared across team boundaries: a contract artefact carrying schema (names/types/constraints), ownership/team, SLA (freshness/latency/retention), quality rules and version — the three specifications converge on exactly these sections, and dbt's contract scoping ("public models that other teams rely on") agrees on where contracts are required.
- **MANDATORY (streaming)**: a registered compatibility mode other than NONE; Confluent's registry rejects incompatible registrations, giving the technical enforcement point for "breaking vs non-breaking".
- **RECOMMENDED**: enforce contracts in producer CI (Sanderson, Jones) and detect breaking changes by diffing against prior state (dbt `--state` comparison); bump major version on breaking change (dbt), mirroring API semantics.
- **OPTIONAL/CONTEXTUAL**: pricing, authoritative definitions, custom properties sections of ODCS.
- Standards convergence: the DCS → ODCS deprecation removes the earlier conflict between two YAML dialects; the framework should target ODCS v3.x and use the Data Contract CLI for export/translation.

### Gaps
- ODCS pages fetched did not enumerate the quality rule types (text/library/sql/custom) or SLA property names; those remain unverified here.
- Sanderson's own manifesto/Data Quality Camp posts were not fetched directly; only InfoWorld's summary.
- No source quantified the agility cost of contracts; the "declarative contracts vs agility" conflict is argued (Jones; Oliver) but not measured.

## Key Question 4 — Reconciliation: row counts, hash/aggregate totals, control/balance tables, Kimball audit dimension and error-event schema, financial subledger-to-GL ties, data-diff, CDC lag, late-arriving data, idempotent reloads

### Takeaway
Reconciliation is prescribed at three grains: (a) batch-level control totals (row counts and aggregates compared source-to-target: Soda `row_count_diff`, Databricks `a_count == b_count`, Netflix row-count audits), (b) row-level diffs via segment hashing/bisection across databases or JOIN within one database (data-diff, archived 2024; reladiff fork), and (c) Kimball's back-room error-event schema plus an audit dimension that "elevates metadata to the status of ordinary data." For financial data the authoritative practice (Oracle Fusion docs) is subledger-to-GL reconciliation per period with control accounts locked to subledger sources, run after period close.

### Cited Findings
- **Soda** reconciliation: `row_count_diff` between a Snowflake target and a MySQL source with `must_be_less_than: 1`; "Compare a target dataset against one or more sources, from row counts and aggregates down to individual records." — [Soda Docs](https://docs.soda.io/) (n.d.)
- **Databricks** row-count validation materialized view with `EXPECT (a_count == b_count)` + fail-on-violation "checks that no data is lost during transformations". — [Databricks expectation patterns](https://docs.databricks.com/aws/en/ldp/expectation-patterns) (2026-10-26)
- **Netflix** WAP audits: row count ≥ 0 and ≥ prior value (fail), null count vs normal distribution (warn). — [Scaling Data Quality @ Netflix](https://www.slideshare.net/MichelleFUfford/scaling-data-quality-netflix-76917740) (2017-06-12)
- **Kafka Connect**: with `errors.tolerance=all`, "you must use internal metrics or compare source and processed record counts to find failures." — [Kafka Connect Concepts](https://docs.confluent.io/platform/current/connect/concepts.html) (2026-10-16)
- **data-diff** (Datafold, MIT): "Compare datasets fast, within or across SQL databases"; repository "was archived by the owner on May 17, 2024"; Datafold is "no longer actively supporting or developing open source data-diff"; 318 forks. — [datafold/data-diff](https://github.com/datafold/data-diff) (archived 2024-05-17)
- **reladiff** (erezsh, MIT): "a fork of an archived project called data-diff"; cross-database mode uses "a divide-and-conquer algorithm, based on matching hashes" to find modified segments and download only what is needed; same-database mode compares with a JOIN, can materialise the diff into a local table; benchmarks "over 25M rows in under 10 seconds" and ~1B rows in ~5 minutes assuming no differences; "over a dozen" databases incl. MySQL, Postgres, Snowflake, BigQuery, Oracle, ClickHouse; cross-database (e.g., PostgreSQL → Snowflake). — [erezsh/reladiff](https://github.com/erezsh/reladiff) (n.d.)
- **Kimball audit dimension** (Design Tip #164, Ralph Kimball, March 3, 2014): attached to fact tables; "elevates metadata to the status of ordinary data"; "One of the most effective tools for managing data quality and data governance"; two column groups — environment/version variables (ETL master version number, currency-conversion version, allocation version) and data-quality indicator flags (missing-data flag, data-supplied/estimated flag, unlikely-value flag) derived "from the error event fact table that logs errors along the ETL pipeline"; flags are warnings only ("the business user should tread cautiously"); advice to "keep it simple and not get too idealistic in the beginning"; "Business users are surprisingly grateful for this kind of information." — [Design Tip #164: Have You Built Your Audit Dimension Yet?](https://www.kimballgroup.com/2014/03/design-tip-164-built-your-audit-dimension/) (2014-03-03). The technique page adds that audit attributes "could include environment variables describing the versions of ETL code used to create the fact rows", useful "for compliance and auditing purposes". — [Kimball Techniques: Audit Dimension](https://www.kimballgroup.com/?p=19403) (n.d.)
- **Kimball error event schema**: quality depends on "a comprehensive system of data quality screens or filters that test the data as it flows from the source systems to the BI platform"; each detected error is logged in a dimensional schema "available only in the ETL back room": an error event fact table (one row per error event) and an error event detail fact table (one row per column per table involved). — [Kimball Techniques: Error Event Schemas](https://www.kimballgroup.com/?p=19414) (n.d.). Search results (table of contents of *The Data Warehouse ETL Toolkit*, not the full text) name the screen taxonomy as column property enforcement, structure enforcement, and data/value rule enforcement — not verified against the book.
- **Kimball late-arriving facts**: a fact row arrives late when the current dimensional context "does not match the incoming row"; the dimensions must be searched for "the dimension keys that were effective" when "the late arriving measurement event occurred". — [Kimball Techniques: Late Arriving Facts](https://www.kimballgroup.com/data-warehouse-business-intelligence-resources/kimball-techniques/dimensional-modeling-techniques/late-arriving-fact/) (n.d.)
- **Oracle Fusion subledger-to-GL reconciliation** (Using General Ledger, release 26A): prerequisite — subledger transactions imported and accounted in GL and journals posted; open payables/receivables balances in the subledgers are compared with the corresponding GL account balance for the period; on a difference the process matches each subledger transaction to its accounting entry; exceptions flagged automatically: transactions without complete accounting, amounts that don't tie to the accounting entry, manually entered journals posted to the account, journals not from the subledger modules. Reports: Account Analysis (beginning/ending balances and all journals affecting the account), Payables/Receivables to Ledger Reconciliation (OTBI, drill from summary to detail; AP report integrates with the AP Trial Balance), plus Trial Balance, General Ledger and Journal reports. Controls: run reconciliation "only after the Receivables and Payables periods are closed to new subledger transactions"; reconcile at ledger level or per primary balancing segment; "Designate payables and receivables GL accounts as control accounts and prevent other sources from posting to them"; the accounting department owns reconciliation. The page does not state a numeric "zero difference" target; it says discrepancies must be identified and explained. — [Oracle: Account Reconciliation and Subledgers](https://docs.oracle.com/en/cloud/saas/financials/26a/faugl/account-reconciliation-and-subledgers.html) (n.d.)
- **Debezium CDC lag metrics** (PostgreSQL connector, docs 3.7): streaming MBean `debezium.postgres:type=connector-metrics,context=streaming,server=<topic.prefix>` exposes `MilliSecondsBehindSource` ("Gap between the last change event's timestamp and when the connector processed it. Clock differences between the database and connector hosts affect this value"), min/max/avg and P50/P95/P99 variants (when `statistics.metrics.enabled`, default true), `MilliSecondsSinceLastEvent`, `Connected`, `QueueTotalCapacity`/`QueueRemainingCapacity`, `NumberOfCommittedTransactions`, `NumberOfErroneousEvents`, `NumberOfEventsFiltered`, `SourceEventPosition`, `LastTransactionId`, `CapturedTables`; snapshot MBean exposes `SnapshotRunning/Completed/Aborted`, `RowsScanned`, `RemainingTableCount`, chunk bounds for incremental snapshots. — [Debezium connector for PostgreSQL](https://debezium.io/documentation/reference/stable/connectors/postgresql.html) (3.7, n.d.)
- **Idempotent reloads**: Airflow — tasks "should produce the same outcome on every re-run"; no plain INSERT on re-run (upsert instead); partition reads by `data_interval_start`; "never produce incomplete results". — [Airflow Best Practices](https://airflow.apache.org/docs/apache-airflow/stable/best-practices.html) (3.4.0). Iceberg — WAP writes go to a branch so "The main table history is unaffected" until `fast_forward`. — [Iceberg Branching](https://iceberg.apache.org/docs/latest/branching/)

### Inferences
- **MANDATORY (financial pipelines)** — following Oracle's control model: (1) control accounts that only the subledger/source pipeline may post to; (2) per-period reconciliation of subledger activity and balances to the GL account after the period is closed to new transactions; (3) every difference classified (unaccounted transaction, amount mismatch, manual journal, non-subledger journal) and explained before publication. Row counts alone are insufficient — amounts must tie.
- **MANDATORY (any load)** — a batch control record (Kimball audit row / Netflix audit table / Databricks event log) with source and target row counts and at least one aggregate (sum of a measure), compared with a tolerance of zero for financial measures; idempotent, partition-scoped writes so a failed audit can be re-run without duplicates.
- **RECOMMENDED** — an audit dimension FK on every fact row (Kimball) carrying ETL version and quality flags; an error-event schema in a back-room schema; a `valid-thru`/published timestamp in the catalog (Netflix Metacat example).
- **RECOMMENDED** — hash/segment diffs (reladiff) for migration or replication validation; monitor CDC lag with `MilliSecondsBehindSource` percentiles and alert on `MilliSecondsSinceLastEvent` and `Connected=false`.
- **RECOMMENDED** — late-arriving facts resolve surrogate keys as of the event's effective date (Kimball), which requires type-2 dimensions to keep effective-date ranges — a schema-design consequence.
- **OPTIONAL/CONTEXTUAL** — restatement handling by versioned snapshots/tags (Iceberg historical tags with retention) rather than in-place overwrite.

### Gaps
- No fetched source gives a formal definition of "trial balance = 0" as a pipeline assertion; Oracle's page frames reconciliation as explained differences rather than a numeric zero target. Treat "debits = credits" as accounting first principles not sourced here.
- The Kimball ETL Toolkit's full ABC (audit/balance/control) chapter was not accessible; only Kimball Group web pages and a table of contents in search results.
- data-diff's original hashdiff/joindiff naming was not present on the archived README; reladiff describes the same two modes without those names.

## Key Question 5 — Lineage and metadata: OpenLineage spec; DataHub, OpenMetadata, Atlas, Amundsen, Unity Catalog, Snowflake, dbt artifacts, Purview, Dataplex; table vs column lineage; push vs pull; what a schema framework should require at design time

### Takeaway
OpenLineage (LF AI & Data graduate project, spec 1.55.0) is the de-facto interchange model — Job/Run/Dataset plus facets, including a column-lineage facet with DIRECT/INDIRECT transformation types — implemented by Marquez (reference), DataHub, Dataplex and the Airflow/Spark/dbt/Flink/GX integrations. Platform catalogs (Unity Catalog, Snowflake Horizon, Purview, Dataplex) now capture table- and column-level lineage automatically from query logs with retention windows ranging from 30 days (Dataplex) to 1 year (Snowflake, Databricks system tables; UI indefinite). Design-time metadata (owner, description, classification) is expected to be declared in the schema artefact itself (dbt YAML / `COMMENT ON` / glossary-term and tag assignments) and ingested by pull or pushed as events.

### Cited Findings

**OpenLineage specification**
- Object model (docs 1.55.0): Job = "a process that consumes or produces Datasets", unique name within a namespace; Run = "an instance of a Job that represents one of its occurrences in time", client-generated `runId` (UUIDv7 recommended); Dataset = "an abstract representation of data", name from physical location, "The combined namespace and name for a Dataset should be enough to uniquely identify it within a data ecosystem." Event types: RunEvent (runtime; usually START then COMPLETE; additive updates with timestamps), JobEvent (design-time job metadata, not tied to a Run), DatasetEvent (design-time dataset metadata such as schema/ownership). Facets: job (`sourceCodeLocation`, `sourceCode`), run (`nominalTime`, `parent`, `errorMessage`, `sql`), dataset (`schema`, `dataSource`, `lifecycleStateChange`, `version`), input (`dataQualityMetrics`, `dataQualityAssertions`), output (`outputStatistics`). — [OpenLineage: Object Model](https://openlineage.io/docs/spec/object-model) (1.55.0, n.d.)
- Column lineage facet (`outputs[].facets.columnLineage`, schema 1-2-0): "provides fine grained information on datasets' dependencies"; `fields` keyed by output column, each with `inputFields` (`namespace`, `name`, `field`, `transformations`); transformation `type` DIRECT ("the output value is derived from the input") with subtypes IDENTITY/TRANSFORMATION/AGGREGATION, or INDIRECT ("the input affects the output but is not derived from it") with subtypes JOIN/GROUP_BY/FILTER/SORT/WINDOW/CONDITIONAL; `masking` boolean for obfuscated inputs (hash/count). Spark emits it; `spark.openlineage.columnLineage.datasetLineageEnabled=True` yields the compact representation (recommended). — [OpenLineage: Column Level Lineage Dataset Facet](https://openlineage.io/docs/spec/facets/dataset-facets/column_lineage_facet) (n.d.)
- Governance/integrations: "an LF AI & Data Foundation Graduate project"; spec defined in OpenAPI, extensible with custom facets; integrations: Apache Airflow, Flink, Hive, Spark; dbt, Feast, Great Expectations, SQL, Trino; Marquez is "an LF AI & Data project and the reference implementation of the OpenLineage API"; Egeria listed as a metadata bus. — [OpenLineage docs](https://openlineage.io/docs/) (1.55.0, n.d.)
- Marquez: "the reference implementation of OpenLineage"; released/open-sourced by WeWork; real-time OpenLineage-compatible metadata endpoint, visual graph of job inputs/outputs and dataset lineage with execution metrics, lineage API for "backfills and root cause analysis" and enrichment of catalogs/data-quality systems; integrations: Airflow, Spark, Flink, dbt, Dagster. — [Marquez](https://marquezproject.ai/) (n.d.)

**Catalogs and platform lineage**
- DataHub (docs 1.8.0; "started at LinkedIn in 2019"; Apache-2.0; "150+ integrations"): table-level and column-level lineage (expand columns in the lineage view; column breadcrumb focus), pipeline lineage; capture = automatic from ingestion sources with "Table Lineage Capability", manual UI edits since v0.9.5 (warning: manual and programmatic edits can overwrite each other — use `incremental_lineage`), or programmatic API; impact analysis and metadata propagation along lineage. — [DataHub: Lineage](https://docs.datahub.com/docs/features/feature-guides/lineage) and [datahub-project/datahub](https://github.com/datahub-project/datahub) (n.d.)
- DataHub ingestion architecture: Metadata Change Proposals (MCPs) are "requests to change an organization's Metadata Graph"; transported over Kafka ("highly scalable async publishing") or synchronously to the GMS HTTP endpoint; **pull-based** = Python ingestion framework connects to sources and pushes MCPs (schedulable with Airflow); **push-based** = any system emitting an MCP to Kafka or REST, with Python emitters provided; `mce-consumer-job` writes to `datahub-gms` `/ingest`. — [DataHub: Metadata Ingestion Architecture](https://docs.datahub.com/docs/architecture/metadata-ingestion) (1.8.0, n.d.)
- DataHub Business Glossary: Terms ("words or phrases with a specific business definition") and Term Groups (folders); `Contains`/`Inherits From` relationships turn the glossary into "a business ontology"; Terms and Groups "allow you to add documentation and unique owners"; glossary can be defined in a file and ingested by CLI "on a git commit hook" (GitHub Action available). — [DataHub: Business Glossary](https://docs.datahub.com/docs/glossary/business-glossary) (1.8.0, n.d.)
- OpenMetadata (docs v2.0.x): "Unified platform for data discovery, lineage, and governance"; observability/data quality with "Dimensional Validation (completeness, accuracy, consistency, timeliness)" and "Data Quality as Code (version-controlled checks)"; guides for Data Contracts and Governance; MCP Server and AI SDK (Python/TypeScript/Java/CLI); deployment via Docker, Kubernetes, cloud-managed. — [OpenMetadata docs](https://docs.open-metadata.org/) (n.d.)
- Apache Atlas (Apache-2.0): "extensible set of core governance services" for Hadoop with a common metadata store so "different metadata consumers can work together"; lineage "enriched by business taxonomical metadata, with both prescriptive and forensic models"; RBAC/ABAC with Apache Ranger preventing unauthorised access at runtime; hooks for HBase, Hive, Impala, Kafka, Sqoop, Storm, Falcon, Couchbase; builds on Java 8/11/17. — [apache/atlas](https://github.com/apache/atlas) (n.d.)

Note: the domain amundsen.io returned a 301 to an unrelated third-party site on 2026-11-07, so only the GitHub source is cited. — [amundsen-io/amundsen](https://github.com/amundsen-io/amundsen) (archived 2026-09-29)

- Google Dataplex Universal Catalog lineage: automatic from BigQuery (copy/load/DDL/DML; appears "within 24 hours"), Managed Service for Apache Airflow, Vertex AI Pipelines, Data Fusion, Dataproc/Serverless Spark and Dataflow (publish events); API model = Process ("A data transformation definition. - dbt artefacts for lineage/ownership: exposures define "a downstream use of your dbt project" with required `name`, `type` (dashboard/notebook/analysis/ml/application) and `owner` (`name` or `email`), expected `depends_on` (ref/source/metric), optional `url`, `maturity` (high/medium/low), `description`, `tags`, `meta`; exposures appear as "EXP" nodes in the dbt Catalog DAG; `dbt run -s +exposure:<name>` builds everything upstream. — [dbt: Add exposures to your DAG](https://docs.getdbt.com/docs/build/exposures) (last updated Nov 3, 2026). - Design-time descriptions in DDL: PostgreSQL `COMMENT ON TABLE/COLUMN/CONSTRAINT ...` — see Key Question 1. — [PostgreSQL COMMENT](https://www.postgresql.org/docs/current/sql-comment.html)

### Inferences
- Push vs pull: DataHub's architecture documents both (pull = ingestion framework scraping sources; push = emitters/MCPs from the job itself); OpenLineage is the push-side event standard, and Marquez/Dataplex/DataHub consume it; Amundsen's Databuilder and Purview scans are pull-only. **RECOMMENDED**: push OpenLineage run events from orchestrators/engines (Airflow, Spark, dbt) for run-level lineage and pull catalog metadata (schemas, owners, tags) on a schedule; use `incremental_lineage` where both coexist (DataHub warning).
- Table vs column lineage: every modern platform fetched (Unity Catalog, Snowflake, Dataplex, Purview, DataHub, OpenLineage) provides column lineage, with platform-specific holes (UDFs, renamed objects, nested STRUCTs, >1,500 links). **RECOMMENDED**: design schemas to be lineage-friendly — avoid renames (Databricks loses lineage), avoid path-based references, prefer SQL over opaque UDFs, keep nested structs shallow for BigQuery.
- Design-time requirements for a schema framework (synthesised from dbt exposures' required `owner`, DataHub glossary owners, Purview's "ownership" in high-fidelity lineage, Netflix Metacat attributes such as audience/lifecycle, and PostgreSQL `COMMENT ON`):
  - **MANDATORY**: every table has an owner (dbt requires `owner` on exposures; ODCS has Team/Roles sections), a description (DDL COMMENT or dbt `description`), and a classification/tag for PII (Atlas/Ranger tag-based access; OpenLineage `masking` flag exists precisely because PII columns propagate).
  - **MANDATORY**: column descriptions in the schema artefact (dbt YAML or `COMMENT ON COLUMN`) — but never sensitive values, per PostgreSQL's visibility warning.
  - **RECOMMENDED**: steward and glossary-term bindings (DataHub Terms with owners), `maturity`/lifecycle attributes (dbt exposures `maturity`; Netflix Metacat lifecycle/audience), and stable namespace+name identity for datasets (OpenLineage naming rule).
- Retention asymmetry (30 days Dataplex vs 395 days Databricks system tables vs 1 year Snowflake) means **RECOMMENDED**: export lineage to a catalog (DataHub/OpenMetadata/Marquez) if audit needs exceed platform retention.

### Gaps

- Apache Atlas's official site is a single-page app that returned only the title; type system, classification propagation and release info are not verified here.

## Key Question 6 — Observability and monitoring: freshness/volume/schema-change detection, anomaly detection, alert routing, incident management; schema-change propagation and breaking vs non-breaking classification

### Takeaway
Observability tooling monitors the same handful of signals — freshness, volume/row counts, schema changes, distribution/quality metrics, lineage for blast radius — either as native warehouse tests (Elementary, dbt freshness) or as SaaS monitors (Monte Carlo, DataHub observability, Elementary Cloud); alert routing to Slack/Teams/PagerDuty-style channels and incident objects are standard. Breaking vs non-breaking schema change is formally defined by Schema Registry compatibility modes and by dbt's contract diff (column removal / type change / constraint removal = breaking).

### Cited Findings
- Monte Carlo [vendor] five pillars: freshness, quality (NULL %, unique %, accepted range), volume, schema ("changes to how data is organized, and who made them and when"), lineage ("which upstream sources and downstream consumers were affected"). — [What is Data Observability?](https://montecarlo.ai/blog-what-is-data-observability) (2026-10-28)
- Elementary: "Automated monitors for freshness, volume, and schema issues"; anomaly-detection tests "collect data quality metrics and flag anomalies as native dbt tests"; alerts to Slack and Microsoft Teams with "custom channels and owner tagging"; lineage "enriched with test results, for impact and root-cause analysis"; Cloud docs list "Alerts and incidents", "incidents", "AI triage/resolution", and "Critical assets". — [elementary-data/elementary](https://github.com/elementary-data/elementary); [Elementary docs](https://docs.elementary-data.com/)
- DataHub observability: "data quality assertions, freshness checks, and incident tracking". — [datahub-project/datahub](https://github.com/datahub-project/datahub)
- OpenMetadata: "Dimensional Validation (completeness, accuracy, consistency, timeliness)" and "Data Quality as Code". — [OpenMetadata docs](https://docs.open-metadata.org/)
- dbt freshness thresholds (`warn_after`/`error_after`) and `dbt freshness` artefacts (`target/freshness.json`). — [dbt sources](https://docs.getdbt.com/docs/build/sources)
- Deequ anomaly detection on metrics stored in a `MetricsRepository`; Netflix null-count vs normal distribution; Databricks mean ± 3σ over 30 days; dbt-expectations stdev-based anomaly checks — see Key Questions 1-2.
- CDC lag/health: Debezium `MilliSecondsBehindSource` (P50/P95/P99), `MilliSecondsSinceLastEvent`, `Connected`, queue capacity metrics via JMX; Prometheus/Grafana export with example dashboards "maintained on a best-effort basis". — [Debezium PostgreSQL connector](https://debezium.io/documentation/reference/stable/connectors/postgresql.html); [Debezium: Monitoring](https://debezium.io/documentation/reference/stable/operations/monitoring.html) (3.7)
- OpenLineage run events carry `errorMessage` run facets and `dataQualityMetrics`/`dataQualityAssertions` input facets, so quality results can travel with lineage. — [OpenLineage Object Model](https://openlineage.io/docs/spec/object-model)
- Schema-change classification:
  - Schema Registry: BACKWARD allows "Add optional fields; remove fields" (removal requires the field was optional/had a default), FORWARD allows "Remove optional fields; add fields", FULL allows "Add or remove optional fields only"; registration of an incompatible schema is rejected. — [Confluent Schema Evolution](https://docs.confluent.io/platform/current/schema-registry/fundamentals/schema-evolution.html) (2026-10-13)
  - dbt contracts: breaking = remove column, change `data_type`, remove/modify constraint, remove contracted model; "requires a bump in major version". — [dbt model contracts](https://docs.getdbt.com/docs/collaborate/govern/model-contracts) (2026-10-29)
  - dbt contracts on incremental models require `on_schema_change: append_new_columns` or `fail` (i.e., additive or halt). — same source
  - Iceberg: branch writes "are validated against the current table schema"; tag/snapshot queries use the schema in place at snapshot time. — [Iceberg Branching](https://iceberg.apache.org/docs/latest/branching/)
  - Databricks: "Renamed catalogs, schemas, tables, views, or columns lose their lineage." — [Unity Catalog lineage](https://docs.databricks.com/en/data-governance/unity-catalog/data-lineage.html)
  - Monte Carlo [vendor] schema pillar: track who changed what and when. — [Monte Carlo](https://montecarlo.ai/blog-what-is-data-observability)

### Inferences
- **MANDATORY (contracted/public datasets)**: classify every schema change as breaking (drop/rename column, narrow/alter type, tighten constraint, remove dataset) or non-breaking (add optional/nullable column, widen/relax) — this classification is identical in Confluent's compatibility rules and dbt's contract diff; emit a major version bump for breaking changes and block in CI/registry.
- **RECOMMENDED**: monitor the five signals with thresholds derived from history (freshness via `loaded_at_field`, volume via row-count vs prior/historical bands, schema diffs vs contract, null/unique % bands, CDC lag percentiles), route alerts to the dataset owner recorded in metadata (Elementary "owner tagging"; dbt exposure `owner`), and open incidents linked to lineage for impact analysis (DataHub, Elementary Cloud, Purview "impact analysis").
- **OPTIONAL/CONTEXTUAL**: ML-based anomaly detection; Netflix's lessons ("Not every table needs quality coverage") and Databricks' simple ±3σ pattern suggest statistical bands suffice for most tables.

### Gaps
- No fetched source specifies alert-routing or incident-SLA numbers (e.g., acknowledgement times); incident management is described functionally only.
- Monte Carlo's methodology for anomaly detection is not disclosed on the fetched page.

## Key Question 7 — Conflicts between sources (warehouse testing vs ingestion validation; declarative contracts vs agility; vendor claims vs open standards)

### Takeaway
The sources disagree less on *whether* to validate than on *where the primary gate sits*: dbt/Elementary/GX place assertions post-build in the warehouse, while Netflix/Iceberg/Databricks/Intuit/Airbnb gate before publication, and Sanderson/Jones push enforcement to the producer's CI. The reconciled position in the fetched docs is that each layer catches a different failure class, and that platform constraint enforcement is weaker in analytical engines than in OLTP databases.

### Cited Findings
- **Post-build vs pre-publish**: dbt data tests run after a model is built and "seek to grab 'failing' records" ([dbt data tests](https://docs.getdbt.com/docs/build/data-tests)); contradicted in emphasis by Iceberg/Netflix WAP, which validate on an audit branch/table *before* `fast_forward`/publish ([Iceberg Branching](https://iceberg.apache.org/docs/latest/branching/); [Netflix slides](https://www.slideshare.net/MichelleFUfford/scaling-data-quality-netflix-76917740)), and by Databricks `expect_or_fail`, which rolls back the transaction ([Databricks expectations](https://docs.databricks.com/aws/en/ldp/expectations)). dbt partially bridges this: unit tests run pre-build in CI, and contracts fail the build on shape mismatch ([dbt unit tests](https://docs.getdbt.com/docs/build/unit-tests); [dbt contracts](https://docs.getdbt.com/docs/collaborate/govern/model-contracts)).
- **Constraints vs tests**: dbt says constraints can replace some tests only where the platform enforces them; "Most platforms only enforce `not_null`" ([dbt contracts](https://docs.getdbt.com/docs/collaborate/govern/model-contracts)) — which directly conflicts with any assumption that warehouse DDL constraints (PK/FK/UNIQUE) are enforced; PostgreSQL is the exception listed.
- **Blocking everything vs tiered**: Lyft/Airbnb-style blocking operators halt the DAG; Airbnb reportedly added non-blocking checks because minor failures "had been holding up critical pipelines' SLAs" (search snippet; [Airbnb Wall](https://medium.com/airbnb-engineering/how-airbnb-built-wall-to-prevent-data-bugs-ad1b081d6e8f), URL from search only); Netflix's "Not every table needs quality coverage" and Databricks' warn-by-default agree with tiering, while Intuit's circuit breaker ("data availability in dashboards a function of the data quality") is strictly blocking ([Strata 2019](https://conferences.oreilly.com/strata/strata-ca-2019/public/schedule/detail/73082.html)).
- **Shift-left vs downstream tooling**: Jones (Confluent) and the Sanderson manifesto argue downstream remediation is duplicated and too late ([Confluent blog](https://www.confluent.io/blog/shifting-left/); [InfoWorld](https://www.infoworld.com/article/4023622/it-is-time-to-shift-data-left.html)); both are vendor-adjacent (Confluent; Gable). Warehouse-native tools (dbt, Elementary, dbt-expectations) implicitly assume data has already landed.
- **Declarative contracts vs agility**: Confluent's compatibility table formalises the trade-off — BACKWARD lets producers add optional fields freely but forces consumer-first upgrades; FULL allows independent upgrades but restricts changes to optional fields only; NONE gives "no safety net" ([Schema Evolution](https://docs.confluent.io/platform/current/schema-registry/fundamentals/schema-evolution.html)). dbt likewise restricts contracted incremental models to `append_new_columns` or `fail`.
- **Vendor taxonomies vs open standards**: Monte Carlo's five pillars (vendor; author claims coinage of the term) vs OpenLineage's spec-defined facets (`dataQualityMetrics`, `dataQualityAssertions`, `schema`, `columnLineage`) under LF AI & Data governance; note Monte Carlo's own pillar list changed ("quality" now replaces "distribution" in the updated 2026 page). Similarly, three contract YAML dialects (PayPal → ODCS; DCS) have converged on ODCS only as of ODCS v3.1.0.
- **Tool lifecycle risk**: data-diff archived (May 17, 2024) and Amundsen archived (Sept 29, 2026); amundsen.io now redirects to an unrelated site — open-source observability/catalog tooling churns, whereas the specifications (OpenLineage 1.55.0, ODCS 3.2.0) and platform-native features (Unity Catalog, Snowflake, Dataplex, Purview) are the stable layer.

### Inferences
- The framework should prescribe *both* ingestion-time gating and warehouse tests, with OLTP constraints as the non-negotiable floor; it should treat contract enforcement location as a maturity dimension (warehouse tests → pipeline gates → producer CI).
- Prefer specifications over tools when prescribing: ODCS for contracts, OpenLineage for lineage events, Schema Registry compatibility vocabulary for breaking-change classification; name tools only as reference implementations.

### Gaps
- No controlled comparison or benchmark was found quantifying defect-catch rates of warehouse testing vs ingestion validation; the conflict is argued from architecture, not measured.
