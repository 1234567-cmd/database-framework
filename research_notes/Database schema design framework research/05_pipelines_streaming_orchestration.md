# 05 – Pipelines, Streaming and Orchestration: how pipeline technology and architecture patterns constrain schema design

Research scope: Apache Kafka (+ Confluent Schema Registry, event-streaming patterns, Kafka Connect SMTs), Debezium (log-based CDC, transactional outbox), Apache Spark (schema inference, Structured Streaming), open table formats (Iceberg, Delta Lake, Hudi), Apache Airflow and Dagster orchestration guidance, and the ETL-vs-ELT / batch-vs-streaming / lambda-vs-kappa / Dataflow-model debates, plus data contracts. Verified on 2026-11-07 (fetch dates); page "last updated" dates recorded where shown, otherwise "n.d.".

Labelling convention used throughout: **MANDATORY** = the source states it as a requirement or a precondition for correctness; **RECOMMENDED** = the source states it as best practice / default advice; **OPTIONAL/CONTEXTUAL** = the source presents it as a trade-off or situational choice. Applicability tags: `[streaming]`, `[OLTP]`, `[OLAP/warehouse]`, `[lakehouse/data_lake]`, `[all]`.

Authority scale used: 5 = official project documentation / standards body / foundational peer-reviewed paper; 4 = recognised book or major-organisation engineering blog; 3 = reputable tool docs or well-known practitioner post.

## KQ1a – Apache Kafka: topics, partitions, keys, ordering, log compaction, exactly-once, retention

### Takeaway
Kafka's official design docs make the **partition** the unit of ordering and the **record key** the only mechanism that maps an entity to a partition; log compaction turns a keyed topic into a "latest value per key" table whose deletes are null-payload tombstones. Exactly-once exists inside Kafka (idempotent producer + transactions + `read_committed`), but the docs explicitly push end-to-end exactly-once onto the *consumer's* storage (offset stored with output). All of this means an event schema must carry a stable entity key and an explicit event timestamp, and deletes must be modellable as a key with no value.

### Cited Findings
- Ordering is per partition: a topic is "a set of totally ordered partitions", and each partition "is consumed by exactly one consumer within each subscribing consumer group at any given time" — [Apache Kafka 4.3 Design](https://kafka.apache.org/43/design/design/) (n.d., Kafka 4.3 docs; authority 5). `[streaming]` **MANDATORY** (ordering is only guaranteed within a partition, so anything that must be ordered must share a key).
- Keys drive partition placement: "We expose the interface for semantic partitioning by allowing the user to specify a key to partition by", and the key is used to "hash to a partition" — [Apache Kafka 4.3 Design](https://kafka.apache.org/43/design/design/). `[streaming]` **MANDATORY** for per-entity ordering.
- Delivery semantics defined verbatim: at most once = "Messages may be lost but are never redelivered"; at least once = "Messages are never lost but may be redelivered"; exactly once = "Each message is processed once and only once" — [Apache Kafka 4.3 Design](https://kafka.apache.org/43/design/design/).
- Idempotent producer: "Since 0.11.0.0, the Kafka producer also supports an idempotent delivery option which guarantees that resending will not result in duplicate entries in the log"; "the broker assigns each producer an ID and deduplicates messages using a sequence number" — [Apache Kafka 4.3 Design](https://kafka.apache.org/43/design/design/). The older KafkaProducer Javadoc (URL returned by WebSearch, not opened; Kafka 1.1) states the idempotent producer "strengthens Kafka's delivery semantics from at least once to exactly once delivery" but "can only guarantee idempotence for messages sent within a single session" — [KafkaProducer (kafka 1.1.0 API)](https://kafka.apache.org/11/javadoc/org/apache/kafka/clients/producer/KafkaProducer.html). `[streaming]` **RECOMMENDED** (enable idempotence; it does not cover cross-session or cross-system duplicates).
- Transactions and read_committed: "the producer supports the ability to send messages atomically to multiple topic partitions using transactions"; with read_committed "the consumer will only return messages from transactions which were committed"; "Kafka supports exactly-once delivery in Kafka Streams" — [Apache Kafka 4.3 Design](https://kafka.apache.org/43/design/design/). `[streaming]` **OPTIONAL/CONTEXTUAL** (only when read-process-write loops stay inside Kafka).
- End-to-end exactly-once is delegated to the sink: because many output systems do not support two-phase commit, the docs describe the simpler approach of "letting the consumer store its offset in the same place as its output" — [Apache Kafka 4.3 Design](https://kafka.apache.org/43/design/design/). `[streaming → OLTP/OLAP sinks]` **RECOMMENDED** → the *target table schema* needs room for an offset/checkpoint or an idempotency key.
- Log compaction: "Log compaction ensures that Kafka will always retain at least the last known value for each message key"; "A message with a key and a null payload will be treated as a delete from the log"; tombstones are kept for `delete.retention.ms` (default 24 hours); guarantees paraphrased from the list: ordering is preserved (compaction removes but never reorders), offsets never change once assigned, consumers caught up to the head see every message, and consumers reading from offset 0 see the final state of each key provided they reach the head within `delete.retention.ms` — [Apache Kafka 4.3 Design](https://kafka.apache.org/43/design/design/). `[streaming]` **MANDATORY** for "table-like" topics: a stable key and null-value tombstones are the only way to express state and deletion.
- Topic-level defaults (Kafka 4.2 config reference): `cleanup.policy` default `delete` ("This config designates the retention policy to use on log segments"); `retention.ms` default `604800000 (7 days)`; `retention.bytes` default `-1`; `delete.retention.ms` default `86400000 (1 day)` ("The amount of time to retain delete tombstone markers for log compacted topics"); `min.insync.replicas` default `1`; `min.compaction.lag.ms` default `0`; `max.compaction.lag.ms` default `9223372036854775807`; `min.cleanable.dirty.ratio` default `0.5`; `message.timestamp.type` default `CreateTime` ("Define whether the timestamp in the message is message create time or log append time"); `segment.ms` default 7 days — [Kafka 4.2 Topic Configs](https://kafka.apache.org/42/configuration/topic-configs/) (n.d.; authority 5). `[streaming]`
- Replication: producers choose `acks` of 0, 1 or all in-sync replicas; `min.insync.replicas` is the minimum ISR size that `acks=all` writes require; only ISR members may become leader — [Apache Kafka 4.3 Design](https://kafka.apache.org/43/design/design/). **RECOMMENDED** (`acks=all` + `min.insync.replicas` ≥ 2 for durability; the docs describe the mechanism, the numeric choice is contextual).
- Retention rationale: the design doc says Kafka can "retain messages for a relatively long period (say a week)" and old data is discarded "after a fixed period of time or when the log reaches some predetermined size" — [Apache Kafka 4.3 Design](https://kafka.apache.org/43/design/design/). `[streaming]` **OPTIONAL/CONTEXTUAL** (retention length is a reprocessing-window decision, see KQ4 kappa).

### Inferences
- Because `message.timestamp.type` defaults to `CreateTime` (producer-set) and can be switched to `LogAppendTime` per topic, a schema framework should not rely on the broker timestamp as the business event time; an explicit `event_time` field in the payload is the portable choice (this is an inference linking the Kafka config default to the Dataflow event-time/processing-time distinction in KQ4).
- A compacted topic is effectively a materialised table; its "primary key" is the Kafka record key. Composite keys must be serialised deterministically (same bytes for the same entity) or compaction/ordering break. Not stated verbatim by Kafka docs; follows from "hash to a partition" and "last known value for each message key".
- Default 7-day retention bounds the kappa-style reprocessing window unless raised; schema-compatibility guarantees must therefore cover at least the retention window (inference combining Kafka defaults with Kreps' kappa in KQ4).

### Gaps
- The main https://kafka.apache.org/documentation/ page is a JavaScript redirect; the fetched content came from the versioned 4.3 design page and 4.2 topic-config page instead. I did not retrieve the exact sentence "Messages sent by a producer to a particular topic partition will be appended in the order they are sent" from the 4.3 page (the fetch reported it absent); the "totally ordered partitions" wording is what the current page carries.
- The 4.3 design page has no dedicated retention section with numeric defaults; defaults come from the 4.2 topic-config reference.

## KQ1b – Confluent Schema Registry: compatibility modes and per-format evolution rules

### Takeaway
Schema Registry's default is **BACKWARD** (not transitive); compatibility is only checked against the *latest* schema unless a `_TRANSITIVE` mode is chosen, and each mode dictates a specific producer/consumer upgrade order. Which field changes are legal depends on how fields were originally declared (optional / default-valued fields are the only ones that can be added or removed safely), and the rules differ for Avro, Protobuf and JSON Schema (open vs closed content model).

### Cited Findings
- Default: "The Confluent Schema Registry default compatibility type is `BACKWARD`, not `BACKWARD_TRANSITIVE`" — [Schema Evolution and Compatibility for Schema Registry on Confluent Platform](https://docs.confluent.io/platform/current/schema-registry/fundamentals/schema-evolution.html) (Last updated Oct 13, 2026; authority 5). `[streaming]`
- Definitions (paraphrased from the page): BACKWARD = consumers using new schema X can read data produced with X or X-1; BACKWARD_TRANSITIVE: "consumer using schema `X` can process data produced with schema `X`, `X-1`, or `X-2`" (all previous); FORWARD = data produced with schema X can be read by consumers on X or X-1; FORWARD_TRANSITIVE extends to all earlier schemas; FULL = backward and forward compatible between X and X-1; FULL_TRANSITIVE across all registered schemas; NONE = "schema compatibility checks are disabled". The transitive modifier "checks compatibility of a new schema against all previously registered schemas"; otherwise only the latest schema is checked — same source.
- Upgrade order is mode-dependent: BACKWARD → "upgrade all consumers before you start producing new events"; FORWARD → upgrade producers first, ensure older data is no longer available to consumers, then upgrade consumers; FULL → producers and consumers can be upgraded independently; NONE → timing must be handled with care — same source. **MANDATORY** (the ordering is a precondition of the compatibility guarantee). `[streaming]`
- Kafka Streams restriction: only BACKWARD, BACKWARD_TRANSITIVE, FULL and FULL_TRANSITIVE are supported; upgrade Streams apps before the upstream producer — same source. **MANDATORY** when Kafka Streams consumes the topic.
- "The allowed changes depend on how fields were originally defined"; deleting a field while staying compatible requires it was optional or had a default — same source. **MANDATORY** design consequence: fields that may ever be removed must be declared optional/defaulted from day one.
- Avro: adding a field needs a default or "the new schema is not backward compatible"; "Avro requires that the default value conform to the first branch of the union", so optional fields should be `["null", T]` with `"default": null`; Avro has no `optional` keyword, nullability is a union with `"null"` — same source. **MANDATORY** for Avro under BACKWARD.
- Protobuf: "best practice for Protobuf is to use BACKWARD_TRANSITIVE"; "adding new message types is not forward compatible"; fields with default values can be added or removed as a fully compatible change — same source. **RECOMMENDED**.
- JSON Schema: compatibility depends on `compatibilityPolicy` (`LENIENT` or `STRICT`) and the content model (`additionalProperties`). Under STRICT with a *closed* content model (`additionalProperties: false`) adding or removing a required field is not compatible; an *open* model allows more changes — same source. **OPTIONAL/CONTEXTUAL** (open vs closed is a deliberate trade-off between flexibility and strictness).
- Summary table (Avro/Protobuf): add or remove an *optional* field is compatible under backward, forward and full; adding/removing a *required* field is compatible in only one direction (the page's table column alignment was lost in extraction; verify the exact cell on the live page) — same source.

### Inferences
- "Backward compatible" in Schema Registry is consumer-centric (new reader, old data). For a warehouse/lakehouse landing table fed from a topic, BACKWARD means the *table loader* (consumer) must be redeployed before producers change — the loader's target schema must therefore be a superset with defaults (link to Delta/Iceberg "add nullable column" rules in KQ2b).
- The default (non-transitive BACKWARD) silently permits a chain X→X-1→X-2 where X cannot read X-2 data; for compacted/long-retention topics (KQ1a), `_TRANSITIVE` is the safer default. The page states the mechanism; the recommendation to prefer transitive modes for long-retention topics is my inference.

### Gaps
- The second half of the Confluent page (per-type rules for primitives, enums, arrays, unions; "Format-specific compatibility rules") was not retrieved in readable form (the offset fetch returned navigation only). The checkmark tables for required-field changes could not be read cell-by-cell.
- No official statement about Avro *aliases* was found on this page.

## KQ1c – Confluent event-streaming patterns: Data Contract, Schema Evolution, idempotency patterns

### Takeaway
Confluent's pattern catalogue frames the schema as the contract itself ("Data Contract" = a shared schema in a registry) and offers two evolution strategies: compatible changes evolve **in place**; breaking changes require **dual schema upgrades** (versioned streams such as `payments-v1`/`payments-v2`) with explicit consumer migration. The catalogue also names Idempotent Writer / Idempotent Reader, Compacted Event Stream, Schema Validator, Dead Letter Stream, Event Envelope and Correlation Identifier as first-class patterns.

### Cited Findings
- Catalogue scope: "This catalog contains simple and reusable architectural patterns that can be applied over event streaming systems." Categories and patterns listed include Event (Event, Command, Correlation Identifier, Data Contract, Event Envelope, Event Serializer/Deserializer, Event Standardizer, Schema-on-Read); Event Stream (Partitioned Parallelism, Schema Compatibility, Schema Evolution); Event Source (Database Write Aside, Database Write Through, Event Source Connector, Schema Validator); Event Storage (Compacted Event Stream, Infinite Retention Event Stream, Limited Retention Event Stream); Event Processing (Claim Check, Dead Letter Stream, Event Router, Idempotent Writer, Idempotent Reader …); Stream Processing (Event-Time Processing, Wall-Clock-Time Processing, Suppressed Event Aggregator …); Table (Projection Table, State Table); Compositional (CQRS, Event Collaboration, Pipeline, Strangler Fig) — [Confluent Event Streaming Patterns](https://developer.confluent.io/patterns/) (n.d.; authority 5 for Confluent-authored docs, 4 if treated as vendor guidance).
- Data Contract pattern: problem = how can an application know how to process an event sent by another application; solution = a shared schema so applications exchange events without knowing each other's internals; "The Data Contract pattern allows these different applications to cooperate while remaining loosely coupled"; implementation uses Avro (example: purchase record with item, amount, customer ID) and a central repository such as Schema Registry; considerations: use an established schema framework (Avro, Protocol Buffers, JSON Schema) rather than custom support — [Data Contract pattern](https://developer.confluent.io/patterns/event/data-contract/) (n.d.). `[streaming]` **RECOMMENDED**. Note: this page defines the contract as *schema only*; it does not mention SLAs, quality rules or ownership (contrast ODCS in KQ4).
- Schema Evolution pattern: two solutions — *evolve in place* (a stream holds events of both versions; compatibility checks ensure processors and sinks read both) and *dual schema upgrades* for breaking changes (sources write to `payments-v1` and `payments-v2`; "clients must only write to and read from the Event Stream that corresponds to the schema that they can process"; old stream retired after all consumers migrate). Considerations: "Follow Schema Compatibility rules to determine which schema changes are compatible and which are breaking changes." — [Schema Evolution pattern](https://developer.confluent.io/patterns/event-stream/schema-evolution/) (n.d.). `[streaming]` **MANDATORY** decision rule (compatible → in place; breaking → new versioned stream).

### Inferences
- A schema framework needs a *stream-versioning convention* (e.g., `-vN` suffix) as the escape hatch for breaking changes, because Schema Registry compatibility modes (KQ1b) cannot express them.
- "Idempotent Writer/Reader" being catalogued patterns implies the message schema should carry a deduplication identifier (event id / correlation id), consistent with Debezium's outbox `id` column (KQ1d).

### Gaps
- The catalogue page as fetched did not list patterns named "Change Data Capture", "Transactional Outbox", "Event Sourcing" or "Event Deduplication"; related ideas appear under Database Write Through / Write Aside and Event Source Connector. Individual pattern bodies for Idempotent Writer, Compacted Event Stream, Schema Validator were not fetched.

## KQ1d – Debezium: log-based CDC semantics and the transactional outbox

### Takeaway
Debezium documents log-based CDC as capturing *every* committed row change in commit order with millisecond latency, with no `Last Updated` column required and with deletes captured; delivery is exactly-once in normal operation but **at-least-once under failure, so "consumers should always anticipate some duplicate events."** Schema consequences are concrete: captured tables need a primary key (otherwise only create events are emitted), REPLICA IDENTITY controls whether `before` images exist, deletes are emitted as a delete event plus a null-value tombstone, and the outbox table has a prescribed column set (`id`, `aggregatetype`, `aggregateid`, `type`, `payload`).

### Cited Findings
- Why log-based CDC: "Unlike other approaches, such as polling or dual writes, log-based CDC as implemented by Debezium:" "Ensures that all data changes are captured"; "Produces change events with a very low delay while avoiding increased CPU usage required for frequent polling" ("for MySQL or PostgreSQL, the delay is in the millisecond range"); "Requires no changes to your data model, such as a "Last Updated" column"; "Can capture deletes"; "Can capture old record state and additional metadata such as transaction ID and causing query" — [Debezium Features](https://debezium.io/documentation/reference/stable/features.html) (n.d., Debezium stable; authority 5). `[OLTP → streaming]`
- Mechanism (PostgreSQL): "The connector relies on and reflects the PostgreSQL logical decoding feature"; `pgoutput` is "The standard logical decoding output plug-in in PostgreSQL 10+"; "upon restart the connector continues reading the WAL where it last left off"; on first connection "the connector takes a consistent snapshot of all schemas"; snapshot rows carry `op = r` "because a snapshot is a `READ` operation" — [Debezium connector for PostgreSQL](https://debezium.io/documentation/reference/stable/connectors/postgresql.html) (n.d., Debezium 3.7 stable; authority 5).
- Event envelope: `before` is "An optional field that specifies the state of the row before the event occurred", `after` is the new state, `source` is a "Mandatory field that describes the source metadata for the event", and `op` is a "Mandatory string that describes the type of operation" with values `c` create, `u` update, `d` delete, `r` read (snapshot), `t` truncate, `m` message — same source. `[streaming]` **MANDATORY** envelope for CDC consumers.
- Primary key / REPLICA IDENTITY: with `DEFAULT`, "For an `UPDATE` event, only the primary key columns with changed values are present"; without a primary key "the connector emits only _create_ events"; with `FULL`, "Emitted events for `UPDATE` and `DELETE` operations contain the previous values of all columns in the table"; with `NOTHING`, updates/deletes "do not contain any information about the previous value of any table column" — same source. `[OLTP]` **MANDATORY**: a captured table must have a primary key; **OPTIONAL/CONTEXTUAL**: set REPLICA IDENTITY FULL when consumers need full before-images.
- Deletes and tombstones: the connector "follows a _delete_ event with a special _tombstone_ event that has the same key but a `null` value"; the rationale is log compaction, which "enables removal of some older messages as long as at least the most recent message for every key is kept"; `tombstones.on.delete` default `true` ("Controls whether a _delete_ event is followed by a tombstone event") — same source. `[streaming]` **RECOMMENDED** (keep tombstones on for compacted topics).
- Delivery guarantees: "When the system is operating normally or being managed carefully then Debezium provides _exactly once_ delivery of every change event record"; on faults "Debezium, like Kafka, provides _at least once_ delivery of change events"; "The new replacement tasks might generate some of the same change events that were processed just prior to the crash"; "Consumers should always anticipate some duplicate events." — same source. `[streaming → sinks]` **MANDATORY**: sinks must be idempotent.
- Schema-change handling: "Logical decoding does not support DDL changes"; `schema.refresh.mode` default `columns_diff` "is the safest mode. It ensures that the in-memory schema stays in sync with the database table's schema at all times"; the in-memory schema can become outdated "if TOASTable columns are dropped from the table"; "Never drop a replication slot on the primary server or you will lose data."; the connector "does not support schema changes while an incremental snapshot is running" — same source. `[OLTP]` **MANDATORY** operational constraints on schema migrations of CDC-captured tables.
- Ordering caveat: for truncate events "Ordering is guaranteed only for topics that use a single partition." `skipped.operations` default `t` (truncates skipped) — same source.
- Transactional outbox: "The outbox pattern is a way to safely and reliably exchange data between multiple (micro) services." Default outbox columns: `id` (unique event ID, usable to "remove duplicate messages"), `aggregatetype` (routing; default topic is "`outbox.event.` followed by the `aggregatetype` column value"), `aggregateid` (event key: "When this column contains a value, the SMT uses that value as the key in the emitted outbox message" and "This is important for maintaining correct order in Kafka partitions"), `type`, `payload` ("A representation of the outbox change event", JSON by default). "The SMT automatically filters out `DELETE` operations on an outbox table"; "updates to records in an outbox table are not allowed" (default `table.op.invalid.behavior=warn`); `route.tombstone.on.empty.payload` default `false` — [Debezium Outbox Event Router](https://debezium.io/documentation/reference/stable/transformations/outbox-event-router.html) (n.d., Debezium 3.7; authority 5). `[OLTP → streaming]` **MANDATORY** outbox table shape when using the SMT; outbox rows are insert-only and may be deleted immediately (deletes are filtered).

### Inferences
- Because the outbox write and the business write share one database transaction, the outbox table is the schema-level solution to the dual-write problem that the Features page contrasts with log-based CDC ("polling or dual writes"). The Debezium page itself does not use the phrase "dual write"; this is my linkage.
- Debezium removes the need for `updated_at` for *CDC* sources, but non-CDC (query-based) incremental loads still need one; a schema framework should treat `updated_at`/version columns as **MANDATORY unless CDC is in place**.
- Since Debezium does not emit DDL via logical decoding and relies on `columns_diff` refresh, additive column changes are the only ones that propagate transparently; drops/renames should be coordinated with consumer schema updates (ties to KQ1b compatibility).

### Gaps
- `column.include.list` text and the `provide.transaction.metadata` ordering semantics were not captured. The outbox page did not state an explicit at-least-once/exactly-once guarantee; it only notes `id` can be used to deduplicate.

## KQ1e – Kafka Connect single message transforms and schema handling

### Takeaway
Confluent's SMT reference positions SMTs as per-record, in-flight modifications inside Connect (no separate stream processor) and documents that most transforms behave differently for schema-aware records (`Struct`) vs schemaless records (`Map`); several transforms exist purely to manipulate schema metadata (`SetSchemaMetadata`), structure (`Flatten`, `HoistField`, `ExtractField`, `Cast`) or keys (`ValueToKey`), which means schema decisions (nesting, key fields, schema names/versions) can be bent at the connector boundary.

### Cited Findings
- SMTs modify "individual records as they flow through Connect", eliminating "the need for a separate stream-processing application"; inbound records are transformed after a source connector produces them and before Kafka; outbound before a sink connector receives them — [Single Message Transforms for Confluent Platform](https://docs.confluent.io/kafka-connectors/transforms/current/overview.html) (Last updated Oct 22, 2026; authority 5). `[streaming]`
- Schema-aware vs schemaless: `ExtractField` works on a "Struct when schema present, or a Map for schemaless data"; `HoistField` has the same dual behaviour — same source.
- Schema- and key-shaping transforms (paraphrased): `Cast` (change field/key/value type), `Flatten` (flatten nested structures with a delimiter), `HoistField` (wrap data in a named field), `InsertField` (add fields from record metadata or static value), `MaskField` (replace with null-equivalent), `ReplaceField` (filter or rename fields; Confluent version handles nested fields), `SetSchemaMetadata` (set schema name/version), `TimestampConverter` (convert timestamp formats), `ValueToKey` (build new key from value fields), `RegexRouter`/`TimestampRouter`/`MessageTimestampRouter` (topic routing), `TombstoneHandler`, `EventRouter` (Debezium outbox), `Filter` ("Designed to be used in conjunction with a Predicate") — same source. **OPTIONAL/CONTEXTUAL**.

### Inferences
- `Flatten` and `Cast` at the sink edge mean nested event schemas can still land in flat relational tables, but the flattening delimiter and type coercions become part of the implicit contract; a schema framework should document the canonical flattening (e.g., `address_city`) rather than letting each connector pick one.
- `ValueToKey` existing as a transform confirms that producers frequently omit a proper key; the framework should instead mandate the key at production time (KQ1a) so ordering/compaction are correct *before* Connect.

### Gaps
- The page gives no guidance on when to prefer SMTs vs stream processing and does not describe SMTs as stateless; the Apache Kafka Connect page itself was not fetched.

## KQ2a – Apache Spark: schema inference pitfalls, explicit schemas, Structured Streaming semantics

### Takeaway
Spark's batch JSON reader infers schemas by default (with knobs such as `samplingRatio`, `primitivesAsString`, `prefersDecimal`, and `inferTimestamp=false`, so timestamps become strings unless you ask), and malformed records are silently nulled under the default `PERMISSIVE` mode. Structured Streaming, by contrast, **requires an explicit schema for file sources** "to ensure a consistent schema will be used for the streaming query, even in the case of failures." Watermarks guarantee only that data *less* late than the threshold is kept; later data "may or may not" be processed. Exactly-once holds for the file sink; Kafka/foreach sinks are at-least-once and `foreachBatch` needs `batchId`-based deduplication.

### Cited Findings
- Inference defaults (Spark 4.3.0 docs): "Spark SQL can automatically infer the schema of a JSON dataset and load it as a DataFrame"; `samplingRatio` (default 1.0) "Defines fraction of input JSON objects used for schema inferring"; `primitivesAsString` (default false) "Infers all primitive values as a string type"; `prefersDecimal` (default false) "Infers all floating-point values as a decimal type. If the values do not fit in decimal, then it infers them as doubles"; `inferTimestamp` (default false) "Allows inferring of `TimestampType` and `TimestampNTZType` from strings that match the timestamp patterns…"; `dropFieldIfAllNull` (default false) — [Spark SQL JSON Files](https://spark.apache.org/docs/latest/sql-data-sources-json.html) (Spark 4.3.0; authority 5). `[OLAP/lakehouse]`
- Malformed data: `PERMISSIVE` (default) "puts the malformed string into a field configured by `columnNameOfCorruptRecord`, and sets malformed fields to `null`… When inferring a schema, it implicitly adds a `columnNameOfCorruptRecord` field"; `DROPMALFORMED` "ignores the whole corrupted records"; `FAILFAST` "throws an exception when it meets corrupted records" — same source. **RECOMMENDED**: capture `_corrupt_record` via a user-defined schema (the page: "a user can set a string type field named `columnNameOfCorruptRecord` in a user-defined schema").
- Streaming requires explicit schema: "By default, Structured Streaming from file based sources requires you to specify the schema, rather than rely on Spark to infer it automatically. This restriction ensures a consistent schema will be used for the streaming query, even in the case of failures. For ad-hoc use cases, you can reenable schema inference by setting `spark.sql.streaming.schemaInference` to `true`." — [Structured Streaming Programming Guide – APIs on DataFrames and Datasets](https://spark.apache.org/docs/latest/streaming/apis-on-dataframes-and-datasets.html) (n.d.; same `/docs/latest/` tree as the 4.3.0 JSON page; authority 5). `[streaming]` **MANDATORY** (default behaviour); inference is **OPTIONAL** for ad-hoc only.
- Output modes: Append (default) outputs only new Result Table rows and "is supported for only those queries where rows added to the Result Table is never going to change. Hence, this mode guarantees that each row will be output only once (assuming fault-tolerant sink)"; Complete outputs the whole Result Table after every trigger, "supported for aggregation queries"; Update outputs only rows updated since last trigger. Aggregations without watermark: "Append mode is not supported as aggregates can update thus violating the semantics of this mode"; non-aggregate queries: "Complete mode not supported as it is infeasible to keep all unaggregated data in the Result Table" — same source.
- Watermark semantics: "late data within the threshold will be aggregated, but data later than the threshold will start getting dropped"; "A watermark delay … of '2 hours' guarantees that the engine will never drop any data that is less than 2 hours delayed"; "the guarantee is strict only in one direction. Data delayed by more than 2 hours is not guaranteed to be dropped; it may or may not get aggregated." Conditions to clean state: "Output mode must be Append or Update"; aggregation must have the event-time column or a `window` on it; `withWatermark` must be on the same column as the aggregate's timestamp and "must be called before the aggregation" — same source. `[streaming]` **MANDATORY** preconditions.
- Stream-stream joins: inner joins grow state indefinitely unless additional time constraints are defined; "for outer joins they must be specified. This is because for generating the NULL results in outer join, the engine must know when an input row is not going to match"; semi joins likewise; "if any of the two input streams being joined does not receive data for a while, the outer … output may get delayed" — same source. **MANDATORY** for outer/semi joins.
- Fault tolerance: "Some sources are not fault-tolerant because they do not guarantee that data can be replayed using checkpointed offsets after a failure"; sink guarantees: File sink "Yes (exactly-once)", Kafka sink "Yes (at-least-once)", Foreach "Yes (at-least-once)", ForeachBatch "Depends on the implementation", Memory "No"; "By default, `foreachBatch` provides only at-least-once write guarantees. However, you can use the batchId provided to the function as way to deduplicate the output and get an exactly-once guarantee"; file source: "the files must be atomically placed in the given directory, which in most file systems, can be achieved by file move operations" — same source. `[streaming → OLAP/OLTP sinks]` **MANDATORY** for exactly-once into databases: idempotent writes keyed by `batchId` or natural keys.

### Inferences
- Inference pitfalls documented by Spark (timestamps-as-strings by default, floating→double unless `prefersDecimal`, sampled schemas with `samplingRatio<1`, implicit `_corrupt_record`) translate into a framework rule: landing/bronze tables should be created from a declared schema (DDL or schema file), never from `inferSchema` output, and monetary values should be declared `DECIMAL` explicitly.
- Watermark one-directionality means a target aggregate table can receive *post-watermark* late updates in Update mode; the schema for streaming aggregates should keep a `last_updated_processing_time` column so downstream reconciliation can detect late corrections (inference from the "may or may not get aggregated" statement).

### Gaps
- The Spark JSON page does not itself recommend explicit schemas for batch reads; the only explicit requirement is for streaming file sources. Spark's partitioning guidance (partition discovery, `partitionBy`) was not fetched; see Iceberg hidden partitioning for the table-format perspective.
- The "Recovering from Failures with Checkpointing" section was beyond the fetched range.

## KQ2b – Open table formats: schema evolution, hidden partitioning, ACID, time travel (Iceberg vs Delta Lake vs Hudi)

### Takeaway
All three formats make additive, nullable, end-of-struct column additions and numeric *widening* safe. They diverge sharply on rename/drop/reorder: **Iceberg** tracks columns by immutable field IDs so add/drop/rename/widen/reorder are all metadata-only and "free of side-effects"; **Delta Lake** enforces schema on write (extra columns, type mismatches and case-only name clashes are rejected) and allows rename/drop without rewrite only when column mapping is enabled, otherwise `overwriteSchema` rewrites; **Hudi** supports only backward-compatible changes out of the box, rejects non-nullable adds, demotions and reorder-with-add, and puts rename/drop behind an experimental, irreversible schema-on-read switch. Iceberg uniquely makes partitioning *hidden* so queries don't depend on physical layout.

### Cited Findings — Apache Iceberg
- Spec: "Schemas may be evolved by type promotion or adding, deleting, renaming, or reordering fields in structs"; "Columns in Iceberg data files are selected by field id"; "Renaming an existing field must change the name, but not the field ID"; promotions include int→long, float→double, widening decimal precision, and for v3+ date→timestamp and timestamp_ns — [Iceberg Table Spec](https://iceberg.apache.org/spec/) (n.d.; authority 5). `[lakehouse]` **MANDATORY** (field IDs are the mechanism; never reuse IDs).
- Spec partitioning: transforms identity, bucket[N], truncate[W], year, month, day, hour, void; "This simplifies queries because users don't have to supply both logical predicates and partition predicates"; "Changing a partition spec produces a new spec identified by a unique spec ID"; "When evolving a spec, changes should not cause partition field IDs to change" — same source.
- Spec ACID/isolation: "An atomic swap of one table metadata file for another provides the basis for serializable isolation"; "All changes to table state create a new metadata file and replace the old metadata with an atomic swap"; "Writers create table metadata files optimistically"; "Reads will be isolated from concurrent writes and always use a committed snapshot of a table's data" — same source. **MANDATORY** semantics of the format.
- Format versions: v1 manages "large analytic tables using immutable file formats"; v2 "adds row-level updates and deletes for analytic tables with immutable files"; v3 adds "Binary deletion vectors", row lineage tracking and new types (nanosecond timestamps, unknown, variant, geometry, geography); "Version 4 is under active development and has not been formally adopted" — same source.
- Docs (Evolution): supported operations Add ("add a new column to the table or to a nested struct"), Drop, Rename, Update ("widen the type of a column, struct field, map key, map value, or list element"), Reorder; "Iceberg schema updates are **metadata changes**, so no data files need to be rewritten to perform the update"; "Note that map keys do not support adding or dropping struct fields that would change equality." Correctness guarantees: schema evolution changes are "independent and free of side-effects": "Added columns never read existing values from another column"; "Dropping a column or field does not change the values in any other column"; "Updating a column or field does not change values in any other column"; "Changing the order of columns or fields in a struct does not change the values associated with a column or field name"; "When you add a column, it is assigned a new ID so existing data is never used by mistake"; "Formats that track columns by name can inadvertently un-delete a column if a name is reused, which violates #1"; formats that track by position cannot delete columns without changing names (violates #2) — [Iceberg Docs – Evolution](https://iceberg.apache.org/docs/latest/evolution/) (n.d.; docs "Latest 1.12.0"; authority 5). `[lakehouse]` **MANDATORY** framework rule derived: never reuse a dropped column's *name* in name-tracked formats; Iceberg makes this safe by ID.
- Docs (Partition evolution): "Iceberg table partitioning can be updated in an existing table because queries do not reference partition values directly"; "the old data written with an earlier spec remains unchanged"; "each partition layout plans files separately using the filter it derives for that specific partition layout"; "Partition evolution is a metadata operation and does not eagerly rewrite files"; sort order can be evolved likewise and "Engines can always choose to write data in the latest sort order or unsorted when sorting is prohibitively expensive" — same source. **OPTIONAL/CONTEXTUAL**.
- Docs (Partitioning): "Partitioning is a way to make queries faster by grouping similar rows together when writing." Iceberg "handles the tedious and error-prone task of producing partition values for rows in a table", "avoids reading unnecessary partitions automatically", and "partition layouts can evolve as needed". Hive problems: "Hive can't validate partition values -- it is up to the writer to produce the correct value"; "Using the wrong format, `2018-12-01` instead of `20181201`, produces silently incorrect results, not query failures"; "It is up to the user to write queries correctly"; "Users that don't understand a table's physical layout get needlessly slow queries"; "Working queries are tied to the table's partitioning scheme". Hidden partitioning: "Iceberg produces partition values by taking a column value and optionally transforming it"; "Because Iceberg doesn't require user-maintained partition columns, it can hide partitioning"; "Most importantly, queries no longer depend on a table's physical layout." — [Iceberg Docs – Partitioning](https://iceberg.apache.org/docs/latest/partitioning/) (n.d.; authority 5). `[lakehouse]` **RECOMMENDED**: derive partitions from a real event-time column via transforms instead of adding synthetic `dt`/`event_date` columns.

### Cited Findings — Delta Lake
- Schema validation (schema-on-write): "If there are columns in the DataFrame not present in the table, an exception is raised"; "DataFrame column data types must match the column data types in the target table"; "DataFrame column names cannot differ only by case"; "Columns present in the table but not in the DataFrame are set to null" — [Delta Lake – Table batch reads and writes](https://docs.delta.io/latest/delta-batch.html) (n.d.; newest features labelled Delta Lake 4.3.0; authority 5). `[lakehouse]` **MANDATORY** (default enforcement).
- Automatic evolution: "Columns present in the source data but missing from the table are automatically added" when using `WITH SCHEMA EVOLUTION` / `.withSchemaEvolution()` (4.3+), the `mergeSchema` option, or `spark.databricks.delta.schema.autoMerge.enabled`; "Adding nested columns is supported only for structs. Arrays and maps are not supported."; "`NullType` columns are dropped from the DataFrame when writing into Delta tables, but are still stored in the schema" and when a different type later arrives for that column "Delta Lake merges the schema to the new data type" — same source. **OPTIONAL/CONTEXTUAL** (opt-in).
- Explicit DDL: adding, reordering, replacing and renaming columns via ALTER TABLE; dropping and renaming without rewriting data require that "you must enable column mapping for the table"; renaming available from 1.2.0 and dropping from 2.0, both marked experimental; dropping metadata "does not delete the underlying data for the column in files"; otherwise "You can change a column's type or name or drop a column by rewriting the table" (`overwriteSchema`) — same source. **OPTIONAL/CONTEXTUAL**.
- Time travel/retention: `SELECT * FROM table_name VERSION AS OF version` / `TIMESTAMP AS OF`; DataFrame options `versionAsOf`/`timestampAsOf`; "To time travel to a previous version, you must retain _both_ the log and the data files for that version"; "By default you can time travel to a Delta table up to 30 days old unless you have" run VACUUM or changed retention; `delta.logRetentionDuration` default `interval 30 days`; `delta.deletedFileRetentionDuration` default `interval 7 days`; "`VACUUM` _does not_ delete Delta log files; log files are automatically cleaned up after checkpoints are written" — same source. **RECOMMENDED** to align retention with reprocessing/audit needs.

### Cited Findings — Apache Hudi
- "Hudi supports backwards-compatible schema evolution scenarios out of the box" (schema evolution on write; recommended where possible); "Hudi has experimental support for allowing backward incompatible schema evolution scenarios on write while resolving it during read time" via `hoodie.schema.on.read.enable=true`; "If schema on read is enabled, it cannot be disabled again." — [Apache Hudi – Schema Evolution](https://hudi.apache.org/docs/schema_evolution) (Version 1.2.1; n.d.; authority 5). `[lakehouse]` **RECOMMENDED** (stay in write-mode evolution); schema-on-read **OPTIONAL/CONTEXTUAL** and irreversible.
- Write-mode allowed/disallowed (COW/MOR): add nullable column at root level at end — Yes; add nullable column to inner struct at end — Yes; add complex type field with default (map, array) — Yes; add nullable column *and reorder fields* — No; promote type (root, nested, complex value) — Yes; add *non-nullable* column at root or in inner struct — No; demote type — No; missing incoming columns require `hoodie.write.set.null.for.missing.columns` "otherwise the pipeline will fail"; adding a non-nullable root column on MOR with Spark datasource writes but reads fail (workaround: make it nullable) — same source. **MANDATORY** constraints.
- Promotion matrix (reconstructed from page text; verify on live page): int→long/float/double/string; long→float/double/string; float→double/string; double→string; string→bytes; bytes→string; int/long/float/double→bytes not allowed — same source.
- Schema-on-read DDL: `ALTER TABLE … ADD COLUMNS` (with `FIRST`/`AFTER`), `ALTER COLUMN … TYPE`, `DROP COLUMN(S)`, `RENAME COLUMN`; requires Hudi > 0.11 and Spark > 3.1.x; Hive metastore needs `hive.metastore.disallow.incompatible.col.type.changes=false` for type changes — same source.

### Conflicts between formats (explicit)
- **Rename/drop**: Iceberg = safe by default (field IDs) vs Delta = only with column mapping (else rewrite) vs Hudi = only with experimental, irreversible schema-on-read. Sources: [Iceberg Evolution](https://iceberg.apache.org/docs/latest/evolution/), [Delta batch](https://docs.delta.io/latest/delta-batch.html), [Hudi schema evolution](https://hudi.apache.org/docs/schema_evolution).
- **Reorder**: Iceberg allows reorder as a side-effect-free operation; Hudi disallows "add nullable column and reorder fields" in write mode.
- **Type widening scope**: Iceberg spec lists int→long, float→double, decimal precision widening (+ date→timestamp in v3); Hudi additionally allows promotion of numerics to `string` and string↔bytes; Delta's type widening is a separate feature page (not fetched). A portable framework should only rely on the *intersection* (int→long, float→double, decimal precision widen).
- **Unknown columns on write**: Delta rejects extra DataFrame columns by default; Hudi fails on *missing* columns unless `set.null.for.missing.columns`; Iceberg docs fetched do not state write-time rejection rules.
- **Partition columns**: Iceberg hides them (derived via transforms); Delta/Hudi (and Hive) expose partition columns explicitly (Iceberg page's critique of Hive). This conflicts with the common warehouse habit of adding `dt` columns.

### Inferences
- The portable "safe schema change" set across all three formats is: add nullable column at end of a struct/table, widen int→long and float→double, widen decimal precision. Everything else is format-specific and must be governed by the framework.
- Iceberg's "never reuse an ID" rule generalises to a framework rule for *all* storage: never reuse a dropped column name for a different meaning, because Hive/Delta-without-column-mapping track by name.

### Gaps
- Iceberg spec sections on snapshots/time travel beyond isolation statements were not reached; Delta's dedicated type-widening and column-mapping pages were not fetched; Hudi's ACID/time-travel pages were not fetched.

## KQ3 – Orchestration: Airflow best practices vs asset-based orchestration (Dagster)

### Takeaway
Airflow's official Best Practices page frames tasks as database transactions: re-runs must produce the same outcome (use UPSERT, never plain INSERT), tasks must read the partition for their data interval ("Never read the latest available data in a task"), `datetime.now()` must not drive logic, DAG files must not run DB/network code at top level, XCom is for small messages only, and deleting tasks loses history. Dagster reframes the unit of orchestration as a persisted **asset** (table/file/model) with declared dependencies and attachable **asset checks** (schema, nulls, freshness) that can block downstream materialisation.

### Cited Findings — Apache Airflow
- Idempotency/atomicity: "You should treat tasks in Airflow equivalent to transactions in a database"; "Airflow can retry a task if it fails. Thus, the tasks should produce the same outcome on every re-run"; avoid plain INSERTs on re-run because they duplicate rows — "Replace it with UPSERT" — [Airflow Best Practices](https://airflow.apache.org/docs/apache-airflow/stable/best-practices.html) (Airflow 3.4.0; n.d.; authority 5). `[all]` **MANDATORY**.
- Data intervals: "Never read the latest available data in a task"; read a specific partition, using `data_interval_start` as the partition — same source. **MANDATORY** → target tables need an interval/partition column.
- Wall-clock: `datetime.now()` "should never be used inside a task, especially to do the critical computation, as it leads to different outcomes on each run"; "It's fine to use it, for example, to generate a temporary log" — same source. **MANDATORY**.
- Top-level code: "Specifically you should not run any database access, heavy computations and networking operations"; "Expensive imports should be avoided as top level imports, because Dag files are parsed frequently" — same source. **MANDATORY**.
- Data passing: "If possible, use `XCom` to communicate small messages between tasks"; "a good way of passing larger data between tasks is to use a remote storage such as S3/HDFS"; "you should not store any file or config in the local filesystem"; credentials belong in Connections — same source. **RECOMMENDED**.
- Deleting tasks: "Be careful when deleting a task from a Dag" — history becomes hard to inspect ("You would not be able to see the Task in Graph View, Grid View, etc") — same source. **RECOMMENDED**.
- Testing/environments: "Unit tests ensure that there is no incorrect code in your Dag"; operators can be tested by calling `execute()` without a DAG run or metadata DB; "If possible, keep a staging environment to test the complete Dag run before deploying in the production"; "Do not hard code values inside the Dag and then change them manually according to the environment" — same source. **RECOMMENDED**.
- Upgrades: "It's always a wise idea to backup the metadata database before undertaking any operation modifying the database"; "Some database migrations can be time-consuming"; `db clean` "Use with caution" — same source. **RECOMMENDED**.
- Dependencies: Airflow's Python dependencies can conflict; use `PythonVirtualenvOperator`/`@task.virtualenv`, `ExternalPythonOperator`/`@task.external_python`, `DockerOperator`/`KubernetesPodOperator`; virtualenvs "cannot have conflicting system-level dependencies" — same source. **OPTIONAL/CONTEXTUAL**.
- DAG design: "There are no magic recipes for making your Dag "less complex""; fewer DAGs per file, linear structures where possible, avoid copy-pasted near-identical DAG files; watcher pattern "Its primary purpose is to fail a Dag Run when any other task fail"; "Be aware that trigger rules only rely on the direct upstream (parent) tasks" — same source.

### Cited Findings — Dagster
- "An **asset** is an object in persistent storage, such as a table, file, or persisted machine learning model." Asset definitions describe an asset that should exist and how to produce/update it, and "enable a declarative approach to data management" with code as the source of truth; "Materializing an asset is the act of running its function and saving the results to persistent storage"; asset definitions "know about their dependencies", whereas ops are not connected to dependencies until placed in a graph — [Dagster Docs – Assets](https://dagster.io/docs/guides/build/assets) (Latest 1.12.8; n.d.; authority 5 as official tool docs / 3 by the brief's scale for tool docs). `[all]` **RECOMMENDED** framing.
- Asset checks test properties of assets (examples: a column has no nulls, a tabular asset matches a specified schema, freshness); "Each asset check should test only a single asset property to keep tests uncomplicated, reusable, and easy to track over time"; by default a failed check does not stop the run, but `blocking=True` prevents downstream assets from materialising when the check fails; checks run with asset jobs by default and can be scheduled separately with alerting — [Dagster Docs – Asset checks](https://dagster.io/docs/guides/test/asset-checks) (n.d.). **RECOMMENDED**: encode schema conformance as a check on the asset.

### Conflict / contrast
- Airflow models dependencies between *tasks* and warns about task deletion losing history; Dagster models dependencies between *data assets* and attaches quality checks directly to the table. Both agree on idempotent, re-runnable units; they differ on whether the schema/table or the job is the first-class object. Sources: [Airflow Best Practices](https://airflow.apache.org/docs/apache-airflow/stable/best-practices.html) vs [Dagster Assets](https://dagster.io/docs/guides/build/assets).

### Inferences
- Airflow's "UPSERT not INSERT" and "read the partition for the interval" rules imply two schema requirements: (1) every pipeline-written table needs a declared natural/business key for the UPSERT merge condition; (2) a partition/interval column (`data_interval_start`-aligned) so backfills can overwrite exactly one interval.
- Dagster's asset-check model implies the schema definition should be machine-readable so a check can compare the materialised table against it (schema-as-code).

### Gaps
- Prefect's framing of assets/lineage was not researched (no fetch). The Airflow page does not literally use the words "idempotent" or "atomic"; the transaction analogy is its wording. Dagster's assets page does not discuss lineage in depth or freshness policies (sidebar links only).

## KQ4 – Architecture patterns: ETL vs ELT, batch vs streaming, lambda vs kappa, the Dataflow model, schema-on-read vs schema-on-write, data contracts

### Takeaway
Google Cloud (BigQuery) and dbt both *recommend ELT by default* (load raw, transform in the warehouse) while acknowledging ETL for regulated or pre-existing transformation processes; dbt is explicit that raw landing creates storage, complexity, performance and "security and compliance risks" — but neither mentions data contracts, which is exactly the gap the Open Data Contract Standard and Confluent's Data Contract pattern fill. On processing models, Kreps (2014) attacks lambda's dual codebases and proposes kappa (replay the retained log with a second job into a new table, then swap), and Akidau et al. (VLDB 2015) argue that batch/micro-batch/streaming should be an *engine* choice under one model ("Never rely on any notion of completeness"), with Google's own lambda experience showing users "stopped trusting the weakly consistent results".

### Cited Findings — ETL vs ELT
- Google: "With the extract-load-transform (ELT) approach, you perform data integration in two discrete steps" (load into BigQuery, then transform there); "In the extract-transform-load (ETL) approach, you extract and transform data before it reaches BigQuery"; "In general, we recommend the ELT approach to most customers." Reasons: splits integration into two manageable stages, removes other processing tools, uses BigQuery to transform at scale, SQL users can build pipelines with Dataform. ETL "is beneficial if you have an existing process in place for data transformation" or to reduce BigQuery resource usage (Cloud Data Fusion and partners named) — [BigQuery: Introduction to loading, transforming, and exporting data](https://docs.cloud.google.com/bigquery/docs/load-transform-export-intro) (n.d.; authority 5). `[OLAP/warehouse]` **RECOMMENDED** (ELT default); ETL **OPTIONAL/CONTEXTUAL**.
- dbt: "ELT, which stands for Extract, Load, Transform, is a data integration process that flips the traditional ETL sequence." Benefits: "We'd always have the raw source data available"; "The transformation step occurring within the warehouse, leverages the data warehouse's computational power"; "Analytics code can now follow the same best practices as software code" (version control, rollbacks, tests, CI/CD, docs). Drawbacks: "ELT requires storing raw, untransformed data in the data warehouse, which can lead to increased storage costs"; "managing transformations at scale can be complex"; "large and complex transformations can still lead to performance bottlenecks if not optimized properly"; "Storing raw, untransformed data in the warehouse may pose security and compliance risks"; "ETL is ideal for industries that require strict data governance" (finance, healthcare) where data must be cleaned/validated before entering the warehouse; hybrid model suggested; "Organizations must implement strict data governance policies" (GDPR, HIPAA) — [dbt Labs: Understanding ELT](https://www.getdbt.com/blog/extract-load-transform) (Daniel Poppy, 2023-09-06; authority 4 vendor blog). `[OLAP/warehouse]`
- **Conflict/controversy**: both pro-ELT sources concede the raw-landing risk (dbt: security/compliance; Google: resource usage) but neither mentions producer–consumer contracts; the Confluent Data Contract pattern ([Data Contract](https://developer.confluent.io/patterns/event/data-contract/)) and ODCS (below) are the sources that add contracts. This is the "ELT without contracts" controversy stated across sources rather than within one.

### Cited Findings — Lambda vs Kappa vs Dataflow
- Kreps: Lambda is "an approach to building stream processing applications on top of MapReduce" where records are "captured and fed into a batch system and a stream processing system in parallel" and you "implement your transformation logic twice"; "maintaining code that needs to produce the same result in two complex distributed systems" is painful and "I don't think this problem is fixable"; abstraction layers over both have leaked. Kappa proposal: retain the full input log in Kafka with retention covering the reprocessing window; when code changes "start a second instance of your stream processing job" from the beginning of the log, "direct this output data to a new output table", and when it catches up "switch the application to read from the new table", then stop the old job and delete its table; reprocessing happens only when code changes — [Questioning the Lambda Architecture](https://www.oreilly.com/radar/questioning-the-lambda-architecture/) (Jay Kreps, O'Reilly Radar, July 2, 2014; authority 4, widely cited practitioner/architect post). `[streaming]` **RECOMMENDED** pattern: output tables must be *versioned/swappable* (blue-green tables).
- Akidau Streaming 101: streaming defined as "a type of data processing engine that is designed with infinite data sets in mind", vs "unbounded data" = "A type of ever-growing, essentially infinite data set"; "I would argue that well-designed streaming systems actually provide a strict superset of batch functionality"; event time = "the time at which events actually occurred", processing time = "the time at which events are observed in the system", skew is "essentially the latency introduced by the processing pipeline"; Lambda's parallel pipelines are "a bit unsavory" and maintaining them "is a hassle", predicting "the relegation of the Lambda Architecture to the antiquity of big data history where it belongs"; processing-time windows break unless data "arrive in event time order"; event-time windowing is "the gold standard of windowing" — [The world beyond batch: Streaming 101](https://www.oreilly.com/radar/the-world-beyond-batch-streaming-101/) (Tyler Akidau, O'Reilly Radar, Aug 5, 2015; authority 4). `[streaming]`
- Dataflow Model paper: abstract: "We as a field must stop trying to groom unbounded datasets into finite pools of information that eventually become complete, and instead live and breathe under the assumption that we will never know if or when we have seen all of our data"; contributions: decomposes pipelines across "What results are being computed. Where in event time they are being computed. When in processing time they are materialized. How earlier results relate to later refinements." and "Separates the logical notion of data processing from the underlying physical implementation, allowing the choice of batch, micro-batch, or streaming engine to become one of simply correctness, latency, and cost." Design principles (§3.2): "Never rely on any notion of completeness."; "Be flexible, to accommodate the diversity of known use cases…"; "Not only make sense, but also add value, in the context of each of the envisioned execution engines."; "Encourage clarity of implementation."; "Support robust analysis of data in the context in which they occurred." Watermark = "a lower bound (often heuristically established) on event times that have been processed", with the footnote that "most watermarks must be heuristically defined based on limited knowledge available". Refinement modes: "Discarding: Upon triggering, window contents are discarded, and later results bear no relation to previous results"; "Accumulating: Upon triggering, window contents are left intact in persistent state, and later results become a refinement of previous results" (useful when the consumer overwrites old values); a third accumulating-and-retracting mode integrates retractions. Lambda experience (§3.3.1): a MillWheel customer "ran their streaming pipeline in weak consistency mode, with a nightly MapReduce to generate truth. They found that customers stopped trusting the weakly consistent results over time" and re-implemented around strong consistency — [The Dataflow Model (PVLDB vol. 8, pp. 1792–1803, 2015)](https://www.vldb.org/pvldb/vol8/p1792-Akidau.pdf) (Akidau, Bradshaw, Chambers, Chernyak, Fernández-Moctezuma, Lax, McVeety, Mills, Perry, Schmidt, Whittle; authority 5 peer-reviewed; metadata also at [Google Research](https://research.google/pubs/the-dataflow-model-a-practical-approach-to-balancing-correctness-latency-and-cost-in-massive-scale-unbounded-out-of-order-data-processing/)). `[streaming]` **MANDATORY** design stance for streaming schemas: carry event time; expect retractions/refinements.
- Book anchors (publisher pages returned HTTP 403; bibliographic facts from WebSearch result listings): *Streaming Systems: The What, Where, When, and How of Large-Scale Data Processing* (Akidau, Chernyak, Lax; O'Reilly, July 2018; expanded from Streaming 101/102) — [O'Reilly listing](https://www.oreilly.com/library/view/streaming-systems/9781491983867/) (url not opened). *Fundamentals of Data Engineering* (Reis & Housley; O'Reilly, June 2022; Chapter 1 "Data Engineering Described") — [O'Reilly listing](https://www.oreilly.com/library/view/fundamentals-of-data/9781098108298/) (url not opened). *Designing Data-Intensive Applications* — "an O'Reilly book by Martin Kleppmann", copyright "2014-2019 Martin Kleppmann", "available in print and ebook formats" — [dataintensive.net](https://dataintensive.net/) (opened; no TOC on page). No book-content quotes are asserted here because the publisher pages could not be read.

### Cited Findings — schema-on-read vs schema-on-write
- Schema-on-write enforcement is the default in Delta ("If there are columns in the DataFrame not present in the table, an exception is raised") and in Spark Structured Streaming file sources (schema must be specified) — [Delta batch](https://docs.delta.io/latest/delta-batch.html); [Structured Streaming guide](https://spark.apache.org/docs/latest/streaming/apis-on-dataframes-and-datasets.html).
- Schema-on-read appears as a named Confluent pattern ("Schema-on-Read" in the Event category) — [Confluent patterns](https://developer.confluent.io/patterns/) — and as Hudi's experimental `hoodie.schema.on.read.enable` mode that "cannot be disabled again" — [Hudi](https://hudi.apache.org/docs/schema_evolution).
- **Conflict**: ELT guidance (Google, dbt) favours landing raw data (schema-on-read-leaning), while table-format and streaming engines default to strict schema-on-write; dbt's own drawbacks list (compliance/security risk of raw data) is the bridge.

### Cited Findings — data contracts
- ODCS: the standard "describes the keys and values expected in a YAML data contract, per the Open Data Contract Standard"; maintained under the Bitol GitHub organisation; "Since v3.1.0, each section has its own page"; the Executive Summary lists 15 sections: Fundamentals, Schema, Context, References, Data Quality, Support & Communication Channels, Pricing, Team, Roles, Service-Level Agreement, Infrastructures & Servers, Custom & Other Properties, Authoritative Definitions, Tags, Variables; a contract "should be **platform agnostic**" — [Open Data Contract Standard (latest)](https://bitol-io.github.io/open-data-contract-standard/latest/) (n.d.; authority 4–5: open standard under a foundation-affiliated org; the page itself does not name LF AI & Data). `[all]` **RECOMMENDED**.
- Confluent's Data Contract pattern defines the contract as the schema plus a central registry only — [Data Contract](https://developer.confluent.io/patterns/event/data-contract/). **Conflict in scope**: ODCS's contract includes data quality, SLA, team/roles, support and pricing; Confluent's is schema-only.

### Inferences
- Kappa's "new output table then swap" requires the serving layer to support table versioning or view-swapping; a schema framework should reserve a naming/versioning convention for output tables and views (inference from Kreps).
- The Dataflow accumulation modes map directly onto sink-schema choices: discarding → append-only fact rows; accumulating → upsert by (key, window); accumulating & retracting → sinks must accept negative/retraction rows or versioned rows (inference from the paper's descriptions).
- The "trust" anecdote in the Dataflow paper is the strongest argument in the fetched sources against lambda-style eventual reconciliation: if a schema framework offers two tables (speed vs batch) for the same metric, consumers will defect to the batch one.

### Gaps
- Fivetran's ETL/ELT definitions were not fetched. Streaming 102 and the full Dataflow §2 windowing/trigger API were not quoted beyond the refinement modes. Book content (FoDE, Streaming Systems, DDIA) could not be read from publisher pages (403 / connection refused), so no book quotes are included; treat the book rows in the catalog as bibliographic anchors only.

## KQ5 – Pipeline-driven requirements a schema framework should impose (synthesis)

### Takeaway
Across Kafka, Debezium, Spark, the table formats and Airflow, the same handful of schema obligations recur: a stable identity key per row/event, an explicit event-time column, additive-nullable-with-default evolution only, representable deletes, an idempotency/deduplication key, an interval/partition column aligned with orchestration, and retention windows long enough for reprocessing. Each item below is labelled and tied to the source that motivates it.

### Cited Findings (requirements with source rationale)
1. **Stable identity key on every entity table and event — MANDATORY `[all]`.** Kafka orders only within a partition and routes by key ("hash to a partition"; "last known value for each message key") — [Kafka Design](https://kafka.apache.org/43/design/design/); Debezium emits only create events for tables without a primary key — [Debezium PostgreSQL](https://debezium.io/documentation/reference/stable/connectors/postgresql.html); the outbox `aggregateid` key "is important for maintaining correct order in Kafka partitions" — [Debezium Outbox](https://debezium.io/documentation/reference/stable/transformations/outbox-event-router.html); Airflow's "Replace it with UPSERT" needs a merge key — [Airflow Best Practices](https://airflow.apache.org/docs/apache-airflow/stable/best-practices.html).
2. **Reliable incremental watermark (CDC *or* `updated_at`/version column) — MANDATORY `[OLTP sources → OLAP]`.** Debezium states log-based CDC "Requires no changes to your data model, such as a "Last Updated" column" — [Debezium Features](https://debezium.io/documentation/reference/stable/features.html) — which is precisely the column non-CDC incremental loads depend on; so the framework must require either CDC enablement (primary key + REPLICA IDENTITY decision) or an `updated_at`/version column. (The "either/or" is my inference; no fetched source prescribes `updated_at` directly.)
3. **Explicit event-time column, distinct from processing/ingest time — MANDATORY `[streaming, lakehouse]`.** Kafka's `message.timestamp.type` default is `CreateTime` but may be `LogAppendTime` — [Kafka Topic Configs](https://kafka.apache.org/42/configuration/topic-configs/); Spark watermarks must be defined on the aggregated event-time column — [Structured Streaming](https://spark.apache.org/docs/latest/streaming/apis-on-dataframes-and-datasets.html); the Dataflow model separates event time from processing time and windows "where in event time" — [Dataflow Model](https://www.vldb.org/pvldb/vol8/p1792-Akidau.pdf); Iceberg derives hidden partitions from such a column via `day`/`hour` transforms — [Iceberg Partitioning](https://iceberg.apache.org/docs/latest/partitioning/).
4. **Additive, nullable, defaulted evolution as the only "free" change — MANDATORY `[all]`.** Avro new fields need defaults to be backward compatible — [Confluent compatibility](https://docs.confluent.io/platform/current/schema-registry/fundamentals/schema-evolution.html); Hudi permits only nullable adds at end and rejects non-nullable adds — [Hudi](https://hudi.apache.org/docs/schema_evolution); Delta auto-adds columns only with `mergeSchema` and sets missing columns to null — [Delta](https://docs.delta.io/latest/delta-batch.html); Iceberg: "Added columns never read existing values from another column" — [Iceberg Evolution](https://iceberg.apache.org/docs/latest/evolution/).
5. **Never reuse a dropped column's name/ID for a different meaning — MANDATORY `[lakehouse, OLAP]`.** "Formats that track columns by name can inadvertently un-delete a column if a name is reused" — [Iceberg Evolution](https://iceberg.apache.org/docs/latest/evolution/).
6. **Deletes must be representable — MANDATORY `[streaming, OLAP]`.** Kafka tombstone = key with null payload retained for `delete.retention.ms` — [Kafka Design](https://kafka.apache.org/43/design/design/); Debezium delete event + tombstone — [Debezium PostgreSQL](https://debezium.io/documentation/reference/stable/connectors/postgresql.html). For warehouse tables this implies a soft-delete flag or `op` column in CDC landing tables (inference).
7. **Idempotency / deduplication key at the sink — MANDATORY `[all sinks]`.** "Consumers should always anticipate some duplicate events" — [Debezium PostgreSQL](https://debezium.io/documentation/reference/stable/connectors/postgresql.html); Kafka's advice to store the offset with the output — [Kafka Design](https://kafka.apache.org/43/design/design/); Spark `foreachBatch` is at-least-once unless `batchId` is used to deduplicate — [Structured Streaming](https://spark.apache.org/docs/latest/streaming/apis-on-dataframes-and-datasets.html); outbox `id` usable to "remove duplicate messages" — [Debezium Outbox](https://debezium.io/documentation/reference/stable/transformations/outbox-event-router.html); Airflow "tasks should produce the same outcome on every re-run" — [Airflow](https://airflow.apache.org/docs/apache-airflow/stable/best-practices.html).
8. **Interval/partition column aligned to the orchestrator's data interval — MANDATORY `[OLAP, lakehouse]`.** "Never read the latest available data in a task"; partition by `data_interval_start` — [Airflow](https://airflow.apache.org/docs/apache-airflow/stable/best-practices.html); Iceberg's hidden partitioning removes the need for a *user-maintained* partition column but still requires the underlying timestamp — [Iceberg Partitioning](https://iceberg.apache.org/docs/latest/partitioning/). **Conflict**: Hive/Delta/Hudi-style explicit `dt` columns vs Iceberg's hidden transforms.
9. **Late-arriving data policy per table — RECOMMENDED `[streaming]`.** Spark's watermark guarantee is one-directional ("Data delayed by more than 2 hours is not guaranteed to be dropped") — [Structured Streaming](https://spark.apache.org/docs/latest/streaming/apis-on-dataframes-and-datasets.html); Dataflow's accumulation modes define how refinements relate — [Dataflow Model](https://www.vldb.org/pvldb/vol8/p1792-Akidau.pdf). Framework consequence (inference): aggregate tables need `(key, window_start)` upsert keys and a processing-time `updated_at` so late refinements are visible; late-arriving dimensions need a placeholder/unknown member strategy (no fetched source prescribes this; gap).
10. **Compatibility mode and upgrade order declared per subject/stream — MANDATORY `[streaming]`.** Default is BACKWARD (non-transitive); consumers first under BACKWARD, producers first under FORWARD — [Confluent compatibility](https://docs.confluent.io/platform/current/schema-registry/fundamentals/schema-evolution.html); breaking changes go to a new versioned stream — [Confluent Schema Evolution pattern](https://developer.confluent.io/patterns/event-stream/schema-evolution/).
11. **Retention ≥ reprocessing/audit window — RECOMMENDED `[streaming, lakehouse]`.** Kafka default `retention.ms` 7 days — [Kafka Topic Configs](https://kafka.apache.org/42/configuration/topic-configs/); kappa requires retention long enough to replay — [Kreps](https://www.oreilly.com/radar/questioning-the-lambda-architecture/); Delta default 30-day log retention and 7-day deleted-file retention bound time travel — [Delta](https://docs.delta.io/latest/delta-batch.html).
12. **Declared (not inferred) schemas for landing tables — RECOMMENDED `[OLAP, lakehouse]`; MANDATORY for streaming file sources.** Structured Streaming requires schemas by default; Spark JSON inference defaults (`inferTimestamp=false`, `prefersDecimal=false`, `PERMISSIVE`) yield strings/doubles/nulls silently — [Spark JSON](https://spark.apache.org/docs/latest/sql-data-sources-json.html); [Structured Streaming](https://spark.apache.org/docs/latest/streaming/apis-on-dataframes-and-datasets.html).
13. **Contract beyond schema (quality, SLA, ownership) — RECOMMENDED `[all]`.** ODCS sections include Data Quality, Service-Level Agreement, Team, Roles — [ODCS](https://bitol-io.github.io/open-data-contract-standard/latest/); Dagster asset checks can block downstream materialisation on schema/null/freshness failures — [Dagster Asset checks](https://dagster.io/docs/guides/test/asset-checks).
14. **Swappable/versioned output tables for reprocessing — OPTIONAL/CONTEXTUAL `[OLAP, streaming]`.** Kreps' kappa: write to "a new output table" and "switch the application to read from the new table" — [Kreps](https://www.oreilly.com/radar/questioning-the-lambda-architecture/).

### Inferences
- The strictest common denominator across streaming, lakehouse and warehouse guidance is: *key + event_time + processing_time + nullable-additive evolution + explicit delete representation + idempotency key*. A framework that mandates these six at table-creation time satisfies Kafka compaction, Debezium CDC, Spark exactly-once sinks, Iceberg/Delta/Hudi safe evolution and Airflow idempotent re-runs simultaneously.
- Reconciliation checkpoints are implied rather than prescribed: Debezium (duplicates), Spark (one-directional watermark) and Kreps (parallel old/new tables) all presuppose a way to compare counts/versions between stages, but no fetched official document specifies a reconciliation table schema.

### Gaps
- No official source fetched prescribes `updated_at`, soft-delete columns, late-arriving-dimension placeholders, or reconciliation checkpoint tables explicitly; these are inferences from the mechanisms documented above and should be labelled as framework decisions rather than vendor mandates.
- Prefect, Fivetran, Streaming 102 and the book bodies were not retrieved.
