## Key Question 1 — SQL Server (learn.microsoft.com): what the official docs prescribe

### Takeaway
Microsoft's design guidance is engine-structural: almost every table should have a narrow, unique, ever-increasing, immutable, non-nullable clustered index (a heap is "generally not recommended"), the PK is clustered by default but need not be; use `decimal` not `money` for arithmetic, `datetime2`/`datetimeoffset` not `datetime`; constraints are the integrity mechanism (FK indexes are not auto-created); and the engine ships declarative features for history (system-versioned temporal + ledger), row/column security (RLS, Always Encrypted, DDM, TDE) and HA (AGs — which "aren't backups"). The default isolation level is locking READ COMMITTED on SQL Server but RCSI (row versioning) on Azure SQL Database and Fabric SQL database.

### Cited Findings

**Table storage, clustered index and primary-key choice** — [SQL Server and Azure SQL index architecture and design guide](https://learn.microsoft.com/en-us/sql/relational-databases/sql-server-index-design-guide) (ms.date 2026-09-14; applies to SQL Server, Azure SQL Database, Azure SQL MI, Fabric SQL database)
- "The clustered index stores all rows and all columns of a table. Rows are sorted in the order of index key values. There can only be one clustered index per table." A heap is "an *unsorted* data structure on disk that contains all rows and all columns of a table."
- **RECOMMENDED (all workloads, strongest for OLTP)**: "With a few exceptions, every table should have a clustered index." Desirable properties, each with the vendor's reasoning: **Narrow** ("The clustered index key is a part of any nonclustered index on the same base table"); **Unique** (otherwise "a 4-byte internal uniqueifier column is automatically added"); **Ever-increasing** ("data is always added on the last page of the index. This avoids page splits"); **Immutable** ("When a key column of a clustered index is modified, a change must also be made in all nonclustered indexes"); **Has not nullable columns only** (nullable columns need a NULL block adding "3-4 bytes of storage per row").
- Worked example in the guide: "a clustered index key with a single **int** or **bigint** not nullable column has all of these properties if it's populated by an `IDENTITY` clause or a default constraint using a sequence and isn't updated after a row is inserted." Conversely "a clustered index key with a single **uniqueidentifier** column is wider because it uses 16 bytes of storage instead of 4 bytes for **int** and 8 bytes for **bigint**, and doesn't satisfy the **ever-increasing** property unless the values are generated sequentially."
- PK vs clustered key: "When you create a `PRIMARY KEY` constraint, a unique index supporting the constraint is created automatically. By default, this index is clustered; however, if this index doesn't satisfy the desired properties of the clustered index, you can create the constraint as nonclustered and create a different clustered index instead." And: "If you don't create a clustered index, the table is stored as a heap, which is generally not recommended."
- Workload split: OLTP → "a few narrow rowstore indexes targeted for the most critical queries would be a good initial index design"; OLAP/DW → "using clustered columnstore indexes would be especially appropriate."
- Nonclustered guidance (RECOMMENDED): "Create nonclustered indexes on the columns that are frequently used in predicates and join expressions ... avoid adding unnecessary column to indexes"; "Keep the length of the index key short, particularly for clustered indexes"; "Avoid over-indexing heavily updated tables and keep indexes narrow"; "It's often better to modify an existing index than to create a new but mostly duplicate index"; covering indexes: put SARGable columns in the key and "all other columns that cover the query included nonkey columns"; filtered indexes "on columns that have well-defined subsets, for example columns with many NULLs."
- Hard limits (MANDATORY): index key "16 key columns maximum, and a total index key size of 900 bytes"; "The maximum number of included columns is 1,023"; LOB/`json`/`vector` columns "can't be specified as index key columns" but can be included.
- Row locator mechanics: with a clustered index "the row locator is the clustered index key for the row"; on a heap it is a RID; nonunique nonclustered indexes get the clustered keys appended to their key.

**Keys and constraints** — [Primary and foreign key constraints](https://learn.microsoft.com/en-us/sql/relational-databases/tables/primary-and-foreign-key-constraints) (ms.date 2024-07-19)
- MANDATORY engine rules: "A table can contain only one primary key constraint"; "A primary key can't exceed 32 columns and a total key length of 900 bytes"; "If clustered or nonclustered isn't specified for a primary key constraint, clustered is used if there's no clustered index on the table"; PK columns are forced NOT NULL; limits of "999 nonclustered indexes and 1 clustered index."
- FK limits: "A table can reference a maximum of 253 other tables and columns as foreign keys (outgoing references)"; incoming references raised to 10,000 in SQL Server 2016+ but ">253 ... only supported for `DELETE` DML operations."
- FK indexing (RECOMMENDED, not required): "creating a foreign key constraint doesn't automatically create a corresponding index. However, manually creating an index on a foreign key is often useful ... creating this index isn't required."
- Cascading actions: `NO ACTION`, `CASCADE`, `SET NULL`, `SET DEFAULT`; "`CASCADE` can't be specified if a **timestamp** column is part of either the foreign key or the referenced key"; `ON DELETE CASCADE` can't be used with `INSTEAD OF DELETE` triggers.
- [Unique constraints and check constraints](https://learn.microsoft.com/en-us/sql/relational-databases/tables/unique-constraints-and-check-constraints) (ms.date 2023-12-29): UNIQUE "allow for the value `NULL` ... only one null value is allowed per column"; a UNIQUE constraint creates a unique **nonclustered** index by default; CHECK "reject values that evaluate to `FALSE`. Because null values evaluate to UNKNOWN, their presence in expressions might override a constraint"; "`CHECK` constraints aren't validated during `DELETE` statements"; **Caution**: "Avoid data type conversion in constraint definitions" (can break `ALTER TABLE...SWITCH` for partitioning).

**Schemas and identifiers** — [Database identifiers](https://learn.microsoft.com/en-us/sql/relational-databases/databases/database-identifiers) (ms.date 2026-04-08) and [Ownership and user-schema separation](https://learn.microsoft.com/en-us/sql/relational-databases/security/authentication-access/ownership-and-user-schema-separation) (ms.date 2024-05-09)
- MANDATORY: "Both regular and delimited identifiers must contain from 1 through 128 characters. For local temporary tables, the identifier can have a maximum of 116 characters." Regular identifiers start with a Unicode letter, `_`, `@` or `#`; subsequent chars letters, digits, `@`, `$`, `#`, `_`; "must not be a Transact-SQL reserved word"; "Don't use embedded spaces or special characters"; "Don't use Supplementary characters."
- RECOMMENDED: "`@` always denotes a local variable or parameter"; `#`/`##` denote temp objects — "you should avoid this practice" for other object types; "don't use names that start with `@@`."
- Identifier case-sensitivity follows database collation; constraint names "must be unique within a database schema."
- Schemas: "A *schema* is a named container for database objects, which allows you to group objects into separate namespaces"; "Once you set up access permissions for a schema, those permissions are automatically applied as new objects are added to the schema"; `dbo` is the default schema; one-part names are resolved first in the user's default schema then `dbo`. The nine `db_*`-named legacy schemas: "The recommendation is to not use them for user objects."
- Note: Microsoft publishes identifier *rules*, not a naming convention (no case/prefix/singular-plural guidance found).

**Data types** (all MANDATORY-or-RECOMMENDED statements come from the T-SQL reference; apply to all workloads)
- [money and smallmoney](https://learn.microsoft.com/en-us/sql/t-sql/data-types/money-and-smallmoney-transact-sql) (ms.date 2024-05-21): 8/4 bytes, "accurate to a ten-thousandth of the monetary units"; **Warning (RECOMMENDED against)**: "You can experience rounding errors through truncation, when storing monetary values as **money** and **smallmoney**. Avoid using this data type if your money or currency values are used in calculations. Instead, use the **decimal** data type with at least four decimal places." Currency symbols are accepted in literals but "SQL Server doesn't store any currency information associated with the symbol."
- [decimal and numeric](https://learn.microsoft.com/en-us/sql/t-sql/data-types/decimal-and-numeric-transact-sql) (ms.date 2026-10-13): "fixed precision and scale ... synonyms"; precision 1–38, "The default precision is 18", default scale 0; storage 5/9/13/17 bytes for precision 1–9/10–19/20–28/29–38; "each combination of precision and scale as a different data type."
- [datetime](https://learn.microsoft.com/en-us/sql/t-sql/data-types/datetime-transact-sql) (ms.date 2026-06-29): **RECOMMENDED against**: "Avoid using **datetime** for new work. Instead, use the **time**, **date**, **datetime2**, and **datetimeoffset** data types. These types align with the SQL Standard, and are more portable ... **datetimeoffset** provides time zone support for globally deployed applications." datetime range 1753–9999, "Rounded to increments of `.000`, `.003`, or `.007` seconds", "isn't ANSI or ISO 8601 compliant."
- [datetime2](https://learn.microsoft.com/en-us/sql/t-sql/data-types/datetime2-transact-sql) (ms.date 2024-10-25): range `0001-01-01` to `9999-12-31`, "0 to 7 digits, with an accuracy of 100 nanoseconds", storage "6 bytes for precision less than 3. 7 bytes for precision 3 or 4. All other precision requires 8 bytes"; "Use explicit casting to **datetime2** data type whenever a mixed comparison scenario between **datetime** and **datetime2** datatypes exists."
- [nchar and nvarchar](https://learn.microsoft.com/en-us/sql/t-sql/data-types/nchar-and-nvarchar-transact-sql) (ms.date 2024-06-06): "*n* defines the string length in **byte-pairs** (0-4,000). *n* never defines numbers of characters"; RECOMMENDED: "Use **nchar** when the sizes of the column data entries are consistent. Use **nvarchar** when the sizes ... vary considerably. Use **nvarchar(max)** when ... the string length might exceed 4,000 byte-pairs." Warning: each non-null `(n)varchar(max)` column "requires 24 bytes of additional fixed allocation, which counts against the 8,060-byte row limit during a sort operation."
- [uniqueidentifier](https://learn.microsoft.com/en-us/sql/t-sql/data-types/uniqueidentifier-transact-sql) (ms.date 2024-09-24): "Is a 16-byte GUID"; "ordering is not implemented by comparing the bit patterns"; "All column constraints and properties, except IDENTITY, can be used"; used by merge/transactional replication "to guarantee that rows are uniquely identified across multiple copies of the table"; not supported by PolyBase.
- [NEWSEQUENTIALID](https://learn.microsoft.com/en-us/sql/t-sql/functions/newsequentialid-transact-sql) (ms.date 2025-10-20): "Creates a GUID that is greater than any GUID previously generated by this function on a specified computer since Windows was started"; "using `NEWSEQUENTIALID` can be faster than using the `NEWID` function ... helps to completely fill the data and index pages"; "can only be used with `DEFAULT` constraints on table columns of type **uniqueidentifier**"; **Important**: "If privacy is a concern, don't use this function. It's possible to guess the value of the next generated GUID"; **Warning**: "clusters of sequential values can develop" when databases move to other computers or an AG/Azure SQL failover occurs; "unique across multiple computers only if the source computer has a network card."

**Partitioning** — [Partitioned tables and indexes](https://learn.microsoft.com/en-us/sql/relational-databases/partitions/partitioned-tables-and-indexes) (ms.date 2025-12-29)
- Components: partition function (`RANGE LEFT|RIGHT`; "`LEFT` ... is the default"; `RIGHT` "often simpler ... when partitioning a table based on a column of **datetime**") and partition scheme (maps partitions to filegroups). Example: `CREATE PARTITION FUNCTION [myDateRangePF1](DATETIME) AS RANGE RIGHT FOR VALUES ('2022-02-01', ...)`.
- MANDATORY rules: "When partitioning a clustered index, the clustering key must contain the partitioning column"; unique nonclustered indexes must contain the partitioning column; computed partitioning columns must be `PERSISTED`; LOB, CLR and `timestamp` columns can't be partitioning columns; "The database engine supports up to 15,000 partitions."
- RECOMMENDED: "Avoid designs with the number of partitions in many hundreds or thousands unless strictly necessary"; "a single filegroup for all partitions is recommended" unless tiered storage or piecemeal restore is needed; align indexes; "If you frequently run queries that involve an equijoin between two or more partitioned tables, their partitioning columns should be the same as the columns on which the tables are joined."
- Workload statement (CONTEXTUAL): "partitioning rarely improves performance in OLTP systems where such queries [single-row seeks without the partitioning column] are common." Benefits are manageability (switch/truncate partitions, loading OLTP→OLAP "takes only seconds") and partition-level lock escalation (`LOCK_ESCALATION = AUTO`).

**System-versioned temporal tables** — [Temporal tables](https://learn.microsoft.com/en-us/sql/relational-databases/tables/temporal-tables) (ms.date 2026-08-18; SQL Server 2016+) and [Temporal table considerations and limitations](https://learn.microsoft.com/en-us/sql/relational-databases/tables/temporal-table-considerations-and-limitations) (ms.date 2026-08-18)
- Mechanism: "Every temporal table has two explicitly defined columns, each with a **datetime2** data type ... period columns"; history table "with a mirrored schema"; times "are based on the begin time of the transaction itself" in UTC; `ValidTo` open rows = `9999-12-31`; "the Database Engine adds a row to the history table, even if no column values change."
- DDL given verbatim in the doc:
  ```sql
  CREATE TABLE dbo.Employee (
      [EmployeeID] INT NOT NULL PRIMARY KEY CLUSTERED,
      [Name] NVARCHAR (100) NOT NULL, ... [AnnualSalary] DECIMAL (10, 2) NOT NULL,
      [ValidFrom] DATETIME2 GENERATED ALWAYS AS ROW START,
      [ValidTo] DATETIME2 GENERATED ALWAYS AS ROW END,
      PERIOD FOR SYSTEM_TIME (ValidFrom, ValidTo))
  WITH (SYSTEM_VERSIONING = ON (HISTORY_TABLE = dbo.EmployeeHistory));
  ```
- Query: `FOR SYSTEM_TIME AS OF | FROM..TO | BETWEEN..AND | CONTAINED IN | ALL`; "`FOR SYSTEM_TIME` filters out rows that have a period of validity with zero duration."
- MANDATORY constraints: "A temporal table must have a primary key defined ... The history table can't have a primary key defined"; period columns "must be defined with a data type of **datetime2**"; "The history table can't have constraints"; "`TRUNCATE TABLE` isn't supported while `SYSTEM_VERSIONING` is `ON`"; "`INSTEAD OF` triggers aren't permitted on either the current or the history table"; no FileTable/FILESTREAM; history table must be in the same database; merge replication not supported.
- RECOMMENDED indexing: "An optimal indexing strategy includes a clustered columnstore index or a B-tree rowstore index on the current table, and a clustered columnstore index on the history table"; history is `PAGE` compressed by default; RLS predicates, indexes, partitioning, check constraints are NOT copied to the history table.
- Use cases (CONTEXTUAL): auditing/forensics, point-in-time reconstruction, "Maintaining a slowly changing dimension for decision support applications", recovering from accidental changes.

**Ledger tables** — [Ledger overview](https://learn.microsoft.com/en-us/sql/relational-databases/security/ledger/ledger-overview) (ms.date 2025-08-07; SQL Server 2022+, Azure SQL DB/MI)
- "The ledger feature provides tamper-evidence capabilities in your database. You can cryptographically attest to other parties ... that your data hasn't been tampered with"; "protect data from any attacker or high-privileged user, including database administrators."
- How: rows "are cryptographically SHA-256 hashed using a Merkle tree"; blocks chained → "forms a blockchain"; database digests "can be periodically generated and stored outside the database in tamper-proof storage" (immutable blob, Azure Confidential Ledger, WORM).
- Two forms: **Updatable ledger tables** ("a system-versioned table that contains a reference to another table with a mirrored schema ... history table") and **Append-only ledger tables** ("block updates and deletions at the API level"). A **ledger database** "can only contain ledger tables" and "cannot be converted to a regular database."
- Honesty statement: "Ledger can't prevent such attacks but guarantees that any tampering will be detected when the ledger data is verified." OPTIONAL/CONTEXTUAL (audit/finance/multi-party).

**Row-level security** — [Row-level security](https://learn.microsoft.com/en-us/sql/relational-databases/security/row-level-security) (ms.date 2025-09-11; SQL Server 2016+)
- "RLS supports two types of security predicates: Filter predicates silently filter the rows available to read operations (`SELECT`, `UPDATE`, and `DELETE`). Block predicates explicitly block write operations"; implemented via inline TVF + `CREATE SECURITY POLICY`; "functionally equivalent to appending a `WHERE` clause."
- Verbatim example: `CREATE FUNCTION Security.tvf_securitypredicate(@SalesRep AS nvarchar(50)) RETURNS TABLE WITH SCHEMABINDING AS RETURN SELECT 1 AS tvf_securitypredicate_result WHERE @SalesRep = USER_NAME() OR USER_NAME() = 'Manager';` then `CREATE SECURITY POLICY SalesFilter ADD FILTER PREDICATE Security.tvf_securitypredicate(SalesRep) ON Sales.Orders WITH (STATE = ON);` Multi-tenant middle-tier pattern uses `SESSION_CONTEXT(N'UserId')` with `@read_only = 1`.
- RECOMMENDED best practices: "create a separate schema for the RLS objects"; "Avoid type conversions in predicate functions"; "Avoid recursion"; "Avoid using excessive table joins"; predicates "shouldn't implicitly convert character strings to **date**..." (SET-option leakage).
- Scope note: "Security policies apply to all users, including dbo users"; side-channel caveat: "`SELECT 1/(SALARY-100000) FROM PAYROLL ...` would let a malicious user know that John Doe's salary is exactly $100,000." Interactions: "indexed views can't be created on top of tables that have a security policy"; temporal history tables need their own predicate; CDC can leak rows.

**Always Encrypted** — [Always Encrypted](https://learn.microsoft.com/en-us/sql/relational-databases/security/encryption/always-encrypted-database-engine) (ms.date 2026-01-28)
- Purpose: "provides a separation between those who own the data and can view it, and those who manage the data but should have no access"; keys "never exposed to the Database Engine"; column encryption keys protected by column master keys stored in Azure Key Vault / Windows cert store / HSM.
- **Deterministic** "always generates the same encrypted value ... you can perform point lookups, equality joins, grouping, and indexing", but "unauthorized users might guess information ... especially if there's a small set of possible encrypted values"; **Randomized** "encrypts data unpredictably" and (without enclaves) "doesn't support searching, grouping, indexing, or joining."
- Schema-impacting MANDATORY restrictions: string columns must use a `_BIN2` collation; unsupported on `xml`, `rowversion`, `sql_variant`, `hierarchyid`, spatial, `vector`, IDENTITY, ROWGUIDCOL, computed, sparse, partitioning columns, columns with default constraints, check constraints, DDM-masked columns; PK/unique/FK columns only with deterministic encryption; FOR XML/FOR JSON and table-valued parameters not supported; T-SQL can't do key provisioning; replication (logical) not supported but AGs are. DDL: `CREATE TABLE ... ENCRYPTED WITH`, `CREATE COLUMN MASTER KEY`, `CREATE COLUMN ENCRYPTION KEY`. OPTIONAL/CONTEXTUAL.

**Dynamic data masking** — [Dynamic data masking](https://learn.microsoft.com/en-us/sql/relational-databases/security/dynamic-data-masking) (ms.date 2025-06-30; SQL Server 2016+)
- Five functions: `default()`, `email()`, `random(start,end)`, `partial(prefix,[padding],suffix)`, `datetime("Y|M|D|h|m|s")` (2022+). DDL: `FirstName VARCHAR(100) MASKED WITH (FUNCTION = 'partial(1, "xxxxx", 1)') NULL`; `GRANT UNMASK` at database/schema/table/column level (2022+).
- Explicit limitation (the vendor's own caveat): "dynamic data masking shouldn't be used alone to fully secure sensitive data from users running ad hoc queries ... It's appropriate for preventing accidental sensitive data exposure, but doesn't protect against malicious intent to infer the underlying data"; "Creating a mask on a column doesn't prevent updates to that column"; "highly recommended to use it with" auditing, encryption, RLS. OPTIONAL/CONTEXTUAL.

**Transparent data encryption** — [Transparent data encryption (TDE)](https://learn.microsoft.com/en-us/sql/relational-databases/security/encryption/transparent-data-encryption) (ms.date 2025-09-07)
- "TDE does real-time I/O encryption and decryption of data and log files ... protects data at rest"; "doesn't increase the size of the encrypted database"; "TDE doesn't provide encryption across communication channels"; not available for `master`/`model`/`msdb`; "`tempdb` is automatically encrypted when a user database enabled TDE."
- Enable sequence (verbatim): `CREATE MASTER KEY ENCRYPTION BY PASSWORD=...; CREATE CERTIFICATE MyServerCert ...; CREATE DATABASE ENCRYPTION KEY WITH ALGORITHM = AES_256 ENCRYPTION BY SERVER CERTIFICATE MyServerCert; ALTER DATABASE ... SET ENCRYPTION ON;`
- MANDATORY operational rule: "Backup files for databases that have TDE enabled are also encrypted with the DEK ... Data loss results if the certificates are no longer available"; FILESTREAM data isn't encrypted; replication doesn't automatically replicate encrypted.

**Isolation levels** — [SET TRANSACTION ISOLATION LEVEL](https://learn.microsoft.com/en-us/sql/t-sql/statements/set-transaction-isolation-level-transact-sql) (ms.date 2025-09-26)
- `READ COMMITTED` "is the SQL Server default"; "If `READ_COMMITTED_SNAPSHOT` is set to `OFF` (the default on SQL Server), the Database Engine uses shared locks"; "If `READ_COMMITTED_SNAPSHOT` is set to `ON`, the Database Engine uses row versioning ... `READ_COMMITTED_SNAPSHOT ON` is the default on Azure SQL Database and SQL database in Microsoft Fabric."
- `SNAPSHOT` needs `ALLOW_SNAPSHOT_ISOLATION ON`; "`SNAPSHOT` transactions reading data don't block other transactions from writing data"; `REPEATABLE READ`/`SERIALIZABLE`: "use this option only when necessary"; shared locks "can be escalated to page or table locks"; Azure Synapse default is `READ UNCOMMITTED`.
- SQL Server 2025 adds [Optimized locking](https://learn.microsoft.com/en-us/sql/sql-server/what-s-new-in-sql-server-2025) ("Reduces blocking and lock memory consumption, and avoids lock escalation").

**Backup/restore and Always On** — [Backup overview (SQL Server)](https://learn.microsoft.com/en-us/sql/relational-databases/backup-restore/backup-overview-sql-server) (ms.date 2023-10-05) and [What is an Always On availability group?](https://learn.microsoft.com/en-us/sql/database-engine/availability-groups/windows/overview-of-always-on-availability-groups-sql-server) (ms.date 2026-01-26)
- Backup types: full ("all the data ... and also enough log"), differential ("only the data extents that have changed since the differential base"), log ("all log records that were not backed up in a previous log backup (full recovery model)"), file/partial/copy-only; "Table-level backups cannot be created"; three recovery models simple/full/bulk-logged; "the full recovery model requires creating backups of the transaction log." Backup compression supported in Standard since 2016; SQL Server 2025 adds ZSTD compression and backup to immutable blob storage.
- AG: "high-availability and disaster-recovery solution that provides an enterprise-level alternative to database mirroring"; "one set of primary databases and one to eight sets of corresponding secondary databases"; **MANDATORY**: "Secondary databases *aren't* backups. Continue to back up your databases and their transaction logs regularly"; synchronous-commit ("committed transactions are fully protected ... at the cost of increased transaction latency"; up to 5 sync replicas since 2019) vs asynchronous-commit ("making some data loss possible"); automatic/planned manual/forced failover; secondary joins via `RESTORE WITH NORECOVERY`; SQL Server 2025 allows full/differential backups on secondaries.

**What's new relevant to schema design (SQL Server 2025)** — [What's New in SQL Server 2025](https://learn.microsoft.com/en-us/sql/sql-server/what-s-new-in-sql-server-2025) (ms.date 2026-09-28): native `vector` data type, vector index (preview), native binary JSON data type and `JSON_OBJECTAGG`/`JSON_ARRAYAGG`, REGEXP functions, optimized locking, change event streaming, `||` concatenation, Web edition discontinued, Express limit 50 GB, Standard 256 GB buffer pool.

### Inferences
- Microsoft's whole index/PK doctrine follows from one structural fact: the clustered index IS the table and its key is embedded in every nonclustered index. Hence narrow/static/increasing surrogate keys (int/bigint IDENTITY or sequence) and the explicit caution about GUID keys.
- Declarative security features (RLS, DDM, Always Encrypted, TDE, ledger) each change schema constraints (BIN2 collations, no computed/default columns under AE, no indexed views on RLS tables), so they must be designed in, not bolted on.
- Microsoft deliberately documents the limits of DDM and ledger ("doesn't protect against malicious intent", "can't prevent such attacks"), which should be reflected as "defense in depth, not substitutes."

### Gaps
- No official SQL Server naming-convention page (casing, prefixes, singular/plural) was found; only identifier rules.
- The Index Design Guide's columnstore, memory-optimized and filtered-index sections were not read in full (file was 82 KB; key clustered/nonclustered sections were extracted).
- No explicit official statement on "always use `datetimeoffset` vs store UTC in `datetime2`" beyond "datetimeoffset provides time zone support for globally deployed applications."

## Key Question 2 — Oracle Database (docs.oracle.com): what the official docs prescribe

### Takeaway
Oracle's Concepts guide makes declarative integrity constraints the default ("use integrity constraints or assertions whenever possible"), treats the heap-organized table as the default with IOTs for specific cases, and reserves bitmap indexes for low-DML warehousing. The Data Warehousing Guide explicitly inverts two OLTP rules for DW: most indexes should be bitmap, and FKs should be `RELY`/non-enforced. Oracle does publish naming guidance (128-byte limit at COMPATIBLE ≥ 12.2; "Use full, descriptive, pronounceable names"; avoid quoted identifiers, `$`, `#`, `SYS_`/`ORA_` prefixes). Security is layered (VPD → superseded by RAS for new work; TDE; Data Redaction; unified auditing on by default, traditional auditing desupported in 26ai). History is served by Flashback Data Archive plus application-time Temporal Validity (`PERIOD FOR`), and all databases are multitenant CDBs since 21c.

### Cited Findings

**Data integrity** — [Data Integrity (Oracle Database Concepts)](https://docs.oracle.com/en/database/oracle/oracle-database/23/cncpt/data-integrity.html) (n.d.; URL path /23/ resolved to Oracle AI Database 26ai Concepts)
- "To enforce data integrity, use integrity constraints or assertions whenever possible." Advantages over application code: **Declarative ease** ("no additional programming is required"), **Centralized rules** ("data entered by all applications must adhere to the same integrity constraints"), **Flexibility when loading data** ("disable integrity constraints ... temporarily"). → RECOMMENDED (OLTP strongly; DW see RELY below).
- Constraint types: NOT NULL, unique key ("allows some values to be null"), primary key ("Each table can have one primary key"), foreign key, check. Examples: `CONSTRAINT emp_email_uk UNIQUE (email)`; `ALTER TABLE employees ADD CONSTRAINT max_emp_sal CHECK (salary < 10001);`
- Key types: natural ("a postal code in a lookup table") vs surrogate ("a system-generated incrementing identifier ... Typically, a sequence or UUID generates surrogate keys"). The Concepts page does NOT prescribe "short/immutable" PKs (that advice appears only in SQL Server's docs).
- Referential actions: no action (default), `DELETE CASCADE`, `DELETE SET NULL`; other actions "can be enforced using database triggers."
- Constraint states: `ENABLE VALIDATE`, `ENABLE NOVALIDATE`, `DISABLE VALIDATE` ("drops its index, and prevents modification of the constrained columns"), `DISABLE NOVALIDATE`; deferrable `INITIALLY IMMEDIATE`/`INITIALLY DEFERRED` ("checked when a `COMMIT` is issued"); `PRECHECK` state for check constraints with a JSON-schema equivalent.
- **FK indexing (RECOMMENDED, near-mandatory for OLTP)**: "As a rule, foreign keys should be indexed. The only exception is when the matching unique or primary key is never updated or deleted." Reason: "Prevents a full table lock on the child table. Instead, the database acquires a row lock on the index" and "Removes the need for a full table scan of the child table."

**Tables and indexes** — [Indexes and Index-Organized Tables](https://docs.oracle.com/en/database/oracle/oracle-database/26/cncpt/indexes-and-index-organized-tables.html) (n.d.; 26ai Concepts)
- "An **index** is an optional structure ... logically and physically independent of the data"; "The database must update the index when DML occurs on the indexed data, which creates performance overhead."
- When to index (RECOMMENDED): columns "queried frequently and return a small percentage of the total number of rows"; "A referential integrity constraint exists on the indexed column"; unique key constraint where you want to control the index.
- B-tree: "the standard index type ... excellent for highly selective indexes ... and primary key indexes."
- Bitmap (CONTEXTUAL, DW): "primarily designed for data warehousing or environments in which queries reference many columns in an ad hoc fashion"; candidates have "low cardinality" and are "read-only or not subject to significant modification by DML"; "Because a key points to many rows, DML on indexed data typically locks all of these rows. For this reason, bitmap indexes are not appropriate for many OLTP applications."
- Bitmap join index example: `CREATE BITMAP INDEX employees_bm_idx ON employees (jobs.job_title) FROM employees, jobs WHERE employees.job_id = jobs.job_id;` Function-based: `CREATE INDEX emp_fname_uppercase_idx ON employees ( UPPER(first_name) );` Invisible indexes "especially useful for testing the removal of an index before dropping it."
- Storage model: "a **heap-organized table** inserts rows where they fit" (default). IOT: "the index is the data, and the data is the index"; "a primary key constraint must be defined"; "useful when related pieces of data must be stored together or data must be physically stored in a specific order ... information retrieval, spatial data, and OLAP applications."

**Data types** — [Data Types (SQL Language Reference)](https://docs.oracle.com/en/database/oracle/oracle-database/23/sqlrf/Data-Types.html) (n.d.; resolved to 26ai)
- `NUMBER(p,s)`: "precision *p* can range from 1 to 38. The scale *s* can range from -84 to 127 ... requires from 1 to 22 bytes"; **RECOMMENDED**: "It is good practice to specify the scale and precision of a fixed-point number column for extra integrity checking on input ... If a value exceeds the precision, then Oracle returns an error. If a value exceeds the scale, then Oracle rounds it."
- Floating point: "Oracle recommends that you use the `BINARY_FLOAT` and `BINARY_DOUBLE` data types instead [of FLOAT], as they are more robust."
- `VARCHAR2`: max "4000 bytes or characters if `MAX_STRING_SIZE` = `STANDARD`", "32767 ... if `EXTENDED`"; stored "without any blank-padding"; `CHAR` blank-pads, max 2000. **MANDATORY-style warning**: "Do not use the `VARCHAR` data type. Use the `VARCHAR2` data type instead ... `VARCHAR` ... might be redefined in a future release."
- `DATE`: "year, month, day, hour, minute, and second ... fixed at 7 bytes ... does not have fractional seconds or a time zone." `TIMESTAMP(fsp)` precision 0–9, default 6. `TIMESTAMP WITH TIME ZONE` "includes a time zone region name or a time zone offset ... useful for preserving local time zone information" (13 bytes). `TIMESTAMP WITH LOCAL TIME ZONE` "normalized to the database time zone, and the time zone information is not stored."
- `BOOLEAN` ("`BOOLEAN` or `BOOL`"; supports UNKNOWN as null unless NOT NULL) — present in the 26ai reference; `JSON` native binary type: "Oracle recommends that you use JSON data type for the JSON columns"; max 32 MB; requires `compatible` ≥ 20 and ASSM tablespaces.
- `LONG`: "deprecated in Oracle8i Release 8.1.6 ... Do not create tables with `LONG` columns. Use LOB columns (`CLOB`, `NCLOB`, `BLOB`) instead." LOBs ≤ ~4000 bytes stored inline if enabled.

**Identifier rules and naming guidance** — [Database Object Names and Qualifiers (SQL Language Reference)](https://docs.oracle.com/en/database/oracle/oracle-database/23/sqlrf/Database-Object-Names-and-Qualifiers.html) (n.d.; resolved to 26ai)
- MANDATORY: with `COMPATIBLE` ≥ 12.2 "names must be from 1 to 128 bytes long" (exceptions: database names 8 bytes; tablespaces/rollback segments/disk groups 30 bytes; PDB names 64 bytes from 21c); below 12.2 "1 to 30 bytes". Nonquoted identifiers begin with a letter and contain alphanumerics, `_`, `$`, `#`; are "interpreted as uppercase"; "cannot be Oracle SQL reserved words"; `ROWID` cannot be a column name.
- RECOMMENDED: "Oracle does not recommend using quoted identifiers for database object names"; "Oracle strongly discourages you from using $ and # in nonquoted identifiers"; "Do not use words beginning with `SYS_` or `ORA_` as schema object names, and do not use the names of SQL built-in functions."
- **Published naming guidance** (answers the sub-question "Does Oracle publish schema naming guidance?" — yes, briefly): "Use full, descriptive, pronounceable names (or well-known abbreviations)"; "Use consistent naming rules"; "Use the same name to describe the same entity or attribute across tables" (e.g. `department_id` in both `employees` and `departments`).
- Namespaces: tables, views, sequences, packages, synonyms share one namespace per schema; indexes and constraints have their own.

**Partitioning** — [Partitioning Concepts (VLDB and Partitioning Guide)](https://docs.oracle.com/en/database/oracle/oracle-database/23/vldbg/partition-concepts.html) (n.d.; resolved to 26ai; guide edition G43505-02 January 2026)
- "From the perspective of the application, a partitioned table is identical to a nonpartitioned table"; benefits: performance (pruning, parallelism), manageability (rolling window), availability ("if one partition ... is unavailable, then all of the other partitions ... remain online").
- Strategies: range (`VALUES LESS THAN`, `MAXVALUE`), hash ("evenly distributes rows"), list (`DEFAULT` partition), composite (range-hash, range-list, list-range, ...), interval ("automatically create partitions"), reference (through an enabled PK/FK), virtual-column, partition-by-expression (`PARTITION BY HASH (base_total + tax_amount) PARTITIONS 8`).
- When to partition (RECOMMENDED): "Tables that are greater than 2 GB. These tables should always be considered as candidates for partitioning"; historical tables; tables spread across storage tiers. Limit: "up to a million separate partitions except those tables containing columns with `LONG` or `LONG RAW`."
- Index decision rules (in order): partitioning column subset of index keys → local; unique index without partitioning key → global; manageability priority → local; "For OLTP with quick response times, use global. For DSS focused on throughput, use local." "Bitmap indexes must be local." Pruning "can often improve query performance by several orders of magnitude."

**Data warehouse schema design** — [Data Warehousing Logical Design (Data Warehousing Guide)](https://docs.oracle.com/en/database/oracle/oracle-database/26/dwhsg/data-warehouse-logical-design.html) (n.d.; guide edition G43670-01 October 2025)
- 3NF: "seeks to minimize data redundancy and avoid anomalies ... 3NF databases use very many tables and this requires complex queries with many joins." Star: "The goal for star schemas is structural simplicity and high performance data retrieval ... accepts data redundancy (denormalization) in its dimension tables." Snowflake: "normalize dimensions to eliminate redundancy ... more complex queries and reduced query performance."
- Layering (RECOMMENDED for DW): "the modern approach to data warehousing does not pit star schemas and 3NF against each other. Rather, both techniques are used, with a foundation layer of 3NF ... and star schemas as a central part of an access and performance optimization layer."
- Keys: "A fact table has a composite key made up of the primary keys of the dimension tables"; **RECOMMENDED**: "Surrogate or artificial keys, usually sequential integers, are recommended for dimension tables ... compact integer keys may allow for better performance than large and complex alphanumeric keys."
- **Constraints in DW (RECOMMENDED, conflicts with OLTP rule)**: "Whenever possible, foreign keys and referential integrity constraints should be defined as non-enforced conditions, since it enables better query optimization and cardinality estimates."
- Star design concepts: "each fact table store just one grain level"; conformed dimensions "designed identically across the various star schemas"; "Type 2 is the most common treatment for slowly changing dimensions."

**DW indexing, star transformation, RELY constraints, DW partitioning** — [Data Warehousing Optimizations and Techniques](https://docs.oracle.com/en/database/oracle/oracle-database/26/dwhsg/data-warehouse-optimizations-techniques.html) (n.d.; 26ai)
- "Bitmap indexes are primarily intended for data warehousing applications where users query the data rather than update it. They are not suitable for OLTP applications with large numbers of concurrent transactions modifying the data."
- Cardinality rule of thumb: candidate when "There are 100 or more rows for each distinct value in the indexed column" and the column is in `WHERE` or "is a foreign key for a dimension table"; "a column with 10,000 distinct values [in a million-row table] is a candidate"; "B-tree indexes should be used only for unique columns or other columns with very high cardinalities ... The majority of indexes in a data warehouse should be bitmap indexes"; "usually best to use single-column bitmap indexes"; bitmap indexes "include rows that have `NULL` values"; "must be local to the partitioned table." (Internal inconsistency noted: the same page also contains the generic sentence "Indexes are more beneficial for high cardinality columns.")
- Bitmap join index example: `CREATE BITMAP INDEX sales_cust_gender_bjix ON sales(customers.cust_gender) FROM sales, customers WHERE sales.cust_id = customers.cust_id LOCAL NOLOGGING COMPUTE STATISTICS;` restrictions: dimension join columns must be PK/unique; "No table can appear twice in the join."
- Star transformation prerequisites (MANDATORY to get the optimization): "A bitmap index should be built on each of the foreign key columns of the fact table"; "`STAR_TRANSFORMATION_ENABLED` should be set to `TRUE` ... set to `FALSE` by default."
- Constraints: "data in a data warehouse is typically added or modified under controlled circumstances during the ... ETL process"; `RELY` ("belief") constraints: "the constraint must be in the `RELY` state ... Creating a `RELY` constraint is inexpensive and does not impose any overhead during DML or load"; examples `ALTER TABLE sales ADD CONSTRAINT sales_uk UNIQUE (...) DISABLE VALIDATE;` ("ensures uniqueness without the cost of a unique index" but no DML on those columns), `... FOREIGN KEY (time_id) REFERENCES times (time_id) RELY DISABLE NOVALIDATE;`
- DW partitioning (RECOMMENDED): "The larger tables should be partitioned using composite partitioning (range-hash or list-hash)"; "the number of hash partitions is a power of 2 ... Each hash partition should be at least 16MB"; "local indexes will be more common than global indexes."

**Materialized views** — [Basic Materialized Views](https://docs.oracle.com/en/database/oracle/oracle-database/26/dwhsg/basic-materialized-views.html) (n.d.; 26ai)
- "A materialized view eliminates the overhead associated with expensive joins and aggregations"; "The query optimizer automatically recognizes when an existing materialized view can and should be used ... transparently rewrites"; must `ENABLE QUERY REWRITE`; RECOMMENDED: "create materialized views that satisfy the largest number of queries ... 20 queries ... five or six well-written materialized views."
- Refresh: `ON COMMIT` / `ON DEMAND` / `ON STATEMENT`; `COMPLETE` / `FAST` / `FORCE` / `NEVER`; "Materialized view logs are required if you want to use fast refresh"; aggregate MVs "must specify `COUNT(*)`". Example DDL: `CREATE MATERIALIZED VIEW LOG ON sales WITH SEQUENCE, ROWID (...) INCLUDING NEW VALUES;` then `CREATE MATERIALIZED VIEW product_sales_mv BUILD IMMEDIATE REFRESH FAST ENABLE QUERY REWRITE AS SELECT ... COUNT(*) AS cnt ... GROUP BY p.prod_name;`

**Virtual Private Database** — [About Oracle Virtual Private Database (Security Guide)](https://docs.oracle.com/en/database/oracle/oracle-database/26/dbseg/oracle-virtual-private-database.html) (n.d.; 26ai; guide edition G43025-06 July 2026)
- "adds a dynamic `WHERE` clause to a SQL statement that is issued against the table, view, or synonym"; applies to `SELECT`, `INSERT`, `UPDATE`, `INDEX`, `DELETE`; policy evaluation types static / context-sensitive / dynamic; `DBMS_RLS` creates policies (needs `ADMINISTER ROW LEVEL SECURITY POLICY`); application context via `SYS_CONTEXT` "works much like a bind variable."
- Bypass: "Oracle Database does not protect tables and views that have VPD policies against the `SYS` user and against users who have an out-of-the-box database administrator role."
- **Recommendation**: "Oracle Database release 12c introduced Real Application Security (RAS) to supersede VPD. Oracle recommends that you use RAS for new projects." DDL (TRUNCATE/ALTER) is not filtered.

**Transparent Data Encryption** — [Introduction to Transparent Data Encryption (TDE Guide, 26ai)](https://docs.oracle.com/en/database/oracle/oracle-database/26/dbtde/introduction-to-transparent-data-encryption.html) (n.d.; edition G43027-06 July 2026); same intro text in the [19c Advanced Security Guide page](https://docs.oracle.com/en/database/oracle/oracle-database/19/asoag/introduction-to-transparent-data-encryption.html)
- "TDE enables you to encrypt sensitive data that you store in tables and tablespaces. It also enables you to encrypt database backups ... protect data stored on media (also called data at rest)."
- Column vs tablespace encryption (CONTEXTUAL): column encryption for "credit card and Social Security numbers" but no index range scans / compression interplay; tablespace encryption "useful if your tables contain sensitive data in multiple columns ... allows index range scans"; "`BFILE` data is not encrypted"; "You cannot add salt to indexed columns ... choose the `NO SALT` parameter."
- Key architecture: master key in a keystore (TDE wallet, Oracle Key Vault, OCI Vault); "The TDE master encryption key encrypts ... the tablespace encryption key"; 26ai: default algorithm `AES256`; GOST/SEED removed; `3DES168` "should not be used in new deployments"; `sqlnet.ora` configuration desupported (`WALLET_ROOT`/`TDE_CONFIGURATION` required).

**Data Redaction** — [Introduction to Oracle Data Redaction (Data Redaction Guide, 26ai)](https://docs.oracle.com/en/database/oracle/oracle-database/26/dbred/introduction-to-oracle-data-redaction.html) (n.d.; edition G43026-03 July 2026); detail from the [19c Advanced Security Guide page](https://docs.oracle.com/en/database/oracle/oracle-database/19/asoag/introduction-to-oracle-data-redaction.html)
- "obscure data that is returned from queries without affecting the data directly"; "Unlike data masking ... leaving the data in the database unchanged"; policies "created and applied at the PDB level ... cannot create redaction policies in the CDB root."
- Types: full (NUMBER → 0, char → single space), partial (`***-**-4320`), regular expression, random, nullify, no redaction (testing).
- Caveats (vendor's own): "not designed to prevent data exposure to database users who run ad hoc queries directly against the database"; "the `WHERE` clause can be used in an iterative fashion to infer the actual data"; "Take care ... with applications that perform updates back to the database, because redacted data can be written back."

**Unified auditing** — [Introduction to Auditing (Security Guide, 26ai)](https://docs.oracle.com/en/database/oracle/oracle-database/26/dbseg/introduction-to-auditing.html) (n.d.)
- "Oracle AI Database auditing (unified auditing) is enabled by default"; "Traditional auditing is desupported in Oracle AI Database 26ai. Oracle recommends that you use unified auditing." Trail: `AUDSYS.AUD$UNIFIED` in `SYSAUX`, "allows only `INSERT` activity", exposed via `UNIFIED_AUDIT_TRAIL`.
- Policies via `CREATE AUDIT POLICY` / `AUDIT POLICY` (role `AUDIT_ADMIN`); predefined `ORA_SECURECONFIG` (enabled by default from 12.2) and `ORA_LOGIN_LOGOUT` (enabled by default from 26ai). Best practices (RECOMMENDED): use predefined policies; "collect the amount of information that you need to meet compliance requirements"; archive/purge with `DBMS_AUDIT_MGMT`; separate tablespace; separate `AUDIT_ADMIN` and `AUDIT_VIEWER` duties.

**Flashback, Flashback Data Archive and Temporal Validity** — [Using Oracle Flashback Technology (Database Development Guide, 26ai)](https://docs.oracle.com/en/database/oracle/oracle-database/26/adfns/flashback.html) and [Design Basics — Temporal Validity Support](https://docs.oracle.com/en/database/oracle/oracle-database/26/adfns/design_basics.html) (n.d.; edition G43974-07 July 2026)
- "Oracle Flashback Technology is a group of Oracle Database features that let you view past states of database objects or to return database objects to a previous state without using point-in-time media recovery." Features: Flashback Query (`AS OF`), Version Query (`VERSIONS BETWEEN`, with `VERSIONS_XID`/`VERSIONS_OPERATION`), Transaction Query, Transaction Backout, Flashback Time Travel (Flashback Data Archive), Flashback Table/Drop/Database.
- Undo limitation (MANDATORY to understand): "Setting `UNDO_RETENTION` does not guarantee that unexpired undo data is not discarded"; long-term history needs a Flashback Archive: `CREATE FLASHBACK ARCHIVE DEFAULT fla1 TABLESPACE tbs1 QUOTA 10G RETENTION 1 YEAR;` ... `ALTER TABLE employee FLASHBACK ARCHIVE fla1;`; not allowed on `LONG`, nested tables, temporary/external tables, MVs; "Adding or enabling a constraint fails with ORA-55610"; "wait at least 20 seconds before inserting data and ... up to 5 minutes before using Flashback Query"; archive "can slow down or become unresponsive when its space usage exceeds 90%."
- Temporal Validity (application/valid time): "lets you associate one or more valid time dimensions with a table and have data be visible depending on its time-based validity"; DDL `CREATE TABLE my_emp(empno NUMBER, last_name VARCHAR2(30), start_time TIMESTAMP, end_time TIMESTAMP, PERIOD FOR user_valid_time (start_time, end_time));` queries `SELECT * from my_emp AS OF PERIOD FOR user_valid_time TO_TIMESTAMP('01-Jun-10');` and `VERSIONS PERIOD FOR ... BETWEEN`; `ALTER TABLE my_emp ADD PERIOD FOR user_valid_time;` adds hidden columns; session visibility via `DBMS_FLASHBACK_ARCHIVE.ENABLE_AT_VALID_TIME`. The Design Basics chapter also states "OLTP systems use fully normalized schemas, while data warehouses use denormalized or star schemas."

**Multitenant** — [Introduction to Multitenant Administration](https://docs.oracle.com/en/database/oracle/oracle-database/26/multi/introduction-to-the-multitenant-architecture.html) (n.d.; 26ai)
- MANDATORY architecture: "Starting in Oracle Database 21c, a multitenant container database is the only supported architecture." "A **PDB** is a portable collection of schemas, schema objects, and nonschema objects that appears to an application as a separate database"; `CDB$ROOT`, `PDB$SEED` ("cannot be modified or dropped"), application containers.
- Benefits: "100 PDBs in a single CDB on a single host can share one database instance"; plug/unplug/clone; "easier to apply a patch to one CDB than to 100 databases"; per-PDB flashback/PITR "without affecting other PDBs."
- Users: common users "must begin with ... `c##` or `C##` by default"; "No local user name may begin with the characters `c##`." DDL: `CREATE PLUGGABLE DATABASE hrpdb ADMIN USER dba1 IDENTIFIED BY password;` / `CREATE PLUGGABLE DATABASE salespdb FROM hrpdb;` (The page does not state the max PDBs per CDB.)

**Concurrency / isolation** — [Data Concurrency and Consistency (Concepts, 26ai)](https://docs.oracle.com/en/database/oracle/oracle-database/26/cncpt/data-concurrency-and-consistency.html) (n.d.)
- "Oracle AI Database offers the read committed (default) and serializable isolation levels. Also, the database offers a read-only mode"; "Oracle AI Database *never* permits a dirty read."
- "Oracle AI Database always enforces **statement-level read consistency**"; "A reader never blocks a writer" (except `SELECT ... FOR UPDATE`); "A writer never blocks a reader"; "A writer of a row blocks a concurrent writer of the same row"; "*Oracle AI Database never escalates locks.* Lock escalation greatly increases the probability of deadlocks"; consistency "through undo data." Recommended optimistic update pattern: `UPDATE employees SET email = ?, phone_number = ? WHERE employee_id = ? AND email = ? AND phone_number = ?;`

**Backup and recovery** — [Introduction to Backup and Recovery (Backup and Recovery User's Guide, 26ai)](https://docs.oracle.com/en/database/oracle/oracle-database/26/bradv/introduction-backup-recovery.html) (n.d.)
- "RMAN is the preferred solution for database backup and recovery"; "Physical backups are the foundation of any sound backup and recovery strategy. Logical backups [Data Pump] are a useful supplement ... but are not sufficient protection against data loss without physical backups" (MANDATORY in spirit); incremental backups "store only blocks changed since a previous backup"; Flashback Database "requires that you configure a fast recovery area"; 26ai allows a separate disk location for flashback logging. (ARCHIVELOG requirement for PITR and Data Guard are not on this page — see Gaps.)

### Inferences
- Oracle's docs treat OLTP and DW as different regimes with opposite defaults on constraints (enforced vs `RELY`) and index type (B-tree vs bitmap); the report writer should present these as context-dependent, not contradictory.
- Because Oracle never escalates locks and readers never block writers, Oracle's schema advice is less about lock avoidance (except FK indexes) than SQL Server's; conversely, SQL Server's docs push row versioning (RCSI) as the way to get similar behavior.
- Oracle offers both system-time (Flashback Archive) and application/valid-time (Temporal Validity) history natively; SQL Server docs cover only system-versioned time; MongoDB has only an application-level pattern.

- The 23ai HTML URLs now resolve to 26ai content; I could not verify whether a separately-maintained 23ai HTML set still exists (the 19c set does and matched the 26ai intro text for TDE/Redaction).
- Oracle Concepts "Tables and Table Clusters" chapter (table-level design, column limits, wide tables) was not fetched.
- The backup intro page does not cover ARCHIVELOG mode, incremental level 0/1 or Data Guard; those statements should be sourced from other chapters before being asserted.
- Max PDBs per CDB not confirmed from the page opened.

## Key Question 3 — MongoDB (mongodb.com/docs, 9.0 current): what the official Data Modeling docs prescribe

### Takeaway
MongoDB's official rule is "data that's accessed together should be stored together", decided per access pattern via a four-step process (identify workload → map relationships → apply patterns → create indexes); embedding is bounded by hard limits (16 MiB documents, 100 nesting levels, 64 indexes, 32-field compound index) and by named anti-patterns (unbounded arrays, bloated documents, unnecessary indexes, too many collections, too many `$lookup`s). Schema validation (`$jsonSchema`) is the opt-in integrity mechanism, now with a 9.0 `constraint` level that guarantees every document conforms. Multi-document transactions are explicitly positioned as secondary to schema design, and money must be `Decimal128`, not `double`.

### Cited Findings

**Data modeling principles and embed-vs-reference** — [Data Modeling](https://www.mongodb.com/docs/manual/data-modeling/), [Designing Your Schema](https://www.mongodb.com/docs/manual/data-modeling/schema-design-process/), [Best Practices for Data Modeling](https://www.mongodb.com/docs/manual/data-modeling/concepts/embedding-vs-references/) (all 9.0 Current, n.d.)
- "Data modeling refers to the organization of data within a database and the links between related entities"; flexible model: "Documents within a single collection are not required to have the same set of fields or data types"; "Enforce a fixed structure with schema validation, if needed."
- **Core principle (RECOMMENDED, all MongoDB workloads)**: "A core principle of data modeling in MongoDB is that data that's accessed together should be stored together. You should structure your data model based on your application's data access patterns"; "embedding data allows you to avoid complex joins across multiple collections."
- Process: "Identify your workload ... Map relationships ... Apply design patterns ... Create indexes." Contrast with relational: in relational databases "you must determine a table's schema before inserting data" and often "join several tables."
- Embed when: "has-a or contains relationship", "Your application queries pieces of information together", "data that's often updated together", "data that should be archived at the same time." Reference when: "The child side of the relationship has high cardinality", "Data duplication is too complicated to manage", "The combined size of your data takes up too much memory or transfer bandwidth", "Your embedded data grows without bounds", "Your data is written at different times in a write-heavy workload", "your data can exist by itself without a parent."
- Duplication: "Duplicating data can remove the need to perform joins ... However, frequently updating duplicate data can cause heavy workloads and performance issues"; consistency options "embedding, transactions, and Atlas Database Triggers."
- Atomicity (MANDATORY semantics): "a write operation is atomic on the level of a single document"; "a distributed transaction incurs a greater performance cost over single document writes, and the availability of distributed transactions should not be a replacement for effective schema design."

**Schema design patterns** — [Schema Design Patterns](https://www.mongodb.com/docs/manual/data-modeling/design-patterns/), [Group Data with the Bucket Pattern](https://www.mongodb.com/docs/manual/data-modeling/design-patterns/group-data/bucket-pattern/), [Document and Schema Versioning](https://www.mongodb.com/docs/manual/data-modeling/design-patterns/data-versioning/), [Model Tree Structures](https://www.mongodb.com/docs/manual/applications/data-models-tree-structures/) (9.0, n.d.)
- The current manual lists six pattern groups: Handle Computed Values ("Perform calculations in the database so results are ready"), Group Data ("Group data into series to improve performance and account for outliers" — i.e., bucket + outlier), Polymorphic Data, Document and Schema Versioning, Archive Pattern, Single Collection Pattern. The attribute, extended reference, subset, approximation and preallocation patterns of the older blog-era taxonomy are NOT listed on this page (subset appears inside the unbounded-arrays anti-pattern; see Gaps).
- Bucket: "separates long series of data into distinct objects ... useful when you have similar objects that relate to a central entity, such as stock trades made by a single user"; bucket `_id` = `customerId_firstTradeEpoch`, `count` field caps buckets ("no `history` array contains more than 10 documents") via `updateOne({_id:/^123_/, count:{$lt:10}}, {$push:..., $inc:{count:1}, $setOnInsert:...}, {upsert:true})`; **Tip**: "Time series collections apply the bucket pattern automatically, and are suitable for most applications that involve bucketing time series data."
- Versioning (OPTIONAL/CONTEXTUAL): "By retaining historical versions of documents and schemas, you avoid performance-intensive schema migrations and downtime"; Document Versioning stores "each update in a separate document ... in a separate collection"; Schema Versioning "adds a `schemaVersion` field to tell the application how it should query each document."
- Trees: Parent References, Child References, Array of Ancestors, Materialized Paths ("stores the `_id` of the nodes ancestors or path as a string"), Nested Sets ("optimizes discovering subtrees at the expense of tree mutability").

**Schema anti-patterns** — [Schema Design Anti-Patterns](https://www.mongodb.com/docs/manual/data-modeling/design-antipatterns/), [Avoid Unbounded Arrays](https://www.mongodb.com/docs/manual/data-modeling/design-antipatterns/unbounded-arrays/), [Reduce Bloated Documents](https://www.mongodb.com/docs/manual/data-modeling/design-antipatterns/bloated-documents/), [Remove Unnecessary Indexes](https://www.mongodb.com/docs/manual/data-modeling/design-antipatterns/unnecessary-indexes/) (9.0, n.d.)
- Five named anti-patterns: Unbounded Arrays, Reduce Number of Collections ("too many collections can decrease storage engine performance"), Unnecessary Indexes ("consume additional disk space and can degrade write performance"), Bloated Documents ("excessively large documents ... degrade the performance of your most common queries"), Reduce `$lookup` Operations. Atlas Performance Advisor (M10+) and Compass flag them.
- Unbounded arrays (RECOMMENDED against; MANDATORY ceiling): "if you do not limit the number of elements in an array, your documents might exceed the 16MB BSON document size limit. An unbounded array can strain application resources and decrease index performance." Fixes: subset pattern ("best for when you need quick access to data that is not frequently updated ... duplicates data which causes updates to be expensive") or referencing ("best for ... large or frequently updated datasets ... introduces latency"), joined with `$lookup`.
- Bloated documents: "The working set, consisting of frequently accessed data and indexes, is stored in the RAM allotment ... if documents are too large, the working set might not fit into RAM"; fix: "restructure your schema with smaller documents and use document references to separate fields that aren't returned together."
- Unnecessary indexes: "Creating indexes for every field in a collection can lead to bloated collections and negatively impact write performance"; identify with `db.courses.aggregate([{ $indexStats: {} }])` (`accesses.ops` = 0), then `hideIndex()` before `dropIndexes()`.

**Schema validation** — [Schema Validation](https://www.mongodb.com/docs/manual/core/schema-validation/), [Specify JSON Schema Validation](https://www.mongodb.com/docs/manual/core/schema-validation/specify-json-schema/), [Specify Validation Level for Existing Documents](https://www.mongodb.com/docs/manual/core/schema-validation/specify-validation-level/) (9.0, n.d.)
- "After you establish an application schema, use schema validation to prevent unintended schema changes and data type errors"; "most useful for an established application with a defined data structure"; "By default, MongoDB rejects any insert or update operation that would produce an invalid document."
- Verbatim example: `db.createCollection("students", { validator: { $jsonSchema: { bsonType: "object", title: "Student Object Validation", required: [ "address", "major", "name", "year" ], properties: { name: { bsonType: "string", ... }, year: { bsonType: "int", minimum: 2017, maximum: 3017, ... }, gpa: { bsonType: [ "double" ], ... } } } } })`; "MongoDB supports **draft 4** of JSON Schema"; cannot validate `admin`/`local`/`config` or system collections.
- Levels: `strict` (default) "applies the same validation rules to all document inserts and updates"; `moderate` exempts existing non-conforming documents; **new in 9.0 `constraint`**: "guarantees that every document in the collection satisfies the rules ... You cannot bypass document validation", requires `validationAction` `error` or `errorAndLog`, set via `collMod ... prepareConstraintValidationLevel: true` then `validationLevel: "constraint"`.

**Indexes and the ESR rule** — [The ESR (Equality, Sort, Range) Guideline](https://www.mongodb.com/docs/manual/tutorial/equality-sort-range-guideline/), [Indexing Strategies](https://www.mongodb.com/docs/manual/applications/indexes/) (9.0, n.d.)
- "In most cases, applying the ESR (Equality, Sort, Range) Guideline to arrange the index keys creates a more efficient compound index"; "Ensure that equality fields always come first"; "If avoiding in-memory sorts is critical, place sort fields before range fields (ESR)"; "If your range predicate in the query is very selective, then put it before sort fields (ERS)". Example: query `{directors:"David Lynch", runtime:{$lt:130}}.sort({year:1})` → index `{ directors: 1, year: 1, runtime: 1 }`. `$ne`, `$nin`, `$regex` are range operators; `$in` behaves as equality with `sort()` under 201 elements and as a range at 201+ ("not guaranteed to stay the same for all MongoDB versions").
- Strategy (RECOMMENDED): "Before building indexes, map out your application's queries and the fields they access. Indexes have a performance cost"; "Drop indexes that are no longer used"; "MongoDB only uses one index to fulfill most queries" (except `$or`).

**Transactions** — [Transactions](https://www.mongodb.com/docs/manual/core/transactions/), [Production Considerations](https://www.mongodb.com/docs/manual/core/transactions-production-consideration/) (9.0, n.d.)
- "MongoDB supports multi-document ACID transactions"; "The MongoDB document model supports embedding related data within a single document, which reduces the need for multi-document transactions ... for many scenarios, modeling your data appropriately will minimize the need for distributed transactions."
- MANDATORY limits: standalone deployments unsupported ("must be a multiple node replica set"); "a transaction must have a runtime of less than one minute" (`transactionLifetimeLimitSeconds`, default 60 per [Limits](https://www.mongodb.com/docs/manual/reference/limits/)); no 16 MB total-transaction limit but "each oplog entry still must be within the BSON document size limit of 16MB"; lock wait default 5 ms (`maxTransactionLockRequestTimeoutMillis`); write conflicts abort; cannot write to capped or `system.*` collections; cannot create collections in cross-shard write transactions; "at most one open transaction at a time for a session"; 9.0 adds `maxConcurrentMultiDocumentTransactions` (default 10000).
- Read/write concern: `snapshot` + `w:"majority"` gives a cross-shard-synchronized snapshot; `w:1` "can be rolled back if there is a failover"; "Read operations inside a transaction can return old data ... stale read."

**Sharding / shard key** — [Choose a Shard Key](https://www.mongodb.com/docs/manual/core/sharding-choose-a-shard-key/) (9.0, n.d.)
- "Where possible, choose a shard key with high cardinality"; frequency: skewed values make chunks "a bottleneck"; "A shard key on a value that increases or decreases monotonically is more likely to distribute inserts to a single chunk ... consider using Hashed Sharding"; "consider your most common query patterns and whether a given shard key covers them ... When the queries do not contain the shard key, the queries are broadcast to all shards"; "Starting in MongoDB 5.0, you can change your shard key ... `reshardCollection`"; `refineCollectionShardKey` adds suffix fields; `_id` is immutable. Namespace limit for sharded collections 235 bytes ([Limits](https://www.mongodb.com/docs/manual/reference/limits/)).

**Documents, field naming and hard limits** — [Documents](https://www.mongodb.com/docs/manual/core/document/), [MongoDB Limits and Thresholds](https://www.mongodb.com/docs/manual/reference/limits/) (9.0, n.d.)
- MANDATORY: "The maximum BSON document size is 16 mebibytes"; "no more than 100 levels of nesting"; "The field name `_id` is reserved for use as a primary key; its value must be unique in the collection, is immutable, and may be of any type other than an array or regex"; "Field names cannot contain the `null` character"; "MongoDB 5.0 adds improved support for the use of (`$`) and (`.`) in field names. There are some restrictions"; "Each field name must be unique within the document"; "A single collection can have no more than 64 indexes"; "no more than 32 fields in a compound index"; namespace 255 bytes (235 sharded); a sort can use max 32 keys; Atlas guidance of ≤5,000 collections+indexes on M10, 10,000 on M20/M30, 100,000 on M40+.
- "the fields in a BSON document are ordered ... `{a: 1, b: 1}` is not equal to `{b: 1, a: 1}`"; `_id` always first; default `ObjectId`.

**Monetary data** — [Model Monetary Data](https://www.mongodb.com/docs/manual/tutorial/model-monetary-data/) (9.0, n.d.)
- "The binary-based floating-point arithmetic used by many modern systems (i.e., float, double) is unable to represent exact decimal fractions ... making it unsuitable for monetary arithmetic"; "`decimal128` does not approximate decimal values and is able to provide the exact precision required for working with monetary data"; "Using the decimal type for modeling monetary data is preferred over the Scale Factor method"; example `price: Decimal128("2.099")`; migration `updateMany({price:{$type:"long"}}, {$mul:{price: Decimal128("0.01")}})`; "there is no support for downgrading datafiles containing decimals."

**Backup** — [Backup Methods for a Self-Managed Deployment](https://www.mongodb.com/docs/manual/core/backups/) (9.0, n.d.)
- Methods: Cloud Manager/Ops Manager ("creates snapshots at set intervals and offers point-in-time recovery"; Enterprise), filesystem snapshots ("you must have journaling enabled and the journal must reside on the same logical volume"; sharded clusters: "disable the balancer and capture a snapshot from every shard as well as a config server at approximately the same moment"), `cp`/`rsync` ("must stop all writes"), `mongodump`/`mongorestore` ("tools for backing up and restoring small MongoDB deployments"). Comparison table: only Cloud/Ops Manager offers point-in-time restore and guaranteed sharded-cluster consistency; snapshots and `mongodump` "require write lock" on sharded clusters.

**Release currency** — [Release Notes for MongoDB 9.0](https://www.mongodb.com/docs/manual/release-notes/9.0/): 9.0.0 released Sept 28, 2026; new `constraint` validation level; server validates all ingested BSON by default; time series stored "as a single namespace containing data compressed into buckets"; per-operation memory cap "1 GB or 20% of server memory"; `$function`/`$where` un-deprecated on a WASM engine.

### Inferences
- MongoDB's guidance is the mirror image of relational normalization: default to co-location/duplication, then pull data apart only when the named anti-patterns or hard limits bite. The report should present embedding as a *bounded* default, not an absolute.
- The 9.0 `constraint` validation level narrows the historic gap with relational CHECK/NOT NULL constraints: an enforced, un-bypassable schema is now available on an opt-in basis.
- "Index to the query pattern" is the one principle stated almost identically by all three vendors (SQL Server covering/SARGable guidance, Oracle "queried frequently and return a small percentage", MongoDB "map out your application's queries").

### Gaps
- The current manual's pattern page omits attribute, extended reference, subset (as a standalone page), approximation and preallocation; I found no official 9.0 manual page for them (they may persist only in MongoDB blog/University material, which was out of scope for this pass).
- No official date/time modeling page was fetched (BSON `Date` UTC semantics) — the datetime comparison across engines is incomplete for MongoDB.
- Time series collection details (granularity, `metaField`) were not fetched.
- The sharding page does not state a shard-key size limit; that number should not be asserted.

## Key Question 4 — Universal principles vs engine-specific principles, and explicit conflicts

### Takeaway
Three principles are stated by all three vendors: (1) use exact decimal types for money, (2) design indexes from the query pattern and remove unused ones, (3) replicas/secondaries are not backups and physical/point-in-time backups are mandatory. Everything about *physical* layout (clustered index as table, bitmap/star transformation, embedding) is engine-specific, and the vendors disagree outright on constraint enforcement in warehouses, on whether to normalize by default, and on who can bypass row-level security.

### Cited Findings

**Universal (stated by all three)**
- Exact numeric for money — MANDATORY-by-reasoning in each: SQL Server "Avoid using [money] if your money or currency values are used in calculations. Instead, use the **decimal** data type with at least four decimal places" ([money](https://learn.microsoft.com/en-us/sql/t-sql/data-types/money-and-smallmoney-transact-sql)); Oracle "It is good practice to specify the scale and precision of a fixed-point number column" and prefers `NUMBER` for exact values ([Data Types](https://docs.oracle.com/en/database/oracle/oracle-database/23/sqlrf/Data-Types.html)); MongoDB "float, double ... unsuitable for monetary arithmetic ... `decimal128` ... preferred" ([Model Monetary Data](https://www.mongodb.com/docs/manual/tutorial/model-monetary-data/)).
- Index to the query pattern, keep indexes few and narrow — RECOMMENDED: SQL Server "Avoid over-indexing heavily updated tables and keep indexes narrow" ([Index Design Guide](https://learn.microsoft.com/en-us/sql/relational-databases/sql-server-index-design-guide)); Oracle "The database must update the index when DML occurs ... which creates performance overhead" ([Concepts: Indexes](https://docs.oracle.com/en/database/oracle/oracle-database/26/cncpt/indexes-and-index-organized-tables.html)); MongoDB "Unnecessary indexes consume additional disk space and can degrade write performance" ([Anti-Patterns](https://www.mongodb.com/docs/manual/data-modeling/design-antipatterns/)).
- Replication ≠ backup; physical backups are foundational — MANDATORY: SQL Server "Secondary databases *aren't* backups" ([AG overview](https://learn.microsoft.com/en-us/sql/database-engine/availability-groups/windows/overview-of-always-on-availability-groups-sql-server)); Oracle "Logical backups ... are not sufficient protection against data loss without physical backups" ([Backup intro](https://docs.oracle.com/en/database/oracle/oracle-database/26/bradv/introduction-backup-recovery.html)); MongoDB `mongodump` is for "small MongoDB deployments" and only Ops/Cloud Manager gives PITR ([Backup Methods](https://www.mongodb.com/docs/manual/core/backups/)).
- Declarative integrity where possible — RECOMMENDED: Oracle "use integrity constraints or assertions whenever possible" ([Data Integrity](https://docs.oracle.com/en/database/oracle/oracle-database/23/cncpt/data-integrity.html)); SQL Server "Constraints are rules that the SQL Server Database Engine enforces for you" ([Unique and check constraints](https://learn.microsoft.com/en-us/sql/relational-databases/tables/unique-constraints-and-check-constraints)); MongoDB "use schema validation to prevent unintended schema changes and data type errors" ([Schema Validation](https://www.mongodb.com/docs/manual/core/schema-validation/)) — but MongoDB frames it as opt-in for "an established application."
- Masking/redaction is not a security boundary — both SQL Server DDM ("doesn't protect against malicious intent to infer the underlying data") and Oracle Data Redaction ("the `WHERE` clause can be used in an iterative fashion to infer the actual data") say so in nearly identical terms.
- Surrogate integer keys for dimension tables (DW) — Oracle "Surrogate or artificial keys, usually sequential integers, are recommended for dimension tables" ([DW Logical Design](https://docs.oracle.com/en/database/oracle/oracle-database/26/dwhsg/data-warehouse-logical-design.html)); SQL Server's clustered-key properties produce the same conclusion for all tables.

**Engine-specific**
- Clustered index = table storage (SQL Server only): "With a few exceptions, every table should have a clustered index ... stored as a heap, which is generally not recommended" vs Oracle where heap-organized is the default and IOTs are for "information retrieval, spatial data, and OLAP." MongoDB has no equivalent (documents are stored by `_id` index; `_id` immutable).
- Bitmap indexes + star transformation (Oracle only): "The majority of indexes in a data warehouse should be bitmap indexes"; SQL Server's DW answer is "clustered columnstore indexes would be especially appropriate." MongoDB has no bitmap/columnstore guidance in the pages read.
- Embedding/denormalization by default (MongoDB only): "data that's accessed together should be stored together" vs Oracle "OLTP systems use fully normalized schemas" ([Design Basics](https://docs.oracle.com/en/database/oracle/oracle-database/26/adfns/design_basics.html)).
- Multitenancy: Oracle PDB/CDB is the mandatory architecture ("only supported architecture" since 21c); SQL Server and MongoDB docs model tenancy via RLS (`WHERE TenantId = 42`) or shard keys instead.
- Application-time (valid-time) temporal support: Oracle `PERIOD FOR` only; SQL Server `PERIOD FOR SYSTEM_TIME` only; MongoDB document-versioning pattern only.
- Isolation defaults: SQL Server READ COMMITTED with locks (RCSI on Azure/Fabric); Oracle read committed with MVCC and "never escalates locks"; MongoDB single-document atomicity with opt-in snapshot transactions limited to 60 s.
- Identifier length: SQL Server 128 characters; Oracle 128 bytes (30 bytes below COMPATIBLE 12.2); MongoDB namespace 255 bytes (235 sharded), field names free-form except null/`_id` rules.

**Explicit conflicts between sources (flag for the report)**
1. **Constraint enforcement in warehouses**: Oracle Concepts says enforce constraints "whenever possible" but Oracle's DW Guide says FKs "should be defined as non-enforced conditions" / `RELY DISABLE NOVALIDATE`. SQL Server's docs give no DW exemption. Resolution: context (OLTP vs ETL-controlled DW).
2. **FK indexes**: Oracle "As a rule, foreign keys should be indexed" (lock-avoidance reasoning) vs SQL Server "creating this index isn't required" (merely "often useful"). Stronger in Oracle because unindexed FKs cause child-table locks there.
3. **Cardinality for indexing**: Oracle DW page contains both "Indexes are more beneficial for high cardinality columns" and "a bitmap index can be considered for any non-unique column"; SQL Server "an index might be useful for columns with many distinct data values, but less so for columns with many duplicate values." Resolution: B-tree/rowstore → high cardinality; bitmap → low cardinality (DW, low DML).
4. **GUID primary keys**: SQL Server offers `NEWSEQUENTIALID` to make GUID keys ever-increasing but then warns "If privacy is a concern, don't use this function" and that failover produces "clusters of sequential values"; the Index Design Guide says a `uniqueidentifier` key "doesn't satisfy the ever-increasing property unless the values are generated sequentially." Oracle merely lists UUID as a surrogate option; MongoDB's default `ObjectId` is itself a 12-byte roughly increasing key and `_id` is immutable. Net: SQL Server docs lean toward int/bigint identity; neither vendor bans GUIDs.
5. **Row-level security bypass**: SQL Server "Security policies apply to all users, including dbo users" (but dbo can alter the policy) vs Oracle "does not protect tables and views that have VPD policies against the `SYS` user and against users who have an out-of-the-box database administrator role", and Oracle now recommends RAS over VPD for new projects.
6. **Normalize vs co-locate**: MongoDB "data that's accessed together should be stored together" and "Duplicating data can remove the need to perform joins" vs Oracle 3NF "seeks to minimize data redundancy and avoid anomalies" (with star denormalization only in the DW access layer). Also an intra-MongoDB tension: embedding is bounded by "Avoid Unbounded Arrays" and "Reduce Bloated Documents".
7. **Transactions as a design tool**: MongoDB "the availability of distributed transactions should not be a replacement for effective schema design" vs the relational engines where multi-row transactions are the baseline (SQL Server/Oracle isolation-level pages assume them).
8. **Partitioning for performance**: SQL Server "partitioning rarely improves performance in OLTP systems" vs Oracle "Tables that are greater than 2 GB ... should always be considered as candidates for partitioning" and pruning "can often improve query performance by several orders of magnitude." Both agree manageability is the primary win; Oracle is more bullish on query benefit (DW context).
9. **Generic "best practice" vs vendor**: generic advice "always use the money type / use GUIDs everywhere / always use datetime / mongodump nightly / masking equals security" is contradicted by, respectively, the SQL Server money warning, the uniqueidentifier/NEWSEQUENTIALID caveats, the datetime "avoid for new work" statement, MongoDB's "small deployments" limitation, and both DDM and Data Redaction caveats.

### Inferences
- A cross-engine framework can safely make four items MANDATORY (exact decimal money, declare PK/unique/NOT NULL, physical backups + restore testing, respect hard engine limits) and keep everything else as engine-conditioned RECOMMENDED items with the vendor's reasoning attached.
- The strongest evidence of convergence is MongoDB 9.0's `constraint` validation level and Oracle's `PRECHECK` JSON-schema constraint state: both engines now describe JSON-schema-shaped constraints, which a framework can treat as one "domain integrity" concept across models.

### Gaps
- No vendor page gives an official OLAP-vs-OLTP decision table; the OLTP/DW split above is assembled from scattered statements (SQL Server index guide, Oracle DW guide, MongoDB workload step).
- Lakehouse/streaming applicability is not addressed by any of the pages read (Fabric SQL database and Synapse appear only as moniker notes).
