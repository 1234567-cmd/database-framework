# What Official Vendor and Platform Documentation Prescribes

Research deliverable for the Database Schema Design and Data Engineering Standards Framework (research phase only: no schemas, DDL templates or framework implementation). Evidence baseline: pages opened 2026-11-07, as recorded in the research notes. `CORRECTIONS.md` has been applied and overrides the notes. Updated 2026-11-08 from notes 20 (thin areas), 21 (engine and platform gaps) and 22 (evidence verification) with `verification_results.json`. No new web research was done for the update.

## 0. How to read this file

**Labels.** The labels are this repository's classification. Vendors do not use them.

- **MANDATORY**: an engine-enforced rule or hard limit, or a rule whose violation the source itself ties to a correctness, integrity or contractual failure.
- **RECOMMENDED**: the source advises it (best practice, should, recommend).
- **OPTIONAL/CONTEXTUAL**: the source presents a trade-off or a feature for specific scenarios.

**Workload scope.** Every principle is tagged OLTP, OLAP/warehouse, lakehouse, streaming or all. Document and key-value stores are tagged OLTP with the model in parentheses. These scopes are not interchangeable: a warehouse rule is not an OLTP rule, and a lakehouse layer is not a warehouse model.

**Wording.** Statements are paraphrase unless in quotation marks. Quotation marks appear only around text extracted directly from the page or PDF (curl or pdftotext, recorded in note 21) or confirmed as exact wording in note 22. Findings tagged **[WF]** were read only through a summarizing fetch tool (WebFetch). They stay paraphrase, and their numbers and conditions, the MySQL online DDL matrix above all, must be re-checked against the page before being relied on. Older untagged entries were also read through that tool and remain paraphrase. Short code identifiers are in backticks.

**Citations.** Format is title link, then (date or n.d.; catalog ID where one exists). The date is the page's own date, ms.date or last-updated value. n.d. means the page shows none. PostgreSQL section numbers appear only where note 22 confirmed them for documentation 18 (8.3, 8.14, 9.14). Others remain omitted, because `CORRECTIONS.md` marks several as unconfirmed.

**Source tiers.** Product documentation outranks vendor blogs, wikis and white papers. Lower tiers are named as such where used: PostgreSQL wiki (community-maintained, project-hosted), Databricks, Snowflake and dbt blogs, and the Snowflake 2021 white paper. Inferences are marked **Inference**. The abbreviation n/c means not captured in the notes, which is not evidence that a feature is absent.

## 2. PostgreSQL (baseline 18.6)

### Key prescriptions

**Integrity**

- **RECOMMENDED** | OLTP: every table should have a primary key. PostgreSQL does not enforce this but calls it usually best practice. [PostgreSQL: Constraints](https://www.postgresql.org/docs/current/ddl-constraints.html) (n.d.; PGMY-01)
- **RECOMMENDED** | all: most columns in most designs should be NOT NULL. [PostgreSQL: Constraints](https://www.postgresql.org/docs/current/ddl-constraints.html) (n.d.; PGMY-01)
- **MANDATORY** | all: a CHECK passes when its expression is true or NULL, so CHECK alone does not exclude NULL. [PostgreSQL: Constraints](https://www.postgresql.org/docs/current/ddl-constraints.html) (n.d.; PGMY-01)
- **MANDATORY** | all: CHECK expressions must be immutable and must not depend on other rows or tables. Such a check can appear to work but cannot guarantee the invariant and can break dump and restore. Use UNIQUE, EXCLUDE or FOREIGN KEY. [PostgreSQL: Constraints](https://www.postgresql.org/docs/current/ddl-constraints.html) (n.d.; PGMY-01)
- **RECOMMENDED** | OLTP: choose referential actions by relationship: CASCADE for dependent components, RESTRICT or NO ACTION for independent objects, SET NULL or SET DEFAULT for optional links. [PostgreSQL: Constraints](https://www.postgresql.org/docs/current/ddl-constraints.html) (n.d.; PGMY-01)
- **RECOMMENDED** | OLTP: declare composite foreign key columns NOT NULL, because default MATCH SIMPLE lets a row escape the check if any referencing column is NULL. [PostgreSQL: Constraints](https://www.postgresql.org/docs/current/ddl-constraints.html) (n.d.; PGMY-01)
- **RECOMMENDED** | OLTP: index referencing columns yourself. They are not indexed automatically, and parent DELETE or UPDATE must scan the child. [PostgreSQL: Constraints](https://www.postgresql.org/docs/current/ddl-constraints.html) (n.d.; PGMY-01)
- **OPTIONAL/CONTEXTUAL** | OLTP: use DEFERRABLE where a check must wait for commit. Only UNIQUE, PRIMARY KEY, REFERENCES and EXCLUDE are deferrable; NOT NULL and CHECK always run immediately. NO ACTION can be deferred and RESTRICT cannot. [PostgreSQL: SET CONSTRAINTS](https://www.postgresql.org/docs/current/sql-set-constraints.html) (n.d.); [PostgreSQL: Constraints](https://www.postgresql.org/docs/current/ddl-constraints.html) (n.d.; PGMY-01)
- **OPTIONAL/CONTEXTUAL** | OLTP: use a partial unique index for uniqueness over a subset of rows, `NULLS NOT DISTINCT` to treat NULLs as equal, and EXCLUDE for non-overlap rules. The SQL standard leaves NULL treatment implementation-defined, so portability needs care. [PostgreSQL: Constraints](https://www.postgresql.org/docs/current/ddl-constraints.html) (n.d.; PGMY-01); [PostgreSQL: Partial Indexes](https://www.postgresql.org/docs/current/indexes-partial.html) (n.d.; PERF-08)

**Types**

- **MANDATORY** | all: use `numeric` for money and other exact quantities. Floating-point types are inexact, and numeric arithmetic is much slower than integer or float arithmetic. [PostgreSQL: Numeric Types](https://www.postgresql.org/docs/current/datatype-numeric.html) (n.d.; PGMY-02)
- **RECOMMENDED** | all: avoid the `money` type. It depends on `lc_monetary`, may not reload under a different setting, and carries no currency (the wiki says to use numeric plus a currency column). [PostgreSQL: Monetary Types](https://www.postgresql.org/docs/current/datatype-money.html) (n.d.); [PostgreSQL wiki: Don't Do This](https://wiki.postgresql.org/wiki/Don%27t_Do_This) (2024-11-21; PGMY-10)
- **RECOMMENDED** | all: use types with both date and time when time zones matter, and not `time with time zone`. `timestamp with time zone` is normalized and stored as UTC, and the original zone is not retained. [PostgreSQL: Date/Time Types](https://www.postgresql.org/docs/current/datatype-datetime.html) (n.d.; PGMY-03)
- **RECOMMENDED** | all: use `text` or `varchar` rather than `char(n)`. There is no meaningful performance difference apart from padding and a length check. [PostgreSQL 18, section 8.3: Character Types](https://www.postgresql.org/docs/current/datatype-character.html) (n.d.)
- **RECOMMENDED** | all: prefer `jsonb` over `json` unless legacy key-order assumptions apply. Keep documents reasonably structured and small, because any update takes a row-level lock on the whole row. [PostgreSQL 18, section 8.14: JSON Types](https://www.postgresql.org/docs/current/datatype-json.html) (n.d.; PGMY-04)
- **OPTIONAL/CONTEXTUAL** | all: UUIDs give better uniqueness in distributed systems than per-database sequences; version 4 and time-ordered version 7 can be generated natively (`uuidv7()`, new in 18). [PostgreSQL: UUID Type](https://www.postgresql.org/docs/current/datatype-uuid.html) (n.d.); [PostgreSQL 18, section 9.14: UUID Functions](https://www.postgresql.org/docs/current/functions-uuid.html) (n.d.; PERF-15)
- **OPTIONAL/CONTEXTUAL** | all: enum values can be added and renamed but not removed, and order is fixed without recreating the type. [PostgreSQL: Enumerated Types](https://www.postgresql.org/docs/current/datatype-enum.html) (n.d.)
- **OPTIONAL/CONTEXTUAL** | all: identity columns need a separate PRIMARY KEY or UNIQUE for uniqueness; ALWAYS gives more protection against explicit inserts than BY DEFAULT. The manual states no preference over serial. The wiki does. [PostgreSQL: Identity Columns](https://www.postgresql.org/docs/current/ddl-identity-columns.html) (n.d.); [PostgreSQL wiki: Don't Do This](https://wiki.postgresql.org/wiki/Don%27t_Do_This) (2024-11-21; PGMY-10)
- **OPTIONAL/CONTEXTUAL** | all: generated columns are virtual by default in 18 and cannot be part of a partition key. [PostgreSQL: Generated Columns](https://www.postgresql.org/docs/current/ddl-generated-columns.html) (n.d.)

**Indexes and partitioning**

- **RECOMMENDED** | OLTP: B-tree is the default. Choose hash, GIN, GiST, SP-GiST or BRIN by operator need; BRIN depends on correlation with physical row order. [PostgreSQL: Index Types](https://www.postgresql.org/docs/current/indexes-types.html) (n.d.; PGMY-05)
- **RECOMMENDED** | OLTP: do not replace partitioning or a composite index with many per-category partial indexes. [PostgreSQL: Partial Indexes](https://www.postgresql.org/docs/current/indexes-partial.html) (n.d.; PERF-08)
- **OPTIONAL/CONTEXTUAL** | OLTP: use INCLUDE conservatively, since payload adds bloat and helps little on frequently updated tables. [PostgreSQL: Index-Only Scans and Covering Indexes](https://www.postgresql.org/docs/current/indexes-index-only-scans.html) (n.d.; PERF-07)
- **OPTIONAL/CONTEXTUAL** | OLTP and OLAP/warehouse: partition only when a table would otherwise be very large. The rule of thumb is table size above server memory. [PostgreSQL: Table Partitioning](https://www.postgresql.org/docs/current/ddl-partitioning.html) (n.d.; PGMY-06)
- **RECOMMENDED** | OLTP and OLAP/warehouse: partition on columns most common in WHERE clauses, and so that data removed together sits in one partition. Warehouse workloads can sensibly use more partitions than OLTP. [PostgreSQL: Table Partitioning](https://www.postgresql.org/docs/current/ddl-partitioning.html) (n.d.; PGMY-06)

**Security, concurrency, operations**

- **MANDATORY** | all (multi-user): do not grant CREATE on a schema in `search_path` to mutually untrusting users. CREATE on public is revoked by default from 15. [PostgreSQL: Schemas](https://www.postgresql.org/docs/current/ddl-schemas.html) (n.d.)
- **MANDATORY** | OLTP (when RLS is used): RLS is default-deny once enabled. Superusers and BYPASSRLS roles bypass it, and owners bypass unless FORCE is set. Uniqueness and foreign key checks ignore RLS, which can leak through covert channels. [PostgreSQL: Row Security Policies](https://www.postgresql.org/docs/current/ddl-rowsecurity.html) (n.d.; PGMY-07)
- **RECOMMENDED** | all: use column-level grants and default privileges to narrow access. The older wiki page advises roles over users and a NOLOGIN owner role, and is flagged as dated. [PostgreSQL: Privileges](https://www.postgresql.org/docs/current/ddl-priv.html) (n.d.); [PostgreSQL wiki: Database Schema Recommendations for an Application](https://wiki.postgresql.org/wiki/Database_Schema_Recommendations_for_an_Application) (2016-09-15)
- **MANDATORY** | OLTP (when Repeatable Read or Serializable is used): applications must retry on serialization failure (SQLSTATE 40001). [PostgreSQL: Transaction Isolation](https://www.postgresql.org/docs/current/transaction-iso.html) (n.d.; PGMY-08)
- **RECOMMENDED** | OLTP: declare READ ONLY when possible, and keep transactions no larger than integrity requires. [PostgreSQL: Transaction Isolation](https://www.postgresql.org/docs/current/transaction-iso.html) (n.d.; PGMY-08)
- **MANDATORY** | all (when PITR is used): `wal_level` replica or higher, archive commands must not overwrite and must return zero only on success, and pg_dump cannot serve as the base for PITR. [PostgreSQL: Continuous Archiving and PITR](https://www.postgresql.org/docs/current/continuous-archiving.html) (n.d.; PGMY-11); [PostgreSQL: Backup and Restore](https://www.postgresql.org/docs/current/backup.html) (n.d.)
- **MANDATORY** | OLTP and streaming (logical replication): DDL, sequence data and large objects are not replicated. Tables need a replica identity, usually the primary key, for UPDATE and DELETE. [PostgreSQL: Logical Replication](https://www.postgresql.org/docs/current/logical-replication.html) (n.d.); [PostgreSQL: Logical Replication Restrictions](https://www.postgresql.org/docs/current/logical-replication-restrictions.html) (n.d.)

- **MANDATORY** | OLTP (awareness): "PostgreSQL streaming replication is asynchronous by default." Hot standby data is described as eventually consistent with the primary. [PostgreSQL 18: Log-Shipping Standby Servers](https://www.postgresql.org/docs/current/warm-standby.html) (n.d.; ENG-07)
- **OPTIONAL/CONTEXTUAL** | OLTP: `synchronous_commit` set to `remote_apply` makes each commit wait until the current synchronous standbys report replay, which allows load balancing with causal consistency in simple cases, at the cost of "much larger commit delays". Cascading replication is asynchronous, and synchronous settings do not apply to it. `pg_stat_replication` exposes write, flush and replay lag. [PostgreSQL 18: Log-Shipping Standby Servers](https://www.postgresql.org/docs/current/warm-standby.html) (n.d.; ENG-07)

**PostgreSQL wiki (community, 2024-11-21).** The page itemizes 19 anti-patterns, which the notes miscounted as 22. Relevant RECOMMENDED items: no upper-case names; no BETWEEN on timestamps; no `timestamp` without zone, no `timetz`, no `timestamp(0)`; no `char(n)`; no `varchar(n)` by default; no `money`; no `serial` (use identity); no rules; no table inheritance. [PostgreSQL wiki: Don't Do This](https://wiki.postgresql.org/wiki/Don%27t_Do_This) (2024-11-21; PGMY-10)

### Hard limits (MANDATORY)

- Identifiers: 63 bytes by default; longer names are truncated. Unquoted names fold to lower case, contrary to the SQL standard, and quoting makes a name case-sensitive. Names should be always quoted or never quoted. [PostgreSQL: Identifiers and Key Words](https://www.postgresql.org/docs/current/sql-syntax-lexical.html) (n.d.; PGMY-09) | all
- Character type: `n` up to 10,485,760 characters; strings up to about 1 GB. [PostgreSQL 18, section 8.3: Character Types](https://www.postgresql.org/docs/current/datatype-character.html) (n.d.) | all
- Enum labels: limited to NAMEDATALEN (63 bytes). [PostgreSQL: Enumerated Types](https://www.postgresql.org/docs/current/datatype-enum.html) (n.d.) | all
- Partitioning: unique and primary key constraints must include all partition key columns, and the partition key must have no expressions in that case. No extra columns on partitions. [PostgreSQL: Table Partitioning](https://www.postgresql.org/docs/current/ddl-partitioning.html) (n.d.; PGMY-06) | OLTP and OLAP/warehouse
- Partition count: no hard limit in the notes; planner guidance is up to a few thousand when pruning works. Treat this as guidance, not a limit. [PostgreSQL: Table Partitioning](https://www.postgresql.org/docs/current/ddl-partitioning.html) (n.d.; PGMY-06)
- Foreign keys and partitioned tables: foreign keys may reference partitioned tables from version 12 ("Allow foreign keys to reference partitioned tables") [PostgreSQL 12 Release Notes](https://www.postgresql.org/docs/release/12.0/) (2019-10-03; ENG-08). A unique or primary key on a partitioned table is limited as above ("the constraint's columns must include all of the partition key columns."), so a referenced key on a partitioned parent is limited the same way (**Inference** from the two statements) [PostgreSQL: Table Partitioning](https://www.postgresql.org/docs/current/ddl-partitioning.html) (n.d.; PGMY-06). Whether a partitioned table can hold foreign keys (child side) was not confirmed in current docs. Detaching a partition takes a "SHARE lock" on tables referencing it through foreign keys. | OLTP and OLAP/warehouse

## 3. MySQL (baseline 8.4 LTS, InnoDB)

### Key prescriptions

- **RECOMMENDED** | OLTP: define a primary key on every table, adding an auto-increment column if nothing natural exists. Without one, InnoDB uses the first UNIQUE NOT NULL index or a hidden 6-byte row ID. [MySQL 8.4: Clustered and Secondary Indexes](https://dev.mysql.com/doc/refman/8.4/en/innodb-index-types.html) (n.d.; PGMY-12); [MySQL 8.4: Best Practices for InnoDB Tables](https://dev.mysql.com/doc/refman/8.4/en/innodb-best-practices.html) (n.d.; PGMY-20)
- **RECOMMENDED** | OLTP: keep the primary key short, because its columns are copied into every secondary index. [MySQL 8.4: Clustered and Secondary Indexes](https://dev.mysql.com/doc/refman/8.4/en/innodb-index-types.html) (n.d.; PGMY-12); [MySQL 8.4: Optimizing Data Size](https://dev.mysql.com/doc/refman/8.4/en/data-size.html) (n.d.); [MySQL 8.4: Optimizing InnoDB Queries](https://dev.mysql.com/doc/refman/8.4/en/optimizing-innodb-queries.html) (n.d.)
- **RECOMMENDED** | OLTP: define the primary key in CREATE TABLE. Adding one rebuilds the table, and dropping one requires a table copy. [MySQL 8.4: Online DDL Operations](https://dev.mysql.com/doc/refman/8.4/en/innodb-online-ddl-operations.html) (n.d.; ENG-01)
- **RECOMMENDED** | OLTP and OLAP/warehouse: bulk-load in primary key order, especially for tables larger than the buffer pool. The pages read do not mention UUIDs, random keys or page splits; that argument belongs to non-official sources. [MySQL 8.4: Bulk Data Loading for InnoDB Tables](https://dev.mysql.com/doc/refman/8.4/en/optimizing-innodb-bulk-data-loading.html) (n.d.)
- **MANDATORY** | all: use DECIMAL or NUMERIC for exact values such as monetary data. Default is DECIMAL(10,0). [MySQL 8.4: Fixed-Point Types](https://dev.mysql.com/doc/refman/8.4/en/fixed-point-types.html) (n.d.)
- **MANDATORY** | all (awareness): TIMESTAMP converts to and from UTC using the session zone and ends 2038-01-19; DATETIME does no conversion and runs to year 9999. The manual does not choose between them. [MySQL 8.4: The DATE, DATETIME, and TIMESTAMP Types](https://dev.mysql.com/doc/refman/8.4/en/datetime.html) (n.d.; PGMY-13)
- **RECOMMENDED** | all: write explicit DEFAULT and ON UPDATE clauses for timestamp columns. [MySQL 8.4: Automatic Initialization and Updating for TIMESTAMP and DATETIME](https://dev.mysql.com/doc/refman/8.4/en/timestamp-initialization.html) (n.d.)
- **RECOMMENDED** | all: use utf8mb4. It is the server default, and utf8mb3 is deprecated and expected to be removed. [MySQL 8.4: The utf8mb3 Character Set](https://dev.mysql.com/doc/refman/8.4/en/charset-unicode-utf8mb3.html) (n.d.); [MySQL 8.4: Server Character Set and Collation](https://dev.mysql.com/doc/refman/8.4/en/charset-server.html) (n.d.)
- **RECOMMENDED** | all: use the smallest suitable data types and declare columns NOT NULL where possible. [MySQL 8.4: Optimizing Data Size](https://dev.mysql.com/doc/refman/8.4/en/data-size.html) (n.d.)
- **RECOMMENDED** | OLTP: use identical types and character sets on join columns; mismatched charsets can preclude index use. [MySQL 8.4: How MySQL Uses Indexes](https://dev.mysql.com/doc/refman/8.4/en/mysql-indexes.html) (n.d.); [MySQL 8.4: Best Practices for InnoDB Tables](https://dev.mysql.com/doc/refman/8.4/en/innodb-best-practices.html) (n.d.; PGMY-20)
- **OPTIONAL/CONTEXTUAL** | OLTP versus OLAP/warehouse: keep transactional data in third normal form as the norm, and relax normalization or add summary tables for business intelligence over large tables. [MySQL 8.4: Optimizing Data Size](https://dev.mysql.com/doc/refman/8.4/en/data-size.html) (n.d.)
- **RECOMMENDED** | OLTP: create only needed indexes, and prefer one composite index with the most-used column first over one index per column. [MySQL 8.4: Optimizing Data Size](https://dev.mysql.com/doc/refman/8.4/en/data-size.html) (n.d.); [MySQL 8.4: Optimizing InnoDB Queries](https://dev.mysql.com/doc/refman/8.4/en/optimizing-innodb-queries.html) (n.d.)
- **OPTIONAL/CONTEXTUAL** | all: index JSON via generated columns or multi-valued indexes, since JSON columns cannot be indexed directly. [MySQL 8.4: The JSON Data Type](https://dev.mysql.com/doc/refman/8.4/en/json.html) (n.d.); [MySQL 8.4: Secondary Indexes and Generated Columns](https://dev.mysql.com/doc/refman/8.4/en/create-table-secondary-indexes.html) (n.d.); [MySQL 8.4: CREATE INDEX Statement](https://dev.mysql.com/doc/refman/8.4/en/create-index.html) (n.d.; ENG-05)
- **RECOMMENDED** | all: use lowercase database and table names, and `lower_case_table_names=1` everywhere for InnoDB portability. [MySQL 8.4: Identifier Case Sensitivity](https://dev.mysql.com/doc/refman/8.4/en/identifier-case-sensitivity.html) (n.d.; PGMY-17)
- **OPTIONAL/CONTEXTUAL** | OLTP: plan column additions as INSTANT where allowed, and data type changes as table copies. [MySQL 8.4: Online DDL Operations](https://dev.mysql.com/doc/refman/8.4/en/innodb-online-ddl-operations.html) (n.d.; ENG-01)

## 4. SQL Server (baseline SQL Server 2025, 17.x)

### Key prescriptions

**Keys and indexes**

- **RECOMMENDED** | all, strongest for OLTP: with few exceptions every table should have a clustered index, and a heap is generally not recommended. ## 13. Conflicts between sources, with context

Each conflict is resolved by context where the sources allow it. Where they do not, it is reported as open.

**C1. Ever-increasing keys versus monotonic-key prohibition (scope: OLTP).** SQL Server's clustered key should be ever-increasing to avoid page splits [SQL Server and Azure SQL index architecture and design guide](https://learn.microsoft.com/en-us/sql/relational-databases/sql-server-index-design-guide) (2026-09-14; MSOM-01), and InnoDB favors insertion in primary key order [MySQL 8.4: Bulk Data Loading for InnoDB Tables](https://dev.mysql.com/doc/refman/8.4/en/optimizing-innodb-bulk-data-loading.html) (n.d.). Spanner says not to lead a high-write key with a monotonic column [Spanner: Schema design best practices](https://docs.cloud.google.com/spanner/docs/schema-design) (n.d.; CLOUD-11); DynamoDB and Cosmos DB want even key distribution [DynamoDB: NoSQL design](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/bp-general-nosql-design.html) (n.d.; CLOUD-06); [Cosmos DB: Partitioning and horizontal scaling](https://learn.microsoft.com/en-us/azure/cosmos-db/partitioning-overview) (2026-02-02; CLOUD-20); MongoDB points monotonic shard keys to hashed sharding [MongoDB: Choose a Shard Key](https://www.mongodb.com/docs/manual/core/sharding-choose-a-shard-key/) (n.d.; PERF-30). **Inference** on context: a single-node B-tree benefits from append locality, while range-distributed stores concentrate those appends in one place, so key ordering must be chosen per storage architecture. There is no universal rule.

**C2. Time-ordered UUIDs versus random UUIDs (scope: OLTP).** PostgreSQL offers time-ordered version 7 [PostgreSQL 18, section 9.14: UUID Functions](https://www.postgresql.org/docs/current/functions-uuid.html) (n.d.; PERF-15). Spanner advises version 4 and warns against version 1, which places timestamps in high-order bits [Spanner: Schema design best practices](https://docs.cloud.google.com/spanner/docs/schema-design) (n.d.; CLOUD-11). SQL Server's `NEWSEQUENTIALID` is faster but guessable [SQL Server: NEWSEQUENTIALID](https://learn.microsoft.com/en-us/sql/t-sql/functions/newsequentialid-transact-sql) (2025-10-20). Same cause as C1, with a privacy dimension. No vendor bans UUIDs.

**C3. Enforced constraints, OLTP versus warehouse (scope: OLTP versus OLAP/warehouse).** Oracle Concepts favors constraints wherever possible [Oracle Concepts: Data Integrity](https://docs.oracle.com/en/database/oracle/oracle-database/26/cncpt/data-integrity.html) (n.d.; MSOM-08), while its warehouse guide favors non-enforced foreign keys [Oracle Data Warehousing Guide: Data Warehousing Logical Design](https://docs.oracle.com/en/database/oracle/oracle-database/26/dwhsg/data-warehouse-logical-design.html) (n.d., guide edition 2025-10; MSOM-12). Snowflake standard tables, Databricks and Synapse do not enforce keys [Snowflake: Constraints overview](https://docs.snowflake.com/en/sql-reference/constraints-overview) (n.d.; LAKE-09); [Databricks: Constraints](https://docs.databricks.com/aws/en/tables/constraints) (2026-10-29; LAKE-02); [Azure Synapse: Designing tables](https://learn.microsoft.com/en-us/azure/synapse-analytics/sql-data-warehouse/sql-data-warehouse-tables-overview) (2025-01-22). dbt tests act as the substitute [dbt: Add data tests to your DAG](https://docs.getdbt.com/docs/build/data-tests) (2026-09-16; LAKE-19). Context: controlled ETL and the cost of checks on distributed columnar tables [Oracle Data Warehousing Guide: Optimizations and Techniques](https://docs.oracle.com/en/database/oracle/oracle-database/26/dwhsg/data-warehouse-optimizations-techniques.html) (n.d.); [Snowflake: Constraints overview](https://docs.snowflake.com/en/sql-reference/constraints-overview) (n.d.; LAKE-09). Declared is not enforced, and the two must be tracked separately.

**C4. Foreign key indexing (scope: OLTP).** Oracle says index as a rule, because of child table locks [Oracle Concepts: Data Integrity](https://docs.oracle.com/en/database/oracle/oracle-database/26/cncpt/data-integrity.html) (n.d.; MSOM-08). PostgreSQL says it is often a good idea [PostgreSQL: Constraints](https://www.postgresql.org/docs/current/ddl-constraints.html) (n.d.; PGMY-01). SQL Server says useful but not required [SQL Server: Primary and foreign key constraints](https://learn.microsoft.com/en-us/sql/relational-databases/tables/primary-and-foreign-key-constraints) (2024-07-19; MSOM-02). InnoDB creates the index automatically [MySQL 8.4: FOREIGN KEY Constraints](https://dev.mysql.com/doc/refman/8.4/en/create-table-foreign-keys.html) (n.d.; PGMY-14). Context: the strength tracks each engine's locking and enforcement mechanics.

**C5. Money and float inside dbt (scope: OLAP/warehouse).** The dbt style guide asks for decimal currency [dbt: How we style our dbt models](https://docs.getdbt.com/best-practices/how-we-style/1-how-we-style-our-dbt-models) (2026-09-10; LAKE-16), but the same guide's staging example, confirmed on the page in note 22, computes `( order_total / 100.0 ) :: float as order_total`. This conflicts with the exact-decimal rule stated by PostgreSQL, MySQL, SQL Server, MongoDB and Snowflake [PostgreSQL: Numeric Types](https://www.postgresql.org/docs/current/datatype-numeric.html) (n.d.; PGMY-02); [MySQL 8.4: Fixed-Point Types](https://dev.mysql.com/doc/refman/8.4/en/fixed-point-types.html) (n.d.); [SQL Server: money and smallmoney](https://learn.microsoft.com/en-us/sql/t-sql/data-types/money-and-smallmoney-transact-sql) (2024-05-21; MSOM-03); [MongoDB: Model Monetary Data](https://www.mongodb.com/docs/manual/tutorial/model-monetary-data/) (n.d.); [Snowflake: Numeric data types](https://docs.snowflake.com/en/sql-reference/data-types-numeric) (n.d.). Treat the example as illustrative. It should not be adopted for financial data.

**C6. Key data types in analytics (scope: OLAP/warehouse and lakehouse).** dbt says keys should be string types [dbt: How we style our dbt models](https://docs.getdbt.com/best-practices/how-we-style/1-how-we-style-our-dbt-models) (2026-09-10; LAKE-16), and its Kimball tutorial hashes natural keys [dbt developer blog: Building a Kimball dimensional model with dbt](https://docs.getdbt.com/blog/kimball-dimensional-model) (2023-04-20; DWM-21). Databricks' Data Vault blog recommends hash keys [Databricks blog: Data Vault Prescriptive Guidance](https://www.databricks.com/blog/2022/06/24/prescriptive-guidance-for-implementing-a-data-vault-model-on-the-databricks-lakehouse-platform.html) (2022-06-24). Snowflake strongly recommends numeric join keys and warns that clustering considers only the first five VARCHAR bytes [Snowflake: Performance guide](https://www.snowflake.com/en/developers/guides/performance/) (n.d.; LAKE-14); Oracle recommends sequential integers for dimensions [Oracle Data Warehousing Guide: Data Warehousing Logical Design](https://docs.oracle.com/en/database/oracle/oracle-database/26/dwhsg/data-warehouse-logical-design.html) (n.d., guide edition 2025-10; MSOM-12). Context: hashes favor join-free, parallel loading, and integers favor join and clustering performance [Snowflake blog: Optimizing the Data Vault Architecture](https://www.snowflake.com/en/blog/tips-for-optimizing-the-data-vault-architecture-on-snowflake/) (2020-02-03). This remains a genuine open design fork.

**C7. Normalize versus co-locate (scope: OLTP relational versus OLTP document).** Oracle and Azure describe OLTP as normalized [Oracle Development Guide: Design Basics](https://docs.oracle.com/en/database/oracle/oracle-database/26/adfns/design_basics.html) (n.d., guide edition 2026-07; MSOM-14); [Azure Architecture Center: OLTP](https://learn.microsoft.com/en-us/azure/architecture/data-guide/relational-data/online-transaction-processing) (2026-02-06; CLOUD-16); MongoDB, DynamoDB and Cosmos DB co-locate by access pattern [MongoDB: Data Modeling](https://www.mongodb.com/docs/manual/data-modeling/) (n.d.; MSOM-15); [DynamoDB: NoSQL design](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/bp-general-nosql-design.html) (n.d.; CLOUD-06); [Cosmos DB: Data Modeling](https://learn.microsoft.com/en-us/azure/cosmos-db/nosql/modeling-data) (2026-07-31). Context: a paradigm difference tied to the absence of joins and foreign keys [AWS Well-Architected PERF03-BP01](https://docs.aws.amazon.com/wellarchitected/latest/framework/perf_data_use_purpose_built_data_store.html) (n.d.; CLOUD-01). Embedding remains bounded by document limits [MongoDB: Avoid Unbounded Arrays](https://www.mongodb.com/docs/manual/data-modeling/design-antipatterns/unbounded-arrays/) (n.d.).

**C8. Degree of warehouse denormalization (scope: OLAP/warehouse).** Fabric and Oracle put star schema at the presentation layer [Microsoft Fabric: Dimensional Modeling](https://learn.microsoft.com/en-us/fabric/data-warehouse/dimensional-modeling-overview) (2025-04-06); [Oracle Data Warehousing Guide: Data Warehousing Logical Design](https://docs.oracle.com/en/database/oracle/oracle-database/26/dwhsg/data-warehouse-logical-design.html) (n.d., guide edition 2025-10; MSOM-12). BigQuery prefers nested fields for hierarchies but concedes stars are typically optimized [BigQuery: Use nested and repeated fields](https://docs.cloud.google.com/bigquery/docs/best-practices-performance-nested) (n.d.; CLOUD-12). dbt prefers wider marts than Kimball [dbt: Marts](https://docs.getdbt.com/best-practices/how-we-structure/4-marts) (2026-07-07) and reverses this under its Semantic Layer. Snowflake says there is no universal degree [Snowflake: Performance guide](https://www.snowflake.com/en/developers/guides/performance/) (n.d.; LAKE-14). No source mandates one big table.

**C9. Partition key in every unique key is not universal (scope: OLTP and OLAP/warehouse).** PostgreSQL and MySQL require it [PostgreSQL: Table Partitioning](https://www.postgresql.org/docs/current/ddl-partitioning.html) (n.d.; PGMY-06); [MySQL 8.4: Partitioning Keys, Primary Keys, and Unique Keys](https://dev.mysql.com/doc/refman/8.4/en/partitioning-limitations-partitioning-keys-unique-keys.html) (n.d.), and SQL Server requires the partitioning column in clustered and unique nonclustered keys [SQL Server: Partitioned tables and indexes](https://learn.microsoft.com/en-us/sql/relational-databases/partitions/partitioned-tables-and-indexes) (2025-12-29; PERF-03). Oracle allows a global index for a unique key without the partitioning key [Oracle VLDB and Partitioning Guide: Partitioning Concepts](https://docs.oracle.com/en/database/oracle/oracle-database/26/vldbg/partition-concepts.html) (n.d., guide edition 2026-01; MSOM-11). The notes' claim of universality rests only on PostgreSQL and MySQL.

**C10. Partitioning benefit (scope: OLTP versus OLAP/warehouse).** SQL Server says it rarely helps OLTP [SQL Server: Partitioned tables and indexes](https://learn.microsoft.com/en-us/sql/relational-databases/partitions/partitioned-tables-and-indexes) (2025-12-29; PERF-03); Oracle is more positive, citing a 2 GB candidate threshold and large pruning gains [Oracle VLDB and Partitioning Guide: Partitioning Concepts](https://docs.oracle.com/en/database/oracle/oracle-database/26/vldbg/partition-concepts.html) (n.d., guide edition 2026-01; MSOM-11); PostgreSQL suggests a size above memory [PostgreSQL: Table Partitioning](https://www.postgresql.org/docs/current/ddl-partitioning.html) (n.d.; PGMY-06). Databricks and Fabric move away from partitioning for new tables [Databricks: Use liquid clustering](https://docs.databricks.com/aws/en/delta/clustering) (2026-11-02; LAKE-03); [Microsoft Fabric: Medallion Lakehouse Architecture](https://learn.microsoft.com/en-us/fabric/onelake/onelake-medallion-lakehouse-architecture) (2026-02-12; CLOUD-21), while BigQuery encourages it [BigQuery: Schema and data transfer overview](https://docs.cloud.google.com/bigquery/docs/migration/schema-data-overview) (n.d.). Context: engine and workload differ. These thresholds must not be merged into one number.

**C11. String sizing (scope: all).** PostgreSQL finds no performance reason for declared lengths, and the wiki opposes `varchar(n)` by default [PostgreSQL 18, section 8.3: Character Types](https://www.postgresql.org/docs/current/datatype-character.html) (n.d.); [PostgreSQL wiki: Don't Do This](https://wiki.postgresql.org/wiki/Don%27t_Do_This) (2024-11-21; PGMY-10). MySQL advises the smallest types [MySQL 8.4: Optimizing Data Size](https://dev.mysql.com/doc/refman/8.4/en/data-size.html) (n.d.). Context: MySQL index prefix limits and row formats make declared size matter [MySQL 8.4: CREATE INDEX Statement](https://dev.mysql.com/doc/refman/8.4/en/create-index.html) (n.d.; ENG-05); [MySQL 8.4: Online DDL Operations](https://dev.mysql.com/doc/refman/8.4/en/innodb-online-ddl-operations.html) (n.d.; ENG-01). Snowflake precision does not affect storage at all [Snowflake: Numeric data types](https://docs.snowflake.com/en/sql-reference/data-types-numeric) (n.d.).

**C12. Time zone storage (scope: all).** PostgreSQL normalizes to UTC and drops the zone [PostgreSQL: Date/Time Types](https://www.postgresql.org/docs/current/datatype-datetime.html) (n.d.; PGMY-03). MySQL TIMESTAMP converts via UTC with a 2038 ceiling [MySQL 8.4: The DATE, DATETIME, and TIMESTAMP Types](https://dev.mysql.com/doc/refman/8.4/en/datetime.html) (n.d.; PGMY-13). SQL Server offers `datetimeoffset` for global applications [SQL Server: datetime](https://learn.microsoft.com/en-us/sql/t-sql/data-types/datetime-transact-sql) (2026-06-29). Oracle can store the zone or normalize to the database zone [Oracle SQL Reference: Data Types](https://docs.oracle.com/en/database/oracle/oracle-database/26/sqlrf/Data-Types.html) (n.d.; MSOM-10). Snowflake notes that TZ types hurt pruning [Snowflake: Performance guide](https://www.snowflake.com/en/developers/guides/performance/) (n.d.; LAKE-14). dbt requires UTC by naming convention [dbt: How we style our dbt models](https://docs.getdbt.com/best-practices/how-we-style/1-how-we-style-our-dbt-models) (2026-09-10; LAKE-16). UTC-normalized instants are common, but the type semantics are not interchangeable. The PostgreSQL wiki is stricter than the manual here [PostgreSQL wiki: Don't Do This](https://wiki.postgresql.org/wiki/Don%27t_Do_This) (2024-11-21; PGMY-10); [PostgreSQL: Date/Time Types](https://www.postgresql.org/docs/current/datatype-datetime.html) (n.d.; PGMY-03).

**C13. Row-level security strength (scope: OLTP).** SQL Server policies apply to all users including dbo [SQL Server: Row-level security](https://learn.microsoft.com/en-us/sql/relational-databases/security/row-level-security) (2025-09-11; MSOM-05); Oracle VPD does not bind SYS or DBA roles and is superseded by RAS for new work [Oracle Security Guide: About Virtual Private Database](https://docs.oracle.com/en/database/oracle/oracle-database/26/dbseg/oracle-virtual-private-database.html) (n.d., guide edition 2026-07; MSOM-13); PostgreSQL superusers bypass and owners may [PostgreSQL: Row Security Policies](https://www.postgresql.org/docs/current/ddl-rowsecurity.html) (n.d.; PGMY-07). Azure notes that many multitenant solutions avoid RLS [Azure Architecture Center: Storage and Data in Multitenant Solutions](https://learn.microsoft.com/en-us/azure/architecture/guide/multitenant/approaches/storage-data) (2026-08-21; CLOUD-18). RLS must be evaluated per engine.

**C14. Schema-on-write at ingestion (scope: lakehouse versus OLAP/warehouse).** Databricks advises string, VARIANT or binary in bronze [Databricks: Medallion lakehouse architecture](https://docs.databricks.com/aws/en/lakehouse/medallion) (2026-10-29; LAKE-01), and Snowflake VARIANT when patterns are unknown [Snowflake: Considerations for data stored in VARIANT](https://docs.snowflake.com/en/user-guide/semistructured-considerations) (n.d.). Azure's OLAP trait table states schema-on-write [Azure Architecture Center: OLAP](https://learn.microsoft.com/en-us/azure/architecture/data-guide/relational-data/online-analytical-processing) (2025-04-11). Context: typing is deferred to silver or staging, and the raw layer is not a warehouse model. The Lakehouse paper concedes some loss of data independence [Lakehouse paper, CIDR](https://www.cidrdb.org/cidr2021/papers/cidr2021_paper17.pdf) (2021-01; LAKE-07).

**C15. dbt contracts versus platform docs (scope: OLAP/warehouse and lakehouse).** dbt says CHECK is not definable on most warehouse adapters [dbt: Model contracts](https://docs.getdbt.com/docs/mesh/govern/model-contracts) (2026-10-29; LAKE-17), while Snowflake and Databricks enforce CHECK at the platform [Snowflake: Constraints overview](https://docs.snowflake.com/en/sql-reference/constraints-overview) (n.d.; LAKE-09); [Databricks: Constraints](https://docs.databricks.com/aws/en/tables/constraints) (2026-10-29; LAKE-02). The adapter-by-adapter table could not be read. Platform docs are authoritative for enforcement, and the dbt statement concerns what contracts can express.

**C16. Medallion status (scope: lakehouse).** Fabric recommends it [Microsoft Fabric: Medallion Lakehouse Architecture](https://learn.microsoft.com/en-us/fabric/onelake/onelake-medallion-lakehouse-architecture) (2026-02-12; CLOUD-21); Databricks recommends it but says it is not required [Databricks: Medallion lakehouse architecture](https://docs.databricks.com/aws/en/lakehouse/medallion) (2026-10-29; LAKE-01); Google calls it common [Google Cloud Lakehouse: Key concepts](https://docs.cloud.google.com/lakehouse/docs/key-concepts) (n.d.; CLOUD-15). Treat it as a RECOMMENDED pipeline quality topology, not a mandate and not a data model.

**C17. Clustering guidance over time (scope: lakehouse).** The 2022 Databricks blog recommends Z-order on keys [Databricks blog: Data Modeling Best Practices](https://www.databricks.com/en/blog/data-modeling-best-practices-implementation-modern-lakehouse) (2022-10-20). 2026 docs say liquid clustering replaces ZORDER and is incompatible with it [Databricks: Use liquid clustering](https://docs.databricks.com/aws/en/delta/clustering) (2026-11-02; LAKE-03). Temporal conflict: use the 2026 docs. The Z-order advice in the 2022 Data Vault blog is likewise legacy [Databricks blog: Data Vault Prescriptive Guidance](https://www.databricks.com/blog/2022/06/24/prescriptive-guidance-for-implementing-a-data-vault-model-on-the-databricks-lakehouse-platform.html) (2022-06-24).

**C18. Naming (scope: all).** MySQL's optimization page suggests short unprefixed column names under 18 characters [MySQL 8.4: Optimizing Data Size](https://dev.mysql.com/doc/refman/8.4/en/data-size.html) (n.d.); Oracle wants full descriptive names and dbt no abbreviations [Oracle SQL Reference: Database Object Names and Qualifiers](https://docs.oracle.com/en/database/oracle/oracle-database/23/sqlrf/Database-Object-Names-and-Qualifiers.html) (n.d.); [dbt: How we style our dbt models](https://docs.getdbt.com/best-practices/how-we-style/1-how-we-style-our-dbt-models) (2026-09-10; LAKE-16). dbt's style guide says plural, while its own Kimball tutorial uses singular `dim_product` [dbt developer blog: Building a Kimball dimensional model with dbt](https://docs.getdbt.com/blog/kimball-dimensional-model) (2023-04-20; DWM-21). PostgreSQL's manual and SQL Server publish rules, not conventions [PostgreSQL: Identifiers and Key Words](https://www.postgresql.org/docs/current/sql-syntax-lexical.html) (n.d.; PGMY-09); [SQL Server: Database identifiers](https://learn.microsoft.com/en-us/sql/relational-databases/databases/database-identifiers) (2026-04-08).

**C19. Single-table design (scope: OLTP key-value).** DynamoDB's general page says as few tables as possible [DynamoDB: NoSQL design](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/bp-general-nosql-design.html) (n.d.; CLOUD-06), while its foundations page lists reasons for multiple tables [DynamoDB: Data Modeling foundations](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/data-modeling-foundations.html) (n.d.; CLOUD-07). Treat as contextual.

**C20. Bitmap and cardinality (scope: OLAP/warehouse versus OLTP).** Oracle's warehouse page favors bitmap indexes for low-cardinality columns but also carries a general statement that indexes help high-cardinality columns [Oracle Data Warehousing Guide: Optimizations and Techniques](https://docs.oracle.com/en/database/oracle/oracle-database/26/dwhsg/data-warehouse-optimizations-techniques.html) (n.d.). Context: B-tree and rowstore prefer high cardinality [SQL Server and Azure SQL index architecture and design guide](https://learn.microsoft.com/en-us/sql/relational-databases/sql-server-index-design-guide) (2026-09-14; MSOM-01), while bitmap prefers low cardinality under low DML.

**C21. Identity versus serial, manual versus wiki (scope: all).** The PostgreSQL manual is neutral and the wiki says to avoid serial [PostgreSQL: Identity Columns](https://www.postgresql.org/docs/current/ddl-identity-columns.html) (n.d.); [PostgreSQL wiki: Don't Do This](https://wiki.postgresql.org/wiki/Don%27t_Do_This) (2024-11-21; PGMY-10). Attribute the preference to the wiki.

**C22. Per-tenant tables (scope: OLTP SaaS).** Azure calls per-tenant tables an anti-pattern [Azure Architecture Center: Storage and Data in Multitenant Solutions](https://learn.microsoft.com/en-us/azure/architecture/guide/multitenant/approaches/storage-data) (2026-08-21; CLOUD-18). The current AWS SaaS Lens defines bridge per service [AWS SaaS Lens: Silo, Pool, and Bridge Models](https://docs.aws.amazon.com/wellarchitected/latest/saas-lens/silo-pool-and-bridge-models.html) (2023-04-04; CLOUD-03). An older AWS description of bridge as per-tenant tables exists only in search snippets of retired whitepapers (unverified), so it is not treated as current guidance. Snowflake's object-per-tenant model is an analytics-platform pattern with a stated scale ceiling [Snowflake white paper: Design Patterns for Multi-Tenant Applications](https://www.snowflake.com/wp-content/uploads/2021/10/Design-Patterns-for-Building-Multi-Tenant-Applications-on-Snowflake.pdf) (2021; LAKE-13).

**C23. NULL in UNIQUE (scope: all).** SQL Server allows one NULL per column in a UNIQUE constraint [WF] [SQL Server: Unique constraints and check constraints](https://learn.microsoft.com/en-us/sql/relational-databases/tables/unique-constraints-and-check-constraints) (2023-12-29; ENG-10). MySQL unique indexes permit multiple NULLs [WF] [MySQL 8.4: CREATE INDEX Statement](https://dev.mysql.com/doc/refman/8.4/en/create-index.html) (n.d.; ENG-05). Oracle applies a composite-specific rule [WF] [Oracle SQL Reference: constraint](https://docs.oracle.com/en/database/oracle/oracle-database/23/sqlrf/constraint.html) (n.d., page reports 26; ENG-15). PostgreSQL treats NULLs as distinct unless `NULLS NOT DISTINCT` is set [PostgreSQL: Constraints](https://www.postgresql.org/docs/current/ddl-constraints.html) (n.d.; PGMY-01). A portable uniqueness rule cannot assume one behaviour.

**C24. Redshift isolation names (scope: OLAP/warehouse).** Redshift calls both SNAPSHOT and SERIALIZABLE "serializable isolation levels", yet the same page says only SERIALIZABLE prevents write-skew anomalies [Redshift: Isolation Levels](https://docs.aws.amazon.com/redshift/latest/dg/c_serial_isolation.html) (n.d.; ENG-22). Do not treat the shared label as a guarantee.

**C25. MySQL Group Replication default consistency (scope: OLTP).** The consistency guarantees page does not state the default and describes EVENTUAL as the historic behaviour, while the variables page gives BEFORE_ON_PRIMARY_FAILOVER [WF] [MySQL 8.4: SHOW REPLICA STATUS](https://dev.mysql.com/doc/refman/8.4/en/show-replica-status.html) (n.d.; ENG-02). The variables page is used; re-check against the manual.

**C26. `datetimeoffset` and daylight saving (scope: all).** The property table says daylight saving aware = No, while the prose says the offset is assumed DST aware [WF] [SQL Server: datetimeoffset](https://learn.microsoft.com/en-us/sql/t-sql/data-types/datetimeoffset-transact-sql?view=sql-server-ver17) (2025-08-28; ENG-09). Treat the type as storing a fixed offset. `AT TIME ZONE` was not opened.

**C27. Metric Views status (scope: lakehouse).** The last release-note status for the whole feature is Public Preview, but the current page has no preview label, and sub-features differ [Databricks: Unity Catalog metric views](https://docs.databricks.com/aws/en/uc-semantics/metric-views) (2026-10-29; ENG-28). Status is unresolved; do not state GA.

**C28. UNIQUE status on Databricks (scope: lakehouse).** The constraints page lists UNIQUE as Public Preview [Databricks: Constraints](https://docs.databricks.com/aws/en/tables/constraints) (2026-10-29; LAKE-02), while the RELY page supports UNIQUE from DBR 18.2 with no preview label [Databricks: Optimize queries with RELY](https://docs.databricks.com/aws/en/sql/user/queries/query-optimization-constraints) (2026-10-26; ENG-29). **Inference**: RELY support does not by itself establish that UNIQUE is GA.
